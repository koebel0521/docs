## 1. 現況

| 項目 | 現況 |
| --- | --- |
| 登入方式 | 只有帳號＋密碼。Gate 收 `LoginRequest`，轉 Central；Central 以 bcrypt 驗密碼（`cmd/central/internal/flow/login/`） |
| 帳號規則 | `pkg/accountrule`：帳號最長 100 字、可見字元、首尾無空白，註冊時另擋不可見字元 |
| 角色編號 | Central `user` 表配發 `player_id`，以 `account` 查詢 |
| 好友系統 | 伺服器沒有。名詞定義中掠奪配對已提到「好友或陌生人類別」，好友資料將影響配對 |
| 玩家名字 | 伺服器沒有名字欄位 |
| 敏感詞過濾 | 伺服器沒有 |
| 帳號清除 | `accountrule.PurgeAfter`：360 天無活動由 Central 每日清除 |

## 2. FB 能給什麼、不能給什麼

先跟企劃對齊預期：

| 企劃可能以為 | 實際上 |
| --- | --- |
| 拿得到玩家所有 FB 好友 | **拿不到。** `/me/friends` 只回傳「也用 FB 登入過這款遊戲、而且有同意分享好友清單」的人 |
| 可以列出沒玩的好友來邀請 | **不行。** 邀請要用 FB 的 Game Request 或分享功能，是另一個功能 |
| 串好就能上線 | 讀好友的權限 `user_friends` 要送 Meta 審核（App Review），還要做公司驗證，**要排時程** |
| iPhone、Android 都一樣 | iPhone 玩家拒絕「允許追蹤」（ATT）時，FB SDK 改走 Limited Login，伺服器無法自己查好友（見第 9 節） |
| FB 使用者 ID 全公司通用 | FB 給的是 App-scoped ID（ASID），每個 App 不同。多款遊戲要互通時要改用 `token_for_business` |

結論：**FB 好友功能＝自動把也在玩的 FB 朋友加成遊戲好友**，不是拉新工具。

## 3. 整體架構

```text
 ┌────────┐   1.FB 登入     ┌──────────┐
 │ Client │ ─────────────▶ │ Facebook │   Client 用 FB SDK 拿到 token
 │        │ ◀───────────── │          │
 └────────┘   token         └──────────┘
     │                           ▲
     │ 2.帶 token 登入             │ 3.問 FB：token 是真的嗎？是誰？
     ▼                           │
 ┌────────┐ ────────────────────┘
 │  Gate  │  驗證 token（打 FB HTTP，有逾時、限流、斷路器）
 └────────┘
     │ 4.已驗證：「這是 facebook 使用者 X」
     ▼
 ┌─────────┐   查／建    ┌──────────────────────────┐
 │ Central │ ─────────▶ │ Central MySQL             │
 │         │            │  user（既有，加名字欄位）     │
 │         │            │  user_identity（新）        │
 │         │            │  friend（新）               │
 │         │            │  friend_sync（新）          │
 │         │            │  name_history（新）         │
 └─────────┘            └──────────────────────────┘
     │ 5.照原本流程轉 World
     ▼
 ┌────────┐
 │ World  │
 └────────┘

 登入完成後，背景另外跑：
 Central 好友同步工作 ──▶ Facebook /me/friends ──▶ 寫 friend 表
```

分工理由：

- **Gate 驗 token。** 打 FB 要等約 0.1～0.3 秒。Gate 可以開多台分攤；放 Central 會卡住登入的帳號鎖，登入量大時塞車。
- **Central 只收已驗證的身分。** Gate 與 Central 之間是已驗證的 S2S 連線（見 [S2S 身份驗證](../../30-部署與開發/S2S身份驗證.md)），Central 相信 Gate 給的 `provider + uid`。
- **好友同步不擋登入。** 抓好友要多打幾次 FB，慢或失敗都不能讓玩家進不了遊戲。
- **不用 FB 官方 Go SDK。** 驗證只需要幾個 HTTP 呼叫，直接用 `net/http`。驗 Limited Login 的 JWT 若專案還沒有 JWT 庫，新增依賴前先確認（依 AGENTS.md）。

## 4. 身分模型與 playerID 不衝突的保證

### 4.1 核心規則

**`player_id` 永遠由 Central 自己配發。任何平台的外部 ID 都不當 `player_id`。**

```text
外部身分（不可信、各家格式不同）          內部身分（我方唯一）
facebook / fb_123     ──┐
google   / 1098...    ──┼──▶ user_identity ──▶ player_id = 1001
apple    / 000.abc..  ──┤      （對照表）
password / alice      ──┘
```

- `player_id` 沿用現有 `store.Create` 的自增配發，所有登入方式共用同一個號碼池。
- 外部 ID 只存在 `user_identity.provider_uid`，和 `player_id` 是兩個欄位、兩個命名空間，不可能撞號。
- 外部 ID 之間的衝突用複合主鍵 `(provider, provider_uid)` 解決：
  - Google 的 `12345` 與 FB 的 `12345` 是兩列，不衝突。
  - 同一個 FB 帳號只能出現一次，由 DB 保證，不靠程式碼檢查。
- 唯一鍵 `(player_id, provider)`：一個角色每個平台最多綁一個帳號。

### 4.2 與現有帳密帳號的關係

**不要**把 FB 帳號寫成 `user.account = "fb_123"`。玩家可以自己註冊一個叫 `fb_123` 的帳密帳號，搶走或卡住別人的 FB 身分。

| | A. 帳密也進 identity 表（建議） | B. 帳密留在 `user.account` |
| --- | --- | --- |
| 做法 | 遷移時把既有 `account` 寫成 `provider=password` 的列 | `user.account` 不動，社群登入另走 identity 表 |
| 優點 | 所有登入方式一致，加新平台零改動 | 不用遷移舊資料 |
| 缺點 | 要一次性遷移、登入查詢路徑要改 | 兩套查詢路徑長期並存 |

選 B 也安全，前提是社群登入的新玩家 `user.account` 填內部保留值，且這個值不可能被帳密註冊撞到（例如加上 `accountrule.Registrable` 會拒絕的字元，或改為可為 NULL 的欄位）。

### 4.3 以後加其他社群平台

加一個平台只需要：

1. `provider` 多一個字串值（`google`、`apple`、`line`…）。
2. Gate 加一個該平台的 token 驗證器。
3. 登入訊息的 `oneof credential` 多一個分支。

表結構、`player_id`、登入收尾（`completeLogin`）完全不用動。

### 4.4 合併規則

- **不自動合併。** 同一個人用 FB 和 Google 各登入一次，會是兩個角色。
- 合併只能走「已登入的角色主動綁定另一平台」，而且對方身分已綁別的角色時直接拒絕。
- **Email 相同不能當合併依據。** Apple 可以隱藏信箱，各家 email 驗證強度不同，用 email 合併會被拿來搶帳號。

## 5. 流程：FB 登入

```text
玩家按「FB 登入」
   │
   ▼
Client 呼叫 FB SDK ──▶ FB 授權畫面（public_profile + user_friends）
   │
   ▼
拿到 FB token
   │
   ▼
Client 送 LoginRequest { facebook_token: "..." } 給 Gate
   │
   ▼
Gate：同來源登入太頻繁？ ──是──▶ 回「請稍後再試」
   │否
   ▼
Gate 問 FB：GET /debug_token?input_token=<token>&access_token=<app token>
   │
   ├─ FB 沒回應／逾時 ──────────▶ 回「服務暫時無法使用」（密碼登入不受影響）
   ├─ token 無效／過期 ─────────▶ 回「FB 登入失敗，請重新登入」
   ├─ token 是別的 App 發的 ────▶ 回「FB 登入失敗」（防止拿別家 App 的 token 冒充）
   │
   ▼ 驗證通過：檢查 app_id、is_valid、user_id、expires_at，得到 fb_123
Gate 送給 Central：provider=facebook, uid=fb_123
   │
   ▼
Central 取帳號鎖（key = facebook:fb_123），查 user_identity
   │
   ├─ 有 ──▶ 拿到 player_id ────────────┐
   │                                   │
   └─ 沒有 ──▶ 同一筆交易：               │
              建 user（預設名、好友碼）    │
              寫 user_identity           │
                                       ▼
                      走原本的登入收尾（completeLogin）
                      轉 World、寫路由快取
                                       │
                                       ▼
                                 玩家進入遊戲
                                       │
                                       ▼
                        背景觸發好友同步（第 7 節）
```

重點：

- **同一個 FB 帳號同時登兩次：** 沿用現有帳號鎖，鎖的 key 改成 `provider:uid`，不會建出兩個角色。
- **建角色和寫 `user_identity` 同一筆交易：** 中途失敗不會留下沒有身分對照的孤兒角色。
- **token 只用一次就丟：** Gate 驗完後只把 token 交給好友同步工作使用，不寫進資料庫。

## 6. 流程：既有角色綁定、解除綁定

### 6.1 綁定

很多玩家先用帳密或遊客玩，之後才綁 FB。

```text
玩家已登入（player_id = 1001），在設定頁按「綁定 FB」
   │
   ▼
Client 走 FB SDK 拿到 token
   │
   ▼
送 BindRequest { facebook_token } ──▶ Gate 驗證（同第 5 節）
   │
   ▼ 得到 fb_123
Central 查 user_identity：fb_123 已經綁人了嗎？
   │
   ├─ 沒綁 ──────────────▶ 寫入 (facebook, fb_123, 1001) ──▶ 成功，觸發好友同步
   │
   ├─ 已綁 1001 自己 ─────▶ 直接回成功（重複按不算錯）
   │
   └─ 已綁別人（例 2002）─▶ 回「這個 FB 已綁定其他角色」
                            不自動合併（牽涉道具、進度，風險太大）

1001 已經綁了另一個 FB（fb_999）
   └──▶ 回「請先解除綁定」
```

### 6.2 解除綁定

```text
玩家按「解除 FB 綁定」
   │
   ▼
解除後還有其他登入方式嗎？（密碼或其他平台）
   │
   ├─ 沒有 ──▶ 拒絕：「請先設定其他登入方式」（避免解完就登不進來）
   │
   ▼ 有
刪 user_identity (facebook, *, 1001)
清 1001 所有 facebook 來源的好友標記（第 7.3 節規則）
```

## 7. 流程：FB 好友同步

### 7.1 主流程

```text
觸發：FB 登入成功／綁定 FB 成功
   │
   ▼
friend_sync.last_synced_at 在 24 小時內？ ──是──▶ 跳過
   │否
   ▼
用登入當下的 token 呼叫 GET /me/friends（分頁抓完）
   │
   ├─ 失敗 ──▶ 記日誌，放棄這次；下次登入再試（不影響遊戲）
   │
   ▼ 得到 FB 好友 ID：[fb_200, fb_300, fb_400]
   │   （一定都是「也玩這遊戲、也同意分享」的人）
   ▼
查 user_identity 換成 player_id：
   fb_200 → 2002
   fb_300 → 3003
   fb_400 → 查不到（玩過但帳號已清除）→ 忽略
   │
   ▼
和目前 facebook 來源的好友比對：
   │
   ├─ 新出現（2002、3003）
   │     └─▶ 寫雙向：1001→2002、2002→1001、1001→3003、3003→1001
   │         source_mask 加上 FACEBOOK
   │
   └─ 原本有、這次沒有（例 5005，FB 上解除好友）
         └─▶ 拿掉 1001↔5005 的 FACEBOOK 位元（第 7.3 節）
   │
   ▼
更新 friend_sync.last_synced_at
```

### 7.2 為什麼雙向一起寫

```text
A 先玩，A 同步時 B 還沒玩 → A 的好友沒有 B
B 後來加入，B 同步時抓到 A
   └─▶ 同時寫 B→A 和 A→B
       A 不用等自己下次登入，馬上看得到 B
```

FB 好友關係本來就是雙向的，所以可以直接寫雙向。

### 7.3 為什麼要來源標記

```text
1001 和 2002：遊戲內互加過 ＋ FB 也是好友 → source_mask = GAME | FACEBOOK
之後 FB 上解除好友
   └─▶ 只拿掉 FACEBOOK → 還剩 GAME → 仍然是好友
       source_mask 變成 0 時才刪除這一列
```

不分來源的話，FB 解除好友會誤刪玩家自己加的好友。

### 7.4 token 不保存

只用登入當下 Client 給的短期 token，用完就丟。資料庫裡沒有 FB token，就算資料外洩也不會外洩 FB 權限。代價是只有玩家登入時才能同步，這對好友功能已經夠用。

## 8. 流程：取消授權與刪除資料（Meta 規定）

這兩個端點 Meta 審核會檢查，上架前一定要好。

```text
玩家到 FB 設定頁「移除這個 App」
   │
   ▼
FB 呼叫 Deauthorize Callback（HTTPS，帶 signed_request）
   │
   ▼
Central 用 App Secret 驗簽名 ──失敗──▶ 回 400，不處理
   │成功
   ▼
清掉這個玩家所有 facebook 來源的好友標記
（角色、user_identity 保留，玩家仍可用其他方式登入；
  下次再用 FB 登入會重新授權）


玩家到 FB 申請「刪除我在這個 App 的資料」
   │
   ▼
FB 呼叫 Data Deletion Callback
   │
   ▼
Central 驗簽名 → 刪 user_identity(facebook) ＋ facebook 來源好友標記
   │
   ▼
回給 FB 查詢網址＋確認碼（Meta 規定的回應格式）
```

另外，現有的 360 天帳號清除（`accountrule.PurgeAfter`，見[帳號保留政策](../../10-核心流程/帳號保留政策.md)）要一併清掉該角色的 `user_identity`、`friend`（雙向）、`friend_sync`、`name_history`。

## 9. iOS Limited Login 特例

```text
iPhone 玩家按 FB 登入
   │
   ▼
玩家允許「追蹤」（ATT）？
   │
   ├─ 允許 ──▶ 一般登入，拿到 token ──▶ 第 5、7 節，完全一樣
   │
   └─ 拒絕 ──▶ Limited Login，拿到 JWT（FB 簽名的身分憑證）
                 │
                 ▼
               Gate 用 FB 公開金鑰（JWKS）驗簽名
               檢查 aud（我方 App ID）、iss、exp、nonce
               （不用呼叫 Graph API）
                 │
                 ▼
               登入：可以，走同一張 user_identity
                 │
                 ▼
               好友：伺服器無法自己查
                 └─▶ 只能由 Client 回報好友清單，但 Client 可以造假
```

Client 回報的好友不能直接相信：好友類別會影響掠奪配對（見 `PJA-Docs/名詞定義.md` 的「每日被掠奪次數上限」），造假可能被拿來挑對手。

**解法：雙方互相回報才成立**

```text
A 回報：我的好友有 B
B 回報：我的好友有 A
   └─▶ 兩邊都說了 → 建立 FACEBOOK 來源好友

只有 A 單方面說 → 暫存，不生效（設保存期限，例如 30 天後丟棄）
```

造假的人沒辦法控制對方回報什麼，所以假不了。

> ⚠ Limited Login 能不能拿到好友清單，FB 官方 iOS 文件（列出 `friendIDs`）和第三方文件（說拿不到）互相矛盾。**要用真機實測後再定案。** 實測拿不到時，Limited Login 玩家就不提供 FB 好友同步。

## 10. 好友頭像

**Client 用 SDK 自己向 FB 取，伺服器不存、不轉。**

- 伺服器在好友清單中下發好友的 FB uid（`user_identity` 裡有）。
- Client 用 `https://graph.facebook.com/{uid}/picture` 向 FB 取圖。這個網址對 ASID 是否需要帶 token 要實測；需要時用玩家自己當下的 token，不經過我方伺服器。

| 問題 | 建議 |
| --- | --- |
| 要不要把 FB uid 下發給 Client？ | 只對 `source_mask` 含 FACEBOOK 的好友下發，而且只下發給本人自己的好友；陌生人（例如配對對手）不下發 |
| 遊戲內加的好友怎麼顯示頭像？ | 用遊戲內頭像，不要為了頭像去查對方的 FB uid |
| 玩家解除綁定 FB 後？ | 不再下發他的 FB uid，頭像退回遊戲內頭像 |
| 要不要快取？ | Client 本地快取即可 |
| 以後多個平台？ | 下發通用的 `{provider, provider_uid}` 清單，Client 依 provider 選對應 SDK 取頭像 |

伺服器不碰頭像的理由：不用處理圖片儲存、換頭像同步、平台資料使用政策，也不用追蹤每次換頭像。

## 11. 玩家名字與好友碼

### 11.1 核心規則：名字只拿來顯示，不拿來認人

名字可以重複，所以系統裡任何「找人」都不能用名字。

| 用途 | 用什麼 |
| --- | --- |
| 系統內部辨識 | `player_id`（不給玩家看） |
| 玩家互相找人、加好友 | 好友碼（公開、隨機、不重複） |
| 畫面顯示 | 名字（可重複、可改） |

不直接公開 `player_id` 的原因：它是自增流水號，等於公開遊戲人數，也能被人逐號掃出所有玩家。好友碼用隨機碼（例如 8 碼 `K7QX2M9P`），掃不出規律。兩個同名玩家並排時，顯示成 `小明 #K7QX` 來分辨。

### 11.2 名字規則

| 規則 | 建議 | 說明 |
| --- | --- | --- |
| 長度 | 顯示寬度 2～12（中文算 2、英數算 1） | 以寬度計算，畫面不會被一串中文撐爆。現有依賴 `golang.org/x/text/width` 可算 |
| 正規化 | 存之前做 NFKC | 全形 `ＡＢＣ` 轉成 `ABC`，同一名字不會有兩種寫法。現有依賴 `golang.org/x/text/unicode/norm` |
| 禁止字元 | 控制字元、不可見字元、首尾空白 | 沿用 `accountrule` 的 `valid`、`Registrable` 規則 |
| 連續空白 | 合併成一個 | 避免 `小　　　明` |
| 敏感詞 | 髒話、政治、冒充官方（GM、客服、官方） | 詞庫建議放 PJA-Config，企劃自己維護 |
| 規則位置 | 新增 `pkg/namerule`，Gate、Central 共用 | 照 `accountrule` 的做法：Gate 先擋，Central 再擋一次 |

### 11.3 流程：新玩家取名

```text
新玩家第一次登入（帳密或社群平台都一樣）
   │
   ▼
Central 建角色時：
   name        = 「玩家」＋ 4 位亂數，例如「玩家8271」
   friend_code = 隨機 8 碼（撞號重抽，唯一索引兜底）
   │
   ▼
進遊戲後 Client 跳出取名畫面
   │
   ├─ FB 登入的玩家：Client 用 FB SDK 拿 FB 名字預填
   │                 （玩家自己按確定才送出，伺服器不向 FB 取名字）
   │
   ▼
玩家按確定 ──▶ 走改名流程（11.4），第一次免費、不計冷卻
```

不直接存 FB 名字：FB 名字常是真名，玩家不一定想在遊戲公開；由玩家自己確認送出，才是玩家自己取的名字。

### 11.4 流程：改名

```text
玩家送 RenameRequest { name: "大明" }
   │
   ▼
Gate：改名太頻繁？（每分鐘上限）──是──▶ 回「請稍後再試」
   │否
   ▼
Gate：namerule 檢查 ──不過──▶ 回對應錯誤碼
   │                         （太短／太長／非法字元／含敏感詞）
   ▼ 通過
轉給 Central
   │
   ▼
Central 再用 namerule 檢查一次（防止繞過 Gate）
   │
   ▼
禁止改名中？（GM 設定）──是──▶ 回「目前無法改名」
   │否
   ▼
冷卻中？──是──▶ 回「X 天後才能改名」
   │否
   ▼
要扣費嗎？（第一次免費）
   │
   ├─ 要扣 ──▶ 通知 World 扣道具 ──失敗──▶ 回「道具不足」
   │
   ▼
同一筆 DB 交易：
   更新 user.name、name_ver + 1、name_changed = now
   寫 name_history
   │
   ├─ 交易失敗且已扣道具 ──▶ 退還道具（沿用既有跨服務補償做法）
   │
   ▼
更新 Central 記憶體與 Redis 的名字快取
   │
   ▼
回 Client 成功 ──▶ 推播「名字變更」給線上好友（11.5）
```

扣費牽涉 World 道具。扣與退的順序、冪等鍵，實作時依[資料一致性](../../10-核心流程/資料一致性.md)另外細看。

### 11.5 別人怎麼看到你的名字

```text
Client 要顯示好友清單
   │
   ▼
Central 回傳 [{player_id, name, name_ver, friend_code, fb_uid?}, ...]
   │
   ▼
Client 以 player_id 為 key 快取名字，連同 name_ver
   │
   ▼
之後再看到同一人：
   name_ver 相同 ──▶ 用快取
   不同 ──────────▶ 換新名字
```

| 場景 | 做法 |
| --- | --- |
| 好友清單 | Central 從快取一次查一批名字回傳 |
| 掠奪配對 | 配對結果直接附對手的 `name`、`name_ver`，World 不另外查 |
| 聊天 | 訊息送出時帶上當下名字（快照）。之後改名，舊訊息仍顯示舊名，檢舉時對得上 |
| 好友改名 | 線上好友收到推播；離線好友下次拿清單時靠 `name_ver` 自動更新 |

### 11.6 用好友碼加好友

```text
玩家輸入好友碼 K7QX2M9P
   │
   ▼
Gate 限流（防止狂試好友碼）
   │
   ▼
Central 以 friend_code 唯一索引查 ──查不到──▶ 回「找不到玩家」
   │
   ▼ 找到 2002
顯示「小明 #K7QX」讓玩家確認 ──▶ 送好友邀請
   │
   ▼
對方同意 ──▶ 寫雙向好友，source_mask 加上 GAME
```

好友邀請、同意、拒絕、刪除、上限等細節屬好友系統本身，另立規格。

### 11.7 GM 與檢舉

```text
玩家檢舉「名字不雅」
   │
   ▼
GM 後台查 name_history，看完整改名紀錄
   │
   ▼
GM 強制改名 ──▶ 改成「玩家XXXX」，reason = GM，不扣費、不計冷卻
             ──▶ 可設「禁止改名 N 天」（玩家又改回不雅名字時）
```

GM 操作沿用現有 Lobby gm 指令機制，跟封禁同一套流程。

## 12. 資料表

全部放 Central MySQL，遷移由 PJA-Database 提供。

### 12.1 `user`（既有，新增欄位）

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `name` | `varchar`（依 12 寬度、NFKC 後的位元組上限決定） | 名字，**不加唯一索引** |
| `friend_code` | `char(8)` | 好友碼，唯一索引 |
| `name_ver` | `int unsigned` | 每改一次名字 +1 |
| `name_changed_at` | `datetime NULL` | 上次改名時間，算冷卻用；NULL 表示還沒改過（第一次免費） |
| `rename_banned_until` | `datetime NULL` | GM 禁止改名的期限 |

既有玩家遷移時補預設名與好友碼。

### 12.2 `user_identity`（新）

| 欄位 | 說明 |
| --- | --- |
| `provider` | `password`／`facebook`／`google`／`apple`… |
| `provider_uid` | 平台給的使用者 ID |
| `player_id` | 對應的角色 |
| `created_at` | 綁定時間 |

- 主鍵 `(provider, provider_uid)`：一個外部身分只能綁一個角色。
- 唯一 `(player_id, provider)`：一個角色每個平台最多綁一個帳號。

### 12.3 `friend`（新，雙向各存一列）

| 欄位 | 說明 |
| --- | --- |
| `player_id` | 自己 |
| `friend_player_id` | 好友 |
| `source_mask` | 位元：`1 = GAME`（遊戲內互加）、`2 = FACEBOOK`；以後平台依序加位元 |
| `created_at` | 建立時間 |

- 主鍵 `(player_id, friend_player_id)`。
- `source_mask` 變成 0 時刪除該列。

### 12.4 `friend_sync`（新）

| 欄位 | 說明 |
| --- | --- |
| `player_id` | 主鍵 |
| `provider` | 同步來源（目前只有 `facebook`） |
| `last_synced_at` | 上次同步時間，判斷 24 小時 |

主鍵改 `(player_id, provider)`，以後多平台同步各自計時。

### 12.5 `friend_claim`（新，只用於第 9 節 Limited Login）

| 欄位 | 說明 |
| --- | --- |
| `player_id` | 回報者 |
| `claimed_provider_uid` | 回報的好友外部 ID |
| `created_at` | 回報時間，超過保存期限刪除 |

### 12.6 `name_history`（新）

| 欄位 | 說明 |
| --- | --- |
| `player_id` | 角色 |
| `old_name`、`new_name` | 改名前後 |
| `changed_at` | 時間 |
| `reason` | `player`／`gm` |

### 12.7 刻意不存

FB 名字、大頭照、email、任何平台的 token。

## 13. 錯誤處理與防護

| 狀況 | 處理 |
| --- | --- |
| FB 整個掛掉 | 斷路器打開，FB 登入回「暫時無法使用」；密碼登入照常 |
| FB 很慢 | 驗證加逾時（例如 3 秒）；Gate 同時驗證數量設上限（參考 Central bcrypt 槽位做法），避免拖垮 Gate |
| 好友同步失敗 | 只記取樣日誌，下次登入再同步 |
| 有人狂刷 FB 登入 | 沿用 Gate 現有登入次數限制 |
| FB 呼叫次數上限 | 每位使用者約每小時 200 次；24 小時同步一次遠低於上限 |
| 拿別的 App 的 token 冒充 | `debug_token` 檢查 `app_id`；JWT 檢查 `aud` |
| Limited Login 好友造假 | 雙方互相回報才成立（第 9 節） |
| 狂試好友碼 | Gate 限流；好友碼 8 碼隨機，空間大、掃不完 |
| 改名洗頻 | Gate 每分鐘上限＋Central 冷卻天數 |
| 冒充官方名字 | 敏感詞庫包含 GM、客服、官方等詞 |
| Callback 偽造 | 用 App Secret 驗 `signed_request`，失敗回 400 |

需要新增的指標（依 [日誌規範](../../30-部署與開發/日誌規範.md) 與現有 `game_login_total` 慣例）：

- 社群登入結果：`provider`、`result` 標籤。
- FB 呼叫延遲與失敗數：`endpoint` 標籤。
- 好友同步結果與新增／移除的好友數。
- 改名結果：`result` 標籤。

## 17. 刻意不做

| 項目 | 理由 | 何時再考慮 |
| --- | --- | --- |
| 邀請沒玩的 FB 好友 | FB 不提供清單，要另做 Game Request | 企劃要拉新功能時 |
| 多款遊戲共用好友 | ASID 每 App 不同 | 公司有第二款遊戲要互通時，改用 `token_for_business` |
| 自動合併同一人的多個角色 | 牽涉道具、進度，且易被利用搶帳號 | 不考慮 |
| 用 email 合併帳號 | 各平台 email 驗證強度不一，Apple 可隱藏信箱 | 不考慮 |
| 保存 FB token 做離線同步 | 外洩風險；登入時同步已足夠 | 需要「好友在線狀態」等即時功能時 |
| 伺服器存或轉頭像 | 儲存、同步、平台政策成本 | 有自訂頭像上傳需求時另立方案 |
| 以名字搜尋玩家 | 名字重複時無法分辨，易被騷擾或冒充利用 | 企劃確定需要時：最多回 20 筆、只比對開頭、加限流 |
| 名字唯一 | 企劃已決定名字可重複 | — |

## 19. 實作與方案的差異

2026-11-05 實作完成（登入、綁定、好友同步、好友清單、好友碼查詢、個人資料、改名）。下表是與上文不同的地方，以程式為準；現行規則寫在[帳號與社群身分](../../10-核心流程/帳號與社群身分.md)。

| 主題 | 方案 | 實作 |
| --- | --- | --- |
| 好友同步的觸發 | 登入或綁定成功後由 Central 背景自動跑（第 5、7 節） | 由 Client 送 `SyncSocialFriendsRequest`（帶當下憑證）觸發；登入與綁定都不自動同步。24 小時節流在 Central（`friend_sync.last_synced_at`） |
| 誰打平台 HTTP | Gate 驗 token，Central 的同步工作抓 `/me/friends` | Gate 做所有平台 HTTP（`debug_token`、`/me/friends`、JWKS）；Central 不呼叫任何平台，也不拿 token。好友清單由 Gate 取得後放進 `AccountOpRequest` 轉給 Central |
| 帳密是否遷入 `user_identity`（4.2） | 建議 A，B 也可 | 選 B：帳密玩家維持 `user.account`，不寫 `provider=password` 列。社群登入建立的玩家，`user.account` 填保留格式 `~<provider>~<uid>`（例如 `~facebook~123`），無密碼雜湊；`accountrule` 的 `CheckLogin` 與 `Registrable` 擋下這個前綴，密碼登入與註冊碰不到它 |
| 封禁檢查位置 | 未提 | 社群玩家的帳號要 Central 解出來才知道，所以封禁查詢移到 Central：查 Redis `gm:ban:<帳號>`，查詢失敗 fail-closed 回 `AuthServiceUnavailable`。Gate 對社群登入不做封禁檢查 |
| 帳號鎖 key | `provider:uid` | 鎖保留格式帳號字串（與帳號清除同一把鎖）；已綁在密碼帳號玩家上的身分，另鎖該玩家的 `user.account` |
| 登入訊息 | `LoginRequest` 改成 `oneof credential` | 獨立訊息 `SocialLoginRequest{Provider, Credential}`；Gate 驗過後送 Central `SocialLoginGateToCentral{Provider, ProviderUid}`；`LoginRequest` 不動。結果碼新增 `AuthSocialAuthFailed`（14） |
| 帳號操作的訊息 | 每種操作各自一組 S2S 訊息（隱含） | Gate 與 Central 之間只有一組信封 `AccountOpRequest`／`AccountOpResponse`，以 `Operation` 操作碼分派（`pkg/accountop`）；Client 面仍是各操作自己的請求與回應訊息 |
| 名字設定區段 | 未指定，詞庫放 PJA-Config | Central 設定區段 `player_name.*`：`rename_cooldown_hours`（預設 168）與 `extra_forbidden_file`（額外敏感詞檔路徑，每行一詞）；內建保留字寫在 `pkg/namerule`。詞庫沒有放進 PJA-Config |
| 改名費用 | 第一次免費，之後扣費並由 World 扣道具 | 只留 `RenameFee` 接點，預設 `NoFee`，不扣費，World 不參與（企劃尚未決定費用）。同名重送視為成功且不消耗冷卻 |
| 好友清單與好友碼查詢的回傳 | 第 11.5、11.6 節未指定 | Central 把結果放在 `AccountOpResponse.Friends`：`ListFriends` 回整份清單（最多 500 筆），`FindByCode` 只放第一筆（回應的 `PlayerID` 是請求者）；Client 面分別是 `ListFriendsResponse.Friends` 與 `FindPlayerByCodeResponse.Player` |
