# 道具取得與使用現行規範

## 文件狀態

本文件定義道具取得、背包保存、立即使用與跨系統行為的責任邊界。

目前已完成：

- `internal/game/item` 的取得模式、Item Action、設定驗證與查詢。
- `internal/game/item` 的取得與背包使用流程。
- PJA-Config 的 `Item` 取得模式設定與 Loader。
- World 的 GM 道具發放入口已經過取得流程規劃後再寫入背包。
- `Item.Type = 1` 已對應為 `AdjustVariable`：取得道具增加、扣除道具減少 Variable；`Param1` 是 VariableId、`Param2` 是單個道具的絕對數量。
- `tools/itemsim` 可讀取正式設定並模擬取得或使用道具。

尚未實作：

- 其他 `Item.Type`、`Param3` 與 `ItemSource` 的 Item Action 規則。

本方案沿用既有名稱：

- `Inventory System` 管理玩家持有的堆疊道具。
- `Variable System` 管理玩家的通用數值。
- `Effect System` 管理具有來源、可新增與移除，並會影響遊戲數值或功能的效果。
- `Item Action` 表示道具被使用後要執行的行為，不稱為 Effect，避免和既有 Effect System 混淆。

## 1. 核心概念

「取得道具」有兩種處理方式：

```text
取得道具
├─ Inventory：加入背包，之後由玩家使用
└─ Immediate：不進背包，立即執行 Item Action
```

進入背包的道具之後仍可被使用：

```text
取得道具
  → 加入背包
  → 玩家使用
  → 扣除背包數量
  → 執行 Item Action
```

因此「取得方式」與「使用後行為」是兩個不同設定，不應由道具 ID 硬編碼在 Handler 中。

### 1.1 遊戲邏輯與協定分離

道具規則必須能被 World、企劃預覽工具、自動測試與資料驗證工具共同呼叫，因此遊戲邏輯不得依賴：

- `pkg/protocol/client` 產生型別。
- `pkg/msg` 編解碼器。
- TCP message ID、socket 或封包回傳碼。
- Handler 專用的 request／response 型別。

依賴方向固定為：

```text
Client Protocol
      ↓ decode
Handler Adapter
      ↓ domain Command
Item Service
      ↓ domain Result
Handler Adapter
      ↓ encode
Client Protocol
```

企劃工具走另一個 Adapter，但共用同一個 Item Service：

```text
CLI／GUI Tool
      ↓ tool input
Tool Adapter
      ↓ domain Command
Item Service
      ↓ domain Result
Tool Output
```

Protocol 與工具只能做輸入轉換、錯誤碼映射與輸出格式化，不得各自重寫道具規則。

## 2. 系統責任

### 2.1 Inventory System

負責：

- 查詢玩家持有的道具與數量。
- 增加堆疊道具。
- 驗證並扣除堆疊道具。
- 道具資料持久化與冪等。

不負責：

- 解讀道具使用後的業務意義。
- 直接修改 Variable。
- 呼叫釣魚、商店等其他遊戲系統。

### 2.2 Item Use System

負責：

- 驗證道具是否可使用及使用數量。
- 背包道具使用時協調扣除數量。
- 將道具設定轉成 `ItemAction`。
- 呼叫 Item Action 執行邊界。
- 回傳與協定無關的操作結果及狀態變更。

Item Use System 只負責流程協調，不直接依賴所有目標系統。

概念依賴：

`item.Service` 只根據 Item 定義產生取得或使用計畫；World 的 `itemaction.Executor` 依 Action Type 路由至各系統 Handler。因此道具 domain 不直接依賴 Inventory、Variable 或 Effect。

### 2.3 Item Action

`ItemAction` 是道具使用後的行為描述，例如：

```text
AdjustVariable
StartFishing
OpenChest
```

`ActionExecutor` 根據 Action 類型交給對應實作。各實作只依賴自己需要的系統：

```text
AdjustVariableAction → Variable System
StartFishingAction → Fishing System
```

這可避免 `item.Service` 同時持有 `inventory`、`effect`、`variable` 與所有未來業務系統。

Action 的輸入與輸出使用 Domain 型別，不得直接使用 Protocol 生成型別：

```go
type UseCommand struct {
	OperationID string
	PlayerID    uint64
	ItemID      uint32
	Quantity    int32
}

type Result struct {
	Variables []VariableChange
	Items     []ItemChange
}
```

`Result` 表示遊戲操作結果；Handler 再把它轉成 Protocol 的 `ChangeSet`，工具則可轉成表格、JSON 或預覽畫面。

### 2.4 Variable System

維持既有責任：

- 管理 `VariableID` 與 `int64` 數值。
- 提供 `Get`、`Set`、`Add`。
- 驗證 Default、範圍與 overflow。
- 保存並產生 Variable 變更資料。

Item Action 只能透過 Variable System 的公開操作修改數值，不重複實作數值規則。

### 2.5 Effect System

維持企劃既有命名，負責：

- 保存 Effect 的來源種類與來源 ID。
- 新增、移除及查詢 Effect。
- 依來源種類清除 Effect。
- 依指定來源 ID 或 Effect instance ID 清除 Effect。
- 聚合 Effect 對數值、規則或功能造成的影響。

概念資料至少包含：

```text
Effect
├─ InstanceID
├─ SourceType
├─ SourceID
├─ EffectID
└─ ExpiresAt
```

## 3. 道具設定

道具設定分成取得方式與使用行為：

```text
ItemConfig
├─ ID
├─ Type: 0 = 無使用效果；1 = AdjustVariable
├─ Param1: Type = 1 時為 VariableId
├─ Param2: Type = 1 時為單個道具的數量
├─ Param3: 保留
├─ ItemSource: 保留
├─ AcquireMode: Inventory | Immediate
└─ 使用時依 Type 與 Param 轉成 Item Action
```

### 3.1 背包道具

```text
ItemID: 3001
AcquireMode: Inventory
Type: 1
Param1: Energy
Param2: 30
```

取得時加入背包；玩家使用後扣除一個道具並增加 Variable。

### 3.2 立即使用道具

```text
ItemID: 3002
AcquireMode: Immediate
Type: 1
Param1: Energy
Param2: 30
```

取得時不加入背包，直接執行正向的 `AdjustVariable`。

### 3.3 導向其他系統

```text
ItemID: 3003
AcquireMode: Inventory
Actions:
  - Type: StartFishing
    ConfigID: 100
```

玩家使用後由 Fishing System 驗證並執行實際規則；Item Use System 不實作釣魚邏輯。

## 4. 執行流程

### 4.1 取得背包道具

```text
Grant(itemID, quantity)
  → 讀取 ItemConfig
  → AcquireMode = Inventory
  → Inventory.Add
  → 回傳 ItemChange
```

### 4.2 取得立即使用道具

```text
Grant(itemID, quantity)
  → 讀取 ItemConfig
  → AcquireMode = Immediate
  → 建立 ItemAction
  → ActionExecutor.Execute
  → 回傳 Domain Result
```

立即使用不應先加入背包再扣除，避免無意義的兩次寫入。

### 4.3 使用背包道具

```text
Use(playerID, itemID, quantity)
  → 驗證 ItemConfig 與使用數量
  → 驗證背包數量
  → 執行 ItemAction
  → 扣除背包數量
  → Commit
  → 回傳 Domain Result
```

所有輸入由 Server 依設定重新驗證；Client 只提供要使用的道具 ID 與數量。

## 5. 交易、冪等與失敗處理

- 每次取得或使用必須帶 `OperationID`，重送不得重複發放、扣除或執行 Action。
- 同一資料庫內的道具、Variable 與其他持久資料修改應在同一個 Transaction 完成。
- Action 失敗時不得消耗背包道具。
- 涉及外部或無法加入同一 Transaction 的系統時，不宣稱具備原子性；應由該系統提供可重試且冪等的操作。
- Domain Service 只回傳 Domain Result；Inventory、Variable、Effect 與各業務系統不直接送封包。
- Handler 是唯一將 Domain Result 轉成 Protocol `ChangeSet` 與錯誤碼的位置。

## 6. 建議命名與目錄

可被 World 與工具共用的遊戲規則放在專案根層 `internal/game`；World 專屬的狀態、持久化與協定 Adapter 留在 `cmd/world/internal`：

```text
internal/game/
└─ item/                    與協定、資料庫無關的道具取得、使用與 Action 規則

cmd/world/internal/
├─ inventory/               玩家背包、堆疊道具與持久化
├─ effect/                  多來源 Effect
├─ variable/                玩家通用數值
├─ handler/gate/            Protocol decode／encode 與錯誤碼映射
├─ itemaction/              Item Action Handler 與執行器
└─ services/                組裝 Store、Item Service 與 Handler

tools/
├─ itempreview/             預覽道具行為
├─ itemvalidate/            驗證道具設定
└─ itemsim/                 模擬道具取得與使用
```

建議 Go 名稱：

```text
inventory.Service
item.Service
item.UseCommand
item.Action
item.ActionExecutor
item.Result
effect.Service
variable.Service
```

package 已經提供 `item` 上下文，所以避免 `item.ItemService`、`item.ItemAction` 這類重複命名。

如果目前只有一至兩種 Item Action，可先在 `item` 使用明確的 `switch`；只有 Action 數量持續增加或各功能由不同模組維護時，才改成 Handler 註冊表。

### 6.1 工具與共用邏輯位置

所有工具統一放在專案根目錄 `tools/`。Go 的 `internal` 規則會禁止它們匯入 `cmd/world/internal/...`，所以需要共用的純遊戲規則放在根層：

```text
internal/game/item
```

`cmd/world/...` 與 `tools/...` 都位於根層 `internal` 的允許範圍內，可以共用同一套規則；專案外部則無法匯入。這也避免把遊戲業務規則塞進只放通用基建的 `pkg/`。

`internal/game/item` 只包含：

- Domain Command、Result、Definition 與 Action。
- 純驗證與決策邏輯。
- 由 consumer 定義的最小 Inventory／Action 執行介面。

不得包含：

- MySQL、Redis 或 GORM 實作。
- TCP、Protocol、codec 或 message ID。
- World `App`、socket、logger 或服務探索。

World 透過正式 Store Adapter 執行，工具則注入唯讀或記憶體 Adapter；兩者不得各自複製規則。

### 6.2 邊界檢查

遊戲邏輯 package 應留下依賴檢查，至少確保：

```text
internal/game/item           不 import pkg/protocol 或 pkg/msg
internal/game/item           不 import cmd/world/internal
cmd/world/internal/inventory 不 import pkg/protocol 或 pkg/msg
cmd/world/internal/effect    不 import pkg/protocol 或 pkg/msg
cmd/world/internal/variable  不 import pkg/protocol 或 pkg/msg
```

Protocol 改版只應影響 Handler Adapter 與 codec；道具規則與工具不應跟著修改。

### 6.3 Board Simulator 統一案例

Board Simulator 已統一至根目錄 `tools/boardsimulator`。其 API Server 曾放在 `cmd/world/boardsimulator/main.go`，而 Web UI 與啟動腳本位於 `tools/boardsimulator/`；原因是 API Server 當時需要匯入 `cmd/world/internal`。

```text
tools/boardsimulator/
├─ main.go                   Simulator API Server
├─ run.bat
└─ web/                      Simulator UI
```

盤面規則與設定轉換已抽至 `internal/game`，使 World 與工具能共用，但仍不將遊戲邏輯放入公開 `pkg/`：

```text
internal/game/
├─ board/                    純盤面規則
└─ boardconfig/              Luban 設定轉換與事件選擇

cmd/world/internal/board/
├─ Store Adapter
└─ Protocol Adapter

tools/boardsimulator/
├─ main.go                   Simulator API Server
├─ run.bat
└─ web/                      Simulator UI
```

依賴方向：

```text
cmd/world ────────────┐
                      ├─→ internal/game/board
tools/boardsimulator ─┘          ↑
                                 └── internal/game/boardconfig
```

已完成的遷移：

1. `cmd/world/internal/boarddomain` 已搬至 `internal/game/board`。
2. `LoadDefinition`、`NewEventSelector` 與必要 Luban 轉換邏輯已搬至 `internal/game/boardconfig`。
3. Shop、Protocol、Store 與 World Runtime 邏輯保留在 `cmd/world/internal/board`。
4. API Server 已搬至 `tools/boardsimulator/main.go`。
5. `tools/boardsimulator/run.bat` 已改為執行 `go run ./tools/boardsimulator`。
6. World 與 Board Simulator 共用 `internal/game/board`，不得各自維護盤面規則。

這是獨立的結構重構，不改變盤面規則或 Simulator HTTP API 行為。

## 7. 第一階段範圍

納入：

- `Inventory` 與 `Immediate` 兩種取得方式。
- `AdjustVariable` Item Action。
- 一個導向既有業務系統的 Item Action。
- `OperationID` 冪等。
- Inventory 與同資料庫狀態的交易一致性。
- Domain Result 與 Protocol ChangeSet 轉換。
- 至少一個不經網路協定即可呼叫 Item Service 的測試或工具入口。

暫不納入：

- 通用腳本語言。
- 動態 Plugin 系統。
- 非同步事件總線。
- 為每種 Action 建立獨立 package。
- 未出現實際需求前的通用 Reward Manager。

## 8. 與既有系統的關係

```text
外部獎勵／商店／GM
          ↓
      道具取得流程
      ├─ Inventory.Add
      └─ Item Action

玩家使用背包道具
          ↓
       item.Service
      ├─ Inventory.Consume
      └─ ActionExecutor
           ├─ Variable
           └─ 其他遊戲系統

World Handler／企劃工具
          ↓
     各自的 Adapter
          ↓
       item.Service
```
