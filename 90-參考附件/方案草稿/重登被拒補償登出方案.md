# 重登被 World 拒絕時的補償登出方案

> **文件狀態：草稿，待決定。** 尚未實作。下列時序是讀碼推導的，**沒有實際重現過**；動手前建議先寫一個重現測試（見「驗證計畫」）。

## 一句話

同一玩家已在 Gate A 上線，又從 Gate B 登入，若 World 剛好拒絕這次登入，Gate B 的「善後登出」會讓 Central 與 World 把這位玩家整個登出，**連原本在 Gate A 的合法 session 一起踢掉**。

## 現況流程

涉及的程式位置：

| 步驟 | 位置 |
| --- | --- |
| Central 先改記錄、再送 World | `cmd/central/internal/flow/login/persist.go` 的 `completeLogin` |
| World 拒絕（資料庫寫入失敗、滿載） | `cmd/world/internal/flow/login/state.go` 的 `completeLoginAccepted`、`rejectIfFull` |
| World 通知舊 Gate「被重登」 | `cmd/world/internal/flow/login/relogin.go` 的 `handleLoginRelogin` |
| Gate 收到拒絕後的善後 | `cmd/gate/internal/handler/world/on_login_world_to_gate.go`、`login_world_helpers.go` 的 `notifyLogoutToCentral` |
| Central 處理登出 | `cmd/central/internal/flow/logout/`（`preflight.go`、`normal.go`） |

```
玩家 P 已在 Gate A 上線。P 又從 Gate B 登入：

Gate B            Central                        World                    Gate A
  │                 │                              │                        │
  │─ 登入請求 ─────▶│                              │                        │
  │                 │ ① 記錄 P 的 Gate 改成 B       │                        │
  │                 │   （原本 A 的記錄被覆蓋）      │                        │
  │                 │─ 轉送登入 ──────────────────▶│                        │
  │                 │                              │ ② 先寫登入時間到資料庫   │
  │                 │                              │   失敗（或 World 滿載）   │
  │                 │                              │ ③ 直接回拒絕，           │
  │                 │                              │   還沒切換 Gate、         │
  │                 │                              │   也沒通知 A「被重登」    │
  │◀─ 拒絕 ─────────┼──────────────────────────────│                        │
  │                 │                              │                        │
  │ ④ 善後：清掉預寫狀態                            │                        │
  │─ 登出 P ───────▶│                              │                        │
  │                 │ ⑤ 檢查：P 記錄在 B，通過      │                        │
  │                 │ ⑥ 刪除 P 的記錄               │                        │
  │                 │─ 通知 World 登出 P ─────────▶│ ⑦ 把 P 登出、卸載資料    │
  │                 │                              │──────────────────────▶│ 手機掉線
  ▼                 ▼                              ▼                        ▼
結果：B 登入失敗，A 也被踢。P 兩邊都沒了。
```

關鍵事實（都在程式碼裡可以驗證）：

- **World 拒絕發生在切換之前**：`completeLoginAccepted` 在資料庫寫入失敗時直接回覆，之後才有 `handleLoginRelogin` 與 `SetUserGate`。所以此刻 **World 仍認為 P 在 Gate A**。
- **Central 是先改記錄再問 World**：這是刻意的（`completeLogin` 的註解：讓舊 Gate 的登出在空窗到達時看到新 Gate 而被擋下）。代價就是 World 拒絕時，Central 已經改過了。
- **Central 現有的還原只涵蓋「送給 World 失敗」**：`completeLogin` 會在 `sendToWorld` 失敗時把 `previous` 還原。World 回覆拒絕時，Central 完全不知道。
- **善後登出無法區分新舊**：Central 的登出只檢查「記錄上的 Gate 是不是送登出的這個」，B 通過檢查後就整個清掉。

## 影響範圍

- 需要同時成立：同一帳號重登、舊 session 還在線、World 在這個瞬間拒絕（資料庫逾時 2 秒、或 World 滿載）。
- 滿載不影響這條路徑：`rejectIfFull` 對「已在線的玩家」不拒絕（`ok && worldUser.GateID != 0`），所以實際觸發原因主要是**資料庫寫入登入時間失敗**。
- 後果：玩家兩個裝置都掉線，要重新登入。**不會遺失資料**（World 登出會正常寫回）。

## 另一個容易誤判的情境

Gate B 發送善後登出有兩種原因，Central 現在**分不出來**：

```
情境一：World 拒絕了（回應碼不是成功）
        → World 沒有切換，仍在 Gate A
        → 正確做法：還原 Central 記錄為 Gate A，不要登出

情境二：World 已接受並切換到 B，但玩家在 B 的連線已斷
        → World 已經通知 A「被重登」，A 已被踢，World 記錄在 B
        → 正確做法：完整登出（B 已不存在）
```

兩種情況送出的 `LogoutGateToCentral` 內容一樣（`RequestID`、`TraceID`、`PlayerID`），任何只在 Central 端的修法都分不出來。這是方案選擇的核心限制。

## 方案

### 方案 A：World 不因資料庫失敗拒絕「已在線玩家」的重登（建議先做）

```
World 收到登入
   │
   ├─ 玩家已在記憶體且在線（GateID != 0）？
   │       │
   │       是 ──▶ 登入活動寫入失敗只記警告，照常切換到新 Gate、通知舊 Gate
   │       │
   │       否 ──▶ 維持現狀：寫入失敗就回拒絕
   │            （全新玩家要靠這個寫入建立主檔，不能略過）
```

- **為什麼合理**：`TouchLoginActivity`（`cmd/world/internal/store/gamestore/mysql_login_activity.go`）只做兩件事：玩家主檔不存在時建立、存在時更新活躍時間（封存中的玩家只更新封存表的時間，不還原）。已在線的玩家主檔必然存在、資料在記憶體，失敗頂多是這次活躍時間沒更新。`rejectIfFull` 已經用同樣的條件（`GateID != 0`）對在線玩家放行，這個做法與它一致。
- **要確認的小風險**：活躍時間是封存與保留期判斷的依據。在線玩家少一次更新，只會讓「最後活躍」晚一點更新，且在線期間的寫回與登出也會更新，影響可忽略；但請你確認。
- **改動**：只動 `cmd/world/internal/flow/login/state.go`，約十行，**不改協定**。
- **效果**：消除最常見的觸發原因（資料庫逾時）。
- **沒解決的**：World 因其他原因拒絕、或回覆根本沒送達的情況（例如 Gate B 的連線在 World 回應前就斷了，見情境二）。
- **風險**：低。要補測試：已在線玩家寫入失敗仍登入成功並踢掉舊 Gate；不在線玩家寫入失敗仍回拒絕。

### 方案 B：善後登出帶「登入被拒」旗標，Central 還原舊記錄（完整解法）

```
Central 登入成功路徑：把「被覆蓋的舊 Gate」記進登入 journal
        │
Gate B 善後登出（新增欄位 LoginRejected = true / false）
        │
Central 收到登出
   ├─ LoginRejected=true 且 journal 有舊 Gate 且該 Gate 仍連線
   │       ──▶ 把 P 記錄還原為舊 Gate，同步共享路由，
   │           回覆 B「已處理」，不通知 World
   └─ 其他                                  ──▶ 維持現狀：完整登出
```

- **改動**：
  1. `PJA-Protocol` 的 `LogoutGateToCentral` 加一個欄位並重新產生（**不在本專案範圍**，要走 Protocol 的流程）。
  2. `LoginRequestRecord` 加舊 Gate 欄位（Redis journal 格式要相容）。
  3. Gate 在善後時填旗標；Central 登出流程加還原分支。
- **風險**：中到高。協定變更要 Gate 與 Central 同時升版（舊 Gate 不填旗標時要退回現狀行為）；還原與「舊 Gate 剛好同時斷線」交錯時要再比對一次 Gate（可沿用這輪新增的 `DeleteUserIfGate` 思路）。

### 方案 C：什麼都不做，只記錄成已知行為

- 條件窄（重登加資料庫逾時）、後果輕（重新登入一次、不遺失資料）。
- 若上線前資料庫穩定度有把握，這是合理選擇。

## 建議

```
先做 方案 A ──▶ 消除絕大多數觸發原因，不動協定，風險低
        │
        └─ 上線觀察一段時間：
              Central 登出日誌若仍看到「重登後被拒、舊 session 被踢」，
              再評估是否值得做方案 B（需 Protocol 配合）
```

## 驗證計畫

1. **先重現再修**：用 World 登入流程的現有測試替身（`cmd/world/internal/flow/login/` 的 `loop_app_test.go`），建立「玩家已在 Gate A、`TouchLoginActivity` 回錯誤、從 Gate B 重登」的案例，確認目前會回拒絕且沒有切換 Gate。再用 Central 登出流程測試，確認善後登出會刪掉記錄並送 World 登出。這兩步證明時序成立。
2. 方案 A 的測試：
   - 在線玩家寫入失敗：登入成功、舊 Gate 收到 `AuthReLogin`。
   - 不在線玩家寫入失敗：回 `AuthServiceUnavailable`（維持現狀）。
   - 補一個整合測試（`-tags integration`）：實際資料庫下已在線玩家重登。
3. 跑叢集整合測試（`./integration/...`），確認登入、重登、登出情境不變。
