# 跨服戰鬥與金幣結算方案

> 文件狀態：核心流程已實作；本文件保留方案背景，現行行為以第 10 節為準。

## 1. 目標與結論

玩家在盤面觸發戰鬥時，可隨機選取全伺服器玩家作為敵方，包含離線玩家。戰鬥由 Client 執行；Client 回傳「我方對敵方基地造成的傷害」後，由 Server 結算金幣。

建議拆分為三個服務：

| 服務 | 責任 | 不負責 |
| --- | --- | --- |
| Central | 登入、玩家目前所在 World、服務路由 | 戰鬥快照、金幣餘額、金幣轉帳 |
| Combat／Match | 離線玩家快照、隨機選敵、戰鬥 Session、傷害比例與結算規則 | 金幣餘額的權威保存 |
| Wallet／Currency | 全服金幣餘額、帳本、扣款、補貼、發放 | 戰鬥配對與盤面狀態 |

Combat／Match 的快照以 MySQL 為權威資料，Redis 用於候選玩家索引與快取；Wallet 是金幣唯一權威來源。World 不再直接保存可變動的金幣餘額。

```text
World ──戰鬥快照異動事件──> Combat／Match
                                  │
                             MySQL 快照
                                  │
                             Redis 候選索引
                                  │
Client ──開始戰鬥──> Combat／Match ──> 固定敵方快照與 Session
Client ──提交傷害──> Combat／Match ──> Wallet 結算金幣
```

## 2. 對戰快照

### 2.1 原則

對戰快照是玩家存檔的戰鬥投影，不是另一份完整玩家存檔，也不包含金幣。它允許稍舊；一旦建立戰鬥 Session，該場使用的敵方資料即固定，不受敵方後續下線、升級或換裝影響。

快照的權威來源是 Combat／Match 的 MySQL。Redis 重啟後可由此重建，不能作為唯一存檔。

### 2.2 快照欄位

實際欄位依戰鬥系統的正式存檔補齊；目前至少需有：

| 欄位 | 說明 |
| --- | --- |
| `playerId` | 被選為敵方的玩家 |
| `snapshotVersion` | 此玩家快照版本 |
| `updatedAt` | 快照最後更新時間 |
| `eligible` | 是否允許被配對，例如封禁、保護期或資料不完整時為否 |
| `bunkerConfigKey` | 基地／堡壘配置 |
| `bunkerHealth` | 敵方基地 HP |
| `ownedAmmo` | 敵方砲彈數量 |
| `carryCapacity` | 敵方攜帶上限 |
| `loadoutConfigKeys` | 敵方裝備／載具配置 |

World 在影響上述欄位的資料變更後，透過 Outbox 發送快照更新事件。Combat／Match 消費事件時先更新 MySQL，再更新 Redis。

首次導入時，從各 World 既有玩家存檔做一次全量匯入；其後僅靠異動事件更新。Redis 遺失時，從 Combat／Match MySQL 重建全部候選索引，重建完成前暫停新配對。

## 3. 隨機選敵

Combat／Match 從 Redis 的候選集合隨機取出玩家，並排除：

- 攻方自己。
- `eligible = false` 的玩家。
- 快照不存在或已失效的玩家。
- 未來加入的保護期、近期被攻擊冷卻或其他配對限制。

抽到攻方本人或無效快照時重新抽取；重試有限次仍沒有有效目標時，回覆目前沒有可戰鬥的對手。

離線不是排除條件。因為戰鬥使用固定快照，目標 World 不需要在線才能開始戰鬥。

## 4. 戰鬥 Session

開始戰鬥時，Combat／Match 必須持久化建立一次性 Session：

| 欄位 | 說明 |
| --- | --- |
| `sessionId` | 本場戰鬥唯一 ID，Client 提交結算必填 |
| `attackerPlayerId` | 攻方玩家 ID |
| `defenderPlayerId` | 守方玩家 ID |
| `defenderSnapshotVersion` | 此場使用的快照版本 |
| `defenderBaseHP` | 傷害比例分母，由 Server 固定 |
| `randomSeed` | 戰鬥亂數種子 |
| `status` | `active`、`settling`、`settled`、`expired` |
| `settlementId` | Wallet 結算的冪等 ID |
| `rewardBaseGold` | 開戰時守方金幣；固定獎勵基準 |

Client 不能指定敵方、基地 HP、快照版本或結算 ID。

重送同一個結算請求時，Server 回傳第一次結算結果，不會再扣款、補貼或發獎。

## 5. Client 回傳與傷害驗證

Client 回傳戰鬥結果，其中本方案只用到我方對敵方基地傷害 `damageToEnemyBase`。

Combat／Match 必須驗證：

- Session 存在，且屬於該攻方。
- Session 尚未結算或過期。
- 傷害是有效有限數值。
- 傷害範圍為 `0 <= damageToEnemyBase <= defenderBaseHP`。

傷害比例由 Server 計算：

```text
ratio = clamp(damageToEnemyBase / defenderBaseHP, 0, 1)
fixedRewardGold = floor(rewardBaseGold × ratio)
```

本階段 Client 戰鬥結果被視為可接受的結算輸入，Server 只驗證 Session 與數值邊界，無法驗證傷害是否真的由戰鬥操作造成。若日後需要防作弊，需改為伺服器戰鬥模擬，或提交可由 Server 重播驗證的操作紀錄。

## 6. 金幣結算與系統補貼

### 6.1 規則

攻方的獎勵以開戰時守方金幣 `rewardBaseGold` 為準，因此畫面預期與實際獎勵一致。守方之後即使花掉金幣，攻方仍取得固定獎勵；不足部分由系統補貼。

結算時 Wallet 讀取守方當下金幣：

```text
defenderDebit = min(defenderCurrentGold, fixedRewardGold)
systemSubsidy = fixedRewardGold - defenderDebit
attackerCredit = fixedRewardGold
```

範例：

```text
開戰時守方金幣：10,000
傷害比例：50%
攻方固定獎勵：5,000

結算時守方金幣：2,000
守方實扣：2,000
系統補貼：3,000
攻方實得：5,000
```

### 6.2 Wallet 原子操作

> 現行實作已改為 World 記憶體版 `MemoryGameStore.SettleCombatGold`，守方不在本 World 時以待套用的調整單扣款，與下列單一資料庫交易的描述不同；差異與已知限制見第 11 節。

Wallet 提供冪等操作：

```text
SettleCombatGold(settlementId, attackerPlayerId, defenderPlayerId, fixedRewardGold)
```

在同一個 Wallet 資料庫交易中：

1. 依固定 PlayerId 順序鎖定攻、守雙方金幣餘額，避免死鎖。
2. 讀取守方目前金幣並計算 `defenderDebit`、`systemSubsidy`。
3. 扣除守方 `defenderDebit`。
4. 增加攻方 `attackerCredit`。
5. 寫入守方掠奪、系統補貼、攻方獎勵三筆帳本。
6. 以 `settlementId` 記錄結算結果。

同一 `settlementId` 重送時回傳原本帳本結果，禁止重複入帳。

### 6.3 經濟含義

系統補貼會產生新金幣。守方刻意在戰鬥期間花費金幣，會提高系統補貼比例，因此帳本必須分開記錄：

| 帳本類型 | 金額 | 用途 |
| --- | --- | --- |
| `combat_loot_debit` | `defenderDebit` | 從守方轉出的金幣 |
| `combat_system_subsidy` | `systemSubsidy` | 系統產生的補貼金幣 |
| `combat_reward_credit` | `attackerCredit` | 攻方實際取得的金幣 |

日後可依營運數據調整補貼規則、加入每日上限或改用獨立的可掠奪金幣池；本方案不預先加入這些限制。

## 7. 通知與恢復

Wallet 成功結算後，Combat／Match 將結算結果持久化並發送事件：

- 攻方：固定獎勵、守方實扣、系統補貼、最終金幣變化。
- 守方：被扣除金幣與來源戰鬥資訊。

守方離線時，通知保留為持久事件，於下次登入同步。Client 不必重送已成功結算的請求。

| 故障情況 | 處理方式 |
| --- | --- |
| Redis 重啟 | 從 Combat／Match MySQL 快照重建；完成前暫停新配對 |
| World 離線 | 仍可用已保存的對戰快照選為敵方 |
| Combat／Match 重啟 | 從 MySQL 恢復 Session；可安全重送結算 |
| Wallet 暫時失敗 | Session 維持 `settling`，以 `settlementId` 重試 |
| Client 重送 | Session 與 Wallet 都依唯一 ID 回傳原結果 |

## 8. 通知與 Client 協定

World 目前提供兩組戰鬥結算通知操作：

- `ListCombatSettlementNotifications`：讀取玩家尚未讀取的攻守結算通知，回傳通知 ID、對手、戰鬥與金幣結果。
- `MarkCombatSettlementNotificationsRead`：依通知 ID 批次標記已讀；重複標記不會重複產生結算。

開始戰鬥與提交結果仍由盤面流程觸發。盤面事件會先回傳戰鬥 Session 與固定敵方快照，Client 完成戰鬥後提交傷害結果；Server 只接受該 Session 所屬攻方的結果。

## 9. 目前實作狀態

以下流程已接通：

1. 玩家載入或盤面資料異動時，World 發布戰鬥快照。
2. 開戰前刷新攻方快照，再從有效候選索引選擇敵方。
3. 開戰時固定敵方快照、基地 HP、配置、亂數種子、獎勵基準與過期時間，並持久化 Session。
4. 同一開始請求重送時，沿用原 Session，不建立第二場戰鬥。
5. 提交結果時由 Wallet 以 settlement ID 執行原子、冪等金幣結算。
6. 結算完成後保存結算時間與攻守雙方通知；通知可離線保留，登入後由 Client 查詢。
7. 候選索引不足或包含攻方本人時會重新篩選；沒有有效候選才回覆無可戰鬥對手。

快照與 Session 的 MySQL 資料是持久化來源，Redis 只保存候選索引。戰鬥 Session 建立後使用的敵方資料不會因對手後續盤面異動而改變。

## 10. 後續待定項目

- 戰鬥快照的完整資料來源：基地、砲彈、裝備／載具的正式玩家存檔尚未建立。
- 可被挑選與保護規則：保護期、被攻擊冷卻、快照逾時門檻。
- Client 戰鬥結果的防作弊程度：目前只驗證數值邊界。
- 金幣系統補貼的營運上限與異常監控門檻。
- 跨 World 併發結算的扣款與帳本不一致：見第 11 節，處理方式尚未決定。

## 11. 已知限制：跨 World 併發結算的扣款與帳本不一致

> 狀態：已用實驗確認，處理方式尚未決定（2026-10-04）。

### 11.1 現行結算方式

玩家資料常駐在所屬 World 記憶體，每秒寫回資料庫。結算時攻方一定常駐在本 World，守方分兩種情況：

| 守方位置 | 做法 |
| --- | --- |
| 常駐在本 World | 直接改記憶體，扣款與入帳在同一個玩家鎖內完成 |
| 不在本 World | 讀**資料庫**中的守方金幣計算扣款與補貼；不改守方，改留一筆待套用的調整單 `PlayerGoldAdjustment`，與攻方入帳、結算紀錄、三筆帳本在攻方下一次寫回時同一交易落地；守方所屬 World 每秒輪詢調整單並套用，金幣不低於 0 |

調整單與攻方入帳放在同一個寫回交易，是為了當機時不會只有一邊生效。

### 11.2 問題

計算扣款時讀到的守方金幣，不含「尚未套用的調整單」，也可能落後於守方所屬 World 尚未寫回的記憶體異動。因此守方不在本 World 時：

- 兩筆結算只要都發生在守方 World 套用調整單之前，就會各自以同一個金幣數字計算扣款。
- 套用時金幣被夾在 0，實際扣得比帳本記錄的少，差額等於多發的金幣，帳本與餘額對不上。
- 守方 World 有未寫回的金幣異動時，單一攻方也可能以落後的數字計算扣款（扣款偏多或偏少）。

### 11.3 實驗結果

守方 5 金幣；兩個攻方分別在兩個 World（兩個 `MemoryGameStore` 共用同一個資料庫），同時各結算 `FixedRewardGold = 20`，攻方都已常駐、守方都不在本 World。連續執行 5 次結果相同：

| | 帳本記錄 | 實際 |
| --- | --- | --- |
| 守方扣款 | 5 + 5 = 10 | 5（第二筆套用時夾在 0） |
| 系統補貼 | 15 + 15 = 30 | 多發 35 |
| 攻方入帳 | 20 + 20 = 40 | 40 |

守方金幣不會變成負數。實驗用的臨時測試沒有保留；重現方式為上述情境，以兩個 `NewMemoryGameStore(mysqlStore, mysqlStore)` 並行呼叫 `SettleCombatGold`。

### 11.4 影響範圍

- 窗口約為守方 World 套用調整單前的時間（寫回與輪詢各約 1 秒），不是同一毫秒。
- 每多一筆重疊結算，多記的扣款最多為 `min(獎勵, 守方當時金幣)`；守方沒有金幣時差額很小。
- 系統補貼本來就會產生新金幣（見 6.3），此問題是補貼與扣款的分攤不精確，並使帳本多記扣款，不是新增一種發幣管道。
- 以前的 MySQL 版 `SettleCombatGold` 在單一交易內鎖定雙方，沒有此問題，但 production 沒有使用，已於 `0d403ea08` 刪除；其「併發戰鬥不得讓守方透支」測試因同一原因沒有移植。

### 11.5 尚未確認

- 配對時是否限制同一守方同時被多個攻方開局。目前只確認 `DefenderProtectionPeriod` 在結算後生效，擋不住結算前同時開的多場戰鬥。
- 實際營運中守方金幣通常高於還是低於獎勵，會決定此誤差的實際大小。

### 11.6 可選處理方式

| 選項 | 內容 | 成本與限制 |
| --- | --- | --- |
| 1 接受 | 文件註明限制，不改程式 | 零成本；帳本不可作為精確稽核依據 |
| 2 補沖正帳本 | 套用調整單被夾在 0 時，補寫一筆沖正帳本記下少扣的差額 | 小改動；帳本一致，多發金幣仍存在但可見 |
| 3 配對預約 | 守方被選為對手後預約（例如 Redis 鎖），結算完成前不讓第二個攻方選到 | 中等改動；從源頭避免重疊，需先確認候選索引的現有機制；預約逾時與 Session 過期要對齊 |
| 4 結算時鎖定守方 | 結算時在資料庫鎖定守方金幣，並把未套用的調整單算進去 | 大改動、不建議：攻方入帳是延後寫回，改成結算時立即寫資料庫會破壞調整單與入帳同交易落地的原子性 |
| 5 交給守方 World 扣款 | 攻方 World 請求守方所屬 World 在記憶體內扣款並回報實際金額 | 最大改動；需要新的 World 間通訊，守方 World 離線時要有備案 |

建議方向：先評估 3，必要時再加 2；若金幣不涉及稽核或真實金錢價值，可維持 1。
