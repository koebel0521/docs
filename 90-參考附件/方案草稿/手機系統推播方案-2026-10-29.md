# 手機系統推播方案（草稿）

狀態：方案草稿，尚未實作。2026-10-30 依現有程式重新審查，修正初版的錯誤假設（見第 2 節）。

目的：玩家離線時，在 Android／iOS 通知欄顯示通知，叫玩家回來。

## 1. 現況（已對照程式）

| 項目 | 現況 | 出處 |
|------|------|------|
| 對離線玩家的主動通知 | 沒有。即時推送只走 World → Gate 的 TCP，玩家不在線就沒有通道 | — |
| 戰鬥結算通知 | 已有。結算後替攻守雙方各寫一筆 `combat_settlement_notification`，玩家上線用 `ListCombatSettlementNotifications` 拉取。在線的守方也不會即時收到 | `internal/combat/match.go` 的 `settleAndNotify`、`cmd/world/internal/store/combatstore/notification.go` |
| 系統公告 | 存在 Redis，玩家用 `GET /notices?after=X` 增量拉取 | [系統公告](../../10-核心流程/系統公告.md) |
| GM 發道具 | **玩家必須在線**；離線回 `GrantPlayerOffline`，不排入 | `cmd/lobby/internal/gm/gm.go` 的 `Grant` |
| 玩家在線狀態 | Redis 的 `playerstore.PlayerState`（`WorldID`、`GateID`），GM 已用它判斷在線 | `gm.PlayerFinder` |
| RabbitMQ | 只用於 World → Record：World 先把事件寫進 MySQL `record_outbox_event`，再由 outbox relay 發布 | `cmd/world/internal/outbox/relay.go` |
| Lobby 資料庫 | Lobby 只連 Redis，沒有 MySQL | — |
| 玩家語系、時區 | Server 端沒有存。任務重置時區是全服設定 `day_reset.timezone`（原名 `mission_reset.timezone`，舊鍵保留一版） | `cmd/world/run.go` |
| 帳號清除 | 帶 `player_id` 的表統一在 `playerTables` 決定清除方式，新表必須登記，測試會檢查 | `cmd/world/internal/store/gamestore/mysqlstore/player_tables.go` |

## 2. 初版方案的錯誤與修正

| 初版寫法 | 問題 | 修正 |
|----------|------|------|
| GM 發道具給離線玩家時推播 | GM 發道具要求玩家在線，離線玩家根本不會被發到 | 移出第一批觸發事件。要支援離線發放是另一個功能 |
| 由 Lobby 跑 Push worker、查 token 表 | Lobby 沒有 MySQL，要它查 token 就要新增 DB 依賴 | 個人推播放在 World，全服公告由 Lobby 直接發 FCM topic，不需要 token |
| 新增 RabbitMQ `push.send` 佇列 | 多一個佇列與消費者。World 已有「MySQL outbox → 背景發送」的模式 | 沿用 outbox 模式，World 背景迴圈直接呼叫 FCM，不經 RabbitMQ |
| 公告每批 500 人分批推 | topic 是一次發給全部訂閱者，無法用人數分批 | 把 topic 依玩家 ID 切成分桶，逐桶間隔發送（見第 7 節） |
| Server 依玩家語系組文案 | Server 沒有存玩家語系 | Client 上報 token 時一起帶語系與時區偏移 |
| Push worker 自己做同類合併 | 要多寫合併邏輯與狀態 | 用 FCM 的 `collapse_key`（Android）與 `apns-collapse-id`（iOS）讓手機只留最新一則 |
| 「被攻擊」是新事件 | 戰鬥結算通知已存在 | 直接掛在 `settleAndNotify` 建立通知之後 |

## 3. 原則

- 推播只負責叫玩家回來，不傳資料。資料仍由既有的拉取機制提供，所以推播沒送到也不會漏資料。
- 玩家在線就不推播。
- 推播失敗不得影響遊戲主流程：不擋結算、不擋登入、不阻塞事件迴圈。
- 能沿用既有模式就不新增元件。

## 4. 技術選擇

兩個平台都走 FCM HTTP v1，不自行串 APNs。

- FCM 會轉送到 APNs，Server 只接一套。
- 套件：官方 `firebase.google.com/go/v4/messaging`。
- iOS 需在 Firebase 專案上傳 APNs Auth Key（`.p8`）。用 Auth Key 而不是憑證，憑證每年過期，Auth Key 不會。
- 費用：FCM 與 APNs 本身免費。需要 Apple Developer Program（約 US$99／年）與 Google Play 開發者帳號（一次性 US$25），上架本來就要有。Firebase 用免費的 Spark 方案即可。
- 不含中國大陸 Android。

## 5. 流程

### 5.1 Token 註冊

```
Client 取得 FCM token
  → Gate → World：RegisterPushToken(token, platform, locale, utc_offset_min, enabled_categories)
  → World 以 session 的 playerID 寫入，不從 payload 取 playerID
  → MySQL：以 token 為唯一鍵 upsert player_push_token
```

- 走既有的 World 玩家指令（`board.Handler` 形式），playerID 由 Gate session 帶入，玩家只能綁自己的帳號。
- token 會輪替。Client 每次啟動與 FCM 回呼 token 更新時都要上報。
- 玩家關閉通知、登出時，Client 送 `UnregisterPushToken`，Server 刪該 token。避免共用手機登出後還收到前一個帳號的通知。
- 速率限制：同一玩家每分鐘最多幾次，避免被拿來灌表。

### 5.2 戰鬥結算推播（第一批唯一的個人事件）

```
settleAndNotify 建立結算通知成功
  → 對守方寫一筆 push_outbox（與結算通知同一個 notification_id 當事件 ID）
World 背景推播迴圈（每秒）
  1. 領取待送的 push_outbox
  2. 查 Redis PlayerState：GateID != 0（在線）→ 標記略過
  3. 查玩家 token（含語系、時區、分類開關）
  4. 分類關閉、安靜時段 → 標記略過
  5. 依語系組文案，設 collapse key（同一玩家的戰鬥通知只留最新一則）
  6. 呼叫 FCM
  7. 處理回應：
       成功 → 標記已送
       UNREGISTERED、INVALID_ARGUMENT（token 錯）→ 刪 token
       QUOTA_EXCEEDED、UNAVAILABLE、INTERNAL → 指數退避重試，有次數上限
       超過 TTL（建議 1 小時）→ 放棄，計入指標
```

- 只推守方。攻方是發起者，一定在線。
- 為什麼寫 outbox 而不是結算後直接呼叫 FCM：結算的收尾已有自己的逾時與重送語意，直接打外部 HTTP 會拖長結算，World 重啟也會遺失。outbox 讓推播可重送、可去重。
- 每次結算都推一則；collapse key 讓手機上只留最新一則。
- 在線判斷在發送時才做，不在結算時做，所以玩家在 outbox 等待期間上線也不會收到。

### 5.3 系統公告推播

```
Lobby 建立公告（POST /admin/notices，多一個「是否推播」參數）
  → Lobby 依語系與分桶，逐一呼叫 FCM topic，例如 notice_zh-TW_b0 … notice_zh-TW_b9
  → 每桶間隔數十秒
```

- 不需要 token 表，Lobby 不需要 MySQL。
- Client 登入後訂閱自己語系、自己分桶的 topic：桶號 = `playerID % 桶數`。切換語系時先退訂舊的。
- 在線玩家也會收到系統通知。Client 在前景時可自行忽略，或改顯示遊戲內提示。
- 分桶與間隔見第 7 節。

### 5.4 玩家點通知後

App 啟動，走正常登入，再拉公告與戰鬥結算通知。通知 payload 帶 `type`（`combat`、`notice`）讓 Client 決定開啟哪個畫面。

## 6. 資料表

新增兩張，都放 World 資料庫。

```
player_push_token
  token          varchar(255)  主鍵
  player_id      bigint        索引
  platform       tinyint       1=Android 2=iOS
  locale         varchar(16)   例如 zh-TW
  utc_offset_min smallint      安靜時段用
  categories     int           位元旗標：bit0 戰鬥、bit1 公告
  updated_at     datetime

push_outbox
  event_id       varchar(64)   主鍵（沿用 notification_id）
  player_id      bigint
  kind           tinyint       1=戰鬥結算
  payload        json          組文案需要的參數
  attempts       int
  next_retry_at  datetime
  created_at     datetime
  sent_at        datetime NULL
```

- 以 token 為主鍵 upsert：同一支手機換帳號時直接覆寫 `player_id`，通知不會送到前一個人。
- 每個玩家最多保留 5 筆 token，超過刪 `updated_at` 最舊的。
- `updated_at` 超過 60 天的 token 定期刪除。FCM 文件說明 token 長期不活躍會失效，確切天數以 Firebase 文件為準。
- `push_outbox` 已送或已放棄的列保留短期（例如 7 天）後清除。
- 兩張表都要登記在 `playerTables`：`player_push_token` 屬於 `roleLiveOnly`，帳號清除時刪除；`push_outbox` 屬於 `roleRetained`，依自身保留期清除。封存（不活躍玩家）時 token 保留，玩家回來就能繼續收。
- 日誌只印 token 的前 8 個字元。

## 7. 大量推播與登入洪峰

只有全服公告會造成洪峰。戰鬥結算推播是個別玩家、隨時間分散，不構成洪峰。

專案實測的登入容量（出處：[容量與壓測基準](../../20-排障與監控/容量與壓測基準.md)）：

- Central 同時處理登入上限 64，超過回 code 9（可重試）。
- 同時 500 人登入平均 1.18 秒，被擋的重試 434 次後全部成功。
- 單一 Gate 未登入連線上限約 256（正式範本），超過會淘汰最舊的連線。
- 實測只到約 500 人同時登入。萬人級同時回來沒量過。

估算方式：每桶發送後實際點開的人數 ≈ 桶內在線外的玩家數 × 點擊率。點擊率通常是個位數百分比，但不要依賴這個數字。

建議：

1. 預設 10 桶、每桶間隔 60 秒。全服 5 萬人時每桶約 5000 人，若 10% 在第一分鐘點開，就是約 500 人同時登入，落在實測範圍內。
2. 桶數與間隔做成 Lobby 設定，可依玩家數調整。
3. 推播進行中提供中止。發送狀態存 Redis，Lobby 重啟不重送已送的桶。
4. 確認 Client 對 code 9 有退避重試，加隨機抖動。這是洪峰時能不能撐住的關鍵。
5. 上線前用 `tools/private` 壓測工具模擬「N 千人 60 秒內登入」，觀察 `game_login_total{result="busy"}` 與 Gate 未登入連線淘汰數。

## 8. 文案與平台差異

- 兩個平台都送 notification message，由系統直接顯示，App 沒在執行也看得到。Android 若只送 data message，App 被關閉時不會顯示。
- 文案由 Server 依上報的 `locale` 組，文案表放 PJA-Config。找不到語系時用預設語系。
- 公告文案在建立公告時就依語系組好，每個語系的 topic 各送一次。
- 文案不放金額、帳號等敏感資訊，因為會顯示在鎖定畫面。戰鬥通知只寫「你的基地被攻擊了」，不寫損失多少金幣。
- payload 上限 4KB，只放 `type` 與少量參數。
- Android 8 以上要建立通知頻道（戰鬥、公告分開），讓玩家在系統設定分別關閉。這是 Client 的事，但頻道 ID 要和 Server 送的一致。
- iOS 的角標數字（badge）第一版不做。

## 9. 安全與隱私

- FCM service account JSON 不進版控，走環境變數或 secret 掛載。只給 Firebase Cloud Messaging 權限，不給專案管理權限。
- `RegisterPushToken` 的 playerID 由 session 決定，不信任 payload。
- 對 token、locale 欄位做長度與格式檢查。
- token 與時區屬個人資料：帳號清除時刪除（`roleLiveOnly`），日誌只印前綴。
- 開發與正式使用不同 Firebase 專案，避免測試推播打到真實玩家。
- 行銷類推播第一版不做。日後要做時需玩家另外同意，並遵守 Apple 規範。

## 10. 維運與指標

- 指標：
  - `push_sent_total{kind,result}`：result 為 sent、skipped_online、skipped_quiet、skipped_disabled、invalid_token、failed、expired。
  - `push_outbox_pending`：待送筆數。
  - `push_send_duration_seconds`：FCM 呼叫延遲。
- 告警：失敗率持續升高（通常是憑證或 Firebase 設定錯誤）、`push_outbox_pending` 持續增加。
- FCM 呼叫設逾時（建議 5 秒），HTTP 連線數有上限。
- 推播迴圈套用既有的 panic 防護與關機流程（`appcore.TaskGroup`），關機時不等待未送出的推播，留給下次啟動。
- 功能開關：`push.enabled`，關閉時只寫 outbox 不發送。

## 11. 責任分界

| 項目 | 負責 |
|------|------|
| 取得 token、通知權限、通知頻道、訂閱與退訂 topic、點擊跳轉、code 9 退避重試 | Client（不在本專案工作範圍） |
| `RegisterPushToken`、`UnregisterPushToken` 訊息 | PJA-Protocol（`pkg/protocol` 為產生檔，不得手改） |
| `player_push_token`、`push_outbox` 表 | PJA-Database |
| 推播文案表 | PJA-Config |
| World 推播迴圈、結算觸發、Lobby 公告推播、token 清理、指標 | PJA-Server |

## 12. 待決策

1. 公告推播的分桶數與間隔預設值（建議 10 桶、60 秒）。
2. 安靜時段的時間範圍（建議當地 23:00～08:00），以及安靜時段內的推播是丟棄還是延後。建議丟棄，玩家上線仍能拉到結算通知。
3. 單一玩家保留的 token 上限（建議 5）。
4. 是否要支援 GM 對離線玩家發道具。這是另一個功能，不屬於推播。
5. 與 Client 負責人確認訊息欄位、topic 命名、通知頻道 ID 與 code 9 重試策略。

## 13. 建議實作順序

1. PJA-Database 新增兩張表，登記 `playerTables`。
2. World 推播迴圈與 FCM 呼叫，先用測試腳本直接寫入 token 驗證能送到真機。
3. PJA-Protocol 新增註冊與取消註冊訊息，World 加 handler。
4. 戰鬥結算觸發。
5. Lobby 公告推播與分桶。
6. 壓測登入洪峰，校正分桶參數。

## 14. 未驗證項目

- FCM 的發送配額、token 失效天數：以 Firebase 官方文件為準，本文未即時查證。
- 既有帳號在洪峰下是否仍受 bcrypt 併發限制：壓測文件只量過新帳號進場與 500 人同時登入。
- 點擊率與洪峰估算：沒有實際數據，只供設定初始值。
