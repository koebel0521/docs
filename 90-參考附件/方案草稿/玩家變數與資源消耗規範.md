# 玩家變數與資源消耗現行規範

## 文件狀態

本文件是玩家變數、貨幣與資源消耗系統的現行規範；未完成項目會在對應段落明確標示。

已確認的同步策略：

- 玩家登入時，Server 傳送完整的 Client 可見變數。
- 登入後，Server 只傳送本次有變動的變數。
- Client 只接受 Server 傳回的值，不可自行修改權威數值。

## 1. 設計原則

### 1.1 變數系統只負責通用數值

Variable System 管理玩家的：

- `VariableID`。
- `int64` 數值。
- Default、範圍與保存設定。
- Server Runtime 的數值檢查。
- Client 同步變更。

Variable System 不應知道變數代表金幣、鑽石、進度或次數，也不應在程式內針對特定 `VariableID` 寫入業務規則。

適合放入 Variable System 的資料是「單一 ID 對應單一數值」；背包、任務清單、建築物、英雄與裝備等複合資料仍由各自的 Domain 管理。

### 1.2 Domain System 負責業務規則

金幣由 Currency System 管理，道具由 Inventory System 管理，消耗協調由 Cost System 管理。

```text
Shop / Building / Craft / Gacha
              ↓
         Cost System
       ┌──────┴──────┐
       ↓             ↓
 Currency System  Inventory System
       ↓             ↓
       Variable      PlayerItem
```

### 1.3 Server 是唯一權威來源

Client 可以顯示金額、預估消耗與按鈕狀態，但不能決定：

- 玩家實際擁有多少金幣。
- 本次要扣除多少金幣。
- 商店商品價格。
- 是否有足夠資源。
- 購買是否成功。

Server 必須依照自己的設定資料重新取得價格並重新驗證。

## 2. Luban 變數定義

### 2.1 Variable ID

Variable ID 使用 Luban 產生的 enum，不使用字串作為 Runtime Key。

概念上：

```text
Shared.VariableID.Gold = 1001
```

使用 enum 的原因：

- Client、Server 使用相同 ID。
- 避免字串拼寫錯誤。
- 減少封包與索引成本。
- 讓程式碼可以直接表達變數用途。

### 2.2 變數型別與範圍

Server Runtime 的變數值統一使用 `int64`。

Luban 欄位使用 `#range` 表示企劃資料的合法範圍，例如：

```text
long#range=[0,999999999]
```

`#range` 的責任是產檔時驗證企劃資料；Server Runtime 仍必須重新檢查運算結果。

已驗證目前 Luban 5.0.0 的自訂模板可以透過 `field.type` 取得完整型別字串，例如：

```text
long#range=[0,999999999]
```

因此可以由自訂模板解析 `#range`，產生 Server 使用的範圍常數或範圍資料。這些產生檔仍屬於 Luban 產物，不得在 PJA-Server 手動修改。

### 2.3 不額外增加 Min／Max 資料欄位

Variable 定義不需要另外增加：

```text
minValue
maxValue
```

範圍直接放在 Luban 型別：

```text
long#range=[0,999999999]
```

模板產生的範圍資料只供 Runtime 驗證使用。

### 2.4 Default 與初始金幣分工

目前新玩家的初始金幣仍由既有的：

```text
GameRules.InitialMoney
```

決定。

Variable 的 Default 是「資料不存在時的有效預設值」，不取代 `GameRules.InitialMoney`。因此兩者責任不同：

```text
建立新玩家       → GameRules.InitialMoney
查不到 Variable  → Variable Default
```

## 3. Variable System

### 3.1 Runtime API

第一版需要的通用操作：

```text
Get(playerID, variableID)
Set(playerID, variableID, value)
Add(playerID, variableID, delta)
```

每次寫入必須依序：

```text
確認 VariableID 存在
        ↓
讀取玩家值；沒有資料時使用 Default
        ↓
檢查 int64 overflow
        ↓
檢查 Luban 產生的範圍
        ↓
寫入玩家值
        ↓
產生變更資料
```

超出範圍時必須拒絕操作，不得自動 Clamp 成上下限。自動 Clamp 會掩蓋業務錯誤。

### 3.2 資料保存

採用 Sparse Storage：只保存與 Default 不同的玩家變數。

概念資料表：

```text
player_variable
├─ player_id
├─ variable_id
├─ value
└─ updated_at
```

主鍵：

```text
(player_id, variable_id)
```

讀取規則：

```text
DB 有資料       → 使用 DB value
DB 沒有資料     → 使用 Luban Default
```

若數值被修改回 Default，可以刪除該筆資料，讓資料表維持稀疏。

### 3.3 金幣不使用延遲 Dirty Save

金幣涉及商店、交易與道具發放，不可只依賴記憶體 Dirty Save 或非同步寫回。

扣除金幣、給予道具與完成商店操作必須在同一個可靠交易中完成，避免 Server 崩潰造成：

- 已扣金幣但沒有取得道具。
- 已取得道具但沒有扣金幣。
- 同一筆購買重複執行。

## 4. Currency System

### 4.1 責任

Currency System 是 Variable System 上層的貨幣業務模組，負責：

- 取得貨幣餘額。
- 增加貨幣。
- 扣除貨幣。
- 判斷餘額不足。
- 傳入異動原因與關聯資料。

Variable System 不判斷「餘額是否足夠」；它只負責執行通用範圍限制。金幣最低值為 0 時，`Min = 0` 是最後一道資料不變性防線，餘額不足則由 Currency System 先判斷並回傳錯誤。

### 4.2 異動上下文

所有重要貨幣變更必須帶有：

```text
Reason
ReferenceType
ReferenceID
```

例如商店購買：

```text
Reason        = ShopPurchase
ReferenceType = ShopItem
ReferenceID   = Shop Interaction 或商品識別
```

這些資料供錯誤排查、對帳與異動紀錄使用。

## 5. Cost System

### 5.1 責任

Cost System 負責協調「一次操作需要消耗哪些資源」，但不直接持有金幣或道具，也不繞過 Currency／Inventory 的業務 API。

第一版支援：

```text
Currency
StackItem
```

暫不支援具有獨立 InstanceID 的裝備或實體物件。現有 `PlayerInventoryItem` 是堆疊道具資料，適用於 `StackItem`。

### 5.2 Cost 資料

概念結構：

```text
Cost
├─ Type
├─ ID
└─ Amount
```

範例：

```text
Currency / Gold / 500
Item     / 1001 / 2
```

Cost 的數量使用 `int64`。網路封包使用的型別與編碼另依 Protocol 規範處理。

### 5.3 Normalize

執行 Check 或 Consume 前，先合併相同資源：

```text
Gold 100
Gold 200
Item 1001 × 2
Item 1001 × 3
```

整理為：

```text
Gold 300
Item 1001 × 5
```

### 5.4 Check 與 Consume

可以提供兩個 API：

```text
Check(costs)
Consume(costs, context)
```

`Check` 可供 UI 預覽或顯示缺少的資源，但不能把 `Check` 與 `Consume` 當成兩筆獨立交易。

真正消耗時，`Consume` 必須在同一個交易內完成：

```text
Normalize
    ↓
Check 所有 Currency／Item
    ↓
全部扣除
    ↓
執行操作結果
    ↓
Commit
```

任何一項不足或任何後續操作失敗，整筆交易 Rollback。

## 6. 商店購買流程

商店只能在玩家擲骰後停留於商店終點時產生操作機會。經過商店不產生商店事件。

```text
Client 發送 Purchase + InteractionID
              ↓
Server 驗證玩家目前有有效 Interaction
              ↓
Server 依設定資料取得商品與價格
              ↓
建立 ShopPurchase Context
              ↓
Cost System Normalize + Check
              ↓
Currency System 扣除 Gold
              ↓
Inventory System 增加商品
              ↓
標記 Interaction 已完成
              ↓
Commit
              ↓
建立 ChangeSet
              ↓
回傳結果與變動資料
```

Client 不得傳送可信任的商品價格或扣款數量。Client 傳送的 `InteractionID` 只用來指定目前操作的商店互動，Server 必須重新查詢並驗證。

跳過流程：

```text
Client 發送 Skip + InteractionID
              ↓
Server 驗證有效 Interaction
              ↓
標記 Interaction 已完成
              ↓
回傳 Skipped
```

跳過不修改金幣與道具。

## 7. 交易與冪等

商店購買必須具備以下保護：

- 同一個 Interaction 只能完成一次。
- 同一個操作請求重送時，不得重複扣款或重複發道具。
- 金幣扣除、道具增加與 Interaction 完成必須同時成功或同時失敗。
- 資料庫寫入使用明確的 Transaction。
- 重要貨幣異動保留 `OperationID`、Before、Delta、After、Reason 與 Reference。

## 8. Client 同步

採用「登入完整同步，執行中只同步變動」的方案。

### 8.1 登入

`LoadPlayerResponse` 傳送所有 `SyncClient=true` 的變數：

```text
Gold = 5000
Energy = 20
TutorialStep = 3
```

Client 建立本機變數快照。

### 8.2 Runtime 變更

商店購買扣除 500 金幣後，只傳：

```text
Gold = 4500
```

傳送變更後的完整值，不傳送 `Delta = -500`。Client 收到後直接覆蓋指定 VariableID 的本機值。

### 8.3 ChangeSet

一次 Server 操作完成後，先收集本次所有變更，再由操作結果統一回傳：

```text
ChangeSet
├─ VariableUpdates
└─ InventoryUpdates
```

Cost System、Currency System 與 Inventory System 不直接送封包。它們只產生變更資料，由最外層的操作流程統一組裝 Protocol 回應。

## 9. Protocol 原則

Protocol 需要能表達：

```text
VariableID
最新值
```

登入結果使用完整清單；商店購買、擲骰或其他操作結果使用本次變更清單。

Protocol 仍由 `PJA-Protocol` 的 XML 產生，PJA-Server 不手動修改生成的 Go 程式碼。第一版沿用現有封包生成與封裝方式，不因 Variable System 先加入新的變長整數格式。

只有實際量測到變數同步成為流量問題時，才評估另外導入 VarInt 或其他封包壓縮方式。

## 10. 第一版範圍

納入：

- `VariableID` enum。
- `int64` Variable Value。
- Luban `#range` 與模板產生 Runtime 範圍資料。
- Sparse `player_variable` 保存。
- Gold Currency System。
- Currency 與 StackItem 的 Cost System。
- 商店購買的原子交易。
- ChangeSet。
- 登入完整同步與 Runtime 變動同步。
- 金幣異動原因與冪等識別。

暫不納入：

- Item Instance 消耗。
- 多型 Variable Value，例如 string、float、任意 JSON。
- 每日／每週 Variable Reset。
- 非同步金幣保存。
- Reward Manager。
- 通用 Plugin／Handler 註冊框架。
- 為節省封包而改用 VarInt。
