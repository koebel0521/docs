# 全專案優化審查 2026-10-14

> 只讀審查，未改任何程式。目標：找出「還沒被處理」的效能與精簡機會，每條附最優方案（非最小補丁）。
> 方法：主審先讀網路層與各服務入口；再分六區並行深審（World、internal 遊戲核心、Central、Gate/Chat/Lobby/User/Record、pkg 基礎層、建置/依賴/CI/測試/工具），每區跑逃逸分析、既有 benchmark 與零引用普查；主審再逐條核實關鍵發現。

## 0. 總結

- 網路層每則訊息熱路徑（tcpsocket／framecodec／msg）實測 0 allocs/op，先前優化全部成立。剩餘空間不在 CPU，在 **每次登入／每則指令的 MySQL／Redis 往返數**、**背景無條件寫入**、**每連線一次性配置**、以及 **CI 的重複工作**。
- 共 48 條發現：效能 22、精簡／死碼 14、建置／CI／測試 12。前 12 條（§1）為高信心、改完可量測的項目。
- 三條需產品決策：Gate 頻道投影整套無生產者（刪或補 World 端）；Chat 批次投遞與 Central→World 批次登出需改 PJA-Protocol；產生器層的 Reset／就地解碼改法屬跨 repo。

## 1. 效能（依效益 × 信心排序）

### ★1 World 登入多付 ~7 次 MySQL 往返，且同步做戰鬥快照與任務修復
- 位置：`cmd/world/internal/store/gamestore/memory_passthrough.go:87-119`（`InitializePlayer*`、`residentProfileExists`、`TouchLoginActivity`）、`memory_store.go:254-283`（`delegate`）、`mysql_player_variables.go:34-74`、`cmd/world/internal/services/board_router.go:222-247`（`loadPlayer`）。
- 問題：`TouchLoginActivity` 走 `delegate`（flush → 卸載玩家），接著 `LoadPlayerRequest` 的 `InitializePlayerWithConfigVersion` 看到玩家不常駐 → 再 `delegate` → 完整初始化交易（BEGIN、SELECT…FOR UPDATE、INSERT IGNORE ×3、UPDATE、COMMIT ≈ 7 RTT），對回鍋玩家全是 no-op。同一請求再同步 `PublishCombatSnapshot`（MySQL upsert + Redis SADD）與 `repairMissions`（JOIN SELECT）。合計登入 ≈ 11 RTT，≥ 7 可省。
- 最優方案：
  1. `InitializePlayer*` 改 `lockLoaded`（快照下一步反正要載）；`data.ProfileExists` 且金幣列存在就直接 return，否則才 `delegate`（新玩家／封存還原不變）。
  2. `TouchLoginActivity` 不經 `delegate`：只動 `player_profile.updated_at`，與常駐資料無衝突。
  3. `PublishCombatSnapshot` 排進 `combatRefresher`；`repairMissions` 每位常駐玩家只做一次（`residentPlayer` 加旗標）。
- 驗證：擴充 `mysql_login_concurrent_integration_test.go` 斷言「回鍋玩家登入 + LoadPlayer 的 SQL 句數」。

### ★2 每則盤面指令無條件重發戰鬥快照
- 位置：`cmd/world/internal/services/board_router.go:206-220`（`withCombatRefresh`）、`combat_refresher.go`、`combat_snapshot.go:93`（`Version: at.UnixNano()`）。
- 問題：快照只有 `OwnedAmmo` 與 `CarryCapacity` 會變，但 Version 每次都新，`SaveMany` 的 `IF(VALUES(snapshot_version) >= …)` 必成立 → 每則 roll/shop/useItem/upgrade 各寫一列 MySQL 並 SADD；輕載時批次大小為 1。背景建快照另做 3 次玩家鎖。
- 最優方案：`combatRefresher` 保留 `published map[int64]{ownedAmmo, carryCapacity, eligible}`，算出快照與上次相同就略過；map 以 2×maxPlayers 清空或由 `EvictPlayer` 刪除。
- 驗證：單元測試同一玩家連續兩次相同狀態只 `sync` 一次。

### ★3 每位玩家每秒寫回交易固定帶 3 句 no-op SQL（≈ 30% RTT）
- 位置：`gamestore/mysql_player_snapshot.go:59-65`（每次 flush touch `updated_at`）、`memory_board.go:187,380` + `memory_tx.go:121-123`（`setConfigVersion` 無條件寫）、`mysql_player_board.go:58-99`（`pruneStaleRoadStars` 每次 Pluck）。
- 問題：道路星星歸零是 `RoadStars[id] = 0` 不是刪鍵，prune 幾乎永遠無事可做；config_version 只在換版時變；`updated_at` 只服務 90 天封存門檻。一次擲骰 flush ≈ 9–10 RTT。`memory_store.go:28` 實測「400 位玩家一輪寫回 0.72s」即每位 28ms，往返數是主因。
- 最優方案：`PlayerChanges` 加 `RoadStarsRemoved`，只在鍵集變動時 prune；`setConfigVersion`／`setVariable`／`setItem` 值等於 base 且未在 changes 時略過；`residentPlayer` 記 `lastTouched`，每 10 分鐘或登入／登出才 touch。
- 驗證：`mysql_save_changes_bench_integration_test.go` 比句數。

### ★4 玩家 socket 先配 10000 深 `sendCh` 再整個換掉：每條連線 160 KB 純垃圾
- 位置：`pkg/tcpsocket/socket_factory.go:55-63`（`make(chan …, maxSendQueueDepth)` 在套用 opts 之前）、`socket.go:49-55`（`WithSendQueueDepth` 再 `make`）、`cmd/gate/internal/services/userserver.go:51-58`。
- 問題：`ServeConn` 以預設 `DefaultSocketSendQueueDepth = 10000` 建 socket（160 KB channel 緩衝），option 立刻換成 1024。重連風暴 10k 玩家 ≈ 1.6 GB 瞬時垃圾。
- 最優方案：`Socket` 加 `sendQueueDepth` 欄位，option 只設值；`NewSocket` 在 opts 迴圈之後才 `make`。
- 驗證：benchmark `NewSocket(..., 10000, WithSendQueueDepth(1024))` B/op 由 ~160 KB 降到 ~16 KB。

### ★5 每次擲骰 clone 100 筆科技並逐筆解析兩個效果，但一回合最多只開始一筆
- 位置：`internal/game/boardconfig/effects.go:21-47`（`EffectiveDefinition`）、呼叫點 `internal/game/turn/turn.go:74`、唯一消費 `internal/game/board/roll.go`（`startResearch`）。
- 證據：真實設定微基準 `EffectiveDefinition` 11,794 ns／17,864 B／12 allocs；整個擲骰 `roll` 只要 1,688 ns／2,245 B。前處理比擲骰貴 7 倍。
- 最優方案：不 clone。`board.Definition` 加 hook `ResolveTechnology func(ResearchTechnology) (ResearchTechnology, error)`，`startResearch` 只對那一筆解析；`EffectiveDefinition` 只解析一次 `FactoryProductionSteps`；刪 `memoizeResolver`；`simulation/runner.go:129-139` 改呼叫同一 hook。預期 ~12 µs/17.8 KB → < 0.5 µs/< 1 KB。
- 驗證：`boardconfig`、`turn`、`board`、`simulation`、`cmd/world/internal/board` 擲骰測試；補真實 tables 的 benchmark。

### ★6 建築升級每次線性掃 2000 列並配置 ~300 KB（在玩家交易鎖內）
- 位置：`internal/game/boardconfig/upgrade.go:31-55`（`PlanBuildingUpgrade`、`BuildingIDsAt`、`boardBuildingLevels`）、`internal/game/board/building.go:32-72`（`UpgradeBuilding`、`buildingLevelsAt`）、呼叫點 `gamestore/memory_board.go:360-362`。
- 證據：真實 2000 列 `BuildingIDsAt` 16,546 ns／158 KB；`PlanBuildingUpgrade` 18,775 ns／158 KB；一次升級合計 ~35 µs、~317 KB 垃圾。
- 最優方案：載入期建索引 `*BuildingCatalog{byBoard: map[int]{ids []int32; next map[[2]int32]int; max map[int32]int}}`，`Plan`／`IDsAt` 變 O(1)；`board.UpgradeBuilding` 改收 `maximums` 與 `has(id, level)`；`gameconfig.Bundle.BuildingUpgrades` 改存 catalog（World 與 simulator 一起換）。
- 驗證：`board/building_test`、`boardconfig/upgrade_test`、gamestore 升級測試、simulation building 測試。

### ★7 Central 登出在單一事件迴圈同步等 4 次 Redis 往返；路由快取無冷卻
- 位置：`cmd/central/internal/handler/gate/on_logout_gate_to_central.go:37-57`、`flow/logout/{coordinator.go:65,preflight.go:34,normal.go:26,33}`；`store/routingcache/routingcache.go`。
- 問題：單人登出依序 GET（登出 journal）→ GET（登入 journal，常態必 nil）→ EVALSHA（compare-and-delete）→ SET（journal），全同步；Redis RTT 1 ms 時 250 登出/s 即吃滿迴圈（同迴圈還有每秒 TimeSync 廣播）。journal 後端失敗有 10 s 冷卻，routingcache 沒有：Redis 卡住時每則登出停 `routingCacheTimeout` 3 s。
- 最優方案：登入 journal 改無條件 DEL 併入 pipeline；`[EVALSHA deleteIfGate, SET logout journal, DEL login journal]` 一次 `DoMulti`（rueidis `Lua.ExecMulti`）；journal 寫入改 `StoreDeferred` 交 `GoBackground`（World 已如此）。EVAL 保持同步（防快速重登刪錯路由）。迴圈同步往返 4 → 2。routingcache 搬入 journal 的 `backendDownUntil` 冷卻模式。
- 驗證：`flow/logout` 既有測試；Redis 延遲注入量 handler timer p99；停 Redis 後 `Update1s` 仍每秒觸發。

### ★8 gorm 追蹤插件在追蹤停用時仍每句 SQL 付 7 allocs／212 ns
- 位置：`pkg/mysql/mysql.go:263-290`（`startSpan` → `db.InstanceSet`；`endSpan` → `InstanceGet`）。
- 證據：gorm v1.31.2 `InstanceSet/Get` = `fmt.Sprintf("%p", stmt)+key` + `sync.Map` Store/Load；微基準 212.6 ns/op、352 B/op、7 allocs/op。`tracing.StartSpan` 停用／未取樣時已回同一 ctx 與靜態 noop，plugin 未判斷。
- 最優方案：`startSpan` 內 `if ctx == db.Statement.Context { return }`（2 行歸零）；進一步把 `end` 放進 `context.WithValue`，取樣路徑 7 → 1 alloc，不再依賴 gorm 內部 `%p` 鍵。
- 驗證：`pkg/mysql` 既有測試；integration 容器量 `db.First` allocs/op。

### ★9 Chat 房間 fan-out 逐（Gate, 玩家）各送一幀
- 位置：`cmd/chat/internal/handler/gate/send.go:62`、`broadcast.go:24-65`、`cmd/gate/internal/handler/chat/event.go:67-88`。
- 問題：N 位成員 = N 個 `Deliver`、N 次 payload 複製、N 個 S2S frame；Gate 端 N 次解碼與事件分派。200 人房、10% 以限流上限 2 msg/s 發言 → Chat→Gate 每秒 8k frame，只為 40 則訊息。
- 最優方案（需 PJA-Protocol）：新增 S2S `ChatDeliverBatch{MessageID, SenderPlayerID, RoomID, TargetPlayerIDs []int64, Payload}`；Chat `RoomTargetsByGate(roomID)` 一次 RLock 分組，每 Gate 一幀；Gate 對每個目標 `ByID` 後建 client `ChatDeliver`。過渡期 Gate 保留舊 handler。
- 驗證：100 人房基準比 Chat→Gate frame 數與 Gate `HandlerDuration`。

### ★10 經過次數變數每回合逐一 `Get`，每個 Get 付 7 次鎖
- 位置：`internal/gamecore/variable/service.go:121-137`（`Get`）、`:304-315`（`ensureMigrated`）、`internal/game/boardconfig/conditions.go:250-269`（`PassedCountValues`）、呼叫點 `cmd/world/internal/services/board_router.go:380-400`。
- 問題：每個 `Get` = keyLock + `ensureMigrated`（readPlayer：全域 RLock ×2 + 玩家鎖）+ `LoadVariable`（再一次 readPlayer）；一次擲骰 4–6 種格子 → 28–42 次鎖，全在 `SaveRoll` 交易之前。`Snapshot` 已有批次版，`Get` 沒有。
- 最優方案：`variable.Service` 加 `Values(ctx, playerID, ids) ([]int64, error)`（遷移檢查一次、`batchStore.LoadVariables` 一次）；`PassedCountValues` 改批次簽名，內部以固定陣列累計；`Service` 以 `(playerID, configVersion)` 記住已遷移，跳過往返。鎖數 28–42 → 7。
- 驗證：`passed_count_overrides_test.go`、`variable` 測試、`-race` 跑 board_router。

### ★11 戰鬥結算多一次 DB 往返、四次無用 JSON 解碼
- 位置：`internal/combat/match.go:251-301`、`internal/combat/store/session.go:91-130`（`ClaimSettlement`）、`:247-256`（`sessionRecord.session()` 解兩份快照）。

### ★12 `SendQueueDepth` gauge：每則送出在共用 word 做 2 次 CAS 迴圈，事件迴圈直接付 ~60 ns

### 13 任務事件分派 N+1
- 位置：`cmd/world/internal/mission/record_event.go:62-78`、`gamestore/mission_event_prefetch.go:27-57`、`memory_mission.go:152-174`、`mission/progress.go:47-51`。
- 問題：預查只信「已存在」，「不存在」一律鎖內重查；N 個命中任務 = N 次玩家交易 + N 次 `LoadMissionEvent` + N 次 `LoadPendingMissionClaims`；自動任務帶條件時先做一次丟棄結果的 precheck。dev 設定任務 ≈ 0 所以現在無感，正式設定線性放大。
- 最優方案：一個事件一筆玩家交易 `ExecutePlayerMissionEventsWithView`，鎖內用 changes/pending/inflight 過濾後一句 `LoadMissionEvents` IN；刪 `PrefetchMissionEvents` 與 ctx value；precheck 改明確 `EnsureMigrated` 或拿掉。保住「單一任務失敗不擋其他任務」。

### 15 Gate：`SendAll` 當單播、`LeaveAllChat` 無條件送、Session 為讀一欄整份 clone
- 位置：`cmd/gate/internal/handler/user/on_chat.go:35,48,79,93`、`flow/user/flowbase/helpers.go:92-103`；`flow/user/login/coordinator.go:42,80`、`flow/user/logout/preflight.go:27`、`handler/user/disconnect_cleanup.go:25-30`。

### 16 Central：Gate 斷線單一 EVAL 帶全部 key、對 World 一人一幀；稽核深拷貝全表

### 17 pkg：預序列化訊息多一次複製；`chat.System.Reset` 不保留容量；斷線路徑未守門 Debug；framecodec 3 次 ReadFull
- `socket_send.go:85-101`：`OwnedRaw`／`Raw`／`packedMsg` 已是 wire bytes 仍 memcpy 進 `sendBuf`，大廣播讓每條 socket 永久占 64 KB → `Socket` 加 `hdr [6]byte`，小於 `w.Available()-6` 時兩次 `w.Write`，大於時 `Flush` 後 `net.Buffers{hdr, payload}.WriteTo(conn)`（writev 一次 syscall）。
- `pkg/msg/chat/chat_codec.go:64-67`：`System.Reset` 整份歸零 → 比照 `Deliver` 用 `msgpool.Retain`（benchmark 94 ns/256 B/1 alloc → 0）。
- `socket_receive.go:26,63,67,78`：4 個 `logger.Debug` 未守門，每次玩家斷線 4–5 allocs → 包 `IsDebugEnabled` 或刪 EOF 分支（`close()` 已記）。
- `framecodec/coder_decode.go:97-126`：size／id／payload 三次 `ReadFull` → `buf[4:]` 一次讀；對 `*bufio.Reader` 用 `Peek(6)+Discard(6)` 省借小池。效益 ~10–20 ns/frame，排最後。

### 18 internal：效果快照雙轉換；抽獎每請求重建 HMAC

- `internal/gamecore/lottery/random.go:582-626`、`cmd/world/internal/lottery/lottery.go:151-190`：每個 `DrawRequest` 複製 secret、`hmac.New` 金鑰展開、每個 multiplier clone 兩個 map → `sync.Pool` 的 `hmac.Hash`、`Definition.DrawN`。

- `redis.go:129-132`：`ReplayCapacity=4096` 在 Central 150 登入/s 只留 27 s（TTL 2 m）→ 容量 = 速率 × TTL，各服務建構時傳入。
- `store/sharedstate/sharedstate.go:68-79`：`Client.Exists` 改收 `keys ...string` 一次 EXISTS。

### 20 登入路徑 5–6 次 Redis 往返可併成 2 次，但 bcrypt 才是瓶頸
- bcrypt cost 10 實測 38.7 ms/compare，`bcryptSlots = NumCPU/2` → 本機上限約 155 登入/s；Redis 合計 3–6 ms。合併 `SETNX+GET`、`Write+SET+EVALSHA` 只改 p50 延遲 5–7%。除非 cost 調降（安全決策）否則效益低。

## 3. 建置／CI／測試

### ★27 CI 四個 stage 純串行，`build` job 只是重複編譯
- `.gitlab-ci.yml` stages build→lint→test→post-test，只有 `coverage-report` 有 `needs`；`build` 用 `-trimpath -pgo` 編譯，GOCACHE 產物與測試 job 的 action ID 不同，完全不能重用，且 `go build ./...` 不留產物。無 `interruptible`。
- 方案：`default: interruptible: true`；lint／govulncheck／trivy／compose-config／unit／integration／e2e 全加 `needs: []`；刪 `build` job；刪 `unit-checks`（`go vet` 與 lint 的 govet 重疊、編譯已由 unit 分片做），`go run ./tools/configaudit` 移到 lint job 末尾。pipeline wall 由「三段相加」變「最慢一段」。

### ★28 `integration` job 用 `-race` 把 4,906 個單元測試整套再跑一次
- `.gitlab-ci.yml:244`：`-tags=integration` 只「加入」196 個檔（217 個測試），不排除一般測試；重跑成本 ≈ 300 s × 2.5 ≈ 750 CPU-s + 183 個測試二進位的 race 編譯。
- 方案：job 內以 `grep -rlE '^//go:build integration'` 產生套件清單與 `-run "^(Test…)$"` 名單，只跑整合測試。

### ★29 快取：golangci-lint cache 沒存、單一 key 被 11 個 job 互相覆蓋
- `GOLANGCI_LINT_CACHE` 未設（本機冷／熱 lint 47 s／5 s）；所有 job 共用一把 key 且 pull-push，同 key「最後完成者覆蓋」。
- 方案：GOMODCACHE 用 `key.files: [go.sum]` 全部 `pull`、只 lint pull-push；GOCACHE 用 `key: "$CI_JOB_NAME_SLUG-$CI_COMMIT_REF_SLUG"` + `fallback_keys` 指 develop；lint job 加 `GOLANGCI_LINT_CACHE` 納入 paths。

### ★30 生產碼寫死的 ticker 讓六個測試純等 35 秒
- `cmd/world/internal/gm/capability.go:21-22`（`ttl/3` = 10 s ×2）、`cmd/gate/internal/handler/user/session.go:12-15`（5 s ×2）、`cmd/world/internal/handler/gate/lifecycle.go:52`（5 s）；另 `cmd/record` Sleep 1200 ms、`pkg/s2sauth` Sleep(1 s)×4。
- 方案：`testing/synctest`（倉庫已有 33 個測試檔在用）包住啟動，假時鐘下 ticker 立即觸發，不動生產碼。目標 `-run 'TestAnnounceGrantItem|TestSweepSessions|TestSweepUnavailableGates'` < 1 s。

### ★31 `tool` 指令把 5 個工具的整棵樹塞進主 module graph
- `go list -m all` 445 個 module，程式＋測試實際用 67；go.mod 222 條 `// indirect` 只有 34 條被程式用到；go.sum 686 行中 508 行屬工具；trivy 掃 go.mod 的 indirect 會因 linter 用的 logrus／zap／grpc／gopher-lua 等 CVE 擋合併。
- 方案：`go get -tool -modfile=go.tool.mod <5 個工具>@<現版本>`，主 go.mod tidy 刪 tool 區塊與 ~190 條 indirect；Makefile／CI／pre-commit 6 處改 `go tool -modfile=go.tool.mod …`；lint job 加 `go mod tidy -modfile=go.tool.mod && git diff --exit-code`。Renovate 要加 `managerFilePatterns`。預期 module ≈ 70、go.sum ≈ 180 行。

### 32 `.dockerignore` 漏掉 4.9 GB 的 `protocol_records/` 與 154 MB 的 `bin/`
- 六次 `docker build … .` 每次走訪／雜湊整個 context。補 `protocol_records/`、`bin/`、`spill/`、`.pgo-profiles/`；六次 build 改一次 `docker buildx bake`。

### 33 unit 分片按目錄切，最重分片是最輕的 9 倍
- 無 race 總和 pkg 71.5 s／cmd 169.4 s／internal 18.2 s／tools 40.0 s；cmd 內 world 58.8、gate 34.8、lobby 26.1、central 24.5。

### 34 建置旗標：未 strip、CGO 未釘、`make build` 不產二進位、PGO 只來自 benchmark

### 35 生成碼漂移檢查只在 `vX.Y.Z` tag 跑
