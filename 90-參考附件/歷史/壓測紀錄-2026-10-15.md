# 壓測紀錄 2026-10-15

本機（loopback、單機）壓測與告警校準紀錄。工具在 `tools/private/`（不進版控）；dev Prometheus 在 `127.0.0.1:39090`，改規則後 `POST /-/reload`。

## 環境與限制

- 全部同機 loopback，沒有網路延遲，結果只當下界參考。
- Gate 對單一來源 IP 有連線數（100）、接入速率與登入嘗試限流，壓測用 `127.0.x.y` 多來源 IP 繞過（`loadtest -source-ips`、`soakload`、`chatload`、`cmdload` 內建）。
- Prometheus 計數有約 15 秒抓取延遲，要即時值直接看服務 `/metrics`。

## 第 1 步：登入與連線容量

| 人數 | 來源 IP | 成功 | 錯誤 | p95 登入 |
|---|---|---|---|---|
| 300 | 8 | 300 | 0 | 16ms |
| 600 | 16 | 600 | 0 | 14ms |
| 2000（`max_connections` 4096） | 64 | 2000 | 0 | 15ms |

- `max_connections: 1024` 時 1200 人只成功 1024，其餘 `rejecting connection: at capacity`；dev 設定已改 4096。
- gate heap 約 70–80KB／連線、goroutine 約 3／連線。

## 第 2 步：soak（登入＋擲骰常駐）

- 1500 人、20 分鐘、每人約 10 秒擲骰：0 失敗、goroutine 與 RSS 持平、heap 為 GC 鋸齒，無洩漏，無告警觸發。擲骰 p50 約 1.57ms、p99 約 5ms。
- 3800 人、6 分鐘：gate goroutine 11450、heap 峰值約 302MB、RSS 約 540MB、擲骰 p99 6–23ms、0 失敗。

## 第 3 步：聊天與盤面指令、重連洪水

- chatload（200 人、每人 40 則）：廣播投遞約 6779 次／秒，延遲 p50 10.5ms、p99 23.9ms。
- Central `maxConcurrentLogins = 64`：同時登入超過 64 立刻回 `AuthServiceUnavailable`（code 9，可重試），`game_login_total{result="busy"}` 計數。500 人同時登入，434 次重試後全數成功，平均登入總耗時 1.18 秒。
- LoadPlayer 尾延遲：新帳號 p99 1.44s、已存在帳號 0.30s、常駐 6ms。每次 LoadPlayer 都會跑一次 `InitializePlayer` 交易（含 `SELECT FOR UPDATE`）。是否加「已初始化就跳過」快取待決策（會動死結敏感程式）。

## 已調整的告警（`monitoring/prometheus/alert-rules.yml`）

- `GameMemoryPressureHigh`：舊的 `heap_inuse / next_gc` 比值在 GC 鋸齒下常態接近 1，閒置即誤報；改為 `go_memstats_heap_inuse_bytes > 512MB`（3800 連線時 gate 峰值約 300MB）。
- `GameRecordMQDisconnected`：限縮為 `job="record"`；consumer 連線成功才把 `recordmq_connection_status` 設為 1（原本只有 publisher 會設，Record 永遠為 0）。
- 新增 `GameLoginCentralBusy`：5 分鐘內 `busy` 超過 10 次且持續 2 分鐘。
- 待決策：Central busy 拒絕會讓 `GameLoginAvailabilityLow`、`GameLoginFailureRatioHigh` 在大批同時登入時 firing（客戶端會重試，實際沒失敗），是否排除 busy。

## 第 4 步：churnload（登入、登出、重登穿插）

300 人、3 分鐘，每人隨機執行「擲骰後登出」「登入後立刻斷線」「同帳號重登踢舊連線」。

- 結果：登入成功 4356 次、擲骰 3162 次、擲骰失敗 137 次，結尾資料驗證 `verify: bad=0/300`（沒有資料不一致）。
- Central 併發 64 的 busy 拒絕共 35098 次（工具遇 busy 立即重試，沒有退避）。
- 結束後 gate goroutine 回到 46（無洩漏）；world goroutine 108 → 396，與 soak 常駐 1500～3800 人時的 382～416 同一水位，視為進入穩態而非洩漏。
- World 錯誤與 Windows 暫時埠耗盡有關：`connectex: Only one usage of each socket address`（world → MySQL 13306）14 次，造成 `context deadline exceeded` 301 次，進而讓 MySQL circuit breaker 開啟，`failed to update login activity` 5001 次、`failed to write back player game data` 1092 次（`circuit breaker is open`）。
- 判斷：暫時埠耗盡主因是壓測工具在 busy 時無退避地大量重連，使整機 TIME_WAIT 暴增，屬測試環境（Windows 單機）的人為壓力；但它也示範了 DB 暫時不可用時，登入活動與逐出寫回會被熔斷器擋下。壓測不要在 busy 時立即重連。
- Central 日誌 `login rejected: cannot restore previous gate, falling back to logout` 4921 次、Gate `duplicate login, kicking old session` 1071 次，都是重登路徑的預期行為。

## 環境事件

- 測試中途機器重開（Windows 開機時間 18:52），Docker Desktop 沒有自動啟動，dev 容器與所有服務都停了；第一次 churnload 因此全部失敗（`logins=0`），結果作廢。
- Docker Desktop 啟動失敗原因：`%LOCALAPPDATA%\Docker\run\sailor-ingest.sock` 是無法刪除的過期 AF_UNIX socket（`The file cannot be accessed by the system`）。處理方式：結束 Docker Desktop，把整個 `Docker\run` 資料夾改名為 `run.stale-<時間>`（沒有刪任何資料），Docker 重建後引擎 15 秒內起來，dev 容器自動恢復，`scripts/dev-up.sh` 重新拉起六個服務。

## 第 5 步：recordload（Record 消費端寫入量）

連續發布 20000 筆 `WorldStartPass` 事件到 dev RabbitMQ（`recordload -url amqp://…:25672/ -mq project-dev-rabbitmq -n 20000`，視窗 256 個未確認）。

- 發布 1.207 秒（約 16567 筆／秒）；從開始到佇列排空 6.15 秒（約 3252 筆／秒）。
- 20000 筆全部寫進當日 `record_events_YYYYMMDD`，`record.events` 與所有 `.dead` 佇列為 0，沒有死信。
- Record goroutine 23、heap 約 8.5MB，壓測前後持平。
- Record 日誌有 `gorm slow query`（INSERT 批次最長約 5.4 秒、21 列），是整批壓測期間唯一異常；佇列仍在 6 秒內排空。
- 結論：Record 消費端寫入吞吐約 3 千筆／秒，發布端遠快於消費端，由 RabbitMQ 佇列吸收；目前沒有針對「佇列積壓」的告警，若要觀察積壓需要另外加。
- `recordmq_connection_status{job="record"}` 在整個過程維持 1，`GameRecordMQDisconnected` 沒有觸發。
