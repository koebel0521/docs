# 壓測紀錄 2026-10-15

本機（loopback、單機）壓測與告警校準紀錄。工具在 `tools/private/`（不進版控）；dev Prometheus 在 `127.0.0.1:39090`，改規則後 `POST /-/reload`。

## 環境與限制

- 全部同機 loopback，沒有網路延遲，結果只當下界參考。
- Gate 對單一來源 IP 有連線數（100）、接入速率與登入嘗試限流，壓測用 `127.0.x.y` 多來源 IP 繞過（`loadtest -source-ips`、`soakload`、`chatload`、`cmdload` 內建）。
- Prometheus 計數有約 15 秒抓取延遲，要即時值直接看服務 `/metrics`。

## 第 1 步：登入與連線容量

| 人數 | 來源 IP | 成功 | 錯誤 | p95 登入 |
|---|---|---|---|---|
| 300 | 8 | 300 | 0 | 16ms |
| 600 | 16 | 600 | 0 | 14ms |
| 2000（`max_connections` 4096） | 64 | 2000 | 0 | 15ms |

- `max_connections: 1024` 時 1200 人只成功 1024，其餘 `rejecting connection: at capacity`；dev 設定已改 4096。
- gate heap 約 70–80KB／連線、goroutine 約 3／連線。

## 第 2 步：soak（登入＋擲骰常駐）

- 1500 人、20 分鐘、每人約 10 秒擲骰：0 失敗、goroutine 與 RSS 持平、heap 為 GC 鋸齒，無洩漏，無告警觸發。擲骰 p50 約 1.57ms、p99 約 5ms。
- 3800 人、6 分鐘：gate goroutine 11450、heap 峰值約 302MB、RSS 約 540MB、擲骰 p99 6–23ms、0 失敗。

## 第 3 步：聊天與盤面指令、重連洪水

- chatload（200 人、每人 40 則）：廣播投遞約 6779 次／秒，延遲 p50 10.5ms、p99 23.9ms。
- Central `maxConcurrentLogins = 64`：同時登入超過 64 立刻回 `AuthServiceUnavailable`（code 9，可重試），`game_login_total{result="busy"}` 計數。500 人同時登入，434 次重試後全數成功，平均登入總耗時 1.18 秒。
- LoadPlayer 尾延遲：新帳號 p99 1.44s、已存在帳號 0.30s、常駐 6ms。每次 LoadPlayer 都會跑一次 `InitializePlayer` 交易（含 `SELECT FOR UPDATE`）。是否加「已初始化就跳過」快取待決策（會動死結敏感程式）。

## 已調整的告警（`monitoring/prometheus/alert-rules.yml`）

- `GameMemoryPressureHigh`：舊的 `heap_inuse / next_gc` 比值在 GC 鋸齒下常態接近 1，閒置即誤報；改為 `go_memstats_heap_inuse_bytes > 512MB`（3800 連線時 gate 峰值約 300MB）。
- `GameRecordMQDisconnected`：限縮為 `job="record"`；consumer 連線成功才把 `recordmq_connection_status` 設為 1（原本只有 publisher 會設，Record 永遠為 0）。
- 新增 `GameLoginCentralBusy`：5 分鐘內 `busy` 超過 10 次且持續 2 分鐘。
- 待決策：Central busy 拒絕會讓 `GameLoginAvailabilityLow`、`GameLoginFailureRatioHigh` 在大批同時登入時 firing（客戶端會重試，實際沒失敗），是否排除 busy。

## 第 4 步：churnload（登入、登出、重登穿插）

300 人、3 分鐘，每人隨機執行「擲骰後登出」「登入後立刻斷線」「同帳號重登踢舊連線」。

- 結果：登入成功 4356 次、擲骰 3162 次、擲骰失敗 137 次，結尾資料驗證 `verify: bad=0/300`（沒有資料不一致）。
- Central 併發 64 的 busy 拒絕共 35098 次（工具遇 busy 立即重試，沒有退避）。
- 結束後 gate goroutine 回到 46（無洩漏）；world goroutine 108 → 396，與 soak 常駐 1500～3800 人時的 382～416 同一水位，視為進入穩態而非洩漏。
- World 錯誤與 Windows 暫時埠耗盡有關：`connectex: Only one usage of each socket address`（world → MySQL 13306）14 次，造成 `context deadline exceeded` 301 次，進而讓 MySQL circuit breaker 開啟，`failed to update login activity` 5001 次、`failed to write back player game data` 1092 次（`circuit breaker is open`）。
- 判斷：暫時埠耗盡主因是壓測工具在 busy 時無退避地大量重連，使整機 TIME_WAIT 暴增，屬測試環境（Windows 單機）的人為壓力；但它也示範了 DB 暫時不可用時，登入活動與逐出寫回會被熔斷器擋下。壓測不要在 busy 時立即重連。
- Central 日誌 `login rejected: cannot restore previous gate, falling back to logout` 4921 次、Gate `duplicate login, kicking old session` 1071 次，都是重登路徑的預期行為。

## 環境事件

- 測試中途機器重開（Windows 開機時間 18:52），Docker Desktop 沒有自動啟動，dev 容器與所有服務都停了；第一次 churnload 因此全部失敗（`logins=0`），結果作廢。
- Docker Desktop 啟動失敗原因：`%LOCALAPPDATA%\Docker\run\sailor-ingest.sock` 是無法刪除的過期 AF_UNIX socket（`The file cannot be accessed by the system`）。處理方式：結束 Docker Desktop，把整個 `Docker\run` 資料夾改名為 `run.stale-<時間>`（沒有刪任何資料），Docker 重建後引擎 15 秒內起來，dev 容器自動恢復，`scripts/dev-up.sh` 重新拉起六個服務。

## 第 5 步：recordload（Record 消費端寫入量）

連續發布 20000 筆 `WorldStartPass` 事件到 dev RabbitMQ（`recordload -url amqp://…:25672/ -mq project-dev-rabbitmq -n 20000`，視窗 256 個未確認）。

- 發布 1.207 秒（約 16567 筆／秒）；從開始到佇列排空 6.15 秒（約 3252 筆／秒）。
- 20000 筆全部寫進當日 `record_events_YYYYMMDD`，`record.events` 與所有 `.dead` 佇列為 0，沒有死信。
- Record goroutine 23、heap 約 8.5MB，壓測前後持平。
- Record 日誌有 `gorm slow query`（INSERT 批次最長約 5.4 秒、21 列），是整批壓測期間唯一異常；佇列仍在 6 秒內排空。
- 結論：Record 消費端寫入吞吐約 3 千筆／秒，發布端遠快於消費端，由 RabbitMQ 佇列吸收；目前沒有針對「佇列積壓」的告警，若要觀察積壓需要另外加。
- `recordmq_connection_status{job="record"}` 在整個過程維持 1，`GameRecordMQDisconnected` 沒有觸發。

  - Gate `/metrics`：94474 次、9447 rps、錯誤 0、p50 5.0ms、p99 27.7ms。

## 第 7 步：故障注入

背景負載：`soakload` 500 人常駐擲骰（gate 連線 504）。依序停掉一個元件約 100 秒，再還原並量測；每次都記錄 `/ready` 通過數、gate 連線數、`up==0` 的 job、firing 與 pending 的告警。

| 注入 | +30 秒 | +100 秒 | 還原後 |
|---|---|---|---|
| 殺 World 程序 | ready 5/6、gate 連線 504→60、`GameServiceDown` pending | gate 連線 3、`GameServiceDown` **firing**、重連告警 pending | 重啟 World 2 秒後 6/6 ready |
| 停 Redis | ready 2/6（四個依賴 Redis 的服務不 ready）、`GameRecoveryMismatchDetected` firing | 同左 | 啟動後立即 6/6 ready |
| 停 RabbitMQ | ready 仍 6/6、`GameRecordMQDisconnected` pending | 同左（`for: 5m`，100 秒未到 firing） | 還原後 pending 消失 |
| 停 MySQL | ready 3/6 | ready 3/6、`GameCircuitBreakerOpen` pending | 5 秒內 6/6 ready，熔斷器告警在還原後仍 pending 一段時間 |

觀察：
- 所有元件還原後 `/ready` 都在數秒內回到 6/6，服務沒有因為依賴中斷而需要手動重啟。
- `/ready` 不檢查 RabbitMQ，所以 RabbitMQ 中斷時服務仍顯示 ready，只有 `GameRecordMQDisconnected` 能提醒；該告警 `for: 5m`，短於 5 分鐘的中斷不會 firing。
- `GameRecoveryMismatchDetected` 在 Redis 中斷後 firing，因為它引用 10 分鐘窗口（`increase(...[10m]) > 0`），還原後約 10 分鐘才會消失，值班時要知道這是殘留訊號。
- soakload 的虛擬玩家被踢後**不會重連**（gate 連線停在 4，沒有回到 500），所以這次沒有量到「中斷後玩家自動重連的成功率與時間」。要量重連需要有重連邏輯的客戶端（`tools/user` 或 loadtest 的 reconnect 路徑）。
- 測試開始時 `GameDataSaveFailure`、`GameLoginAvailabilityLow`、`GameLoginCentralBusy`、`GameLoginFailureRatioHigh` 仍 firing，是前面 churnload 的殘留，說明這幾個告警在尖峰後要等窗口過去才會恢復。

- 登入 0 失敗、擲骰 0 失敗；擲骰 p50 0.5～1.2ms、p99 1.1～15ms（少數取樣點 max 80～94ms，下一輪即回落）。

## 第 9 步：容量預測（capacityforecast）

用 `pjaload loadtest -n 1000 -ramp 40s -duration 60s -source-ips <32 個> -write-baseline .run/loadtest-baseline.json` 產生 baseline（1000 人登入 0 失敗、平均登入 7ms、p95 9ms），再執行 `capacityforecast -target-p95-ms 100 -target-queue-depth 1000`。

- 輸出：`baselinePlayers=1000 estimatedPlayers=1000 headroom=100% reason=queue`，`latencyFactor=11.11 queueFactor=1.00 errorFactor=1.00`。
- 解讀：延遲係數 11.11，代表登入延遲離 100ms 目標還有約 11 倍空間，延遲不是限制；`queueFactor=1.00` 是工具拿不到佇列深度（baseline 只有登入統計，沒有佇列指標）時的保守值，所以它把預估人數卡在 1000，**不能解讀為容量只有 1000 人**。
- baseline 檔案只含登入統計（`elapsedSeconds`、`loginOK`、`p95LoginLatencyMs` 等），沒有 heap、goroutine、CPU，因此這個預測無法反映記憶體或連線上限。實際邊界以前面各步為準：Gate `max_connections` 4096、heap 約 80KB／連線（3800 連線約 300MB）、Central 登入併發 64。
- 檔案 `.run/loadtest-baseline.json` 在 `.gitignore` 內，不進版控。

## 總結與待辦

**已確認穩定**：Gate 在 4096 連線內 0 錯誤；1500 人 60 分鐘 soak 無洩漏；Record 寫入約 3 千筆／秒無死信；World、Redis、RabbitMQ、MySQL 任一中斷後服務數秒內自動恢復 ready；churnload 資料驗證無不一致。

**已調整並進版控（主倉庫）**：`GameMemoryPressureHigh`（512MB 絕對值）、`GameRecordMQDisconnected`（限縮 `job="record"` 並讓 Record 消費端設 `recordmq_connection_status`）、新增 `GameLoginCentralBusy`、loadtest 的 `-source-ips`。

**後續處理結果**：
1. 重連：第 10 步已量到，300 人在 World 重啟後約 25 秒內全數重新登入，成功率 100%。
2. busy 與登入可用率：在 Alertmanager 加 inhibit 規則，`GameLoginCentralBusy` firing 時抑制 `GameLoginAvailabilityLow` 與 `GameLoginFailureRatioHigh`（開發與正式設定都改，`amtool check-config` 通過）；Prometheus 規則本身不改，所以 Grafana 的登入失敗率面板仍會反映 busy。
3. LoadPlayer 每次跑 `InitializePlayer` 交易：決定不動（會動死結敏感程式，收益有限）。
4. Record 佇列積壓：新增 `recordmq_queue_messages` gauge（消費端每 15 秒以被動宣告取樣）與 `GameRecordQueueBacklog` 告警（持續 5 分鐘超過 1 萬筆）。實測 12 萬筆突發發布時積壓峰值 46872 筆，十幾秒排空，吞吐 8606 筆／秒（前面 recordload 的 3252 筆／秒受當時慢查詢影響）。
5. `/ready` 不檢查 RabbitMQ 維持現狀；MQ 中斷由 `GameRecordMQDisconnected` 負責（`for: 5m`，短於 5 分鐘不會響）。

**仍待補**：
- 壓測工具遇 Central busy 應退避（私有工具，不進版控）。
- 全部是單機 loopback，正式容量需要多機與真實網路。

**環境注意**：機器重開後 Docker Desktop 不會自動啟動；若出現 `sailor-ingest.sock: The file cannot be accessed by the system`，把 `%LOCALAPPDATA%\Docker\run` 資料夾改名（不要刪、不要重設為出廠預設）後重啟 Docker Desktop。

## 第 10 步：玩家重連（補第 7 步的缺口）

`pjaload loadtest -soak -n 300 -session 900s -cooldown 2s -source-ips <16 個>`：soak 模式玩家在連線被中斷後，會等 2 秒冷卻再重登（每輪最多 3 次登入嘗試）。測試中途殺掉 World 程序、30 秒後重啟，從每 5 秒的 `connected` 觀察恢復。

| 時間（測試開始後） | connected | 說明 |
|---|---|---|
| 90 秒前 | 300 | 全部在線 |
| 95 秒 | 0 | World 被殺，gate 立即踢掉全部玩家 |
| 95～125 秒 | 0 | World 停止期間，登入重試 274 次、失敗 35 次（3 次嘗試用完） |
| 130 秒 | 85 | World 重啟後開始恢復 |
| 145 秒 | 300 | 全部恢復 |

- 恢復時間：World 重啟後約 25 秒內 300 人全部重新登入，最終成功率 100%（`loginOK=600` = 初始 300 + 重連 300）。
- World 停止期間失敗的 35 次登入嘗試是用完 3 次重試的玩家，下一輪冷卻後都成功，沒有玩家永久掉線。
- 最終報告：平均登入 17ms、p95 57ms（含重連高峰）；`reconnects=1617`、`errors=982` 是 World 停止期間每 2 秒一次的重連嘗試累計，不是新增失敗玩家。
- 告警：`GameLoginCentralBusy` firing，`GameLoginAvailabilityLow`、`GameLoginFailureRatioHigh`、`TCPReconnectSuccessLow`、`GameHandlerP95High` pending；重連高峰期會同時觸發這些告警，與第 3 步發現的 busy 計入失敗率問題一致。
- 這補上了第 7 步沒量到的「中斷後自動重連」：重連成功率 100%，恢復時間約等於 World 重啟時間加 25 秒。

## 第 11 步：混合負載

800 人 `soakload`（登入後每 10 秒擲骰，持續 9 分鐘）先跑 100 秒，再同時加上 200 人 `chatload`（每人 900 則，間隔 400ms）與 100 人 `cmdload`（盤面指令序列，1500 輪）。三個工具共用同一台 Gate、World 與 Redis。

| 工作負載 | 單獨跑 | 混合時 |
|---|---|---|
| soak 擲骰 p50／p99 | 約 1.6ms／5ms | 1.1～1.6ms／2.6～3.2ms（無退化） |
| chat 延遲 p50／p99 | 10.5ms／23.9ms（200 人 40 則） | 7.4ms／70.9ms、max 84ms（約 2100 次投遞／秒，p99 約 3 倍） |
| cmd 指令 p99（ListMissions、ActivateMission、UpgradeBuilding、ClaimMission） | 5～18ms | 7～18ms |
| cmd LoadPlayer p99 | 195ms（新帳號）／300ms | 125ms |

- 擲骰與指令延遲沒有因為混合而退化；聊天尾延遲變大（p99 71ms），但仍在可接受範圍。
- Gate 每條連線有訊息速率限制（`gateUserRatePerSec=50`、`gateUserRateBurst=100`）：`cmdload` 每輪連送 5 個指令，100 條連線都被 `rate limit exceeded, closing connection` 關閉（約完成 24 輪），這是對過快客戶端的保護，不是故障；要量更長的指令負載需要在輪與輪之間加間隔。
- `chatload` 有 74 人登入時遇到 Central busy（code 9）沒有重試而退出，實際只有約 126 人在發聊天；該工具沒有重試邏輯。
- 期間告警只有 `GameLoginCentralBusy` firing（chat／cmd 兩個工具同時登入造成，預期行為）；goroutine、heap 沒有異常增長（world goroutine 約 397、gate 約 2447）。
- Gate 日誌 `gm kick queue: blpop error`（連線被拒）102 次是第 7 步停 Redis 時留下的紀錄，不是本次問題。

## 第 12 步：滾動優雅重啟（負載下）

400 個 soak 模式玩家（斷線後等 2 秒自動重登，`pjaload loadtest -soak -session 900s`）在線時，用 `shutdowntime`（對服務程序送 CTRL_BREAK 並計時）依序優雅重啟 gate → world → central，每個服務重啟後等 60 秒。

| 服務 | 優雅關機耗時 | 新實例 ready | 玩家影響 |
|---|---|---|---|
| gate | 30.03 秒（exit 1） | 2 秒 | 400 人在 5 秒內全被中斷；舊 gate 關閉期間 327 人重連到新連線，約新實例啟動後 20 秒恢復到 400 |
| world | 5.02 秒（exit 1） | 0 秒 | `connected` 始終維持 400，Gate 進入寬限期，玩家沒有被踢 |
| central | 5.01 秒（exit 1） | 0 秒 | 同上，沒有玩家被踢 |

- 三個服務的關機都以 `drain timeout` 結束（日誌 `shutdown task "user drain": drain timeout with 401 remaining connections`、`world drain … 1 remaining`、`central drain … 4 remaining`），所以耗時剛好等於各自的 drain 逾時（gate 30 秒、其他 5 秒），並以 exit code 1 結束。這是設計行為：drain 等待連線自行離開，逾時後強制收尾；但在有玩家在線時 gate 滾動重啟固定要多等 30 秒，world、central 因為對端（gate、central）不主動斷線也固定等滿 5 秒。
- World 關機時 `flushed player states count=400`（400 位在線玩家的狀態在停機前寫回），日誌沒有任何寫回失敗；重啟後玩家資料沒有遺失跡象。
- 最終報告：`loginOK=800`（初始 400 + 重連 400）、平均登入 10ms、p95 88ms；`loginRetry=1903`、`loginFail=863`、`reconnects=1892` 是 gate 關閉與重啟期間每 2 秒一次的重連嘗試累計。
- 告警：只有 `GameLoginCentralBusy` firing（重連洪水），沒有 `GameServiceDown` 等故障告警。
- 觀察與建議（沒有改程式碼）：
  - exit code 1：orchestrator 若用退出碼判斷是否成功，滾動重啟會被誤判為失敗；若這是預期設計，值班文件應註明。
  - gate 的 `drain_timeout` 可由設定覆寫（`parseDrainTimeout`），要縮短滾動重啟時間可在部署設定調小，代價是玩家被更早斷線。
  - Gate 重啟是唯一會中斷玩家的步驟，建議滾動順序仍為 world → central → gate，gate 最後。

## 第 13 步：大聊天室與多房間

`chatload` 補上登入重試（遇 code 9 換連線重試）與 `-rooms`（玩家平均分到多間房），避免登入階段被 Central busy 淘汰玩家。

| 情境 | 結果 |
|---|---|
| 單一房間 1500 人、每人 3 則 | 1.96M 次投遞、174039 次／秒；延遲 p50 356ms、p90 613ms、p99 714ms、max 1.07 秒；2 人登入遇到 code 8（單 IP 登入限流）未進房 |
| 300 間房、每房 5 人、每人 20 則 | 146824 次投遞、17987 次／秒；延遲 p50 133ms、p99 232ms、max 255ms；1 人遇到 code 8 |

- Chat 服務資源很小：單一大房 goroutine 最高 32、heap 13.8MB；300 間房時 goroutine 最高 333（約每房一個工作者），壓測結束 20 秒後回到 40，**房間工作者有回收**；`game_msg_queue_dropped_total{service="chat_room"}` 為 0，`game_chat_room_queue_pending` 為 0，沒有丟訊息或積壓。
- 瓶頸在扇出與 Gate：1500 人大房單則訊息要投遞給 1500 人，延遲隨房內人數線性上升（p50 356ms）；同時 Gate goroutine 峰值 4022、heap 86MB，仍在正常範圍。
- 多房間情境的延遲（p50 133ms）比第 3 步的 200 人 1 房（p50 7ms）高，原因是整體訊息率放大 7.5 倍（1500 人同時送），不是房間數造成。
- 沒有發現需要修的缺陷；大房（上千人）的聊天延遲是否可接受屬產品決策，必要時可限制單房人數或分流。
