## 環境與做法

- Windows 保留了連接埠範圍 59969～60068，`config/dev` 的 Central 內部埠 `60001`～`60004` 綁定失敗（`bind: An attempt was made to access a socket in a way forbidden by its access permissions`）。改用 `.run/dev-load/config` 的副本，把這四個埠換成 `64001`～`64004`，其餘設定不變，不動系統設定。

## 告警判讀

- 3800 人、每秒約 1900 次擲骰下，沒有任何 queue、延遲、GC 類告警觸發；`GameSendQueueDepthHigh`、`GameEventQueueDepthHigh`、`GameMessagesDropped` 等門檻沒有被逼近，所以這次資料**不支援調整**這些門檻。要驗證它們真的會響，需要注入人為壓力（例如 netproxy 限速），不是單靠登入人數。
- `ban_check_failed` 3 筆發生在服務剛啟動、Redis 連線尚未穩定的瞬間；爬坡期沒有再出現。新指標可正常記錄。
- pending 中的 `GameStateAuditMismatch`（未達 30 分鐘持續，沒有 firing）：Central 稽核在服務啟動時回報 `result=error`（`transport=world service has no connection`，World 尚未連上）與一次 `result=mismatch issues=46`（`gate 2001 missing user …`，發生在 3800 人同時登入的爬坡期，`repairs=0`）。判斷為登入進行中的暫態競態，不是持久漂移；稽核對「登入尚在進行中」的使用者沒有容忍，值得在後續確認。
- `GameProcessRestarted`、`GameServiceDown`、`TCPReconnectFailuresSustained` 來自這次啟動過程（第一次啟動因埠被保留而 Central 失敗，其他服務連不上），屬環境造成的假警報。

## 補充：稽核暫態與慢讀取壓力

### 稽核 mismatch 已修

爬坡期的 `missing user` 是 Central 先記路由、Gate／World 稍後才綁定造成的暫態。Central 稽核現在對 10 秒內剛登入的玩家（`User.routedAt`，由登入流程以 `MarkUserRouted` 標記）缺人不回報，超過寬限仍缺才算漂移；修復見 `f1b055d57`。

### 慢讀取壓力：送出佇列堆不起來

私有工具 `slowreader`：150 條連線登入後只送擲骰（每 120 ms 一次）與心跳（每 5 秒），完全不讀回應，持續 8 分鐘。

| 項目 | 結果 |
|---|---|
| 送出擲骰 | 589,770 次，寫入錯誤 0 |
| `tcp_send_queue_depth`（全服務） | 全程 0 |
| `tcp_send_queue_overflow_total`、`tcp_dropped_messages_total` | 0 |

- 沒有送心跳時，150 條連線在約 90 秒被 `game_heartbeat_timeout_total` 斷開（150 筆，`GameHeartbeatTimeoutSurge` 觸發）。
- 每連線限流是每秒 10 次、突發 20；送擲骰間隔 10 ms 時連線會先被限流踢掉（`rate limit exceeded, closing connection`），佇列同樣沒有機會堆積。
- 結論：客戶端只能在限流之內送指令，而伺服器回覆被作業系統緩衝吸收，單靠慢讀取的客戶端無法讓 `tcp_send_queue_depth` 逼近告警門檻 3000。`GameSendQueueDepthHigh`、`GameEventQueueDepthHigh` 防的是內部病態（例如大量廣播、對端卡死），需要用服務端故障注入驗證，不是客戶端壓力。

### 登入告警在真實忙碌下會響，`central_reply` 對上 Central busy

- 慢讀取工具一次登入 300 個新帳號（尚無重試）撞到 Central 併發上限 64：Central `busy` 408 筆，`GameLoginCentralBusy`、`GameLoginAvailabilityLow`、`GameLoginFailureRatioHigh` 都實際觸發。
- `game_login_unavailable_total{reason="central_reply"}` 是 408，與 Central 的 `busy` 完全一致：Central 滿載回的 code 9 在 Gate 端就是 `service_unavailable`，所以登入可用率與失敗率告警會把 Central busy 當成失敗。這與 2026-10-15 紀錄的待決策事項是同一件事（客戶端會重試，實際沒有失敗）；`central_reply` 現在可以量化它，但它也包含 Central 其他原因的 `service_unavailable`，要不要把 busy 排除出可用率仍待決定。
### `GameRedisCommandErrors` pending：Docker 網路瞬斷，非程式缺陷

- World 日誌有 182 筆 `request journal redis load failed`（`get key: context deadline exceeded`，逾時上限 500 ms），集中在 18:05（150 筆，同一毫秒）與 18:06（31 筆）；150 剛好等於同時在線的慢讀取連線數，是同一瞬間所有進行中的 journal GET 一起逾時。
- Redis 本身沒有停頓：慢查詢紀錄最大約 37 ms，當時沒有 RDB 存檔（最近一次在 8 秒後，fork 約 1 ms），無 AOF；World 的 sched p99 最高 8 ms、GC 暫停占比 < 1%、goroutine 穩定 441，沒有行程停頓。判斷為 Docker Desktop（Windows）連接埠轉發的瞬間延遲，屬本機環境。
- 逾時時 journal 視為未命中（fail-open）並進入後端冷卻，與設計一致；告警在持續 5 分鐘前就恢復，行為正確。
- 另一個觀察（World handler p99 爬升）已在下方「p99 爬升查明」更正：不是負載固定下的成長。

## 補充：p99 爬升查明

前面曾記「負載固定，World `board_roll_dice` p99 從約 42 ms 爬到約 87 ms」，這個前提不對：

| 項目 | 18:00 起每分鐘取樣 |
|---|---|
| `board_roll_dice` 請求率（5 分鐘窗口，次／秒） | 400 → 846 → 1122 → 1227 → 1223 |
| `board_roll_dice` p99（5 分鐘窗口，ms） | 25 → 24 → 46 → 71 → 87 |
| World heap inuse | 49～58 MB，無成長 |
| World GC CPU 占比 | 0.06% → 0.6% |
| goroutine | 穩定 441 |

- 請求率在這段時間從 400 爬到約 1227 次／秒（150 條連線陸續登入），p99 跟著負載上升；p99 與請求率都是 5 分鐘窗口，所以曲線落後實際負載。
- 記憶體、goroutine、DB 等待與佇列都沒有成長，沒有洩漏跡象；p99 是負載上升時的排隊延遲，約 1200 次擲骰／秒時 p99 約 87 ms。
- 2026-10-27 的 3800 人 soak 在固定負載下，客戶端量到的擲骰 p99 反而從爬坡期 340 ms 降到常駐期 8～86 ms，也不支持「隨時間成長」。
- 沒有做長時間固定負載的 pprof 前後對比；若之後在固定負載下看到 p99 持續上升，再補。

## 補充：滾動重啟下的 service_unavailable 原因

私有工具 `churnload`（120 位玩家持續登入登出，5 分鐘）期間依序重啟 gate 兩次、Central 兩次（每次間隔約 50 秒），驗證 `game_login_unavailable_total{reason}` 在真實重啟下的行為。啟動腳本自己逐一起停服務、沒有監控者；`scripts/dev-up.sh` 會在任一子行程結束時收掉全部服務，不能用來單獨重啟一個服務。

單一 Gate 行程（最後一次重啟後）的原始計數器：

| reason | 筆數 |
|---|---|
| `time_not_synced` | 193 |
| `central_reply` | 158 |
| `no_central` | 97 |
| `ban_check_failed` | 14 |
| `central_gone` | 0 |
| 合計 | 462，與 `game_login_total{result="service_unavailable"}` 的 462 完全相等 |

- 重啟 gate：剛啟動時 `time_not_synced`（尚未收到 Central 的 TimeSync）與 `no_central`（還沒連上 Central）最多；`ban_check_failed` 也出現 14 筆，是 gate 剛起來、Redis 連線尚未就緒的瞬間。
- 重啟 Central：`central_reply`（Central 自己回覆暫不可用）最多。`central_gone` 在兩輪實驗都是 0：Central 斷線時 pending 中的登入極少，因為登入通常在毫秒內完成。
- 用 Prometheus `increase()` 看各原因加總時，當時 series 是第一次遞增才出現，gate 重啟會讓新出現的 series 少算起頭的增量，第一輪比總數少 262 筆、第二輪少 40 筆；這是查詢假象，直接看單一行程的原始計數器則完全相等。**更正**：後來序列已改由 Gate 啟動時預建為 0，`increase()` 預建後可用，上述假象不再發生；代價是單次超過 10 筆的爆量仍會讓 `GameLoginGateUnavailable` 響約 3 分鐘（見 `alert-rules.yml` 該告警註解）。
- `world_reply`（World 自己回覆 `service_unavailable`）是第五個原因，這輪沒有實際出現，由單元測試覆蓋。
- `GameLoginGateUnavailable` 只涵蓋 `ban_check_failed`、`no_central`：這輪 `no_central` 約 100 筆分散在兩輪重啟，沒有達到 5 分鐘內超過 10 筆且持續 2 分鐘的門檻，沒有誤響。
- churnload 的 `verify: bad=120/120` 與大量 `wrong_password` 是工具的帳號／密碼設定造成，與本次驗證的指標無關，未追。
