# 壓測紀錄 2026-10-16 第四輪

接續[壓測紀錄 2026-10-15](壓測紀錄-2026-10-15.md)（第 1～25 步）。本輪為第 26～45 步，驗證 Gate 連所有 World 的修正與先前沒測過的區域；整理後的結論與操作在[容量與壓測基準](../../20-排障與監控/容量與壓測基準.md)、[壓測手冊](../../30-部署與開發/壓測手冊.md)、[多 World 部署](../../30-部署與開發/多World部署.md)。環境與限制同前：單機 loopback、Windows、Docker Desktop 跑依賴。

## 第 26 步：多 Gate × 多 World

拓撲：2 個 Gate（`2001`、`2002`，後者監聽 `62002`）、3 個 World（`1001`、`1002`、`1003`，監聽 `61001`～`61003`），每個 Gate 的 `dial.world` 列出三個 World（全網狀），同一個 Central 與 MySQL。第二個 Gate 與第二、三個 World 用暫存設定檔啟動（診斷埠寫死，第二個 Gate 與 World 會記錄 `debug server listen` 錯誤但不影響服務，只有第一個的 `/metrics` 可抓）。新增私有工具 `dupgate`（同帳號先後從兩個 Gate 登入）。

| 項目 | 結果 |
|---|---|
| Gate 連到的 World | Gate A、Gate B 日誌各有 `61001`、`61002`、`61003` 三筆 `connect` |
| 新帳號從 Gate A 登入（90 個） | 90／90 成功；World 分配 1001：24、1002：30、1003：36 |
| 新帳號從 Gate B 登入（90 個） | 90／90 成功；World 分配 1001：35、1002：25、1003：30 |
| 同帳號先 Gate A 後 Gate B 登入（30 個） | 新連線 30／30 存活；舊連線收到 ReLogin 通知（30／30），舊連線上擲骰無效（0／30），**舊 TCP 連線沒有被伺服器關閉** |
| 同帳號先 Gate B 後 Gate A 登入 | 同上 |
| 同帳號兩次都從同一個 Gate 登入（30 個） | 舊連線被關閉（30／30）並收到 ReLogin 通知，新連線存活 |
| 兩個 Gate 各 450 人常駐，殺 Gate B | Gate A 的連線數不變，Gate B 玩家全部中斷；重啟 Gate B 後 25 秒內再次連上三個 World |
| 殺 World 1002 | Gate A 的連線由約 450 降到約 325（失去綁在 1002 的玩家），其餘玩家不受影響 |
| World 1002 重啟（兩個 Gate 都**沒**重啟） | 約 75 秒後，既有的 90 個帳號從 Gate A 與 Gate B 登入都 90／90 成功 |

- 全網狀拓撲運作正常：任一 Gate 可服務任一 World，Gate 重啟、World 重啟都不需要重啟另一端。
- 跨 Gate 重複登入：World 發 `LogoutWorldToGate`（`AuthReLogin`）給舊 Gate，舊 Gate 清掉 session 並通知玩家，但**不關閉 TCP 連線**；同 Gate 重複登入則直接關閉舊 socket。兩者行為不同是因為舊 Gate 的登出處理（`flowbase.FinishLogout`）與一般登出相同：結束 session、回覆 `LogoutResponse`、讓連線留給客戶端決定，連線之後會因登入逾時被關閉。舊 session 在伺服器端已失效（擲骰無效），不是資料問題；客戶端收到 ReLogin 後應主動斷線。
- 沒有發現需要修的缺陷。
- 工具踩到的坑：`dupgate` 第一版把 `read ... i/o timeout`（被包在錯誤鏈裡）當成連線關閉，造成「舊連線被踢、新連線也死」的假結果；偵測逾時要用 `errors.As(err, &net.Error)` 而不是型別斷言。
- 限制：Gate B 的 `/metrics` 因診斷埠寫死抓不到，連線數以 `netstat` 的 ESTABLISHED 計（環回連線兩端各算一次，除以二）；沒測 Gate 與 World 數量更大的組合。

## 第 27 步：World 排空與 canary 流量切片

沿用第 26 步的 2 Gate × 3 World 拓撲。排空用 Lobby admin API（`POST /admin/world/drain?worldID=<id>`、`undrain`、`GET /admin/world/draining`，需帶 `X-Requested-By: admin` 與 Bearer token）；每步之間等 12 秒（Central 每 5 秒從 Redis 刷新排空集合）。canary 用 Central 的環境變數 `TRAFFIC_SLICE_PERCENT=50`、`TRAFFIC_SLICE_WORLD_ID=1003`（viper `AutomaticEnv`，Central 啟動時讀，要重啟）。

| 情境 | 結果 |
|---|---|
| 基準：90 個新帳號 | 1001：34、1002：26、1003：30，全部登入 |
| 排空 World 1002（HTTP 204，列表出現 `1002`） | 90 個新帳號**完全沒有被分到 1002**（1001：48、1003：42），全部登入 |
| 排空中，既有帳號（約 30 個綁在 1002） | 90／90 仍可登入 |
| 解除排空 1002 | 90 個新帳號再次分散到三個 World（22／37／31） |
| 三個 World 全部排空 | 新帳號**無法登入**（沒有可選的 World，Central 回 `AuthServiceUnavailable`，帳號不會被建立）；既有帳號 90／90 仍可登入 |
| 全部解除排空 | 新帳號立即恢復（30／30，1001：5、1002：9、1003：16） |
| canary 50% → World 1003（Central 重啟，約 70 秒後穩定） | 200 個新帳號全部登入；依 `fnv32a(帳號) % 100 < 50` 預期命中切片的有 100 個，**這 100 個全部在 1003**；其餘 100 個依最少負載分配（1003 另外只多 20 個，1001：41、1002：39） |

- 排空與 canary 都如設計運作：排空只影響新帳號的指派，既有玩家不受影響；切片命中的帳號確定性地導向指定 World（雜湊結果可離線預算驗證），未命中的帳號才走最少負載。
- 沒有發現需要修的缺陷。
- 注意：三個 World 同時排空時，開服登入請求會一律得到可重試的「服務忙碌」，客戶端若無限重試會持續打 Central；維運上避免全部排空。
- 限制：排空時既有玩家「不被踢」是由設計決定，沒有量測排空後讓玩家自然離線的時間；canary 切片需重啟 Central 才能調整，沒有執行期 API。
- 測試後 Central 已重啟為不帶切片的設定，六個服務 `/ready` 為 200。

## 第 28 步：其他依賴變慢（Redis、Central 的 MySQL、RabbitMQ）

拓撲沿用第 26 步，負載走 Gate A：300 人 `soakload`（每 3 秒擲骰，常駐 150 秒），常駐 25 秒後開始擾動，擾動期間再用 60 個既有帳號登入（`cmdload`）量登入延遲。

- **Redis 停頓**：不改服務，在 Redis 容器內迴圈執行 `redis-cli client pause <ms>`，讓所有 client 停頓：每 100ms 停 50ms（約 33% 時間被擋）、每 250ms 停 200ms（約 80%），各持續約 55 秒。
- **Central 的 MySQL 延遲**：`netproxy` 夾在 Central 與 MySQL（13307）之間，Central 以 `MYSQL_PORT` 指到代理，單向延遲 25ms（RTT 50ms）與 100ms（RTT 200ms）；代理確認有被使用（Central 的連線池經過代理）。
- **RabbitMQ 暫停**：`docker pause project-dev-rabbitmq` 約 30 秒（broker 無回應）。

| 情境 | 擲骰 p50／p99（擾動期間窗口） | 登入（60 個既有帳號） | 告警 |
|---|---|---|---|
| 基準（無擾動） | 1.57ms／3.5ms | 平均 305ms、LoadPlayer p99 22ms | 無新告警 |
| Redis 停頓 50ms／100ms | **14～20ms**／142～455ms（max 579ms），擾動結束後回到 1.55ms／3ms | 平均 369ms、LoadPlayer p99 416ms（p50 4.3ms 不變） | 無 |
| Redis 停頓 200ms／250ms | **88～100ms**／374～422ms（max 474ms），擾動結束後立即回到基準 | 平均 446ms、LoadPlayer p99 24ms | 無 |
| Central MySQL RTT 50ms | 無可辨識變化（約 0.5ms／1.2～2.7ms） | 平均 279ms、LoadPlayer p99 7.4ms | 無 |
| Central MySQL RTT 200ms | 無可辨識變化（約 1.0ms／1.6～2.3ms） | 平均 277ms、LoadPlayer p99 15ms | 無 |
| RabbitMQ 暫停約 30 秒 | 無可辨識變化 | 平均 291ms、LoadPlayer p99 11ms | 無 MQ 相關告警 |

- **擲骰對 Redis 停頓很敏感**：每次擲骰至少經過一次 Redis，Redis 被擋 33% 時間，p50 就從 1.6ms 變成約 15ms；擋 80% 時 p50 到約 100ms。沒有任何失敗或斷線，擾動結束後立即恢復。Redis 的 RDB／AOF 重寫、大 key 刪除或慢指令造成的停頓會直接反映在擲骰延遲上，值得監控 Redis 的 `latency`／`slowlog`。
- **Central 的 MySQL 延遲幾乎不影響既有帳號登入與常駐玩家**：既有帳號的登入走 Central 記憶體快取，不查 MySQL；只有新帳號建立與玩家路由寫入會經過 MySQL。這次沒有量「新帳號建立」在高延遲下的表現。
- **RabbitMQ 暫停對玩家路徑沒有影響**（事件走 World 的 outbox 非同步送出）；30 秒短於 `GameRecordMQDisconnected` 的 `for: 5m`，所以沒有觸發，Record 佇列暫停後的排空沒有另外量。
- 期間 `TCPReconnectSuccessLow` firing（`world`、`gate`、`lobby`、`chat`）是測試中重啟 Central（接代理與還原）造成的 S2S 重連失敗，不是依賴變慢的結果。
- 沒有發現需要修的缺陷。測試後 Central 已換回直連 MySQL，六個服務 `/ready` 為 200。

## 第 29 步：訊息層 fuzz（登入後框架合法、內容畸形）

先前只有框架層（`pkg/framecodec`）與少數訊息有 fuzz；玩家連線是不受信任的輸入，Gate 的 handler 在 `Unpack` 之前沒有其他檢查。這一步補兩層：

1. **單元層**（主倉庫新增 `pkg/msg/client_unpack_fuzz_test.go`）：對 20 種玩家端訊息（登入、登出、心跳、握手、盤面 8 種、戰鬥 4 種、聊天 4 種）：
   - `FuzzClientMessageUnpack`：餵任意位元組，`Unpack` 不可 panic；解碼成功的內容重新 `Pack` 後必須能再解碼。本機跑 150 秒、約 1820 萬次執行（約 12 萬次／秒），**沒有找到問題**。
   - 截斷測試：合法封包逐位元組截短，`Unpack` 不可 panic，通過。
   - 長度宣稱測試：用全 `0xFF`、`0x7F`、int32／int64／uint16 最大值與大 varint 樣式餵每種訊息，單次 `Unpack` 配置不得超過 1MB，通過——沒有任何訊息照著宣稱的長度配置記憶體。
2. **端對端**（`badclient -s bad-payload`）：200 個玩家登入後，對 13 種玩家端訊息 ID 送合法 frame、隨機內容（0～200 位元組），持續到被關閉。

| 項目 | 結果 |
|---|---|
| 連線被伺服器關閉 | 200／200，存活時間 p50 731ms、max 1.57 秒（`message unpack failed` 後 Gate 直接關閉連線） |
| Gate 資源 | goroutine 59 → 峰值 320 → 59，heap 約 35～43MB，日誌沒有任何 `panic` |
| 正常玩家（canary）登入 | p50 10ms、p99 22ms，不受影響 |
| 其他服務 | 六個服務 `/ready` 維持 200 |

- 結論：玩家端訊息解碼對畸形輸入是穩健的——不 panic、不被宣稱長度騙去配置記憶體，畸形 payload 一出現連線就被關閉，沒有被拖慢。
- 沒有發現需要修的缺陷。
- 注意：解碼失敗即斷線是設計（`handleUnpackFailure` 對玩家連線關閉）；客戶端若序列化有 bug，會看到無預警斷線而不是錯誤回應。
- 限制：fuzz 只涵蓋 `Unpack` 與 `Pack` 的往返，不涵蓋解碼成功但數值不合理（例如負的數量、超大的 `RequestID`）在各 handler 內的處理；那些屬於業務驗證，由各 handler 的測試負責（例如 `UseItem` 拒絕 `RequestID==0`）。

## 第 30 步：S2S 認證開啟（TLS＋節點 token）

所有先前測試都是 `s2s_auth.enabled: false`（`config/dev` 預設；正式設定一律啟用）。這一步用 `scripts/new-s2s-dev-secrets.ps1` 產生開發用 CA、各服務憑證、每目的服務獨立 token 與 SHA-256 授權清單，把 Central、Gate、World、Chat、Lobby 的設定改成 `enabled: true` 並指到各節點自己的機密目錄（Chat 同時是接收端與 Central 的用戶端，兩份機密合併），單 Gate、單 World 的 dev 堆疊在關閉與開啟兩種模式各量一次。負載用 500 個既有帳號（`sk_*`，綁在 World 1001）常駐擲骰 90 秒，登入用 60 個既有帳號（`cmd_*`）。

第一次比較不能用：前一輪的 World 1002／1003 還在跑（持續用明文連 Central，被認證拒絕 491 次），新帳號走 bcrypt 建立太慢使 300 人只有 95 人登入。清掉所有服務程序、改用既有帳號重跑，結果如下。

| 項目 | 認證關閉 | 認證開啟 |
|---|---|---|
| 擲骰 p50（穩態視窗） | 1.43～1.58ms | 1.52～1.58ms |
| 擲骰 p99（穩態視窗） | 3.3～4.9ms | 3.7～6.3ms |
| 登入（60 個既有帳號） | 60／60，平均 58ms | 60／60，平均 64ms |
| LoadPlayer p50／p99（登入洪水） | 12.5ms／54ms | 9.9ms／45ms |
| Gate／World 記憶體 | 同 | 同（World RSS 約 110MB、Gate 約 120MB，兩者差距在雜訊內） |
| World 重啟後 Gate 重連 | 3 秒 | 5 秒（多一次 TLS 1.3＋token 握手） |

- **效能成本可忽略**：穩態擲骰延遲幾乎相同（p99 約高 0.4ms 量級，在視窗雜訊內），登入平均多約 6ms，重連多約 2 秒。TLS 只加在 S2S 長連線上，連線建立時才有握手成本，熱路徑只多一層加密。
- **拒絕行為正確**：
  - 一個不在授權清單內的 Gate（id 2002）對 Central、World、Chat 三個目的都連不上：Gate 端日誌 `S2S handshake: read S2S authentication ack: EOF`，Central 端日誌 `invalid node credential`（`server_accept.go`），World 連線數為 0。
  - 明文（認證未開啟）的客戶端連到開啟認證的接收端會被拒絕：`S2S handshake: tls: first record does not look like a TLS handshake`。第一次比較中殘留的 World 1002／1003 就是這樣被擋下的 491 次。
- 沒有發現需要修的缺陷。
- 測試後 dev 堆疊已換回 `config/dev`（認證關閉、單 Gate、單 World），六個服務 `/ready` 為 200，沒有殘留的第二個 Gate 或 World。
- 限制：只量了單 Gate、單 World；多 Gate × 多 World 全網狀時連線數成長（Gate 數 × World 數）的握手總成本、授權清單熱更新（接收端每秒檢查摘要）與 token 撤銷時關閉連線的行為沒有量測；憑證用開發 CA，憑證到期輪替（`s2s-renew-certificates.py`）沒有演練。

## 第 31 步：聊天落庫（持續高訊息率）

沿用單 Gate、單 World 的 dev 堆疊，`chatload` 以既有 `rm_*` 帳號（空密碼，登入遇忙碌自動重試）持續送訊息，量 `chat_message` 的寫入完整性、房間佇列、Gate 聊天限流與 Chat 服務資源。基準：`chat_message` 約 4.6 萬列、9MB。

已知限制（程式讀到）：Gate 對每條連線的聊天送出限流為 `chatSendPerSecond = 2`、`chatSendBurst = 5`（同步為 1／秒、burst 3）；Chat 每間房的工作佇列深度 `roomQueueDepth = 256`，滿了就丟棄並計入 `game_msg_queue_dropped_total{service="chat_room"}`。

| 情境 | 結果 |
|---|---|
| A：600 人分 60 間房（每房 10 人），每人 300 則、間隔 250ms（嘗試 4 則／秒，約 18 萬則） | 88 秒內廣播成功 92246 則（約 51%，其餘被 Gate 的 2 則／秒限流擋掉）；`chat_message` **剛好新增 92246 列**，與廣播成功數一致，沒有掉訊息；房間佇列沒有丟棄；廣播投遞延遲 p50 29.8ms、p99 70ms、max 154ms；約 10816 次投遞／秒 |
| B：1000 人同一間房，每人 200 則、間隔 250ms（約 20 萬則） | 62 秒；廣播成功 68388 則，`chat_message` 新增 68555 列；Gate 限流 86651 則；**房間佇列丟棄 26117 則（約 13%）**；投遞約 103 萬次／秒（總計 6200 萬次）；廣播延遲 p50 193ms、p90 481ms、p99 856ms、max 1.26 秒；房間佇列峰值（5 秒取樣）210／256 |

- **落庫完整性**：只要訊息被房間接受並廣播，就一定寫進 `chat_message`（A 情境兩個數字完全相同；B 情境差 167 列是工具停止讀取的邊界）。寫入速率約 1100 列／秒（單間大房）到 1085 列／秒（60 間房），MySQL 沒有成為瓶頸（Chat 日誌 `gorm slow query` 僅 3 筆）。
- **限流是主要節流**：每條連線 2 則／秒，所以 4 則／秒的客戶端只有一半被處理；這是保護，不是故障。
- **單房過載時的行為**：1000 人同房、每人 2 則／秒（合計約 2000 則／秒進同一間房，每則要投遞給 1000 人）超過單房工作者的處理量（約 1100 則／秒被接受處理），佇列滿後丟棄約 13%，延遲 p99 到 0.86 秒；`GameChatRoomMessageDropped`（page）正確 firing。Chat 服務本身沒有崩潰，過載結束後立即恢復。
- 房間規模建議：延遲隨房內人數線性上升（第 13 步 1500 人 1 房 p50 356ms）；單房上千人且每人持續發言會丟訊息，必要時限制單房人數或分流。
- 觀察：`GameChatRoomQueueBacklog` 的門檻是 `game_chat_room_queue_pending > 1000`，但單房佇列深度上限只有 256，只有多房同時積壓才可能超過；單房過載時看的是 `GameChatRoomMessageDropped`。
- 沒有發現需要修的缺陷。
- 限制：`chatload` 不量歷史查詢（`ChatSync`）；沒有量 `chat_message` 長期成長（數千萬列）後的查詢與清理；這次寫入約 16 萬列，表仍很小。

## 第 32 步：含登入登出的長時間 soak（約 2 小時）

先前最長的 soak（2.5 小時、1000 人）只有常駐，沒有登入登出。這一步同時跑兩種負載，單 Gate、單 World 的 dev 堆疊（S2S 認證關閉）：

- `soakload`：500 個既有帳號（`sk_*`）常駐，每 5 秒擲骰，持續約 2 小時 10 分（23:14～01:24）。

## 第 33 步：資源上限（以 Go 執行期旋鈕模擬）

**範圍聲明**：用 `GOMAXPROCS` 模擬 CPU 限制、`go.memory_limit_mb`（`debug.SetMemoryLimit`，軟限制）模擬記憶體上限。不是 cgroup，沒有 OOM kill。單 Gate、單 World，1500 個既有帳號常駐 150 秒，每個情境重啟 Gate，並在每個情境開頭用 `go_sched_gomaxprocs_threads` 確認設定生效。

**更正**：本步驟最初提交的兩輪結果（「限制沒有綁到」）無效。腳本匯出了 `MSYS_NO_PATHCONV=1`，使 `taskkill //PID` 沒有殺掉舊 Gate，且 `APP_CONFIG=/c/...` 路徑 exe 無法解析，新 Gate 以「找不到設定檔」退出，所有情境量到的都是同一個沒改過的 Gate。以下為修正腳本後的重跑結果。

| 情境 | 擲骰間隔 | Gate CPU（核） | GC／分 | GC 佔 CPU | 擲骰 p50 | 擲骰 p99 |

| 預設（12 核） | 100ms | 1.23 | 47 | 0.4% | 531µs | 2.7～3.2ms |
| `GOMAXPROCS=4` | 100ms | 1.09 | 48 | 0.7% | 533～615µs | 2.9～6.9ms |

- **CPU 限制**：100ms 間隔約 1.5 萬次／秒請求。`GOMAXPROCS` 4／2 仍可承受（p99 升到 6.9ms）；降到 1 時 p50 翻倍、p99 到約 42ms，但仍無失敗、無斷線。
- **記憶體上限太低會造成 GC 死亡螺旋**：1500 人常駐時 Gate 的 Go 記憶體總量約 140MB（goroutine 約 4550、heap_inuse 約 77～150MB）。上限 120MB（低於總量）起，GC 每分鐘約 9000～9800 次，GC 吃掉約 1/3 CPU（Go 會把 GC 佔用限制在約 50% 以內），Gate CPU 從 0.1 核飆到 4.3 核，擲骰 p99 從約 2ms 到約 15ms。系統沒有失敗，但沒有任何餘裕。

- 沒有發現需要修的缺陷。
- 限制：`GOMAXPROCS=1` 不等於容器 1 核（cgroup 限制會 throttle 全部執行緒，這裡不會）；沒有 OOM kill。容器層限制見第 34 步。

## 第 34 步：容器 cgroup 限制（Docker）

與第 33 步不同，這步把 Gate 放進 Docker 容器（`docker/app.Dockerfile` 建的映像，`--cpus`／`--memory` 為真的 cgroup 限制），其餘服務留在主機（容器經 `host.docker.internal` 連 Central、World、Chat、MySQL、Redis、RabbitMQ）。

**客戶端也要放進容器**：經 Docker NAT，所有玩家對 Gate 都是同一個來源位址（`172.17.0.1`），會撞到單 IP 連線數（100）與登入速率（30／10 秒）限制，只能登入約 20 人。改為 15 個客戶端容器（`debian:bookworm-slim` 掛載交叉編譯的 `soakload`，各有自己的 IP），每個負責 100 人，共 1500；`soakload` 為此加了 `-offset`（帳號序號偏移）、`-nobind`（不綁定來源位址）、`-pace`（登入間隔，配合單 IP 登入速率）。

因為客戶端也在 Docker 網路內，絕對延遲包含 NAT 與 15 個客戶端容器的競爭，**不能與主機直連的數字（p50 約 0.5ms）比較**，只能在本表內部比較。

**CPU 限制**（每個玩家平均 100ms 擲骰，約 1.5 萬次／秒；Go 在 cgroup 下把 `GOMAXPROCS` 設為 max(2, 向上取整的 CPU 數)，所以 0.25～1 核都是 2）：

| `--cpus` | Gate 實際 CPU（核） | 每視窗擲骰完成數 | 擲骰 p50 | 擲骰 p99 | 連線／登入 |
|---|---|---|---|---|---|
| 12（不限） | 2.7 | 約 16000 | 4.3～5.7ms | 18～24ms | 1503 全部成功 |
| 2 | 1.9 | 約 12400～12900 | 41～51ms | 91～110ms | 1503 全部成功 |
| 1 | 1.0 | 約 7200～7600 | 178～185ms | 343～397ms | 1503 全部成功 |
| 0.5 | 0.5 | 約 3600～4500 | 316～394ms | 588～717ms | 約 1500；登入較慢，視窗內有玩家尚未登入完 |
| 0.25 | 0.25 | 約 2000～2600 | 477～587ms | 841～1024ms | 1467～1486；登入明顯變慢 |

- **吞吐量與 CPU 配額成正比，延遲隨飽和線性惡化**；沒有崩潰、沒有失敗、沒有被踢，連線數維持。GC 佔 CPU 僅 1～2%，CPU 受限時 GC 不是瓶頸。
- 1.5 萬次／秒是過載負載；正常負載（每 3 秒擲骰，約 330 次／秒）在主機上 Gate 約 0.1 核，所以 0.25 核配額在正常負載下仍有餘裕，但登入尖峰與 CPU 吃緊時登入會被拖慢（0.25 核時登入 100 人明顯延後）。

**記憶體限制**（每 3 秒擲骰；Gate 的 `go.memory_limit_mb: 512` 不變，容器上限低於它）：

|---|---|---|---|---|---|
| 512MB | 185MiB | 否 | 2.7 | 1.39ms | 約 2.0～2.2ms |

- 上限低於約 185MiB 後沒有 OOM kill、沒有斷線，但延遲尾巴明顯變長（128MB 以下 p99 到數百 ms）：推測是核心把可回收的記憶體（page cache、可換出頁）擠掉，而 Go 因 `go.memory_limit_mb`（512MB）高於容器上限而沒有收縮 heap，進程在 cgroup 邊緣運作（未用 cgroup 記憶體統計驗證）。這個環境是 Docker Desktop 的 Linux VM，OOM 行為與正式 Linux 主機（無 swap 時可能直接 OOM kill）不一定相同，沒有實測 kill 後的重啟與玩家重連。
- **設定建議**：容器記憶體上限必須高於「`go.memory_limit_mb` 以內」的實際用量並留餘裕；`go.memory_limit_mb` 應低於容器上限約 10～20%，讓 Go 在到達 cgroup 邊緣前就開始收縮，而不是讓核心去擠。Gate 1500 連線約 185MiB，`config/docker/gate.yaml` 的 `max_connections: 1024` 配 512MB 有足夠餘裕。
- 沒有發現需要修的缺陷。測試後 Gate 已換回主機的 `config/dev`，六個服務 `/ready` 為 200。
- 限制：Docker Desktop VM 非正式環境；沒有測 `--memory-swap 0`（禁用 swap）的真 OOM kill；容器網路使 NAT 與客戶端競爭計入延遲。

## 第 35 步：資料量放大（聊天表約 1280 萬列）

建一張結構相同的 `chat_message_big`（2797MB，約 1267 萬列，`room_id` 分散在 2000 間房、`created_at` 分布在約 66 天），與 MySQL 的 `innodb_buffer_pool_size`（**dev 為 128MB**，所以此表遠大於記憶體）。用私有工具 `dbload` 在 SQL 層量三種語句（形狀與 `cmd/chat/internal/store/mysql/history_store.go` 的 `RecordsSince`、`AppendRecords`、`PurgeBefore` 相同），小表 `chat_message`（約 25 萬列）當基準。

| 語句 | 小表（25 萬列） | 大表（1267 萬列） | 備註 |
|---|---|---|---|
| `RecordsSince`（隨機房、隨機位置、limit 50），c=1 | p50 1.0ms、p99 3.2ms | p50 14.3ms、p99 18.5ms | 約 14 倍，原因是隨機位置多為冷讀，要從磁碟讀頁 |
| 同上，c=16 | p50 2.1ms、p99 5.2ms，7577 qps | p50 19.7ms、p99 25.7ms，807 qps | |
| 同上，c=64 | — | p50 59ms、p99 91ms，1064 qps | 磁碟 IO 飽和 |
| `AppendRecords`（20 列批次），c=16 | p50 8.5ms、p99 19.1ms，1801 批／秒 | p50 9.0ms、p99 20.7ms，1693 批／秒 | 追加寫入不受表大小影響 |
| `PurgeBefore` 一批（刪 1000 列） | — | **p50 648ms、p99 1.84s**（單獨） | 每批要更新三個索引，隨機 IO |
| `PurgeBefore` 一批，同時有 c=16 寫入與 c=16 讀取 | — | p50 722ms、p99 2.9s、max 3.7s | 寫入 p99 升到 95ms（max 280ms），讀取 p50 升到 55ms、p99 215ms |

- **歷史查詢與寫入沒有被表大小拖垮**：`EXPLAIN` 走 `idx_chat_message_room_id_message_id` 範圍掃描並覆蓋索引；冷讀最壞約 20ms，真實情境多為近期訊息，熱資料在 buffer pool 內，接近小表數字。
- **保留期清理是瓶頸**：一批 1000 列平均約 0.65 秒（最慢 1.8 秒，離 `historyPurgeTimeout` 的 10 秒仍有餘裕）。以 1.27 萬列表中早於 30 天的約 677 萬列計算，要約 6770 批、約 1.2 小時才能清完，期間會拖慢同表的讀寫（見上表）。清理每小時啟動一次（`historyPurgeInterval`），穩態下它只需刪一小時的資料；若持續寫入超過約 1500 列／秒（`1000 列 / 0.65 秒`），清理會追不上寫入。實際聊天寫入率遠低於此（第 31 步 1000 人同房過載時也只有約 1100 列／秒）。

## 第 36 步：Redis 停頓與停機對登入、盤面指令、抽獎與商店的影響

第 28 步只量了擲骰。這步在單 Gate、單 World 的 dev 堆疊上，用既有帳號（`cmd_*` 60 人 3 輪的盤面指令，`sk_*` 100 人 30 秒的擲骰＋抽獎＋商店）比較三種條件，最後實際停掉 Redis 容器 20 秒，期間有 500 位常駐玩家。停頓用 `client pause`：每 100ms 停 50ms（約 33% 時間被擋）、每 250ms 停 200ms（約 80%）。

| 指標 | 基準 | Redis 被擋約 33% | Redis 被擋約 80% |
|---|---|---|---|
| 登入（60 人平均總時間） | 58ms | 310ms（約 5 倍） | **13.1 秒**，重試 67 次，59／60 成功 |
| LoadPlayer p50／p99 | 2.8ms／29.6ms | 1.2ms／24.5ms | 1.2ms／**6.4 秒**（max 10 秒） |
| UpgradeBuilding p50／p99 | 6.3ms／11.9ms | 2.2ms／78ms（p90 68ms） | **278ms**／501ms |
| ListMissions p50 | 1.2ms | 0.6ms | 0.7ms |
| 擲骰＋抽獎＋商店：100 人中登入失敗數 | 0 | **24** | **67** |
| 擲骰 p50／p99 | 525µs／1.6ms | 545µs／501ms | （多數玩家登不進去，無有意義樣本） |

- **登入是對 Redis 變慢最敏感的路徑**：登入包含多次 Redis 往返，Redis 被擋 33% 就慢約 5 倍，被擋 80% 時一部分登入用完客戶端重試次數而失敗（gameload 的 100 人中 67 人登不進去）。已經在線的玩家只有受影響的指令變慢，不會被踢。
- **只讀的盤面指令（ListMissions）幾乎不受影響**；寫狀態的指令（UpgradeBuilding）p50 受 Redis 停頓直接影響。
- 與第 28 步（常駐 500 人擲骰，Redis 被擋 33% 時 p50 約 15ms）的負載形狀不同（這裡是 100 人短時間），兩者的擲骰數字不要直接比較。

**Redis 停機 20 秒（500 位常駐玩家，每 3 秒擲骰）**：

| 時點 | Gate 連線 | `/ready`（Central／Gate／World／Lobby／Chat） | 備註 |
|---|---|---|---|
| 停機前 | 503 | 全部 200 | — |
| 停機中（20 秒時） | **503（沒有人被踢）** | Central、Gate、World、Lobby 為 503；Chat 仍為 200 | 擲骰視窗的 p50 變成 0s（立即失敗），p99 約 420～450ms |
| 啟動 Redis 後 | 503 | World 在停機後 21 秒（Redis 啟動後約 1 秒）回到 200 | 之後的視窗擲骰 p50 回到約 0.5ms |
| 恢復後 20 秒 | 503 | 全部 200 | 告警 `GameLoginCentralBusy`、`GameServiceDown`、`GameTimeSyncJump` 仍 firing（告警有延遲窗口；`GameServiceDown` 的 `record`、`user` 另有原因，見下） |

- **玩家連線在 Redis 停機期間完全保留**，Redis 回來後約一個取樣視窗（10 秒）內擲骰恢復正常，沒有玩家需要重連，取樣的失敗欄全程為 0。
- 停機期間擲骰立即失敗（不是掛住）；本步沒有逐一核對錯誤碼。
- 沒有發現需要修的缺陷。維運上：Redis 變慢時登入失敗率會先上升，`GameLoginAvailabilityLow` 與 Redis 延遲相關告警要一起看。
- 工具備註：第 34 步前我誤殺了所有 `go.exe`，連帶讓以 `go run` 啟動的 Record 與 user 結束（`GameServiceDown` 的 `record`、`user` 來自這件事，與 Redis 無關）；Record 已在本步後重啟，user 是手動冒煙客戶端，沒有重啟。長時間測試前不要用 `Stop-Process -Name go`。
- 限制：停頓是 `CLIENT PAUSE`（Redis 對所有 client 暫停），與真實的網路延遲或 CPU 飽和不完全相同；沒有測 Redis 資料遺失（無持久化重啟）後的恢復。

| 動作 | 已建立連線 | 玩家 | 恢復 |
|---|---|---|---|
| 撤銷 Gate 2001 對 World 的授權（`-Action Revoke -GateID 2001 -Destination World`） | **約 2 秒內** World 關閉與該 Gate 的連線；Gate 重連一直被拒絕（Gate 端 `S2S handshake: read S2S authentication ack: EOF`，World 端 `invalid node credential`），重連退避約 1、2、4、9、17、36 秒 | Gate 進入寬限期；連線數 302（10 秒）→ 183（20 秒）→ 2（40 秒），玩家被清掉 | 對已撤銷的目的再跑 `Rotate` 回報「NodeID 不存在」，**不會重新開通**；用 `Add` 同一個 ID 才重新授權，Gate 下一次重連即成功（之後玩家需重新登入） |
| 輪替 Gate 2001 的 token（`-Action Rotate -GateID 2001`，預設 All） | Gate 與 Central、World 的連線**同一秒**被關閉，**約 1.5 秒內**用新 token 重連成功 | Central 在 Gate 斷線時立即清掉該 Gate 的所有 session（日誌 `gate disconnected, clearing sessions`，沒有寬限期）；**300 位玩家約 20 秒後全部被斷線** | 玩家需重新登入 |
| 強制換發所有服務憑證（`s2s-renew-certificates.py --force`） | **既有連線不受影響**（303 條連線維持，Gate 到 World 沒有斷線） | 無影響 | 序號與到期日更新（+90 天）；換發後重啟 World，Gate 在 6 秒內重連，World 日誌握手錯誤 0 |

- **輪替 Gate token 等於踢光該 Gate 的玩家**：連線 1 秒內就恢復，但 Central 已清掉 session，玩家在約 20 秒後被斷線。這與文檔「操作可能影響玩家登入態，應安排適當時機」一致，是設計行為，不是缺陷；維運上要安排在低峰或先排空該 Gate。
- 撤銷同樣讓該 Gate 上的玩家在數十秒內全部掉線，且撤銷後必須 `Add` 才能重新授權。
- 憑證換發是三者中唯一對玩家零影響的動作，符合文檔「已建立連線不因服務憑證續期而關閉」。
- 沒有發現需要修的缺陷。
- 工具備註：`s2s-renew-certificates.py` 要在非隔離的 `python`（不加 `-I`）下執行，才找得到同目錄的 `s2s-secret-receiver` 模組；正式流程應走 `invoke-s2s-maintenance.ps1`（文檔已說明不要直接執行底層 Python）。
- 限制：只測單 Gate、單 World；多 Gate × 多 World 全網狀時握手總量隨 Gate 數乘 World 數成長，這次沒有量（第 26 步已確認全網狀本身運作正常）；沒有測 CA 輪替與跨主機分發（`s2s-distribute.py`）。測試後 dev 堆疊已換回 `config/dev`（認證關閉）。

## 第 38 步：設定熱重載帶實際差異

先前（`配置熱重載.md`）只量過內容相同的兩個 release。這步讓 World 以 artifact 目錄（`current.json`＋`releases/`，`allow_legacy_directory: false`）啟動，工作目錄是暫存複本，400 位玩家每 3 秒擲骰常駐，依序做：

| 動作 | 結果 |
|---|---|
| A. 發布版本資訊不同的新 release（`config_seq`＋1、`config_version` 換新） | World 偵測並重載成功，日誌 `data config reloaded`（`oldVersion`→`newVersion`），耗時 **7.3ms**；`data_config_reload_total{result="success"}` = 1 |
| B. 繞過發布端，直接把 `current.json` 指到一份 `Tech.bytes` 被截半的 release | World 拒絕：`data config reload failed: load candidate snapshot: load current release: config file checksums …`；`data_config_reload_total{result="failed"}` = 1；**舊 snapshot 保留**，World 繼續以原版本服務 |
| C. 把 `current.json` 還回有效版本 | 與生效中版本相同，不重載、無異常 |
| 全程玩家 | 400 人無一失敗；擲骰 p50 約 0.5～1.0ms、p99 約 1.1～3.8ms，重載與拒絕前後無可見差異 |

- **第一道防線在發布端**：把 `Tech.bytes` 截半後用 `configartifact` 發布，直接被拒絕（`validate source tables: load generated tables: failed to load TechConfigTable error`），不會產生 release，`current.json` 不變。發布端還會擋「同 `config_version` 但內容不同」的重複發布（`release version already exists with different content`）：換內容必須換 `config_version`。
- **第二道防線在 World**：即使有人繞過發布端直接改 artifact（竄改檔案或 `current.json`），World 以檔案雜湊驗證，拒絕載入並保留舊 snapshot，且計入 `data_config_reload_total{result="failed"}`，可據此告警。
- 沒有發現需要修的缺陷。
- 工具備註：`data_config_*` 指標中 `data_config_reload_total` 要在第一次重載後才出現；World 啟動時對 `config\data\version.json` 記一筆 `data config version manifest not found` 警告（artifact 模式沒有 legacy 的 version.json，屬預期）；`game config references an effect the server does not apply yet` 是既有警告，與熱重載無關。
- 限制：變更的是版本資訊，沒有驗證「遊戲規則數值改變後新請求用新值、進行中請求用舊值」這個語意（請求固定使用同一份 snapshot 由程式設計與單元測試保證，本步未重複驗證）；`.bytes` 內容的合法修改需要重新產生，這裡沒有做。測試後 World 已換回 `config/dev`（legacy 目錄、不啟動 watcher）。

## 第 39 步：接近 `max_connections` 時的 Gate 記憶體上限（3800 連線）

第 33 步只在 1500 連線下試記憶體上限。這步用 `bg2_*` 共 3800 個帳號（統一密碼）把 dev Gate（`max_connections: 4096`）推到 3800 連線，每 3 秒擲骰，比較 `go.memory_limit_mb` 為 512（dev 預設）、384、768MB。

|---|---|---|---|---|---|---|
| 768 | 3803 | 0.24 | 1.3 | 0% | **524µs** | **1.1ms** |
| 512（dev 預設） | 3803 | 0.29 | 2.7 | 0.2% | 1.6～2.1ms | 5.4～5.8ms |

## 第 40 步：無 swap 的 OOM kill 與多 Gate 的 S2S 握手

### 無 swap 的 OOM kill

第 34 步的記憶體情境沒有觸發 OOM kill（Docker Desktop VM 允許換出）。這步把 `--memory-swap` 設成與 `--memory` 相同（不可換出），Gate 容器 1500 連線、每 3 秒擲骰：

| 設定 | 結果 |
|---|---|
| `--memory 160m --memory-swap 160m` | **被 OOM kill**（`OOMKilled=true`、結束碼 137），約在連線穩定後 80～100 秒；1500 位玩家全部斷線；容器沒有重啟策略所以不會自己回來 |
| 128m、96m | 未跑完（客戶端容器卡在重試登入一個已死的 Gate，腳本掛住，已清除）；實際用量 1500 連線約 185MiB，低於這個值一定會被殺 |

- 對照第 34 步：同樣是 160MB，允許 swap 時 Gate 撐住（延遲變差），不允許 swap 時直接被殺。**正式環境容器若不允許 swap，Gate 的容器記憶體上限必須高於實際用量並留餘裕**：1500 連線約 185MiB、3800 連線約 600MB（見第 39 步）。
- Gate 被殺後所有連線中斷，玩家需重新登入；排程系統應設重啟策略（`restart: unless-stopped` 等），並以 Gate 的 `/ready` 做健康檢查。
- 沒有發現需要修的缺陷。

### 多 Gate 的 S2S 握手

用 `update-s2s-gate-secret.ps1 -Action Add` 授權 Gate 2002～2005，與 2001 同時啟動（S2S 認證開啟，單 World），量握手與登入：

| Central 累計 CPU | 5 個 Gate 同時握手後的 10 秒內約 0.42 CPU 秒 |
| Central 日誌 `invalid node credential` | 0 |
| 每個 Gate 各登入 20 位玩家 | 5 個 Gate 各 20／20 成功 |

- 多 Gate 同時啟動的 S2S 握手成本很低，沒有惡化跡象；Gate 數乘以 World 數的總連線數對 Central 不是瓶頸（至少到 5 個 Gate）。

## 第 41 步：本機模擬 GCP 方案（5000 人，Docker cpuset）

不租雲端機器，在本機用 Docker 模擬 GCP 機型：伺服端（Central、World、Chat、Lobby、Gate、Record、MySQL×2、Redis、RabbitMQ、Prometheus）全部放進 `docker/compose/compose.full.yml`，再疊上 `tools/private/gcp-loadtest/` 的覆寫：以 `cpuset` 把全部伺服端容器固定在 N 個核心（等同一台 N vCPU 的 VM 共用），Gate 連線上限 5500、Gate 記憶體上限 1280MB、World 人數上限 6000、MySQL 緩衝池 2GB。客戶端放另一個容器（固定在其他核心），容器內加 64 個次要位址（等同 GCP 別名 IP 範圍），`soakload -srcnet` 讓玩家輪流綁定，避開 Gate 單一來源 100 條連線的上限。每次都是全新資料庫，5000 個帳號全是新建（bcrypt）。

限制：Docker 虛擬機 12 核、約 15GB（`e2-standard-8` 是 32GB）；本機 CPU 比 GCE 的 e2 vCPU 快，結果偏樂觀；方案 2（16 vCPU）放不下。

| 連線／登入 | 5003 條，5000 位全部成功 | 5003 條，5000 位全部成功 |
| 5000 個新帳號進場時間 | 817 秒（約 6 帳號／秒，主要受工具的 `-pace 100ms` 序列登入限制） | 815 秒 |
| Gate CPU／記憶體 | 0.49 核／611MiB，goroutine 15050 | 0.64 核／613MiB，goroutine 15050 |
| World CPU／記憶體 | 0.78 核／157MiB | 1.08 核／164MiB |
| MySQL（遊戲庫）CPU／記憶體 | 0.67 核／1.07GiB | 0.85 核／1.14GiB |

## 第 41 步：聊天保留期清理的批次大小

第 35 步發現 `PurgeBefore` 一批 1000 列約 0.65 秒、清理追不上持續寫入。這步在較小的表（320 萬列，`chat_message_big`，同樣遠大於 128MB buffer pool）上比較每批 1000／5000／20000 列，各刪 20 萬列（`dbload -mode purge -batch N`），看調大批次是否能提高速度。

| 每批列數 | 每批耗時 p50／p90／max | 清理速度（約，列／秒） |
|---|---|---|
| 1000 | 0.42s／1.0s／4.4s | 1800 |
| 5000 | 2.2s／7.9s／16.6s | 1300 |
| 20000 | 8.3s／20.1s／20.9s | 1800 |

- **調大批次沒有提高速度**：每列刪除成本幾乎固定（約 0.5～0.8ms，要更新主鍵與兩個二級索引的隨機 IO），速度停在約 1300～1800 列／秒。
- **調大批次會撞逾時**：`historyPurgeTimeout` 是單批 10 秒。每批 5000 列時 p90 已達 7.9 秒、max 16.6 秒；每批 20000 列時中位數 8.3 秒、p90 超過 20 秒，`dbload` 沒有逾時所以沒有報錯，但實際服務中這些批次會被中止。**不要調高 `historyPurgeBatch`**。
- 清理進行時的寫入影響：每批 1000 列期間，16 併發的 20 列批次寫入 p50 29.6ms、p99 250ms（無清理時 p50 約 9ms、p99 約 20ms）；每批 20000 列的對照因為寫入負載在第一批清理期間就跑完，重疊時間不同，不能直接比較。
- 結論：單靠調批次大小解決不了；吞吐上限約 1500 列／秒，需要依 `created_at` 分區（`DROP PARTITION` 取代逐批 `DELETE`）才能根本解決。目前聊天寫入遠低於此（第 31 步過載情境也只有約 1100 列／秒），不急。
- 限制：單一磁碟、單一 MySQL 實例的 dev 環境；沒有量二級索引更少時的差異。測試後 `chat_message_big` 已刪除。

## 第 42 步：Central 對 Gate 斷線的寬限期（修正第 37 步發現的問題）

第 37 步發現輪替或撤銷 Gate token 會讓該 Gate 的 300 位玩家約 20 秒後全部掉線，原因是 Central 在 Gate 斷線時立即清 session 並通知 World 登出。主倉庫提交 `e19ff94c7` 改為：Gate 斷線只標記 30 秒寬限期（沿用 `appcore.ServiceDisconnectGracePeriod`，與 World 對 Gate 的寬限一致）；寬限期內以同 ID 重連即取消清理，重連後 Gate 送來的玩家快照（既有的 `SyncUsersGateToCentral`）負責對帳——快照有的保留，沒有的（例如 Gate 重啟過）移除並通知 World；逾期未重連才由 5 秒一次的 sweeper 走原本的全清流程。

在 S2S 認證開啟的單 Gate、單 World 堆疊上重跑第 37 步的輪替（`update-s2s-gate-secret.ps1 -Action Rotate -GateID 2001`，預設 All），300 位 `bg2_*` 玩家常駐：

| 項目 | 第 37 步（修正前） | 第 42 步（修正後） |
|---|---|---|
| Gate 與 Central、World 連線 | 同一秒關閉，約 1.5 秒重連 | 同左 |
| Central 對該 Gate 玩家 | 立即清 session、通知 World 登出 | 日誌 `gate disconnected, entering grace period` → `gate reconnected within grace` → `central restored user routes from gate sync`，不清 |
| Gate 連線數 | 303 → 3（約 20 秒後） | **303 全程不變**，60 秒後仍 303 |
| Central 收到的登出請求 | 全部 300 位玩家被清（約 20 秒後掉線） | **0** |
| 300 位玩家 | 全部掉線 | **全部保留**，擲骰 p50 約 0.52～0.58ms、p99 約 1.1～2.6ms，沒有失敗 |

- 輪替 Gate token 不再中斷玩家；撤銷（Gate 重連被拒）則仍會在寬限期後清掉其玩家，與設計一致。
- **客戶端需要重試**：輪替造成的約 1 秒 Gate 與 World 瞬斷，會讓剛好送出的請求遺失（約三成玩家）。用不會重試的壓測客戶端時，這些玩家在 15 秒讀取逾時後自己離開（第一次重跑 91／300 因此掉線，不是伺服器踢人）；`soakload` 加了 `-tolerate-timeout` 模擬會重試的客戶端後，全部保留。對應待決策第 5 項。
- 單元測試：寬限期內保留、重連取消清理、完整快照保留、空快照（Gate 重啟）移除並通知 World、逾期才清、掃描時已連回則保留（`disconnect_grace_test.go`）。
- 沒有發現新缺陷。限制：只測單 Gate；寬限期內 Gate 真的崩潰時，玩家最多在 Central 多留 30 秒（World 同樣有 30 秒寬限，兩邊一致）。
- 測試備註：重跑過程中兩次無效——第一次是我的腳本把 Gate 啟動了兩次，兩個同 ID 的 Gate 互踢連線；第二次用了被熱重載測試（第 38 步）污染的 `sk_*` 帳號，其盤面狀態帶假版本 `bbbb…`，擲骰全部失敗。這批 `sk_*` 玩家（約前 400 個）不要再用於壓測。

## 第 43 步：Central 寬限期的邊界情況（整合驗證）

第 42 步只驗證了「輪替造成的瞬斷」。這步在單 World、兩個 Gate（A 是 dev Gate 62001，B 是 62002）上用 `bg2_*` 玩家驗證三個邊界情況：

| 情況 | 結果 |
|---|---|
| a. Gate B 崩潰（殺程序），5 秒後重啟 | World 線上人數 200 → **重連後 0 秒內降到 100**：B 重連送來的快照是空的，Central 對帳移除 B 的玩家並通知 World 登出，不用等 30 秒；A 的 100 位玩家不受影響 |
| b. Gate B 崩潰且不重啟 | World 線上人數約 **29 秒**降到 0，與 30 秒寬限期一致（同一時段 A 那批玩家的 soak 剛好也結束，無法完全排除 A 的影響，只能說與寬限期相符） |
| c. B 崩潰後，同一批 100 位玩家在寬限期內改從 Gate A 重登 | 重登後 World 線上人數 100；B 的寬限期過後（等 45 秒）**仍是 100**，新 session 沒有被逾期清理誤刪；這批玩家持續擲骰無失敗；B 重啟重連後仍是 100 |

- 三個情況都符合設計：重連走快照對帳、不重連走逾期清理、寬限期內換 Gate 重登的新 session 受保護。
- 沒有發現需要修的缺陷。
- 限制：沒有測「兩個 Gate 同時輪替」與「Central 重啟加 Gate 斷線同時發生」（前者需要多 Gate 的 S2S，後者需要重啟 Central 時 Gate 重連，兩者的單元層面行為已由 `disconnect_grace_test.go` 涵蓋）。

## 第 44 步：Gate 與 World 瞬斷時的請求遺失

為了量化「客戶端需要重試」的規模，用 `netproxy` 夾在 Gate 與 World 之間，每 25～35 秒切斷連線一次（共切 6 次、約 190 秒），300 位 `bg2_*` 玩家每 3 秒擲骰，壓測客戶端用 `-tolerate-timeout`（擲骰逾時算單次失敗，不離開）。

| 指標 | 結果 |
|---|---|
| Gate 偵測到 World 斷線 | 6 次；重連 7 次（含一次初始連線），每次都在寬限期內重連 |
| 遺失的擲骰 | **402／11334（3.55%）**，平均每次切斷約 67 個（約 300 位玩家的 22%） |
| 玩家 | 300 位全部保留，沒有一位被踢 |
| 吞吐 | 各視窗擲骰完成數約 480～670（切斷瞬間的視窗略低），p50 約 0.53～1.0ms、p99 約 1.1～4.6ms，恢復後立即正常 |

- 每次切斷約 0.7 秒的請求遺失（300 位玩家每 3 秒擲骰 = 約 100 個請求／秒，遺失約 67 個 ≈ 0.67 秒），與「Gate 1～2 秒內重連」一致。
- **遺失的請求沒有任何回應**（不是回錯誤）：客戶端若不設讀取逾時就會永遠等；設 15 秒逾時會讓該玩家在 15 秒內無回應。建議客戶端對「送出後一定時間（例如 3～5 秒）沒回應」的請求主動重送，並確保重送是冪等的（擲骰、升級、商店購買要靠 `RequestID` 去重）。
- 沒有發現需要修的缺陷。
- 限制：只模擬 Gate 與 World 的斷線；Central、Chat 連線瞬斷的請求遺失沒有分開量。
