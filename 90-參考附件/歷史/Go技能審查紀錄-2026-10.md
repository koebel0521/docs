**身分與連線處理（Gate／World／Central）**

- N6 `cmd/world/internal/handler/gate/on_validate_gate_to_world.go:38-43`、`cleanup.go:14-31`：Gate 驗證失敗回覆與寬限期清理無條件 `DeleteUser`，不看玩家目前綁在哪個 Gate。玩家改連 Gate B 後，Gate A 的回覆會刪掉 B 上的新 session，盤面指令被靜默丟棄直到重登，Redis 狀態也被刪。`lifecycle/recovery_reconcile.go` 已用 `DeleteUserIfGate`，這兩處漏用（`gate.UserRegistry` 介面需補方法）。

**慢 I/O 在共用鎖內與關機**

- N9 `pkg/tcpsocket/owner_base_socket.go:88-105`：`Disconnect` 在 `authenticatedMu` 寫鎖內呼叫 `ownerEvent.Disconnect`，該鎖被事件迴圈上每則訊息的 `RLock` 共用；Central 處理 Gate 斷線時在鎖內做無逾時的 Redis 呼叫（`DeleteUserRoutings`），Redis 變慢時整個事件迴圈停擺。

- N12 `cmd/world/internal/store/gamestore/memory_player.go:267-321`：GM 發放的 `OperationID` 沒有長度檢查（只有任務事件路徑檢查 64），而欄位是 `size:64`、`pkg/grantitem` 只檢查非空。超過 64 字元時 MySQL 回 1406，寫回每秒重試永遠失敗，該玩家所有異動與登出都卡住；關機時落地成 spill 檔，`ReplaySpills` 遇第一筆失敗就整個回錯，下次啟動被擋。前提：strict `sql_mode`（8.0 預設）。

### 查證後不成立或不需要修改

- **N8(b)：** 見上，已還原。**N8(c)：** Central 查無玩家時不回覆 Gate 是刻意的單一回覆設計，session 由 30 秒逾時處理。
- **N6 的驗證失敗回覆路徑：** 現有測試要求 Gate 回報不一致時刪除玩家；只修了寬限期清理路徑。
- **N29 的「預設 pattern 沒有年齡門檻會搬走仍在重試的死信」：** 誤解。死信佇列是終點，重試排程在另一個 key（`RetryKey`），不會被預設 pattern 命中。
- **N34：** `beforePublish` 被拒絕時還原 `current.json` 是設計並有測試；正式 compose 以唯讀掛載 artifact root，World 不會改寫，共用可寫 root 的部署不在支援範圍。
- **L12（`SendMsg` 後立刻 `Close()`）：** `Socket.Close` 在發送佇列尾端放一個 nil 哨兵，`sendLoop` 排空已排入的訊息才關連線，告知訊息會先送出。
- **L13（`/diag/reconcile` 無認證）：** debug 埠在正式 compose 不對主機發布，`compose.full` 只綁 `127.0.0.1`；屬部署控制，不是程式缺陷。
- **L14（`UseItem` 在 `RequestID=0` 時被當成重送）：** `UseItemCommand.Unpack` 已拒絕 `RequestID == 0`，不會走到。L15 同理無此問題。
- **L43（`OwnerBase.Sockets` 競態）：** 只在 `RunLifecycle` 啟動任何監聽 goroutine 之前寫入一次，讀者都在其後啟動；`go test -race` 通過，沒有可重現的競態。
