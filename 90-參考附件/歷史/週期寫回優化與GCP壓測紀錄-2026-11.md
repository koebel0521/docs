# 週期寫回優化與 GCP 壓測紀錄（2026-11-12～13）

歷史紀錄，不作為現行規範。現行規則見 [資源預算](../../20-排障與監控/資源預算.md)、[Docker 生產部署](../../30-部署與開發/Docker生產部署.md)、[指標面板](../../20-排障與監控/指標面板.md)。

## 1. 摘要

- 目標：World 在 5000 人、3 倍負載下，把玩家異動寫回 MySQL（write-behind）的吞吐拉高，並用實測定出各服務的 CPU 配額與資料庫規格。
- 結論：
  - 寫回吞吐的牆是 **Cloud SQL 的 CPU**，不是往返次數。應用端優化（單次往返、抽獎去重、多位玩家合交易）在本機有大幅收益，雲端增益很小。
  - Cloud SQL 4 → 8 vCPU 約 +60%，寫回並行 16 → 32 再 +20%；World 4 核、Gate 2 核、Central 1.5 核夠用。
  - 先前「3 倍負載」其實只撐了約 7 分鐘：機器人骰子用完後伺服器回 `Rejected`（不改狀態、不寫回），壓測工具卻把它算成功。
- 正式環境現況：Cloud SQL 8 vCPU、World 4 核、`mysql.flush_concurrency=32`、`max_open_conns=80`、`mysql.flush_group_size=8`（預設；之後 repo 的正式設定已改為 1 關閉，理由見文末）。壓測結束後 VM 與 Cloud SQL 已停機省費用。

## 3. 優化項目

### 3.1 單次往返寫回（commit `21aefbf6e`）

- 原本一位玩家寫回約 10 次往返（START TRANSACTION、鎖主檔、各表 upsert、COMMIT）。
- 作法：以記錄用的假 GORM 連線池執行原本的 `savePlayerChangesTx`，收下語句與參數，組成一個多語句請求一次送出；主檔不存在就回滾，結果由最後一個 `SELECT` 回報。語句內容只在 `savePlayerChangesTx` 定義一處。
- 需要讀資料庫的步驟（拿掉道路星星、抽獎去重）與主檔不存在時，退回逐句路徑，結果與原路徑相同。
- 獨立 16 連線池 `pkg/mysql.OpenBatchWriter`；啟動探測失敗就降級。
- 指標：`game_player_flush_batch_total{result=committed|fallback_unrecordable|fallback_no_profile}`。

### 3.2 抽獎去重改唯一鍵（commit `c48cbb1fe`）

- 原本寫入前先 `SELECT seed … FOR UPDATE` 去重，需要讀結果，單次往返只能退回逐句。
- `(player_id, seed)` 改為唯一索引 `ux_player_lottery_draw_player_seed`，寫入改單句 `INSERT … ON DUPLICATE KEY UPDATE player_id=VALUES(player_id)`。
- 不能用 gorm `DoNothing`：MySQL 會產生 `draw_id=draw_id`，多列自增主鍵報 Error 1869。
- **正式環境關閉 AutoMigrate，部署前要手動 ALTER**（先確認沒有重複種子），SQL 見 [Docker 生產部署](../../30-部署與開發/Docker生產部署.md)。
- 曾實作「拿掉星星改單句 `DELETE … NOT IN`」，GCP 沒有更高吞吐，且企劃上正式環境不會出現格子不見，已從歷史丟掉。

### 3.3 並行數改為設定（commit `3d14383ad`）

- `flushConcurrency` 原本寫死 16。改為 `mysql.flush_concurrency`（預設 16），單次往返寫回連線池大小跟著它走。
- 陷阱：直接建構的 `Memory`（測試）沒設值時，`errgroup.SetLimit(0)` 會永遠阻塞，已用預設值兜住。
- `max_open_conns` 至少為並行數的 2 倍加 8。

### 3.4 多位玩家合一個交易（commit `b4c7acec7`、`8e188383c`）

- `SavePlayersChangesBatch`：一個請求先依玩家 ID 由小到大鎖住各主檔（固定鎖順序避免死結），再套用各自記錄到的語句，全部主檔存在才提交。
  - 無法錄製的玩家不放進交易（回未處理）；缺任一主檔整批回滾；回傳錯誤時沒有任何玩家被寫入。
- `gamestore.flushGroup` 把有異動的玩家每 8 位分一組（`mysql.flush_group_size`，1 關閉）：組內先取出各自 pending 與寫回鎖，能合併的一個交易寫回，未處理與合併失敗（含 panic）的逐位寫回，沿用原本的隔離、失敗計數與併回 pending。
- 本機 benchstat（每輪 400 人、並行 16、n=10）：耗時 -63.5%、players/s 約 1000 → 2747（+175%）。
- 修正：合併路徑與逐位路徑重複計入退回指標（顯示 530/s，實際約 265/s），會讓退回告警誤報。

### 3.5 告警與面板（commit `3df8f6e6a`）

- `GameFlushBatchFallbackHigh`：`fallback_unrecordable` 佔比 > 30%、總量每秒 > 1，持續 15 分鐘（warning）。附 promtool 觸發與不觸發測試。
- Grafana 總覽新增 `Player Flush Batch Results`。

## 4. 壓測結果

### 4.1 各服務 CPU（5000 人、3 倍負載，上限放寬後讀 cgroup）

| 服務 | 峰值 | 平均 | 結論 |
|---|---|---|---|
| World | 2.69～3.07 核 | 約 2.4 | 配 4 核；3 核太緊 |
| Gate | 約 1.1 核 | 約 0.85 | 2 核夠用 |
| Central | 登入湧入約 2.5 分鐘滿 3.0 核（節流 35～45%），其後約 0.02 | 0.45 | 登入時間由新帳號速率限制決定，放寬上限不會變快，1.5 核維持 |
| Record | 0.06 核 | | 不動 |
| Redis／RabbitMQ | 約 0.5～0.7 核 | | 不動 |

早期量到「World 約 1.1 核」是骰子用完後才量的，低估了。

### 4.2 寫回吞吐（持續 10 分鐘、骰子放大、0 失敗、0 遺失擲骰）

| 設定 | 寫回合計 | 資料庫 CPU | 備註 |
|---|---|---|---|
| 4 vCPU、並行 16 | 約 530／s | 89～93%（牆） | committed 約 250＋fallback 約 280 |
| 8 vCPU、並行 16 | 約 850／s | 平均 66% | committed 578＋fallback 272 |
| 8 vCPU、並行 32、連線池 80 | 約 1017／s | 平均 81%，峰值 85% | committed 749＋fallback 268 |
| 8 vCPU、並行 32、分組 8 | 約 1041／s | 平均 80% | committed 776＋fallback 約 265（重複計數已修） |

- 退回逐句的玩家全是機器人拿掉星星（伺服器端盤面邏輯觸發，客戶端無法避開）。
- 分組在雲端沒有明顯增益。推測：一半玩家走逐句路徑、且寫回主體是各表 upsert 而非 BEGIN／COMMIT，本機 fsync 成本在雲端不是主因。**尚未量測無拿掉星星負載下的雲端增益。**

### 4.3 異常：寫回約 7 分鐘後崩到近 0（壓測假象）

- 現象：擲骰仍 3330／s，但寫回從約 800／s 掉到 0～20／s，無錯誤、資料庫閒置。
- 原因：機器人骰子用完。`roll_dice.go` 骰子不足回 `Rejected`＋`InsufficientDiceToken`、error 為 nil，伺服器指標計 `ok`、不改狀態、不標髒、不寫回；soakload 只看有沒有收到結果事件就算成功。
- 處置：soakload 新增 `rejected rolls=` 統計（私有 repo）。持續負載時把遊戲設定 `GameRules` 的初始骰子數與上限改大。

## 5. 作業流程與做法

1. **建 image**：`docker build -f docker/app.Dockerfile --build-arg APP_DIR=cmd/world --build-arg HEALTHCHECK_PORT=6062 --build-arg VERSION=<tag> …`，推到 `asia-east1-docker.pkg.dev/plinkopoly/pja`。World 健康檢查埠是 **6062**。
2. **遊戲設定 release 要重發**：develop 編出的 World 預期 `schema_hash` 與 VM 舊 release 不同，啟動報 `dataconfig: config schema is not supported`。用 `scripts/publish-data-config.ps1 -Source config\data -Root <暫存>` 重發，換進 `DATA_CONFIG_ROOT`，舊的先備份。
3. **資料庫**：先手動 ALTER 建唯一索引，再換 image。
4. **壓測**：開帶別名 IP 的 Spot 客戶端 → 備份並暫時調整 VM 設定（Gate 連線／記憶體／來源 IP 上限、密碼登入、World 人數、Central 建帳速率、各服務 cpus 放寬）→ 修改 `GameRules.bytes` 放大骰子 → soakload 持續 10 分鐘，同時取樣 cgroup 與 World 指標 → 還原設定、清庫、刪客戶端。
5. **放大骰子的做法**：`config/data/Shared/GameRules.bytes` 為 71 位元組的 Luban 二進位，偏移 4 是初始骰子數、偏移 16 是骰子上限（皆 `0x64`=100），改為 `BF FF`（=16383）後，更新 `checksums.json` 內該檔的 sha256。壓測後用備份還原。
6. **升降 Cloud SQL**：`gcloud sql instances patch pja-mysql --tier=db-custom-8-32768`（會重啟）；停機用 `--activation-policy=NEVER`，恢復用 `ALWAYS`。

## 6. 陷阱與教訓

- `ssh --command` 內寫 `pkill -f 名稱` 會殺掉自己的 shell（命令列含該名稱），要寫 `pkill -f '[n]ame'`。
- PowerShell 的 `Get-Content`／`Set-Content` 重寫含中文的腳本會損毀編碼並吃掉換行，把 YAML 註解與 `services:` 黏成一行，override 檔因此失效；含中文的檔案用 bash `sed` 改。
- `python -` 與其他等待 stdin 的指令會卡住；Python 一律寫檔再跑。
- git-bash 的 `gcloud` 路徑含空格會失敗；PowerShell 內多字 `--command` 的引號會壞，改寫成 `.sh` 後 scp 再執行。
- 子模組指標指向的提交要先 push 子模組，主倉庫 push 才不會讓 CI 找不到。
- 並行調高要搭配資料庫 CPU 餘裕：4 vCPU 已頂滿時調高無效，8 vCPU 才有 +20%。

## 8. 未完成與待決策

- 分組在無拿掉星星負載下的雲端增益未量測；正式環境有真實玩家後，用 `flush_group_size` 在 1 與 8 切換比較。
- 正式設定已改為 `flush_group_size: 1`：雲端合併只多約 2% 吞吐，而整組鎖 8 列 `player_profile`、全有全無回滾的死結／lock wait／回滾頻率沒在真實流量下驗證。部署含 `game_player_flush_dirty_players` 的版本、用含拿掉星星的流量重測，並盯 MySQL deadlock、lock wait 與 `fallback_*` 比例後再評估改回 8。
- 8 vCPU 資料庫費用約為 4 vCPU 的兩倍，上線後依資料庫 CPU 實際用量決定是否降回。
- 企劃上「正式環境不會拿掉格子」尚未用實機遊玩驗證；若常態發生，單次往返的退回比例會偏高（`GameFlushBatchFallbackHigh` 會提醒）。
- 固定外部 IP `pja-game-ip` 在 VM 停機時仍計費；釋放後重開會換新 IP。
