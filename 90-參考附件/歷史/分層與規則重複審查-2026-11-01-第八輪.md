## 六、白話說明（每類一個本專案例子）

- **A1 資料層混入業務**：資料層應該只管「怎麼存、怎麼取」，不該決定「這筆算不算錯」。例：`memory_resources.go:153-164` 把道具溢位錯誤改包成「輸入錯誤」，好讓 GM 發放把它當永久失敗；可是這個判斷已經在 `itemaction.IsPermanentGrantError` 寫過一次，同一規則兩份（R2）。
- **A2 非資料型別放在資料層**：領域常數住在資料層，業務層反而要回頭找資料層拿。例：主盤面 ID `DefaultBoardID = 1` 在 `gamestore`，`board/upgrade_building.go:68` 從資料層取，領域層另有 `board.MainBoardID`（R3）。
- **A3 傳輸層自己做規則**：入口程式應該只解析參數，規則放在業務層，換個入口才不會漏。例：Lobby 封禁時「帳號要先正規化」只在 HTTP handler 做，`gm.Ban` 直接拿原字串組鍵；以後若有批次封禁入口直接呼叫 gm，就會寫出 Gate 永遠查不到的封禁鍵（R5）。
- **A4 業務層直接碰基礎設施**：業務程式不該自己認識 MySQL 或斷路器套件。例：GM 發放為了分辨「資料庫暫時壞了」開了 `grantinfra` 子套件直接 import `pkg/mysql` 與 gobreaker（R2）。
- **A5 同流程多套後端**：本輪 World Memory 與 MySQL 已無新的重複；最接近的是封存迴圈寫在 MySQL 實作裡，記憶體版得用回呼把規則塞進去（N4）。
- **B1–B3 模擬器與真實不一致**：模擬器要跟真的伺服器得到一樣的結果才有參考價值。例：World 一個擲骰只看一次時鐘，模擬器每個步驟各看一次；剛好跨過遊戲日的那一毫秒，效果用昨天判斷、抽獎卻已經是今天（F18）。
- **B4 工具摻規則**：工具介面應只轉格式。例：控制台診斷頁寫死 `limit: 100`，CLI 預設 200，同一個 trace 兩邊查出來筆數不同（F19）。
- **B5 測試旁路**：只給測試用的匯出要有 `ForTest` 後綴，守門才看得到。例：`EnableSharedState`、`RetentionDays` 只有測試在用，名字卻像正式 API（R4、R5）。
- **B6 一致性測試**：同一輸入，正式版與替身必須給同一答案。例：帳號清除的替身 `HasAccountTraces` 不看路由，寫不出「快取過期但路由還在」的情況（R9）。
- **C1 同判斷多處**：例：帳號正規化在 Central、Gate、Lobby 都有做，四支私人工具卻沒做，所以用全形帳號查會說「找不到」（F9）。
- **C2 兩端結果不同**：例：Central 密碼最短長度可設 73，Gate 與 Central 卻都拒絕超過 72 的密碼，兩條規則一夾，誰都註冊不了（F4）。
- **C3 手寫對照表**：例：Record `/events` 的 view 合法值與上限寫在 Record 內部套件，控制台因為 import 不到只好手抄一份（R5）。
- **C4 寫死字面值**：例：踢人原因 `"ban"` 在 Lobby 與 kickcmd 各寫一次，補踢用的 `"ban_rekick"` 不在 Gate 的認得名單裡（F3）。
- **C5 工具自己重做解碼**：例：`configaudit` 自己用 map 讀 rabbitmq 設定鍵，服務端改鍵名時守門會讀不到新鍵、誤判一致（R8）。
- **D1 設定多處解析**：例：`new_user.min_password_bytes` 只檢查不為負，上限規則在別的套件，設定載入時沒合起來檢查（F4）。
- **D2 序列化層補值**：本輪沒有新問題；`recordapi.Event`、`NewEnvelopeWithID` 都只做型別轉換。
- **E1 背景迴圈放錯層**：例：World 封存的逐位走訪與「連續 3 位失敗就放棄」寫在 MySQL 實作裡（N4）。
- **E2 只為打點的分支**：例：World 重連對帳刪完人後，再掃一次記憶體只為了算刪除數，而且算出來的數字還包含別人刪的（F25）。
- **F1 通用套件含業務**：本輪 pkg 正式碼 0 條匯入 cmd／internal／tools；最接近的是 `pkg/msg/system` 這種純訊息套件夾帶連線流程，因而連進 appcore（R6）。
- **F2 同工具多份**：例：「驗證失敗鎖定」的預扣、429、401、退款流程在 Lobby、Record、debug 三處各寫一份（R7）。
- **G1 外鍵耦合**：本專案沒有外鍵，關聯都靠應用層；封存與還原在同一交易內以 `player_id` 整批搬移，這是刻意的（第四節）。
- **G2 過度依賴**：例：Lobby 死信清單為了一個走不到的 `redis.ErrNil` 判斷 import `pkg/redis`，讓 gm 整個遞移連進 rueidis（R5）。
- **G3 同規則多層**：例：GM 發放的錯誤三分法，永久錯誤在 itemaction、暫時錯誤在 grantinfra、包裝在 services，同一件事分住三處（R2）。
- **H1 單一職責**：例：同上的封存，Memory → cbstore → mysqlstore 迴圈 → cbstore 回呼 → Memory 回呼，五層交錯只為封存一位玩家（N4）。
- **H2 DRY**：例：`/diag/protocol` 與 Record `/events` 的 limit 解析逐字相同各寫一份（R3）。
- **H3 KISS**：本輪沒有只有一個實作的多餘介面；`tcpruntime` 的選用能力介面是刻意的。
- **H4 YAGNI**：例：`CandidateIndex.Intn` 註解說「測試注入固定值可重現」，但全倉沒有任何人注入（Q3）。
- **H5 死碼**：例：`condition.UsesOperandType` 在改用 `UnsupportedOperandType` 後只剩測試在呼叫（R1）。
- **I1 快取交錯**：例：稽核修復路由時，登入自己的序號還沒寫回記憶體，修復又多配一個序號，記憶體與 Redis 對不上（F11）。
- **I2 舊動作抹掉新狀態**：例：World 重啟後恢復玩家，同時玩家在同一個 Gate 重登；晚到的「恢復不一致」回覆把剛登入的 session 刪掉（F7）。
- **I3 檢查與動作間無鎖**：例：World A 讀到舊快照決定把 P 移出候選集合，同時 World B 剛把 P 加回去；A 的移除晚到，P 就一直不在集合（F15）。
- **I4 內部錯誤轉通用碼沒日誌**：本輪 15 筆候選都有對應的計量或取樣日誌，無新問題。
- **I5 `%w` 配 nil**：本輪 1621 處掃過，無新問題。
- **I6 部分成功當整體失敗**：例：一筆任務事件對 A 是「格式不相容、重試無益」，對 B 是「資料庫暫時壞了」；程式只看到 A 就把整筆丟掉，B 的進度跟著不見（F8）。
- **I7 永久錯誤無限重試／暫時錯誤當已處理**：例：帳號清除後刪封禁鍵遇到 Redis 暫時失敗，只記一行就當處理完，之後再也不會重試（F26）。
- **I8 失敗算成功**：例：staterepair 清帳號鎖時不看刪除數，刪了一個根本不存在的鍵也回報成功（F9）。
