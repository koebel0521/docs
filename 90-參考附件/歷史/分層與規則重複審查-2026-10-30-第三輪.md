## 六、白話說明（每類附一個本專案的例子）

- **A1 資料層混入業務**：資料層只負責存取，「該不該做、怎麼算」放業務層。例子：商店「價格為 0 不扣款」、「發放 ID 用 `shop:`＋編號」仍在記憶體 store（D11，未變）。
- **A2 型別或組裝放錯層**：資料層不該組業務服務。例子：gamestore 自己建 `shop.Service` 並把「資源不足」翻成商店的「金幣不足」（第 17 項）。
- **A3 傳輸層自己做規則**：入口各自判斷就會分歧。本輪沒有新發現；前例是 Gate 自回與 Central 回同一個碼時 session 是否結束（第二輪 N3，已改註解）。
- **A4 業務層直接依賴基礎設施**：業務程式 import 資料庫套件就被迫連結 gorm。例子：board、mission 為了 DTO import gamestore（D12，未變）。
- **A5 同一流程兩套儲存後端**：本輪沒有新發現；變數遷移的 MySQL 版與記憶體版檢查已一致。
- **B 測試工具與真實流程**：模擬器跟正式系統不一樣，結果就不能代表正式服。例子：盤面模擬器前端送的欄位名 `techID` 和伺服器的 `TechnologyID` 對不上，以前被靜默忽略，改嚴格解碼後整個 UI 回 400（第 2 項）；重設後工廠仍是啟動狀態，World 新玩家不是（第 6 項）。
- **C 同一規則多份實作**：抄成多份，改一份漏另一份。例子：opsconsole 把「只驗證」的選項用舊欄位名送出，工具認不得就當一般發布，真的換了線上設定（第 1 項）；文件的重送 SQL 用 31 天，Record 只收 30 天（第 3 項）。
- **D 設定與協定**：同一份設定被解析兩次，日後規則一改就分歧。例子：建築成本的變數預設值在 boardconfig 又讀了一次設定表，而 gameconfig 已經解析過（第 20 項）。
- **E 背景任務與觀測**：同一事件在多處記錄，或打點方式不一致。例子：GM 發放被重跑時，Record 會多一筆隨機 ID 的發放紀錄（第 5 項）；佇列滿時 World 每位玩家各寫一行 Warn，Gate 端則有取樣（第 22 項）。
- **F 工具套件**：通用工具不該各寫一份。例子：連接埠解析有三份，兩份接受 `+61001`、一份拒絕（第 19 項）；百分位已在本輪前統一。
- **G1 外鍵**：外鍵會強迫刪除順序、跨服務寫不進去。本專案已全部改為應用層一致性，`player_tables` 是單一來源；舊庫外鍵靠文件手動移除。
- **G2 依賴過重**：只剩 D12（World 業務層經 gamestore 拖進 gorm）。
- **H 原則**：沒人用的程式碼留著會誤導。例子：`Runner.ShopQuotes` 在有 `QuotesBySpace` 之後只剩測試用，報價對照變成兩個來源（第 21 項）。
- **I 並行與錯誤處理**：I7 指錯誤分類錯。例子：Gate 佇列滿只是暫時過載，但 World 重送三次仍失敗後還是把在線玩家當殘留剔除（M1）。I8 指失敗當成功：熔斷演練腳本把 `docker compose` 的輸出連同結果一起回傳，Redis 回 `NOAUTH` 也判為健康（第 8 項）。
