## 五、白話說明（每類附一個本專案的例子）

- **A1 資料層混入業務**：資料層應該只負責存取，「該不該做、怎麼算」要放在業務層。例子：商店購買時「價格為 0 就不扣款」、「發放 ID 用 `shop:`＋編號」這些規則，寫在 `gamestore/memory_resources.go:174` 這個資料層函式裡，`shop` 套件只剩轉手（D11）。
- **A2 型別放錯層**：純資料格式或純函式放在資料層，別人要用時只好依賴資料層。例子：商店購買的 Record 事件格式 `shopPurchasePayload` 放在 gamestore，其他同類事件都在 `pkg/recordevent`（R2）。
- **A3 傳輸層自己做規則**：不同入口各自判斷，判斷結果就會不同。例子：GM 發道具會看「取得模式」，抽獎和商店入帳則不看。同一個 Immediate 道具，GM 發放是加變數，抽獎拿到是背包裡一個不能用的道具（D2）。
- **A4 業務層直接依賴基礎設施**：業務程式直接 import 資料庫或 MQ 套件，就很難用假的元件測試，也被迫一起連結 GORM。例子：chat 判斷「整批失敗還是逐筆重試」時，直接呼叫 `mysql.IsDataRejection`（R5）。
- **A5 同一流程兩套儲存後端**：這輪查下來已大致收斂，記憶體版是唯一正式的 Store，MySQL 版只負責快照寫回與遷移。殘留的分歧是兩個遷移入口的參數驗證不同：41 字元的版本號，一邊回參數錯誤，一邊回 MySQL 1406（第 7 項）。
- **B 測試工具與真實流程**：模擬器或測試替身與正式系統行為不同時，測試通過不代表正式服沒問題。例子：任務模擬接受「戰鬥勝場」指標，正式 World 根本不產生這個事件，同一份任務在模擬器會完成，在正式服永遠完成不了（D4）。測試替身 `variabletest` 對「現值已超出範圍」的處理也和正式版相反（第 14 項）。
- **C 同一規則多份實作**：同一條規則抄成多份，改一份時忘記改另一份，結果就悄悄分歧。例子：outbox 的重試退避，Go 版有防負值，SQL 版沒有，壞資料下 SQL 版永遠不進死信（第 8 項）；7 支壓測工具的登入重試條件，已經各自長成三種（第 3 項）。
- **D 設定與協定**：同一份設定、同一個欄位，在不同地方有不同的解讀。例子：`recordmq.Config.RoutingKey` 在消費端是綁定樣式 `record.#`，在發布端被當成路由鍵，讓原本設計的 fallback `record.unknown` 永遠走不到（D10）。
- **E 背景任務與觀測**：排程應該由應用層控制，資料層只提供動作，指標也應該集中在一層計數。例子：同一個指標 `RecordOutboxTotal`，有的結果在 store 計、有的在 relay 計，很難核對（R6）。
- **F 工具套件**：通用套件不該依賴業務，也不該各寫一份。本專案的 `pkg` 很乾淨，問題在工具：百分位數算法寫了 8 份、公式不一，n=100 時有的 p99 就等於最大值（R4）。
- **G1 外鍵**：外鍵會強迫刪除順序並增加鎖競爭，跨服務或分表時根本加不上。本專案已全部改為應用層一致性，舊庫殘留的盤面外鍵會在 World 啟動時移除（三）。
- **G2 依賴過重**：只為一個小函式 import 大套件，連帶拖進整串依賴。例子：`pkg/recordmq` 為了 `mysql.RedactedError` 一個函式 import 整個 `pkg/mysql`，連壓測工具都要連結 GORM（D15）。
- **H 原則**：H4/H5 指沒人用的程式碼，留著會誤導，也可能被誤用。例子：`DeleteUsers` 是無條件刪除整批玩家的危險 API，正式碼已經沒有任何呼叫端，日後若被誤用就會抹掉新登入的 session（R1）。H3 指沒必要的抽象，例如 `mission.Calendar` 介面只有一個實作，測試替身也只是它的翻版（R5）。
- **I 並行與錯誤處理**：「先查再刪」中間沒有鎖住時，查完之後狀態可能已經變了。例子：Gate 重連同步時，Central 先列出 stale 玩家再整批刪除，中間若有玩家從別的 Gate 重登，他的新登入會被刪掉並收到登出（第 1 項）。I7 指永遠不會成功的錯誤卻一直重試，例如 GM 發放佇列的外層 panic 沒有計次，那筆指令會在每次重啟時重新 panic（第 6 項）。
