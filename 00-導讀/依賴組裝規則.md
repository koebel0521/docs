# 依賴組裝規則

本專案使用手動 constructor injection。

- `cmd/*/run.go` 是 composition root，負責建立 DB、MQ、Redis 與 service。
- `internal/app` 與 `internal/services` 只接收已建立的依賴與已解析的設定，不建立 DI container，也不接收 `*viper.Viper`（Gate、Central 由 `cmd/<svc>/services_config.go` 解析成 `services.Config`；Lobby 的 Redis 連線也已移到 `cmd/lobby/run.go` 建立）。
- 例外（設定）：Lobby 的 `token_reload.go` 的 `Reload`／`TokensFromConfig` 接收 `*viper.Viper`（熱重載後的設定），與 `handler/servers.go` 同為 `viper_boundary_test.go` 白名單放行的組合根延伸。
- 例外：World 的 RabbitMQ record sink 啟動連不上時在背景重試建立，Record 的 RabbitMQ consumer 在自己的重連迴圈內重撥；這兩處連線在 composition root 之外（重連迴圈內）建立，是刻意的。
- 不做 I/O、沒有生命週期的 store adapter 可以在 `internal/services` 建立（例如 Central 的 `services.Start` 以傳入的 `db`、`rdb` 包出 store adapter）；有 I/O 或生命週期的依賴（連線、背景 goroutine、需要 `Close` 的物件）仍由組合根建立後傳入。
- 介面由消費者定義，實作在啟動層或 store adapter 建立；只有一個實作且沒有測試替身的介面不要建立（Gate 的 handler 與 flow、`tools/user` 已改為直接用具體的 `*app.App`），Central、World 有替身的 App 介面保留。
- 新增依賴時優先增加 constructor 參數；只有依賴圖已經無法閱讀時才重新評估容器。

這樣可以讓啟動順序、資源釋放與錯誤處理直接可見，避免同一 module 同時維護多套組裝方式。
