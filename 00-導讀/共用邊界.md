# pkg 邊界準則

`pkg` 只放可重用基建。任何帶服務語意的東西，都要留在 `cmd/*/internal`。

## 可以放

- transport
- logger / metrics
- `pkg/metrics` 可放跨服務共用的指標名稱與 label 契約，變更前要先確認所有引用端。審查 N28(b)：也承認它是指標的集中處，World、Chat 等服務專屬指標（`world.go`、`chat_room_queue.go`）與告警規則、儀表板同源，維持放在這裡，不搬到各服務的 internal/metrics 目錄。
- generic cache / journal
- generic reconnect / backoff strategy
- generic IP rate limiter
- TCP config / address resolver
- enum / DTO
- 純工具型 helper（例如 `pkg/mapx` 只有依 key 排序的 `SortedKeys` 與 nil 轉空 map 的 `CloneOrEmpty` 等小工具，不依賴其他專案套件）

## 不可以放

- login / logout / session 狀態機
- world routing / assignment policy
- recovery / reconcile decision
- return code policy
- service-specific fallback
- 任何只給單一 service 用的業務規則

## 各包紅線

### `pkg/appcore`

- 只做 event loop、time sync、signal 入口
- 不放 stdin／console 輸入：User 測試客戶端的 stdin 指令在 `tools/user/internal/stdinevent`
- signal 監聽由 `pkg/startup.Main` 以標準庫 `signal.NotifyContext` 處理
- 不加 service-specific lifecycle rule
- 不放登入、登出、重連決策
- panic 恢復輔助（`RecoveredError`、`LogRecovered`、`RecoverPanic`、`RunRecovered`、`RunRecoveredCtx`、`RunEvery`）的本體在葉套件 `pkg/panicx`（只依賴 `logger`、`metrics`；第十一輪）。**新程式碼一律直接用 `panicx`**（第十二輪起服務端呼叫點也已全部改用）；appcore 的同名轉呼叫（`pkg/appcore/recover.go`）已於第十三輪刪除。`RecoverPanic` 必須在被 defer 的函式本體內 recover，不能轉呼叫
- `pkg/appname`、`pkg/updaterorder`、`pkg/appcore` 不得直接匯入 `pkg/protocol`：協定結果碼別名 `AuthResultCode`／`Auth*` 在 `pkg/errcode`（第十一輪由原 `pkg/enum` 搬出；第十三輪原 `pkg/enum` 拆成 `pkg/appname`〔服務名稱 `appname.Central` 等〕與 `pkg/updaterorder`〔定時 Updater 登記順序〕，泛用的 `enum` 套件名不再存在）

### `pkg/panicx`

- 只放 panic 恢復與計量輔助，只依賴 `pkg/logger`、`pkg/metrics`
- 識別標籤參數一律叫 `label`（第十二輪統一），它會成為 `game_panic_recovered_total` 的 `msg` 標籤值與日誌 `msg` 欄位，必須是常數字串；`RecoveredError`、`LogRecovered`、`RunRecoveredCtx` 等把 kv 轉交給 `pkg/logger` 的函式都登記在 `.golangci.yml` 的 `loggercheck.rules`
- HTTP 中介層 `httpx.Recover` 也走 `panicx.LogRecovered`（第十二輪），全專案只剩 `tcp handler` 一個就地 recover 點自寫日誌（`ready check` 已改走 `panicx`）
- `httpx` 不依賴 `pkg/appcore`：goroutine 傾印函式仍在 `pkg/appcore/goroutine_dump.go`，`httpx` 只透過 `onTimeout` 由呼叫端注入；`pkg/httpx` 與 `pkg/debug` 列入葉套件守門，不得遞移連進 appcore。
- 葉套件共 12 個：`ratelimit`、`circuitbreaker`、`configwatch`、`dataconfig`、`recordmq`、`s2sauth`、`tcpdiag`、`panicx`、`release`、`httpx`、`debug`、`msg`（含子套件；`releasehello` 是範例服務，排除）。它們正式檔不得匯入 `pkg/appcore`（`pkg/pkg_boundary_test.go` 的 `TestLeafPackagesDoNotImportAppcore` 直接匯入守門），也不得遞移連進（`TestLeafPackagesDoNotTransitivelyDependOnAppcore` 遞移守門），避免為 panic 防護連進事件迴圈框架與協定生成碼

### `pkg/audit`

- 稽核結果的共用報告 `audit.Report`：新增不一致一律走 `Addf`（先計數、樣本未滿 `IssueSampleLimit`＝3 才 `Sprintf`）或 `Merge`（總數相加、樣本補到上限），總數欄位是私有的，對外只有 `IssueTotal()`（取代舊的 IssuesCount／`Total`／issueCount／issueTotal 多個名字）。World 的 `derivedCheck` 與 Central 的 `auditReport` 內嵌它，不各自維護計數邏輯。
- Gate 每分鐘稽核走**取樣模式**（直接用 `audit.Report`）：持 `sessionMu`／`userMu` 讀鎖期間只計總數、只格式化前 3 筆樣本，不保存無上限清單；`DiagnoseConsistency`（診斷端點 `/diag/reconcile`：GET 只檢查、POST 另外修復並回 before／after）保留**完整清單**，另有玩家篩選模式（`SnapshotPlayer`）只格式化牽涉該玩家的問題。日誌與 `game_state_audit_total` 不受影響（issues 數由總數計算）。
- 只放報告、`LogResult`、`PrimeMetrics` 與結果標籤常數，不依賴服務內部型別。

### `pkg/startup`（含 `dbstartup`、`redisstartup`、`mqstartup`）

- 根套件只放啟動流程輔助，**不得匯入** `redis`、`recordmq`、`mysql`（`pkg/pkg_boundary_test.go` 守門）：Chat 依賴樹因此不含 rueidis，Central、Chat 不含 amqp091
- 依賴設定各放子套件：`dbstartup` 只管 MySQL（`MySQLConfig`）與 schema 驗證，`redisstartup.Config` 讀 Redis 設定，`mqstartup.Config` 讀 RabbitMQ 設定；只有需要該依賴的服務才匯入對應子套件

### `pkg/tcpserver`

- 只做 TCP listen／accept 與 server runtime：接入時先以 `pkg/ratelimit` 的來源 IP 限流、再檢查連線上限（`server_accept.go`）
- listen 只經 `Server.listenFunc` 函式欄位（預設 `net.ListenConfig`），測試可注入替身；不另設 Transport 介面
- S2S 的來源 CIDR 白名單在 `pkg/s2sauth`（`allowed_cidrs`），不在本套件
- 不放 session、kick、login、routing policy；不變成 service locator

### `pkg/tcpclient`

- 只做 TCP dial／reconnect 與 client runtime：預設備援模式（依序嘗試、單連線），`WithDialAll` 全連模式（每個位址各一個撥號迴圈）
- 重連退避用 `cenkalti/backoff`；dial 只經 `Client.dial` 函式欄位（預設 `net.Dialer`，10 秒逾時），測試可注入替身
- 服務選擇由 `pkg/servicefinder` 與各服務自行決定
- 不放 session、kick、login、routing policy

### `pkg/s2shandshake`

- 只做 S2S 連線層握手與心跳：ConnectInfo／ServiceHello 收送、發版身分比對、hello 逾時與前置守門、背景心跳廣播
- 訊息型別在 `pkg/msg/system`，本套件只放使用它們的執行期流程
- 不放 session、login、routing policy

### `pkg/playerstore`

- 只做 World presence store / restore helper
- 不放 session policy
- 不放 recovery 裁決

### `pkg/protocol`（含 `wire`）、`pkg/dataconfig`（含 `generated`、`luban`）

- 只放 PJA-Protocol / PJA-Config 的**生成物**與其 Go runtime
- 由 `scripts/sync-protocol.ps1` / `scripts/sync-data-config.ps1` 同步，不得手改
- 生成物放 `pkg/` 而非 `internal/`，是為了讓 `pkg/msg`、`pkg/errcode`、`pkg/startup`
  不反向依賴 `internal/`（依賴方向只往下）
- 每個目錄都必須有 `doc.go`；`pkg/pkg_boundary_test.go` 會強制檢查
- 生成物目錄內不得放其他 `.go` 檔——同步腳本會把非生成物的 `.go` 刪掉
- `pkg/dataconfig` 只做 artifact、manifest、checksum 與快照 store 的機制（其中 `pkg/dataconfig/manifest` 的 `config_version.go` 放 `ConfigVersion*` 規則、`variable_migration.go` 放 `VariableMigration*` 型別；遷移步驟索引、鏈檢查與走訪在只依賴標準庫的葉套件 `pkg/dataconfig/migration`，`pkg/dataconfig` 以別名／包裝轉出，純規則套件走遷移鏈時不必連進 prometheus 與日誌），**不認識任何資料表內容**；World 專屬的換版規則（任務進度相容、道具／效果／事件 ID 不得移除、變數上下限與拓撲遷移檢查、熱重載與各種發布放行的檔案）放在 `internal/gamecore/configcompat`，由組合根與 `tools/internal/configartifact` 以 `dataconfig.CompatibilityChecker`（`NewSnapshotStore` 的 `checker` 參數（排程換版用的 `dataconfig.GameClock` 也是必要參數，nil 回錯，離線工具與測試傳 `HostClock{}`）、`Publisher{Checker: ...}`）注入；Checker 為 nil 時不檢查換版規則

### `pkg/servicefinder`

- 只做 service lookup
- 不放 routing 決策
- 不放 fallback policy

### `pkg/ratelimit`

- 只做通用 IP rate limiter、嘗試次數鎖定（`AttemptLimiter`，Gate 登入／登出限流）與驗證失敗鎖定（`FailureLimiter`，`httpx.AuthLimiter` 的實作）；三者共用 `maxTrackedKeys`（未匯出，10 萬）容量與 LRU 淘汰（fail-open）的表滿策略
- 不管 TCP service runtime
- 不放 session policy

### `pkg/tcpconfig`

- 只做 TCP config 讀取與地址解析
- 不管 runtime 生命週期
- 不放 session / routing policy

### `pkg/tcpsocket`（原 `pkg/tcpdeadline`）

- 做 Socket／`OwnerBase` 的收送 runtime：frame 收送迴圈、發送佇列與 deadline 常數（`socket_loops.go`）、連線生命週期與事件派送
- 不放 session／routing／kick 等 service policy
- 只依賴純標準庫葉套件 `pkg/msgmeta`（`ReqMeta`／`TrcMeta` 與三個選用訊息介面，`pkg/msg` 以別名轉出），不 import `pkg/msg`
- 測試接縫匯出（`pkg/startup.TCPShutdownMaxDuration`、`tcpclient.Client` 的 `IsDialAll` 方法、`tcpsocket.OwnerBase` 的 `SocketIndex` 方法）只有測試呼叫，列名保留

### `pkg/metrics`（非同步失敗契約）

- 佇列失敗 outcome 標籤與 `RecordAsyncFailure`／`InitAlertedAsyncOutcomes`／`IsDiscardOutcome` 在 `pkg/metrics`（原在 `pkg/appcore`，第六輪搬出），World／Gate gm 與診斷工具不必為此 import appcore
- 佇列深度告警門檻（`SendQueueDepthWarn`、`EventQueueDepthWarn`）也在此，configaudit 比對 alert-rules 的 expr 右值

### `pkg/mysql/dberr`

- `ErrDataRejected` 哨兵的零依賴葉套件（只 import `errors`），Chat 等服務 App 用它而不連進 gorm；分類函式 `IsDataRejection`／`MarkDataRejection` 留在 `pkg/mysql`（需要驅動錯誤型別），`pkg/mysql` 以變數轉出同一個哨兵；`gamestore` 沒有自己的別名，直接用 `dberr.ErrDataRejected`；`internal/archtest` 的 `TestServiceAppPackagesDoNotDependOnDrivers` 守每個 `cmd/*/internal/app` 的遞移依賴

### `pkg/localdeps`、`pkg/lobbyadminapi`、`pkg/recordapi`

- `localdeps`：本機依賴（MySQL 13306／13307、Redis 16379、RabbitMQ 25672）端點與帳密的單一來源，整合測試與維運工具引用；列入 `TestNonTestFilesDoNotImportTestutil` 的前綴清單，正式程式碼不可 import
- `lobbyadminapi`／`recordapi`：Lobby admin 與 Record `/events` 的路徑、查詢參數名與 DTO，服務端、整合測試與 opsconsole 共用

### `pkg/clihelp`

- 命令列工具共用的旗標解析（`Parse`：`-h` 用法寫 stdout、解析錯誤寫 stderr，回傳的錯誤以 `%w` 包住 `clihelp.ErrFlagParse`，`Run` 據此不重印用法）與執行骨架（`Run`：`-h` 回 0、用法錯誤回 2、執行失敗回 1 或呼叫端指定的結束碼），只依賴標準庫（第十二輪由原 `cmd/world/tools/internal/toolcli.Run` 搬出）
- `tools/` 的 `configaudit`、`configartifact`、`releasemanifest` 與 World 維運工具共用；World 工具把 `toolcli.ExitCode` 傳給 `Run`，保留被訊號取消時 128＋n 的結束碼。錯誤訊息前綴統一為 `<工具名>: `
- 服務的 `startup.Main` 也經 `clihelp.Parse` 解析旗標，`-h` 用法寫 stdout

### `pkg/timex`

- 與 context 搭配的計時小工具，沒有業務邏輯
- 單調時鐘值（第十二輪 TR-M1）：`Mono(t)` 把時間點換成自行程起點起算的單調奈秒數（可存進 atomic 欄位），`MonoNow()` 取現在，`FromMono(ns)` 換回帶單調讀數的 `time.Time`。要把計時用的時間點存進 atomic 欄位時用它，**不要存 `UnixNano`**：換回會丟掉單調讀數，牆鐘跳動時逾時判斷跟著錯。Gate 的握手／心跳逾時、pending session 清理、版本寬限期與 `redis.BackendCooldown` 都改用它；synctest 假時鐘下 `MonoNow` 可能為負，零值要另判

### `pkg/netx`

- 只做純網路 helper
- 不管 socket runtime
- 不管 service policy

### `pkg/testutil`

- 根套件只放輕量測試輔助（`VerifyTestMain`、`InCI`、測試時鐘），只依賴 `pkg/appcore`；Compose `stop_grace_period` 解析（需 yaml）第十二輪搬到 `pkg/testutil/composetest`（原 `testutil.ComposeStopGracePeriod`，現為 `composetest.StopGracePeriod`），根套件不再匯入 testify 與 yaml；讀 Prometheus 指標內容的輔助（`HistogramSampleCount`）在 `pkg/testutil/promtest`，同樣獨立子套件，根套件不匯入 prometheus 客戶端；`pkg/testutil/alertrules` 以 YAML 結構化解析 `monitoring/prometheus` 的告警規則與 promtool 案例，供契約測試共用（不用正規式逐行掃描）。現有子套件：`alertrules`、`composetest`、`fakes`、`promtest`、`repo`、`testdb`、`testredis`
- 測試替身（`StubSocket`、`StubService`、`StubFinder`、`EventLoopSocket`、`NoopPlayerStore`）在 `pkg/testutil/fakes`；倉庫路徑定位在 `pkg/testutil/repo`（純標準庫；測試一律用 `repo.Path` 定位倉庫根，不依目錄深度寫 `"..", ".."`、`Chdir("../..")` 或三層 `filepath.Dir`，`internal/archtest` 的 `TestTestFilesUseSharedHelpers` 守門）；`pkg/testutil/testredis`（miniredis＋`pkg/redis` 客戶端，獨立子套件以免 `pkg/redis` 外部測試形成循環）與 `pkg/testutil/testdb`（整合測試每套件獨立 MySQL 庫）。需要 miniredis 的測試一律用 `testredis.New`，不手建 `DisableCache` 客戶端（同一 archtest 守門；`pkg/redis` 自身測試與 example 例外）
- 只供測試使用，正式程式碼不可 import。測試專用套件不只 `pkg/testutil`，還有 `integration/`（含 `testenv`，匯入 testify）、`internal/gamecore/variable/variabletest`，另有本機依賴常數 `pkg/localdeps`；`internal/archtest/testutil_boundary_test.go` 的 `TestNonTestFilesDoNotImportTestutil` 以前綴清單守住這些套件

### `pkg/bootstrap` 調校鍵與 `pkg/logger.Set`（審查定案）

- N27 例外：`pkg/bootstrap/tuning.go` 的調校鍵清單含服務專屬鍵（`lottery.secret`、`admin_token` 等），維持集中列舉、不改成各服務以 WithTuningKeys 登記——登記制漏登記會退回寬鬆讀取，等於把「寫錯靜默改值」的風險放回各服務；新增服務專屬調校鍵時在清單補列。
- `logger.Set` 是共用邊界的接縫（組合根把 zerolog logger 交給 `pkg/logger`），維持原名不改。

### 測試探針與資料層守門

- 測試探針一律以 ForTest 結尾並放在被測型別旁：World 資料層 `Memory` 的 `HasChangeNotifierForTest`、`RequiresChangeNotifierForTest`、`HasDirectPersistenceForTest`、`HasQuarantineSpillForTest`；World Gate handler 的 `HasResourceReaderForTest`、`HasVariableRulesForTest`；`faultinject.EnableForTest`／`ResetForTest`；`tcpsocket.OwnerBase.MarkClosedForTest`；`ratelimit.AttemptLimiter.SeedForTest`；Record 資料層 `Events.RetentionDaysForTest`（組合根測試確認保留天數有傳進來）；Chat `App.WaitRoomJobsForTest`。
- World 資料層（`cmd/world/internal/store/...`）的遞移依賴不得含應用層套件（lifecycle、App、requestjournal、recordmq、amqp、tcpruntime）：`internal/archtest` 的 `TestWorldStoreDoesNotImportUpperLayers` 守門。要共用的型別放零依賴葉套件，例如保留期的 `PurgeJob`／`Purger` 在 `cmd/world/internal/retention`。

## 判斷規則

`pkg` 套件至少要有兩個實際 consumer；只有單一服務使用的放回 `cmd/<服務>/internal`（例如故障注入已搬到 `cmd/world/internal/faultinject`，request journal 已搬到 `cmd/world/internal/store/requestjournal`：Central、Gate 的 journal 刪除後只剩 World 使用）。`internal/archtest/pkg_consumer_test.go` 的 `TestPkgPackagesHaveAtLeastTwoServiceConsumers` 以 `go list` 的遞移相依計算每個 `pkg/` 套件被幾個 `cmd/<服務>` 使用（`pkg/testutil` 底下不計），不足兩個且不在白名單 `singleConsumerPkgAllowlist` 就失敗；白名單的值是理由（使用者其實橫跨服務與 `tools/`、`internal/game/simulation` 的共用碼才可列入），使用者增至兩個以上或套件被刪時，守門會要求移除該項。

若一個 package 的修改會同時牽動 `Gate / Central / World` 三邊流程，它多半不該在 `pkg`。

若一個 package 名字看起來很 generic，但 API 內已出現 `Login`、`Logout`、`Session`、`World`、`Gate`、`Central` 這類詞，它已經開始越界。

## 原則

- `pkg` 要薄
- `cmd/*/internal` 要厚
- 依賴方向只往下，不往回滲

## 根層 `internal/game` 例外

需要由正式服務（`cmd/world`，含其測試）與私人模擬器（`tools/private`）共用的純遊戲規則，可放在根層 `internal/game/{domain}`。`internal/game/playeraction` 即為此類：購買商店報價、使用背包道具的交易編排只依賴 `board.PlayerTx` 的子集，World 的 `gamestore` 以常駐玩家的暫存交易實作、模擬器以玩家副本實作，流程只有一份，鎖、冪等查詢與寫回留在各自儲存層。GM 發放與變數批次套用（`playeraction.ApplyGrant`、`ApplyVariables`，`grant.go`）也在這裡，道具使用（`ApplyUse`）與單筆調整共用同一套變數規則；擲骰提交順序在 `board.CommitRoll`，任務領獎順序在 `mission.ApplyClaim`（見[盤面回合與事件結算](../10-核心流程/盤面回合與事件結算.md)、[任務系統](../10-核心流程/任務系統.md)）。版控內的 `tools/` 只有 `tools/internal/configartifact` 匯入根層 internal：`internal/gamecore/configcompat`（換版規則），以及 `internal/game/gameconfig`、`internal/gamecore/gameday`（換日時刻的 `Schedule`；`loadableChecker` 以 `gameconfig.Load` 驗證候選版本，與 World 載入同一份規則）；其餘 `tools/` 工具不匯入。這是 module 內部共用的遊戲邏輯，不屬於公開 `pkg` 基建。

只允許放：

- 與傳輸、資料庫及服務 Runtime 無關的 Domain 型別與規則。
- 可由 World 與工具注入不同 Adapter 的小型 consumer-side interface。
- 確定已有 `cmd/world`（含測試）與工具（`tools/private` 模擬器；`gameconfig` 另有 `tools/internal/configartifact`）兩個實際 consumer 的邏輯。

禁止放：

- Protocol／message／socket 型別。
- MySQL、Redis、GORM 或特定服務的 Store 實作。
- World、Gate、Central 等服務生命週期與路由規則。

## 時間規則

時間分三種來源，另加日誌類。判斷原則：**拿來與遊戲時間戳比較、或寫進會被這樣比較的欄位，就是遊戲時間**。

| 種類 | 用途 | 來源 |
| --- | --- | --- |
| 遊戲時間 | 骰子恢復、冷卻、任務輪次與領獎期限、商店與抽獎每日重置、公告上下架、GM 發放請求時間與重試期限、聊天時間戳與保留期、Record 事件 `OccurredAt`、玩家活動時間（`updated_at`）與封存、帳號保留 | Central 校正時鐘：`App.GameNow()`（`pkg/appcore/clock.State.Now`），只前進 |
| 計時 | 逾時、TTL、退避、心跳、寬限、期限、限流、關機等待 | 主機單調時鐘：`time.Since`／timer；`time.Now()` 只用來算期限；存進 atomic 欄位的時間點用 `pkg/timex` 的單調值（`Mono`／`FromMono`），不存 `UnixNano` |
| 資料庫／Redis 仲裁 | Record outbox 租約、重試排程、第一次嘗試時間（`next_attempt_at`）與送出時間；Redis TTL | MySQL `NOW(3)`（連線 `time_zone` 為 UTC）／Redis 伺服器端 TTL |
| 日誌、指標、trace | 時間戳、耗時 | 主機時鐘 |

校正時鐘：

- Central 是遊戲時間來源，其主機時鐘（須 NTP，見 [Docker 生產部署](../30-部署與開發/Docker生產部署.md)）即遊戲時間；每秒（與 tick 異常跳躍時）以 S2S `TimeSync` 廣播給 Gate、World、Chat、Lobby，連線建立時立即補送一次。
- 接收端 `ApplySync`：第一次同步或偏差達 1 秒直接跳到 Central（記 Warn、`game_time_sync_jumps_total`，第一次不計）；第一次同步另把「已對外回傳的最大遊戲時間」重設為 Central 時間（對時前讀到的只是主機時鐘，偏快時不能釘住對時後的時間），其餘每秒最多修正 100 ms 逐步追上；對外遊戲時間取 max(上次, 新值)，往回跳時遊戲時間停住直到牆鐘追上，不倒退。偏移見 `game_clock_offset_seconds`。
- 收到第一則 `TimeSync` 前 `/ready` 不就緒：Gate 登入回 `AuthServiceUnavailable`、World 不建立玩家（回 Gate 服務不可用）、Chat 不寫訊息、Lobby 的公告與 GM 發放回 503。整合測試的假 Central（`integration/testenv`）同樣會送 `TimeSync`，不另設旁路。
- Record 不連 Central：事件時間只採生產者填的 `OccurredAt`，缺漏進死信；Record 主機時鐘只界定日分表範圍（界限寬達數日）。

用法：

- Gate、World 直接用 `App.GameNow`。World 注入點：盤面 router（每個指令取一次 now）、任務、`gamestore.NewMemory`／`NewWriteThroughMemory`（第一參數 `now`）、抽獎時間由請求帶入（`DrawRequest`，`lottery.New` 不收時鐘）、GM 發道具佇列 `gm.New(…, now)`、玩家歸檔、gorm `NowFunc`。
- Chat、Lobby 以 `pkg/centralclock.Start(app, tcpCfg)` 連 `<appID>.dial.central`（Central 60003／60004，S2S 授權讀 `s2s_auth.central`），`TimeSync` 在 App 事件迴圈套用，之後一樣用 `App.GameNow`。
- World 的 gorm `NowFunc` 是 `App.GameNow`：`autoCreateTime`／`autoUpdateTime` 與活動時間的 raw SQL 都寫遊戲時間，比較這些欄位（封存截止、帳號保留、金幣調整回看窗口、任務補償回看）也用遊戲時間；只有 outbox 的租約與排程欄位用 `NOW(3)`。
- 規則函式以參數接收 `now`；注入點為 nil 時的 `time.Now` 後備只給記憶體假件與模擬器，World 正式路徑不用。`pkg/appcore/clock` 的 `State.Now` 單調下限綁同步世代：尚未同步時下限是 `lastGame`（主機時鐘世代），首次 `ApplySync` 換世代後改用同步點自己的下限，對時前讀到的偏快主機時間不再約束對時後的遊戲時間。
- 注入方式統一為建構子必填：`gamestore.NewMemory`／`NewWriteThroughMemory`（第一參數 `now`）、`gm.New(…, now)` 都把遊戲時鐘列為必填，傳 nil 會 panic，不退回主機牆鐘；抽獎時間由請求帶入（`DrawRequest`），`lottery.New` 不收時鐘（原 `lottery.New(…, now)` 與 `worldSnapshotStore.now` 已刪），否則多台 World 的保護期、場次到期與重試期限會各自判斷。World 的其餘時鐘入口同樣必填：擲骰 `RollDiceDeps.Now` 列入 `validate`，缺漏在建構時回錯；載入玩家 `LoadPlayerOptions.Now` 在設定骰子懶恢復時零值回錯；任務自動領獎 `Config.Now` 零值回 `errGameplayEventNotConfigured`；`useGameClock` 在有資料庫卻沒時鐘時 panic（與 `lateClock` 一致），不再靜默沿用 gorm 預設牆鐘。啟動接線擋 nil 指標介面：`isNilClock` 只守快照倉庫的換版時鐘。其他必要依賴也不用可選 setter／Option：`lobbyreporter.New` 的就緒檢查是第四個位置參數（nil 時 panic，`WithReadyCheck` 已移除；漏傳會讓壞掉的實例照常續期公告），Central 首次登入自動建帳政策是 `gate.NewHandler` 的第四個位置參數（`SetNewUserPolicy` 已移除；組合根 `newGateHandler` 有測試斷言 `Config.NewUser` 確實交給處理器）。新增 World 依賴時鐘的服務請比照列為建構子必填。App 與 GameStore 互相需要造成的建構循環由 `cmd/world` 的 `lateClock` 處理：儲存層建構時傳入 `gameClock.Now` 當延遲取值的時鐘，App 建好後 `bind(App.GameNow)`；`bind` 之前就取時間代表接線順序錯誤，直接 panic。gorm `NowFunc` 同樣取 `App.GameNow`。
- `internal/archtest/game_time_boundary_test.go` 以 go/ast 禁止 `internal/` 與 `cmd/*/internal/` 直接用 `time.Now`／`time.Since`／`time.Until`；例外列在 `gameTimeAllowlist`（只能逐函式列出，格式 `路徑#函式` 或 `路徑#型別.方法`，附理由；沒有檔案級條目），失效項目也會讓測試失敗。

## World 與 simulator 共用遊戲邏輯

原則：**遊戲邏輯只有一份，通用系統放在 `internal/gamecore`，盤面等玩法放在 `internal/game`；World 與模擬工具（共用 `internal/game/simulation`）只實作外部依賴（儲存、亂數、時間）的轉接器。** simulator 只測遊戲邏輯，不測儲存語意（交易、回滾、冪等、outbox）。

| 套件 | 共用的邏輯 | World 轉接器 | simulator 轉接器 |
| --- | --- | --- | --- |
| `gameconfig` | 設定載入與跨表檢查（`Load`）；`Bundle` 帶出已驗證的骰子規則（`DiceToken`） | `buildWorldSnapshot` | loadRunner（私有工具 `tools/private/boardsimulator`，不進版控）、`LoadMissionRunner` |
| `dicetoken` | 骰子規則：容量、初始數量、恢復間隔的驗證（`LoadOptions`、`Options.Validate`）、玩家效果換算（`WithEffects`）、懶恢復與扣除（`Recovered`、`Consume`） | `board` 在玩家交易內套用（`recoverDiceTokens`、`newDiceSpend`；`gamestore.DiceUpdate`（原 `DiceSpend`）同時用於懶恢復與扣骰） | 尚未模擬骰子顆數，只共用 `Load` 的設定驗證 |
| `gamecore/condition` + `boardconfig.EvaluateCondition` | 條件樹求值；運算元由 `condition.Readers` 注入，盤面運算元（經過格數、建築等級）在 `boardconfig` | 變數與建築讀取器 | 變數讀取器（`variableReader`） |
| `gamecore/variable` | 缺值用預設、越界報錯（`Definition.Resolve`）與變數服務 | 組合根注入 `gamestore.VariableStore` | 同左 |
| `board` | 擲骰結算：`Inventory`（研究費用、工廠砲彈、事件獎勵）、`EffectStore`（研究效果替換） | `playerTx`（玩家記憶體交易） | `inventoryMap`、`effectList` |
| `boardconfig` | 建築升級：`BuildingCatalog.Plan`（查表）、`PayBuildingCosts`（直接收 `board.Wallet`）、`ApplyBuildingEffects` | `playerTx` | `simWallet`、`effectList` |
| `turn` | 擲骰回合流程 `turn.Play`：效果、擲骰、研究費用不足降級重算、工廠效果、抽獎條件、商店報價、收集抽獎、掛回獎勵 | `RollDiceDeps.turnPorts`（`Commit` 在玩家交易內保存並抽獎） | `Runner.turnPorts`（`Commit` 在玩家副本上套用並抽獎） |
| `gamecore/mission` | 任務接取與事件流程 `Play.Activation`／`Play.Event`（輪次、流程、跨輪次欄位、待領獎勵）、`IsClaimExpired`、`IsAutoClaim` | `restoreMissionState` 與 `missionStateRecord` | `missionSim.commit` |

規則：

- 規則函式以參數接收時間（`now time.Time`），不自己呼叫 `time.Now()`；simulator 有自己可調的時間來源。
- World 遊戲時間取 Central 校正時鐘（`clock.State.Now`，對外為 `App.GameNow`）：盤面指令建立請求時取一次 now，同一指令的規則判斷與任務事件時間戳共用；SQL store 與玩家歸檔也注入同一時鐘。TTL、逾時、重試、metrics 與 journal 等計時仍用主機時鐘，outbox 租約以資料庫 `NOW(3)` 仲裁；完整規則見〈時間規則〉。
- 模擬器 `RollOptions.Seed` 非 0 時以 PCG 決定加星道路、事件挑選、商店報價、互動 ID 與抽獎，配合 `Runner.Now` 可完全重現。
- 抽獎必須在儲存的鎖內「讀狀態、抽、寫狀態」，所以 `turn.Play` 把抽獎交給 `Commit`，不在共用層先抽。
- 兩邊行為不同時，**以 World 現行行為為準**，只改 simulator。
- 新增 World 與 simulator 都會用到的規則時，先放 `internal/game`，不要在 `cmd/world/internal` 寫一份再讓 simulator 複製。
- 抽獎結果轉道具只有 `lottery.Reward.AsItem` 一份規則：非道具、目標 ID 不在 1～MaxInt32、數量為負一律不合法回錯；數量 0 的道具獎勵載入設定時即拒絕，執行期在 World 入帳、`turn`、simulator、任務領獎一律略過屬縱深防禦（不再由 `turn`／simulator 回錯）。一個指令只有一個遊戲時間：由呼叫端取一次，經 `gamestore.WithGameNow` 帶在 ctx 上，Memory 的玩家交易、事件與 outbox 時間都用它，不在換日邊界前後各取一次。`DrawRequest.DrawMultiplier` 少於 1 視為抽 1 次，任務領獎明確以倍率 1 抽獎。
- World 沒有自己的 shop 轉接層：`internal/gamecore/shop` 的 `Quote`／`Receipt`／`Service`／錯誤直接使用；World 的持久層接線放在組裝層：`shopPersistence` 介面與 `shopStoreAdapter` 在 `cmd/world/internal/services/shop_service.go`（`newShopService`，未匯出，由它接線），`gamestore/shop_store.go` 只留資料列與領域互動的轉換，原 `cmd/world/internal/shop` 已刪除。
- 合法設定只有 `gameconfig.Load` 這一份：World 的 `buildWorldSnapshot`（啟動與熱重載）與模擬工具都經它驗證，`cmd/world` 不得另外放寬或加嚴；`services/config_test.go` 以一致性測試守住兩邊對壞設定的結論相同。設定發布與切換版本（`configartifact`）也跑同一份 `gameconfig.Load`（`loadableChecker`，包住 `configcompat.Checker`），所以商店引用等跨表規則只在 `gameconfig.Load` 維護一份，`configcompat` 不再有商店檢查；熱重載由 World 的 prepare 把關。

仍未共用：

- 任務領獎（`claim`）與抽獎狀態的儲存：World 在玩家交易內保存抽獎計數、紀錄與道具，simulator 以記憶體狀態與可重現亂數，這屬於儲存語意，不共用。
- 成本變數沒有資料列時，World 視為 0；若日後變數 `Default` 不為 0，兩邊要一起決定規則。

## `internal/gamecore` 通用遊戲系統

與玩法無關的系統（variable、item、effect、condition、lottery、mission、shop，以及全 Server 共用的遊戲日 `gameday`）放在 `internal/gamecore/<系統>`，每個系統一個包，含規則、設定載入與必要的服務。

設定換版規則（`configcompat`）也放在這裡：它只依賴 `pkg/dataconfig` 的生成物與機制，不依賴其他 gamecore 子包；World 以 `configcompat.Checker{}` 注入快照 store，任務狀態版本相容判斷用 `configcompat.IsMissionStateCompatible`，變數遷移步驟用 `configcompat.LoadVariableMigrationSteps`。

- 純規則套件不得遞移依賴 prometheus、zerolog、otel、viper：`internal/archtest/domain_deps_test.go`（`TestDomainPackagesDoNotDependOnObservabilityLibs`）守 `internal/game`、`internal/gamecore` 的純規則套件（`boardconfig`、`dicetoken`、`gameconfig`、`playeraction`、`turn`、`variable`、`variabletest` 等），豁免 `configcompat`（實作 `dataconfig.CompatibilityChecker` 必然 import `pkg/dataconfig` 根套件）與 `simulation`（`LoadEffectiveBundle`／`LoadMissionRunner` 用 `dataconfig.LoadEffective`，根套件連進 `pkg/metrics`、`pkg/logger`；把載入便利函式搬出 simulation 另案）；`TestSimulationDoesNotImportLoggerDirectly` 另守 simulation 不直接 import `pkg/logger`。
- 依賴方向：`cmd/world` → `internal/game`（玩法層）→ `internal/gamecore`。`gamecore` 不得引用 `cmd`、`tools`、`integration`、`internal/game`，子包之間也不得互相引用，例外兩條：`gameday`（全子包共用的遊戲日規則，不含任何玩法，兄弟子包可直接引用）與 `configcompat → variable`（理由：變數表解析須與載入端同一份 `variable.LoadDefinitions`，見 `internal/gamecore/boundary_test.go` 的 `allowedSiblingEdges`）；由 `internal/gamecore/boundary_test.go` 強制。
- 外部能力一律由消費端定義介面並以建構子注入：Store（`variable.Store`、`effect.Store`）、Handler（`item.Handler`）、取值來源（`condition.Readers`）、獎勵目錄（`mission.RewardCatalog`）。原 `variable.WithSaveFailureHook` 指標回呼已刪。
- 亂數、互動 ID、抽獎種子、時鐘一律由呼叫端注入：`board.Definition.RandomIntn` 於需要隨機時必填、`shop.New` 需 `WithIDSource`、`simulation.Runner.Now` 必填；World 組合根注入 `board.DefaultIntn`、`secureInteractionID`、`secureSeed`，全域亂數檢查（A4）的白名單只剩 `board.DefaultIntn`。
- 持久化轉接器放在 `cmd/world/internal/store/gamestore`（`VariableStore`、`EffectStore`），商店服務接線在 `services/shop_service.go` 的 `newShopService`，皆由 `services` 組合根建立；斷路器包裝在子套件 `gamestore/cbstore`（`cbstore.New`，gobreaker 與 `mysql.BreakerSettings` 不留在業務層 `gamestore`）；archtest 擋 `cmd` 正式碼 import 模擬器與測試替身）。
- 跨系統的載入與驗證放在 `internal/game`：`gameconfig`、`missionconfig`、`boardconfig`（盤面運算元 `OperandTypeBoardSpaceKindPassedCount`／`OperandTypeBuildingLevel` 與 `EvaluateCondition`、效果來源 `board.EffectSource*`；抽獎條件允許的運算元種類是變數、經過格數，任務再加建築等級，未知種類載入時拒絕）。
- 不要把 `GameConfigs` 當 service locator 傳進 `gamecore`；載入函式只在啟動時呼叫一次，之後只傳具體的 `Definitions`。
