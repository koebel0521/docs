# 工作規範

## 操作習慣

- 新增說明文檔時，檔名與內容皆使用中文。保留通用慣例名（`README.md`）與專有名詞（Docker／Redis／TCP／World／SLO／p0 等縮寫）。
- 日誌統一走 `pkg/logger`，底層固定 `zerolog`；不要直接在新程式碼引入 `log/slog`。
- zerolog 為本專案唯一日誌庫，禁止遷移至 slog 或其他日誌庫。
- 只做會降低重複、收斂錯邊界、或明確減少複雜度的重構；禁止為了「拆薄」而把正常共用邏輯拆散到多處，或把一段本來單純的程式變成更多 wrapper / 更多重複 code。

## 模組化與工程骨架

### 1. 合理模組化

- 以「合理模組化」為目標，禁止為拆分而拆分。
- 每個模組都必須有明確責任（single responsibility）、清楚邊界（boundary）、以及實際存在的價值。
- 不允許只為了形式而新增抽象層。
- 不允許過度拆分，避免模組過薄（thin modules）。
- 不允許把單一流程切成多個沒有實質意義的層。

### 2. Cross-App 一致性

- 所有 apps 都必須遵守一致的結構原則。
- 統一層級（layering），例如 `handler / service / domain / infra`。
- 不允許任意新增、混用、或漂移層級。
- 統一角色（role），相同職責的模組在不同 app 中要對應到一致位置。
- 不允許同名不同責，避免語意漂移。
- 統一命名（naming），相同概念必須使用相同命名。
- 不允許同義多命名混用，例如 `svc` 與 `service` 混用。
- 不強制統一粒度（granularity）；模組大小可依實際需求調整。
- 不能為了對齊結構而強行拆分或合併模組。

### 3. 重構決策

- 所有重構都必須有明確收益，至少包含可讀性、維護性、或擴展性提升之一。
- 如果看不出明確收益，就要停止，不得進行修改。
- 禁止為了風格一致而重構。
- 禁止為了「看起來更乾淨」但沒有實質改善的調整。
- 禁止 over-engineering。

### 4. 漸進式優化

- 只在正在修改的區域做優化。
- 禁止對無關區域做大範圍重構。
- 每次修改都要符合小範圍（small scope）、低風險（low risk）、可回滾（reversible）。
- 禁止一次性大規模重寫（big-bang refactor）。
- 禁止跨多模組的無必要結構重整。
- 原則上讓系統隨每次變更逐步改善，不追求一次到位的理想結構。

## 依賴注入原則

### 1. 預設：手動建構注入

- 小範圍（< 10 services）使用手動建構注入，不需要 DI 框架。
- 依賴透過建構子參數傳入，禁止使用全域變數或 `init()` 初始化服務。

### 2. Functional Options 模式

- App 層的依賴（RedisClient、PlayerStore、GameStore 等）透過 Functional Options 注入。
- 欄位設為私有（unexported），透過存取方法（`PlayerStore()`）對外提供。
- Option 應回傳 `error` 以便建構時驗證參數合法性。

### 3. 介面隔離

- Handler 層不應接收整個 `*app.App`，而應定義最小所需介面（如 `WorldEventDeps`）。
- 介面定義在 consumer 端（handler package 內），不另外開共用介面包。

### 4. DI 框架為選用

- `samber/do/v2` 已加入依賴基底，可選用於新 service 或需要容器化管理的場景。
- 既有 service 持續使用手動 DI，不強制遷移。
- injector 僅存在於 composition root（`run.go`），禁止傳遞 injector 給業務層。

## Handler 防禦性檢查規範

### 1. EventBase nil-check 順序

- 優先檢查 `r.App == nil`（或 `r.Deps == nil`），不檢查個別方法參數。
- 範例：`if r.App == nil || sock == nil { return }`

### 2. Coordinator nil-check 順序

- 優先檢查 `c == nil`，再檢查核心參數。
- 範例：`if c == nil || m == nil { return }`

### 3. 只檢查必要的 nil

- 不檢查已經在 Init/Constructor 中驗證過的欄位。
- 測試用的 nil 場景用獨立的 TestCase 覆蓋，不在 production handler 中檢查。

### 4. Type assertion 安全規範

- 所有 `any` 或 interface 的型別斷言**必須**使用 comma-ok 形式：`v, ok := x.(T)`
- 禁止用 `_` 捨棄 `ok` — 型別不符時應回傳 error 或做降級處理，而非靜默設零值
- 泛型函式中對 unconstrained type parameter 做介面斷言時，同樣必須 comma-ok guard
- 參考實作：`pkg/msgpool/pool.go`、`pkg/msgpool/pack.go`、`pkg/requestjournalredis/journal_load.go`

### 5. 定時器集中化規範

- per-connection 的 goroutine + timer 模式（handshake timeout 等）應改為中央掃描 goroutine，從 O(n) 降為 O(1)
- 集中化可參考 `cmd/gate/internal/handler/user/connect_watchdog.go`：`startHandshakeWatchdogChecker` + `checkHandshakeTimeouts`
- 判斷依據：若能透過 socket 標記狀態（如 `sock.ID() == 0`）判定逾時，就無需 per-connection timer

## 效能慣例

### 1. 序列化零分配

- 所有訊息型別**必須**實作 `PackTo(buf []byte) []byte`，讓 send 路徑可經由 `socket.sendBuf` 零分配序列化
- 固定大小訊息使用 `binary.LittleEndian.AppendUint{64,32}(buf, val)` 取代 stack buffer + slice escape
- `Pack()` 應委託 `PackTo(nil)`：`func (m *T) Pack() []byte { return m.PackTo(nil) }`
- 有 `Payload []byte` 的可變大小訊息應有 `PackTo` 與 `Reset` 保留 backing array
- 參考實作：`pkg/msg/chat/chat_codec.go`、`pkg/msg/channel/broadcast.go`、`pkg/msg/channel/membership.go`

### 2. Lock-free 讀取優先

- 高頻唯讀路徑優先使用 `atomic.Pointer` 或 `atomic.Value` + copy-on-write，取代 `sync.Mutex` / `sync.RWMutex`
- 適用場景：config 快照、service picker、路由表等讀多寫少的狀態
- 參考實作：`pkg/tcpclient/client_picker.go`：`Picker` 以 `atomic.Pointer[pickerState]` 取代 `sync.Mutex`

### 3. sync.Pool 臨時 slice

- 函式內部建立的臨時 slice（如查詢結果的 candidate list）應使用 `sync.Pool` 重用 backing array
- 設定合理的初始容量（如 16），過大的 slice（> 4096）不歸還以防止 large object 堆積
- 參考實作：`pkg/tcpsocket/sockets_query.go`：`socketsSlicePool` for `Random()`

## 單一 Go module

本專案只有一個 Go module：`github.com/koebel0521/project`（根目錄 `go.mod`）。`pkg/`、
`cmd/<service>/`、`tools/` 全在同一個 module 內，沒有 `go.work`。

- 服務實作位於 `cmd/<service>/internal/`，Go 的 `internal` 規則天然阻止其他服務
  引用（`cmd/gate/internal` 只能被 `cmd/gate/...` import）。
- 跨服務引用另外由 `pkg/cmd_boundary_test.go` 把關；服務之間只能透過 TCP 協定
  （`pkg/msg`、`pkg/protocol`）溝通，不得直接引用彼此的 internal 實作。
- 新增依賴時在專案根目錄執行 `go get`，再 `go mod tidy`。
- 工具依賴（`golangci-lint`、`benchstat`、`govulncheck`）以 `go.mod` 的
  `tool` directive 宣告，透過 `go tool <name>` 執行。

## 共用套件

各 `pkg/` 套件與 `internal/testutil` 的職責與邊界，統一寫在 [[共用邊界]]，這裡不再重複。
