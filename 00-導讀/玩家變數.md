# 玩家變數

現行 Variable 行為；完整方案背景見[方案草稿](../90-參考附件/方案草稿/玩家變數與資源消耗規範.md)。

- 定義：Luban `Variable`，Runtime 使用 `int64`、default、上下限與 `SyncClient`。
- 保存：保存所有 variable 值（包含 default），一律寫入；玩家恢復時一併載入。
- 同步：登入回傳 Client 可見變數；登入後只回傳變更值。
- 權威：Server 決定數值與扣除結果，Client 不得自行修改。
- 合法性：變數 ID 必須為正數且不超過 int32（`variable.ValidID`），範圍定義 Min/Max/Default 由 `Definition.Valid` 檢查；`LoadDefinitions`、`validateDefinitions`、調整單與盤面路由的經過次數變數檢查共用，負 ID 變數表在 `gameconfig.Load` 就被拒絕。同一批調整（GM 發變數、道具使用）含重複變數 ID 時整批拒絕（`variable.ValidBatch`）。
- 沒有變數服務時，推送變更集與道具使用結果都不對 Client 同步變數（`Service.ClientVisible` 對 nil 回 false）。
- 遷移鏈（盤面拓撲、玩家變數）共用 `dataconfig.WalkMigrationChain`：缺步驟、不前進或步驟數超過總數（A→B→A 繞圈）都回錯，不再無限迴圈；拓撲遷移的新科技 ID 必須為正數。
- 實作：`internal/gamecore/variable`；定義載入見 `definition.go`，快照見 `Snapshot`。Store、deltaStore、migratingStore 與寫入失敗回呼由組合根注入，World 的持久化轉接器是 `gamestore.VariableStore`。
- 變數遷移記錄（`migratedPlayers`：該玩家已確認過遷移版本，之後讀寫不再重複確認）是有界 LRU（`hashicorp/golang-lru/v2`，上限 8192，執行緒安全、無額外 goroutine），滿了只淘汰最久沒用的玩家；玩家卸載（`EvictPlayerData` 與離線卸載成功）時由 World 呼叫 `Service.ForgetPlayer` 一併刪除，記錄數跟著線上人數走。舊版滿 8192 筆就整表清空，5000 名線上玩家的記錄一起失效，每人下一次變數讀寫都要重新確認版本，形成週期性突波。

## 增減的原子性與骰子規則

- `variable.Service.Add` 走 `GameStore.AddVariable`：在玩家交易內讀取、加減、檢查 Min/Max 後寫回，與擲骰扣骰、道具使用等交易內寫入互斥。測試替身沒有實作時退回讀後寫。`Set`、`Add` 都是單次 Store 原子呼叫，服務本身不再有 64 段 `keyLocks`（舊版持鎖期間還會讀 MySQL）；原子性完全由 Store 的玩家交易保證，離線遷移在 Store 交易內冪等。
- 骰子數量（`DiceCount`、`DiceRecoveryAt`）**不允許超過上限**，只由擲骰與登入載入時的恢復寫入（`nextDiceState` 會截回上限）。
- 因此設定載入時會拒絕「立即生效」道具調整骰子變數（`services/config.go` 的 `validateItemVariables`）：GM grant 在背景 goroutine 套用，會繞過上限，也會與載入時讀後寫的 `RecoverDiceTokens` 互相覆蓋。背包道具走使用交易，不受此限。
- 若日後要發放骰子獎勵，做成專門的「補骰子到上限」動作，由骰子邏輯處理，不要用道具直接加。

變數 migration 使用[配置操作入口](../30-部署與開發/配置操作入口.md)。
