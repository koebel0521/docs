# 設定注入與熱更新

服務啟動時由 `startup.InitializeRuntime` 建立該服務專用的 `*viper.Viper`。

## 規則

- `viper.Viper` 只能在 composition root 建立與讀取。
- 基礎套件與服務內部透過參數接收設定，不讀取 Viper singleton。
- Redis、MySQL、TCP 與 tracing 設定由 `run.go` 建構後傳入。
- `configwatch.Start(path, load, onReload)` 必須接收非 nil 的 loader（`load == nil` 回傳錯誤）。
- 熱重載讀出新的設定實例，只交給明確註冊的回呼（`applyDynamicConfig`、服務自己的 `onReload`）；啟動實例永遠不會被改寫，所以沒有註冊的鍵改了不會生效。

## 新增服務

1. 呼叫 `startup.InitializeRuntime`（選項型別 `startup.RuntimeOption`），成功後立刻 `defer rt.Close()`。
2. 從回傳的 `*startup.Runtime` 的 `Config` 建立 typed config 或基礎設施設定（觀測設定為 `startup.ObservabilityConfig`）。
3. 將設定傳給 service constructor / `Run`：Gate、Central 的組合根在 `cmd/<svc>/services_config.go` 解析成 `services.Config`，`internal/services` 不再接收 `*viper.Viper`。
4. 不在 `pkg` 或 `cmd/*/internal` 重新呼叫 `viper.Get*`。允許 import viper 的只有 `cmd/<服務>/` 頂層（組合根）與 `pkg` 內的 `bootstrap`、`startup/**`（含 `dbstartup`、`redisstartup`、`mqstartup`）、`configwatch`；`pkg/s2sauth`（`Configure*For`）與 `pkg/tcpconfig`（`BuildConfig`）是只給組合根呼叫的轉換函式，刻意留在原處不搬（搬移收益低），列為明確例外。Lobby 另有兩個明確例外：`cmd/lobby/internal/handler/servers.go` 與 `cmd/lobby/internal/services/token_reload.go` 被視為組合根的延伸，可 import viper 讀取熱重載後的設定（白名單在 `internal/archtest/viper_boundary_test.go` 的 `viperAllowed`）。`internal/archtest` 的 `TestViperOnlyImportedByCompositionRoot` 以 import 掃描守住這份清單，`cmd/*/internal/**`、`internal/**` 與其餘 `pkg` 一旦 import viper 測試就失敗。

這個邊界讓測試可以建立獨立的 Viper 實例，也避免不同啟動流程共用可變設定。

## 環境變數覆寫

- 以 `Get*` 逐鍵讀取的設定鍵都可用環境變數覆寫：鍵名轉大寫、`.` 換成 `_`，例如 `redis.password` 對應 `REDIS_PASSWORD`、`s2s_auth.world.server_name` 對應 `S2S_AUTH_WORLD_SERVER_NAME`。
- 沒有服務前綴（`AutomaticEnv` 未設 `SetEnvPrefix`）：Docker compose 正是靠這個規則注入 MySQL、Redis、RabbitMQ 帳密與 Lobby token。代價是主機上任何同名的環境變數都會被服務讀進去，同一台主機直接跑多個服務時，彼此的環境變數不可混用。
- **與設定區段同名的環境變數會讓啟動失敗**：viper 對巢狀鍵（如 `debug.addr`）會先檢查每一層父鍵有沒有同名且非空的環境變數，有的話整個子樹回零值、`IsSet` 回 false，設定被靜默忽略（`DEBUG` 讓 `debug.addr` 失效、`MISSION_RESET` 讓全服換日時間退回 UTC 00:00、`GO` 讓 Go 記憶體上限消失、`REDIS` 讓 Central 的 Redis 設定消失而走單機記憶體模式；Central 有設定 Redis 卻連不上時則直接拒絕啟動）。`pkg/bootstrap` 載入設定後檢查這類衝突，發現就拒絕啟動，錯誤訊息列出變數名與被遮蔽的區段；請移除或改名該環境變數。常見會撞名的區段有 `DEBUG`、`REDIS`、`MYSQL`、`GO`、`SESSION`、`TCP`、`OTEL`、`COMBAT`、`FEATURE`、`RABBITMQ`、`MISSION_RESET`、`GAME_STORE`、`DATA_CONFIG`，以及 `S2S_AUTH_<服務>` 這類中間層。葉鍵同名（`MYSQL_HOST`）是正常覆寫，空值也不受影響。
- 清單型設定（`s2s_auth.*.allowed_cidrs`、`redis.sentinel_addrs`、`combat.loadout_config_keys`）用環境變數覆寫時以逗號分隔多個值。
- 例外：`<id>.listen.*`、`<id>.dial.*` 以 `GetStringMap` 整段讀取，不套用環境變數；`--protocol-record` 是純旗標，不經 viper：設定檔的 `protocol-record` 鍵已無作用，也不在熱重載前綴內；協定記錄的優先序為 旗標 `--protocol-record` > 環境變數 `DEBUG_PROTOCOL_RECORD` > 設定檔 `protocol_record_enabled`。
- `--log-format`、`--log-level` 在讀設定檔前就交給 logger，不進 viper；未給旗標時預設取環境變數 `LOG_FORMAT`、`LOG_LEVEL`（再預設 `json`、`info`），層級只接受 `trace`、`debug`、`info`、`warn`、`error`，寫錯以結束碼 2 拒絕啟動，錯誤訊息標明來源（如 `from env LOG_LEVEL`）；`--protocol-record` 寫錯也是用法錯誤（結束碼 2），`-version` 在旗標與環境變數檢查之前處理。
- 設定檔路徑：`-config` 優先；未給時取環境變數 `APP_CONFIG`（容器用），再退回各服務的預設 dev 路徑。啟動成功會記一筆 `config loaded`（含實際路徑）。

## 嚴格解析

viper 的 `GetDuration`、`GetInt`、`GetBool` 遇到寫錯的值不報錯：沒有單位的數字被當成奈秒（`history_retention: 30` 變成 30ns，會刪光聊天紀錄）、無法解析的值變成零值。會改變業務結果的鍵改用 `bootstrap.Duration`、`bootstrap.Int`、`bootstrap.Bool`，已設定但不合法時讓啟動失敗：

- 時長只接受帶單位的字串（`30s`、`720h`）與 `0`：Chat `history_retention`、Gate `session.*` 時長、`redis.conn_max_lifetime`／`conn_max_idle_time`。可熱重載的 `protocol_record_ttl`、`protocol_record_file_retention` 寫錯只記 Warn 並用預設。
- 整數：各服務 `id`（必須是正整數；驗證後以十進位寫回 viper，`1001.5`、環境變數 `01001` 不再被截斷或當成八進位）、World `max_players`（未設定或 `0` 用預設值，**負值是設定錯誤，World 拒絕啟動**，錯誤 `max_players must not be negative`；`6k`、`6,000` 等壞值也拒絕啟動，不再退回預設）、Gate `session.board_command_burst`、`session.max_connections_per_ip`、Central `new_user.burst`、`new_user.min_password_bytes`、`mission_reset.hour`／`minute`、`session.max_login_attempts`、`go.memory_limit_mb`（寫成 `512MB` 不再變 0 而悄悄不設 GOMEMLIMIT）、`redis.db`（寫錯不再悄悄改寫 db 0）。
- 浮點數：`otel.sample_rate`（`bootstrap.Float`；寫成 `5%` 不再變 0 而開啟全量匯出）、Gate `session.board_command_rate`、Central `new_user.rate`。
- 布林只接受 `true`／`false`：`feature.central.state_auditor`（YAML 1.2 的 `on`、`yes` 是字串，會被拒絕）。
- **調校數值鍵與開關鍵**（`bootstrap.validateTuningKeys`，`InitRuntime` 啟動時驗證並把十進位結果寫回 viper，之後各套件的寬鬆 `GetInt`／`GetBool` 讀到同一個值；未設定的鍵不受影響）：整數鍵 `max_connections`、`tcp.max_connections`、`tcp.rate_limit_burst`、`tcp.socket_send_queue_depth`、`mysql.port`、`mysql.max_open_conns`、`mysql.max_idle_conns`、`redis.pool_size`、`redis.min_idle_conns`、`rabbitmq.prefetch_count`、`rabbitmq.buffer_size`、`protocol_record_limit`；浮點鍵 `tcp.rate_limit_per_second`；布林鍵 `redis.disable_cache`、`debug.pprof_enabled`、`protocol_record_payload_enabled`、`protocol_record_enabled`、`data_config.allow_legacy_directory`；時長鍵 `mysql.audit_record_slow`（見下）。浮點鍵另含 `otel.sample_rate`，`NaN`／`Inf`（例如 `.nan`）一律拒絕，前後空白經嚴格解析後寫回。寫錯讓啟動失敗：舊行為是 `1k` 靜默變 0 而退回預設、`020` 被當八進位變 16、`yes` 變 false。
- **`mysql.audit_record_slow`**（原 `mysql.audit_record_slow_ms`，已改名）：Central 稽核紀錄查詢的慢查詢門檻，時長必須帶單位（`500ms`）；該鍵不在任何設定範本，只影響日誌 `central audit query slow` 的觸發。舊名 `audit_record_slow_ms` 不再被讀取。
- **環境變數 `AUTO_MIGRATE_DISABLED`**：不屬 viper 鍵，由 `bootstrap.ParseSwitch` 解析，接受 `true`／`false`／`1`／`0`／`t`／`f`（`strconv.ParseBool` 的寫法）與 `on`／`off`／`yes`／`no`，不分大小寫、略過前後空白。舊版只認小寫 `true`，`TRUE`、`1`、`yes` 反而在正式庫開啟 AutoMigrate。寫錯（例如 `ture`）讓 `InitRuntime` 啟動失敗；空字串視為未設定（啟用 AutoMigrate）。
- **World `lottery.secret`**：非空之外，World 啟動拒絕 `change-me`／`change_me` 開頭的範本佔位與短於 16 字元的值（`validateLotterySecret`；開發與整合測試設定的 secret 是 25～26 字元，所以門檻訂 16 而非 32）。

範本裡的鍵另有反向檢查（`tools/internal/configaudit` 的 `TestEveryConfigTemplateKeyIsReadByCode`）：範本鍵名打錯會讓測試失敗。這個守門除了 `Get*` 呼叫，也掃 `bootstrap` 嚴格讀取器、Gate `session.*` 表格與組合根的 `xxxKey` 常數；`optionalConfigKeys`（不在範本的選填鍵）每一項都必須被掃到，否則測試失敗。Record 範本已移除不會被讀到的 `protocol_record_*`、User 範本已移除 `tcp.rate_limit_*`。

## 熱更新

- 所有走 `startup.InitializeRuntime` 的服務都會監看設定檔（含 Chat、Record）。可熱更的鍵只有白名單內的：
  - 可熱更鍵由各服務經 `startup.WithHotReload(HotReload{Prefixes, Apply})` 宣告，`Prefixes` 是該服務要追蹤的鍵前綴，`Apply` 回傳套用結果；共用的協定紀錄鍵不必各服務重複宣告。
  - `protocol_record*`（含 `protocol_record_ttl`、`protocol_record_file_retention`）：所有服務；協定檔案記錄的參數沒變時沿用同一個記錄器，不會每次熱重載關檔重開。
  - `traffic_slice_*`：Central（`SetTrafficSlice`）。Central 在 `initStorage` 期間收到的重載，會在 App 建好後套用，不再被啟動時的舊值蓋掉。**啟動時 `traffic_slice_*` 不合法 Central 拒絕啟動**（啟動沒有舊切片可保留，否則 canary 看似已開卻全量走舊 World）；啟動後熱重載收到不合法值才只記 Warn、保留上一版有效切片。
  - `admin_token`、`ops_token`、`gm_token`：只有 Lobby 真的重載（先驗證才套用）；其他服務讀了也不會用。驗證規則：`change-me`／`change_me` 開頭的佔位值拒絕、非空須至少 32 字元、**三個非空 token 不可跨層級重複**（admin／ops／gm 任兩個相同，`Match` 會先命中高層級，稽核身分與權限會混淆；啟動與熱重載都拒絕）。
  - **被同名環境變數遮蔽的鍵不會生效**：`AutomaticEnv` 下非空的同名環境變數（鍵轉大寫、`.` 轉 `_`，例如 `ADMIN_TOKEN`）優先於設定檔；`protocol_record_enabled`、`protocol_record_payload_enabled` 另受 `DEBUG_PROTOCOL_RECORD` 覆寫。這些鍵改了設定檔不會被記成 applied，改記 Warn `config change shadowed by environment variable, not applied`（`config`、`keys`）。正式環境 Lobby token 由環境變數提供，所以輪替 token 要改環境變數並重啟，不能靠改設定檔熱更。
  - **熱重載與啟動走同一套嚴格解析**：調校數值鍵（見上，含 `otel.sample_rate`）有不合法值（例如 `protocol_record_limit: 1k`）時，整份新設定被拒絕（`invalid reload config`）、沿用舊設定，不會靜默改值後記 applied。
  - 只能監看單一路徑（watcher 只盯 `paths[0]`）：傳入多個設定路徑時熱重載整個關閉並記 Warn `config hot reload disabled: only a single config path can be watched`；目前正式呼叫端只傳一個路徑。
  - 其餘鍵（`session.*`、`tcp.*`、`redis.*`、`max_players`、`mission_reset.*`、`debug.*`、`history_retention`、`s2s_auth.*`、`<id>.dial.*` 等）只在啟動時讀一次，改了要重啟。
- 重載時與上一份快照比對，日誌依**實際套用結果**分三種：Info `config hot reload applied`（`keys` 只列真的套用的鍵）；Warn `config hot reload not applied`（`keys`、`err`：服務宣告可熱更的鍵套用失敗，例如值無效、token 驗證失敗，或 Lobby 啟動時沒有 token、事後才補上而需重啟才有 admin 端點）；Warn `config change requires restart, not applied`（`keys`：改了不能熱更的鍵，不含值）；另有 Warn `config change shadowed by environment variable, not applied`（`keys`：鍵被同名環境變數遮蔽，見上）。維運看到 `not applied` 或 restart 警告就要修正值或重啟該服務；`applied` 不再等於「鍵名前綴符合」，只列真的生效的鍵。`configwatch` 監看單一設定檔所在目錄；同一檔案連續的寫入、改名事件在最後一個事件後 100ms 才重載一次，重讀失敗時沿用舊設定並記 Warn。
- fsnotify 回報的錯誤（例如事件佇列溢位）記 Warn：熱重載可能漏掉變更，需確認設定是否已套用。
- **熱重載拒絕沒有 `id` 的設定**：就地覆寫（`cp`、編輯器非原子寫入）時可能讀到空檔或截斷但仍可解析的 YAML，每個服務設定必有 `id`，缺 `id` 就視為讀取失敗（`readReloadConfig`，熱重載與基準快照共用），沿用 `configwatch` 的重試與沿用舊設定路徑，不會把空設定當有效值套用（例如 Central 讀到空的 `traffic_slice_percent` 而關閉 canary）。基準快照讀取失敗時記 Warn：第一次熱重載的差異清單不可信（所有鍵可能被誤記成 `requires restart`／`applied`）。
- 正式 compose 以目錄掛載 `docker/prod/config:/config:ro`。單檔 bind mount 在宿主機以暫存檔改名（vim、`sed -i`、部署工具）更新時會停在舊 inode，熱重載收不到；改完設定一律確認有 `config hot reload applied` 日誌且 `keys` 含你改的鍵；看到 `config hot reload not applied`、`config change requires restart` 或都沒有就修正或重啟。
- `feature.central.state_auditor` 只在啟動讀一次，改了要重啟 Central。
- 可熱更的 `protocol_record_ttl`、`protocol_record_file_retention` 寫錯只記 Warn 並用預設（與嚴格解析的啟動鍵不同）；`traffic_slice_*` 壞值保留上一版有效的切片。

## Gate `session.*` 選填鍵

都不在範本內，以預設值運作；時長必須帶單位，寫錯讓 Gate 啟動失敗。只影響 Gate 本身：Central 對 Gate 斷線的寬限固定 30 秒（`appcore.ServiceDisconnectGracePeriod`），不可調。

| 鍵 | 預設 | 說明 |
|---|---|---|
| `session.pending_login_ttl` | 30s | 登入請求等待 Central 回覆的期限 |
| `session.pending_logout_ttl` | 30s | 登出請求等待回覆的期限 |
| `session.service_disconnect_grace_period` | 30s | Gate 端對 World 斷線的寬限，期間保留玩家 |
| `session.max_login_attempts` | 5 | 嘗試窗口內同一（帳號, IP）的登入次數上限 |
| `session.login_attempt_window` | 10s | 登入嘗試計數窗口 |
| `session.login_account_lock_duration` | 30s | 超過次數後的鎖定時間 |
| `session.board_command_rate` | 10（每秒） | 每位玩家盤面指令 token bucket 速率；超過丟棄並計 `game_chat_rate_limited_total{kind="board"}` |
| `session.board_command_burst` | 20 | 盤面指令 token bucket 容量 |
| `session.max_connections_per_ip` | 100 | 單一來源 IP 的同時連線上限；CGNAT 下多位玩家共用 IP，調低前先評估 |

`session.board_command_rate`／`board_command_burst`／`max_connections_per_ip` 都嚴格解析，寫錯 Gate 拒絕啟動；上表所有時長鍵與 `session.max_login_attempts` 為負數也一律拒絕啟動（`must not be negative`）。Gate 啟動時一律記一行 Info `gate max_connections`（生效的總連線上限）；總連線上限的正式鍵是根層 `max_connections`，`tcp.max_connections` 是已棄用別名（有設定時仍優先並記 Warn `tcp.max_connections is deprecated`）。

## Central `new_user.*` 選填鍵

首次登入自動建帳的防濫用設定，都不在範本內，預設 0＝不限制（與既有行為相同），嚴格解析，寫錯 Central 拒絕啟動。

| 鍵 | 預設 | 說明 |
|---|---|---|
| `new_user.rate` | 0 | 全服自動建帳的整體速率（每秒）；超過時該次登入回 `AuthServiceUnavailable`（可重試） |
| `new_user.burst` | 0 | 自動建帳 token bucket 容量 |
| `new_user.min_password_bytes` | 0 | 新帳號最短密碼位元組數，過短回 `AuthWrongPassword`；**須先與 PJA-Client 的註冊提示同步後才開** |
