# 設定注入與熱更新

服務啟動時由 `startup.InitializeRuntime` 建立該服務專用的 `*viper.Viper`。

## 規則

- `viper.Viper` 只能在 composition root 建立與讀取。
- 基礎套件與服務內部透過參數接收設定，不讀取 Viper singleton。
- Redis、MySQL、TCP 與 tracing 設定由 `run.go` 建構後傳入。
- `configwatch.Start` 必須接收非 nil 的設定實例。
- 熱重載讀出新的設定實例，只交給明確註冊的回呼（`applyDynamicConfig`、服務自己的 `onReload`）；啟動實例永遠不會被改寫，所以沒有註冊的鍵改了不會生效。

## 新增服務

1. 呼叫 `startup.InitializeRuntime`。
2. 從回傳的 `Phase1Result.Config` 建立 typed config 或基礎設施設定。
3. 將設定傳給 service constructor / `Run`。
4. 不在 `pkg` 或 `cmd/*/internal` 重新呼叫 `viper.Get*`。

這個邊界讓測試可以建立獨立的 Viper 實例，也避免不同啟動流程共用可變設定。

## 環境變數覆寫

- 以 `Get*` 逐鍵讀取的設定鍵都可用環境變數覆寫：鍵名轉大寫、`.` 換成 `_`，例如 `redis.password` 對應 `REDIS_PASSWORD`、`s2s_auth.world.server_name` 對應 `S2S_AUTH_WORLD_SERVER_NAME`。
- 沒有服務前綴（`AutomaticEnv` 未設 `SetEnvPrefix`）：Docker compose 正是靠這個規則注入 MySQL、Redis、RabbitMQ 帳密與 Lobby token。代價是主機上任何同名的環境變數都會被服務讀進去，同一台主機直接跑多個服務時，彼此的環境變數不可混用。
- **與設定區段同名的環境變數會讓啟動失敗**：viper 對巢狀鍵（如 `debug.addr`）會先檢查每一層父鍵有沒有同名且非空的環境變數，有的話整個子樹回零值、`IsSet` 回 false，設定被靜默忽略（`DEBUG` 讓 `debug.addr` 失效、`MISSION_RESET` 讓全服換日時間退回 UTC 00:00、`GO` 讓 Go 記憶體上限消失、`REDIS` 讓 Central 在沒有 Redis 下啟動）。`pkg/bootstrap` 載入設定後檢查這類衝突，發現就拒絕啟動，錯誤訊息列出變數名與被遮蔽的區段；請移除或改名該環境變數。常見會撞名的區段有 `DEBUG`、`REDIS`、`MYSQL`、`GO`、`SESSION`、`TCP`、`OTEL`、`COMBAT`、`FEATURE`、`RABBITMQ`、`MISSION_RESET`、`GAME_STORE`、`DATA_CONFIG`，以及 `S2S_AUTH_<服務>` 這類中間層。葉鍵同名（`MYSQL_HOST`）是正常覆寫，空值也不受影響。
- 例外：`<id>.listen.*`、`<id>.dial.*` 以 `GetStringMap` 整段讀取，不套用環境變數；`protocol-record` 的鍵名含 `-`，無法用環境變數設定（用 `DEBUG_PROTOCOL_RECORD`）。
- 只有 `--protocol-record` 繫結到 viper，優先於設定檔。`--log-format`、`--log-level` 在讀設定檔前就交給 logger，不進 viper；未給旗標時預設取環境變數 `LOG_FORMAT`、`LOG_LEVEL`（再預設 `json`、`info`），層級只接受 `trace`、`debug`、`info`、`warn`、`error`，寫錯以結束碼 2 拒絕啟動。
- 設定檔路徑：`-config` 優先；未給時取環境變數 `APP_CONFIG`（容器用），再退回各服務的預設 dev 路徑。啟動成功會記一筆 `config loaded`（含實際路徑）。

## 嚴格解析

viper 的 `GetDuration`、`GetInt`、`GetBool` 遇到寫錯的值不報錯：沒有單位的數字被當成奈秒（`history_retention: 30` 變成 30ns，會刪光聊天紀錄）、無法解析的值變成零值。會改變業務結果的鍵改用 `bootstrap.Duration`、`bootstrap.Int`、`bootstrap.Bool`，已設定但不合法時讓啟動失敗：

- 時長只接受帶單位的字串（`30s`、`720h`）與 `0`：Chat `history_retention`、Gate `session.*` 時長、`redis.conn_max_lifetime`／`conn_max_idle_time`。可熱重載的 `protocol_record_ttl`、`protocol_record_file_retention` 寫錯只記 Warn 並用預設。
- 整數：`mission_reset.hour`／`minute`、`session.max_login_attempts`、`go.memory_limit_mb`（寫成 `512MB` 不再變 0 而悄悄不設 GOMEMLIMIT）、`redis.db`（寫錯不再悄悄改寫 db 0）。
- 浮點數：`otel.sample_rate`（`bootstrap.Float`；寫成 `5%` 不再變 0 而開啟全量匯出）。
- 布林只接受 `true`／`false`：`feature.central.state_auditor`（YAML 1.2 的 `on`、`yes` 是字串，會被拒絕）。

範本裡的鍵另有反向檢查（`tools/internal/configaudit` 的 `TestEveryConfigTemplateKeyIsReadByCode`）：範本鍵名打錯會讓測試失敗。

## 熱更新

- 所有走 `startup.InitializeRuntime` 的服務都會監看設定檔（含 Chat、Record）。可熱更的鍵只有白名單內的：
  - `protocol_record*`（含 `protocol_record_ttl`、`protocol_record_file_retention`）：所有服務。
  - `traffic_slice_*`：Central（`SetTrafficSlice`）。
  - `admin_token`、`ops_token`、`gm_token`：只有 Lobby 真的重載（先驗證才套用）；其他服務讀了也不會用。
  - 其餘鍵（`session.*`、`tcp.*`、`redis.*`、`max_players`、`mission_reset.*`、`debug.*`、`history_retention`、`s2s_auth.*`、`<id>.dial.*` 等）只在啟動時讀一次，改了要重啟。
- 重載時與上一份快照比對：實際套用的鍵記 `config hot reload applied`（`keys` 欄位列出鍵名）；改了不能熱更的鍵記 Warn `config change requires restart, not applied`（`keys` 列鍵名，不含值）。維運看到 restart 警告就要重啟該服務；只看到 applied 才代表生效。`configwatch` 監看單一設定檔所在目錄；同一檔案連續的寫入、改名事件在最後一個事件後 100ms 才重載一次，重讀失敗時沿用舊設定並記 Warn。
- fsnotify 回報的錯誤（例如事件佇列溢位）記 Warn：熱重載可能漏掉變更，需確認設定是否已套用。
- 正式 compose 以目錄掛載 `docker/prod/config:/config:ro`。單檔 bind mount 在宿主機以暫存檔改名（vim、`sed -i`、部署工具）更新時會停在舊 inode，熱重載收不到；改完設定一律確認有 `config hot reload applied` 日誌且 `keys` 含你改的鍵；看到 `config change requires restart` 或兩者都沒有就重啟。
- `feature.central.state_auditor` 只在啟動讀一次，改了要重啟 Central。
- 可熱更的 `protocol_record_ttl`、`protocol_record_file_retention` 寫錯只記 Warn 並用預設（與嚴格解析的啟動鍵不同）；`traffic_slice_*` 壞值保留上一版有效的切片。

## Gate `session.*` 選填鍵

都不在範本內，以預設值運作；時長必須帶單位，寫錯讓 Gate 啟動失敗。只影響 Gate 本身：Central 對 Gate 斷線的寬限固定 30 秒（`appcore.ServiceDisconnectGracePeriod`），不可調。

| 鍵 | 預設 | 說明 |
|---|---|---|
| `session.pending_login_ttl` | 30s | 登入請求等待 Central 回覆的期限 |
| `session.pending_logout_ttl` | 30s | 登出請求等待回覆的期限 |
| `session.service_disconnect_grace_period` | 30s | Gate 端對 World 斷線的寬限，期間保留玩家 |
| `session.max_login_attempts` | 5 | 嘗試窗口內同一（帳號, IP）的登入次數上限 |
| `session.login_attempt_window` | 10s | 登入嘗試計數窗口 |
| `session.login_account_lock_duration` | 30s | 超過次數後的鎖定時間 |
| `session.board_command_rate` | 10（每秒） | 每位玩家盤面指令 token bucket 速率；超過丟棄並計 `game_chat_rate_limited_total{kind="board"}` |
| `session.board_command_burst` | 20 | 盤面指令 token bucket 容量 |
