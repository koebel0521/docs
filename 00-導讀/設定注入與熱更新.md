# 設定注入與熱更新

服務啟動時由 `startup.InitializeRuntime` 建立該服務專用的 `*viper.Viper`。

## 規則

- `viper.Viper` 只能在 composition root 建立與讀取。
- 基礎套件與服務內部透過參數接收設定，不讀取 Viper singleton。
- Redis、MySQL、TCP 與 tracing 設定由 `run.go` 建構後傳入。
- `configwatch.Start(path, load, onReload)` 必須接收非 nil 的 loader（`load == nil` 回傳錯誤）。
- 熱重載讀出新的設定實例，只交給明確註冊的回呼（`applyDynamicConfig`、服務自己的 `onReload`）；啟動實例永遠不會被改寫，所以沒有註冊的鍵改了不會生效。

## 新增服務

1. 呼叫 `startup.InitializeRuntime`（選項型別 `startup.RuntimeOption`），成功後立刻 `defer rt.Close()`。
2. 從回傳的 `*startup.Runtime` 的 `Config` 建立 typed config 或基礎設施設定（觀測設定為 `startup.ObservabilityConfig`）。
3. 將設定傳給 service constructor / `Run`：Gate、Central 的組合根在 `cmd/<svc>/services_config.go` 解析成 `services.Config`，`internal/services` 不再接收 `*viper.Viper`。
4. 不在 `pkg` 或 `cmd/*/internal` 重新呼叫 `viper.Get*`。允許 import viper 的只有 `cmd/<服務>/` 頂層（組合根）與 `pkg` 內的 `bootstrap`、`startup/**`（含 `dbstartup`、`redisstartup`、`mqstartup`）、`configwatch`；`pkg/s2sauth`（`Configure*For`）與 `pkg/tcpconfig/viperbuild`（`BuildConfig`）是只給組合根呼叫的轉換函式，列為明確例外；`BuildConfig` 已從 `pkg/tcpconfig` 拆到 `viperbuild` 子套件，所以 `pkg/tcpconfig` 與 TCP 函式庫（`tcpsocket`、`tcpserver`、`tcpclient`、`centralclock`、`debug`、`tcpdiag`）都不再依賴 viper，不是例外。純函式不要為了用到它而 import `bootstrap`，放進不依賴 viper 的小套件（例如 `pkg/secretcheck`、`pkg/switchparse`）。遞移依賴的守門是 `internal/archtest` 的 `TestPkgLibsDoNotTransitivelyDependOnViper`（除 `viperDependentPkgs` 外，沒有任何 `pkg` 套件的非測試依賴含 viper）。Lobby 另有一個明確例外：`cmd/lobby/internal/services/token_reload.go` 被視為組合根的延伸，可 import viper 讀取熱重載後的設定（`handler/servers.go` 的 `BuildServers` 只收組合根解析好的位址字串，已不在例外內）（白名單在 `internal/archtest/viper_boundary_test.go` 的 `viperAllowed`）。`internal/archtest` 的 `TestViperOnlyImportedByCompositionRoot` 以 import 掃描守住這份清單，`cmd/*/internal/**`、`internal/**` 與其餘 `pkg` 一旦 import viper 測試就失敗。

這個邊界讓測試可以建立獨立的 Viper 實例，也避免不同啟動流程共用可變設定。

## 環境變數覆寫

- 以 `Get*` 逐鍵讀取的設定鍵都可用環境變數覆寫：鍵名轉大寫、`.` 換成 `_`，例如 `redis.password` 對應 `REDIS_PASSWORD`；多層鍵照同一規則串接，例如 `s2s_auth.central.server_name` 的環境變數是 `S2S_AUTH_` 加上其餘層級的大寫名稱。
- 沒有服務前綴（`AutomaticEnv` 未設 `SetEnvPrefix`）：Docker compose 正是靠這個規則注入 MySQL、Redis、RabbitMQ 帳密與 Lobby token。代價是主機上任何同名的環境變數都會被服務讀進去，同一台主機直接跑多個服務時，彼此的環境變數不可混用。審查 N29 的決定：維持現狀、不加 `PJA_` 前綴（`SetEnvPrefix("PJA")` 要同時改 compose、腳本、文件與 configaudit，並需相容期同讀舊名）；`ID`、`DEBUG`、`ADDR` 這類短名易被主機環境誤設，由「與設定區段同名的環境變數會讓啟動失敗」的檢查擋下，代價由運維在主機層避免同名變數。
- **與設定區段同名的環境變數會讓啟動失敗**：viper 對巢狀鍵（如 `debug.addr`）會先檢查每一層父鍵有沒有同名且非空的環境變數，有的話整個子樹回零值、`IsSet` 回 false，設定被靜默忽略（`DEBUG` 讓 `debug.addr` 失效、`DAY_RESET` 讓全服換日時間退回 UTC 00:00、`GO` 讓 Go 記憶體上限消失、`REDIS` 讓 Central 的 Redis 設定消失而走單機記憶體模式；Central 有設定 Redis 卻連不上時則直接拒絕啟動）。`pkg/bootstrap` 載入設定後檢查這類衝突，發現就拒絕啟動，錯誤訊息列出變數名與被遮蔽的區段；請移除或改名該環境變數。常見會撞名的區段有 `DEBUG`、`REDIS`、`MYSQL`、`GO`、`SESSION`、`TCP`、`OTEL`、`COMBAT`、`FEATURE`、`RABBITMQ`、`DAY_RESET`（舊區塊名 `MISSION_RESET` 同理）、`game_store`、`data_config`（區段名的大寫形式），以及 `S2S_AUTH_<服務>` 這類中間層。葉鍵同名（`MYSQL_HOST`）是正常覆寫，空值也不受影響。
- 清單型設定（`s2s_auth.*.allowed_cidrs`、`redis.sentinel_addrs`、`combat.loadout_config_keys`）用環境變數覆寫時以逗號分隔多個值。清單鍵只接受字串或字串清單（`bootstrap.StringList` 回 `([]string, error)`）：寫成 map、list-of-map、清單含非字串，或有元素卻全是空項（例如 `[""]`）都會讓啟動失敗，不會靜默當成空清單；只有未設定或刻意寫 `[]` 才是空清單。`allowed_cidrs` 的空清單代表不限制來源，所以這個行為是為了避免寫錯後 S2S 來源 IP 白名單被靜默關掉（第二十一輪 V-L2）。驗證啟用而 `allowed_cidrs` 為空時，每個監聽區段啟動各記一次 Warn `S2S allowed_cidrs is empty: source IP is not restricted, only token authenticates peers`（欄位 `listener`）。
- 例外：`<id>.listen.*`、`<id>.dial.*` 以 `GetStringMap` 整段讀取，不套用環境變數；`--protocol-record` 是純旗標，不經 viper：設定檔的 `protocol-record` 鍵已無作用，也不在熱重載鍵內；協定記錄的優先序為 旗標 `--protocol-record` > 環境變數 `DEBUG_PROTOCOL_RECORD` > 設定檔 `protocol_record_enabled`。
- `--log-format`、`--log-level` 在讀設定檔前就交給 logger，不進 viper；未給旗標時預設取環境變數 `LOG_FORMAT`、`LOG_LEVEL`（再預設 `json`、`info`），層級只接受 `trace`、`debug`、`info`、`warn`、`error`，寫錯以結束碼 2 拒絕啟動，錯誤訊息標明來源（如 `from env LOG_LEVEL`）；`--protocol-record` 寫錯也是用法錯誤（結束碼 2），`-version` 在旗標與環境變數檢查之前處理。
- 設定檔路徑：`-config` 優先；未給時取環境變數 `APP_CONFIG`（容器用），再退回各服務的預設 dev 路徑。啟動成功會記一筆 `config loaded`（含實際路徑）。

## 嚴格解析

viper 的 `GetDuration`、`GetInt`、`GetBool` 遇到寫錯的值不報錯：沒有單位的數字被當成奈秒（`history_retention: 30` 變成 30ns，會刪光聊天紀錄）、無法解析的值變成零值。會改變業務結果的鍵改用 `bootstrap.Duration`、`bootstrap.Int`、`bootstrap.Bool`，已設定但不合法時讓啟動失敗：

- 時長只接受帶單位的字串（`30s`、`720h`）與 `0`：Chat `history_retention`、Gate `session.*` 時長、`redis.conn_max_lifetime`／`conn_max_idle_time`。可熱重載的 `protocol_record_ttl`、`protocol_record_file_retention` 啟動時寫錯只記 Warn 並用預設（診斷設定不擋啟動）；熱重載時寫錯則整份拒絕、沿用舊設定（第十一輪；原本靜默重設成預設值卻記 applied）。`redis.conn_max_lifetime`／`conn_max_idle_time` 次秒值（`500ms`、`1.5s`）原樣傳給 rueidis（第十一輪前會截成 0 或 1 秒，0 又被當成「使用預設」）。World `combat.bunker_health` 走嚴格浮點解析，寫錯（例如 `100hp`）拒絕啟動，熱重載同樣拒絕。設定檔必須寫有 `id`（第十一輪起啟動也檢查，與熱重載一致；只靠環境變數 `ID` 會拒絕啟動，`ID` 仍可覆寫檔案中的值）。
- 整數：各服務 `id`（必須是正整數；驗證後以十進位寫回 viper，`1001.5`、環境變數 `01001` 不再被截斷或當成八進位；設定檔內的前導零見下方「設定檔前導零整數」）、World `max_players`（未設定或 `0` 用預設值，**負值是設定錯誤，World 拒絕啟動**，錯誤 `max_players: config max_players=-1: must not be negative`（以 `-1` 為例）；`6k`、`6,000` 等壞值也拒絕啟動，不再退回預設）、Gate `session.board_command_burst`、`session.max_connections_per_ip`、Central `new_user.burst`、`new_user.min_password_bytes`、`day_reset.hour`／`minute`、`session.max_login_attempts`、`go.memory_limit_mb`（寫成 `512MB` 不再變 0 而悄悄不設 GOMEMLIMIT）、`redis.db`（寫錯不再悄悄改寫 db 0）。
- **設定檔前導零整數**（第十二輪 V-L3）：yaml v3 以 base 0 解析純量，`id: 01001` 會變 513、`minute: 010` 變 8、`hour: 09` 變浮點數，同值寫在環境變數卻以十進位解析。`ReadConfigPair` 讀檔後掃描未加引號的整數／浮點純量，**八進位與十進位結果不同或不是合法八進位就拒絕**，錯誤標出鍵路徑但不再印原值（`config <鍵>: leading zero makes YAML read it as octal, remove the leading zeros or quote the value`）。`00`、`07` 這類結果相同的寫法與加引號字串照常放行；`0x10`、`0o17`、`0.5` 不在檢查範圍。啟動遇到即拒絕啟動，熱重載遇到即整份拒絕、沿用舊設定。
- **設定檔鍵與 secret**（第二十八輪 V-L1～V-L3）：同層只差大小寫的鍵（如 `mysql` 與 `MySQL`）會被拒絕；含底線的前導零整數（`0_1001`）與顯式標籤的前導零整數（`!!int 01001`）同樣被拒絕；鍵名含 `.` 一律拒絕（viper 以 `.` 切路徑，`go.memory_limit_mb: 512` 平鋪鍵與巢狀 `go: {memory_limit_mb: 512}` 指向同一條路徑，後者會被靜默吃掉，所以本文件與範本中的 `go.memory_limit_mb` 都是巢狀區段 `go:` 底下的 `memory_limit_mb` 的路徑記法，設定檔必須寫成巢狀），YAML merge key（`<<: *b`）展開後與明確寫的鍵只差大小寫也算撞名而拒絕；secret／token／password 類鍵必須是 YAML 字串，`0x1F`、`1e5`、過長數字未加引號會被拒絕，請加引號。
- 浮點數：`otel.sample_rate`（由 `normalizeTuningKeys` 嚴格解析：寫成 `5%` 啟動與熱重載都失敗，不再變 0 而開啟全量匯出）、Gate `session.board_command_rate`、Central `new_user.rate`。
- 布林：`feature.central.state_auditor` 等開關鍵。設定檔只接受 YAML 的 `true`／`false`（YAML 1.2 的 `on`、`yes` 是字串，YAML 的 `1` 是整數，都會被拒絕）；環境變數走 `strconv.ParseBool`，另接受 `1`、`t`、`T`、`TRUE` 等寫法（第十五輪 V-L6）。
- **調校數值鍵與開關鍵**（舊鍵 `tcp.max_connections` 已移除，不在清單內；`normalizeTuningKeys`（未匯出），由啟動與熱重載共用的 `bootstrap.ValidateLoaded` 呼叫：驗證並把十進位結果以 `v.Set` 寫回 viper 的 override 層，之後各套件的寬鬆 `GetInt`／`GetBool` 讀到同一個值；未設定的鍵不受影響。因為會寫 override 層，只能用在一次性的 viper 實例。時長鍵錯誤訊息只帶一次 `config <鍵名>` 前綴）：整數鍵（`protocol_record_limit` 另有上限 131072，超過啟動失敗、熱重載整份拒絕）`max_connections`、`tcp.rate_limit_burst`、`tcp.socket_send_queue_depth`、`mysql.port`、`mysql.max_open_conns`、`mysql.max_idle_conns`、`redis.pool_size`、`redis.min_idle_conns`、`rabbitmq.prefetch_count`、`rabbitmq.buffer_size`、`protocol_record_limit`；浮點鍵 `tcp.rate_limit_per_second`（非負調校鍵：`tcp.rate_limit_per_second`、`tcp.rate_limit_burst`、`tcp.socket_send_queue_depth`、`max_connections`、`mysql.max_open_conns`、`mysql.max_idle_conns`、`redis.pool_size`、`redis.min_idle_conns`、`rabbitmq.prefetch_count`、`rabbitmq.buffer_size`、`protocol_record_limit` 為負值時啟動與熱重載都拒絕（`protocol_record_limit` 以前是靜默換成預設值，第二十輪 V-L2 補），0 維持沿用預設；第十五輪 DP-L1、第十六輪補連線池與連線上限鍵，清單見 `bootstrap.tuningNonNegativeKeys`）；布林鍵 `debug.pprof_enabled`、`protocol_record_payload_enabled`、`protocol_record_enabled`、`data_config.allow_legacy_directory`、`allow_dev_tokens`（Lobby、Record；`yes`／`on` 不再被靜默解成 false，第十五輪 V-L1）；時長鍵 `mysql.audit_record_slow`（見下）。浮點鍵另含 `otel.sample_rate`、`combat.bunker_health`，`NaN`／`Inf`（例如 `.nan`）一律拒絕，前後空白經嚴格解析後寫回。寫錯讓啟動失敗：舊行為是 `1k` 靜默變 0 而退回預設、`020` 被當八進位變 16、`yes` 變 false。
- **`mysql.audit_record_slow`**（原 `mysql.audit_record_slow_ms`，已改名）：Central 稽核紀錄查詢的慢查詢門檻，時長必須帶單位（`500ms`）；該鍵不在任何設定範本，只影響日誌 `central audit query slow` 的觸發。舊名 `audit_record_slow_ms` 不再被讀取。
- **環境變數 `AUTO_MIGRATE_DISABLED`**：不屬 viper 鍵，由不依賴 viper 的 `pkg/switchparse` 的 `Parse` 解析（bootstrap.ParseSwitch 與 IsPlaceholderSecret 轉接層已刪除，呼叫端直接用 `switchparse.Parse`、`secretcheck.IsPlaceholder`），接受 `true`／`false`／`1`／`0`／`t`／`f`（`strconv.ParseBool` 的寫法）與 `on`／`off`／`yes`／`no`，不分大小寫、略過前後空白。舊版只認小寫 `true`，`TRUE`、`1`、`yes` 反而在正式庫開啟 AutoMigrate。寫錯（例如 `ture`）讓 `InitRuntimeWithFile` 啟動失敗；空字串視為未設定（啟用 AutoMigrate）。
- **World `lottery.secret`**：非空之外，World 啟動拒絕 `change-me`／`change_me` 開頭的範本佔位與短於 16 字元的值（`validateLotterySecret`；開發與整合測試設定的 secret 是 25～26 字元，所以門檻訂 16 而非 32）。

**純設定先於外部資源驗證（第十輪）**：設定寫錯的容器不必先連 MySQL／Redis、跑 AutoMigrate 或重放才被拒絕。錯誤訊息不變，只是更早失敗：

- World：`worldSettings` 先於 `openWorldStores`，涵蓋 `day_reset.*`（`gameDayFromViper` 以整個區塊為單位解析：舊區塊 `mission_reset.*` 的相容已移除：設定檔含任何 `mission_reset.*`（不論有沒有 `day_reset`）**啟動失敗**，錯誤 `game day config: gameday: mission_reset is no longer supported, rename the block to day_reset`，不再沿用並記 Warn，也不逐鍵混讀）、`game_store.spill_dir` 與 `lottery.secret`；儲存層建好後才由 `attachWorldStores` 接上儲存選項。
- Central：`validateSettings` 先於連線與 AutoMigrate，涵蓋 `feature.central.state_auditor`、`new_user.*`、`traffic_slice_*`、`mysql.audit_record_slow` 與 `redis.*`；回傳 `centralSettings`，`initStorage` 與 `servicesConfig` 共用這一份，不再各自重讀 viper。`new_user.rate`、`new_user.burst`、`new_user.min_password_bytes` 為負值拒絕啟動。
- Chat：`history_retention` 先於 MySQL 連線與 AutoMigrate。
- Gate：`session.*`、`drain_timeout` 與 S2S 用戶端設定（`gateConfigFromViper`、`servicesConfig`）先於 Redis 連線。

World 的 `services.Options` 新增 `DataDirectory`（遊戲設定 artifact root）：空值沿用相對工作目錄的 `config/data`，只供測試傳假 artifact 目錄跑完整 `Start`，不是設定鍵。

範本裡的鍵另有反向檢查（`tools/internal/configaudit` 的 `TestEveryConfigTemplateKeyIsReadByCode`）：範本鍵名打錯會讓測試失敗。這個守門除了 `Get*` 呼叫，也掃 `bootstrap` 嚴格讀取器、Gate `session.*` 表格與組合根的 `xxxKey` 常數；`optionalConfigKeys`（不在範本的選填鍵）每一項都必須被掃到，否則測試失敗。Record 範本已移除不會被讀到的 `protocol_record_*`、User 範本已移除 `tcp.rate_limit_*`。

## 熱更新

- 所有走 `startup.InitializeRuntime` 的服務都會監看設定檔（含 Chat、Record）。可熱更的鍵只有白名單內的：
  - 可熱更鍵由各服務經 `startup.WithHotReload(HotReload{Keys, Apply})` 宣告，`Keys` 是該服務可熱套用的**完整設定鍵**（鍵本身或其巢狀子鍵才算，不做字串前綴比對），`Apply` 回傳套用結果；共用的協定紀錄鍵不必各服務重複宣告。不在清單內的鍵（含拼錯的，例如 `traffic_slice_precent`、`gm_tokens`）一律歸「需重啟」並記 Warn `config change requires restart, not applied`，不會因為前綴相同被記成 applied（第十五輪 V-M3）。
  - `protocol_record_enabled`、`protocol_record_payload_enabled`、`protocol_record_limit`、`protocol_record_ttl`、`protocol_record_file_dir`、`protocol_record_file_retention`：所有服務；協定檔案記錄的參數沒變時沿用同一個記錄器，不會每次熱重載關檔重開。
  - `traffic_slice_percent`、`traffic_slice_world_id`：Central（`SetTrafficSlice`，由 `services.TrafficSliceKeys()` 宣告）。Central 在 `initStorage` 期間收到的重載，由 `cmd/central/internal/services` 的 `TrafficSliceReloader` 先以 `ParseTrafficSlice` 驗證再暫存，在 App 建好後套用，不再被啟動時的舊值蓋掉；這段期間的不合法值直接回錯（記 `not applied`、計 `rejected`），不覆寫已暫存的上一份合法重載，`Attach` 因此只會套用啟動設定或合法重載，套用失敗一律拒絕啟動（第十二輪 V-L1；以前先記 applied、App 建好後套用失敗只記 Warn，canary 被關）。**啟動時 `traffic_slice_*` 不合法 Central 拒絕啟動**（啟動沒有舊切片可保留，否則 canary 看似已開卻全量走舊 World）；啟動後熱重載收到不合法值才只記 Warn、保留上一版有效切片。
  - `admin_token`、`ops_token`、`gm_token`：只有 Lobby 真的重載（先驗證才套用）；其他服務讀了也不會用。驗證規則：`change-me`／`change_me` 開頭的佔位值拒絕、非空須至少 32 字元、**三個非空 token 不可跨層級重複**（admin／ops／gm 任兩個相同，`Match` 會先命中高層級，稽核身分與權限會混淆；啟動與熱重載都拒絕）。啟動與熱重載共用 `services.NewTokenValidator`（`Validate`＋三層 token 各跑 `httpx.RejectDevStackToken`），組合根以啟動時實際的 admin 位址與 `allow_dev_tokens` 建立一次：admin 綁非 loopback 時，`-local-stack-only` 結尾的公開開發 token 熱重載同樣被拒；`allow_dev_tokens` 取啟動值，熱重載改它不生效（第十二輪；以前熱重載只跑 `Validate`，可繞過啟動時的拒絕）。
  - **被同名環境變數遮蔽的鍵不會生效**：`AutomaticEnv` 下非空的同名環境變數（鍵轉大寫、`.` 轉 `_`，例如 `ADMIN_TOKEN`）優先於設定檔；`protocol_record_enabled`、`protocol_record_payload_enabled` 另受 `DEBUG_PROTOCOL_RECORD` 覆寫。這些鍵改了設定檔不會被記成 applied，改記 Warn `config change shadowed by environment variable or command-line flag, not applied`（`config`、`keys`；第十一輪前訊息沒有 `or command-line flag`）。協定紀錄開關依實際優先序判斷：`protocol_record_payload_enabled` 只有在 `DEBUG_PROTOCOL_RECORD` 解析為 false 時才算被遮蔽；`protocol_record_enabled` 有可解析的 `-protocol-record` 旗標時以旗標為準，沒有旗標時環境變數能解析才算遮蔽，寫錯的旗標或環境變數退回設定檔、不算遮蔽。熱重載的差異比對看**設定檔本身**（`bootstrap.ReadConfigPair` 讀檔一次，同一份內容分別建出套用環境變數的實例與只含設定檔的實例；第十一輪取代 ReadFileConfig，差異快照與套用設定不再各讀一次檔），不是含 `AutomaticEnv` 的實例：後者的 `Get` 在同名環境變數非空時一律回環境變數值，會把設定檔裡「修改」遮蔽鍵的差異整個吞掉而完全沒有日誌（token 輪替改設定檔時就是如此）。需重啟清單（`config change requires restart`）裡被遮蔽的鍵也併入同一則 shadowed Warn，不再當成「重啟後生效」。正式環境 Lobby token 由環境變數提供，所以輪替 token 要改環境變數並重啟，不能靠改設定檔熱更。
  - **熱重載與啟動走同一套讀檔與驗證**（第十二輪 R-M1）：都以 `bootstrap.ReadConfigPair` 讀檔（含前導零檢查與環境變數遮蔽檢查）、`bootstrap.ValidateLoaded` 驗證（設定檔必有 `id`、`id` 嚴格解析並寫回、調校鍵嚴格解析）；鍵轉環境變數名的規則統一由 `bootstrap.EnvName` 提供。調校數值鍵（見上，含 `otel.sample_rate`）有不合法值（例如 `protocol_record_limit: 1k`）或 `id` 不合法（例如 `1001.5`，第十二輪起熱重載也拒絕）時，整份新設定被拒絕（`invalid reload config`）、沿用舊設定，不會靜默改值後記 applied。
  - 只能監看單一路徑（watcher 只盯 `paths[0]`）：傳入多個設定路徑時熱重載整個關閉並記 Warn `config hot reload disabled: only a single config path can be watched`；目前正式呼叫端只傳一個路徑。
  - 其餘鍵（`session.*`、`tcp.*`、`redis.*`、`max_players`、`day_reset.*`、`retention.*`（World 大表保留天數）、`debug.*`、`history_retention`、`s2s_auth.*`、`<id>.dial.*` 等）只在啟動時讀一次，改了要重啟。
- 重載時與上一份快照比對，日誌依**實際套用結果**分三種：Info `config hot reload applied`（`keys` 只列真的套用的鍵）；Warn `config hot reload not applied`（`keys`、`err`：服務宣告可熱更的鍵套用失敗，例如值無效、token 驗證失敗，或 Lobby 啟動時沒有 token、事後才補上而需重啟才有 admin 端點）；Warn `config change requires restart, not applied`（`keys`：改了不能熱更的鍵，不含值）；另有 Warn `config change shadowed by environment variable or command-line flag, not applied`（`keys`：鍵被同名環境變數遮蔽，見上）。維運看到 `not applied` 或 restart 警告就要修正值或重啟該服務；`applied` 不再等於「鍵名前綴符合」，只列宣告過的完整鍵且真的生效的鍵。`configwatch` 監看單一設定檔所在目錄；同一檔案連續的寫入、改名事件在最後一個事件後 100ms 才重載一次，重讀失敗時沿用舊設定並記 Warn。
- 結果計數（第十二輪 O-L6）：`game_config_reload_total{result="applied"|"rejected"|"restart_required"|"shadowed"}`，監看開始時先建為 0，每次重載每種結果最多記一筆；`HotReload.Apply` panic 由 `startup.applyHotReload` 轉成套用錯誤，同樣計 `rejected` 且 baseline 不前進（`configwatch.reload` 對其他回呼 panic 也保底計 `rejected`）；`configwatch` 重試後仍讀檔／驗證失敗（Warn `configwatch: failed to reload config`）也計 `rejected`，`Stop` 中斷重試不計。15 分鐘內有 `rejected` 觸發 `GameConfigReloadRejected`。套用結果的分類在純函式 `classifyReload`（`pkg/startup/config_diff.go`），日誌與計量由 `reportReload` 依分類輸出。
- fsnotify 回報的錯誤（例如事件佇列溢位）記 Warn：熱重載可能漏掉變更，需確認設定是否已套用。
- **熱重載拒絕沒有 `id` 的設定**：就地覆寫（`cp`、編輯器非原子寫入）時可能讀到空檔或截斷但仍可解析的 YAML，每個服務設定必有 `id`，缺 `id` 就視為讀取失敗（`readReloadConfig`，只用於熱重載），沿用 `configwatch` 的重試與沿用舊設定路徑，不會把空設定當有效值套用（例如 Central 讀到空的 `traffic_slice_percent` 而關閉 canary）。差異比對的基準是啟動時同一次讀檔得到的 fileOnly 快照，不另外讀檔，所以沒有「基準快照讀取失敗」的 Warn，也不會因基準讀檔失敗而讓第一次熱重載的差異清單失真。
- 正式 compose 以目錄掛載 `docker/prod/config:/config:ro`；完整、debug、core-test 堆疊同樣掛整個 `config/docker:/config:ro`（第十一輪；core-test 的 Gate 改以 `APP_CONFIG=/config/gate-core-test.yaml` 指定）。單檔 bind mount 在宿主機以暫存檔改名（vim、`sed -i`、部署工具）更新時會停在舊 inode，熱重載收不到；另外 Windows／macOS 的 Docker Desktop 宿主機編輯**不會**把 inotify 事件傳進容器（第二十八輪實測：宿主機追加與改名覆蓋都是 0 個事件，容器內寫入才有事件），本機 Docker 堆疊要演練熱重載請在容器內改檔，或改用 `dev-up.sh` 本機行程；改完設定一律確認有 `config hot reload applied` 日誌且 `keys` 含你改的鍵；看到 `config hot reload not applied`、`config change requires restart` 或都沒有就修正或重啟。
- `feature.central.state_auditor` 只在啟動讀一次，改了要重啟 Central。
- **`<id>.dial.*` 撥號位址只在啟動時讀取**：熱重載從不改寫啟動實例，撥號重試只會輪流嘗試啟動時的那份位址（舊版的「重讀位址」永遠讀到同一份，已移除）；改撥號位址要重啟。
- **`GOMEMLIMIT` 優先於 `go.memory_limit_mb`**：標準環境變數 `GOMEMLIMIT` 非空時，`go.memory_limit_mb` 不套用（啟動記 Info `GOMEMLIMIT set, go.memory_limit_mb ignored`），不會被設定檔覆蓋掉維運刻意設的值；`go.memory_limit_mb` 為 0 或負值時不設定。
- **`public_addr` 啟動即驗證**（World、Gate、Central 等公告對外位址的服務）：設定時必須是不含空白的 `host:port`、埠 1～65535，否則啟動失敗（`bootstrap.PublicAddr`）。寫錯的位址若被原樣公告，服務照常就緒、被分配到的玩家卻全部連線失敗，所以不放行。
- 可熱更的 `protocol_record_ttl`、`protocol_record_file_retention` 熱重載寫錯整份拒絕（啟動時才寬鬆地記 Warn 並用預設）；`traffic_slice_*` 壞值保留上一版有效的切片。

## Gate `session.*` 選填鍵

都不在範本內，以預設值運作；時長必須帶單位，寫錯讓 Gate 啟動失敗。只影響 Gate 本身：Central 對 Gate 斷線的寬限固定 30 秒（`appcore.ServiceDisconnectGracePeriod`），不可調。

| 鍵 | 預設 | 說明 |
|---|---|---|
| `session.pending_login_ttl` | 30s | 登入請求等待 Central 回覆的期限 |
| `session.pending_logout_ttl` | 30s | 登出請求等待回覆的期限 |
| `session.service_disconnect_grace_period` | 30s | Gate 端對 World 斷線的寬限，期間保留玩家；三種讀法：Gate 讀自己的 `gate.yaml`，作為對 World 斷線的寬限；Central 讀 `central.yaml` 的同一個鍵，同時作為對 Gate 與對 World 斷線的寬限（程式欄位 `DisconnectGrace`；預設 30 秒，掃描間隔由寬限推導，兩者共用同一值，已決定維持共用、不拆鍵）；World 對 Gate 斷線的寬限固定 30 秒、不讀此鍵 |
| `session.max_login_attempts` | 5 | 嘗試窗口內同一（帳號, IP）的登入次數上限 |
| `session.login_attempt_window` | 10s | 登入嘗試計數窗口 |
| `session.login_lock_duration` | 30s | 超過次數後的鎖定時間；同時套用到（帳號, IP）與「整個來源 IP」兩個登入限流器（IPv6 以 /64 計；來源 IP 在窗口內的登入請求上限固定 30 次，超過就鎖整個 IP）。舊鍵 `session.login_account_lock_duration` 仍接受（別名，以 `IsSet` 判斷）：舊鍵有設定一律記 Warn；新鍵有設定（含明確寫 0）時舊鍵被忽略（Warn `config key is deprecated and ignored because the new key is set`），新鍵未設定時沿用舊鍵（Warn `config key is deprecated, use the new key`） |
| `session.max_logged_in_per_ip` | 20 | 同一來源同時「已登入或登入進行中」的連線數上限（檢查排在登入限流之後；擋少數來源用自動建帳的帳號把連線槽位佔成「已登入」，已登入連線不受未登入淘汰）；超過時新的登入請求回 `AuthRateLimited`，計 `tcp_rejected_connections_total{reason="logged_in_per_ip"}`。CGNAT、網咖共用 IP 時調高，必須是整數 |
| `session.board_command_rate` | 10（每秒） | 每位玩家盤面指令 token bucket 速率；超過丟棄並計 `game_chat_rate_limited_total{kind="board"}` |
| `session.board_command_burst` | 20 | 盤面指令 token bucket 容量 |
| `session.max_connections_per_ip` | 100 | 單一來源 IP 的同時連線上限；CGNAT 下多位玩家共用 IP，調低前先評估 |
| `session.chat_room_members_per_ip` | 50 | 同一來源 IP（IPv6 以 /64 計）在同一 Chat 房間經此 Gate 的成員上限（第十二輪 SC-L2）；名額滿時 Gate 不轉送加入、計 `game_chat_rate_limited_total{kind="join"}`，Client 收不到失敗回覆（協定無加入結果）。每台 Gate 各自計數；未設定或非正值用預設 |

`session.board_command_rate`／`board_command_burst`／`max_connections_per_ip`／`chat_room_members_per_ip` 都嚴格解析，寫錯 Gate 拒絕啟動；`session.max_logged_in_per_ip` 與這四個鍵為負值同樣拒絕（`must not be negative`；0 或未設定沿用預設，不是「不限」，第十五輪 DP-L1）；上表所有時長鍵與 `session.max_login_attempts` 為負數也一律拒絕啟動（`must not be negative`，錯誤訊息帶實際讀到的鍵名，舊鍵別名也一樣）；`session.max_logged_in_per_ip` 寫成非整數同樣讓 Gate 啟動失敗，0 或未設定維持 20。Gate 啟動時一律記一行 Info `gate max_connections`（生效的總連線上限）；總連線上限的鍵是根層 `max_connections`；原棄用別名 `tcp.max_connections` 已刪除，設定檔還留著它不再生效。

## Central `new_user.*` 選填鍵

首次登入自動建帳的防濫用設定，嚴格解析，寫錯 Central 拒絕啟動。程式預設（鍵未設定時）皆為 0＝不限制；範本不同：正式範本 `docker/prod/config/central.yaml` 設 `new_user.rate: 10`、`new_user.burst: 100`，開發範本（`config/dev`、`config/docker`）為 0（不限速），`new_user.min_password_bytes` 所有範本都沒有（預設 0）。

| 鍵 | 預設 | 說明 |
|---|---|---|
| `new_user.rate` | 0（正式範本 10） | 全服自動建帳的整體速率（每秒）；超過時該次登入回 `AuthServiceUnavailable`（可重試） |
| `new_user.burst` | 0（rate>0 時視為 1；正式範本 100） | 自動建帳 token bucket 容量 |
| `new_user.min_password_bytes` | 0 | 新帳號最短密碼位元組數，過短回 `AuthWrongPassword`；**須先與 PJA-Client 的註冊提示同步後才開** |

## 連線設定鍵（`redis.*`、`rabbitmq.*`）

由 `pkg/startup/redisstartup`、`pkg/startup/mqstartup` 讀取；未設定的 `rabbitmq.*` 鍵由 `recordmq.Config.Normalize` 補預設值。

| 鍵 | 說明 |
| --- | --- |
| `redis.addr` | 單機位址；`redis.master_name` 非空時不使用 |
| `redis.password`、`redis.db` | 密碼與資料庫編號；`redis.db` 寫錯會啟動失敗（不會悄悄改用 0） |
| `redis.username` | ACL 使用者；缺省為空（default 使用者）。Sentinel 模式下同時作為連 Sentinel 的使用者 |
| `redis.master_name`、`redis.sentinel_addrs` | `master_name` 非空即走 Sentinel 模式（不需 `redis.addr`），必須同時設 `sentinel_addrs`，只設其中一個會啟動失敗（`redisstartup` 共用設定檢查，Central 在 `validateSettings` 拒絕）；`master_name` 與 `addr` 都空時 Gate、World、Lobby 啟動失敗；Central 只有 dev 或 `redis.single_node: true`（預設 false）才走單機記憶體模式，其餘拒絕啟動（見 Docker生產部署） |
| `redis.sentinel_password` | 連 Sentinel 節點的密碼（與資料節點的 `redis.password` 分開） |
| `redis.pool_size`、`redis.min_idle_conns`、`redis.conn_max_lifetime`、`redis.conn_max_idle_time` | 連線池；`conn_max_*` 須帶單位（如 `30m`），不合法啟動失敗；未設定採驅動預設 |
| `rabbitmq.url` | 連線字串（`RABBITMQ_URL` 環境變數可覆寫）；密碼含特殊字元要 URL 跳脫，格式錯誤啟動時直接失敗 |
| `rabbitmq.exchange`、`exchange_type`、`queue`、`binding_key`、`consumer_tag`、`prefetch_count` | 拓撲；預設 `record.events`、`topic`、`record.events`、`record.#`、`record-consumer`、128。發布端（World）只用 `url`／`exchange`／`exchange_type`；`queue`／`binding_key`／`consumer_tag`／`prefetch_count` 只有消費端（Record）使用 |

World（發布端）與 Record（消費端）的 `rabbitmq.exchange`／`exchange_type` 必須一致：只覆寫其中一邊會對不上，事件進不了佇列。要改就兩份設定一起改。佇列與綁定只由 Record 宣告；World 不再宣告佇列也不綁定。

## 已知限制（第九輪）

- 單機 Central（未接 Redis 的帳號清除路徑）刪除過期帳號時不會刪除 `gm:ban:{account}` 封禁鍵；封禁鍵只靠自己的 TTL 過期，同名新帳號在封禁期限內仍會被擋。
- 資料庫若開 `sql_require_primary_key=ON` 或使用 Group Replication，無主鍵表無法建立或寫入，見[Docker 生產部署](../30-部署與開發/Docker生產部署.md)「無主鍵表」一節。
