# 系統導讀

## 專案定位

多伺服器遊戲後端框架，使用 Go 語言開發，基於 TCP 長連線與自訂訊息協定。
系統處理玩家的登入/登出流程，跨越多個伺服器實體，提供分散式帳號管理與會話追蹤。

## 六大服務

| 服務 | 角色 | 監聽埠 | 核心職責 |
|------|------|--------|--------|
| **Central** | 帳號中心 | 60001 (world), 60002 (gate) | 使用者驗證、請求去重、MySQL 持久化、World 路由分配、World 間訊息轉發 |
| **Chat** | 文字聊天 | 63001 (chat) | 文字聊天歷史、`ChatSync` 補送、MySQL 歷史、即時 TCP 廣播、系統訊息 |
| **Gate** | 玩家閘道 | 62001 (user) | 玩家連線入口、Session 狀態機、訊息路由、速率限制、GM kick 執行 |
| **World** | 遊戲世界 | 61001 (gate) | 玩家狀態持久化、恢復校驗、遊戲邏輯、頻道管理、遊戲資料 MySQL 持久化 |
| **Record** | 事件流水 | 6070 (HTTP) | RabbitMQ 事件消費、每日 MySQL 分表（`record_events_YYYYMMDD`）、查詢/統計 API |
| **Lobby** | 服務探索 | 8080 (HTTP) | 回傳 Gate/Central/World 地址清單；GM admin API（kick/ban） |
| **User** | 測試客戶端 | — | 模擬玩家連線，支援 stdin 指令操作 |

## 技術棧

- **語言**: Go 1.26
- **資料庫**: MySQL (GORM) — 帳號資料與遊戲進度真相來源
- **佇列**: RabbitMQ — Record 事件流水的非同步旁路
- **JSON 序列化**: goccy/go-json — 玩家狀態寫回 Redis 與 RabbitMQ 事件發布的熱路徑改用零分配高速實作（相容 encoding/json 介面）
- **快取**: Redis — 玩家狀態暫存、服務探索（Gate/Central/World 心跳）、GM 封禁/踢人佇列
- **持久化**: MySQL — 帳號、遊戲進度、聊天歷史、資料真相來源
- **監控**: Prometheus + Grafana（30+ 指標）
- **分散式追蹤**: OpenTelemetry（stdout / OTLP 輸出，Jaeger 可視化）
- **日誌**: `pkg/logger` 封裝的 zerolog 結構化日誌，支援 trace_id 串聯
- **密碼安全**: bcrypt（cost=10）；空 hash 時向下相容舊帳號
- **CI/CD**: GitHub Actions（lint → unit → integration → docs）
- **部署**: Docker Compose（開發/正式環境分離）

## 請先掌握的三個中繼資料

| 欄位 | 由誰建立 | 用途 |
|------|---------|------|
| `protocol_version` | Gate | 標示跨服務登入/登出/恢復校驗使用的協定版本 |
| `request_id` | Gate | 同一筆跨服務 request/reply 鏈路的去重與結果回放 |
| `trace_id` | Gate | 串聯 Gate / Central / World 的日誌與 OTel Span |

> 原始玩家輸入不攜帶這三個欄位，而是在請求進入 Gate 後才建立。
> `trace_id`（uint64）在 OTel 中被映射為 128-bit TraceID（填入後 8 bytes），使同一條鏈路的 Span 在 Jaeger 中聚合為同一條 Trace。

## 資料真相來源

| 資料類型 | 真相來源 | 補充 |
|---------|---------|------|
| 帳號、`player_id`、持久 `world_id` | MySQL (Central) | 長期持久資料，由 Central 寫入 |
| 玩家遊戲進度（等級、經驗、道具） | MySQL (World) | World 記憶體為權威（write-behind），第一次存取時載入，每秒寫回，登出與關機時寫回 |
| 聊天歷史 | MySQL (Chat) | `ChatSync` / 即時廣播的歷史來源 |
| 玩家目前掛在哪個 Gate / World | Central memory | 運行期線上路由，可重新登入重建 |
| 玩家 session 狀態 | Gate memory | `pending_login / logged_in / pending_logout` 的唯一依據 |
| World 在線玩家狀態 | World memory | 單一 World 節點內的即時狀態 |
| 頻道成員 | World memory | 玩家登出或 Gate 斷線時自動清理 |
| 一般操作流水 | Record MySQL | 由 World 異步送到 RabbitMQ，再落地到每日分表 `record_events_YYYYMMDD` |
| World 重啟恢復候選 | Redis (`player:*`) | 僅供 restore 起點，不可直接視為仍在線 |
| Gate/Central/World 服務探索 | Redis (`lobby:*`) | TTL 25s；心跳停止後自動過期 |
| GM 封禁 | Redis (`gm:ban:*`) | 由 Lobby admin API 寫入，Gate 登入時查詢 |

## 核心設計理念

1. **事件驅動** — `AppBase` 事件迴圈，提供 1ms ~ 1d 週期性更新
2. **Session 狀態機** — 明確狀態轉換防止競態條件
3. **請求去重** — `request_id` + request journal 防止重複操作
4. **分散式追蹤** — `trace_id` 貫穿整個請求鏈路，映射為 OTel Span
5. **MySQL 為持久資料來源** — 帳號資料（Central）+ 遊戲進度（World）分庫管理
6. **斷路器容錯** — Redis/MySQL 故障時優雅降級
7. **按需載入與延遲寫回** — 遊戲資料在玩家第一次被存取時載入記憶體，之後讀寫都在記憶體，每秒寫回、登出時寫回；崩潰最多遺失約 1 秒的異動，不預載全量
8. **中介轉發** — World 間通訊透過 Central broker，無需 World 之間直接連線
9. **優雅排空** — Gate rolling deploy 時先停止接受新連線，等玩家自然下線後再強制斷開

## 效能設計要點

逐輪優化的流水記錄已移到 [[效能演進]]；這裡只留現行架構層級、且仍然成立的原則：

- **鎖要按領域拆**：World 拆 `userMu` / `chanMu`，Central 拆 `userMu` /
  `worldMu`，Gate 拆 `sessionMu` / `userMu`；reconcile 先唯讀掃描、有問題才加寫鎖。
- **熱路徑避免分配**：TCP 收發與訊息打包走 `sync.Pool`，熱路徑 JSON 用
  `goccy/go-json`，計數器用 `atomic`。
- **批次化取代逐筆 round-trip**：道具寫入、Redis TTL 刷新、
  World 恢復都走批次或 pipeline。
- **背壓優先**：`persistPool` 等佇列滿載時 drop，不阻塞 event loop。
