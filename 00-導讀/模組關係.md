# 模組關係

## 網路通訊拓撲

```mermaid
graph TD
    User["User 測試客戶端"] -->|TCP :62001| Gate
    Gate["Gate 玩家閘道"] -->|TCP :60002| Central
    Gate -->|TCP :61001| World
    Central["Central 帳號中心"] -->|TCP :60001| World["World 遊戲世界"]
    Chat["Chat 聊天"] -->|TCP :60003 TimeSync| Central
    Lobby -->|TCP :60004 TimeSync| Central
    Central -->|MySQL| DB[(MySQL 帳號)]
    World -->|Redis| Cache[(Redis)]
    World -->|MySQL| GameDB[(MySQL 遊戲資料)]
    Gate -->|Redis| Cache
    Lobby["Lobby HTTP :8080"] -->|Redis| Cache
```

## 連線角色

| 服務 | 被動服務（ServiceServer） | 主動服務（ServiceClient） |
|------|----------------------|------------------------|
| Central | World(:60001), Gate(:60002), Chat(:60003), Lobby(:60004) | — |
| Gate | User(:62001) | Central, World |
| World | Gate(:61001) | Central |
| Chat | Gate(:63001，dev 設定為 `:63201`) | Central（只接收 TimeSync） |
| Lobby | — | Central（只接收 TimeSync）；其餘經 Redis（HTTP 服務） |
| User | — | Gate |

> Gate 同時扮演 Server（對 User）和 Client（對 Central／World）。
>
> User 雖然放在 PJA-Server 專案內，網路角色仍是 Client；它不使用 S2S 端點。

## Lobby HTTP 端點

| 端點 | 方法 | 說明 |
|------|------|------|
| `/gates` | GET | 回傳所有 Gate 地址與負載，依負載升序排列 |
| `/notices?after=X` | GET | 回傳序號 X 後仍有效的系統公告 |
| `/admin/centrals` | GET | 回傳所有 Central 的 S2S 地址（需 ops token；不在公開 listener 提供） |
| `/admin/worlds` | GET | 回傳所有 World 的 S2S 地址（需 ops token；不在公開 listener 提供） |
| `/admin/kick?playerID=X` | POST | 踢出指定玩家（需 Bearer token） |
| `/admin/ban?account=X&duration=Xh` | POST | 封禁帳號並踢出在線玩家（需 Bearer token） |
| `/admin/unban?account=X` | POST | 解除封禁（需 Bearer token） |
| `/admin/notices` | POST | 建立系統公告（需 ops token） |
| `/admin/notices/{seq}` | DELETE | 撤下系統公告（需 ops token） |

## pkg 邊界

`pkg` 只放跨服務共用、而且不會因單一服務業務演進而頻繁變動的東西。

### 可以放

- `tcpserver`
  - TCP 伺服器執行期協調
  - 設定解析、accept 連線管理
- `tcpclient`
  - TCP 用戶端執行期協調
  - 連線管理、重新連線、限流
- `tcpsocket`
  - Socket 生命週期、`OwnerBase`
  - 封包收送與佇列管理
- `tcpruntime`、`tcpregistry`、`tcpconfig`
  - 最小共用介面（`Service`、`Socket`、`Msg`）、連線登記與排空、TCP 設定
- `framecodec`
  - frame 編碼／解碼
- `msg`
  - 協定基礎設施（`protocol_meta.go`、`wire` 編解碼、`RequestMeta` / `TraceMeta`）
- `msg/auth`、`msg/chat`、`msg/board`、`msg/combat`、`msg/system`
  - 協定訊息 DTO，依領域拆分；呼叫端使用具名匯入
- `protocol`
  - `MessageID` 與 `wire` 型別，皆由 PJA-Protocol 生成，不得手改
- `pkg/requestjournalredis`
  - `(scope, request_id) -> result` 的短期冪等快取的 Redis 後端
- `grantitem`
  - GM 發放的共用指令格式、key schema、死信佇列與重試預算
- `metrics`、`logger`、`debug`
  - 觀測與運維，不含業務流程

### 不該放

- 各服務 handler 的業務規則
- MySQL／Redis 的特定領域對應
- 單一服務才會用到的 policy 分支
- 需要跟著玩家流程一起改的狀態機
- 會讓 `pkg` 反過來依賴應用程式的東西

### 判斷原則

1. `pkg` 可以被多個服務直接匯入
2. 單一服務改規則時，不該逼所有應用程式跟著改
3. 只要開始混入業務分支，就應該拆回應用程式或 `internal`

## appcore 與 stdin 指令的角色

- `appcore.AppBase` 提供事件迴圈與週期性更新；各服務建立在同一套 appcore 模式上，因此 handler 初始化、定時清掃、健康檢查行為有一致骨架。
- stdin 指令輸入已不在 appcore：只有 `User` 測試客戶端有，實作在 `tools/user/internal/stdinevent`，目前只有 `login <accountType> <account> [password]` 一條指令（見[開發規則](../30-部署與開發/開發規則.md)）。
- 六個服務（Central、Gate、World、Chat、Lobby、Record）都走 `startup.InitializeRuntime`；User 是另一個工具程式，不使用 S2S 端點。

## 訊息 ID 分區

Client 與 S2S 的 `MessageID` 都由子模組 `deps/PJA-Protocol` 的 `Datas/message-id.xml` 維護，`pkg/protocol/message_id.go` 是 `Scripts/BuildServer.ps1` 產生的檔案（`DO NOT EDIT`），手改會被下次 `scripts/sync-protocol.ps1` 覆蓋。下列 `MessageID` 同時
就是 TCP frame 標頭的 ID，不另設 `wire_id`。

| ID 範圍 | 方向 | 說明 |
|---------|------|------|
| 1–999 | Client ↔ Server | PJA-Protocol 既有玩家遊戲流程訊息 |
| 1001–1004 | Client ↔ Gate | Client 驗證與登入恢復鏈路 |
| 2005–2006 | Client ↔ Gate | Client HeartbeatRequest／Response（Luban） |
| 2101–2199 | Client 預留 | 舊頻道操作協定已移除；頻道 S2S 訊息（30403–30405）已停用，定義待下次升版移除 |
| 2201–2204、2206 | Client ↔ Chat 經 Gate | 聊天加入／離開／傳送／投遞／同步 |
| 2500–29999 | Client 預留 | 新增 Client 訊息更新 PJA-Protocol |
| 30001–30099 | 服務 ↔ 服務 | Server 驗證與登入恢復鏈路 |
| 30101–30199 | 服務 ↔ 服務 | S2S ConnectInfo、HeartbeatReq／Res、TimeSync |
| 30201–30299 | 服務 ↔ Chat | ChatSystem |
| 30301–30399 | 服務 ↔ 服務 | World 轉送、Gate 路由同步 |
| 30401–30499 | Central ↔ 服務 | 稽核快照 |
| 30500–65535 | S2S 預留 | 新增 S2S 訊息改 PJA-Protocol 的 `message-id.xml`，再執行 `scripts/sync-protocol.ps1` |
