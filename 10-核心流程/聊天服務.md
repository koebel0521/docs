# 聊天服務

這份文件描述目前聊天服務的責任邊界、資料來源與同步規則。

## 目標

- 文字聊天與世界廣播群組分離
- 聊天歷史可從 MySQL 補回
- client 換機或重連時，可以用 `ChatSync` 補缺
- 即時送達仍走 TCP 廣播，不引入額外 queue

## 責任邊界

### 聊天服務

- 接收 `ChatSend`、`ChatSystem`、`ChatSync`
- 將聊天歷史寫入 MySQL
- 維護 `MessageID`
- 根據 room membership 做即時 fanout
- 對 `ChatSync` 回傳指定區間的歷史訊息

### Gate

- 只負責轉發玩家聊天請求
- 收到 `ChatDeliverBatch`（每個 Gate 一幀，內含該 Gate 上的目標玩家清單）後，打包一則 `ChatDeliver`，共用同一份封包送給所有本地收件人
- 不保存聊天歷史
- 每條玩家連線各自限流：`ChatSend` 每秒 2 則、突發 5 則；`ChatSync` 每秒 1 次、突發 3 次。超過的請求直接丟棄並計入 `game_chat_rate_limited_total{kind}`；`ChatSend` 內容超過 1024 bytes 也直接丟；內容還必須通過 `pkg/chatrule.ValidPayload`（合法 UTF-8，且不含 C0 控制字元 0x00–0x1F（**含換行與 Tab**）、DEL、C1 控制字元（含 NEL）、U+2028／U+2029 行段分隔字元、雙向覆寫與隔離字元（RLO 等）與零寬字元 U+200B／U+2060／U+FEFF；刻意保留 ZWJ、ZWNJ 與 U+FE0F，組合表情才不會被拒），否則靜默丟棄、不回應。這道檢查 Gate 轉送前與 Chat 受理前各做一次（信任邊界）：這些字元可用來偽造系統訊息的版面、反向顯示連結或檔名、繞過關鍵字過濾，非法 UTF-8 會讓日誌、資料庫與 Client 顯示行為不一。**待與 PJA-Client 負責人確認**：Client 是否允許多行輸入（若要，把 0x0A 從 `chatrule` 排除即可）、是否以 rich text 呈現（`<color>`、`<link>` 標籤要不要在 Client 端跳脫）；規則刻意保守，只擋這兩類棄
- 記錄每位玩家目前加入的聊天室（依轉發成功的 `ChatJoin`／`ChatLeave`）。與 Chat 斷線重連完成 `ConnectInfo` 後，對每位在線玩家重送 `ChatJoin`，重建 Chat 端遺失的房間成員；Chat 重啟後玩家不必重新加入
- 玩家登出、斷線、被踢或驗證失敗而解除綁定時，對所有 Chat 送出 `RoomID = 0` 的 `ChatLeave`（離開全部房間），Chat 不會留下幽靈成員

### World

- 不承擔聊天流程；文字聊天全部由 Chat 服務處理
- 頻道（`Channel*`）功能已移除：World 不送 `ChannelBroadcast`、`ChannelMembershipUpdate`、`ChannelMembershipSnapshot`，Gate 也不再保存頻道成員投影
- `Channel*` 的 S2S 協定定義（30403 至 30405）仍保留在 `protocol.xml`，待下次協定版本提升時一併移除，見 `協議與配置來源需求.md`

## 房間權限

- 目前所有房間都是公開房間：任何已登入玩家都可以 `ChatJoin` 任意 `RoomID`，並讀取該房間的即時訊息與 `ChatSync` 歷史
- 伺服器沒有房間成員的權威來源（公會、隊伍等）；新增私人房間時，必須改由 World 依權威狀態管理成員，不可再讓 Client 自行加入
- Gate 斷線時 Chat 會移除該 Gate 上所有玩家的房間成員資格
- 每位玩家最多加入 16 個房間；每個房間成員上限 `room_max_members`（Chat 設定，未設定為 `app.DefaultMaxRoomMembers`＝500，非正數或非數字拒絕啟動；第十一輪。第十二輪起以 `bootstrap.Int` 嚴格讀取，`1.9`、`"1e3"` 這類非整數也拒絕啟動，並由建構選項 `app.WithMaxRoomMembers` 注入，建構後唯讀）。房間已滿時新成員的 `ChatJoin` 被**靜默拒絕**（不回覆；已是成員的重複加入不受影響），之後在該房間送訊會因非成員被拒。上限是為了擋扇出隨成員數平方成長：少數 IP 開上千條已登入連線進同一房間就能壓垮 Gate
- 先到先得的上限可被少數來源佔滿（第十二輪 SC-L2），Gate 另限制同一來源 IP（IPv6 以 /64 計）在同一房間經此 Gate 的成員數（`session.chat_room_members_per_ip`，預設 50）：名額滿時 Gate 不轉送 `ChatJoin`，計入 `game_chat_rate_limited_total{kind="join"}`，Client 同樣收不到失敗回覆。玩家來源以第一個房間為準、退出時歸還名額；沒有來源 key 的連線不限額。限制：每台 Gate 各自計數，來源分散到多台 Gate 時名額按 Gate 計；保留名額、帳號年齡等更完整的方案仍待決策

## 訊息

### `ChatSend`

- 玩家送出文字聊天訊息
- `Gate` 轉給 `ChatService`
- `ChatService` 先落 MySQL，再即時廣播

### `ChatSystem`

- 其他服務送入的系統訊息（目前正式程式沒有任何 Gate 送出，保留給日後使用）
- 入口與玩家訊息同樣檢查大小與內容：超過 `chat.MaxPayloadBytes` 或未通過 `chatrule.ValidPayload` 直接丟棄
- `RoomID = 0` 代表全域廣播
- 會進歷史，之後也能被 `ChatSync` 補回

### `ChatSync`

- 玩家在登入後或斷線重連後請求歷史補送
- `SinceMessageID` 只當 hint
- `ChatService` 只回 `SinceMessageID` 之後的訊息
- 最多回 `Limit` 筆，server 端有硬上限
- 同一房間連續排隊的多個 `ChatSync` 由房間工作者合併成一次 MySQL 讀取（一批最多 10 個查詢，由 `maxRoomSyncFrames`＝1000 除以每查詢上限 100 推得；第十二輪 P-M1 前是 64 個，一次合併讀取後最多連續送出 6400 幀，重連潮時可能塞滿 Gate 事件佇列）：以其中最小的 `Since` 讀一次硬上限（100 筆），再各自切出 `Since` 之後的前 `Limit` 筆；共用結果讀滿上限仍不涵蓋某個查詢時，才為它單獨再查一次。回應內容與逐筆查詢相同，重連潮時不再一人一句 SELECT 把房間佇列塞滿

### `ChatDeliverBatch`

- `ChatService` 派送到 `Gate` 的 S2S 訊息（協定 ID 30202），每個 Gate 一幀
- 欄位：`messageId`、`senderPlayerId`、`roomId`、`targetPlayerIds`（該 Gate 上的房間成員）、`payload`
- 100 人房分布在 3 個 Gate 時，只送 3 幀（原本逐人送 100 幀）
- 查不到所在 Gate 的玩家，改對所有 Gate 廣播；Gate 端只投遞給自己有連線的玩家

### `ChatDeliver`

- `Gate` 收到 `ChatDeliverBatch` 後送給本地玩家 socket 的訊息（client 協定）
- 帶 `MessageID`，不帶收件人（協定版號 3 起移除 `targetPlayerId`），同一則訊息所有收件人的封包相同，Gate 只打包一次
- client 可用來去重與更新 sync 起點
- 歷史同步（`ChatSync`）也以單一目標的 `ChatDeliverBatch` 回給 Gate，Chat 不再送單則 S2S `ChatDeliver`

## 資料來源

### MySQL

- `chat_message`
- 目前是聊天歷史的 source of truth
- `ChatSync` 的查詢入口

### Memory

- room membership
- user membership
- 鮮活在線目標集合

## 同步規則

1. client 送 `ChatSync(SinceMessageID, Limit)`
2. `ChatService` 查 MySQL
3. 回傳 `SinceMessageID + 1` 之後的歷史
4. 最多回 `Limit` 筆
5. client 用 `MessageID` 去重

## 即時廣播

1. `ChatService` 收到 `ChatSend` 或 `ChatSystem`
2. 排進該房間的序列佇列（見下節）
3. 寫 MySQL
4. 查目前 room 的在線成員
5. 依玩家所在的 Gate 分組，每個 Gate 只送一幀 `ChatDeliverBatch`；查不到所在 Gate 的玩家，對所有 Gate 廣播
6. `Gate` 打包一則 `ChatDeliver`，共用送到本地玩家 socket

## 房間序列佇列

`ChatSend`、`ChatSystem`、`ChatSync` 的 MySQL 讀寫都不在事件迴圈裡執行，而是排進房間序列佇列：

- 同一房間的工作嚴格依進入順序逐一執行，所以同房間訊息的 `MessageID` 遞增順序、送達順序與送出順序一致
- 不同房間平行處理，一個房間的慢查詢不會擋住其他房間
- `ChatSync` 與同房間的送出共用佇列，讀到的歷史一定包含先前已受理的訊息
- `RoomID = 0` 的全服廣播使用同一個機制，key 為 0
- 房間有工作時才有 worker goroutine，佇列清空就結束
- 單一房間等待上限 256，超過時丟棄新訊息並計入 `game_msg_queue_dropped_total{service="chat_room"}`；已受理的訊息順序不受影響
- 關機時先排空佇列再關閉連線

指標與告警見 [[指標面板]] 的 Chat Room Queue。

## 保留與清理

- `chat_message` 依設定 `history_retention` 定期刪除過期訊息：預設 `720h`（30 天），設為 `0` 表示不清理
- Chat 啟動後立即清理一次，之後每小時一次；每批刪除 1000 筆早於保留期限的訊息，直到清完，依 `created_at` 索引（`idx_chat_message_created_at`）掃描
- 保留期限以遊戲時間（Central 校正時鐘）減 `history_retention` 計算；尚未收到 Central 第一則 `TimeSync` 時略過該次清理，避免主機時鐘偏快誤刪
- 關機時清理隨服務 context 停止，先等清理結束才關閉資料庫

## 遊戲時間

- Chat 以 `pkg/centralclock` 連 `<id>.dial.central`（Central `60003`，S2S 授權讀 `s2s_auth.central`）只為接收 `TimeSync`，收到第一則前 `/ready` 的 `time_sync` 檢查不通過；compose 中 Chat 等 Central `healthy` 才啟動
- 訊息的 `created_at` 由 App 以遊戲時間明確寫入（單則與批次相同），不由 GORM 以 Chat 主機時鐘補
- 未同步前寫入聊天紀錄回 `appcore.ErrTimeNotSynced`，訊息不送達；加入、離開與 `ChatSync` 不用時間，照常處理
- room membership 不持久化
- 若未來要做長期歸檔，再補歷史分表或冷資料搬移
