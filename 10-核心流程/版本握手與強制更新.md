# 版本握手與強制更新

Client 與 Server 的相容性在連線的第一個訊息就判斷，不再放在每個登入訊息裡。這份文件說明握手流程、更新政策、線上玩家的處理、服務之間的檢查與啟動驗證。完整設計與取捨見 `PJA-Docs/版本相容重新規劃.md`。

## 版本欄位

| 欄位 | 來源 | 判斷方式 |
| --- | --- | --- |
| `protocol_version` | `PJA-Protocol/protocol.version.json`，產生碼 `protocol.ProtocolVersion` | 必須與 Server 相等 |
| `client_contract` | `PJA-Config/version-policy.json`，寫入 `config/data/version.json` | 必須與 Server 相等 |
| `config_seq` | PJA-Config 主線 commit 數，只增不減 | 不得低於 Server 的 `min_config_seq` |
| `min_config_seq` | `PJA-Config/version-policy.json`；隨 `pkg/release/release.json` 發版 | 低於它的 Client 必須更新 |
| `game_version` | Client 安裝包版本（SemVer） | 與 Redis 政策的 `min` 與 `latest` 比較 |
| `config_version` | PJA-Config 完整 commit SHA | 只用於識別與診斷，不比較新舊 |

協定與設定契約用 schema 指紋 lock 檔檢查是否漏提升版號（`PJA-Protocol/protocol.lock.json`、`PJA-Config/config.lock.json`），規則見各自的 README。

## 握手流程

新連線的第一個訊息必須是 `HelloRequest`（2009）。Gate 在登入前依下表由上而下判斷，第一個成立的即為結果：

| 順序 | 情況 | 結果 | 原因 |
| --- | --- | --- | --- |
| 1 | 政策開啟維護 | `Maintenance` | `None` |
| 2 | 協定版本不同 | `ForcedUpdate` | `ProtocolMismatch` |
| 3 | 設定契約不同 | `ForcedUpdate` | `ClientContractMismatch` |
| 4 | 遊戲版本低於該平台 `min`，或版本字串無法解析 | `ForcedUpdate` | `GameVersionTooOld` |
| 5 | `config_seq` 低於 `min_config_seq` | `ForcedUpdate` | `ConfigTooOld` |
| 6 | 遊戲版本低於該平台 `latest` | `OptionalUpdate` | `None` |
| 7 | 其他 | `Ok` | `None` |

- 回覆 `HelloResponse` 後，`ForcedUpdate` 與 `Maintenance` 直接關閉連線；`Ok` 與 `OptionalUpdate` 進入登入流程。
- 沒有先 Hello 就送其他訊息、或重複 Hello 以外的訊息：直接關閉連線。重複的 Hello 忽略。
- 連線狀態：`awaitHello`（只收 Hello）→ `ready`（收登入與遊戲訊息）→ `draining`（寬限期，只收登出與心跳）→ `closed`。
- 政策尚未載入（Redis 沒資料或讀不到）時只比對發版固定值，遊戲版本一律放行；平台沒有設定政策時也不檢查遊戲版本。
- Hello 的 `schemaHash`、`configVersion` 只寫入 log 供診斷。
- Hello 字串欄位有長度上限：`GameVersion` ≤32、`ConfigVersion` ≤64、`SchemaHash` ≤64 bytes。超過即不回覆、直接關閉連線並計 `game_version_hello_total{result="rejected",reason="invalid_hello"}`，不寫入 log，避免未登入連線以大字串放大日誌與記憶體。

程式：`cmd/gate/internal/handler/user/on_hello_request.go`（握手）、`cmd/gate/internal/versioncheck`（判斷與定期重載，只有 Gate 使用）、`pkg/versionpolicy`（政策 JSON 解析與驗證，Lobby 寫入前與 Gate 共用）。

## 更新政策

營運可即時調整，不必重新發版。政策存在 Redis 字串 `gm:version:policy`（JSON），Gate 啟動時先載入一次，之後每 10 秒重新載入；讀取失敗或內容錯誤時保留舊政策：

```json
{
  "maintenance": { "enabled": false, "end_at": 0 },
  "kick_grace_seconds": 60,
  "platforms": {
    "windows": { "min": "1.2.0", "latest": "1.4.0" },
    "android": { "min": "1.2.0", "latest": "1.4.0" },
    "ios":     { "min": "1.2.0", "latest": "1.3.2" }
  }
}
```

- 平台名稱只接受 `windows`、`android`、`ios`、`mac`；版本必須是 SemVer，`min` 不可大於 `latest`；`maintenance.end_at` 是 Unix 秒；`kick_grace_seconds` 預設 60、上限 600。
- key 不存在代表沒有任何限制。

Lobby 管理介面（需要 ops 角色）：

```bash
# 讀取目前政策；尚未設定回 404
curl -H "X-Requested-By: admin" -H "Authorization: Bearer $OPS_TOKEN" http://lobby/admin/version-policy

# 整份取代；內容驗證失敗回 400 且不動既有政策
curl -X PUT -H "X-Requested-By: admin" -H "Authorization: Bearer $OPS_TOKEN" \
  --data @policy.json http://lobby/admin/version-policy
```

## 線上玩家

Hello 只在連線時檢查一次。政策換新後，Gate 用每條連線 Hello 時回報的版本重新判斷：

- 變成強制更新或維護：推送 `VersionNotice`（2011，帶 `disconnectAt`），連線進入 `draining`，期限到才斷線；寬限期內只處理登出與心跳。
- 變成建議更新：只推送一次 `VersionNotice`，不斷線。
- 限制解除：取消寬限期並推送恢復正常的通知。
- 同一結果對同一條連線只通知一次。

## 熱更新與發版

| 變更 | 做法 |
| --- | --- |
| 調數值、改文字、修 Server 內部問題 | 熱更新設定，不動版本政策 |
| 新增設定內容，舊安裝包缺資料（必須強制更新） | 維護發版：新安裝包上架 → 開維護 → 部署 Server → 調高 `latest` → 關維護 |
| 設定格式不相容、協定變更 | 同上；`client_contract` 或 `protocol_version` 提升 |
| 緊急強制更新（例如外掛漏洞） | 新安裝包上架後，以 `PUT /admin/version-policy` 調高該平台 `min` |

設定熱重載與熱發布會拒絕 `client_contract` 或 `min_config_seq` 與目前版本不同的 artifact（`internal/gamecore/configcompat`）：這兩種變更必須隨新安裝包走維護發版，否則線上舊版 Client 會在寬限期內收到它讀不懂的內容。

## 服務之間

連線建立後，`ConnectInfo` 之後緊接著送出 `ServiceHello`（30105）：發版、Server commit、協定 schema 指紋與設定契約。任何一項與本節點不同就記錄錯誤、累計 `game_service_hello_mismatch_total` 並關閉連線，擋下新舊版服務混著部署。`AppType` 與 `AppID` 只供診斷。

ServiceHello 是強制的：連線建立後 `s2shandshake.ServiceHelloTimeout`（5 秒）內沒收到對端 hello 就記錄 `service hello timeout, closing socket` 並斷線；收到 hello 前除了 `ConnectInfo` 與 `ServiceHello` 以外的訊息一律不處理，記錄 `message before service hello, closing socket` 並斷線。兩者同樣計入 `game_service_hello_mismatch_total`。

**混版本升級注意**：不送 ServiceHello 的舊版服務（審查 N18 修正前的版本仍會送，但未設定身分的建置不會）連到新版時會被斷線；且發版身分本來就必須一致，服務之間不支援新舊版混跑。升版一律整批替換同一次發版的所有服務（Central、World、Gate、Chat、Lobby），不可逐台滾動混跑；整合測試的假服務以同一份 `release.json` 送出 hello。

## 啟動驗證

每個服務啟動時（`pkg/startup`）比對嵌入的 `pkg/release/release.json`，任一項不一致就拒絕啟動：

1. 協定產生碼的版號與 schema 指紋。
2. 載入的設定 artifact：設定契約與最低設定序號；非開發版另比對 `config_version`、`config_seq`。
3. Central、Chat、World、Record 開啟資料庫後比對 `schema_migrations` 的最新版本（尚無版本化 migration 時為 `none`，略過）；查詢有 10 秒逾時，MySQL 不回應時啟動回錯而不是卡住。

正式 World 的 artifact root（`current.json`、`releases/`）頂層沒有 `version.json`，第 2 項的通用檢查會略過；World 載入設定後另以實際載入的 manifest 比對同樣的欄位（組合根把 `release.Info.VerifyConfig` 傳給 `cmd/world/internal/services` 的 `VerifyDataConfig`），不一致就拒絕啟動。`VerifyDataConfig` 是必填：組合根漏接時 `Start` 直接回錯，不會靜默停用這個唯一的發版／設定一致性檢查（單元測試以明確的 no-op 檢查函式傳入）。熱重載的候選 artifact 也走同一個比對，不一致以 `ErrReloadRejected` 拒絕換版（`data_config_reload_total{result="rejected"}`）。

`release.json` 在發版時由 `tools/releasemanifest generate` 依實際產物產生，格式與流程見 [Docker發版流程](../30-部署與開發/Docker發版流程.md)。倉庫內提交的是開發版（`release` 為 `dev`），必須與目前的協定產生碼與 `config/data` 一致；同步 PJA-Protocol 或 PJA-Config 後 `pkg/release` 的測試失敗時，更新它。

## 指標

| 指標 | 說明 |
| --- | --- |
| `game_version_hello_total{result,reason,platform}` | 握手結果；強制更新的原因與平台分布用來判斷何時可以調高 `min` |
| `game_version_notice_total{result,reason}` | 線上政策變動後推送的通知 |
| `game_service_hello_mismatch_total{service}` | 服務之間因發版不同、逾時未送 hello 或 hello 前送其他訊息而被拒絕的連線；大於 0 代表有混版本部署 |

## 測試工具

`tools/private/loadtest`、`pja flow replay` 與模擬玩家 `tools/user` 連線後先送 `HelloRequest`（`pkg/release/releasehello.Request(info, clientContract)`，遊戲版本為 `releasehello.ToolGameVersion`；放在子套件是因為 `pkg/release` 是所有服務匯入的葉套件，不依賴協定訊息）；`tools/private/loadtest`、`pja flow replay` 的 `-client-contract` 預設 0，表示沿用 `pkg/release/release.json` 的 `client_contract`，指定其他值可測試被拒絕的情況。整合測試的 `testenv.DialUser` 自動完成握手，`testenv.DialRaw` 供測試握手本身。
