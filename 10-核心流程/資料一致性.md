# 資料一致性策略

這份文件描述目前 `Central`、`World`、MySQL、Redis player store 之間的資料一致性策略。

這裡描述的是「目前程式已落地的規則」，不是理想化設計。

相關文件：

- [[連線與登入流程]]
- [[時序圖]]

## 資料面分類

目前系統中的玩家資料大致分成 5 類。

### 1. Account Routing Data

位置：

- MySQL `user` table
- Central memory

欄位：

- `player_id`
- `account`
- `world_id`

用途：

- 依 `account` 找到對應玩家
- 決定玩家應登入哪個 `World`

### 2. Online Routing Data

位置：

- Central memory

欄位：

- `player_id`
- `account`
- `world_id`
- `gate_id`

用途：

- 記錄目前玩家被哪個 `Gate` 代理
- 支援 Gate / World 斷線時的清理與重路由

### 3. Session Data

位置：

- Gate memory

欄位：

- `session_key`
- `player_id`
- `world_id`
- `state`
- `created_at`
- `last_seen_at`
- `logged_in_at`

用途：

- 管理玩家登入/登出狀態機
- 管理 `sessionKey <-> playerID` 綁定

### 4. World Presence Data

位置：

- World memory
- Redis player store

欄位：

- `player_id`
- `gate_id`
- `world_id`

用途：

- World 內部玩家在線狀態
- crash/restart 後恢復玩家狀態

### 5. Game Progress Data

位置：

- MySQL `player_profile` / `player_inventory_items` / `player_board` table（由 World 管理）

欄位：

- `player_id`
- `level`
- `exp`
- `updated_at`
- item records（`item_id`, `quantity`）

用途：

- 玩家道具、盤面與活躍時間持久化
- 道具與盤面走同步 MySQL 交易，崩潰不會遺失已提交的寫入

特性：

- 不預載全量玩家資料，只在實際操作時讀寫

## Source Of Truth

先決規則：

- 每一類 state 必須明確標成 `authoritative`、`derived` 或 `rebuildable`
- handler 只能直接改 `authoritative state`
- `derived state` 只能跟著 authoritative state 單一路徑更新，或交給 reconcile / sweep 重建
- `rebuildable cache` 壞掉只准影響效能或重試，不准改變正確性
- 值班與修復流程先判斷 drift 類型，再決定要修哪一層

### MySQL

MySQL 是系統中兩類長期資料的真實來源：

**帳號資料（Central 管理）**：`account -> player_id -> world_id`
**遊戲進度（World 管理）**：`player_id -> level / exp / items`

適用於：

- 玩家是否存在
- 玩家的持久 `world_id` 指派
- 玩家的遊戲進度（等級、經驗、道具）

不適用於：

- 玩家是否當前在線
- 玩家當前掛在哪個 `Gate`
- 玩家 session 是否仍有效

### Central Memory

Central memory 是「當前線上路由資訊」的運行期真實來源。

適用於：

- 玩家目前的 `gate_id`
- 玩家目前被哪個 `World` 服務
- 指定 `Gate` / `World` 上有哪些玩家

特性：

- 可以從登入流程重新建立
- `Central` 重啟後需要依靠玩家重新登入逐步恢復
- 不應被當成 crash 後可完全還原的永久資料

### Gate Memory

Gate memory 是 session 狀態機的真實來源。

適用於：

- 某個 `sessionKey` 是否存在
- 該 session 是否在 `pending_login` / `logged_in` / `pending_logout`
- 玩家 socket 與 user/session 的即時綁定

特性：

- 純運行期狀態
- Gate 斷線或重啟後不可直接從 DB 還原
- 需要靠玩家重新連線與登入重建
- `sessionKeyByUser`、`sessionCentral`、`usersByGate` 這類索引一律視為 derived state，不可直接當成真相來源

### World Memory

World memory 是單一 `World` 節點內玩家在線狀態的真實來源。

適用於：

- 某個玩家是否在此 World 上在線
- 該玩家目前對應哪個 `Gate`

特性：

- 可由 Redis player store 部分恢復
- 恢復後仍需要向 Gate 做主動校驗
- `usersByGate`、`channels`、`userChannels` 這類索引一律視為 derived state，不可直接當成真相來源

### World MySQL (GameStore)

World MySQL 是遊戲進度資料的真實來源。

適用於：

- 玩家等級、經驗值
- 玩家道具清單
- 遊戲進度的長期恢復

特性：

- 由 World 負責讀寫（與帳號 MySQL 分庫）
- 玩家登入時異步載入到 World memory cache
- 玩家登出時異步寫回，非同步操作
- 在線期間對進度的修改只在 memory，不即時落盤

### World Archive

位置：

- MySQL `player_profile_archive`
- MySQL `player_inventory_item_archive`
- MySQL `player_variable_archive`
- MySQL `player_state_archive`

用途：

- 封存長期不活躍玩家的主檔、道具、變數、盤面、道路星星、建築、抽獎狀態、設定版本與未過期玩家效果
- 讓 live 表只保留活躍玩家，降低主表膨脹
- 玩家回來時可自動 restore 回 live 表

特性：

- 以 `player_profile.updated_at` 判斷是否超過 90 天未活躍；登入時更新活躍時間
- 啟動時與每日執行封存，按玩家在同一筆 MySQL 交易中搬移可恢復的遊戲狀態
- 尚未結算的戰鬥會延後封存；封存時停用戰鬥候選快照，登入載入後重新發布
- 登入時先查正式主檔；主檔不存在才查封存並在同一筆交易中恢復，其他遊戲操作不查封存
- 抽獎歷史、商店互動、戰鬥與錢包結算、通知、Outbox 與 GM 冪等紀錄依各自用途保留

### Record Daily Tables

位置：

- MySQL `record_events_YYYYMMDD`

用途：

- 記錄一般操作流水
- 依事件發生日切日表，降低單表膨脹
- `Latest` 查詢時會往前掃最近 31 張日表，直到湊滿 `limit` 或掃完保留窗
- `LatestByView(view=online)` 只掃最近 7 張日表，供近線客服/營運查詢；`view=archive` 保留 31 張日表的完整查詢路徑

特性：

- 寫入時以 `occurred_at` 決定落哪一天的表
- 啟動時 `EventStore.New(ctx, db)` 預先建立最近 31 天的日表，ctx 允許上層控制 migration 超時
- 寫入路徑的 `ensureTable` 降級為冷路徑保險（僅在跨月啟動等極端情況觸發）
- 舊表是否保留由外部 retention 或歸檔流程決定
- 近線查詢與 archive 查詢要走不同 view，不要再共用同一條逐表掃描路徑

### GM Grant Ledger

位置：

- MySQL `gm_grant_record`

用途：

- 記錄 GM 發道具操作的冪等鍵
- `AddItem` 直接查主表，避免重複發放

### Redis PlayerStore

Redis player store 是 `World` 在線狀態的恢復輔助來源，不是最終真實來源。

寫入時機：

- 登入：`persistLoginPlayerStateAsync` 非同步經 `persistPool` 寫入單一玩家；佇列滿時會被
  丟棄（`PersistPoolDiscardTotal` 有監控）。
- 週期補寫：`RunPlayerStateFlush` 每 `PlayerStateFlushInterval`（5 分鐘）把在線玩家整批
  補寫一次，收斂上面被丟棄的部分。
- 優雅關閉：`FlushPlayerStates` 在 PreDrain 階段把全部在線玩家寫回。
- 心跳：`RefreshBatch` 只刷新既有 key 的 TTL，不會補上從未寫入的玩家。

適用於：

- `World` crash/restart 後的恢復起點

不適用於：

- 直接判定玩家仍在線
- 跳過 Gate session 驗證直接保留玩家

原因：

- Redis 可能殘留舊資料
- Gate session 可能已失效
- 玩家可能已斷線但 World 尚未清乾淨

## 可重建與不可重建資料

### 可重建

- Central memory online routing data
- Gate session data
- World memory online users
- Redis player store 內容

意思是：

- 這些資料可以透過重新登入、重新連線、恢復校驗逐步修正
- 短時間不一致是可接受的，但最終要被清理

### 不可隨意重建

- MySQL `user` table 的 `account/player_id/world_id`

意思是：

- 這是持久資料
- 不應因為短暫斷線或重送就重設

## 寫入順序與一致性原則

### Login

一致性原則：

- 先確立 `Central` 的帳號/World 路由，再讓 `World` 接受登入
- `Gate` 只在 `World` 成功回覆後才把 session 從 `pending_login` 轉成 `logged_in`

目前順序：

1. Gate 建立 pending session
2. Central 查 MySQL 或建立新 user record
3. Central 更新 memory route
4. Central 將登入轉送給 World
5. World 決定接受或拒絕
6. Gate 成功時 bind session；失敗時清掉 pending session
7. World 拒絕時，Gate 反向通知 Central rollback

實際含義：

- `Central` 可以比 `World` 早一步知道該玩家要去哪個 World
- 但只有 `Gate` 收到成功回應後，玩家才算真正登入完成
- `Central` 斷線後，Gate 會把綁在死 central 的 session 一起遷走，包含 `pending_logout`，避免路由卡在死節點
- `Gate` 重連後同步 `SyncUsersGateToCentral` 時，`GateID` 不能是 0；空 gate id 會讓 Central 寫出壞路由

### Logout

一致性原則：

- 先把 Gate session 轉成 `pending_logout`
- 再沿 `Gate -> Central -> World` 鏈路清理
- 最終由 Gate 回到 `disconnected`

目前順序：

1. Gate 將 session 從 `logged_in` 轉為 `pending_logout`
2. Central 刪除 memory route
3. World 清理頻道成員（LeaveAllChannels）
4. World 刪除 memory user 與 player store
5. Gate 刪除本地 user/session

實際含義：

- 登出成功的最後一跳是 Gate 清理本地狀態
- 若鏈路中斷，`pending_logout` 會由 sweeper 清掉
- 若 `Central` 斷線，`pending_logout` 的 `sessionCentral` 也會一起改掛新節點，不會留死路由
- 遊戲進度寫回為異步操作，World 崩潰時最後一次寫回可能遺失
- `Central` 登出若因 `World` 不在而失敗，會把同一個 request 的失敗結果寫進 replay cache，避免重送時語意變成 `SessionExpired`
- `Central` 登出若 `Services` 缺席，也要先清掉本機 user 並寫入 `AuthServiceUnavailable` 的 replay cache，不能留下 ghost state

### World Recovery

一致性原則：

- Redis restore 只提供候選集合
- 最終是否保留玩家，以 Gate 驗證結果為準

目前順序：

1. World 從 Redis 還原玩家狀態到 memory
2. 等待 `WorldRecoveryGracePeriod`
3. World 檢查對應 Gate socket 是否存在
4. 若存在，主動送 `ValidateWorldToGate`
5. Gate 依 session 與 `world_id` 回覆成功或 mismatch
6. World 對 mismatch 或無 Gate socket 的玩家執行清理
7. `AuditSnapshotRequest` 在 `App` 暫時不可用時，仍回空 snapshot，讓 Central 不用等 timeout 才知道資料面失聯

### World Crash Window

這段是 `World` crash 後到 `restore + validate + cleanup` 完成前的可接受不一致窗。

這段期間的裁決順序：

1. `World` memory 先失效
2. Redis player store 提供恢復候選
3. `Gate` session / validation 決定玩家是否真的保留

可丟資料：

- `World` memory online state
- 尚未通過 validation 的 Redis restore 候選

不可丟資料：

- MySQL `user` / `world_id` 對照
- 已成功寫回 MySQL 的遊戲進度

最長遺失窗：

- 道具與盤面：走同步 MySQL 交易，崩潰不遺失已提交的寫入
- 在線狀態：最壞只允許在 `WorldRecoveryGracePeriod` 內暫時不一致

收斂責任：

- `restorePlayers` 只做候選還原
- `reconcileRestoredPlayersOnce` 只做驗證與清理

## 短暫失聯與長時間失聯

目前系統將跨服務斷線分成兩類：

### 短暫失聯

條件：

- 斷線時間仍在 ServiceDisconnectGracePeriod 內

處理原則：

- 不立刻刪 Gate session
- 不立刻刪 World memory user
- 允許服務在短時間內重新連回並延續原有在線狀態

### 長時間失聯

條件：

- 超過 ServiceDisconnectGracePeriod 仍未恢復

處理原則：

- Gate 會清掉對應 World 的本地 user/session，並通知 Central 收斂 route
- World 會清掉對應 Gate 的玩家與 observer 狀態
- 此時才正式把狀態視為失效，而不是暫時抖動
## 允許的不一致

目前系統允許短時間存在以下不一致：

- Central memory 已有玩家，但 Gate session 還在 `pending_login`
- World restore 已載入玩家，但 Gate 尚未完成 validation
- pending logout 尚未完全傳遞到 World

這些不一致存在的前提是：

- 有 TTL 或後續鏈路會收斂
- 不會被當成永久真實狀態

## 不允許的不一致

以下狀況應被視為異常並最終清理：

- Gate session 已失效，但 World restore 後仍長期保留玩家
- World 已刪除玩家，但 Central 長期保留過期 route
- MySQL `world_id` 與 Central/World 長期分裂

目前的收斂手段：

- Gate session sweeper
- login replay cache
- World recovery validation
- Gate / World / Central 斷線後的清理路徑

## 故障場景下的判斷原則

### Gate 斷線

- Gate session 視為失效
- Central / World 需要逐步清理該 Gate 代理的玩家

### Central 斷線

- 既有 Gate pending login 應失敗返回
- 玩家可在 Central 恢復後重新登入
- MySQL 持久資料不應受影響

### World 斷線或重啟

- World memory 視為失效
- Redis player store 僅作恢復候選
- 是否保留玩家，以 Gate validation 結果為準

## 實務規則

之後若新增狀態資料，建議先回答 4 個問題：

1. 這份資料的 source of truth 是哪裡
2. 這份資料能不能被重建
3. 如果不同服務看到不同版本，最後由誰裁決
4. 故障後要靠什麼機制收斂

回答不清楚時，不應直接把新狀態塞進 memory 或 Redis。
