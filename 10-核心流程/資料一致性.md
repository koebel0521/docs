# 資料一致性策略

這份文件描述目前 `Central`、`World`、MySQL、Redis player store 之間的資料一致性策略。

這裡描述的是「目前程式已落地的規則」，不是理想化設計。

相關文件：

- [[連線與登入流程]]
- [[時序圖]]

## 資料面分類

目前系統中的玩家資料大致分成 5 類。

### 1. Account Routing Data

位置：

- MySQL Central `user` table（主鍵 `player_id`）
- Central memory

欄位：

- `player_id` (主鍵；Central 帳號 ID 同時是 World 玩家 ID)
- `account`
- `world_id`

用途：

- 依 `account` 找到對應玩家
- 決定玩家應登入哪個 `World`

### 2. Online Routing Data

位置：

- Central memory

欄位：

- `player_id`
- `account`
- `world_id`
- `gate_id`

用途：

- 記錄目前玩家被哪個 `Gate` 代理
- 支援 Gate / World 斷線時的清理與重路由

### 3. Session Data

位置：

- Gate memory

欄位：

- `session_key`
- `player_id`
- `world_id`
- `state`
- `created_at`
- `last_seen_at`
- `logged_in_at`

用途：

- 管理玩家登入/登出狀態機
- 管理 `sessionKey <-> playerID` 綁定

### 4. World Presence Data

位置：

- World memory
- Redis player store

欄位：

- `player_id`
- `gate_id`
- `world_id`

用途：

- World 內部玩家在線狀態
- crash/restart 後恢復玩家狀態

### 5. Game Progress Data

位置：

- MySQL `player_profile` / `player_inventory_item` / `player_board_state` 等 table（由 World 管理）

欄位：

- `player_id`
- `level`
- `exp`
- `updated_at`
- item records（`item_id`, `quantity`）

用途：

- 玩家道具、盤面與活躍時間持久化
- 玩家資料以 write-behind 寫入 MySQL：World 記憶體為權威，異動每秒（`DefaultFlushInterval`）以單一交易寫回，World 崩潰最多遺失約 1 秒的異動；已提交的寫回交易不會遺失（見下文特性與「最長遺失窗」）

特性：

- 不預載全量玩家資料，只在實際操作時讀寫

## Source Of Truth

先決規則：

- 每一類 state 必須明確標成 `authoritative`、`derived` 或 `rebuildable`
- handler 只能直接改 `authoritative state`
- `derived state` 只能跟著 authoritative state 單一路徑更新，或交給 reconcile / sweep 重建
- `rebuildable cache` 壞掉只准影響效能或重試，不准改變正確性
- 值班與修復流程先判斷 drift 類型，再決定要修哪一層

### MySQL

MySQL 是系統中兩類長期資料的真實來源：

**帳號資料（Central 管理）**：`account -> player_id -> world_id`
**遊戲進度（World 管理）**：`player_id -> level / exp / items`

適用於：

- 玩家是否存在
- 玩家的持久 `world_id` 指派
- 玩家的遊戲進度（等級、經驗、道具）

不適用於：

- 玩家是否當前在線
- 玩家當前掛在哪個 `Gate`
- 玩家 session 是否仍有效

### Central Memory

Central memory 是「當前線上路由資訊」的運行期真實來源。

適用於：

- 玩家目前的 `gate_id`
- 玩家目前被哪個 `World` 服務
- 指定 `Gate` / `World` 上有哪些玩家

特性：

- 可以從登入流程重新建立
- `Central` 重啟後需要依靠玩家重新登入逐步恢復
- 不應被當成 crash 後可完全還原的永久資料

### Gate Memory

Gate memory 是 session 狀態機的真實來源。

適用於：

- 某個 `sessionKey` 是否存在
- 該 session 是否在 `pending_login` / `logged_in` / `pending_logout`
- 玩家 socket 與 user/session 的即時綁定

特性：

- 純運行期狀態
- Gate 斷線或重啟後不可直接從 DB 還原
- 需要靠玩家重新連線與登入重建
- `sessionKeyByUser`、`sessionCentral`、`usersByGate` 這類索引一律視為 derived state，不可直接當成真相來源

### World Memory

World memory 是單一 `World` 節點內玩家在線狀態的真實來源。

適用於：

- 某個玩家是否在此 World 上在線
- 該玩家目前對應哪個 `Gate`

特性：

- 可由 Redis player store 部分恢復
- 恢復後仍需要向 Gate 做主動校驗
- `usersByGate` 這類索引一律視為 derived state，不可直接當成真相來源

### World MySQL (GameStore)

World MySQL 是遊戲進度資料的真實來源。

適用於：

- 玩家等級、經驗值
- 玩家道具清單
- 遊戲進度的長期恢復

特性：

- 由 World 負責讀寫（與帳號 MySQL 分庫）
- World 以記憶體為玩家資料的權威（write-behind）：`gamestore.Memory` 在玩家第一次被存取時以 `LoadPlayerSnapshot` 整份載入，之後的讀寫都在記憶體完成
- 每次操作以交易式暫存（`playerTx`）進行：成功才套用並記入待寫回清單，失敗整筆丟棄，與資料庫交易的回滾語意一致；同一玩家的操作以玩家鎖序列化
- 待寫回的異動每 `gamestore.DefaultFlushInterval`（1 秒）以 `SavePlayerChanges` 在單一交易內寫回；寫回失敗時保留異動，下個週期重試，同一筆資料以較新的值為準。週期寫回只處理有待寫回異動的玩家（`dirtyPlayers`），沒有異動的常駐玩家不起 goroutine、不搶寫回鎖；關機寫回（`FlushAll`）仍走完整名單，才能等到進行中的寫回完成
- 純讀取（`LoadItems`、`LoadVariable`、`LoadBoardState`、`LoadBoardBuildings`、`LoadPlayerConfigVersion`）走 `readPlayer` 唯讀路徑：只在玩家鎖內讀取，不建立暫存異動、不 commit、不觸發寫回；會寫入暫存的操作（例如 `LoadPlayerEffects` 會記下要清除的過期效果）仍走 `withPlayer`
- 玩家登出時（`EvictPlayerData`）同步寫回並移除常駐資料；優雅關閉時寫回全部常駐資料；封存不活躍玩家前先寫回全部
- 封存在玩家鎖內逐位執行（`ArchiveGuard`）：取得鎖後若玩家已變成常駐或有未寫回異動就略過本輪，鎖住期間該玩家無法載入，避免封存搬走資料後舊的常駐資料又寫回 live 表，造成同一玩家同時有封存與 live 資料
- 寫回被 MySQL 永久拒絕（`mysql.IsDataRejection`：欄位過長、約束違反）時，該玩家的待寫異動轉存 `<spill_dir>/rejected/` 的隔離檔並視為已寫回、清空 pending，不再每秒重試；背景寫回與經 `flushLocked` 的路徑（`EvictPlayer`、delegate、寫穿）行為相同。隔離後在玩家鎖內丟棄常駐資料與已套用金幣調整 ID，下次存取從 MySQL 重載，被拒批次的結果（含寫回期間新增、一併隔離的異動）不留在記憶體，卸載再載入不會重複套用；代價是這些未落地的合法異動也只留在隔離檔。人工處理 `rejected/` 時要一併處理調整單：隔離檔的 `AppliedGoldAdjustments` 對應的 `player_gold_adjustment` 列沒被刪，重載後會再套用一次並刪除，隔離檔裡的金幣值也已含這筆調整，不可直接重放覆蓋，須扣掉已重新套用的調整；GM 發放與 outbox 操作 ID 同理（資料庫無紀錄，重送已重新套用）。未設定落地目錄、暫時性錯誤或隔離檔寫入失敗時維持重試
- 登出、Gate 斷線與恢復驗證失敗的 Redis 玩家狀態清理共用 `App.DeletePlayerStatesIfOffline`：玩家仍連在 Gate 上就不刪，Redis 端再以本 World 的 ID 與清理當下的舊 GateID 做 compare-and-delete（`DeleteBatchIfWorld`），避免排隊期間的重新登入、同 World 換 Gate 重登或已改登他 World 的狀態被舊動作抹掉；崩潰還原刪除無效玩家狀態以本 World 做 compare-and-delete（GateID 傳 0 不比對）
- 關機取消不算寫回失敗：App ctx 已取消時 `flushOnce` 不計 `game_player_flush_failures_total`、不記 Warn（異動仍在 pending）；`Memory.Run` 收到取消直接返回，最後寫回只由 `FlushPlayerData`／`FinalizePlayerData` 負責。
- 關機前的最後一次寫回（`FinalizePlayerData`）不經斷路器，直接嘗試寫入 MySQL；仍寫不進去的異動以 gob 落地到 `game_store.spill_dir`（gob 依 Go 欄位名編碼，落地檔的全部欄位由 `gamestore/testdata/spill_fields.golden` 守住：新增欄位以 `UPDATE_SPILL_GOLDEN=1` 重產，改名或刪除欄位必須先補舊檔相容處理，見 `spill_legacy_format_test.go`，否則升級後重放舊落地檔會靜默遺失欄位）（正式環境為 `prod-world-spill` volume 的 `/app/spill`，檔名為建立奈秒加行程內序號，並行寫入不相撞），World 下次啟動、開始服務前依建立順序重放，整檔處理完才刪檔。重放遇資料拒絕，或持久層連續 3 次 panic（與背景寫回同一個門檻 `maxSavePanics`，偶發 panic 同一次重放內重試成功，每次間隔 200ms；重試等待期間 ctx 結束就中止並保留原檔）時，把該玩家異動轉存 `rejected/` 後繼續（資料拒絕記 `gamestore spill replay permanently rejected by mysql; changes quarantined`；持久層連續 panic 記 `gamestore spill replay panicked repeatedly; changes quarantined`，兩種原因用不同的固定訊息，值班可直接依訊息分辨）；其他錯誤中止並保留原檔，World 拒絕啟動。中止時（含隔離檔寫入失敗）原檔會原子改寫成尚未處理的部分（`trimReplayedSpill`，第十輪）：前面已寫入的玩家不再重放、已隔離的被拒異動不會在下次啟動時被重複隔離一份；已寫入本來就冪等，改寫失敗只記 Warn `gamestore spill replay: trim processed records failed; file kept as is`，原檔完整保留，最壞情況是重複隔離。`rejected/` 不會被重放，需人工檢視。既有玩家固定回到資料庫記錄的 World，重放只會覆寫本 World 自己的玩家
- 盤面指令（`runBoardCommand`）有 10 秒處理期限（`BoardCommandTimeout`，`cmd/world/internal/handler/gate/on_board.go`；與玩家資料儲存期限 `PlayerStoreOperationTimeout` 各自獨立，關機時停止盤面工作者的預算沿用它；GM 發道具另有 `grantItemTimeout`，同為 10 秒）：同一玩家分片依序處理，資料庫凍結時不再讓整個分片卡死；逾時回覆失敗、斷路器計一次失敗，連線保留。處理器 panic 由 `callBoardHandler` 接住並轉成錯誤，走同一條失敗分支：回 `FailureResponse`、計 `game_board_command_total{result="error"}`，Error 日誌 `panic recovered`（`msg="world board command"`，欄位 `playerID`、`msgID`、`gameTraceID`、`stack`）；以前只被 shardqueue 接住，Client 卡到逾時、指標不計、日誌無 `playerID`。shardqueue 的 panic 日誌帶 `key`（盤面與持久化 pool 皆為 playerID）。第十二輪 CX-M1 起期限在**排入工作者時**起算（含排隊時間），開始前已過期的指令不執行、直接回失敗，積壓數十秒的指令不會在很久之後才提交。
- 關機順序（`cmd/world/internal/services/run.go`）：PreDrain 依序 `wait persist idle`（等已提交的持久化作業完成，**不關 pool**：drain 期間事件迴圈仍會提交登出等作業，pool 關閉會讓它們退回事件迴圈同步做 Redis／MySQL I/O）→ `wait background` → 寫回玩家資料 → 寫回 Redis 狀態；Drain 排空連線，期間事件迴圈仍處理訊息；PostDrain 先停止事件迴圈與盤面工作者（剩餘時限不足一個盤面指令期限時放寬到一個指令期限；第十二輪起等待逾時就取消盤面工作者持有的中止 ctx，執行中的指令 ctx 跟著取消、排隊中的指令直接回失敗），再等一次背景工作（drain 期間才開始的登入活動寫入），接著 `wait persist`（此時才關閉 persist／writeBack pool 並等排隊作業做完），最後才做最後一次寫回（`FinalizePlayerData`）。`gamestore.Memory` 在 `FlushAllForShutdown` 開始時設 shutdown 旗標，之後的提交（`commitLocked`、`withPlayers`）一律回 `gamestore.ErrStoreShutdown`：晚到的指令不會把異動靜默寫進沒人處理的 pending，擲骰／升級也不會在未持久化時把成功寫進 replay journal（第十二輪 CX-M1）；Cleanup 關閉連線登錄與 Record sink，再由 `RunApp` 的 app shutdown 結束。事件迴圈停止或最後寫回前的任一步逾時，後面的步驟仍照樣執行
- 寫回收尾（`settleFlush`，第十輪）在玩家鎖內處理一次寫回的結果，以 defer 解鎖並兜住 panic：收尾 panic 時鎖一定釋放（否則這位玩家之後的所有操作都會永久阻塞），盡力把取出的異動放回 pending（pending 已有新異動就只記 Error `gamestore settle flush panicked while new changes were pending; flushed changes may be lost`），並回傳 `errSettleFlushPanicked`。`flushPlayer` 本體 panic 由 `flushPlayerRecovered` 轉成錯誤。兩者都計入 `flushPlayers` 的失敗人數，所以關機寫回不會把 panic 的玩家算成成功，會照常走落地分支。
- 最後寫回仍寫不進 MySQL 的異動落地到 `spill_dir`，Error 日誌為 `world shutdown could not write player game data to mysql; spilled to file and will replay on next start`（`players`、`path`）；連落地檔也寫失敗時是固定訊息的 Error `world shutdown lost unsaved player game data`（`players`、`playerIDs`、`batch`／`batches`、`dir`、`err`；超過 500 人時每 500 個 ID 一行、全部列出，第十二輪 TR-L2），代表這些玩家的最後異動已遺失，值班以此搜尋
- 背景寫回連續 panic 3 次（成功或其他錯誤歸零）的玩家走與 MySQL 永久拒絕相同的隔離路徑：轉存隔離檔、清空 pending、常駐資料改從資料庫重載，日誌 `gamestore memory write-back panicked repeatedly; changes quarantined and dropped from pending`（第十二輪 TR-L1；以前當暫時性失敗每秒重試）。登出、委派前的同步寫回（`flushLocked`）比照計次，重放落地檔的 panic 也走同一個門檻（第十三輪）。寫回經斷路器時 panic 以 `circuitbreaker.ErrCallbackPanic` 保留標記，`gamestore` 還原成 `errSavePlayerChangesPanicked`，所以連續 panic 的隔離在正式組裝（持久層包斷路器）下才真正生效；`rejected/` 因此也會收到 panic 造成的隔離資料，用日誌的 `err` 欄位分辨是資料拒絕或 panic。開機重放的隔離現在也累加 `game_player_flush_failures_total`，`GameDataSaveFailure` 告警看得到。關機落地階段取玩家鎖受關機任務 ctx 約束（整個迴圈共用一個期限），取不到鎖的玩家記 Error `gamestore memory shutdown could not take player lock; changes of this player are not spilled` 後跳過
- 關機耗時上限：World 的關機任務依序各自計時（`newShutdownPlan` 登記 12 個任務，「stop board workers」以 `AddPostDrainWithTimeout` 拿一個盤面指令期限 10 秒，其餘各 5 秒；`MaxDuration()` 另加 `RunApp` 的 app shutdown 與等事件迴圈退出的各一次逾時），最壞約 75 秒（契約測試直接斷言等於 75 秒，並補上原本少算的「stop board workers」10 秒；第十一輪）。任務內不得以 `WithoutCancel` 自行延長期限（超出的等待不會計入最壞耗時）；最後寫回的取鎖等待整批共用一個期限，不再逐人各等 6 秒。容器 `stop_grace_period` 必須大於它，否則 SIGKILL 會先於最後的寫回與落地檔而丟失玩家異動，所以 compose 的 World 都設 80 秒（高於 75 秒並留 5 秒餘裕，自動擴縮用 `compose run` 啟動的同樣套用）。其他服務同樣補齊：Gate 75 秒、Central 65 秒、Chat 30 秒、Lobby／Record 20 秒（`compose.full`、`debug`、`core-test`、`prod`）；Gate 的 `drain_timeout` 只套給 drain 任務，其餘任務維持 5 秒，上限 40 秒（`MaxDrainTimeout`），超過在啟動時就被拒絕；要調高須同步改常數與 `stop_grace_period`。各服務最壞耗時另加 debug／tracing 收尾最多 4 秒（`startup.ObservabilityCleanupMax`）。新增關機任務時，各服務 `shutdown_plan_test.go` 的契約測試會斷言最壞耗時小於四份 compose 的 grace，超出餘裕就會失敗；Central、Gate 在事件迴圈停止後會再等一次背景工作（`RunTCPService` 的 `waitBackground`），確保 drain 期間才登記的背景寫入（登出結果、登入 rollback 寫 Redis）在呼叫端關閉 Redis 前完成；關機時也會停止協定檔案記錄器並 flush，最後一段紀錄不會遺失
- 關機期間的背景工作計數（World persist／background、Gate 與 Central 的 `backgroundWg`）用 `appcore.TaskGroup`：`Wait` 進行中仍允許 `Add`，因為 PreDrain 等待期間事件迴圈還會派發登出並提交背景工作，`sync.WaitGroup` 在這個視窗會 panic 並讓該筆寫回靜默遺失。`TaskGroup` 的計數變負（`Done` 比 `Add` 多）會直接 panic，不再靜默吞掉配對錯誤。Gate 關機的 `wait background` 與 World、Central 一樣用 `appcore.WaitContext` 受任務期限約束，背景工作卡住不會擋住後面的 drain 與關閉連線。
- 寫回可安全重試：PvP 結算已存在時略過它的帳本與守方扣款，抽獎紀錄以隨機種子判斷是否已寫入；其餘資料是整列 upsert 或以主鍵去重
- `variable.Service` 不再有自己的待寫快取：`Set`、`Add` 直接寫入記憶體版 GameStore
- 只在登入時呼叫、牽涉封存還原的操作（初始化貨幣、登入活躍）與保留期清除，先寫回並卸載玩家再直接操作資料庫，下次存取重新載入
- 冪等紀錄（Record outbox、GM 發獎、任務事件）先查記憶體中尚未落地的異動，再以主鍵查資料庫
- 資料庫層只剩兩種職責：`PlayerPersistence`（整份載入與批次寫回）與 `InnerStore`（Record outbox、封存與保留期、登入活動、初始金幣）。兩者經 `NewCBStores` 包裝並共用同一個斷路器：連續 5 次基礎設施錯誤後，載入、寫回與委派呼叫都立即失敗，業務錯誤不計入；寫回失敗時異動保留在記憶體，下個週期重試。道具、變數、商店、盤面、抽獎、任務等玩家資料的讀寫只有記憶體實作，`mysqlstore.MySQL` 不再提供對應方法；整合測試以寫穿的 `gamestore.NewWriteThroughMemory` 驗證資料庫狀態
- 跨 World 的 PvP 金幣結算在守方不在本 World 時，以資料庫金幣計算扣款，同一守方在一兩秒內被多場結算時帳本可能多記扣款；已知限制與處理選項見 `90-參考附件/方案草稿/跨服戰鬥與金幣結算方案.md` 第 11 節
- `player_variable` 不再因數值等於 Default 而刪列：「沒有列」只代表從未寫入
- 玩家只能由所屬的 World 存取；`tools/` 底下會直接改玩家資料的工具（變數遷移、拓撲基準等）必須在 World 停止時執行，否則會被記憶體中的值覆寫

### PvP 金幣收件匣

- 金幣以背包道具 `SharedItemID_Gold`（`player_inventory_item.item_id = 1`）保存，數量上限為 int32；結算後攻方超過上限時拒絕結算
- 攻方一定常駐在發起結算的 World；守方也常駐在同一個 World 時，依玩家 ID 順序同時鎖定兩人，在記憶體內結算
- 守方不在本 World（其他 World 或離線）時，以資料庫中的守方金幣計算，並寫入 `player_gold_adjustment`（隨攻方的寫回一起落地）
- 守方所屬的 World 在載入玩家或每秒輪詢時套用並刪除調整，金幣不低於 0，同一筆調整只套用一次；輪詢對玩家鎖用 `TryLock`，鎖被占用（例如載入快照或委派資料庫期間）的玩家不阻塞整體寫回，其調整連同讀取當時的載入世代暫存到下一輪再套用，世代已變（之後重新載入的快照已含該批）則不重複套用
- 結算紀錄 `combat_gold_settlement` 與帳本 `wallet_ledger` 隨攻方寫回落地；重送同一結算 ID 時回放，不重複入帳
- 守方金幣可能落後所屬 World 最多一個寫回週期

### World Archive

位置：

- MySQL `player_profile_archive`
- MySQL `player_inventory_item_archive`
- MySQL `player_variable_archive`
- MySQL `player_state_archive`

用途：

- 封存長期不活躍玩家的主檔、道具、變數、盤面、道路星星、建築、抽獎狀態、設定版本與未過期玩家效果
- 讓上列封存範圍的 live 表只保留活躍玩家，降低主表膨脹；任務進度（`player_mission_state`、`player_mission_claim`、`player_mission_event`）、抽獎紀錄與商店互動不搬進封存，封存玩家的這些資料仍留在 live 表，任務三表在帳號清除時才刪除（`player_mission_event` 以 `player_id` 刪除，靠 `idx_player_mission_event_player` 索引；既有大庫須先手動建，見[Docker生產部署](../30-部署與開發/Docker生產部署.md#升級時需手動建立的索引與欄位變更)）
- 玩家回來時可自動 restore 回 live 表

特性：

- 以 `player_profile.updated_at` 判斷是否超過 90 天未活躍；登入時更新活躍時間，常駐期間週期寫回每 10 分鐘（`touchInterval`）才帶一次更新，登出與委派前的同步寫回一律帶
- 等 Central 第一次對時（`FirstTimeSync`）後立即執行一輪，之後每日執行（對時前遊戲時鐘等於主機時鐘、不可信，所以首輪等對時而不是略過），按玩家在同一筆 MySQL 交易中搬移可恢復的遊戲狀態
- 候選依 `(updated_at, player_id)` 升序、以游標分頁讀取；最舊一批若全是本 World 常駐玩家（被跳過），會繼續往後讀到湊滿批次大小，不讓後面的玩家永遠輪不到封存
- 尚未結算的戰鬥會延後封存；封存時停用戰鬥候選快照，登入載入後重新發布
- 登入時先查正式主檔；主檔不存在才查封存並在同一筆交易中恢復，其他遊戲操作不查封存
- 保留期（第十五輪起）：`record_outbox_event` 已送出列（`sent_at` 非空）預設保留 30 天、`combat_session` 已結算列（`settled_at` 非空）預設保留 90 天，由 World 啟動後延遲 5 分鐘（`retentionStartDelay`，避開重啟後的登入潮，不與玩家載入搶資料庫）首輪、之後每日分批清理（`gamedb.RetentionPurger`，`DELETE ... ORDER BY sent_at／settled_at LIMIT 1000`，截止點用資料庫 `NOW(3)`；每批獨立在 ReadCommitted 交易內執行、單批時限 30 秒（預設的 RepeatableRead 會對掃過的區間加間隙鎖，擋住同表並行 INSERT），滿批後停 100ms 再刪下一批；多個 World 共用資料庫時以 MySQL `GET_LOCK` 互斥，取不到鎖的略過）。World 設定檔 `retention.outbox_sent_days`、`retention.combat_session_days`：未設定用預設值，`0` 表示永久保留，其餘不得小於 7（`gamedb.MinRetentionDays`），寫錯拒絕啟動。下限遠大於 request journal 的 TTL（`ReplayTTL`，2 分鐘），因為 outbox 列兼作操作 ID 的冪等鍵（`RecordOutboxExists`），列被刪後同一操作 ID 的重送就查不到；設定時保留期也要大於任何來源（Client 重送、GM 發放佇列）可能重送同一操作的期限。未送出與死信列不刪。另清兩類成長表：①未結算的 `combat_session`（`settled_at` 為 NULL 且 `expires_at` 已過期 N 天，預設 30，`retention.unsettled_combat_session_days`；已結算列照上面的 90 天），逾時未提交的場次不會自己消失；②`player_mission_event`（依 `applied_at`，預設 30 天，`retention.mission_event_days`，下限為 max(7, 任務補償回看範圍 `mission.RepairWindow` 的天數)，目前是 7；去重列要活得比補償回看與 outbox 冪等列久，所以**兩者皆大於 0 時實際刪除天數取 max(`mission_event_days`, `outbox_sent_days`)；任一為 0（永久保留）就不清任務事件**，`outbox_sent_days` 設 0 時任務事件也不清）。每輪結果計入 `game_retention_ops_total{task,result}`，整輪失敗（取不到鎖以外的連線錯誤）記 Warn `retention purge failed`（`err`，指標 `task="round"`），單一作業失敗記 Warn `retention job failed`（`job`、`deleted`、`err`），有刪除列的成功輪次每個作業記一筆 Info `retention purged`（欄位 `job`、`deleted`，只在刪除數大於 0 時記）；`task` 值為 snake_case：`outbox`、`combat_session`、`unsettled_combat_session`、`mission_event`，另有 `player_archive`（玩家封存）、`record_table`（Record 日表），日誌的 `job` 鍵用同一組名稱；告警 `GameRetentionPurgeFailing`（見[指標面板](../20-排障與監控/指標面板.md)）。`combat_session`、`unsettled_combat_session`、`mission_event` 依賴下列索引：索引不存在時**跳過該段清理並計一次 error**（觸發告警），日誌帶手動建索引的 `ALTER` 提示，避免每批 DELETE 全表掃描持鎖。`record_outbox_event` 的刪除沿 `idx_record_outbox_due` 首欄 `sent_at`；`combat_session` 新增複合索引 `idx_combat_session_settled_expires (settled_at, expires_at)`（已結算清理走首欄 `settled_at` 範圍；未結算清理走 `settled_at IS NULL` 等值加 `expires_at` 範圍並沿索引排序，兩種清理共用；不再有 `idx_combat_session_settled_at`、`idx_combat_session_expires_at` 兩個單欄索引），`player_mission_event` 新增 `idx_player_mission_event_applied_at`，既有大庫須先手動建（見[Docker生產部署](../30-部署與開發/Docker生產部署.md#升級時需手動建立的索引與欄位變更)）
- 本輪**不清理**的保留表與成長：`player_lottery_draw`（每次抽獎一列，隨抽獎次數線性成長）、`gm_grant_record`（每筆 GM 發放一列，量小）、`player_shop_interaction`（每次商店互動一列）、`wallet_ledger`（每筆金幣異動一列，帳目性質，刪除前需財務／稽核決策）、`combat_settlement_notification`（每場戰鬥結算一列）。這些表隨營運時間無上限成長，會拉長停機備份時間與佔用 buffer pool；各表的保留期與是否改為歸檔，留待後續決策
- 盤面子表（`player_board_road_star`、`player_board_building`）沒有資料庫外鍵，與其他帶 `player_id` 的表一致，一致性由應用層保證：封存、還原、帳號清除都在同一筆交易內以 `player_id` 整批處理（來源是 `playerTables`），不依賴刪除或寫入順序；保存盤面時在同一交易內以 `(player_id, board_id)` 重建該盤面的道路星星。SQL 版與記憶體版都不檢查建築所屬盤面列是否存在。若資料庫遺留沒有父列的子列，封存會一併搬走並還原，帳號清除前檢查會因 live 表非空而不清除，需人工確認後刪除

### Record Daily Tables

位置：

- MySQL `record_events_YYYYMMDD`

用途：

- 記錄一般操作流水
- 依事件發生日切日表，降低單表膨脹；日期一律以 UTC 計（與行程時區無關），表名、`Latest` 回看的 31 張日表範圍與寫入時間下界都用 UTC 日期，非 UTC 主機不會與別台差一天
- 預建與 `KeepTablesAhead` 只建立不存在的日表（每張 30 秒期限），既有日表不跑 `AutoMigrate`，結構變更走 PJA-Database plan；`AUTO_MIGRATE_DISABLED=true` 時 Record 完全不建表，寫入前只查分表是否已由外部預建（存在即放行並快取，不存在回暫時性錯誤重試）
- `Latest` 查詢時會往前掃最近 31 張日表，直到湊滿 `limit` 或掃完保留窗
- `LatestByView(view=online)` 只掃最近 7 張日表，供近線客服/營運查詢；`view=archive` 保留 31 張日表的完整查詢路徑

特性：

- 寫入時以 `occurred_at` 決定落哪一天的表
- 啟動時 `store.New(ctx, db, autoMigrate)`（型別 `store.Events`）預先建立最近 31 天與明天的日表，ctx 允許上層控制 migration 超時；之後 `KeepTablesAhead` 每小時確保今天與明天的日表存在，跨日後第一筆寫入不必在熱路徑跑 DDL
- 寫入路徑的 `ensureTable` 降級為冷路徑保險（預建失敗或事件日期超出預建範圍時才觸發）
- **保留政策**（`table_retention_days`，Record 設定檔頂層鍵）：`KeepTablesAhead` 每小時順便列出 `record_events_YYYYMMDD` 並 DROP 超過保留天數的日表。預設 90 天；`0` 表示永久保留（不清）；不得小於查詢回看的 31 天（小於會讓 `Latest` 回看窗讀不到表），寫錯或小於下限 Record 拒絕啟動。表名由解析出的日期重新格式化後才 DROP，不使用外部字串；每張表獨立判斷期限，單張失敗只記 Warn、不影響其他張。`AUTO_MIGRATE_DISABLED=true`（分表由外部工具管理）時不執行任何 DDL，包含 DROP，過期分表要由外部流程清理。要保留更久的事件流水，先調高 `table_retention_days` 或自行歸檔再縮短
- 近線查詢與 archive 查詢要走不同 view，不要再共用同一條逐表掃描路徑

### GM Grant Ledger

位置：

- MySQL `gm_grant_record`

用途：

- 記錄 GM 發道具操作的冪等鍵
- `AddInventoryItem` 以 `GrantRecordExists` 查冪等紀錄（記憶體 pending 與主表），避免重複發放
- World 套用發放後先以 `Memory.FlushPlayer` 把該玩家**立即寫回**，成功才 ack（從 Redis processing 清單 `LREM`）；寫不進去就回錯走重試，靠 `gm_grant_record` 冪等不重複發放。處理失敗或 Redis 出錯後 worker 的重試等待改為指數退避（每個 worker 各一份，1 秒起倍增到 30 秒、±30% 抖動，成功即歸零；Warn 只記連續失敗的第一次與間隔到頂之後），Redis 長時間故障時不再每秒一行 Warn，多個 worker 與多台 World 也不會同一秒打回剛恢復的 Redis。原本只進記憶體 pending 就 ack，World 在下次寫回前當機時這筆發放會從 Redis 與資料庫一起消失；現在是 at-least-once，代價是每筆發放多一次單人寫回交易，GM 發道具吞吐估算要以寫回交易計（行為變更）

### Redis PlayerStore

Redis player store 是 `World` 在線狀態的恢復輔助來源，不是最終真實來源。

寫入時機：

- 登入：`persistLoginPlayerStateAsync` 非同步經 `persistPool` 寫入單一玩家；佇列滿時會被
  丟棄（`PersistPoolDiscardTotal` 有監控）。`persistPool` 依 `playerID` 取餘數分片，每個 worker
  專屬一條佇列，同玩家的 Save 與登出 `DeletePlayerStatesIfOffline` 依序執行，不會被搶跑而讓 Redis 留下已登出玩家的狀態。
- 週期補寫：`RunPlayerStateFlush` 每 `playerStateFlushInterval`（5 分鐘）把在線玩家
  補寫一次，收斂上面被丟棄的部分。補寫每 256 位（`playerStateFlushChunk`）一批，每批寫入前重查玩家仍在記憶體且仍綁同一個 Gate，
  已登出或已轉走的略過，避免用舊快照復活已刪的在線狀態；重查到寫入之間仍有毫秒級視窗，殘留靠 24 小時 TTL 與對帳收斂。
- 優雅關閉：`FlushPlayerStates` 在 PreDrain 階段把全部在線玩家寫回。
- 心跳：`RefreshBatch` 只刷新既有 key 的 TTL，不會補上從未寫入的玩家。

適用於：

- `World` crash/restart 後的恢復起點

不適用於：

- 直接判定玩家仍在線
- 跳過 Gate session 驗證直接保留玩家

原因：

- Redis 可能殘留舊資料
- Gate session 可能已失效
- 玩家可能已斷線但 World 尚未清乾淨

## 可重建與不可重建資料

### 可重建

- Central memory online routing data
- Gate session data
- World memory online users
- Redis player store 內容

意思是：

- 這些資料可以透過重新登入、重新連線、恢復校驗逐步修正
- 短時間不一致是可接受的，但最終要被清理

### 不可隨意重建

- MySQL `user` table 的 `account/player_id/world_id`

意思是：

- 這是持久資料
- 不應因為短暫斷線或重送就重設

## 寫入順序與一致性原則

### Login

一致性原則：

- 先確立 `Central` 的帳號/World 路由，再讓 `World` 接受登入
- `Gate` 只在 `World` 成功回覆後才把 session 從 `pending_login` 轉成 `logged_in`

目前順序：

1. Gate 建立 pending session
2. Central 查 MySQL 或建立新 user record
3. Central 更新 memory route
4. Central 將登入轉送給 World
5. World 決定接受或拒絕
6. Gate 成功時 bind session；失敗時清掉 pending session
7. World 拒絕時，Gate 反向通知 Central rollback

實際含義：

- `Central` 可以比 `World` 早一步知道該玩家要去哪個 World
- 但只有 `Gate` 收到成功回應後，玩家才算真正登入完成
- `Central` 斷線後，Gate 會把綁在死 central 的 session 一起遷走，包含 `pending_logout`，避免路由卡在死節點
- `Gate` 重連後同步 `SyncUsersGateToCentral` 時，`GateID` 不能是 0；空 gate id 會讓 Central 寫出壞路由；`Routes` 不是整筆（16 位元組的倍數）時解碼整則拒絕，不處理半筆

### Logout

一致性原則：

- 先把 Gate session 轉成 `pending_logout`
- 再沿 `Gate -> Central -> World` 鏈路清理
- 最終由 Gate 回到 `disconnected`

目前順序：

1. Gate 將 session 從 `logged_in` 轉為 `pending_logout`
2. Central 刪除 memory route
3. World 清理該玩家的衍生索引（頻道已移除，無頻道成員需清理）
4. World 刪除 memory user 與 player store
5. Gate 刪除本地 user/session

實際含義：

- 登出成功的最後一跳是 Gate 清理本地狀態
- 若鏈路中斷，`pending_logout` 會由 sweeper 清掉
- 若 `Central` 斷線，`pending_logout` 的 `sessionCentral` 也會一起改掛新節點，不會留死路由
- 遊戲進度寫回為異步操作，World 崩潰時遺失最後一次寫回之後的異動（見「最長遺失窗」）
- `Central` 登出若因 `World` 不在而失敗，會把同一個 request 的失敗結果寫進 replay cache，避免重送時語意變成 `SessionExpired`
- `Central` 登出若 `Services` 缺席，也要先清掉本機 user 並寫入 `AuthServiceUnavailable` 的 replay cache，不能留下 ghost state

### World Recovery

一致性原則：

- Redis restore 只提供候選集合
- 最終是否保留玩家，以 Gate 驗證結果為準

目前順序：

1. World 從 Redis 還原玩家狀態到 memory
2. 等待 `WorldRecoveryGracePeriod`
3. World 檢查對應 Gate socket 是否存在
4. 若存在，主動送 `ValidateWorldToGate`
5. Gate 依 session 與 `world_id` 回覆成功或 mismatch
6. World 對 mismatch 或無 Gate socket 的玩家執行清理
7. `AuditSnapshotRequest` 在 `App` 暫時不可用時，仍回空 snapshot，讓 Central 不用等 timeout 才知道資料面失聯

### World Crash Window

這段是 `World` crash 後到 `restore + validate + cleanup` 完成前的可接受不一致窗。

這段期間的裁決順序：

1. `World` memory 先失效
2. Redis player store 提供恢復候選
3. `Gate` session / validation 決定玩家是否真的保留

可丟資料：

- `World` memory online state
- 尚未通過 validation 的 Redis restore 候選

不可丟資料：

- MySQL `user` / `world_id` 對照
- 已成功寫回 MySQL 的遊戲進度

最長遺失窗：

- 道具、盤面、金幣與其他玩家遊戲資料：write-behind，World 崩潰時最多遺失約 1 秒的異動（變數也直接寫入記憶體版 GameStore，沒有另一層快取）；這是刻意的取捨，遊戲資料不需要金融等級的保證，事後以 Record 紀錄查證並補償
- 擲骰以 `request_id` 去重：Client 沒收到回應而重送時回放原回應，不會多擲一次；建築升級同理。回放交給呼叫端的位元組必須是複製出來的：回應切片會被池化的 `ClientBoardPayload` 接手並被下一則指令覆寫，直接回傳 journal 內的切片會讓快取被蓋掉（`TestRollDiceReplaysSameRequestIDWithoutRollingAgain`、`TestUpgradeBuildingHandlerReplaysResentRequest` 鎖住這點）
- 在線狀態：最壞只允許在 `WorldRecoveryGracePeriod` 內暫時不一致

收斂責任：

- `lifecycle.RestorePlayers`（`cmd/world/internal/lifecycle/recovery_restore.go`）只做候選還原
- `lifecycle.ReconcileRestoredPlayers`（`recovery_reconcile.go`）只做驗證與清理

## 短暫失聯與長時間失聯

目前系統將跨服務斷線分成兩類：

### 短暫失聯

條件：

- 斷線時間仍在 ServiceDisconnectGracePeriod 內

處理原則：

- 不立刻刪 Gate session
- 不立刻刪 World memory user
- 允許服務在短時間內重新連回並延續原有在線狀態

### 長時間失聯

條件：

- 超過 ServiceDisconnectGracePeriod 仍未恢復

處理原則：

- Gate 會清掉對應 World 的本地 user/session，並通知 Central 收斂 route
- World 會清掉對應 Gate 的玩家與 observer 狀態
- 此時才正式把狀態視為失效，而不是暫時抖動
## 允許的不一致

目前系統允許短時間存在以下不一致：

- Central memory 已有玩家，但 Gate session 還在 `pending_login`
- World restore 已載入玩家，但 Gate 尚未完成 validation
- pending logout 尚未完全傳遞到 World

這些不一致存在的前提是：

- 有 TTL 或後續鏈路會收斂
- 不會被當成永久真實狀態

## 不允許的不一致

以下狀況應被視為異常並最終清理：

- Gate session 已失效，但 World restore 後仍長期保留玩家
- World 已刪除玩家，但 Central 長期保留過期 route
- MySQL `world_id` 與 Central/World 長期分裂

目前的收斂手段：

- Gate session sweeper
- login replay cache
- World recovery validation
- Gate / World / Central 斷線後的清理路徑

## 故障場景下的判斷原則

### Gate 斷線

- Gate session 視為失效；Central 與 World 先給 30 秒寬限（`appcore.ServiceDisconnectGracePeriod`），寬限內同 ID 重連以玩家快照對帳，不清玩家
- 寬限逾期仍未重連，Central / World 才清理該 Gate 代理的玩家（細節見[連線與登入流程](./連線與登入流程.md#central-遇到-gate-斷線)）

### Central 斷線

- 既有 Gate pending login 應失敗返回
- 玩家可在 Central 恢復後重新登入
- MySQL 持久資料不應受影響

### World 斷線或重啟

- World memory 視為失效
- Redis player store 僅作恢復候選
- 是否保留玩家，以 Gate validation 結果為準

## 實務規則

之後若新增狀態資料，建議先回答 4 個問題：

1. 這份資料的 source of truth 是哪裡
2. 這份資料能不能被重建
3. 如果不同服務看到不同版本，最後由誰裁決
4. 故障後要靠什麼機制收斂

回答不清楚時，不應直接把新狀態塞進 memory 或 Redis。
