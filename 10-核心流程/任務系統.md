# 任務系統

玩家在 World 中接取、進行與完成任務，系統支援任務進度追蹤、自動啟用、失敗冷卻、周期重置與領獎機制。

## 架構總覽

任務系統由設定層、狀態層與事件層組成：

- **設定層**：從 PJA-Config 載入任務定義、獎勵、周期與條件
- **狀態層**：玩家任務進度、待領獎勵與冷卻狀態儲存於 MySQL
- **事件層**：道具使用、經過起點等玩法結果觸發任務進度增長；在產生結果的同一個 request 內同步推進進度，不經訊息佇列

## 任務定義與驗證

任務設定由 `PJA-Config` 的 `Mission` 提供，World 啟動時驗證：

- 必要欄位：任務 ID、名稱、類型、目標
- 可選欄位：前置條件、固定獎勵、可選獎勵、顯示欄位、規則版本
- 驗證項目：
  - 引用的條件樹必須存在且有效
  - 引用的道具必須支援任務事件（`IsUsableFromInventory`）
  - 獎勵分配與領獎冷卻時間相容性

## 任務週期與重置

任務支援多種週期重置策略。每個任務在 PJA-Config 的 Mission 表以 `ResetPeriod` 指定週期（`interval` 週期的長度看 `ResetIntervalSeconds`），不是 World 設定：

| 周期類型 | 配置 | 重置時機 | 用途 |
|---------|------|--------|------|
| 無重置 | `none` | 不自動重置 | 一次性任務 |
| 每日 | `daily` | 每日換日時刻 | 日常任務 |
| 每週 | `weekly` | 每週一換日時刻 | 週任務 |
| 每月 | `monthly` | 每月 1 日換日時刻 | 月任務 |
| 全服固定間隔 | `interval` | Mission 表 `ResetIntervalSeconds` 指定的間隔 | 固定間隔任務 |

World 設定只決定換日時刻：`mission_reset.timezone`、`mission_reset.hour`、`mission_reset.minute` 決定，`cmd/world/run.go` 以 `internal/gamecore/mission/reset_schedule.go` 的 `NewResetSchedule` 建立重置排程。全 Server 共用的遊戲日設定（`day_reset`、`internal/gamecore/kernel/gameday`）尚在未合併的 `feat/online-stats` 分支，合併後任務與玩家在線統計的日、週、月週期改用同一個設定，見[玩家在線統計](玩家在線統計.md)。

周期重置、領獎期限、失敗冷卻與自動領獎到期都以遊戲時間（Central 校正時鐘，`App.GameNow`）判斷；同一則盤面或任務指令只取一次 now，規則判斷與任務事件時間戳共用，見[共用邊界](../00-導讀/共用邊界.md#時間規則)。

## 任務生命週期

```
未啟用
  ↓ 手動接取或自動條件成立
待進行 ← 條件檢查失敗時自動拒絕
  ↓ 進度達標
待領獎
  ↓ 玩家手動領獎或自動領獎
完成 ← 領獎逾期時進入冷卻
  ↓ 冷卻期滿後周期重置
未啟用（下一輪）
```

### 手動接取

1. 玩家發送 `ActivateMissionCommand`
2. World 檢查玩家狀態、任務前置條件與啟用條件
3. 接受或拒絕；成功時記錄接取時間與進度

### 自動啟用

World 在玩家登入或周期重置後檢查所有任務的自動啟用條件：

- 依玩家當前變數與盤面狀態評估條件
- 條件成立時自動進入「待進行」狀態
- 條件失敗時保持「未啟用」或自動返回「未啟用」

### 進度與事件

進度由以下事件增長：

- **道具使用**：道具扣除成功後，World 在同一個 request 內以事件 ID `item-use:{playerID}:{requestID}` 推進 `ItemUseCount`；自動領獎發出的道具附在 `UseItemResultEvent.ChangeSet`
- **經過起點**：擲骰移動經過指揮中心（`Start` 格）時，World 在盤面保存後以事件 ID `start-pass:{playerID}:{requestID}` 推進 `StartPassCount`（`TargetId` 必須為 0，進度增量為本次經過次數）；自動領獎發出的道具進 `RollDiceResultEvent` 的背包狀態
- **盤面事件**：擲骰、建築、抽獎等觸發的事件
- **時間戳**：事件發生時間用於版本相容性判斷

事件 ID 與同一交易寫入的 `record_outbox_event` 列相同。進度與事件去重（`player_mission_event`，以事件 ID 加任務 ID 為鍵）在同一份玩家異動中保存，同一請求重送不重複累加。去重在玩家交易內以單一 `LoadMissionEvents` 查詢（原先玩家鎖外的預查 `mission_event_prefetch.go` 已刪除），避免事件仍在寫回中時被重複套用。同步推進失敗只記錄，不翻轉已成功的道具使用或擲骰，漏掉的進度由下文補償處理。

### 進度相容性

任務升級時（門檻調高、顯示欄位變更），系統檢查既有進度是否仍有效：

- **門檻調高**：允許平行任務目標的門檻調高，玩家既有進度保留
- **版本判斷**：以設定版本對比玩家記錄的任務規則版本；還原任務狀態、事件與領獎路徑共用同一判斷（`missionVersionAllowed`），保存版本為空字串一律視為不相容
- **舊事件相容**：設定未變的積壓事件可繼續用於已啟用任務

### 領獎機制

#### 自動領獎

World 定期檢查是否有待領獎的任務：

1. 檢查獎勵是否逾期（`missionClaimExpired`：到期時間當下起即略過，逾期紀錄不再檢查版本相容）
2. 驗證任務版本相容性
3. 成功則自動發放固定獎勵
4. 失敗則進入失敗冷卻

#### 手動領獎

玩家發送 `ClaimMissionRewardCommand`：

1. 檢查任務是否待領獎
2. 驗證版本相容性與時間限制
3. 發放固定獎勵與執行可選獎勵（可選獎勵允許玩家於領獎時選擇）
4. 成功時記錄領獎時間

#### 領獎逾期與冷卻重開

- 待領獎超過逾期時刻時，任務進入失敗冷卻
- 冷卻期滿後，系統在下次周期重置時重新啟用或等待玩家手動接取
- 冷卻期間若發生周期重置，冷卻被重置

### 失敗冷卻與重試

任務失敗（自動或手動領獎失敗）時進入冷卻：

- **自動失敗**：事件觸發但條件失敗時冷卻
- **手動失敗**：玩家接取後未在期限內完成時冷卻
- **冷卻時間**：可由任務設定或全局設定指定
- **重試**：冷卻期滿後由自動啟用流程或玩家手動接取重試

## 完成次數上限（MaxCompletion）

`MaxCompletion` 為 0 表示不限次數。大於 0 時，計算方式依任務是否週期重置而定：

| 任務類型 | 上限的計法 | 範例 |
|---------|-----------|------|
| 週期重置（結束模式為下一重置週期重開，且 `ResetPeriod` 非 `None`） | 每個重置週期內的完成次數，進入新週期歸零 | 每日任務填 1：每日最多完成 1 次，隔天可再做；填 2：每日最多 2 次 |
| 其他（不重置） | 終身累計完成次數 | 填 1：整個遊戲只能完成 1 次 |

- 週期重置任務完成後，若本週期尚未達上限（`MaxCompletion` 為 0 即無上限），同週期立刻開下一輪。
- 累計完成次數（回傳 Client 的 `CompletionCount`）永遠保留，與本週期次數分開保存。

## 超額進度與跨輪保留

任務支援超額進度跨輪保留：

- 進度達標後仍可繼續增長（例如「擊敗敵人 3 次」達標後仍可增長到 5 次）
- 周期重置時，超額進度部分保留到下一輪
- 下一輪進度初值為上輪的超額部分
- 允許玩家在同一周期內達成多輪的進度需求

## 同步套用與補償

任務進度在玩家 request 內同步套用，不依賴 RabbitMQ，玩家用完道具立即看到進度與獎勵：

1. 玩法結果保存後，`mission.ApplyGameplayEvent` 把事件分派給所有命中的任務，進度更新與去重在同一份玩家異動中完成
2. 任務完成且為自動領獎時，同一次呼叫補發獎勵並回傳，由來源 request 的回應附上
3. Record outbox 只負責 Record 分析投遞、冪等鍵（`operation_id`）與流向帳；任務進度不再依賴它投遞
4. 任務事件沒有 World 歸屬問題：事件在持有該玩家記憶體資料的 World 內處理，不會有別台 World 載入並寫回而互相覆蓋

### 補償

同步推進失敗（例如資料庫暫時不可用）時，事件仍在 `record_outbox_event`，但 `player_mission_event` 沒有對應列。玩家下次載入盤面時，`mission.RepairPlayerEvents` 用流向帳補套用：

- 範圍：該玩家 7 天內、類型為 `record.world.item.use` 或 `record.world.start.pass`、且 `player_mission_event` 沒有該 `event_id` 已處理標記（`mission_id = 0`）的 outbox 列，單次最多 200 筆；事件對所有命中任務套用成功後才寫標記。玩家常駐記憶體時，標記列與補償套用的進度加進同一筆玩家交易、隨寫回一起提交（不再直接寫 MySQL），寫回前當機不會留下「已標記卻沒有進度」而永久漏補；玩家不常駐時才直接交給 MySQL
- 沒命中任何任務的事件也會列出，補套用時是 no-op
- 設定版本不相容時拒絕補套用並記錄，等待遷移；單筆失敗不中斷其餘事件；內容不合法（未匯出的 `errInvalidRecordEvent`，包裝 `errInvalidInput`）的事件重試不會成功，記錄後直接標記已處理，不再佔住補償批次；暫時性失敗仍不標記、回傳錯誤
- 同一玩家的所有命中任務在一筆玩家交易內分派（`ExecutePlayerMissionEventsWithView`），去重只查一句 `LoadMissionEvents`；單一任務失敗只回滾它自己的事件紀錄、狀態與待領獎勵，其他任務照常提交。自動補發獎勵中途失敗時，已入帳的獎勵仍回報給呼叫端
- 查詢由 `gamestore.ListUnappliedMissionOutbox` 提供，只看已落地的列；補償失敗只記錄，不影響載入，並撤銷已補償標記（`GameStore.ReleaseMissionRepair`），下次載入再重試

人工排查漏記（與 `ListUnappliedMissionOutbox` 同一判斷：沒有已處理標記 `mission_id = 0`（`MissionEventHandledMarker`）的事件）：

```sql
-- @game_now 帶入 World 的遊戲時間（UTC，取得方式見下），不要用資料庫 NOW()
SET @game_now = '2026-10-14 12:00:00';
SELECT o.operation_id, o.player_id, o.event_type, o.created_at
FROM record_outbox_event o
LEFT JOIN player_mission_event handled
  ON handled.event_id = o.operation_id AND handled.mission_id = 0
WHERE o.event_type IN ('record.world.item.use', 'record.world.start.pass')
  AND handled.event_id IS NULL
  AND o.created_at >= @game_now - INTERVAL 7 DAY
  AND o.created_at < @game_now - INTERVAL 1 MINUTE
ORDER BY o.created_at;
```

時鐘差異：

- `record_outbox_event.created_at` 由 World 寫入，取的是遊戲時鐘：記憶體交易 `playerTx.addOutbox` 以 `tx.now` 補值（`gamestore.Memory.SetNow(baseApp.GameNow)`），留空時 gorm `autoCreateTime` 取 `db.NowFunc`，而 `cmd/world/run.go` 的 `useGameClock` 已把它設為 `GameNow`
- `GameNow` 是 Central 校正時鐘：World 主機牆鐘加上 TimeSync offset（逐步修正、只前進）；資料庫 `NOW()` 是 MySQL 主機時鐘（且受連線時區影響），兩者可能差數秒以上，直接比會誤判邊界上的事件
- 取得遊戲時間：World `/metrics` 的 `game_clock_offset_seconds`（Central 時間減本機牆鐘，單位秒），遊戲時間 ≈ World 主機現在時間 + 該值；精度要求不高時也可用 Central 主機時間。時間欄位一律以 UTC 寫入（`pkg/mysql` 強制 `dsn.Loc = time.UTC`），`@game_now` 也要帶 UTC
- 補償本身的窗口 `now - 7 天` 也是以 World 遊戲時間計算（`RepairPlayerEvents` 的 `now` 參數），上面的 7 天條件與它對齊

### 已移除：任務佇列

任務進度改為在玩家 request 內同步套用後，排空舊佇列的過渡消費端（`cmd/world/internal/missionqueue`、`services/mission_consumer.go`、`DataConfigOptions.MissionMQ`）已於 2026-10-08 移除。

維運待辦：刪除 RabbitMQ 佇列 `mission.events`、`mission.events.<WorldID>`、`mission.events.dead`；durable 佇列綁著 exchange 沒有消費者會持續累積。

## 訊息與指令

### 任務列表

登入與 `LoadPlayerResponse` 不帶任務資料；Client 以 `ListMissionsCommand` 查詢，`ListMissionsResultEvent` 回傳：

- 當前周期的任務列表（接取狀態、進度、待領獎勵；`MissionStateData`）
- 待領獎勵詳情與逾期時刻（`MissionPendingClaimData`）

### 主要指令

| 指令 | 發起者 | 用途 |
|------|-------|------|
| `ActivateMissionCommand`／`ActivateMissionResultEvent` | Client／Server | 玩家手動接取任務與結果 |
| `ClaimMissionRewardCommand`／`ClaimMissionRewardResultEvent` | Client／Server | 玩家手動領獎與結果 |
| `ListMissionsCommand`／`ListMissionsResultEvent` | Client／Server | 查詢任務列表與待領狀態 |

進度增長沒有獨立的協定訊息：在處理道具使用、擲骰等請求時同步套用；`UseItemResultEvent`、`RollDiceResultEvent` 不帶任務狀態（只帶自動領獎發出的道具），任務進度由 `ListMissionsResultEvent` 取得。
