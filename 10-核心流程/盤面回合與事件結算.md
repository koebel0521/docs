# 盤面回合與事件結算

## 流程總覽

玩家擲骰後，World 依盤面格子與事件設定建立本回合結果，並在同一個保存流程中套用可結算效果：

```text
擲骰
  → 判定落點與盤面事件
  → 驗證設定與玩家條件
  → 執行抽獎／建築／研究／生產／戰鬥效果
  → 原子保存玩家盤面、資源、物品與抽獎狀態
  → 回傳盤面事件與獎勵
```

事件結果由 Server 產生，Client 只負責顯示演出與結果。

一則盤面指令只在建立請求時取一次遊戲時間（Central 校正時鐘），骰子懶恢復、扣骰、效果解析、任務事件與自動領獎共用同一個 now，見[共用邊界](../00-導讀/共用邊界.md#時間規則)。

## 抽獎

抽獎設定由 `Shared.Lottery` 載入並在 World 啟動時驗證。每個抽獎群組可設定：

- sequential 或 weighted random 抽取。
- 抽取次數、條件 ID、獎勵數量與單項最大抽取次數。
- 直接發放物品，或巢狀呼叫另一個抽獎群組。
- 無重置、有限物品耗盡重置、每日重置（以遊戲時間判斷，World 抽獎服務注入 `App.GameNow` 與共用的 `gameday.Schedule`：每日重置依 `day_reset` 設定的遊戲日換日，未設定時 UTC 00:00，與任務同一個遊戲日；`gameday.Schedule` 是 `worldlottery.New` 的必填位置參數，沒有隱含預設；抽獎服務的 `Draw`／`DrawMany`／`Choose` 收遊戲日，`DailyResetDate` 存遊戲日日期的 UTC 0 點）。

設定載入時會拒絕未知群組、循環引用與超過巢狀深度的設定。條件由玩家變數與條件系統評估；條件不成立的項目不參與抽取。

每次抽獎進入群組時的規則（`internal/gamecore/lottery/lottery.go` 的 `drawInto`）：

- `Probability` 為 0 的項目是必給：條件成立且仍可抽的每一項各發一次，不佔 `Times` 名額，sequential 與 weighted random 群組都一樣。
- `Probability` 大於 0 的項目最多抽 `Times` 次，沒有候選時提早結束：
  - sequential 群組：依 `SubID` 順序取第一個仍可抽的項目，不看機率值；限量項目抽完後才輪到不限量的項目。指揮中心每日獎勵即依此每次經過起點發下一項，五項都拿完後改發隨機獎勵。
  - weighted random 群組：依 `Probability` 權重隨機抽一項。
- `Times`、`DrawType`、`ResetType` 是群組欄位，同群組各列必須一致；不一致是載入失敗（`ErrInvalidDefinition`，`validateGroups`），不是 warning。

每次抽獎保存亂數種子、抽獎進度、已抽次數與獎勵。多筆抽獎會在同一筆玩家交易中結算，避免只保存部分結果。道路星星、街區、指揮中心每日獎勵與隨機獎勵都透過相同抽獎結算入口。

## 建築、研究與工廠

- 建築升級先驗證前置條件與資源，再原子扣除成本並套用效果。
- 研究啟動會扣除研究成本；科技效果以原子方式套用，避免扣款成功但效果未保存。
- 工廠生產會依有效效果計算產量，先扣除砲彈或其他生產成本，再保存產出。
- 同一效果的研究科技會累加；減量超過基礎值時以下限計：每顆砲彈生產成本最低 0，工廠與研究步數最低 1，擲骰不會因此失敗。
- 伺服器目前套用的效果：工廠步數、研究步數、研究點數成本、工廠產量、砲彈容量、砲彈生產成本、商店折扣、骰子容量（最低 1）、骰子恢復間隔（最低 1 秒）。骰子容量與恢復間隔在載入玩家時的懶恢復與擲骰扣骰都會套用。
- `SharedEffectID_GoldAmount`、`SharedEffectID_ShopGroup`、`SharedEffectID_RoadGoldAmount`、`SharedEffectID_DailyRewardUnlock` 尚未有套用規則：科技或建築引用時只保存貢獻、不改變數值，World 載入設定時會記錄 `game config references an effect the server does not apply yet` 警告。
- 效果與玩家變數的實際值由 World 保存結果；Client 只接收事件演出與更新後狀態。

## 戰鬥事件

盤面戰鬥事件會呼叫戰鬥配對流程，而不是在盤面內自行選敵或保存戰鬥結果：

開戰資格（盤面狀態 `CombatPending`，資料欄位 `combat_pending`）只在擲骰最終停留的格子觸發戰鬥事件時取得：經過戰鬥格、被機會／命運的移動事件帶到戰鬥格，或再次擲骰都不保留資格。建立 Session 成功後消耗資格，一次停留只能開戰一次；開戰時挑到的守方在建立場次時才發現忙碌或快照已消失會重挑（最多 3 次；`Pick` 本來就沒有候選時不重挑，免得把查詢放大 3 倍），玩家造成的拒絕（玩家或格子 ID 為零、盤面不屬於該玩家、停留的格子不是待開戰的戰鬥格）由 World 內部的 `errCombatStartRejected`（未匯出）（訊息 `board: combat start rejected`，與領域層的 `board.ErrCombatNotAvailable` 是不同的錯誤值，前身叫 `ErrCombatNotAvailable`）決定回覆，Client 一律收到固定的 `combat is not available`，不原文回內部錯誤；載入玩家狀態等內部錯誤回固定的 `combat state unavailable`，同樣不回內部錯誤字串，且以 `ErrResolutionFailed` 交給 `runBoardCommand` 計入 `game_board_command_total{result="error"}`（見[問題排查筆記](../20-排障與監控/問題排查筆記.md)的 `board command failed`）。`ConsumeCombatTicket` 在玩家沒有可消耗的資格時回 `ErrCombatTicketMissing`（訊息 `gamestore: no combat ticket available`）；開戰處理器沒有注入盤面狀態來源屬伺服器設定錯誤，走內部失敗路徑；仍找不到對手（`CombatProtocolCombatTerminalError_NoOpponent`）時保留資格，玩家可在同一格重試。同一個 `RequestID` 重送時回傳已建立的 Session，不重新配對；擲骰、建築升級、商店結算、使用道具與任務指令一律拒絕 `RequestID` 為 0（解包失敗），World 不再有「沒有 RequestID 就不寫 journal」的分支；攻方同一時間只能有一場進行中或結算中的戰鬥。

1. 開戰前刷新攻方戰鬥快照。
2. 從有效候選索引選擇敵方並固定敵方快照：隨機抽樣為單次 `SRANDMEMBER key 8`（不重複抽取，集合小於 8 時樣本就是整個集合）加一次 `IN` 查詢載入快照，再從樣本內可挑戰的候選人均勻挑一位；抽樣階段往返由最多 16 次降為 2 次，樣本內沒有可挑戰者時仍走全量掃描。
3. 保存戰鬥 Session，回傳開始戰鬥結果。
4. Client 提交傷害後，由戰鬥與 Wallet 流程完成金幣結算。
5. 攻守雙方結算通知持久化，Client 可稍後查詢未讀通知。

戰鬥快照的刷新與盤面異動同步，避免候選資料長時間停留在舊狀態；已建立的 Session 則繼續使用建立當下的固定快照。快照的碉堡與出戰配置由 `world.yaml` 的 `combat` 區段提供，碉堡血量必須是正的有限數且能被 float32 精確表示（送給 Client 與 Client 回報打滿傷害都是 float32，否則打滿會被判無效或少發金幣），不符合時 World 拒絕啟動。

### Gate 目前不轉送戰鬥與使用道具指令（待 Client 完成後再開放）

World 的盤面路由支援 `UseItemCommand`、`StartCombatCommand`、`SubmitCombatResultCommand`、`ListCombatSettlementNotificationsCommand`、`MarkCombatSettlementNotificationsReadCommand` 五個指令，但 Gate 的客戶端盤面轉送表 `boardClientMessageIDs`（`cmd/gate/internal/handler/user/board.go`，來源是 `pkg/msg/board/client_command_ids.go`）只有 `LoadPlayerRequest`、`ResolveShopCommand`、`UpgradeBuildingCommand`、`ActivateMissionCommand`、`ListMissionsCommand`、`ClaimMissionRewardCommand` 加上擲骰。這是刻意決定：**等 Client 的戰鬥與使用道具功能完成後再開放**（2026-10-16 決議，審查紀錄 D2 選項「先不開放」）。

目前的行為與影響：

- 玩家送出這五個指令時，Gate 當成未知訊息（`unknown message dropped`）並**關閉該連線**，不是回錯誤。Client 在功能完成前不可送出。
- 擲骰停在戰鬥格仍會產生戰鬥事件與開戰資格（`CombatPending`），但玩家無法使用；World 仍維護戰鬥快照（`combat_player_snapshot`），這部分寫入成本目前沒有對應的玩家功能。
- World 端這五個處理器與測試保留不動。

開放前必須先處理（Client 完成後的待辦）：

1. **戰鬥結果由 Client 回報**：`MatchService.Submit` 只收 Client 回報的 `damageToDefenderBunker`，獎勵由 `settleReward(RewardBaseGold, 傷害, DefenderBunkerHealth)` 算出（`internal/combat/match.go`，換算本體是 `wallet.RewardForDamage`）；協定裡的勝負、彈藥、經過秒數伺服器不用來驗證。已有的保護是場次只能由攻方提交一次、逾時、以 `settlementID` 去重、一次停留只能開戰一次。需要決定是否由伺服器重算或加傷害上限（已登記為[已知安全風險](../30-部署與開發/已知安全風險.md) #9，開放轉送前必須先決定）。現況：`wallet.RewardForDamage` 拒絕負值、非有限值與超過血量的傷害（回 `ErrInvalidCombatResult`），獎勵上限為 `RewardBaseGold`；但只要回報傷害等於血量就能拿滿額，伺服器無法分辨真偽。
2. （已完成）`RequestID==0` 規則已統一：擲骰、升級、商店、使用道具與任務指令一律拒絕 0（見上文）。
3. **把五個 ID 加入轉送表**並補跨服務測試：已開放的 Client 盤面指令以 `pkg/msg/board.ClientCommandIDs()` 為單一來源，Gate 轉送表、World 路由表、`failure.go` 的一致性測試都以它為準；這五個 ID 不在清單內，開放時要加進 `ClientCommandIDs` 才會納入比對。
4. **補戰鬥的負載測試**：配對、開戰、結算；私有工具 `tools/private/gameload` 已有擲骰與商店路徑，可擴充戰鬥。
5. 考慮讓 Gate 對「協定已定義但未轉送」的訊息回錯誤，不要直接斷線。

## 保存與回傳規則

盤面事件、抽獎狀態、資源扣除、物品獎勵與建築效果必須在同一個可重試的保存邊界內完成。保存失敗時不回傳成功事件；成功後回傳的事件資料包含 Client 顯示所需的事件類型、結果碼、獎勵與必要的抽獎資料。

擲骰提交的順序只有一份：`board.CommitRoll`（`internal/game/board/commit_roll.go`），World（`gamestore`）與模擬器共用，固定為研究費 → 結算（工廠砲彈、研究效果、事件獎勵道具、經過起點事件）→ 抽獎 → 抽獎獎勵入帳 → 寫入抽取次數；研究費不足在任何改動前回 `ErrResearchStartInsufficient`，抽獎獎勵入帳溢位時抽取次數不會被扣。與舊版的差別：World 的抽獎在結算**之後**才執行（2026-10-31 歸位後）。扣骰、經過次數變數、盤面與商店報價的寫入仍由 World 外層負責，模擬器沒有這些。

常見結果包括：

- 擲骰結果與落點。
- 道路星星／街區完成事件與抽獎獎勵。
- 指揮中心每日或隨機獎勵。
- 經過起點的任務事件：移動路徑經過 `Start` 格時，於同一保存邊界寫入 `record.world.start.pass` outbox 事件（`count` 為經過次數），供 `StartPassCount` 任務進度使用；擲骰回滾時事件一併不寫入。
- 建築升級、研究啟動、工廠生產事件。
- 戰鬥開始待 Client 行動，以及戰鬥提交結果。
