# Session 與登入流程

這份文件描述目前專案中登入、登出、session、恢復校驗的實際規則。

## 鏈路契約總表

這一段只收斂最容易漂移的規則，避免 handler 與文件各講各話。

| 項目 | 規則 |
| --- | --- |
| `request_id` | 由 `Gate` 建立；跨服務鏈路共用；只做去重與結果回放。 |
| `trace_id` | 由 `Gate` 建立；跨服務鏈路共用；只做觀測與除錯。 |
| 版本相容 | 不在每個訊息裡檢查：新連線的第一個訊息 `HelloRequest` 由 `Gate` 判斷，見 [版本握手與強制更新](版本握手與強制更新.md)。 |
| `pending_login` | 玩家登入請求通過輸入與限流檢查後建立。封禁檢查器為必填（Gate 沒有它就啟動失敗），封禁查詢前就以 `CentralID 0` 先建 pending（擋下同連線重送），封禁或查詢失敗時 `rejectPending(sock, code, reason, start)` 收掉（取走 pending 後經 `flowbase.CountLoginResult` 計量）；封禁通過後 `forwardLogin` 選出 Central，選不到就 abort 並回 `AuthServiceUnavailable`，選到才綁定該 Central 並轉送。斷線清理（`Disconnect`）與事件迴圈並行，所以建立 pending 之後（封禁查詢前後與 `forwardLogin` 開頭）會再檢查玩家連線 context：已斷線就立即以 `TakePendingLogin` 收掉 session，不轉送幽靈登入給 Central，也不留孤兒 pending（否則只能等 TTL 逾時）。 |
| `pending_logout` | 只有在 `Gate` 已接住玩家登出請求後才建立；後續失敗也要先清本地 session。 |
| 可重試回傳碼 | 只保留 `AuthServiceUnavailable`、`AuthRateLimited`。 |
| 不可重試回傳碼 | `AuthSessionExpired`、`AuthRecoveryMismatch`、`AuthWrongPassword`、`AuthServerFull`。 |
| 失敗處理 | `SessionExpired`、`RecoveryMismatch` 與登入/登出失敗都要先清 pending 狀態，再回給玩家。 |

## 核心欄位

### `request_id`

- 用途：辨識同一筆 request/reply 鏈路，支援去重與結果回放。
- 建立位置：由 `Gate` 在玩家請求進入伺服器鏈路時建立。
- 傳遞範圍：同一筆登入、登出、恢復校驗的跨服務訊息都沿用同一個 `request_id`。
- 使用規則：
  - 原始玩家輸入訊息不攜帶 `request_id`。
  - `heartbeat`、`connect_info`、`time_sync` 等系統訊息不得使用。
  - `Central` 以 `account + request_id` 去重登入請求，重送時回放前次結果。
  - `Logout` 與 `recovery validation` 以 `playerID + request_id` 去重；不同 `scope` 就算 `request_id` 相同，也視為不同請求。

### `trace_id`

- 用途：串接跨服務日誌與觀測指標。
- 建立位置：由 `Gate` 在進入跨服務鏈路時建立。
- 傳遞範圍：同一筆登入、登出、恢復校驗的跨服務訊息都沿用同一個 `trace_id`。
- 與 `request_id` 的差異：
  - `request_id` 用於冪等與去重。
  - `trace_id` 用於觀測與除錯。

## 訊息中繼資料規範

定義位於 `pkg/msg/protocol_meta.go`。

- `RequestMeta`
  - 只允許出現在可重放、可去重的 server-side request/reply 訊息。
  - 不允許用在 `heartbeat`、`connect_info`、`time_sync` 這類系統訊息。
- `TraceMeta`
  - 只允許出現在需要串接跨服務日誌的訊息。

## Gate Session 狀態機

定義位於 `cmd/gate/internal/app/core_types.go`。
實作上對應到 `UpsertPendingSessionWithCentral`、`BindPendingLogin`、`BeginLogout`、`DeleteSessionByKey`、`TakePendingLoginSessions`、`SweepExpiredSessions` 這幾個入口。

### 狀態

- `pending_login`
  - 玩家已送出登入請求，等待 `Central/World` 回應。
- `logged_in`
  - 玩家已完成登入，`sessionKey <-> playerID` 綁定成立。
- `pending_logout`
  - 玩家已送出登出請求，等待 `Central/World` 完成鏈路。
- `disconnected`
  - session 已失效或已被刪除。

### 主要轉移

| 目前狀態 | 事件 | 前置條件 | 動作 | 下一狀態 |
| --- | --- | --- | --- | --- |
| 無 session | `LoginRequested` | `sessionKey != ""` | 建立或重設 pending session | `pending_login` |
| `pending_login` | `LoginSucceeded` | session 存在 | 綁定 `playerID/worldID`，寫入 `sessionKeyByUser` | `logged_in` |
| `pending_login` | `LoginFailed` | session 存在 | 刪除 session | `disconnected` |
| `logged_in` | `LogoutRequested` | session 目前為 `logged_in` | 切為 pending logout，保留快照給後續流程 | `pending_logout` |
| `pending_logout` | `LogoutCompleted` | session 存在 | 刪除 session，清掉反向索引 | `disconnected` |
| `pending_login` | `SweepExpiredSessions` | 超過 Gate app 本地 `gatePendingLoginTTL` | 刪除 session | `disconnected` |
| `pending_logout` | `SweepExpiredSessions` | 超過 Gate app 本地 `gatePendingLogoutTTL` | 刪除 session，必要時同步清理本地 user | `disconnected` |
| `logged_in` | `Heartbeat` | session 存在 | 更新最後活動時間（`Session.LastSeenAt()`，單調時鐘） | 不變 |
| 任意狀態 | `Disconnected` | socket 或上游失效 | 視情境刪除或標記無效 | `disconnected` |

### TTL 與清掃

Gate session policy 定義位於 `cmd/gate/internal/app/core_types.go`（pending 逾時可由 `Config.PendingLogoutTTL` 覆寫）。

- `pending_login`
  - 超過 `gatePendingLoginTTL` 會被 sweeper 清掉。
- `pending_logout`
  - 超過 `gatePendingLogoutTTL` 會被 sweeper 清掉，並同步清理本地 user/session。
- `logged_in`
  - heartbeat 會更新最後活動時間（`Session.LastSeenAt()` 回 `time.Time`，內部以 `pkg/timex` 單調值儲存；診斷輸出換算成近似牆鐘），供 pending 清理與觀測使用。第十二輪前是 `LastSeenUnixNano()`（牆鐘奈秒）。

### 玩家心跳

玩家心跳相關的 timeout 與輪詢間隔現在由 `cmd/gate/internal/handler/user/connect.go` 以本地常數持有。

- `userHeartbeatTimeout`（90s）
  - 超過此時間未收到心跳就視為斷線。
- `userConnCheckInterval`（5s）
  - Gate 會以此間隔輪詢（`connect_watchdog.go`）玩家心跳與登入握手是否逾時。
- 心跳、握手逾時、pending session 清理與版本寬限期都以單調時鐘判斷（`pkg/timex`，第十二輪 TR-M1）：主機牆鐘前跳不再讓全體玩家一起心跳逾時斷線，後跳也不會讓逾時失效。
- `userLoginHandshakeTimeout`（30s）
  - 連線建立後必須在此時間內完成登入握手，逾時斷線並計入 `tcp_rejected_connections_total{reason="handshake_timeout"}`。

## 服務失聯策略

服務失聯寬限定義在 `pkg/appcore/timeout.go`，Central、Gate、World 共用。

- `appcore.ServiceDisconnectGracePeriod`（30 秒）
  - Gate <-> World、World <-> Gate、Central 看 Gate 斷線後，不立即清理玩家狀態。
  - 先記入 `appcore.DisconnectGrace`，等待短暫抖動恢復。
  - 在 grace 內重新收到 `ConnectInfo` 時，必須清除斷線標記，保留原 session / user 狀態。
  - Gate 對 World 的寬限可由 `session.service_disconnect_grace_period` 調整；Central、World 固定用此值。
- `appcore.ServiceDisconnectSweepInterval`（5 秒）
  - 三個服務以 `panicx.RunEvery` 定期檢查失聯寬限是否到期，每輪各自 recover。

### Gate 遇到 Central 斷線

- 斷線當下：
  - 先移除 dead central 的 ring 節點。
  - 已登入玩家的 `sessionCentral` 仍要遷移到其他存活 Central。
  - 就算 User 服務（`appname.User`）暫時不可用，也不能因此跳過路由遷移。
  - 綁定該斷線 Central 的 `pending_login` session 也要立即清掉（只清綁定斷線 Central 的，綁其他 Central 或已被取走的不動），就算 `Services` 暫時不可用也不能只靠 TTL 等它自己過期。Gate 端 `failPendingCentralLogins` 以 pending session 為主迴圈，取走一筆處理一筆：玩家 socket 仍在線就補送 `service_unavailable` 的 `LoginResponse` 並計 `service_unavailable`，已離線則只計 `client_closed`；剛連上等 Hello、登出後閒置的連線不會收到無法對應的回應。
- 若找不到可用 Central：
  - 先保留現有登入狀態。
  - 後續 logout 再嘗試重新路由。

### Central 遇到 Gate 斷線

- `Disconnect` 只標記該 Gate 進入寬限期（`appcore.ServiceDisconnectGracePeriod`，30 秒，與 World 對 Gate 的寬限一致），不立即清玩家、不刪 Redis 路由、不通知 World 登出。同一 Gate 以新連線取代舊連線時，舊連線的斷線不標記。
- 寬限期內 Gate 以同 ID 重連（`onConnectInfo` 清除標記）：保留 Central 記憶體中的玩家與 session；Gate 重連後照常送出在線玩家快照（`SyncUsersGateToCentral`），`syncuser.Handle` 對帳——補回缺少的、在鎖內從記憶體移除快照裡沒有的；移除者的 Redis 路由刪除與 World 登出通知由 `evictGateUsers` 放到背景執行（與逾期清理共用，同樣以 Gate compare-and-delete 刪路由），Redis 卡住時不拖住 `connectionMu`。Gate 重啟過時快照是空的，舊玩家因此全部被移除，不會留下殘影。
- 逾期仍沒重連：每 5 秒一次的 sweeper（`sweepGateDisconnectsLoop`）呼叫 `clearGateSessions`。掃描當下 Gate 已用同 ID 連回則保留；否則持 `connectionMu` 寫鎖從記憶體移除該 Gate 的玩家（`removeGateUsers`），並以 `ClearPrevGatesOf` 清掉所有 `PrevGateID` 指向該 Gate 的還原目標：它的 session 已全部消失，同 ID 重連後 World 拒絕重登也不可還原過去。
- 放鎖後由 `evictGateUsers` 刪 Redis 路由並通知 World 登出；同一 World 的多位玩家合併成一幀 `LogoutBatchCentralToWorld`，只有單人時沿用 `LogoutCentralToWorld`。期間已從其他 Gate 重新登入的玩家略過。Redis 路由以 `DeleteUserRoutingsIfGate`（Lua 比對 `gate` 欄位等於斷線 Gate 才 DEL）刪除，比對記憶體後才重登寫入的新路由不會被清掉。
- 寬限期內玩家從另一個 Gate 重登：登入流程不依賴舊 Gate 的 Central 連線，直接覆蓋記憶體記錄；逾期清理只處理仍登記在該 Gate 的玩家。
- 斷線的是重登的新 Gate（玩家 `PrevGateID` 指向仍在線的舊 Gate）時仍走登出，不還原：此時不知道 World 是否已接受重登（接受時已踢掉舊 Gate 的 session），還原會讓 Central 與 World 對玩家所在 Gate 不一致；登出讓兩邊一致為離線，舊 Gate 殘留的 session 由 Gate 使用者快照收斂。
- 實測（第四輪第 42 步）：輪替 Gate 的 S2S token 造成約 1 秒瞬斷，300 位玩家全部保留。

### Central 遇到 World 斷線

- 先 `RemoveWorld`（移除連線記錄並記下斷線時間供重連冷卻），再清玩家：清理期間登入流程不會再把新玩家派到這個已斷線的 World。
- 清理用條件刪除 `DeleteUsersIfWorld`：記憶體在同一次持鎖內逐一比對 `WorldID`，Redis 路由以 `DeleteRoutingsIfWorld`（compare-and-delete）只刪仍記在該 World 的；已被改派到其他 World 的玩家與新路由保留。

### Gate 遇到 World 斷線

- 斷線當下：
  - 只標記該 world_id 為 unavailable。
  - 保留玩家 session 與本地在線狀態。
- 若 World 在寬限期內重新連上：
  - 清除 unavailable 標記。
  - 已在線玩家繼續沿用原 session，後續由 World 自己的恢復校驗決定是否收斂。
- 若超過寬限仍未恢復：
  - Gate 清理該 World 上的玩家與 session。
  - 通知 Central 清理 route。
  - 回 AuthServiceUnavailable 給玩家。

### World 遇到 Gate 斷線

- 斷線當下：
  - 只標記該 gate_id 為 unavailable。
  - 保留 World 內玩家狀態。
- 若 Gate 在寬限期內重新連上：
  - 清除 unavailable 標記。
  - World 端玩家狀態維持不變。
- 若超過寬限仍未恢復：
  - World 才清理該 Gate 代理的玩家；清理在背景逐人進行，**每刪一位玩家前再確認 Gate 沒有以同 ID 重連**，重連就立刻停手，其餘玩家與其 Redis 狀態保留（第十六輪）。
  - observer、player store 與 game data 的清理鏈路才會真正觸發。
## Gate 優雅排空（Graceful Drain）

用於 rolling deploy：先讓玩家自然下線，避免強制斷線。

**三步流程**（`cmd/gate/internal/services/run.go` 的 `gateShutdownSetup`，向 `appcore.ShutdownOrchestrator` 登記 PreDrain → Drain → PostDrain）：

1. **停止接受新連線** — Drain 階段由 `registry.DrainService` 呼叫 `StopAccepting()` 關閉 listen socket，既有連線保留
2. **等待自然排空** — 最多等待 Gate 預設的 `30s` 排空時間（可透過 `drain_timeout` config 覆寫，上限 40 秒（`services.MaxDrainTimeout`）；寫錯（缺單位、亂碼、非正數）或超過上限時 Gate 拒絕啟動，未設定才用預設值）
3. **強制斷開剩餘連線** — 超時後對每個仍在線玩家送出 `LogoutResponse`（`AuthServerFail`）並關閉 socket

**預設值**：Gate 預設排空時間 = `30s`（`services.DefaultDrainTimeout`），上限 `40s`（`services.MaxDrainTimeout`）。

**設定覆寫**（Gate 設定檔）：
```yaml
drain_timeout: 35s  # 未設定則用預設 30s，上限 40s
```

範本設定檔預設不含這個鍵；寫在 Gate 設定檔即可。超過 40 秒的值會被拒絕啟動；要更長時須同步調高 `MaxDrainTimeout` 與 Gate 容器的 `stop_grace_period`（目前 75 秒），否則關機尚未完成就被 SIGKILL；`shutdown_plan_test.go` 的契約測試會擋下，見[開發規則](../30-部署與開發/開發規則.md#gate-排空設定)。

## 服務責任邊界

### Gate

- 接收玩家登入/登出請求。
- 建立 `request_id`、`trace_id`。
- 管理玩家連線與 session 狀態機。
- 玩家連線的 per-socket rate limiter 由 `cmd/gate/internal/services` 在服務建構期注入，不再由 `Connect` 期 setter 設定。
- 在入口做限流與短期鎖定：帳號維度的鍵是（帳號, 來源 IP）而不是單獨的帳號（`cmd/gate/internal/app/attempt_limiter.go` 的 `AllowLoginAttempt`，鍵為 `帳號|來源 IP`）；計數發生在密碼驗證前，只以帳號為鍵的話，任何人送幾次錯誤請求就能把受害者帳號鎖住。另有只看來源 IP 的限流（`AllowLoginAttemptFromIP`，IPv6 以 /64 計）。
- 入口先檢查帳密格式：帳號為空回 `AuthAccountEmpty`；帳號不是合法 UTF-8、超過 100 個字元（`user.account` 欄位長度）、含控制字元或零寬等不可見字元、或首尾有空白（`"alice"` 與 `"alice "` 會變兩個帳號）、密碼超過 `accountrule.MaxPasswordBytes`（72 bytes，bcrypt 上限）時直接回 `AuthWrongPassword`，不進限流表也不送 Central。合法的帳號隨即由 `accountrule.Normalize` 改寫成標準寫法（見下方「帳號比對」），之後的限流、封禁查詢、Central 路由與轉送都用改寫後的字串。
- 尚未收到 Central 第一則 `TimeSync`（遊戲時間未校正）時，登入回 `AuthServiceUnavailable`，不消耗限流額度；`/ready` 的 `time_sync` 檢查同時不通過。
- 登入被拒（`LoginRejected`）與登出通知送往處理該 session 的 Central（`SessionCentral`，經 `flowbase.PickCentral`），不隨機挑；找不到該 Central 連線時記 `central notify dropped: no central connection`。多台 Central 時只有處理登入的那台記得 `PrevGateID`，送錯台會無法還原。
- World 回登入成功時，以 `App.BindPendingLogin` 在同一次持鎖（`sessionMu`／`userMu`）內完成綁定 session 與寫入玩家，背景對帳（`reconcileDerivedState`）不會落在兩步之間把剛綁好的 session 刪掉；綁定成功即取得這筆登入的計量權（回傳建立時間供 `flowbase.CountLogin` 單次計數）。
- 將登入請求轉送到 `Central`，將 `World/Central` 結果回給玩家。
- 在 `World` 重啟恢復時，回覆玩家是否仍在線的主動校驗請求。
- `OnlineCount` 與 Lobby 負載回報只算 `logged_in`，`pending_logout` 不算在線。

### Central

- 作為帳號與登入結果的協調者。
- 以 `account + request_id` 做登入去重與結果回放。
- 決定玩家應進入哪個 `World`，可依 `traffic_slice_percent` 將少量帳號導向 canary world。
- `traffic_slice_percent` 的啟動與 hot reload 都呼叫 `cmd/central/internal/app/traffic_slice.go` 的 `App.SetTrafficSlice(percent, worldID)`（由 `cmd/central/internal/services/traffic_slice.go` 的 `TrafficSliceReloader` 套用：`cmd/central/run.go` 註冊熱重載，App 建好後 `Attach`）；比例與 World 一起以 `atomic.Pointer` 整組替換，讀取端不會讀到新舊混搭的值。
- 登出與 World 拒絕登入後的還原，其共享路由（Redis）的刪除與寫入在背景執行（`GoBackground`），不在事件迴圈上持有 Gate 連線讀鎖等 Redis；批次登出的刪路由與 journal 寫刪也在背景（journal 批次寫入用 `StoreManyDeferred`，脫離呼叫端取消）。刪除以 GateID 做 compare-and-delete，寫入前比對記憶體現值，延後執行不會誤刪或蓋回。時序取捨：同一 Gate 的登出與重登若在背景任務間亂序，共享路由可能短暫缺一筆（記憶體內的對照不受影響，下次寫入或還原即補回）。journal 讀取仍同步，因為需要結果才能續行。
- 維護 `account/user/world/gate` 對照。寫共享路由（Redis）前以 `sameUserRouting` 比對記憶體內的 Gate／World／帳號／密碼雜湊，內容不同就略過，舊快照不會蓋掉較新的路由（單筆與批次相同）。
- 路由快取（Redis）失敗（含逾時）後進入 10 秒冷卻：期間所有操作立即回 `ErrCooldown`、不送命令（呼叫端自己取消不算故障）。登出、拒登還原與 Gate 重連都在事件迴圈同步呼叫，Redis 卡住時不會每則停 3 秒。
- 從 Redis 快取還原玩家時，只有該玩家在讀取期間被刪除才放棄（記最近 64 筆被刪 ID；刪除數超過容量才保守回找不到），其他玩家登出不影響。
- 登入覆蓋仍在線的舊記錄時記下 `PrevGateID`（同 Gate 新連線重登時即目前 Gate）。收到 `LoginRejected` 時嘗試把玩家還原到前一個 Gate；同 Gate 時只作廢這次登入，不登出也不踢仍在線的舊連線（Gate 端被拒時只刪這次的 pending session，舊連線的 session 不受影響）；無法還原時改走登出並記 `login rejected: cannot restore previous gate, falling back to logout`（`reason` 為 `no_previous_gate`、`request_mismatch`、`no_services`、`previous_gate_offline`、`restore_precondition_failed` 之一）；回報的 Gate 已不是玩家目前的 Gate、找不到玩家或玩家 ID 為空時略過並記 `login rejected ignored: ...`。
- 接收 `Gate` 的登出請求並轉送給 `World`。以「玩家仍綁在發出登出的 Gate」為條件，在同一次持鎖內比對並刪除記憶體記錄後才通知 World；批次登出（`PlayerIDs`）也一樣，只有 Redis 路由刪除、登出結果與登入結果刪除延到 `FlushBatch` 以單次往返寫入。登出刪 Redis 路由一律以 Gate 比對（compare-and-delete）。

### World

- 作為玩家實際所在的遊戲節點。
- 處理登入最終接受或拒絕。
- 維護 `user <-> gate` 綁定。
- 持久化與恢復玩家狀態。
- 重啟後先從 store 還原，再向 `Gate` 主動校驗玩家是否仍在線。
- `World` 的容量判定只算 `GateID != 0` 的 active player，避免 logout 後殘留的 `GateID=0` user 卡住新登入。

### Chat

- 作為文字聊天的獨立服務。
- 處理跨世界聊天、全服聊天、聊天歷史、審核、禁言與離線補送。
- 其他 Service 可以直接送 `ChatSystem` 進來，由 `Chat` 統一派送。
- 玩家可送 `ChatSync`，以 `SinceMessageID` 當 hint，向 `Chat` 補拉同一個 room 的歷史訊息。
- `Chat` 派送時每個 Gate 只收到一幀 `ChatDeliverBatch`，Gate 打包一則 `ChatDeliver` 共用給本機收件人；`ChatDeliver` 會帶 `MessageID`，client 可用它做去重與下一次 sync 起點。
- 聊天歷史以 `MySQL` 為 source of truth，`ChatService` 只做即時廣播與查詢入口。
- `Gate` 只負責把玩家文字聊天請求轉進 `Chat`，再把 `Chat` 的派送結果送回玩家。
- 頻道（`Channel*`）功能已移除；聊天只由 `Chat` 負責，World 不參與文字聊天。

## 主要鏈路

### 登入

1. 玩家送 `LoginRequest`（含 `Account`、`AccountType`、`Password`）
2. `Gate` 驗證輸入、限流，建立 pending session（封禁查詢前以 `CentralID 0` 先建），背景查封禁（被封禁回 `AuthAccountBanned`，查詢失敗 fail-closed 回 `AuthServiceUnavailable`）
3. 封禁通過後 `Gate` 依帳號以一致性雜湊環（`cmd/gate/internal/centralring`，xxhash64、每個 Central 256 個虛擬節點）選 Central。環的雜湊函式、虛擬節點命名與數量只要變動，帳號就會重新分配到別台 Central，滾動升級期間新舊 Gate 可能把同一帳號導向不同 Central；這是安全的，因為帳號鎖在 Redis 互斥（`SET NX PX`），Central 沒有依帳號綁定節點的記憶體狀態（本機玩家索引 miss 時會從共享快取還原）。第十五輪把雜湊由 FNV-1a 換成 xxhash（FNV-1a 對短鍵分佈差，3 節點最重的佔 46.6%），換版當下一次性重新分配。`Gate` 選 Central（找不到就 abort pending 並回 `AuthServiceUnavailable`），建立 `request_id` / `trace_id`，開啟 OTel Span `gate.login.forward`
4. `Gate -> Central`（攜帶 `Password`）
5. `Central` 做去重、查帳號、**驗證 bcrypt 密碼**、選擇 `World`（必要時先走 traffic slice）；開啟 OTel Span `central.login`
6. `Central -> World`；開啟 OTel Span `world.login.assign`
7. `World` 決定接受或拒絕
8. `World -> Gate`
9. `Gate` 成功時 bind session，失敗時清掉 pending session
10. `Gate -> User`

`Central` 的寫入順序是先 `SwapLoggedInUserInMemory`（內含 `SwapUserInMemory`，並以 App 時鐘標記登入時間給稽核寬限）更新本機記憶體的玩家記錄（保留被取代的舊記錄），再把登入轉發給 `World`；轉發失敗（例如 `World` socket 不可用）就還原舊記錄（原本沒有則刪除新記錄），不能留下半套登入狀態。這樣舊 Gate 的登出在空窗到達時會看到新 Gate 而被擋下，不會出現 World 先收登入、再收舊登出而與 Central 記錄不一致。共享快取（`user / gate / world` 路由）在轉發成功後的 `completeLogin` 才同步（`SyncUserRouting`）。對照[資料一致性](./資料一致性.md)。
`Central` 若 `Services` 暫時不可用，也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能讓 pending session 一直卡到 sweeper。
`Central` 若 `App` 暫時不可用，也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能靜默吞掉登入請求。
`World` 端也必須先確認目標 `Gate` 仍在線，再做舊綁定清理與新綁定更新；否則只會把舊 gate 先踢掉，卻沒真正完成登入。
如果 `Gate` 端收回 World 回應時 `user socket` 已消失，仍要清 session 並通知 `Central` rollback，不能直接沉默離開。
`Gate` 在 `Central` 或 `Central socket` 不可用時不能把 `pending_login` 留著：封禁檢查器為必填，pending 會在封禁查詢前先建立，之後 `forwardLogin` 找不到 Central 或 Central 連線已斷（`coordinator.go` 的 `Coordinator.rejectPending(sock, code, reason, start)`，內部用 `TakePendingLogin`，所有 `service_unavailable` 拒絕都走它，計量統一經單一入口 `flowbase.CountLoginResult`）就立刻 abort 並回 `AuthServiceUnavailable`，不能留下假 session 等 sweeper。
`Gate` 收到 `World` 的登入回應時，如果 User 服務（`appname.User`）不在，也要先清掉 pending session，能回滾就回滾 `Central`，不能把假狀態留到 sweeper。
`Gate` 收到 `Central` 的登入失敗通知時，就算 User 服務（`appname.User`）不在，也要先清掉 pending session，不能留到 sweeper 才收。
`World` 收到登入請求時，若 `App` 不在，若能找到 `Gate` 也要直接回 `AuthServiceUnavailable`，不能讓 `Gate` 卡住。
`World` 尚未收到 Central 第一則 `TimeSync` 時同樣回 `AuthServiceUnavailable`，不建立玩家。
關機 drain 期間 Central 的登出仍會刪除共享路由：路由讀寫用呼叫端 ctx 脫離取消（`WithoutCancel`）並保留單次期限，不再因 App ctx 已取消而殘留幽靈在線（最長 24 小時）。

`World` 登入請求的重複請求回放（request journal）：事件迴圈只查本機快取，Redis 遠端查詢改在 `TouchLoginActivity` 的背景 goroutine 內做，查到命中再回事件迴圈續行，事件迴圈不再為此同步等 Redis（逾時 500ms）。回放判斷現在排在容量檢查之後：有 gameStore 時，重複登入若同時滿載，會先回 `AuthServerFull` 而不是回放前次結果。World 與 Central 的**單人登出**回放仍是同步查詢（批次路徑本來就是一次預取）；是否保留 request journal（N1）尚未決定，若決定刪除 journal，這些往返自然消失。

`World` 登入活動的背景寫入完成後，先以 `gateSvc.ByID` 確認目標 `Gate` 仍是原連線；期間 Gate 斷線或換了連線就不回覆、不建立在線玩家（記 `login aborted: gate connection gone`），該次登入靜默丟棄。
`World` 收到登入失敗回應時，不能先踢舊 gate 或重綁 `GateID`；只要把失敗碼回給 `Gate` 就好。
`World` 只有在登入成功分支才會 rebind 舊玩家與踢舊 gate；失敗回應仍要先回玩家失敗碼，再回滾 `Central`，不改綁定。
若 `World` 已回成功但 `BindPendingLogin` 仍失敗，也要通知 `Central` rollback，不能只回玩家 `SessionExpired`。
`World` 的 logout replay 命中時，就算 Gate 服務（`appname.Gate`）暫時不可用，也不能 panic。
`Gate` 發起登出時，也要先確認 `Central` / `Central socket` 可用，再把 session 推進 `pending_logout`，否則中央沒回時會留下半套登出狀態。
`Gate` 收到 `World` 的登出回應時，就算 `Services` / `User` socket 已消失，也要清掉本機 user / session，不能留下 ghost user。
`Central` 收到 `Gate` 的登出請求時，如果 `World` socket 不在，也要先清掉本機 user，避免把已請求登出的玩家留成 ghost state。
`World` 收到 `Central` 的登出回應時，就算 `Gate` socket 不在，也要先清掉本機 gate 綁定與後續清理，不能把玩家留在 world 內。

### 文字聊天

1. 玩家送 `ChatJoin` / `ChatLeave` / `ChatSend`
2. 玩家也可以送 `ChatSync`，要求從某個 `MessageID` 之後開始補歷史
3. `Gate` 只做登入狀態檢查與轉發，將文字聊天請求送到 `Chat`
4. `Chat` 管理房間成員、審核、禁言、歷史與 sync
5. `Chat` 依玩家所在的 Gate 分組，每個 Gate 送一幀 `ChatDeliverBatch`
6. `Gate` 打包一則 `ChatDeliver`，共用派送給本地玩家 socket

頻道（`Channel*`）已移除：World 不再送 `ChannelBroadcast`、`ChannelMembershipUpdate`，`ConnectInfo` 完成後也不再送 `ChannelMembershipSnapshot`；Gate 不保存頻道成員投影。協定定義仍保留在 `protocol.xml`，待下次升版時移除。

**帳號比對**：`user.account` 欄位使用 `utf8mb4_bin`，帳號區分大小寫與重音（`Alice`、`alice`、`Álice` 是三個帳號）。第十三輪起帳號在入口先正規化成標準寫法（`accountrule.Normalize`：寬度折疊——全形英數與符號轉半形、半形片假名轉全形——再做 NFC，之後套用 `Valid`；大小寫不折疊）：全形 `ａｌｉｃｅ` 與 `alice`、NFD 與 NFC 的 `é` 是同一個帳號，不會再因為玩家切到全形輸入法而被靜默註冊成第二個帳號。Gate 登入、Central 登入（冪等再做一次）與 Lobby 封禁／解封／踢人（`gm.NormalizeAccount`）都經過它，封禁、帳號維度限流、帳號鎖與快取的 key 一律是標準寫法；Lobby 封禁輸入全形也會被折疊成同一個鍵。

**既有帳號遷移**：庫中若有未正規化的既有帳號（全形、NFD、半形片假名），改版後用任何輸入都登入不到（輸入被正規化成另一個字串，查無帳號會被當成新帳號註冊）。Central 啟動時掃描（`centralmysql.WarnNonNormalizedAccounts`，30 秒上限，只讀、不擋啟動；查詢失敗記 Warn），命中逐筆記 **Warn** `stored account is not in normalized form and cannot be logged into; rename or merge it`（最多 20 筆，欄位 `accountHash`、`collides`），另記一行 **Error** 彙總 `stored accounts not in normalized form found`（欄位 `total`、`reported`）。日誌刻意不放明文帳號（PII，與 `account_lock` 一致）：逐筆用 Warn 是因為資料沒清乾淨時每次重啟都會再輸出，逐筆 Error 會觸發以 `level=error` 為條件的日誌告警；彙總行維持 Error 提醒需人工處理。`accountHash` 是帳號 SHA-256 的前 8 位元組（十六進位，16 字元）。`collides=true` 表示標準寫法已被另一個帳號占用，需人工決定合併或保留哪一個；`collides=false` 可直接把 `user.account` 改成標準寫法（同時處理 Redis 的封禁鍵與限流／快取鍵）。

**取得明文清單的現況**：能列出明文與標準寫法的 `FindNonNormalizedAccounts`（`cmd/central/internal/store/mysql/account_normalization.go`）目前**沒有任何工具入口**，版控內只有啟動掃描與整合測試呼叫它。要由日誌找回帳號，直接在庫上用雜湊反查（一次性、全表掃描，建議在唯讀副本執行）：``SELECT account FROM `user` WHERE LEFT(SHA2(account, 256), 16) = '<日誌的 accountHash>'``。若要一次列出全部明文與標準寫法，建議補一個維運子命令（例如 `tools/pja` 底下）呼叫 `FindNonNormalizedAccounts`；補上前以上述 SQL 逐筆處理。上線前先在含正式資料的環境啟動一次 Central 確認沒有命中。

**帳號鎖持有期限**：Central 登入取得帳號鎖後（最多等 `LoginAccountLockWait` 1 秒，取不到回 `AuthRateLimited`；共享鎖故障回 `AuthServiceUnavailable` 並記 `game_account_lock_total{result="error"}`；Central 關機造成的等鎖取消同樣回 `AuthServiceUnavailable`，但不計 `error`、不記 Error；記憶體鎖在 ctx 已取消時一律失敗，不再隨機取到鎖），整段處理以 `LoginAccountLockHold`（Redis 鎖 TTL 15 秒減 5 秒，即 10 秒）作為 context deadline。DB 或斷路器變慢超過期限時流程中止，不讓鎖在中途過期而與另一個 Central 的登入並行。

**密碼驗證規則**（Central）：
- 首次登入（帳號不存在）：以 bcrypt cost=10 雜湊密碼，存入 MySQL `password_hash` 欄位；密碼為空時不建帳號，回 `AuthWrongPassword` 並寫 journal（日誌 `login failed: new user without password`）；密碼短於 `new_user.min_password_bytes`（只對新帳號套用，既有帳號不受影響）同樣回 `AuthWrongPassword` 並寫 journal（日誌 `login failed: new user password too short`）
- 再次登入：從 Redis 快取或 MySQL 取出 `password_hash`，以 `bcrypt.CompareHashAndPassword` 驗證
- `password_hash` 為空（既有舊帳號遷移）：不做 bcrypt，只接受空密碼，帶任何密碼都回 `AuthWrongPassword`（`existing.go`，避免他人用猜的密碼冒用）；新帳號不會產生空 hash，否則知道帳號即可登入。空 hash 帳號送空密碼即可登入的風險見[[已知安全風險]]
- 密碼錯誤：回傳 `AuthWrongPassword`（code 13）
- 新帳號註冊另用 `accountrule.Registrable`（比 `Valid` 多擋 Other_Default_Ignorable_Code_Point，例如 U+3164 韓文填充字元、U+FFA0、U+034F，這些字元可印但渲染為空白，會註冊出肉眼不可見或無法分辨的帳號），不合格回 `AuthWrongPassword`，日誌 `login failed: new user account has invisible characters (sampled)`；只擋註冊，不併入 `Valid`：既有含這類字元的帳號登入、封禁查詢不受影響。
- 前置檢查與 Gate 同規則：帳號不合法或密碼超過 `accountrule.MaxPasswordBytes`（72 bytes）直接回 `AuthWrongPassword`，不進帳號鎖、帳號儲存與 journal；新帳號雜湊時 bcrypt 回 `ErrPasswordTooLong` 也回 `AuthWrongPassword` 並寫 journal（不可重試）
- **登入 journal 只快取確定性的失敗結果**（同一 RequestID 在 `ReplayTTL` 內重送回放同一結果）：`AuthWrongPassword`（密碼錯誤、新帳號空密碼、密碼過長）、`AuthSaveFail`，以及登入成功收尾時 Gate 已斷或轉送 World 失敗的 `AuthServiceUnavailable`（`completeLogin`）。**暫時性或非確定的失敗不寫 journal**（登入成功本身同樣會快取，供重送回放），DB 或 World 恢復後同一 RequestID 重送會重新走流程：`FindByAccount` 失敗（逾時、斷路器開啟、MySQL 瞬斷；日誌 Error `login failed: DB error (sampled)`，每 10 秒最多一筆）、World 服務暫時不在（`login failed: world service not available`）、新帳號沒有可選 World（`login failed: no selectable world for new user`）、World 未識別、`buildNewCentralUser` 的其他錯誤（`login failed: cannot build new user`）、帳號清除中、bcrypt 忙碌、新帳號建帳速率限制、帳號鎖被占或故障。舊版把暫時性 DB 錯誤與 World 暫不在也寫進 journal，DB 恢復後 Gate 重送仍被回放成失敗，直到 TTL（2 分鐘）過期。
- 失敗路徑每次只記一行：`sendDirectError` 的 `login failed, notifying gate directly` 已降為 Debug，原因由各分支自己的日誌記錄（密碼錯誤沒有獨立日誌，量看 `game_login_total` 的 `result`）。
- 新帳號取不到 bcrypt 槽位（`login failed: bcrypt busy`）屬暫時錯誤：回 `AuthServiceUnavailable`，不寫 journal，Client 重送時重新走流程；等槽位最多 3 秒，逾時一律視為取不到（既有用戶登入同樣回 `AuthServiceUnavailable`），登入洪水不再讓排隊者無限佔著帳號鎖

### 登出

1. 玩家送 `LogoutRequest`
2. `Gate` 將 session 從 `logged_in` 切到 `pending_logout`
3. `Gate -> Central`
4. `Central -> World`
5. `World` 先確認 `Gate` 仍可接收，再清理玩家狀態並通知 `Gate`
6. `Gate` 清理本地 user/session
7. `Gate -> User`

若 `Gate` 收到 `LogoutWorldToGate` 時 `User` service 暫時不可用，會直接略過，不會因為缺服務而把登出流程炸掉。
若 `Gate` 收到 `LogoutWorldToGate` 的 `AuthSessionExpired`，也要清掉本地 user / session，不能讓過期 session 留成 ghost user。
若 `Central` 無法把 logout 送到 `World`，會直接回 `LogoutWorldToGate(AuthServiceUnavailable)` 給 `Gate`；`Gate` 收到這種回應也要清掉 pending logout，不能卡住。
若 `Central App` 暫時不可用，logout 也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能把 pending logout 留到 TTL。
若玩家在 `pending_login` 時主動 logout，`Gate` 也要先清掉 pending session，再回 `AuthLoggedOut`，不能讓晚到的登入回應把人又綁回來。
若 `Gate` 的 `App` 暫時不可用，logout 也要直接回 `AuthServiceUnavailable`，不能靜默吞掉請求。
若 `Gate` 的 `App` 暫時不可用，收到 `World` 的登入成功回應也要直接回 `AuthServiceUnavailable`，並盡量回滾 `Central`，不能把半套登入留在後面。
`Central` 斷線後，Gate 會把綁在死 central 的 `sessionCentral` 一起遷走，`pending_logout` 也不例外，避免路由一直指向死節點。
`World` 斷線後的清理 sweep 不能因 `Services` 暫時不可用而停掉，至少要先把本機 `user` 狀態清乾淨。
`Gate` 收到 `ValidateWorldToGate` 時，若本機 `App` 不在，也要回 `AuthRecoveryMismatch`，讓 `World` 自己清殘留。
`Central` 登出查無該玩家時回 `AuthSessionExpired` 給 `Gate`，Client 不必等 `gatePendingLogoutTTL`（30 秒）才登出。
`World` 收到不認識玩家的登出（重啟後未還原到該玩家）時，因登出訊息不帶 `GateID`，改對所有已連線的 `Gate` 回覆（沿用原 `request_id`、`trace_id`、玩家 ID 與 Central 給的結果碼）；`Gate` 只接受玩家記錄指向該 `World` 的回覆，其餘忽略。此路徑不清狀態、不寫登出 journal，沒有 Gate 連線時只記警告。
`Gate` 在登出完成、`pending_logout` 逾時、`World` 斷線清理三處清玩家 ID 時同時重置登入握手計時（`flowbase.ClearSocketPlayer`），同連線登出後可重新登入，不會因握手逾時被關線。
`World` 的登出清理（背景刪 Redis 玩家狀態）執行前再確認玩家沒有重新綁定 `Gate`，已重新登入就略過刪除；恢復驗證失敗只移除仍連在該 `Gate` 的玩家，玩家已改登其他 `Gate` 時不刪新記錄與 Redis 狀態。

### World 重啟恢復

1. `World` 從 player store 還原玩家狀態
2. 經過 `WorldRecoveryGracePeriod` 後開始對帳
3. `World` 對每個恢復玩家送 `ValidateWorldToGate`
4. `Gate` 檢查該 `playerID/worldID` 是否仍為有效 session（本機沒有先前結果時才查 Redis journal，查詢與結果寫入都在背景執行：改為有界佇列（`validateRemoteQueueSize`＝16384）加固定名額工作者（`validateRemoteConcurrency`＝128，即同時進行的 Redis 往返上限）；佇列滿就拒絕，該筆驗證回 `AuthRecoveryMismatch`；App 結束後工作者只收尾佇列、不再打 Redis）
5. `Gate -> World` 回覆成功或 `AuthRecoveryMismatch`
6. `World` 對失敗玩家清掉記憶體與 store 殘留
7. `Gate` 若找不到對應 user socket，也要清掉本地 user / session，避免留 ghost user
8. `Gate` 若 `world_id` 對不上，或無法確認 user socket，也要清掉本地 user / session，避免留下錯綁定

### World Crash Window

這段是 `World` crash 後到 `restore + validate + cleanup` 完成前的「可接受不一致窗」。

規則：

- `lifecycle.RestorePlayers` 只回復候選玩家，不代表已經真正常在線上。
- `WorldRecoveryGracePeriod` 內，`Gate` 可能還在重連，這段時間要保留恢復出的玩家狀態。
- `lifecycle.ReconcileRestoredPlayers` 之後，只有通過 `ValidateWorldToGate` 的玩家才算保留成功。
- `lifecycle.RestorePlayers` 只會重建 `GateID != 0` 的候選玩家；`GateID = 0` 的殘留紀錄會直接丟棄並從 store 清掉。
- `lifecycle.ReconcileRestoredPlayers` 在 `Gate` service 暫時不可用時，仍要清掉已恢復但無法驗證的玩家，不能把殘留掛到下一輪。
- 超過 grace 仍找不到有效 `Gate` 的玩家，要清掉 memory 與 Redis 殘留。
- 清理時要連同 World 的衍生索引（`usersByGate` 等）一起更新，不能只刪 user / route。

可丟資料：

- `World` memory player state
- Redis player store 中尚未驗證成功的恢復候選

不可丟資料：

- MySQL `user` / routing 資料
- 已經成功寫入 MySQL 的玩家資料（道具、盤面）

最長遺失窗：

- player presence 最多只在 `WorldRecoveryGracePeriod` 內保持不一致

## 錯誤語意

回傳碼定義位於 `pkg/errcode/auth_result_code.go`（協定生成型別的別名；第十一輪由原 `pkg/enum` 搬出）。
結果碼對應指標 `outcome` 標籤的轉換位於 `pkg/errcode`。

- `AuthServiceUnavailable`
  - 依賴服務不可用，可重試。
- `AuthSessionExpired`
  - session 或登入上下文已失效，不應直接重放舊鏈路。
- `AuthRecoveryMismatch`
  - `World` 恢復後與 `Gate` 狀態不一致，恢復失敗。
- `AuthRateLimited`
  - 帳號短時間內登入過於頻繁。
- `AuthWrongPassword`（code 13）
  - 密碼雜湊比對失敗，拒絕登入。

### 重試預算

不是所有錯都該重試。現在只把明確 transient 的狀況視為可重試：

- `AuthServiceUnavailable`
- `AuthRateLimited`

不重試的例子：

- `AuthSessionExpired`
- `AuthRecoveryMismatch`
- `AuthWrongPassword`
- `AuthServerFull`

`grant item queue` 另有自己的重試預算：

- 最多 `5` 次
- 最長 `5` 分鐘存活時間
- 退避：每次 `+1s`，線性增加
- 關機取消（ctx 已取消且錯誤為 `context.Canceled`）造成的失敗不是發放失敗：不計重試次數、不記失敗指標，指令留在 processing，重啟時回收重跑（`OperationID` 冪等）

### 錯誤碼標準化

`pkg/errcode` 目前只提供 `MetricOutcomeFromAuthResultCode`：結果碼對應指標的 `outcome` 標籤（原先的 `Class` 分類已移除）。

結果碼的重試判斷與 outcome 反查只有私有壓測與回歸工具使用，放在 `tools/private/internal/authcode`（`ShouldRetry`、`FromOutcome`），不在 `pkg/errcode`。

原則：

- HTTP 只用 canonical status，不自己發明新碼
- queue / RPC 只看 `ack / retry / drop`
- `AuthResultCode` 仍保留給 app 層決策與對外回覆
- 預算耗盡後直接進 dead-letter，不再留在 retry queue

## Request Journal

`request_id` 相關的去重與結果回放，統一由 `pkg/requestjournalredis` 管理：本機 FIFO 快取在前、Redis 在後，查不到本機時才讀 Redis 並回填。

目前使用範圍：

- `Central` login request replay
- `Central` logout request replay
- `World` login request replay（Gate 轉來的登入）
- `World` logout request replay
- `World` 擲骰（roll）與建築升級（upgrade）回應 replay：回應會扣款，Redis 寫入維持同步，回覆送出前 journal 已持久化；這兩個 journal 不合併並發查詢（同一玩家的指令固定在所屬盤面工作者依序執行）
- `Gate / World` recovery validation replay（World 端 validate journal 只存本機）

World 共五個 journal（login、logout、validate、roll、upgrade），集中於 `cmd/world/internal/app/request_journal.go` 的 `requestJournals`；登入、登出與驗證的 Redis 寫入交給持久化 worker，本機快取已同步更新。

規則：

- journal 只負責 `(scope, request_id) -> result` 的短期保存
- 寫進 Redis 的編碼：紀錄型別實作 `encoding.BinaryMarshaler`／`BinaryUnmarshaler` 時存「`0x00` ＋ 二進位」，其餘型別與舊紀錄維持 JSON（JSON 物件以 `{` 開頭，讀取時依首位元組分辨，新舊格式都解得開）。World 擲骰與建築升級的 replay 回應（`replayResponse`：2 byte 大端 MessageID ＋ 原始 payload）使用二進位，省掉 `[]byte` 經 JSON 變 base64 的約三分之一體積，這兩個請求在每次回覆前都同步 `SET`。TTL 只有 2 分鐘，不需要遷移；**滾動部署若在 2 分鐘內回滾到舊版**，舊版讀不到新格式的擲骰／升級紀錄，會當成未命中，Client 重送同一個 requestID 時可能多擲一次或多升一次（風險視窗只有 TTL 長度）
- `scope` 依鏈路決定，例如 `account` 或 `player_id`
- 只有同一個 `scope + request_id` 才能 replay；不同 `scope` 不能互撞
- journal 不處理 metrics；metrics 由各 handler 在命中點統一埋設
- 同一個 key 的並發 Redis 查詢以 singleflight 合併；合併的查詢不跟隨任一呼叫端的取消，只受 500ms 逾時限制，呼叫端只在發查詢前檢查一次 ctx，已在等待的呼叫端最多多等一個逾時，不會因自己的 ctx 提早返回。擲骰、升級 journal 用 `WithoutCoalescing` 不合併（同一玩家的盤面指令固定在同一個工作者依序執行，只有一個呼叫端），查詢直接跟隨呼叫端的取消與期限（盤面指令期限到或關機中止時不必等滿 500ms），仍受 500ms 上限；呼叫端自己取消不算後端故障，不記警告也不進冷卻
- Redis 讀寫失敗後進入 10 秒冷卻：冷卻期間只用本機快取、不碰 Redis（批次與逐筆刪除失敗同樣進入冷卻；刪除本身照常嘗試，避免留下舊回覆）。呼叫端多在事件迴圈上同步等待，Redis 卡住時只有冷卻開始的那一筆付出逾時代價；冷卻期間其他節點寫入的結果查不到，重送會被當成新請求
