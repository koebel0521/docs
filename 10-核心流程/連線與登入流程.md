# Session 與登入流程

這份文件描述目前專案中登入、登出、session、恢復校驗的實際規則。

## 鏈路契約總表

這一段只收斂最容易漂移的規則，避免 handler 與文件各講各話。

| 項目 | 規則 |
| --- | --- |
| `request_id` | 由 `Gate` 建立；跨服務鏈路共用；只做去重與結果回放。 |
| `trace_id` | 由 `Gate` 建立；跨服務鏈路共用；只做觀測與除錯。 |
| `protocol_version` | 由 `Gate` 建立；跨服務鏈路共用；目前只接受 `msg.ProtocolVersionV1`。 |
| `pending_login` | 只有在 `Gate` 確認能把登入請求送進 `Central` 後才建立。 |
| `pending_logout` | 只有在 `Gate` 已接住玩家登出請求後才建立；後續失敗也要先清本地 session。 |
| 可重試回傳碼 | 只保留 `AuthServiceUnavailable`、`AuthRateLimited`。 |
| 不可重試回傳碼 | `AuthSessionExpired`、`AuthRecoveryMismatch`、`AuthProtocolMismatch`、`AuthWrongPassword`、`AuthServerFull`。 |
| 失敗處理 | `SessionExpired`、`RecoveryMismatch`、`ProtocolMismatch` 與登入/登出失敗都要先清 pending 狀態，再回給玩家。 |

## 核心欄位

### `request_id`

- 用途：辨識同一筆 request/reply 鏈路，支援去重與結果回放。
- 建立位置：由 `Gate` 在玩家請求進入伺服器鏈路時建立。
- 傳遞範圍：同一筆登入、登出、恢復校驗的跨服務訊息都沿用同一個 `request_id`。
- 使用規則：
  - 原始玩家輸入訊息不攜帶 `request_id`。
  - `heartbeat`、`connect_info`、`time_sync` 等系統訊息不得使用。
  - `Central` 以 `account + request_id` 去重登入請求，重送時回放前次結果。
  - `Logout` 與 `recovery validation` 以 `playerID + request_id` 去重；不同 `scope` 就算 `request_id` 相同，也視為不同請求。

### `trace_id`

- 用途：串接跨服務日誌與觀測指標。
- 建立位置：由 `Gate` 在進入跨服務鏈路時建立。
- 傳遞範圍：同一筆登入、登出、恢復校驗的跨服務訊息都沿用同一個 `trace_id`。
- 與 `request_id` 的差異：
  - `request_id` 用於冪等與去重。
  - `trace_id` 用於觀測與除錯。

### `protocol_version`

- 用途：標示登入/登出/恢復校驗訊息的協定版本。
- 目前版本：`msg.ProtocolVersionV1`
- 規則：
  - `0` 會被視為目前版本，兼容舊 sender。
  - 同一條 request/reply 鏈路中的服務應透傳相同版本。
  - 目前只接受 `msg.ProtocolVersionV1`，其他值會回 `AuthProtocolMismatch`。
  - `protocol_version_blacklist` 可以在緊急回滾時先封鎖特定版本。

## 訊息中繼資料規範

定義位於 `pkg/msg/protocol.go`。

- `RequestMeta`
  - 只允許出現在可重放、可去重的 server-side request/reply 訊息。
  - 不允許用在 `heartbeat`、`connect_info`、`time_sync` 這類系統訊息。
- `TraceMeta`
  - 只允許出現在需要串接跨服務日誌的訊息。

## Gate Session 狀態機

定義位於 `cmd/gate/internal/app/app.go`。
實作上對應到 `UpsertPendingSession`、`BindSession`、`BeginLogout`、`DeleteSessionByKey`、`DeletePendingLoginSessions`、`SweepExpiredSessions` 這幾個入口。

### 狀態

- `pending_login`
  - 玩家已送出登入請求，等待 `Central/World` 回應。
- `logged_in`
  - 玩家已完成登入，`sessionKey <-> playerID` 綁定成立。
- `pending_logout`
  - 玩家已送出登出請求，等待 `Central/World` 完成鏈路。
- `disconnected`
  - session 已失效或已被刪除。

### 主要轉移

| 目前狀態 | 事件 | 前置條件 | 動作 | 下一狀態 |
| --- | --- | --- | --- | --- |
| 無 session | `LoginRequested` | `sessionKey != ""` | 建立或重設 pending session | `pending_login` |
| `pending_login` | `LoginSucceeded` | session 存在 | 綁定 `playerID/worldID`，寫入 `sessionKeyByUser` | `logged_in` |
| `pending_login` | `LoginFailed` | session 存在 | 刪除 session | `disconnected` |
| `logged_in` | `LogoutRequested` | session 目前為 `logged_in` | 切為 pending logout，保留快照給後續流程 | `pending_logout` |
| `pending_logout` | `LogoutCompleted` | session 存在 | 刪除 session，清掉反向索引 | `disconnected` |
| `pending_login` | `TimeoutSweeper` | 超過 Gate app 本地 `GatePendingLoginTTL` | 刪除 session | `disconnected` |
| `pending_logout` | `TimeoutSweeper` | 超過 Gate app 本地 `GatePendingLogoutTTL` | 刪除 session，必要時同步清理本地 user | `disconnected` |
| `logged_in` | `Heartbeat` | session 存在 | 更新 `LastSeenAt` | 不變 |
| 任意狀態 | `Disconnected` | socket 或上游失效 | 視情境刪除或標記無效 | `disconnected` |

### TTL 與清掃

Gate session policy 定義位於 `cmd/gate/internal/app/app.go`。

- `pending_login`
  - 超過 `GatePendingLoginTTL` 會被 sweeper 清掉。
- `pending_logout`
  - 超過 `GatePendingLogoutTTL` 會被 sweeper 清掉，並同步清理本地 user/session。
- `logged_in`
  - heartbeat 會更新 `LastSeenAt`，供觀測與後續擴充使用。

### 玩家心跳

玩家心跳相關的 timeout 與輪詢間隔現在由 `cmd/gate/internal/handler/user/event.go` 以本地常數持有。

- `userHeartbeatTimeout`
  - 超過此時間未收到心跳就視為斷線。
- `userHeartbeatCheckInterval`
  - Gate 會以此間隔輪詢玩家心跳是否逾時。

## 服務失聯策略

Gate / World 失聯寬限定義位於 `cmd/gate/internal/app/app.go`。

- `cmd/gate/internal/app/app.go` 與 `cmd/world/internal/app/app.go` 的 `ServiceDisconnectGracePeriod`
  - Gate <-> World、World <-> Gate 斷線後，不立即清理玩家狀態。
  - 先標記為暫時失聯，等待短暫抖動恢復。
  - 在 grace 內重新收到 `ConnectInfo` 時，必須清除 unavailable 標記，保留原 session / user 狀態。
- `cmd/gate/internal/handler/world/event.go` 與 `cmd/world/internal/handler/gate/event.go` 的 sweep interval 常數
  - 定期檢查失聯寬限是否到期。

### Central 遇到 Central 斷線

- 斷線當下：
  - 先移除 dead central 的 ring 節點。
  - 已登入玩家的 `sessionCentral` 仍要遷移到其他存活 Central。
  - 就算 `AppUser` service 暫時不可用，也不能因此跳過路由遷移。
  - 所有 `pending_login` session 也要立即清掉，就算 `Services` 暫時不可用也不能只靠 TTL 等它自己過期。
- 若找不到可用 Central：
  - 先保留現有登入狀態。
  - 後續 logout 再嘗試重新路由。

### Gate 遇到 World 斷線

- 斷線當下：
  - 只標記該 world_id 為 unavailable。
  - 保留玩家 session 與本地在線狀態。
- 若 World 在寬限期內重新連上：
  - 清除 unavailable 標記。
  - 已在線玩家繼續沿用原 session，後續由 World 自己的恢復校驗決定是否收斂。
- 若超過寬限仍未恢復：
  - Gate 清理該 World 上的玩家與 session。
  - 通知 Central 清理 route。
  - 回 AuthServiceUnavailable 給玩家。

### World 遇到 Gate 斷線

- 斷線當下：
  - 只標記該 gate_id 為 unavailable。
  - 保留 World 內玩家狀態。
- 若 Gate 在寬限期內重新連上：
  - 清除 unavailable 標記。
  - World 端玩家與 channel 狀態維持不變。
- 若超過寬限仍未恢復：
  - World 才清理該 Gate 代理的玩家。
  - observer、player store 與 game data 的清理鏈路才會真正觸發。
## Gate 優雅排空（Graceful Drain）

用於 rolling deploy：先讓玩家自然下線，避免強制斷線。

**三步流程**（`cmd/gate/internal/main.go` defer LIFO）：

1. **停止接受新連線** — `userSvc.StopAccepting()` 關閉 listen socket，既有連線保留
2. **等待自然排空** — 最多等待 Gate 預設的 `30s` 排空時間（可透過 `drain_timeout` config 覆寫；壞值會被忽略）
3. **強制斷開剩餘連線** — 超時後對每個仍在線玩家送出 `LogoutResponse`（`AuthServerFail`）並關閉 socket

**相關 policy**：
- Gate 預設排空時間 = `30s`

**設定覆寫**（`config/dev/gate.yaml`）：
```yaml
drain_timeout: 60s  # 預設不設定則用 policy 值
```

## 服務責任邊界

### Gate

- 接收玩家登入/登出請求。
- 建立 `request_id`、`trace_id`、`protocol_version`。
- 管理玩家連線與 session 狀態機。
- 玩家連線的 per-socket rate limiter 由 `cmd/gate/internal/main.go` 在服務建構期注入，不再由 `Connect` 期 setter 設定。
- 在入口做帳號維度限流與短期鎖定。
- 將登入請求轉送到 `Central`，將 `World/Central` 結果回給玩家。
- 在 `World` 重啟恢復時，回覆玩家是否仍在線的主動校驗請求。
- `OnlineCount` 與 Lobby 負載回報只算 `logged_in`，`pending_logout` 不算在線。

### Central

- 作為帳號與登入結果的協調者。
- 以 `account + request_id` 做登入去重與結果回放。
- 決定玩家應進入哪個 `World`，可依 `traffic_slice_percent` 將少量帳號導向 canary world。
- `traffic_slice_percent` 的啟動與 hot reload 都走 `cmd/central/internal/app/traffic_slice.go` 的 `WithTrafficSlice(...)`，不再靠 setter。
- 維護 `account/user/world/gate` 對照。
- 接收 `Gate` 的登出請求並轉送給 `World`。

### World

- 作為玩家實際所在的遊戲節點。
- 處理登入最終接受或拒絕。
- 維護 `user <-> gate` 綁定。
- 持久化與恢復玩家狀態。
- 重啟後先從 store 還原，再向 `Gate` 主動校驗玩家是否仍在線。
- `World` 的容量判定只算 `GateID != 0` 的 active player，避免 logout 後殘留的 `GateID=0` user 卡住新登入。

### Chat

- 作為文字聊天的獨立服務。
- 處理跨世界聊天、全服聊天、聊天歷史、審核、禁言與離線補送。
- 其他 Service 可以直接送 `ChatSystem` 進來，由 `Chat` 統一轉成 `ChatDeliver` 派送。
- 玩家可送 `ChatSync`，以 `SinceMessageID` 當 hint，向 `Chat` 補拉同一個 room 的歷史訊息。
- `ChatDeliver` 會帶 `MessageID`，client 可用它做去重與下一次 sync 起點。
- 聊天歷史以 `MySQL` 為 source of truth，`ChatService` 只做即時廣播與查詢入口。
- `Gate` 只負責把玩家文字聊天請求轉進 `Chat`，再把 `Chat` 的派送結果送回玩家。
- `World` 內的 `Channel*` 只保留給世界廣播群組，不再承擔文字聊天主流程。

## 主要鏈路

### 登入

1. 玩家送 `LoginRequest`（含 `Account`、`AccountType`、`Password`）
2. `Gate` 驗證輸入、限流，確認 `Central` 轉發路徑可用後才建立 pending session
3. `Gate` 建立 `request_id` / `trace_id`，開啟 OTel Span `gate.login.forward`
4. `Gate -> Central`（攜帶 `Password`）
5. `Central` 做去重、查帳號、**驗證 bcrypt 密碼**、選擇 `World`（必要時先走 traffic slice）；開啟 OTel Span `central.login`
6. `Central -> World`；開啟 OTel Span `world.login.assign`
7. `World` 決定接受或拒絕
8. `World -> Gate`
9. `Gate` 成功時 bind session，失敗時清掉 pending session
10. `Gate -> User`

`Central` 會在 `World` 轉發成功後才寫入本機 `user / gate / world` 路由；若 `World` socket 不可用，不能留下半套登入狀態。
`Central` 若 `Services` 暫時不可用，也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能讓 pending session 一直卡到 sweeper。
`Central` 若 `App` 暫時不可用，也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能靜默吞掉登入請求。
`World` 端也必須先確認目標 `Gate` 仍在線，再做舊綁定清理與新綁定更新；否則只會把舊 gate 先踢掉，卻沒真正完成登入。
如果 `Gate` 端收回 World 回應時 `user socket` 已消失，仍要清 session 並通知 `Central` rollback，不能直接沉默離開。
`Gate` 也不能在 `Central` 或 `Central socket` 不可用時先寫 `pending_login`，否則會卡一筆假 session。
`Gate` 收到 `World` 的登入回應時，如果 `AppUser` 不在，也要先清掉 pending session，能回滾就回滾 `Central`，不能把假狀態留到 sweeper。
`Gate` 收到 `Central` 的登入失敗通知時，就算 `AppUser` service 不在，也要先清掉 pending session，不能留到 sweeper 才收。
`World` 收到登入請求時，若 `App` 不在，若能找到 `Gate` 也要直接回 `AuthServiceUnavailable`，不能讓 `Gate` 卡住。
`World` 收到登入失敗回應時，不能先踢舊 gate 或重綁 `GateID`；只要把失敗碼回給 `Gate` 就好。
`World` 只有在登入成功分支才會 rebind 舊玩家與踢舊 gate；失敗回應仍要先回玩家失敗碼，再回滾 `Central`，不改綁定。
若 `World` 已回成功但 `BindSession` 仍失敗，也要通知 `Central` rollback，不能只回玩家 `SessionExpired`。
`World` 的 logout replay 命中時，就算 `AppGate` service 暫時不可用，也不能 panic。
`Gate` 發起登出時，也要先確認 `Central` / `Central socket` 可用，再把 session 推進 `pending_logout`，否則中央沒回時會留下半套登出狀態。
`Gate` 收到 `World` 的登出回應時，就算 `Services` / `User` socket 已消失，也要清掉本機 user / session，不能留下 ghost user。
`Central` 收到 `Gate` 的登出請求時，如果 `World` socket 不在，也要先清掉本機 user，避免把已請求登出的玩家留成 ghost state。
`World` 收到 `Central` 的登出回應時，就算 `Gate` socket 不在，或 `ResponseCode=AuthProtocolMismatch`，也要先清掉本機 gate 綁定與後續清理，不能把玩家留在 world 內。

### 文字聊天

1. 玩家送 `ChatJoin` / `ChatLeave` / `ChatSend`
2. 玩家也可以送 `ChatSync`，要求從某個 `MessageID` 之後開始補歷史
3. `Gate` 只做登入狀態檢查與轉發，將文字聊天請求送到 `Chat`
4. `Chat` 管理房間成員、審核、禁言、歷史與 sync
5. `Chat` 對在線玩家派送 `ChatDeliver`
6. `Gate` 收到 `ChatDeliver` 後派送給本地玩家 socket

`World` 的頻道訊息只提供世界廣播群組，不再作為文字聊天主流程；頻道由 Server 依 `(channelType, channelID)` 管理，Client 不提供加入、離開或發送頻道操作。World 透過 `ChannelBroadcast` 將原始 Client 協定送給 Gate，再由 Gate 依本地成員投影 fanout；成員變更則透過 `ChannelMembershipUpdate` 同步。

World 與 Gate 完成 `ConnectInfo`（包含 Gate 重連）後，World 會再送出 `ChannelMembershipSnapshot`，內容包含該 Gate 玩家目前所有 `(channelType, channelID, playerID)` 關係。Gate 會先取代該 World 的本地頻道投影，再接收後續的 `ChannelMembershipUpdate` 增量同步；空快照也會清除該 World 的舊投影。

**密碼驗證規則**（Central）：
- 首次登入（帳號不存在）：以 bcrypt cost=10 雜湊密碼，存入 MySQL `password_hash` 欄位
- 再次登入：從 Redis 快取或 MySQL 取出 `password_hash`，以 `bcrypt.CompareHashAndPassword` 驗證
- `password_hash` 為空（舊帳號遷移）：跳過驗證，保持向下相容
- 密碼錯誤：回傳 `AuthWrongPassword`（code 13）

### 登出

1. 玩家送 `LogoutRequest`
2. `Gate` 將 session 從 `logged_in` 切到 `pending_logout`
3. `Gate -> Central`
4. `Central -> World`
5. `World` 先確認 `Gate` 仍可接收，再清理玩家狀態並通知 `Gate`
6. `Gate` 清理本地 user/session
7. `Gate -> User`

若 `Gate` 收到 `LogoutWorldToGate` 時 `User` service 暫時不可用，會直接略過，不會因為缺服務而把登出流程炸掉。
若 `Gate` 收到 `LogoutWorldToGate` 的 `AuthProtocolMismatch`，也會清掉本地 user / session，避免把已失效的登入態留在 Gate。
若 `Gate` 收到 `LogoutWorldToGate` 的 `AuthSessionExpired`，也要清掉本地 user / session，不能讓過期 session 留成 ghost user。
若 `Central` 無法把 logout 送到 `World`，會直接回 `LogoutWorldToGate(AuthServiceUnavailable)` 給 `Gate`；`Gate` 收到這種回應也要清掉 pending logout，不能卡住。
若 `Central App` 暫時不可用，logout 也要直接回 `AuthServiceUnavailable` 給 `Gate`，不能把 pending logout 留到 TTL。
若玩家在 `pending_login` 時主動 logout，`Gate` 也要先清掉 pending session，再回 `AuthLoggedOut`，不能讓晚到的登入回應把人又綁回來。
若 `Gate` 的 `App` 暫時不可用，logout 也要直接回 `AuthServiceUnavailable`，不能靜默吞掉請求。
若 `Gate` 的 `App` 暫時不可用，收到 `World` 的登入成功回應也要直接回 `AuthServiceUnavailable`，並盡量回滾 `Central`，不能把半套登入留在後面。
`Central` 斷線後，Gate 會把綁在死 central 的 `sessionCentral` 一起遷走，`pending_logout` 也不例外，避免路由一直指向死節點。
`World` 斷線後的清理 sweep 不能因 `Services` 暫時不可用而停掉，至少要先把本機 `user` 狀態清乾淨。
`Gate` 收到 `ValidateWorldToGate` 時，若本機 `App` 不在，也要回 `AuthRecoveryMismatch`，讓 `World` 自己清殘留。

### World 重啟恢復

1. `World` 從 player store 還原玩家狀態
2. 經過 `WorldRecoveryGracePeriod` 後開始對帳
3. `World` 對每個恢復玩家送 `ValidateWorldToGate`
4. `Gate` 檢查該 `playerID/worldID` 是否仍為有效 session
5. `Gate -> World` 回覆成功或 `AuthRecoveryMismatch`
6. `World` 對失敗玩家清掉記憶體與 store 殘留
7. `Gate` 若找不到對應 user socket，也要清掉本地 user / session，避免留 ghost user
8. `Gate` 若 `world_id` 對不上，或無法確認 user socket，也要清掉本地 user / session，避免留下錯綁定

### World Crash Window

這段是 `World` crash 後到 `restore + validate + cleanup` 完成前的「可接受不一致窗」。

規則：

- `restorePlayers` 只回復候選玩家，不代表已經真正常在線上。
- `WorldRecoveryGracePeriod` 內，`Gate` 可能還在重連，這段時間要保留恢復出的玩家狀態。
- `reconcileRestoredPlayersOnce` 之後，只有通過 `ValidateWorldToGate` 的玩家才算保留成功。
- `restorePlayers` 只會重建 `GateID != 0` 的候選玩家；`GateID = 0` 的殘留紀錄會直接丟棄並從 store 清掉。
- `reconcileRestoredPlayersOnce` 在 `Gate` service 暫時不可用時，仍要清掉已恢復但無法驗證的玩家，不能把殘留掛到下一輪。
- 超過 grace 仍找不到有效 `Gate` 的玩家，要清掉 memory 與 Redis 殘留。
- 清理時要連同 `channels` 一起拔掉，不能只刪 user / route。

可丟資料：

- `World` memory player state
- Redis player store 中尚未驗證成功的恢復候選

不可丟資料：

- MySQL `user` / routing 資料
- 已經成功寫入 MySQL 的玩家資料（道具、盤面）

最長遺失窗：

- player presence 最多只在 `WorldRecoveryGracePeriod` 內保持不一致

## 錯誤語意

回傳碼定義位於 `pkg/enum/return_code.go`。
標準分類與 HTTP / queue 對應位於 `pkg/errcode`。

- `AuthServiceUnavailable`
  - 依賴服務不可用，可重試。
- `AuthSessionExpired`
  - session 或登入上下文已失效，不應直接重放舊鏈路。
- `AuthRecoveryMismatch`
  - `World` 恢復後與 `Gate` 狀態不一致，恢復失敗。
- `AuthProtocolMismatch`
  - 協定版本不相容，或該版本已被黑名單封鎖，請更新到支援版本。
- `AuthRateLimited`
  - 帳號短時間內登入過於頻繁。
- `AuthWrongPassword`（code 13）
  - 密碼雜湊比對失敗，拒絕登入。

### 重試預算

不是所有錯都該重試。現在只把明確 transient 的狀況視為可重試：

- `AuthServiceUnavailable`
- `AuthRateLimited`

不重試的例子：

- `AuthSessionExpired`
- `AuthRecoveryMismatch`
- `AuthProtocolMismatch`
- `AuthWrongPassword`
- `AuthServerFull`

`grant item queue` 另有自己的重試預算：

- 最多 `5` 次
- 最長 `5` 分鐘存活時間
- 退避：每次 `+1s`，線性增加

### 錯誤碼標準化

`pkg/errcode` 會把內部回傳碼收斂成三層語意：

- `Class`：`ok / auth / state / capacity / retry / internal / client`
- `HTTPStatusFromAuthResultCode`
- `TransportOutcomeFromAuthResultCode`

原則：

- HTTP 只用 canonical status，不自己發明新碼
- queue / RPC 只看 `ack / retry / drop`
- `AuthResultCode` 仍保留給 app 層決策與對外回覆
- 預算耗盡後直接進 dead-letter，不再留在 retry queue

## Request Journal

`request_id` 相關的去重與結果回放，現在統一由 `pkg/requestjournal/journal.go` 管理。

目前使用範圍：

- `Central` login request replay
- `Central` logout request replay
- `World` logout request replay
- `Gate / World` recovery validation replay

規則：

- journal 只負責 `(scope, request_id) -> result` 的短期保存
- `scope` 依鏈路決定，例如 `account` 或 `player_id`
- 只有同一個 `scope + request_id` 才能 replay；不同 `scope` 不能互撞
- journal 不處理 metrics；metrics 由各 handler 在命中點統一埋設
