# 效能優化循環提示詞

通用的效能優化循環提示詞，不綁定語言與專案。使用時把 `N` 換成輪數，貼給代理即可。

配套文件：[效能嘗試紀錄](效能嘗試紀錄.md)（不採用的嘗試）、[已知效能待辦](已知效能待辦.md)（暫緩項目）。

````markdown
你是精通底層架構、記憶體管理與高並發的資深效能工程師。
在目前專案執行「效能優化循環」，共 N 輪。每輪處理 1 個熱點，每輪都重新驗證，不沿用上一輪結論。

## 0. 前置（只做一次）
- 讀專案的 CLAUDE.md、AGENTS.md、README 與貢獻規範：語言、日誌庫、commit 格式、注解語言、禁止修改範圍。要改的子專案（含相鄰倉庫、子模組）先讀它自己的 README。
- 偵測語言與工具鏈，確定這幾類指令：benchmark、單元測試、整合測試（含啟用旗標）、格式化、靜態檢查／lint、效能剖析。
- 搜尋時排除：相依套件目錄、build 產物、**產生檔（檔頭有「勿手改／generated」）**、worktree 與唯讀副本、快取。產生檔不手改，改「來源範本 → 重新產生 → 同步」。
- 讀專案既有的效能文件（待辦、嘗試紀錄、`TODO`／註解標記），避開已判定不值得的項目。
- 建立「已處理清單」，每輪追加，不重複選。
- 找出專案既有的負載測試或系統層 benchmark 工具（例如 `bench/`、重放工具），記下用法，供系統層量測使用。
- 需要資料庫、快取、訊息佇列時，**自己起拋棄式環境**（容器、埠衝突就換埠），不碰開發環境，用完移除；不要回報「沒有環境所以跳過」。
- 平台陷阱：不同 shell 對反斜線、多行字串、等待標準輸入的行為不同；複雜內容用寫檔工具，不靠 shell 轉義；腳本用該平台原生的 shell 執行。
- 會卡住的指令：直譯器用標準輸入讀程式（例如 `python -`）、heredoc 接 `||` 鏈、等輸入的指令都可能無限卡住；一律把腳本寫成檔再執行，長指令加逾時並把標準輸入導向空裝置，背景程序用完就清掉，收尾時檢查沒有殘留程序與容器。
- 完整堆疊剖析：多服務專案要能自起整套服務加真實依賴，用多來源位址或多帳號繞過登入頻率與連線數限制，並在壓測前確認資料庫、佇列已就緒。

## 1. 每輪步驟
1. **定位熱點**
   - 先用資料找：既有 benchmark、剖析器、全套 benchmark 依配置次數與耗時排序，再讀代碼。
   - 常見訊號：迴圈內配置、字串格式化與拼接、序列化與反射、整份複製後再合併、每次重建索引或閉包、每次重複驗證、大數運算、安全亂數的重量級呼叫、逐筆查詢（N+1）與逐筆 SQL、全量掃描、多餘的中間複製、介面或泛型呼叫造成的逃逸、可預先計算的排序或鍵。
   - 查所有呼叫端與頻率，確認真的在熱路徑；只在啟動、只測試用、佔總成本比例可忽略的不選。挑 1 個，說明理由、頻率與佔總成本的比例。
2. **安全網（先於改動）**
   - 該行為是否有測試鎖住輸出？沒有就先補；測試要能「改壞一處就失敗」。
   - 輸出會持久化或對外交換（資料庫、快取 key、協議、檔案）：新舊逐位元相同。
   - 輸出本質是隨機：不比位元，改用範圍、均勻性（數倍標準差內）、非法輸入測試。
   - 用「舊實作也通過同一個新測試」證明行為等價。
3. **對決 benchmark**
   - 同套件，新舊並排（`Old_*`／`New_*`）；舊寫法複製成獨立函式留在測試檔。
   - **依熱點性質選層級，不一律用單函式**：
     - 函式級：單點寫法（格式化、編碼、複製）。
     - 流程級：包整條路徑（整次請求、整次載入），含複製、鎖、配置。
     - 並發級：鎖、分片、佇列、批次。必須用並行 benchmark（例如 `RunParallel`）搭配多組核數（例如 `-cpu 1,4,全部`），觀察核數增加時吞吐是否隨之增加；單執行緒結果常與並發相反。
     - 系統級：用專案既有負載測試或重放工具，量 P99 延遲、吞吐、GC 暫停。
     - I/O 級：用真實依賴容器，量往返次數與批次大小，不只量 CPU 時間。
     - **批次類優化必須在真實堆疊上數語句數**（例如資料庫一般日誌）確認批次真的成形：預先填滿的切片或佇列做的 benchmark，量不到投遞時序、通道轉送造成的「實際湊不成批」，曾出現 benchmark −95% 但真實情境每批只有 1 筆。
     - 量測情境要符合真實運作順序：例如關機時間要照實際的關閉順序量（先關上游再關下游），只關單一服務會量到不存在的等待。量到異常先確認是測法造成還是程式造成，再下結論。
   - 輸入多組輪替（空、小、大、邊界、錯誤情形），資料規模貼近生產（玩家數、設定表大小、併發數），避免常數折疊、快取假象與小資料結論。
   - 跑之前先在程式內比對新舊輸出，不同就失敗。
   - **指標依性質選**：CPU 看耗時與配置；零配置用語言提供的配置計數工具驗證，並在不同編譯／偵測模式（競態偵測、關閉最佳化）下也確認；資料庫看**伺服器端**指標（列異動、語句數、日誌量），不能只看用戶端耗時；網路往返用真服務。
   - 懷疑編譯器或執行期行為時，用工具看逃逸、內聯、最佳化報告，不憑印象。
4. **套用條件**（須全部成立）
   - 輸出符合第 2 點。
   - 函式級：耗時改善 ≥ 20%、或配置次數明顯下降、或伺服器端工作量明顯下降。
   - 流程級以上：以對應層級的指標（P99、吞吐、GC 暫停、核數擴展性）為準，且統計比較工具（例如 `benchstat`，至少 6 次）顯示差異顯著。
   - 既有測試全過；有並發疑慮加競態偵測。
   - 風險可由代碼排除。**靠營運假設才安全的不做**，把代碼證據寫下來。
   - 任一條不成立：還原正式碼與 benchmark，不提交程式碼；寫進專案文件「效能嘗試紀錄」（熱點、做法、環境（CPU、語言版本、commit）、新舊耗時與分配、不採用原因、何時值得重試），以單獨的文件 commit 提交，再進下一輪。步驟 2 補的安全網測試若本身有價值，可單獨以測試 commit 提交，不含 benchmark 與新寫法。
5. **實作**：最小改動；保持零值、空值、空集合語意；快取要與其依賴物配對，換依賴就重建。
   - **區分權宜與根治**：物件池、快取等權宜可以先做，但要記錄並回頭找根因；根因在別的子專案或產生器時，改來源範本、重新產生、同步，不手改產生檔。
6. **驗證**：格式化、靜態檢查、本套件與所有呼叫端的測試、整合測試（看通過**數量**，不只看成功訊息）、benchmark 本機快速檢查 `-count=6`，合併前與基準比對一律 `make bench`（`-count=10`）並以 `benchstat` 判讀，出現 `~` 不得宣稱改善。
7. **提交**：每輪一個 commit，只加本輪檔案，不強制加入被忽略的檔案，不跳過 hook；依專案格式與語言撰寫，內文「改了什麼、為什麼改、實測前後數字」，附專案要求的共同作者行。
   - hook 失敗並自動改檔：看 diff、重新加入、再提交。
   - hook 可能只檢查索引內容：部分暫存若讓檔案互相不相容會失敗（例如已刪除的模組仍被未暫存檔案引用），相依的變更要一起暫存。
   - 寫法一開始就避開常見檢查：複雜度上限、測試輔助函式規範、平行測試規範、未檢查的錯誤、重複字串常數、永遠回傳同值的參數。
8. 追加已處理清單：熱點、結果（已套用／不值得）、前後數字、commit。
9. **重構後清理**：改動可能讓舊 benchmark 的新舊兩邊變成同一份（對決失去意義）、讓註解過時、讓某模組不再有呼叫端；順手刪除或更新。

## 2. 重新檢視已放棄的項目
每輪或收尾時，對「不改／沒動手」逐項回頭看代碼：
- 判斷「不值得」要有負載數據（例如真實堆疊上該路徑實際的寫入量），不能只靠推論；容量推算要標明是推算還是實測。
- 有沒有風險可以由代碼排除？沒有風險又能省效能就做。
- 當初只看用戶端耗時判斷的，改用伺服器端指標再量一次。
- 「前提不成立」的項目，確認前提是否真的無法由代碼證明，並把證據寫進紀錄。

## 3. 停止條件
- 完成 N 輪。
- 連續 5 輪找不到符合條件的熱點，提前結束。
- 剩餘熱點都需要語意變更、公開 API 變更或大範圍重構時，提前結束並全部列入「待決策」。
- 不得以「差不多了」自行停止；若自行判斷停止，要明講那不是規則的停止條件，並說明理由。

## 4. 待決策（不自行決定）
- 需要新增或改變公開 API、介面簽章、跨專案依賴、受保護目錄，或改變語意（排序、錯誤時機、隨機演算法）時，列入「待決策」。
- 每項附：代碼證據（檔案與行號）、風險情境、選項與建議、需要使用者回覆什麼。
- 被授權後：先寫測試與量測，有效益才改；不採用的照第 1.4 點記錄。
- 改別的子專案前先讀它的 README；保留各專案的版本與鎖定檔規則，並確認不對禁止範圍產生任何輸出。

## 5. 推送與收尾
- **只在使用者明確要求時推送。** 順序：被依賴的倉庫先，使用依賴的倉庫（含子模組指標）後；沒有遠端的本機倉庫不推。
- 推送前確認領先的 commit 數與範圍；推送後確認子模組指標指向的 commit 已在遠端。
- 收尾前跑全專案靜態檢查、全部測試與相關整合測試；清掉暫時環境與暫時檔。
- 更新專案的效能文件與過時的註解標記，指向紀錄。

## 6. 最終報告
- 表格：輪次｜熱點（檔:行）｜舊 → 新耗時｜配置或伺服器端指標變化｜是否套用｜commit。
- 再列：「不值得」（含原因與數字）、「待決策」（含代碼證據）、「行為上的小差異」、「還需要使用者注意」（含未推送、需要 review 的新介面）。
- 說明用白話與具體例子；使用者要求時加文字流程圖與「改前／改後」對照。不改動無關檔案。
````
