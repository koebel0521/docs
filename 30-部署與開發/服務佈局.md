# 服務目錄結構規範

本文件定義 `cmd/*/internal/` 下的目錄結構慣例，確保所有 service 遵循一致骨架。

關聯文件：
- [[工作規範]] — Cross-App 一致性原則的上層規範
- [[共用邊界]] — pkg/ 與 cmd/*/internal 的職責分界

---

## 概覽

每個 service 的 internal 結構統一如下：

```
cmd/{name}/internal/
├── app/                  ← 核心業務邏輯與狀態管理
├── flow/                 ← 多步驟工作流（選擇性）
│   ├── {domain}/
│   │   ├── coordinator.go
│   │   ├── doc.go
│   │   └── {step}.go
│   └── ...
├── handler/              ← 訊務處理器（依對端分組）
│   ├── {peer}/
│   │   ├── event.go
│   │   ├── {event_name}.go
│   │   └── ...
│   └── ...
├── services/             ← 依賴組裝與啟動
├── doc.go                ← package doc
├── main.go               ← 進入點
├── main_test.go          ← package-level 測試
└── run.go                ← 啟動流程（可選，部分 service 寫在 services/）
```

實際案例：

| 層級 | central | gate | world | chat | lobby | record | user |
|------|---------|------|-------|------|-------|--------|------|
| `app/` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `flow/` | ✅ | ✅ | ✅ | — | — | — | — |
| `handler/{peer}/` | ✅ | ✅ | ✅ | ✅ | ✅ | — | ✅ |
| `services/` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `store/` | ✅ | — | ✅ | ✅ | — | ✅ | — |

---

## 資料庫連線生命週期

Central、Chat 與 World 的資料庫連線由各自的 `run.go` 在啟動時建立，透過建構式傳入 store 或 service；服務結束時由同一個啟動層負責關閉。資料庫套件不得以 package-level 變數保存連線，也不得由業務 store 在每次操作時隱式建立連線。

## 目錄規範

### `app/` — 核心業務邏輯（必要）

每個 service 必須有 `app/`，包含：

- **`app.go`** — `App` struct 定義，包含該 service 的核心狀態與 event loop
- **`doc.go`** — app 層的 package doc
- **主測試** — `app_test.go` + `main_test.go`

業務邏輯依領域拆分多檔案，例如：
- `world/app/users_*.go` — 玩家狀態管理
- `gate/app/session_*.go` — Session 狀態機
- `central/app/user_routing_*.go` — 路由

**紅線：**
- ❌ 不放 handler 邏輯（handler 在 `handler/`）
- ❌ 不放依賴組裝（DI 在 `services/`）
- ❌ 不放持久層（persistence 在 `store/` 或外部 `pkg/`）

---

### `flow/` — 多步驟工作流（選擇性）

只在需要**跨多個 handler 或跨服務的多步驟流程**時才使用。目前適用的 service：

| Service | Flow | 說明 |
|---------|------|------|
| central | `flow/login/`, `flow/logout/`, `flow/syncuser/`, `flow/worldroute/` | 帳號登入/登出/同步/路由 |
| gate | `flow/user/login/`, `flow/user/logout/` | 玩家端登入/登出流程 |
| world | `flow/login/`, `flow/logout/` | World 端接收 Central 登入/登出請求 |

每個 flow 子目錄包含：

- **`coordinator.go`** — 流程編排入口
- **`doc.go`** — 該流程的職責說明
- **階段檔案** — 依流程步驟拆分（`preflight.go`、`persist.go`、`replay.go`、`route.go` 等）

**判斷是否該新增 `flow/`：**
- 如果流程跨越 3+ 個 step，且有明確的進入/離開/錯誤路徑 → 用 `flow/`
- 如果只是單一 handler 內部的條件分支 → 放 `handler/` 即可

**紅線：**
- ❌ 不要為只有 1~2 個步驟的邏輯開 `flow/`（放 handler 或 app 即可）
- ❌ 不要把 handler 的職責拉到 flow（handler 做 decode/validate/response，flow 做 orchestration）
- ❌ 不要跨 flow 共享狀態（透過 App struct 傳遞）

---

### `handler/` — 訊務處理器

依**對端（peer）服務**分組。每個子目錄對應一個外部服務，處理來自該服務的 TCP 訊息。

命名規則：`handler/{peer}/`

| Peer | 說明 |
|------|------|
| `gate/` | 來自 Gate 的訊息 |
| `central/` | 來自 Central 的訊息 |
| `world/` | 來自 World 的訊息 |
| `chat/` | 來自 Chat 的訊息 |
| `user/` | 來自 User（玩家）的訊息 |
| `admin/` | HTTP admin API handler（僅 lobby） |
| `discovery/` | 服務探索 handler（僅 lobby） |

每個 handler 子目錄包含：

- **`event.go`** — `EventHandler` 介面定義，Handler 的 dispatch table
- **`{event_name}.go`** — 各 event 的處理實作
- **`{event_name}_test.go`** — 對應測試
- **`doc.go`** — 該 peer handler 的職責範圍

Handler 的職責範圍僅限於：

1. 解碼與驗證請求（decode + validate）
2. 呼叫 `app/` 或 `flow/` 的業務邏輯
3. 組裝與回傳回應

**紅線：**
- ❌ 不放業務邏輯（只做 dispatch + 參數轉換）
- ❌ 不放持久層操作（透過 `app/` 或 `store/` 間接存取）
- ❌ 不以 event 類型分目錄（以 peer 分，不以訊息 ID 分）

---

### `services/` — 依賴組裝（必要）

負責建立 Service 實例、組裝依賴、啟動與優雅關機。相當於手動 DI container。

各服務保留明確的 `InitializeRuntime` 與 `InitializeObservability` 呼叫，因為不同服務的設定驗證、診斷端口與資源清理責任不同；不使用未被正式入口採用的共通 wrapper。

- **`run.go`** — Service 啟動邏輯（NewService → 建立 App → 建立 handler → 啟動 listener）
- **`services.go`** — Service struct 定義與依賴注入
- **設定邊界** — `run.go` 負責讀取 viper 並將設定注入 `app.Config`；`app/` 核心不得直接依賴 viper 全域狀態
- **服務依賴** — handler 透過 `Finder` 的具名方法取得服務（如 `World()`、`User()`），不得自行以 `AppName` 枚舉查找
- **建構子參數** — event 建構子只接受實際需要的型別，不使用 `...any` 相容參數掩蓋錯誤依賴
- **共用 Provider** — DI 只註冊服務實際使用的依賴；未被解析的連線 Provider 不應保留，避免生命週期無主
- **`{provider}.go`** — 特定依賴的建立（如 `redis_features.go`、`grantitem.go`）

所有 `services/` 的函式簽名應該在頂層 `run.go` 或 `main.go` 被呼叫，不從外部 module 引用。

**紅線：**
- ❌ 不引用外部 service 的 internal package（只引用 pkg/ 或其他公開 API）
- ❌ 不放業務邏輯（只做 wiring）
- ❌ 不引入 DI framework（目前採手動 DI，理由見[[工作規範]]）

---

### `store/` — 持久層（選擇性）

只在該 service 需要直接操作 MySQL/Redis/RecordMQ 時存在。命名慣例：

- `store/mysql/` — MySQL 連線與查詢
- `store/gamedb/` — World 的遊戲資料庫（獨立 go.mod 的 MySQL 連線）
- `store/gamestore/` — World 的遊戲資料存取層
- `store/playerstore/` — World 的玩家狀態存取
- `store/recordmq/` — Record 的 RabbitMQ 消費者設定

**紅線：**
- ❌ 不放純共用邏輯（共用邏輯在 `pkg/`）
- ❌ 不走複雜 ORM 抽象（使用 `pkg/mysql` 或標準 `database/sql`）

---

### 根目錄檔案

| 檔案 | 必要 | 內容 |
|------|------|------|
| `doc.go` | ✅ | Package doc，說明該 service 的職責 |
| `main.go` | ✅ | `func main()`，呼叫 `run.go` 或 `services/run.go` |
| `main_test.go` | ✅ | Package-level 測試設定（如 TestMain） |
| `run.go` | 選擇 | 啟動流程；可用於小 service，較大 service 放 `services/run.go` |

## 常見樣式

### Handler dispatch 慣例

```go
// handler/{peer}/event.go
type EventHandler interface {
    OnSomeEvent(ctx context.Context, msg *tcpruntime.Msg) error
}
```

每個 event handler 方法獨立檔案：

```go
// handler/{peer}/on_some_event.go
func (h *Handler) OnSomeEvent(ctx context.Context, msg *tcpruntime.Msg) error {
    // 1. decode
    // 2. validate
    // 3. call app/ or flow/
    // 4. build and send response
}
```

### Service wiring 慣例

```go
// services/run.go
func Run(ctx context.Context, cfg config.AppConfig) error {
    baseApp := appcore.NewBaseApp(...)
    service := NewService(baseApp, ...)
    return service.Start(ctx)
}
```

### Flow coordinator 慣例

```go
// flow/{domain}/coordinator.go
type Coordinator struct {
    app  *app.App
    log  *logger.Logger
}

func (c *Coordinator) Execute(ctx context.Context, req *Request) (*Response, error) {
    // step 1: preflight
    // step 2: route
    // step 3: persist
    // step 4: reply
}
```

## 例外與偏離

以下偏離是刻意為之，不應視為需要「對齊」：

| Service | 偏離 | 理由 |
|---------|------|------|
| world | 多出 `gm/`、`lifecycle/` | `gm/` 是 GM grant queue 的獨立子系統；`lifecycle/` 是 World recovery 的生命週期管理 |
| record | 無 `handler/` | Record 透過 RabbitMQ 消費事件，不走 TCP handler 模式 |
| user | 多出 `stdinevent/` | 測試客戶端透過 stdin 驅動事件，不走 TCP listener |
| lobby | `handler/` 下為 `admin/` + `discovery/` | Lobby 是 HTTP 服務，職責是 admin API + 服務探索，對應的 peer 命名與 TCP service 不同 |

這些偏離已在[[工作規範]]「不強制統一粒度」條款下獲得豁免 — 結構一致性的目標是幫助理解，不是強制所有 service 長得一模一樣。
