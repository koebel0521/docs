# 服務目錄結構規範

本文件定義 `cmd/*/internal/` 下的目錄結構慣例，確保所有 service 遵循一致骨架。

關聯文件：
- [[工作規範]] — Cross-App 一致性原則的上層規範
- [[共用邊界]] — pkg/ 與 cmd/*/internal 的職責分界

---

## 概覽

每個 service 的骨架如下（`main.go`、`run.go` 等在 `cmd/{name}/`，不在 `internal/` 底下）：

```
cmd/{name}/
├── doc.go                ← package doc
├── main.go               ← 進入點
├── main_test.go          ← package-level 測試（TestMain）
├── run.go                ← 組合根：讀設定、建立連線與依賴後交給 services
└── internal/
    ├── app/              ← 核心業務邏輯與狀態管理
    ├── flow/             ← 多步驟工作流（選擇性）
    │   └── {domain}/
    │       ├── coordinator.go
    │       ├── doc.go
    │       └── {step}.go
    ├── handler/          ← 訊務處理器（依對端分組）
    │   └── {peer}/
    │       ├── handler.go
    │       └── {event_name}.go
    ├── services/         ← 依賴組裝與啟動
    ├── store/            ← 持久層（選擇性）
    └── {domain}/         ← 領域子套件（依需要新增，見「例外與偏離」）
```

實際案例（以 `ls cmd/*/internal` 為準；`user` 是測試客戶端，在 `tools/user/`，不在 `cmd/`）：

| 層級 | central | gate | world | chat | lobby | record | user（`tools/user`） |
|------|---------|------|-------|------|-------|--------|------|
| `app/` | ✅ | ✅ | ✅ | ✅ | — | — | ✅ |
| `flow/` | ✅ | ✅ | ✅ | — | — | — | — |
| `handler/{peer}/` | ✅ | ✅ | ✅ | ✅ | ✅ | — | ✅ |
| `services/` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `store/` | ✅ | — | ✅ | ✅ | — | ✅ | — |

---

## 資料庫連線生命週期

Central、Chat 與 World 的資料庫連線由各自的 `run.go` 在啟動時建立，透過建構式傳入 store 或 service；服務結束時由同一個啟動層負責關閉。資料庫套件不得以 package-level 變數保存連線，也不得由業務 store 在每次操作時隱式建立連線。

## 目錄規範

### `app/` — 核心業務邏輯（有事件迴圈的 TCP 服務必要）

Central、Gate、World、Chat 與 `tools/user` 有 `app/`（Lobby、Record 例外，見「例外與偏離」），包含：

- **`app.go`** — `App` struct 定義，包含該 service 的核心狀態與 event loop（World 例外：`App` 定義在 `users_types.go`，沒有 `app.go`）
- **`doc.go`** — app 層的 package doc
- **主測試** — `app_test.go` + `main_test.go`

業務邏輯依領域拆分多檔案，例如：
- `world/app/users_*.go` — 玩家狀態管理
- `gate/app/session_*.go` — Session 狀態機
- `central/app/user_routing_*.go` — 路由

**紅線：**
- ❌ 不放 handler 邏輯（handler 在 `handler/`）
- ❌ 不放依賴組裝（DI 在 `services/`）
- ❌ 不放持久層（persistence 在 `store/` 或外部 `pkg/`）

---

### `flow/` — 多步驟工作流（選擇性）

只在需要**跨多個 handler 或跨服務的多步驟流程**時才使用。目前適用的 service：

| Service | Flow | 說明 |
|---------|------|------|
| central | `flow/login/`, `flow/logout/`, `flow/syncuser/`, `flow/accountpurge/` | 帳號登入/登出/同步/清除 |
| gate | `flow/user/login/`, `flow/user/logout/`（共用 `flow/user/flowbase/`） | 玩家端登入/登出流程 |
| world | `flow/login/`, `flow/logout/` | World 端接收 Central 登入/登出請求 |

每個 flow 子目錄包含：

- **`coordinator.go`** — 流程編排入口（`central/flow/accountpurge` 例外，以 `purge.go` 為入口）
- **`doc.go`** — 該流程的職責說明（`world/flow/login`、`world/flow/logout` 例外，package doc 寫在 `coordinator.go`）
- **階段檔案** — 依流程步驟拆分（`preflight.go`、`persist.go`、`route.go` 等）

**判斷是否該新增 `flow/`：**
- 如果流程跨越 3+ 個 step，且有明確的進入/離開/錯誤路徑 → 用 `flow/`
- 如果只是單一 handler 內部的條件分支 → 放 `handler/` 即可

**紅線：**
- ❌ 不要為只有 1~2 個步驟的邏輯開 `flow/`（放 handler 或 app 即可）
- ❌ 不要把 handler 的職責拉到 flow（handler 做 decode/validate/response，flow 做 orchestration）
- ❌ 不要跨 flow 共享狀態（透過 App struct 傳遞）

---

### `handler/` — 訊務處理器

依**對端（peer）服務**分組。每個子目錄對應一個外部服務，處理來自該服務的 TCP 訊息。

命名規則：`handler/{peer}/`

| Peer | 說明 |
|------|------|
| `gate/` | 來自 Gate 的訊息 |
| `central/` | 來自 Central 的訊息 |
| `world/` | 來自 World 的訊息 |
| `chat/` | 來自 Chat 的訊息 |
| `user/` | 來自 User（玩家）的訊息 |
| `timesync/` | Central 對 Chat、Lobby 的遊戲時間廣播連線（僅 central） |
| `admin/` | HTTP admin API handler（僅 lobby） |
| `discovery/` | 服務探索 handler（僅 lobby） |

每個 handler 子目錄包含：

- **`handler.go`** — `Handler` 結構（內嵌 `appcore.HandlerBase[App, servicefinder.Finder]`）、`App` 型別（Central、World、Chat 的 handler 宣告該 peer 需要的最小 `App` 介面，測試以替身實作；Gate 與 `tools/user` 只有一個實作且無替身，直接用具體的 `*app.App`），以及 `Connect`／`Disconnect`／`Init`；`Init` 以 `tcpruntime.AddMsgHandler` 註冊各訊息的處理方法（dispatch table）
- **`{event_name}.go`** — 各 event 的處理實作
- **`{event_name}_test.go`** — 對應測試
- **`doc.go`** — 該 peer handler 的職責範圍

Handler 的職責範圍僅限於：

1. 解碼與驗證請求（decode + validate）
2. 呼叫 `app/` 或 `flow/` 的業務邏輯
3. 組裝與回傳回應

**紅線：**
- ❌ 不放業務邏輯（只做 dispatch + 參數轉換）
- ❌ 不放持久層操作（透過 `app/` 或 `store/` 間接存取）
- ❌ 不以 event 類型分目錄（以 peer 分，不以訊息 ID 分）

---

### `services/` — 依賴組裝（必要）

負責建立 Service 實例、組裝依賴、啟動與優雅關機。相當於手動 DI container。

各服務保留明確的 `InitializeRuntime` 與 `InitializeObservability` 呼叫（在組合根 `cmd/{name}/run.go`，`cmd/{name}/internal/services` 內不呼叫），因為不同服務的設定驗證、診斷端口與資源清理責任不同；不使用未被正式入口採用的共通 wrapper。

- **`run.go`** — 匯出 `Run(ctx, app, tcpCfg, debugSrv, …)`，接收組合根建好的 App，再建立 handler、啟動 listener 與優雅關機（沒有 `NewService`）；Lobby 無此檔
- **`services.go`** — 只有依賴較多的服務（Gate、World）才有，放未匯出的 `start` 與 World 的 `Runtime`／`Options`；沒有 `Service` struct。Central、Chat、Record、`tools/user` 沒有此檔
- **設定邊界** — 組合根 `cmd/{name}/run.go`（與同層的 `services_config.go` 等）讀取 viper，解析成設定結構（例如 Gate、Central 的 `services.Config`）再傳入；`cmd/{name}/internal/services` 與 `app/` 都不接收 `*viper.Viper`
- **服務依賴** — handler 透過 `Finder` 的具名方法取得服務（如 `World()`、`User()`），不得自行以 `appname.Name` 枚舉查找
- **建構子參數** — event 建構子只接受實際需要的型別，不使用 `...any` 相容參數掩蓋錯誤依賴
- **共用 Provider** — DI 只註冊服務實際使用的依賴；未被解析的連線 Provider 不應保留，避免生命週期無主
- **`{provider}.go`** — 特定依賴的建立（如 `lobby_reporter.go`、`grantitem.go`）

所有 `services/` 的函式簽名應該在頂層 `run.go` 或 `main.go` 被呼叫，不從外部 module 引用。

**紅線：**
- ❌ 不引用外部 service 的 internal package（只引用 pkg/ 或其他公開 API）
- ❌ 不放業務邏輯（只做 wiring）
- ❌ 不引入 DI framework（目前採手動 DI，理由見[[工作規範]]）

---

### `store/` — 持久層（選擇性）

只在該 service 需要直接操作 MySQL/Redis/RecordMQ 時存在。命名慣例：

- `store/mysql/` — MySQL 連線與查詢（Central、Chat）
- `store/gamedb/` — World 的遊戲資料庫連線與 migrate（屬主 module，沒有獨立的 `go.mod`）
- `store/gamestore/` — World 的遊戲資料存取層：介面、資料表模型與記憶體常駐實作；MySQL 實作在子套件 `store/gamestore/mysqlstore/`
- `store/playerstore/` — World 的玩家狀態存取
- Central 的 `store/` 另有 `routingcache/`、`sharedstate/` 子套件；Chat 的 `store/mysql/schema` 為子套件；Record 的 `store/` 是扁平單一套件（RabbitMQ 消費端在共用的 `pkg/recordmq`，不在 Record 的 `store/` 下）

**紅線：**
- ❌ 不放純共用邏輯（共用邏輯在 `pkg/`）
- ❌ 不在 store 之上再疊 repository 泛型層；透過 `pkg/mysql`（GORM 封裝）存取，各服務 store 直接用 GORM，不是禁用 GORM

---

新增 main 套件須同步 `.gitignore`、`.dockerignore`、`Makefile` clean 的 binary 清單，由 archtest `TestMainBinariesListedInIgnoreFiles` 把關。

### `cmd/{name}/` 根目錄檔案

| 檔案 | 必要 | 內容 |
|------|------|------|
| `doc.go` | ✅ | Package doc，說明該 service 的職責 |
| `main.go` | ✅ | `func main()`，呼叫 `run.go` |
| `main_test.go` | ✅ | Package-level 測試設定（如 TestMain） |
| `run.go` | ✅ | 組合根：讀設定、建立 MySQL／Redis 等連線與依賴，再呼叫 `cmd/{name}/internal/services`；設定較多的服務另拆 `services_config.go`、`storage.go` 等同層檔案 |

## 常見樣式

### Handler dispatch 慣例

```go
// handler/{peer}/handler.go
type Handler struct {
    s2shandshake.ConnectInfoOnConnect
    appcore.HandlerBase[App, servicefinder.Finder]
}

func (h *Handler) Init(svc tcpruntime.Service) {
    tcpruntime.AddMsgHandler(svc, system.NewConnectInfo, h.onConnectInfo)
    tcpruntime.AddMsgHandler(svc, msg.NewSomeEvent, h.onSomeEvent)
}
```

每個 event handler 方法獨立檔案：

```go
// handler/{peer}/on_some_event.go
func (h *Handler) onSomeEvent(svc tcpruntime.Service, sock tcpruntime.Socket, m *msg.SomeEvent) {
    // m 已由註冊的 factory 解碼
    // 1. validate
    // 2. call app/ or flow/
    // 3. build and send response
}
```

### Service wiring 慣例

```go
// services/run.go（以 Chat 為例，節錄）
func Run(ctx context.Context, baseApp *app.App, tcpCfg *tcpconfig.Config, debugSrv *debug.Server) error {
    registry := tcpregistry.New()
    handler := gate.NewHandler(baseApp, registry)
    chatSvc := tcpserver.New(appname.Chat.Value, baseApp, handler, tcpserver.WithConfig(tcpCfg))
    registry.Register(chatSvc)
    go chatSvc.Start()
    // 傳外層 App，不傳 baseApp.AppBase（傳內層指標會繞過外層覆寫的 Stop／Shutdown，見 startup.RunTCPService godoc）
    return startup.RunTCPService(ctx, baseApp, registry, startup.DefaultShutdownTimeout,
        chatShutdownSetup(baseApp), nil, debugSrv.CheckStartupAndMarkStarted)
}
```

`app.App`、tcp 設定與 debug server 由 `cmd/{name}/run.go`（組合根）建立後傳入。

### Flow coordinator 慣例

```go
// flow/{domain}/coordinator.go（以 Central login 為例，節錄）
// App 是流程對 App 的最小依賴；*app.App 滿足此介面，不直接依賴具體型別。
type App interface {
    FindUser(ctx context.Context, id int64) (centralapp.User, bool)
    // ...只列本流程用到的方法
}

// gateGuard 不可為 nil（nil 時 panic）；policy 是首次登入自動建帳限制，零值不限制。
func New(app App, services servicefinder.Finder, store Users, gateGuard func(tcpruntime.Socket, func()) bool, policy NewUserPolicy) *Coordinator { /* ... */ }

// Handle 處理一筆請求，回傳結果的 metric 標籤。
func (c *Coordinator) Handle(ctx context.Context, sock tcpruntime.Socket, m *auth.LoginGateToCentral) string {
    // step 1: preflight
    // step 2: route
    // step 3: persist
    // step 4: reply
}
```

## 例外與偏離

以下偏離是刻意為之，不應視為需要「對齊」：

| Service | 偏離 | 理由 |
|---------|------|------|
| world | 多出領域子套件 `board/`、`condition/`、`faultinject/`、`gm/`、`itemaction/`、`lifecycle/`、`lottery/`、`mission/`、`outbox/`、`shardqueue/` | 遊戲規則與子系統各自成套件（`gm/` 是 GM grant queue、`lifecycle/` 是 recovery 與 record sink 生命週期、`faultinject/` 是故障注入開關），避免 `app/` 膨脹 |
| gate | 多出 `diag/`、`gm/`、`versioncheck/`（`centralring/` 已刪，Gate 對 Central 改主備模式） | 診斷端點、GM 踢人與封禁、Client 版本檢查各自成套件 |
| record | 無 `app/`、無 `handler/` | Record 沒有 TCP 事件迴圈：透過 `pkg/recordmq` 消費 RabbitMQ 事件寫入 `store/`，另以 HTTP 提供 `/events` 查詢，組裝都在 `services/` |
| lobby | 無 `app/`；多出 `auth/`（管理端權限層級與 bearer token 組的葉套件，不依賴 viper）、`gm/`、`notice/`；`handler/` 下為 `admin/` + `discovery/`，另有 `handler/servers.go`（`BuildServers`：discovery／admin HTTP server 組裝、IP 限速、請求期限與連線上限常數）；`services/` 放 token 熱重載（`TokenReloader`）與遊戲時鐘。`run.go` 只讀設定與接線（server 組裝放 `services` 會與 `handler/admin` 形成匯入循環，所以在 `handler`） | Lobby 是 HTTP 服務，沒有 TCP 事件迴圈與 App 狀態；職責是 admin API、公告與服務探索，對應的 peer 命名與 TCP service 不同 |
| user | 在 `tools/user/`；多出 `stdinevent/` | 測試客戶端不是正式服務；透過 stdin 驅動事件，不走 TCP listener |

這些偏離已在[[工作規範]]「不強制統一粒度」條款下獲得豁免 — 結構一致性的目標是幫助理解，不是強制所有 service 長得一模一樣。
