## 程式碼慣例

### Handler 模式

所有訊息處理器遵循統一簽名：

```go
func (r *Event) onMessageType(svc tcpruntime.Service, sock tcpruntime.Socket, m *Message)
```

- 第一個參數 `svc` — 來源服務
- 第二個參數 `sock` — 來源連線
- 第三個參數 `m` — 訊息本體

#### traceID 自動注入

dispatch 層（`pkg/tcpsocket/socket_events.go` 的 `msgEvent.Run()`）會自動從實作 `msg.TraceScopedMessage` 的訊息中提取 `traceID` 並注入 `sock.Context()`。Handler 不需要手動呼叫 `logger.WithTraceID`：

```go
var onLoginGateToCentralTimer = metrics.NewHandlerTimer("central", "on_login_gate_to_central")

// 正確 — traceID 已由 dispatch 層自動注入
func (r *Event) onLoginGateToCentral(svc tcpruntime.Service, sock tcpruntime.Socket, m *auth.LoginGateToCentral) {
	defer onLoginGateToCentralTimer.Start().Done()
	ctx, endSpan := tracing.StartSpan(sock.Context(), 0, "central.login")
	defer endSpan()
	logger.DebugCtx(ctx, "login request", "requestID", m.RequestID)
}
```

- `sock.Context()` 已自帶 `traceID`，無需 `logger.WithTraceID`
- `tracing.StartSpan(ctx, 0, ...)` 會從 ctx 自動讀取 `traceID`
- 背景 goroutine／非訊息入口處仍需手動 `logger.WithTraceID`
- 建立新 trace 的入口點（如 `forward.go`）仍手動呼叫 `NextTraceID`

#### 指標記錄

每個 Handler 必須記錄：
- **執行時間** — `game_handler_duration_seconds` histogram：套件層宣告 `var xxxTimer = metrics.NewHandlerTimer("服務", "handler")`，handler 開頭 `defer xxxTimer.Start().Done()`（label 預先解析、不配置記憶體，也不在 handler 直接呼叫 `time.Now`）；label 要執行期才知道時，在建構時解析成 `HandlerTimer` 再傳入（例：`system.BindConnectInfoOnly(timer, sock, m)`、`centralclock` 依 app 名稱建立）。同一服務的 `(service, handler)` 不可重複（`internal/archtest` 守門）：多個對端共用的處理方法要加對端前綴，例如 `<對端>_on_connect_info`（`world`／`chat`／`central`／`gate`／`timesync`）、`centralclock_on_connect_info`、`world_on_audit_snapshot_response`／`gate_on_audit_snapshot_response`，否則 P95／P99 告警分不出是哪個對端慢
- **結果碼** — success/fail label

### 日誌規範

- 以 [`日誌規範`](./日誌規範.md) 為準
- 新程式碼統一使用 `pkg/logger`，底層固定 `zerolog`
- 不要直接引入 `log/slog`、`logrus`、`zap` 作為新日誌入口
- 跨服務訊息必須攜帶 `trace_id` 欄位

### 錯誤處理

- 錯誤回應必須**立即發送**，避免玩家超時等待
- 所有 error 必須處理（errcheck linter 強制）
- error 回傳應包裹上下文語意（wrapcheck linter 強制）`fmt.Errorf("operation: %w", err)`
- 禁止 bare `fmt.Errorf("%w", err)` 空包裝（等同 `return err` 但多一次 allocation）
- 例外：`io.Closer.Close()` 和 `*sql.DB.Close()`

### 管理端權限

- Lobby 管理端依權限分層：`admin / ops / gm`
- `admin` 可通過所有管理端路由
- `ops` 用於踢人、封禁與世界維護
- `gm` 用於發道具與死信處理
- 新增管理端 API 時，先想好該掛哪一層，不要全塞進同一把 token

### 訊息關聯

- `request_id` — 用於請求去重（同一操作重送時保持不變）
- `trace_id` — 用於日誌串聯（每次新請求產生新 ID）
- 兩者分離，職責不同

### 效能慣例

- **TCP 層**：收發熱路徑用 `DecodePooled`/`WriteFrame`（緩衝取自物件池，header 與 payload 組進同一塊緩衝後一次 `Write`），不用 `Decode`；`BuildFrame` 只是測試輔助函式
- **Socket 連線**：發送佇列用原生 `chan tcpruntime.Msg`，深度預設 `tcpconfig.DefaultSocketSendQueueDepth`（10000），可用 `tcp.socket_send_queue_depth` 設定，不引入第三方無界佇列
- **World 狀態**：玩家索引取 `userMu`，不可直接取 `mu`（已移除）；頻道機制與 `chanMu` 已不存在
- **World user 查詢**：`map[uint64]*User` O(1)，不再用 rbtree
- **線上人數**：讀 `activePlayerCount.Load()`，不可遍歷 users map
- **atomic.Bool**：布林原子操作統一用 `sync/atomic.Bool`（Go 1.19+），不用 `gtype.Bool`
- **批次查詢**：以 `FindUsersByGate` 這類批次查詢取多位玩家，不可在迴圈內逐一 `FindUser`（頻道功能已移除，`ChannelMembers`／`ChannelMembersOfType` 不再存在）
- **Redis 批次**：大量 key 操作（如 Refresh、Restore）必須走 pipeline，不可循序單條呼叫
- **msgpool**：`Pack()` 緩衝走 `sync.Pool`，不可每次 `make([]byte)`
- **池化訊息的字串**：訊息會 `Put` 回物件池重用，解碼出的字串必須以一般 `string([]byte)` 複製，不可指向訊息內部緩衝（`UnsafeAppendString` 已因此移除：重用後已存進 `app.User` 的字串會被下一筆覆寫）
- **sync.Pool 歸還**：從 pool 取新物件替換舊物件時，舊的必須先 `Put()` 歸還
- **Redis 客戶端**：RESP3 預設啟用，不設 `AlwaysRESP2`；專案沒有使用 `DoCache`（`pkg/redis` 也不外露），所有設定一律 `redis.disable_cache: true`，不開 client-side caching（正式環境因此不送 `CLIENT TRACKING`）；由建立連線的啟動層負責在服務結束時呼叫 `Close()`
- **goroutine**：背景 goroutine 一律經 `GoBackground`（各服務 App，底層 `appcore.TaskGroup`）、`OwnerBase.Async` 或 `errgroup` 啟動，關機任務以 `appcore.WaitContext` 加期限等待；`TaskGroup` 在 Wait 期間仍允許 Add（關機 PreDrain 時 handler 仍會提交工作，`sync.WaitGroup` 會 panic）。只有確定不會在 Wait 期間 Add 的區域性 fan-out 才用 `sync.WaitGroup`（Go 1.25+ 用 `wg.Go`，fn 不可 panic）
- **AMQP 關閉順序**：`AsyncPublisher.Run` 在自己的 goroutine 執行；關閉時先 `AsyncPublisher.Stop(ctx)`（排空佇列、受關機期限約束），返回後才 `Publisher.Close()`，不可在排空期間關閉連線
- **型別斷言**：一律用 comma-ok 模式，裸斷言會 panic

### 程式碼品質

- **Getter 命名**：Go 慣例省略 `Get` 前綴，直接以欄位名作為方法名（`PlayerID()` 而非 `GetPlayerID()`）。
- **錯誤字串**：一律英文、首字母小寫、結尾不加標點；識別碼、設定鍵與縮寫（`S2S`、`SHA`、`max_players`）保留原樣。以套件或元件名當前綴（例如 `"redis: get key: %w"`），不用 `failed`／`err`／`error` 當包裝前綴，也不重複下層的前綴；包裝一律 `%w`（`errors.Join` 也是），外部來源的字串值用 `%q`。錯誤值可以帶 ID 等上下文，日誌 message 則固定。詳見[日誌規範](./日誌規範.md#錯誤訊息原則)。註解仍用中文。
- **Context.Background 禁止用於生產路徑**：何時傳 `sock.Context()`、何時用 `WithTimeout(WithoutCancel(ctx), d)` 見下方 [Request Context](#request-context)。
- **HTTP request 日誌**：所有 HTTP server 一律經 `httpx.NewPublicServer` 建立（`httpx.NewServer` 已刪除；外部 traceparent 只以 link 關聯），它會自動用未匯出的 `logging` 中介層包住 handler，記錄 method/path/status/elapsed 並計入請求耗時直方圖；內層的 `httpx.Recover` 擷取 handler panic（計 `PanicRecoveredTotal`、記 stack、回 500）。不要自行再包一層。
- **Pool 物件的 slice 賦值須拷貝**：從 pool 取得的訊息物件的 `[]byte` 欄位傳遞給非同步 consumer 時，必須拷貝 backing array（`dst = append(dst[:0], src...)`），避免 pool 回收後 backing array 被重寫導致的 data race。
- **context 參數禁止捨棄**：函式簽名收到 `ctx context.Context` 時必須使用，不得命名為 `_`。若底層 API 不支援 context，應自行包裝逾時控制（如 `dialWithContext` 模式）。
- **goroutine 安全**：所有 `go func()` 內部必須 `defer appcore.RecoverPanic("描述")`，避免單一 goroutine panic 拖垮整個 process。禁止直接寫 `recover()` — 統一用 `appcore.RecoverPanic` 確保 stack trace 被正確記錄。
- **長期迴圈 goroutine 使用 per-iteration recover**：無限 `for` 或 `for-select` 迴圈的 goroutine 不可在函式層級做 `defer RecoverPanic`，否則 panic 後整個 goroutine 靜默退出。應將 `defer RecoverPanic` 移至**每個 iteration 內部的匿名函式**，讓迴圈在 recover 後繼續運行。`stopCh`/`ctx.Done()` 等正常停止訊號留在外層 select，不受 recover 影響。
- **常數錯誤字串**：格式固定、沒有變數內插的錯誤字串使用 `errors.New` 而非 `fmt.Errorf`，減少不必要的格式化開銷。

### MySQL 連線與寫入

- 正式連線（`pkg/mysql`）的 DSN 開 `interpolateParams=true`，**不使用 GORM `PrepareStmt`**：`PrepareStmt` 在交易內每句都重新 PREPARE／CLOSE（`database/sql` 對綁在 Tx 的語句不重用），World 寫回與 outbox 幾乎都只在交易內執行，快取完全無效。量測見[效能嘗試紀錄](./效能嘗試紀錄.md)。
- 因為 `interpolateParams` 會把 `[]byte` 參數寫成 `_binary'…'`，**寫 JSON 欄位禁用裸 `[]byte`**（MySQL 回 Error 3144）：用 `string`，或用 `gamestore.JSONBytes`（底層 `[]byte`，`Value` 回 `string`、nil 寫 NULL，`Scan` 複製內容；`encoding/json` 仍編成 base64，spill 檔格式不變）。BLOB 欄位的 `[]byte` 沒問題。`PlayerStateArchive.Data`、`PlayerMissionState.ProgressJSON`／`FailureProgressJSON`、`RecordOutboxEvent.Payload` 已套用。
- World 的 gorm 模型每個欄位都明寫 `column:` tag（有測試守門）：欄位名不再由 Go 欄位名推導，改名不會讓 `AutoMigrate` 默默新增空欄位。寫進 Redis 的 request journal JSON 紀錄結構（登入、登出、驗證、replay）也都有 `json` tag，鍵名與舊輸出相同（`Code`、`PlayerID`、`WorldID`、`GateID`、`MessageID`、`Payload`），既有資料維持可讀。
- 啟動時 `VerifyDatabaseSchema`（比對 `schema_migrations`）有 10 秒逾時，MySQL 接受連線卻不回應時不會卡死在啟動階段。

### 遊戲系統與企劃工具解耦

未來遊戲系統需要提供工具給企劃測試與調整，遊戲功能應遵守以下原則：

- **規則資料化**：事件、事件群組、格子行為、條件、效果、獎勵與各種門檻，應由企劃工具管理的資料提供；Server 不應把可調整的規則寫死在流程程式中。
- **邏輯與傳輸分離**：遊戲判定邏輯不直接依賴 Client 或封包格式；協定只負責傳送請求與結果。
- **Client 只負責操作與顯示**：Client 不自行判定結果、事件觸發、事件成功與否或獎勵內容。
- **Server 保持唯一判定來源**：正式遊戲與企劃測試工具應使用相同的規則服務與判定邏輯，避免各自實作一份規則。
- **工具可獨立執行**：企劃工具應能載入同一份設定與事件資料，直接呼叫遊戲用例進行模擬，不必依賴 Client 畫面或完整連線流程。
- **資料存取與規則分離**：遊戲規則不直接依賴 MySQL、Redis 等儲存實作；資料透過明確的資料存取介面讀寫。
- **測試輸入可控制**：企劃工具與自動測試應能指定骰子結果或其他測試輸入，重現同一個流程與結果。
- **禁止直接修改外部產出檔**：由 `PJA-Config` 或 `PJA-Protocol` 工具產生、同步至 PJA-Server 的檔案不可直接修改，包含產生的 Go 程式碼、二進位設定資料與協定程式碼。
- **外部產出檔只能重新產生**：需要調整設定、資料或協定時，必須修改 `PJA-Config`／`PJA-Protocol` 的來源資料或定義，再執行對應工具產生並同步；不得在 PJA-Server 以手動修改或腳本覆寫產出檔的方式處理。

目前產出檔與 PJA-Server 同步路徑如下：

| 來源工具 | 來源產出路徑 | PJA-Server 同步路徑 |
|---------|-------------|---------------------|
| `PJA-Config` | `Output/Server/Code/` | `pkg/dataconfig/generated/` |
| `PJA-Config` | `Output/Server/Configs/` | `config/data/` |
| `PJA-Config` | `Output/version.json` | `config/data/version.json` |
| `PJA-Protocol` | `Output/Server/Code/message_id.go` | `pkg/protocol/message_id.go` |
| `PJA-Protocol` | `Output/Server/Code/wire/` | `pkg/protocol/wire/` |

上述同步路徑下的檔案皆視為產出檔，不得直接修改。

### Import 別名

- 預設不加別名，直接用套件宣告名。
- 只在必要時加別名：檔內另有同名識別字（import、區域變數、同套件頂層宣告）而衝突，或 goimports 要求（套件宣告名與路徑最後一段不同，別名即宣告名）。
- 同一路徑需要別名時，全專案用同一個別名（例：`gormlogger`、`worldapp`），不要各檔自取。

## Request Context

- **唯讀查詢、回覆前就可以放棄的工作**：傳 `sock.Context()`（或 handler 收到的 ctx），連線斷了就取消。
- **已受理、必須做完的寫入**（多步驟結算、盤面指令、登入寫入、登出清理、刪路由、request journal、outbox 標記）：用 `context.WithTimeout(context.WithoutCancel(ctx), 期限)`。脫離連線與 App 的取消，避免寫到一半被取消留下半套狀態，同時保留 traceID 與 span；期限讓它不會無限卡住。第三到第六輪修過的多個同類 bug，起因都是把這類寫入綁在連線或 App 的取消上。
- **交給其他 goroutine 的工作**：先在 handler 內同步取出 `sock.Context()` 再傳入。S2S 連線的 `sock.Context()` 是整條服務間連線的生命週期，不是單一請求；dispatch 注入 traceID 的 ctx 也只在 handler 同步執行期間有效。
- **不用 `context.Background()`**：背景工作與關機收尾也以 `WithoutCancel` 從現有 ctx 衍生，日誌才對得回原請求；只有行程入口（`startup`）與測試 stub 的 `Context()` 例外。

## 測試規範

測試類型與名詞的白話說明、各類測試的位置與執行方式見[測試名詞與類型說明](測試名詞與類型說明.md)。

### 通則

- 新增測試**首選 `t.Context()`** 而非 `context.Background()`，確保 goroutine 在測試結束時被 cancel
- 不要在 `t.Run` 閉包內呼叫 `t.Helper()`——該語句對 stack trace 無效，應直接將 subtest 寫為獨立的 `t.Run` 呼叫
- assertion 統一使用 `github.com/stretchr/testify/require` 與 `assert`，避免 raw `t.Fatalf` + `if got != want` 模式；既有手寫 `t.Fatalf` 的檔案是否全樹改寫尚未決定，目前只在改到該檔時順手轉換
- 前置條件（後面要取索引、解參考或依賴其結果）用 `require`，最終驗證用 `assert`；套用在新增或修改的測試，不做全樹機械改寫
- `require`／`t.Fatal` 只能在測試 goroutine 呼叫：背景 goroutine 與 `Eventually` 的 condition 內改用回傳 error 的 helper（例如 `testenv.TryReadMessage`），或改用 `EventuallyWithT` 對 `c` 斷言
- 平行子測試（`t.Run` + `t.Parallel()`）的前置閉包（setup／load）與共用 fixture 要接收**子測試自己的 `t`**，不可捕獲父測試的 `t`：前置條件失敗時才能指出是哪個案例，也不會對父測試呼叫 `FailNow`；計數變數等狀態移進各子測試，避免平行子測試共用未同步變數
- 斷言全域指標（Prometheus 計數器等）只看本輪增量（前後差），不要斷言絕對值；測試要能以 `-count=N` 重跑通過（需要時先清掉專屬序列，fake driver 不要每次 `sql.Register` 固定名稱，改用 `sql.OpenDB(connector)`）。會改寫或斷言全域狀態的測試維持序列
- `Eventually`／`EventuallyWithT` 的上限統一 5 秒、輪詢 10ms（避免 `-race` 與並行負載下偶發逾時，也避免 1ms 輪詢空耗 CPU）；condition 內不呼叫 `t.Fatal`。例外需在測試內註明理由：kick queue 退避測試用 4 秒（配合重試次數上限）、GM grant 多 worker 測試用 10 秒
- condition 內要查詢可能失敗的資源（MySQL、Redis、HTTP）時用 `EventuallyWithT`，在條件內 `require.NoError(c, err)`，逾時才看得到原因；`Never` 之後補一次確實的查詢並斷言，避免條件內一直出錯而空轉通過
- `testing/synctest` 氣泡內等待一律寫 `synctest.Sleep(d)`，不寫 `time.Sleep` 加 `synctest.Wait` 兩行
- Go 1.23 起計時器的 `Stop`／`Reset` 不會留下過期的值在 `C`，不必再手動排空 `timer.C`
- Stub 實作 `Context()` 方法時仍回傳 `context.Background()`（正確語意）
- Socket stub 優先使用 `pkg/testutil/fakes` 提供的 `NewSocket` + `SocketOption` factory，減少自訂 inline stub 的維護成本
- 每個有測試檔的目錄都要有 `TestMain`，並在其中呼叫 `goleak.VerifyTestMain(m)` 或 `testutil.VerifyTestMain(m)`；後者另外忽略函式庫自己的 goroutine（rueidis 的 LazyDo／DelayDo 延遲 singleflight、GORM 預備語句快取的 LRU 清理），用到 Redis 或 MySQL 的套件用它。`pkg/testutil` 本身匯入的套件為避免匯入循環直接用 goleak
- 測試檔以被測原始檔命名：新測試放進 `<source>_test.go`，檔案太大才拆成 `<source>_<concern>_test.go`，不要以情境另開檔名（如 `set_bounds_test.go`、`ring_empty_test.go`），否則同一個原始檔的測試會散在十幾個檔案，IDE 跳轉、覆蓋率對照與審查都得靠全文搜尋。既有約 873 個非原始檔命名的測試檔不做大搬；是否逐目錄合併尚未決定
- 斷言訊息語言：除有意凸顯的業務術語外，assert 的錯誤說明用**英文**（CI log 編碼相容性佳），測試內部註解與函式命名用**中文**（團隊慣例）

### 單元測試

- 在專案根目錄執行一次（`go test ./...`，涵蓋所有服務與 tools）
- 必須加 `-race` flag 偵測資料競爭
- 必須加 `-shuffle=on` flag 隨機化測試順序，抓出 inter-test 相依
- CI 中單元測試有 `-timeout=10m` 上限，防止 hung test 卡住 pipeline
- 使用 `pkg/testutil/fakes` 提供的 StubSocket、StubService
- CI `unit` job 分四片（依測試量平衡）：`./pkg/...`、`./cmd/world/... ./cmd/record/...`、`./cmd/gate/... ./cmd/lobby/... ./cmd/chat/...`、`./cmd/central/... ./internal/... ./tools/...`；帶 `integration` 標記的測試另由 `integration`、`e2e` job 執行
- 零配置守門測試（斷言 `testing.AllocsPerRun` 為 0）名稱一律含 `AllocatesNothing`：`-race` 會改變配置行為，這類測試在 `-race` 下 `Skip`，所以 `unit` 分片從未真正執行它們，改由不帶 `-race` 的 CI `alloc-guard` job（本機 `make ci-alloc`）跑；新增同類測試沿用這個名稱才會被納入
- 測試預設呼叫 `t.Parallel()`（paralleltest 強制）。會改寫全域狀態的測試維持序列，並以 `//nolint:paralleltest // 原因` 註明：`t.Setenv`、logger／tracer／故障注入／協定錄製／協定版本等全域設定、斷言全域 Prometheus 指標的增量
- 父測試底下有並行子測試時，共用資源用 `t.Cleanup` 釋放，不可用 `defer`：父函式回傳時並行子測試還沒開始執行
- 子測試彼此有先後依賴（後者讀前者寫入的資料）時不可並行

#### Windows race test

Windows 的 Go race detector 需要 `CGO_ENABLED=1` 與可用的 C compiler。先以 user scope 安裝 LLVM MinGW UCRT：

```powershell
winget install --id MartinStorsjo.LLVM-MinGW.UCRT --exact --scope user --accept-package-agreements --accept-source-agreements
```

再從專案根目錄執行 `.\scripts\test-race.ps1`。腳本會檢查 Go、CGO 與 `CC`，接著在專案根目錄執行一次 `go test -race -shuffle=on -count=1 ./...`（涵蓋所有服務與 tools）；它會自動尋找 PATH 或 WinGet user package 內的 `clang.exe`／`gcc.exe`，找不到 compiler 時會直接失敗並列出安裝指令，不會靜默跳過 race test。環境變數只在腳本程序內暫時設定。

### 整合測試

- 位於 `integration/` 目錄
- 所有測試檔案必須有 `//go:build integration` 標記
- 整合測試需帶 `-tags=integration`；`make ci-it` 跑 `integration/`，`make ci-it-pkg` 跑各套件內的整合測試（gamestore、recordmq、central/record store、tools 等）
- `testdb.Open` 經 `pkg/mysql.OpenDSN` 開連線，直接沿用正式的 GORM 與 DSN 設定（`SkipDefaultTransaction`、`SingularTable`、`parseTime`／`loc=UTC`／`time_zone`／`interpolateParams`），不再複製一份；`pkg/mysql` 的整合測試改為外部套件 `mysql_test`，沒有匯入循環。整合測試不支援 `PrepareStmt` session（加了之後 `CREATE TRIGGER` 類回滾測試會回 Error 1295）。
- 各套件整合測試以 `pkg/testutil/testdb` 開啟 MySQL：`testdb.Open(t, "WORLD_MYSQL_DSN", models...)` 會建立並改連「原資料庫名_套件名_雜湊」的套件專用資料庫，套件之間可並行，不需要 `-p 1`；同一行程內同一模型只 AutoMigrate 一次。測試 schema 必須等同正式遷移：`gamedb` 的整合測試 `TestMigrateMatchesAutoMigrateSchema` 在兩個全新資料庫分別跑 `AutoMigrate(Models()...)` 與 `gamedb.Migrate`，逐項比對欄位、索引並確認都沒有外鍵；`Migrate` 也會冪等移除既有庫遺留的盤面子表外鍵。GitLab 的 `integration` 與 `e2e` job 分別執行兩者
- 不帶 `-tags=integration` 時這些測試不會被編譯，也不會顯示跳過；改動 gamestore 等 MySQL 路徑時務必在本機或 CI 實際跑過
- 必須加 `-count=1` 禁用測試快取，避免快取結果隱藏服務互動的 flaky 問題
- 啟動真實 Central、Gate、World 子程序
- 透過 `testenv/` 建構測試環境，二進位檔只編譯一次後快取
- 二進位暫存檔在 `TestMain` 結束時由 `testenv.CleanupAll()` 自動清理；Windows 上服務子行程另外加入 Job Object，測試逾時或被強制結束時也會一併終止，不會留下佔用連接埠的程序
- `StartCluster`、`RestartGate` 會等 Gate 送出 `SyncUsersGateToCentral`（`FakeCentral.WaitForGateReady`）才返回：Gate 處理完 Central 的 ConnectInfo、把 Central 加入雜湊環後才會送，只等 TCP 連線就登入可能被 ServiceUnavailable 拒絕。手動組叢集且之後要登入時同樣改用 `WaitForGateReady`
- Gate、World、Chat、Lobby 收到 Central 第一則 TimeSync 前不接登入或不寫入：`FakeCentral` 與真實 Central 一樣在連線建立後立即送 TimeSync；`StartChat`、`StartLobby` 以 `startTimeCentral` 模擬 Central 的 chat／lobby 監聽（連線即送、之後每秒補送），等服務收到第一則才返回；真實叢集的 Central 設定含 chat／lobby 監聽，Chat 連真實 Central
- Central 每秒對 Gate 連線廣播 TimeSync，Gate 只用來校時、不轉發給玩家連線（Client 校時走 TimeSyncRequest）；讀取指定回應用 `testenv.ReadNext[T]`，它會略過 TimeSync 等系統訊息（直連 Central 的測試會收到），不要假設回應一定是下一則訊息
- 冒煙測試 `TestSmoke_*` 起真實 Central、World、Gate，檢查各服務 `/health`、`/ready` 與一次登入；CI 的 `e2e` job 先單獨跑它，叢集起不來就在一分鐘內失敗；完整測試改以 `-skip '^TestSmoke_'` 排除冒煙，不再重跑第二次（`make ci-it` 同）。真實叢集的服務各自用 `debug.addr` 綁空閒診斷埠（`RealCentralCluster.DebugPorts`），不搶預設的固定診斷埠
- 測試以 `-race` 執行時，`integration/testenv` 也以 `go build -race` 編譯 Central、World、Gate、Record 子行程，並在 `Cleanup` 檢查子行程 stderr 是否含 `DATA RACE`、`panic`、`fatal error` 與退出碼 66（race detector 的結束碼），任一項出現即讓測試失敗，不會因子行程內的競態被丟棄而假性通過；`Stop` 先送 `SIGTERM`，逾時 10 秒才 `Kill`
- 等待 Gate 重連／斷線不比對日誌字串：`Cluster` 為 Gate 配置診斷埠（`GateDebugPort`，`WriteGateConfig` 缺 `debug` 時補上），`WaitForGateWorldConnect`、`WaitForGateUserDisconnect` 讀 Gate `/metrics` 的 `tcp_connections_total`、`tcp_connections_active`，日誌格式或層級改動不會讓這些等待失效
- 故障注入用 `testenv.FaultProxy`（夾在服務與依賴之間的 TCP 代理，`Cut()`／`Restore()`），不依賴 docker 指令，本機與 CI services 都能跑；`StartRecordVia` 讓 Record 改連代理。崩潰用 `ServiceProcess.Kill`（`SIGKILL`）與 `RealCentralCluster.RestartWorldHard`；此類測試必須先斷言「中斷確實生效」，否則故障沒注入也會假性通過
- 登入遇到 `ServiceUnavailable`（叢集剛啟動）或 `RateLimited`（同帳號快速重登）是設計上可重試的回應：用 `loginAs`／`loginOnConn`／`logout` 等 helper，不要把它們當失敗；每次用新帳號（帶時間戳），資料庫跨次保留盤面與登入冷卻
- 同一來源 IP 在極短時間建立大量連線會碰到 Gate 的接入限流（每秒 10、burst 20）；要打這類場景的測試用 `setupGateWorldWith` 附加 `tcp.rate_limit_per_second`、`tcp.rate_limit_burst` 放寬，其他測試維持預設
- `TestSmoke_LoginLogoutExternal` 對已啟動的叢集做一輪版本握手、登入、心跳、登出，需設定 `IT_SMOKE_GATE_ADDR`（例如 `127.0.0.1:62001`）才會執行；帳號、密碼預設 `smoke_login_check`／`smoke-secret`，可用 `IT_SMOKE_ACCOUNT`／`IT_SMOKE_PASSWORD` 覆寫。叢集的發版資訊須與本倉庫相同，版本握手才會通過。登入到登出的步驟與 CI 冒煙測試 `TestSmoke_ClusterReadyAndLogin` 共用，不會再無人發現地腐化。用法：`IT_SMOKE_GATE_ADDR=127.0.0.1:62001 go test -tags integration -count=1 -run '^TestSmoke_LoginLogoutExternal$' ./integration/`
- 依賴服務預設使用 `docker-deps-up` 的連接埠：Redis `127.0.0.1:16379`、World MySQL `13306`、Central MySQL `13307`、RabbitMQ `25672`；其他位址以 `IT_REDIS_ADDR`、`IT_WORLD_MYSQL_HOST`／`IT_WORLD_MYSQL_PORT`、`IT_CENTRAL_MYSQL_HOST`／`IT_CENTRAL_MYSQL_PORT`、`IT_RABBITMQ_URL` 覆寫
- 整合測試會寫入固定 ID 的資料；要避免殘留在開發資料庫，用 `scripts/integration-deps-up.sh` 啟動專用依賴（埠號與開發環境錯開）並依它印出的環境變數執行，用完 `down` 移除
- 開發時可用 `INTEGRATION_SKIP_SLOW=1` 跳過 TTL expiry 等依賴真實時間等待的測試
- `testenv.Cluster` 的 `WaitReady`／`DialUser` 與 `RealCentralCluster` 的 `RestartWorldHard`／`DialUser` 使用建立叢集時的 `t`，只能在該測試的 goroutine 呼叫；需要子測試自己的 `t` 時用帶 `t` 參數的方法（`RestartGate(t)`、`RestartWorld(t)`）
- `TestGate_GracefulShutdown` 以 `ServiceProcess.Interrupt(timeout)` 對 `-race` 編譯的 Gate 子行程送 SIGINT 並斷言 drain 行為與結束碼；Windows 無法對子行程送 SIGINT，明確 Skip，只在 Linux／CI 驗證
- 已知：`TestRecordFault_RabbitMQOutage_NoEventLoss` 在 Windows 本機必定失敗（基準版本同樣失敗，疑 `FaultProxy.Cut` 在 Windows 沒有切斷既有連線），Linux 容器內與 CI 通過，尚未修

### 結構性測試

- 六個「程式與文件對照」測試只在有 docs 工作樹（主倉庫的 `docs/`，被 `.gitignore` 忽略）的本機跑，CI 沒有 docs 倉庫一律 Skip：`internal/archtest/docs_links_test.go`、`cmd/central/internal/app/account_lock_timing_test.go`、`pkg/grantitem/key_schema_doc_test.go`、`pkg/recordevent/type_literals_test.go`、`pkg/rediskeys/hash_field_names_test.go`、`pkg/rediskeys/schema_doc_contract_test.go`。改 Redis key schema、事件型別字串、鎖定時序時，請在本機有 docs 工作樹的情況下跑一次（CI 要跑需在 GitLab 設定 docs 倉庫的唯讀憑證，尚未設定）
- 掃描原始碼的結構性測試（`internal/archtest`）略過隱藏目錄與 `testdata`：有 worktree 的開發機（`.claude/worktrees`）不會因掃到其他工作樹而誤報。
- `TestTestPackagesHaveGoroutineLeakDetection`（`pkg/pkg_goleak_test.go`）驗證每個有測試檔的目錄都有 `TestMain`，且函式本體呼叫 `goleak.VerifyTestMain` 或 `testutil.VerifyTestMain`（TestMain 可寫在任何檔名，`integration/` 的寫在 build tag 限定的 `test_main.go`）；隱藏目錄、`testdata` 與本機私有的 `tools/private` 不檢查

### 覆蓋率

- CI 執行單元測試並保存覆蓋率；全專案覆蓋率只做趨勢觀測，新增／修改程式碼的 patch coverage 目標為 **≥ 60%**
- MR 的 `coverage-report` job（`needs` 單元測試與 `integration`）另跑 `scripts/ci-patch-coverage.sh`：以 `git diff -U0` 的改動行對照單元測試與整合測試兩份 profile（直接串接，腳本逐行 OR：改動行只要任一份有執行即算覆蓋），改動行覆蓋率低於 60% 即失敗（排除 `_test.go`、生成碼與子模組）；主要靠整合測試覆蓋的程式因此不會被誤擋
- patch coverage 排除所有帶 `Code generated … DO NOT EDIT.` 檔頭的生成碼（含 `pkg/msg`），不只列舉的生成目錄
- `make cover` 產生覆蓋率報告（本機用）
- 本機 `make ci-unit` 產出 `coverage-unit.out`、`make ci-it-pkg` 產出 `coverage-integration.out`；全專案覆蓋率與 Cobertura 仍只合併單元測試分片（維持趨勢可比），整合測試的 profile 只供 patch coverage 使用
- GitLab 的 `coverage-report` job 合併單元測試覆蓋率並輸出 Cobertura 報告，MR 頁面顯示覆蓋率

## CI/CD Pipeline（GitLab CI）

正式 remote 為自架 GitLab，CI 入口是根目錄的 `.gitlab-ci.yml`，也是唯一的 CI 設定；倉庫不再保留 GitHub Actions。

各 job 以 `needs: []` 組成 DAG 同時啟動，stage（lint、test、post-test、release）只用於介面分組。`default` 設有 `retry`（最多 1 次），只在 runner 故障（`runner_system_failure`）時重跑，測試失敗不會被重試掩蓋；不用已棄用的 `stuck_or_timeout_failure`（它含腳本掛住）。`build-images`、`deploy-staging`、`deploy-production` 設 `retry: 0`，發版與部署不自動重試。

| 階段 | Job | 內容 |
|------|-----|------|
| lint | `lint` | 主 module 以 `go mod tidy -diff` 檢查（只在 CI：CI 樹不含不進版控的 `tools/private`）、`tools/gotools` 內 `go mod tidy` 後 `git diff --exit-code`、`go mod verify`、golangci-lint（經 `tools/gotools` 的 modfile；另以 `GOOS=windows` 對 `pkg/dataconfig`、`integration/testenv` 再跑一次）、`scripts/*.sh` 執行位元檢查（CI 以 `./scripts/x.sh` 直接執行，少了執行位元在 Linux runner 會 Permission denied）、`bash scripts/lib/envfile_test.sh`（`.env` 解析規則回歸測試）、最後以 `go run ./tools/pja configaudit` 檢查設定、compose 掛載、Prometheus 目標、告警與面板引用的指標 |
| lint | `govulncheck` | 掃描主 module、正式部署會 `go run` 的 `deps/PJA-Database`（只 checkout 該子模組），以及 `go -C tools/gotools tool govulncheck tool`（工具模組宣告的全部工具） |
| lint | `trivy` | `trivy fs` 掃描 go.mod 依賴漏洞、Dockerfile 設定與誤提交的機密，HIGH／CRITICAL 即失敗 |
| lint | `alert-rules` | 以與 `compose.prod.yml` 同一個 `prom/prometheus` 映像（同 digest，`TestToolchainVersionsAreConsistent` 比對）執行 `promtool check rules`、`promtool test rules monitoring/prometheus/tests/alert-rules.test.yml` 與 `promtool check config --syntax-only docker/monitoring/prometheus.prod.yml`；列入 `.release-needs`。本機仍可用 `monitoring/prometheus/tests/run.sh` |
| lint | `compose-config` | 以 `docker compose config -q` 驗證各 compose 檔，另驗證 `compose.full.yml` 疊加 `compose.s2s-auth.yml`、`compose.s2s-check.yml` 的合併結果（`scripts/private/check-s2s-docker.ps1` 的實際用法） |
| test | `unit` | 依四組 pattern 分片執行 `go test -race -shuffle=on`，保存覆蓋率分片 |
| test | `alloc-guard` | 不帶 `-race` 執行名稱含 `AllocatesNothing` 的零配置守門測試（`./pkg/framecodec/`、`./pkg/msg/`）；這類測試在 `-race` 下 `Skip`，`unit` 分片從未真正跑到。本機：`make ci-alloc` |
| test | `release-info` | 只在受保護的 `vX.Y.Z` tag 執行：`go run ./tools/pja releasemanifest generate` 與 `verify` 產生並驗證 `pkg/release/release.json`（取子模組，完整歷史），存成 artifact；`verify -config-repo deps/PJA-Config` 另要求 `config_version` 是 PJA-Config 子模組指標或其祖先，子模組與生成物漂移時發版失敗 |
| test | `bench-gate` | 只在 MR：`scripts/ci-bench-gate.sh` 由改動檔與 `go list` 依賴找出受影響的 benchmark 套件，在 base 的獨立 worktree 與目前 HEAD 各先 `go test -c` 編成測試二進位，再交錯執行 `BENCH_COUNT`（預設 10）輪後用 benchstat 比較（同一台機器同一個 job，不拿作者機器的基準檔比）；只判定 `sec/op`、`B/op`、`allocs/op`，顯著（p<0.05）的時間退化超過 25%、配置次數或位元組超過 10%、或配置從 0 變多就失敗並擋下 MR，報告存成 artifact。job timeout 50 分鐘。本機：`make bench-gate BASE=develop` |
| test | `integration` | 只跑含 `//go:build integration` 檔案的套件與測試（以 `grep` 產生套件清單與 `-run` 名單），使用 MySQL×2 與 RabbitMQ services（不再需要 Redis），並輸出 `coverage-integration.out` 供 MR 的 patch coverage 使用 |
| test | `e2e` | `integration/` 端到端測試，以子行程啟動各服務；先單獨跑 `TestSmoke_*` 冒煙測試，通過才跑完整清單（完整清單以 `-skip` 排除冒煙，不重跑） |
| test | `fuzz`、`bench` | 只在排程或手動執行 pipeline 時跑：`fuzz` 跑所有 fuzz target；`bench` 跑熱路徑 benchmark（`-count=10`），用 `go tool -modfile=tools/gotools/go.mod benchstat` 對照 `bench/benchmark_baseline.txt`（只比 `allocs/op`、`B/op`：基準在 Windows 本機產生、CI 在 Linux，`ns/op` 不可比；本機 `make bench` 同為 `-benchtime=1s`），結果存成 artifact，`allow_failure` 只回報不擋合併 |
| test | `build-images-mr` | 同專案 MR 動到映像相關檔案（含 `.gitlab-ci.yml`）時，在 deploy runner 建置映像（不推送）驗證 Dockerfile，並以 `trivy image` 掃描。只有 trivy 掃到可修補 CVE（exit 42）時放行（`allow_failure: exit_codes: [42]`），提早在 MR 看到基底映像的 CVE；映像建置失敗會擋 MR |
| post-test | `coverage-report` | `needs` `unit` 與 `integration`：合併單元測試覆蓋率並輸出 Cobertura 報告；MR 另算 patch coverage（單元與整合兩份 profile，改動行任一份有執行即算覆蓋） |
| release | `build-images` | 只在受保護的 `vX.Y.Z` tag（`$CI_COMMIT_REF_PROTECTED == "true"`）：需 `.release-needs` 全部通過（含 `alert-rules`、`alloc-guard`），建置六個服務映像、`trivy image` 掃描後推送 |
| release | `deploy-staging` | `STAGING_ENABLED=true` 時部署 staging（目前預留） |
| release | `deploy-production` | 只在受保護的 tag、手動觸發，`resource_group` 序列化，以 `scripts/ci-deploy.sh` 部署；CI 中 `ENV_FILE` 必須是絕對路徑（來自 Protected 變數），拿不到時直接失敗，不退回工作目錄的 `.env.prod` |

GitLab 端需另外設定（倉庫內看不到，待確認）：production 設為 Protected environment 並指定核准者；`v*` tag 設為 Protected tag（release 規則只認受保護的 ref）；`develop`／`main` 設為 Protected branch、MR 需 1 人核准且「Pipelines must succeed」（倉庫沒有 CODEOWNERS，MR 可同時修改程式與 CI 守門，靠核准把關）；`release-info`／deploy 以相對 URL 取 `../../Neo/*` 子模組，需把本專案加入那些專案的 CI/CD job token allowlist。deploy runner 的隔離問題見[已知安全風險](./已知安全風險.md)。

看 pipeline 與 job log：內建瀏覽器登入 GitLab 後，以 `/<project>/-/pipelines/<id>.json` 與 `/<project>/-/jobs/<id>/raw` 取得。

各 job 應設定 timeout，避免 runner 被 hung job 長時間佔用；integration 與 e2e 已設定 job timeout。

GitLab 專案設定（倉庫內看不到）：不要關閉「Use separate caches for protected branches」。關掉後，未受保護的 MR lint job（模組快取為 pull-push）能寫入受保護分支與 tag pipeline 共用的模組快取；MR 第一次冷編譯拿不到 develop 的編譯快取，是刻意接受的代價，詳見[Docker發版流程](./Docker發版流程.md)。

### OTel 分散式追蹤設定

Gate / Central / World 的設定檔均支援以下區塊：

```yaml
debug:
  pprof_enabled: true                # pprof handler 開關；缺省為 false（關閉），dev 設定檔明確寫 true

otel:
  exporter: ""                       # 留空 = noop（不輸出）; "stdout" = 終端機; "otlp" = OTLP HTTP
  endpoint: "http://localhost:4318"  # OTLP HTTP exporter 目標（exporter=otlp 時生效）
  sample_rate: 0                     # 0=全量(預設), 0~1=比例取樣, 負值=停用
```

本機快速啟動 Jaeger（All-in-One，含 OTLP HTTP 接收器）：

```bash
# 4318：OTLP HTTP 接收；16686：Jaeger UI。反斜線必須是行尾最後一個字元，後面不可再接註解。
docker run -d --name jaeger \
  -p 4318:4318 \
  -p 16686:16686 \
  jaegertracing/all-in-one:1.62.0
```

映像版本只供本機查看 trace，可自行換成較新的固定版本，不要用 `:latest`。

啟動後將 `otel.exporter` 設為 `otlp` 即可在 `http://localhost:16686` 查看 Trace。

OTLP 只有在設定檔的 `otel.endpoint` 與環境變數 `OTEL_EXPORTER_OTLP_ENDPOINT`／`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` 都沒有指定時（本機預設 `localhost:4318`）才用明文；任一處指定 endpoint 時由 endpoint 的 scheme 決定，`https://` 不會被降級成明文。

#### DB 自動追蹤

Redis 與 MySQL 查詢已自動加入 OTel tracing span：

- **Redis**：`pkg/redis.Client.Do` / `DoMulti` 自動包裝 `redis.call` / `redis.pipeline` span
- **MySQL**：GORM 註冊 tracing plugin，`mysql.query` span 附加 `table` 屬性

無需手動改寫 caller，所有查詢在 Jaeger/Tempo 中可見。

#### 錯誤記錄到 span

```go
tracing.RecordSpanError(ctx, err)
```

在 handler error 路徑加上此行，span 會標為紅色並附帶 error message。需同時保持 `logger.ErrorCtx` 記錄結構化日誌。

### Gate 排空設定

Gate 支援 `drain_timeout` 設定，覆寫預設的 30 秒排空等待。
值必須是正的 duration；壞值（缺單位、亂碼、非正數）使 Gate 拒絕啟動（不是忽略後改用預設），未設定才使用預設值：

```yaml
drain_timeout: 60s  # 根據玩家平均會話長度調整
```

`drain_timeout` 只套給 drain 任務，其餘關機任務維持單一任務逾時 5 秒；最壞關機耗時＝各任務逾時加總＋2 次 5 秒（RunApp 的 app shutdown 與等事件迴圈退出），TCP 服務（Gate、Central）最後再多等一次背景工作 5 秒。容器 `stop_grace_period` 必須大於它，各 compose（`full`、`debug`、`core-test`、`prod`）已補齊：Gate 75 秒、Central 65 秒、World 80 秒（盤面工作者停止任務另有 10 秒期限，最壞約 75 秒）、Chat 30 秒、Lobby／Record 20 秒。調高 `drain_timeout`（超過預設 30 秒時）或新增關機任務，都要同步調高 grace；各服務的 `shutdown_plan_test.go` 契約測試會斷言最壞耗時小於四份 compose 的 grace，漏改就失敗。

### 服務 ID 設定

`id` 必須是正整數，以 `bootstrap.Int` 嚴格解析（十進位整數；`1001.5`、`6k`、`6,000` 一律報錯，環境變數 `01001` 也不會被當成八進位）。
壞值會在啟動期直接報錯，不會被截斷、轉成其他數字或繞過驗證；驗證後以十進位結果寫回 viper，各服務之後讀到的是同一個值。

### World 容量設定

World 支援 `max_players` 設定，用來限制單台世界服最多承載的玩家數：

```yaml
max_players: 5000
```

- 未設定或 `0` 使用程式內建預設值
- 負值是設定錯誤，World 拒絕啟動（錯誤訊息 `max_players must not be negative`），不會被當成預設值悄悄吞掉
- 以 `bootstrap.Int` 嚴格解析：`6k`、`6,000`、`5000.5` 等壞值啟動失敗，不會靜默退回預設值（行為變更：原本會被寬鬆解析成 0 再退回預設 5000）

### Go 執行檔輸出位置

- 本機開發服務使用 GoLand 的 Go Application 設定或 `go run`，不在專案目錄留下服務 exe。
- 需要保留編譯好的服務或工具時，從專案根目錄執行 `make build`（全部服務）或 `go build -o bin/<名稱>.exe ./cmd/<服務>`；運維工具統一用 `go build -o bin/pja.exe ./tools/pja`；`bin/` 是手動建置二進位檔的標準輸出目錄，已加入 `.gitignore`。
- 執行 `go test` 時讓 Go 管理測試產物；若使用 `go test -c`，以 `-o bin/<名稱>.test.exe` 指定輸出位置。
- 不要在根目錄直接執行會輸出單一執行檔的 `go build ./cmd/<服務>`；`.run/` 留給本機執行狀態，`make clean` 只刪 `bin/`、根目錄的 `*.test`／`*.test.exe` 與 `coverage-*.out`，不碰 `.run/`、`cmd/` 或工具相依檔案，也不再 `go clean -cache`（那是使用者全域快取，需要時自行執行）。

### Makefile 指令

### Benchmark 與 PGO

- benchmark 套件清單只維護在 `bench/packages.txt`（一行一個套件），`make bench`、CI `bench` job 與 `scripts/gen-pgo-profile.ps1` 共用；新增熱路徑 benchmark 套件時改這份清單即可。清單只收不需外部服務（純記憶體或行程內 miniredis）的套件，需要真實 MySQL／Redis 的 integration benchmark 不列；`pkg/redis`、`pkg/playerstoreredis`、`pkg/logger`、`pkg/mapx`、`pkg/chatrule`（`BenchmarkValidPayload`）、`cmd/central/internal/app`（`BenchmarkNewUserWorldSelection`）已列入（`pkg/playerstoreredis` 的 benchmark 含 miniredis 伺服端 Lua 直譯成本，`B/op` 不代表用戶端配置）。PGO 腳本另外排除 `./internal/game/simulation/`（伺服器不使用，其 benchmark 會把不在伺服器熱路徑的程式灌進 profile）。
- 基準檔 `bench/benchmark_baseline.txt` 以固定機器 `-count=10` 產生，**僅供參考，沒有重產**：MR 的退化守門（`bench-gate`）已改為同一台機器比 base 與 HEAD，不再拿作者機器的基準檔比；排程 `bench` job 仍對它只比 `allocs/op`、`B/op`。手動比對：`make bench > new.txt`，再 `go tool -modfile=tools/gotools/go.mod benchstat -ignore goos,cpu,/gomaxprocs bench/benchmark_baseline.txt new.txt`（不同機器的 OS、CPU、GOMAXPROCS 不同時，不加 `-ignore` 會被拆成不同表格而沒有比對）。共享 runner 耗時雜訊約 5–10%，判斷退步以 `allocs/op`、`B/op`（確定性高）為主。
- MR 另有 `bench-gate` job 自動比較改動前後（見 CI 表）；它只量受影響的套件（改動檔與測試檔的 import 都算依賴；`go.mod` 有變時全量；base 沒有或跑不了的套件略過，不再讓守門必定失敗），雜訊大的時間門檻放 25%，確定性高的配置門檻收 10%。只判定 `sec/op`、`B/op`、`allocs/op`：`B/s` 越大越好、自訂指標（`events/op`、`dropped/op` 等）是行為數字，都不當退化。時間列任一邊的離散（±）超過門檻一半時只回報不擋；`B/op` 基準小於 64 的列只回報不擋（池與 GC 時機會讓少量位元組浮動），由 `allocs/op` 把關。`BENCH_GATE_REPORT=<benchstat 報告>` 可跳過執行、只對既有報告做判定，用來驗證門檻邏輯。
- 基準檔不含 `Old_` 子 benchmark 列：`make bench` 與 CI 都以 `-skip '.*/Old_'` 產生新結果，基準檔若含舊寫法的列，benchstat 每個新舊對照表格的 geomean 都會因 set differs 失真。新舊並排只在寫 benchmark 當下比較，不進基準檔。
- benchmark 名稱要對應實際量測內容：只量 `Decode` 加 `Unpack` 的叫 `FrameDecode`（不是 EncodeDecode），只量 `Pack` 的叫 `_Pack`；沒有呼叫專案程式（只量標準庫）的 benchmark 不保留。需要外部服務的 benchmark 用 `testutil.RequireEnv(b, "REDIS_ADDR")` 這類環境變數守門（與 CI 及同目錄其他 bench 一致），沒設就明確略過。
- 「0 配置」宣稱要指明條件：logger 的 `BenchmarkLogFacadeVsEvent` 分 Info、Warn（caller 關）、Warn（caller 開）三組，0 配置只對 Info 與 caller 關閉成立；開 caller 時原生入口約 345 B／3 allocs、門面約 361 B／4 allocs（與正式 JSON 設定一致才有參考價值）。
- 寫回吞吐 benchmark（`BenchmarkFlushRoundByConcurrency`）連線池上限設成正式 World 的 40，計時前先寫一輪暖機，確保各組都量「重寫已存在列」的路徑；需要 MySQL，在有資料庫的環境用 `-count≥6` 實跑才有結論。沒有寫回的 benchmark（如 `BenchmarkRollSaveShape`）要定期在計時外重建 store，否則 outbox pending 隨 `b.N` 累積使 `B/op` 漂移。
- 下次重產基準檔時預期：`RandomSourceIntn/New_ReuseHMAC` 改走正式的 `sync.Pool` + `NewRandomSourceFromHash` 路徑（1 次抽獎約 49 B／3 allocs，原基準 833 B／12 allocs），數字會下降，屬預期；新增的 `mapx.SortedKeys` benchmark 對照 `slices.Sorted(maps.Keys)`（約 258 ns／128 B／1 alloc 對 656 ns／312 B／8 allocs）。
- 熱路徑改動前先寫 benchmark 取得基線，改完用 benchstat 比對。perf 類提交的訊息貼 `benchstat` 輸出，不要只貼單次數字：`allocs/op`、`B/op` 至少 `-count=10`，耗時以 `-count=6` 以上，保留 `goos`／`goarch`／`cpu` 行，並註明量測時的機器負載（有無其他程式在跑）；有負載時 `ns/op` 雜訊大，判斷以 `allocs/op`、`B/op` 為主。
- 協定記錄（protocol record）開啟時，每則訊息仍會取共用 ring 鎖並做 `json.Marshal`（dev／docker 設定預設開啟，prod 關閉）；沒有檔案記錄器時程式端已不複製 payload。壓測與基準請固定「關閉協定記錄」再量，或在結果中註明記錄狀態。
- `default.pgo` 由 `scripts/gen-pgo-profile.ps1` 合併各套件 benchmark 的 CPU profile 產生，涵蓋網路編碼、盤面、記憶體 GameStore 與 metrics；Docker 映像與 `make build` 以 `-pgo=default.pgo` 明確指向根目錄的檔案（預設的 `-pgo=auto` 只讀各 main 套件目錄下的 `default.pgo`）。程式碼熱點大幅改變後（例如重構熱路徑）重產一次。`default.pgo` 仍只來自微基準；固定流程建議在壓測後從各服務 `/debug/pprof/profile?seconds=60` 擷取 profile，用 `scripts/gen-pgo-profile.ps1 -ProductionProfile a.pprof,b.pprof` 重產：提供正式 profile 時預設**只用正式 profile**（微基準樣本量遠大於正式 profile，合併會把正式熱點淹沒），確實要補 benchmark 才涵蓋的路徑時加 `-IncludeBenchmarks` 合併；暫存 profile 與 test binary 放系統暫存目錄，不留在倉庫根目錄。每次發版前或大幅重構後重產一次（`pprof` 預設關閉，擷取需先依[本機監控](../20-排障與監控/本機監控.md)啟用並設 `DEBUG_PPROF_BASIC_AUTH`）。
- 寫入需要落盤的檔案（備份、輸出、marker）一律用 `pkg/atomicfile`（暫存檔、fsync、rename、同步目錄項），不要自己 `os.Rename`。

## Docker 部署規則

### 映像檔

- 多階段建構：Go builder + Debian runtime
- 基底映像固定到 digest（`golang:1.27.2-bookworm@sha256:…`、`debian:bookworm-slim@sha256:…`），CI 與 Dockerfile 使用同一組 Go 映像；升版時需同步更新 `.gitlab-ci.yml` 與 `docker/app.Dockerfile`
- 建置：映像在發版時建置（CI 的 `build-images` 呼叫 `scripts/docker-build-images.sh`，手動發版走 `scripts/docker-release.sh`）；MR 動到映像相關檔案時由 `build-images-mr` 以相同腳本建置並掃描（不推送）。`docker/app.Dockerfile` 的 `ARG APP_DIR`、`ARG VERSION` 放在 `go mod download` 之後，否則 BuildKit 會讓每個服務、每次發版都使下載層快取失效
- runtime 階段的 `apt-get upgrade` 層帶 `ARG APT_REFRESH`：`docker-build-images.sh` 預設傳 `CI_PIPELINE_ID`（本機為日期），讓這一層每條 pipeline 重跑一次；基底映像以 digest 釘死，沒有它，deploy 主機的 BuildKit 快取會一直重用舊的安全更新層
- `scripts/ci-deploy.sh` 跑 migrate 時，MySQL DSN 以環境變數傳入容器（`-e MYSQL_DSN` 不帶值），不再出現在 `docker run` 命令列（`ps`、日誌看不到密碼）
- 映像掃描：`build-images` 建置後、推送前對六個映像跑 `trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed`（有可修補的漏洞即失敗）；runtime 階段先 `apt-get upgrade` 套用 Debian 安全更新，否則基底映像已有修補的套件會擋下發版
- 尚未提供：多平台建構、`provenance`／`sbom`；要啟用時在發版腳本或 CI 加入
- CI 的 `docker login`（`build-images`、`deploy-production`）只在 `CI_REGISTRY` 有值時執行，登入失敗即讓 job 失敗（不再 `|| true` 吞掉）；未啟用 Container Registry 的專案略過登入
- `workflow:rules` 只對 `push` 事件擋下已開 MR 的分支 pipeline（避免與 MR pipeline 重複）；排程與手動（`web`）pipeline 不受影響
- 健康檢查：Docker HEALTHCHECK 指令（`wget http://localhost:${HEALTHCHECK_PORT}/ready`）；`HEALTHCHECK_PORT` 以 build arg 傳入各服務的除錯埠並轉成 ENV，建置腳本與 workflow 已依服務設定；`scripts/failover-drill.ps1`、`production-smoke.ps1` 也在容器內讀這個 ENV 打 `/ready`，不另寫埠表，建置腳本列的埠由 `pkg/debug` 契約測試比對 `debug.Endpoint`；p0-daily-check、alert-selfheal 的診斷網址參數預設空字串，交給工具依 `<SERVICE>_DIAG_URL` 或預設埠決定
- 健康檢查間隔：30s、timeout 5s、start-period 15s、重試 3 次
- Config 透過 volume mount 掛載

## TCP 協定說明

**Frame 格式**（`pkg/framecodec/coder.go`）：

```
[4 bytes uint32 LE: total size] [2 bytes uint16 LE: msgID] [payload bytes...]
```

- `size` = 4（size 欄位本身）+ 2（msgID）+ len(payload)
- 最大訊息大小：4 MB（`maxMsgSize = 4 * 1024 * 1024`）
- **協定為 breaking change**：客戶端必須使用 uint32 讀取 frame size，不相容舊版 uint16 協定

## User 測試客戶端指令

透過 stdin 輸入以空白分隔的指令（`tools/user/internal/stdinevent/`，以 `strings.Fields` 切欄位）：

```bash
printf 'login 0 alice mypassword\n' | go run ./tools/user -config config/dev/user.yaml
```

格式：`login <accountType> <account> [password]`

| 位置 | 說明 |
|------|------|
| 第 1 欄 | 指令名稱（`login`，不分大小寫） |
| 第 2 欄 | 帳號類型（accountType，0～255 的數字，範例用 `0`） |
| 第 3 欄 | 帳號名稱（account） |
| 第 4 欄 | 密碼（password，可省略） |

> **注意**：新帳號必須帶非空密碼（首次登入時會以 bcrypt 雜湊存入 MySQL，空密碼回 `AuthWrongPassword`），所以第一次登入要帶密碼；既有舊帳號可省略。未知指令記 `unknown command` 警告並以 `available` 欄位列出可用指令；stdin 讀到 EOF（例如背景執行、輸入已關閉）時記一行 `stdin closed; commands disabled`，之後只保持連線、不再收指令。

## 進階測試

### Fuzz Testing

目前的 fuzz target（以 `git grep -n '^func Fuzz'` 為準）：

| 套件 | Fuzz target | 測試路徑 |
|------|-------------|----------|
| `framecodec` | `FuzzWriteFrame` | WriteFrame 的 header／payload 正確且可由 Decode 讀回 |
| `framecodec` | `FuzzCoderDecode` | Decode／DecodePooled 三條解碼路徑結果一致，且可由 WriteFrame 還原 |
| `tcpsocket` | `FuzzPackedMsgUnpack` | 任意位元組不 panic |
| `tcpsocket` | `FuzzPackedMsgRoundTrip` | Pack/Unpack 往返一致性 |
| `msg` | `FuzzClientMessageUnpack` | 玩家端每一種訊息 Unpack 任意位元組不 panic，長度宣稱不會造成超量配置 |
| `msg` | `FuzzForwardToWorld`、`FuzzTimeSync`、`FuzzHeartbeatReq` | 個別 S2S 訊息 Unpack 不 panic、往返一致 |
| `msg` | `FuzzMsgID`、`FuzzMalformedUnpack`、`FuzzMalformedPack` | 訊息 ID 解析與畸形輸入不 panic |
| `cmd/gate/internal/app` | `FuzzSessionState` | 以任意位元組序列驅動正式路徑的 session 操作（每個位元組選一個操作與參數），每步實際斷言 session 狀態不變式 |

新增玩家端訊息時，`FuzzClientMessageUnpack` 的型別清單取自 `clientRoundTripCases`（`Sender=="Client"`），要同步把新訊息加進該表。

執行 fuzz test：

```bash
go test -fuzz=FuzzCoderDecode ./pkg/framecodec/
go test -fuzz=FuzzPackedMsgUnpack ./pkg/tcpsocket/
```

GitLab 的 `fuzz` job 在排程 pipeline 或從介面手動執行 pipeline 時，自動找出所有 `func Fuzz*` 並各跑 `FUZZ_TIME`（預設 60 秒）；失敗輸入存成 artifact。排程需在 GitLab 專案的 Build → Pipeline schedules 建立（建議每日一次）。

新增 fuzz test 的時機：
- 處理外部輸入的協定解碼器
- 二進位序列化/反序列化
- 任何接受 `[]byte` 作為輸入的公開函式
