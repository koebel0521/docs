## 程式碼慣例

### Handler 模式

所有訊息處理器遵循統一簽名：

```go
func (h *Handler) onMessageType(svc tcpruntime.Service, sock tcpruntime.Socket, m *Message)
```

- 第一個參數 `svc` — 來源服務
- 第二個參數 `sock` — 來源連線
- 第三個參數 `m` — 訊息本體

#### traceID 自動注入

dispatch 層（`pkg/tcpsocket/socket_events.go` 的 `msgEvent.Run()`）會自動從實作 `msg.TraceScopedMessage` 的訊息中提取 `traceID` 並注入 `sock.Context()`。Handler 不需要手動呼叫 `logger.WithTraceID`：

```go
var onLoginGateToCentralTimer = metrics.NewHandlerTimer("central", "on_login_gate_to_central")

// 正確 — traceID 已由 dispatch 層自動注入
func (h *Handler) onLoginGateToCentral(svc tcpruntime.Service, sock tcpruntime.Socket, m *auth.LoginGateToCentral) {
	defer onLoginGateToCentralTimer.Start().Done()
	ctx, endSpan := tracing.StartSpan(sock.Context(), 0, "central.login")
	defer endSpan()
	logger.DebugCtx(ctx, "login request", "requestID", m.RequestID)
}
```

- `sock.Context()` 已自帶 `traceID`，無需 `logger.WithTraceID`
- `tracing.StartSpan(ctx, 0, ...)` 會從 ctx 自動讀取 `traceID`
- 屬性參數是型別化的 `attribute.KeyValue`（`tracing.StartSpan(ctx, 0, "name", attribute.String("k", v), attribute.Int("n", n))`），不是 `...string` 鍵值對；`SetSpanAttrs` 同
- 背景 goroutine／非訊息入口處仍需手動 `logger.WithTraceID`
- 建立新 trace 的入口點（如 `forward.go`）仍手動呼叫 `NextTraceID`

#### 指標記錄

每個 Handler 必須記錄：
- **執行時間** — `game_handler_duration_seconds` histogram：套件層宣告 `var xxxTimer = metrics.NewHandlerTimer("服務", "handler")`，handler 開頭 `defer xxxTimer.Start().Done()`（label 預先解析、不配置記憶體，也不在 handler 直接呼叫 `time.Now`）；label 要執行期才知道時，在建構時解析成 `HandlerTimer` 再傳入（例：`s2shandshake.BindConnectInfoOnly(timer, sock, m)`、`centralclock` 依 app 名稱建立）。同一服務的 `(service, handler)` 不可重複（`internal/archtest` 守門）：多個對端共用的處理方法要加對端前綴，例如 `<對端>_on_connect_info`（`world`／`chat`／`central`／`gate`／`timesync`）、`centralclock_on_connect_info`、`world_on_audit_snapshot_response`／`gate_on_audit_snapshot_response`，否則 P95／P99 告警分不出是哪個對端慢
- **結果碼** — success/fail label

### 日誌規範

- 以 [`日誌規範`](./日誌規範.md) 為準
- 新程式碼統一使用 `pkg/logger`，底層固定 `zerolog`
- 不要直接引入 `log/slog`、`logrus`、`zap` 作為新日誌入口
- 跨服務訊息必須攜帶 `trace_id` 欄位

### 錯誤處理

- 錯誤回應必須**立即發送**，避免玩家超時等待
- 所有 error 必須處理（errcheck linter 強制）
- error 回傳應包裹上下文語意（wrapcheck linter 強制）`fmt.Errorf("operation: %w", err)`
- 禁止 bare `fmt.Errorf("%w", err)` 空包裝（等同 `return err` 但多一次 allocation）
- 例外：只有 `*sql.DB.Close()`（`.golangci.yml` 的 `exclude-functions` 只放行 `(*database/sql.DB).Close`）。刻意不排除 `io.Closer.Close()`：讀取用的 `defer Close` 若被 errcheck 報，要明確處理或以 `//nolint:errcheck // 理由` 說明；寫入檔案請用 `pkg/atomicfile`（細節見後文排除規則段）

### 管理端權限

- Lobby 管理端依權限分層：`admin / ops / gm`
- `admin` 可通過所有管理端路由
- `ops` 用於踢人、封禁與世界維護
- `gm` 用於發道具與死信處理
- 新增管理端 API 時，先想好該掛哪一層，不要全塞進同一把 token

### 訊息關聯

- `request_id` — 用於請求去重（同一操作重送時保持不變）
- `trace_id` — 用於日誌串聯（每次新請求產生新 ID）
- 兩者分離，職責不同

### 效能慣例

- **TCP 層**：收發熱路徑用 `DecodePooled`/`WriteFrame`（緩衝取自物件池，header 與 payload 組進同一塊緩衝後一次 `Write`），不用 `Decode`；`BuildFrame` 只是測試輔助函式
- **Socket 連線**：發送佇列用原生 `chan tcpruntime.Msg`，深度預設 `tcpconfig.DefaultSocketSendQueueDepth`（10000），可用 `tcp.socket_send_queue_depth` 設定，不引入第三方無界佇列
- **World 狀態**：玩家索引取 `userMu`，不可直接取 `mu`（已移除）；頻道機制與 `chanMu` 已不存在
- **World user 查詢**：`map[uint64]*User` O(1)，不再用 rbtree
- **線上人數**：讀 `activePlayerCount.Load()`，不可遍歷 users map
- **atomic.Bool**：布林原子操作統一用 `sync/atomic.Bool`（Go 1.19+），不用 `gtype.Bool`
- **批次查詢**：以 `FindUsersByGate` 這類批次查詢取多位玩家，不可在迴圈內逐一 `FindUser`（頻道功能已移除，`ChannelMembers`／`ChannelMembersOfType` 不再存在）
- **Redis HSet**：`pkg/redis` 的 `HSet`（`Client` 與 `Multi`）只收 `...string` 鍵值對，不再收 map 或任意型別；呼叫端自行轉字串
- **Redis 批次**：大量 key 操作（如 Refresh、Restore）必須走 pipeline，不可循序單條呼叫
- **msgpool**：`Pack()` 緩衝走 `sync.Pool`，不可每次 `make([]byte)`。訊息歸還物件池時，切片欄位以 `msgpool.RetainBytes(s, maxBytes)` 清空重用，上限改以**位元組**計（容量乘元素大小，`[]int64` 與 `[]byte` 共用 `MaxRetainedBytes`＝64 KiB）；以筆數定義上限的欄位用 `msgpool.RetainLen(s, maxLen)`
- **池化訊息的字串**：訊息會 `Put` 回物件池重用，解碼出的字串必須以一般 `string([]byte)` 複製，不可指向訊息內部緩衝（`UnsafeAppendString` 已因此移除：重用後已存進 `app.User` 的字串會被下一筆覆寫）
- **sync.Pool 歸還**：從 pool 取新物件替換舊物件時，舊的必須先 `Put()` 歸還
- **Redis 客戶端**：RESP3 預設啟用，不設 `AlwaysRESP2`；專案沒有使用 `DoCache`（`pkg/redis` 也不外露），`pkg/redis` 固定停用 client-side caching（`DisableCache: true`，沒有 `redis.disable_cache` 設定鍵）（正式環境因此不送 `CLIENT TRACKING`）；由建立連線的啟動層負責在服務結束時呼叫 `Close()`
- **goroutine**：背景 goroutine 一律經 `GoBackground`（各服務 App，底層 `appcore.TaskGroup`）、`OwnerBase.Async` 或 `errgroup` 啟動，關機任務以 `appcore.WaitContext` 加期限等待；`TaskGroup` 在 Wait 期間仍允許 Add（關機 PreDrain 時 handler 仍會提交工作，`sync.WaitGroup` 會 panic）。只有確定不會在 Wait 期間 Add 的區域性 fan-out 才用 `sync.WaitGroup`（Go 1.25+ 用 `wg.Go`，fn 不可 panic）
- **AMQP 關閉順序**：`AsyncPublisher.Run` 在自己的 goroutine 執行；關閉時先 `AsyncPublisher.Stop(ctx)`（排空佇列、受關機期限約束），返回後才 `Publisher.Close()`，不可在排空期間關閉連線
- **型別斷言**：一律用 comma-ok 模式，裸斷言會 panic；唯一例外是 `sync.Pool`／只存單一型別的 `sync.Map`，可用裸斷言並加 `nolint:forcetypeassert` 與理由。只經型別斷言使用的**選用介面**（例如 `tcpruntime.DoneContexter`、`tcpruntime.PackToer`）必須以具名型別宣告，消費端斷言與每個正式實作旁的 `var _ X = (*T)(nil)` 都引用同一個型別：匿名字面值各寫一份時，消費端改了簽名，實作端的編譯期檢查照樣通過，斷言會靜默失敗（OwnerContext 不隨 owner 關閉、訊息退回 `Pack()` 多一次配置）

### 程式碼品質

- **服務入口**：各 `main` 呼叫 `startup.Main(version, defaultConfig, description, run)`，`description` 是 `-h` 用法的一行程序說明，由各 main 自行傳入（不再寫死 `Game service process`）
- **佔位密碼**：`ErrPlaceholderPassword` 已刪；RabbitMQ 佔位密碼檢查只在啟動層的 `mqstartup.CheckURL`（`pkg/recordmq` 不依賴 bootstrap），MySQL、Redis 在各自的 startup 套件
- **商店**：金幣不足的哨兵是 `shop.ErrInsufficientGold`（統一用 Gold 用語，`shop.New` 不再收付款道具參數）
- **Getter 命名**：Go 慣例省略 `Get` 前綴，直接以欄位名作為方法名（`PlayerID()` 而非 `GetPlayerID()`）。
- **錯誤字串**：一律英文、首字母小寫、結尾不加標點；識別碼、設定鍵與縮寫（`S2S`、`SHA`、`max_players`）保留原樣。以套件或元件名當前綴（例如 `"redis: get key: %w"`），不用 `failed`／`err`／`error` 當包裝前綴，也不重複下層的前綴；包裝一律 `%w`（`errors.Join` 也是），外部來源的字串值用 `%q`。哨兵錯誤（`errors.New`）同樣帶元件前綴，例如 `world: persist pool closed`、`lobby: game clock loop panicked`、`board: resolution failed`。錯誤值可以帶 ID 等上下文，日誌 message 則固定。詳見[日誌規範](./日誌規範.md#錯誤訊息原則)。註解仍用中文。
- **Context.Background 禁止用於生產路徑**：何時傳 `sock.Context()`、何時用 `WithTimeout(WithoutCancel(ctx), d)` 見下方 [Request Context](#request-context)。
- **HTTP request 日誌**：對外與 admin 的 HTTP 入口一律經 `httpx.NewPublicServer` 建立（`httpx.NewServer` 已刪除；外部 traceparent 只以 link 關聯），它會自動用未匯出的 `logging` 中介層包住 handler，記錄 method/path/status/elapsed 並計入請求耗時直方圖；內層的 `httpx.Recover` 擷取 handler panic（計 `PanicRecoveredTotal`、記 stack、回 500）。不要自行再包一層。**例外是診斷埠（`pkg/debug`，`/metrics`、`/health`、`/ready`、pprof）**：它自己組 `http.Server`，只包 `SecurityHeaders`、`Recover` 與 CIDR／basic auth 守衛，沒有存取日誌、不計 `game_http_request_seconds`；不設 WriteTimeout（pprof 長時間寫出）、IdleTimeout 為 1 分鐘；otelhttp 未設 `WithPublicEndpointFn`，會採信外部 `traceparent` 當父 span（診斷埠只靠 CIDR 與 basic auth 保護）；`accessGuard` 在 otelhttp 外層（先擋再建 span），被 CIDR 或 Host 擋下的請求不建 span。排查延遲時別在 `game_http_request_seconds` 找診斷埠請求。**Host 標頭白名單**由 `httpx.HostAllowlist`（`DEBUG_ALLOWED_HOSTS`）提供，組合根一律以 `httpx.AllowedHostsFromEnv()` 建立（Lobby、Record；debug 伺服器經 `startup.InitializeObservability` 讀同一個變數；環境變數名稱字面值只留在 `pkg/httpx` 一處，`configaudit` 掃 compose 時才認得），`Guard` 收到 nil 白名單時退回 `NewHostAllowlist("")` 的安全預設（只放行內建範圍：IP 字面值、`localhost`、`*.localhost`、`host.docker.internal` 與單一標籤名稱），**不再是不檢查**，接線漏掉也不會 fail-open；debug 伺服器、Lobby admin 路由與 Record `/events` 共用同一份規則（`Guard` 中介層，不符回 403；`debug.Server.ConfigureAllowedCIDRsFromEnv` 與 `ConfigureAllowedHostsFromEnv` 對稱）；新增對外或 admin 的 HTTP 入口時也要套用。
- **Pool 物件的 slice 賦值須拷貝**：從 pool 取得的訊息物件的 `[]byte` 欄位傳遞給非同步 consumer 時，必須拷貝 backing array（`dst = append(dst[:0], src...)`），避免 pool 回收後 backing array 被重寫導致的 data race。
- **context 參數禁止捨棄**：函式簽名收到 `ctx context.Context` 時必須使用，不得命名為 `_`。若底層 API 不支援 context，應自行包裝逾時控制（如 `dialWithContext` 模式）。
- **goroutine 安全**：所有 `go func()` 內部必須 `defer panicx.RecoverPanic("描述")`，避免單一 goroutine panic 拖垮整個 process。禁止直接寫 `recover()` — 統一用 `panicx.RecoverPanic` 確保 stack trace 被正確記錄。`appcore` 的同名函式已於第十三輪刪除；標籤參數 `label` 必須是常數字串（會成為指標標籤）。
- **長期迴圈 goroutine 使用 per-iteration recover**：無限 `for` 或 `for-select` 迴圈的 goroutine 不可在函式層級做 `defer RecoverPanic`，否則 panic 後整個 goroutine 靜默退出。應將 `defer RecoverPanic` 移至**每個 iteration 內部的匿名函式**，讓迴圈在 recover 後繼續運行。`stopCh`/`ctx.Done()` 等正常停止訊號留在外層 select，不受 recover 影響。
- **常數錯誤字串**：格式固定、沒有變數內插的錯誤字串使用 `errors.New` 而非 `fmt.Errorf`，減少不必要的格式化開銷。

### MySQL 連線與寫入

- 正式連線（`pkg/mysql`）的 DSN 開 `interpolateParams=true`，**不使用 GORM `PrepareStmt`**：`PrepareStmt` 在交易內每句都重新 PREPARE／CLOSE（`database/sql` 對綁在 Tx 的語句不重用），World 寫回與 outbox 幾乎都只在交易內執行，快取完全無效。量測見[效能嘗試紀錄](./效能嘗試紀錄.md)。
- **熱路徑已自行預組語句與參數時用 `mysql.ExecRaw(tx, query, args...)` 取代 `tx.Exec`**（World 每秒寫回的盤面列與道路星星 upsert，`mysqlstore/mysql_player_board_upsert.go`）：GORM `Exec` 對每個 `?` 走 `clause.Expr` 與 `Statement.AddVar`，每個參數約多一次配置；相對 `tx.Exec`，盤面列 allocs 34 到 5、道路星星（120 個參數）167 到 32（GORM 客戶端開銷 sec/op 約 -92%/-85%，不含驅動、網路與伺服器）；相對最初的 GORM `Create`＋`OnConflict`，客戶端開銷 sec/op -97%（allocs 108 到 5）、-90%（allocs 186 到 32）；連實機 MySQL 的整條往返只看到配置降約 75%/72%，sec/op 被往返與伺服器時間淹沒、量不出差異。`ExecRaw` 直接用 `tx.Statement.ConnPool.ExecContext`（交易內就是 `*sql.Tx`），因此繞過 GORM callback 鏈：它自行補 `mysql.raw` span 與 `gormLogger.Trace`（慢查詢、失敗取樣、Debug 紀錄），錯誤原樣回傳，`IsDataRejection`、`IsInfraError` 與 `RetryableTransaction` 的判斷不變；**新增類似熱路徑寫法時，繞過 GORM Statement 就要自己補日誌與 span**，且 benchmark 必須量到送出為止的整條路徑（只量組字串會高估效益，第二十輪 P-M1 就是量錯範圍，見歷史第二十一輪處理結果）。目前只有盤面列與道路星星改用，items、variables、config versions、outbox 沒有（量不出明顯收益，不改）。
- 因為 `interpolateParams` 會把 `[]byte` 參數寫成 `_binary'…'`，**寫 JSON 欄位禁用裸 `[]byte`**（MySQL 回 Error 3144）：用 `string`，或用 `gamestore.JSONBytes`（底層 `[]byte`，`Value` 回 `string`、nil 寫 NULL，`Scan` 複製內容；`encoding/json` 仍編成 base64，spill 檔格式不變）。BLOB 欄位的 `[]byte` 沒問題。`PlayerStateArchive.Data`、`PlayerMissionState.ProgressJSON`／`FailureProgressJSON`、`RecordOutboxEvent.Payload` 已套用。
- World 的 gorm 模型每個欄位都明寫 `column:` tag（有測試守門）：欄位名不再由 Go 欄位名推導，改名不會讓 `AutoMigrate` 默默新增空欄位。寫進 Redis 的 request journal JSON 紀錄結構（登入、登出、驗證、replay）也都有 `json` tag，鍵名與舊輸出相同（`Code`、`PlayerID`、`WorldID`、`GateID`、`MessageID`、`Payload`），既有資料維持可讀。
- 啟動時 `VerifyDatabaseSchema`（比對 `schema_migrations`）有 10 秒逾時，MySQL 接受連線卻不回應時不會卡死在啟動階段。

### 遊戲系統與企劃工具解耦

未來遊戲系統需要提供工具給企劃測試與調整，遊戲功能應遵守以下原則：

- **規則資料化**：事件、事件群組、格子行為、條件、效果、獎勵與各種門檻，應由企劃工具管理的資料提供；Server 不應把可調整的規則寫死在流程程式中。
- **邏輯與傳輸分離**：遊戲判定邏輯不直接依賴 Client 或封包格式；協定只負責傳送請求與結果。
- **Client 只負責操作與顯示**：Client 不自行判定結果、事件觸發、事件成功與否或獎勵內容。
- **Server 保持唯一判定來源**：正式遊戲與企劃測試工具應使用相同的規則服務與判定邏輯，避免各自實作一份規則。
- **工具可獨立執行**：企劃工具應能載入同一份設定與事件資料，直接呼叫遊戲用例進行模擬，不必依賴 Client 畫面或完整連線流程。
- **資料存取與規則分離**：遊戲規則不直接依賴 MySQL、Redis 等儲存實作；資料透過明確的資料存取介面讀寫。
- **測試輸入可控制**：企劃工具與自動測試應能指定骰子結果或其他測試輸入，重現同一個流程與結果。
- **禁止直接修改外部產出檔**：由 `PJA-Config` 或 `PJA-Protocol` 工具產生、同步至 PJA-Server 的檔案不可直接修改，包含產生的 Go 程式碼、二進位設定資料與協定程式碼。
- **外部產出檔只能重新產生**：需要調整設定、資料或協定時，必須修改 `PJA-Config`／`PJA-Protocol` 的來源資料或定義，再執行對應工具產生並同步；不得在 PJA-Server 以手動修改或腳本覆寫產出檔的方式處理。

目前產出檔與 PJA-Server 同步路徑如下：

| 來源工具 | 來源產出路徑 | PJA-Server 同步路徑 |
|---------|-------------|---------------------|

### Import 別名

- 預設不加別名，直接用套件宣告名。
- 只在必要時加別名：檔內另有同名識別字（import、區域變數、同套件頂層宣告）而衝突，或 goimports 要求（套件宣告名與路徑最後一段不同，別名即宣告名）。
- 同一路徑需要別名時，全專案用同一個別名（例：`gormlogger`、`worldapp`），不要各檔自取。
- World 與共用 gamecore 有同名套件（`lottery`、`condition`、`effect`、`variable`、`mission`、`item` 等）時，同檔需要兩者就用前綴區分：共用的 `internal/gamecore/<系統>` 加 `game` 前綴（`gamelottery`、`gameeffect`、`gamecondition`、`gamevariable`、`gamemission`、`gameitem`），World 自己的 `cmd/world/internal/<系統>` 加 `world` 前綴（`worldlottery`、`worldboard`、`worldcondition`、`worldmission`、`worldapp`、`worldplayerstore`）；不要再自取別名。`internal/gamecore/lottery` 的建構函式叫 `lottery.NewDefinition`（原 `lottery.New`）。

## Request Context

- **唯讀查詢、回覆前就可以放棄的工作**：傳 `sock.Context()`（或 handler 收到的 ctx），連線斷了就取消。
- **已受理、必須做完的寫入**（多步驟結算、盤面指令、登入寫入、登出清理、刪路由、request journal、outbox 標記）：用 `context.WithTimeout(context.WithoutCancel(ctx), 期限)`。脫離連線與 App 的取消，避免寫到一半被取消留下半套狀態，同時保留 traceID 與 span；期限讓它不會無限卡住。第三到第六輪修過的多個同類 bug，起因都是把這類寫入綁在連線或 App 的取消上。
- **交給其他 goroutine 的工作**：先在 handler 內同步取出 `sock.Context()` 再傳入。S2S 連線的 `sock.Context()` 是整條服務間連線的生命週期，不是單一請求；dispatch 注入 traceID 的 ctx 也只在 handler 同步執行期間有效。
- **不用 `context.Background()`**：背景工作與關機收尾也以 `WithoutCancel` 從現有 ctx 衍生，日誌才對得回原請求；只有行程入口（`startup`）與測試 stub 的 `Context()` 例外。

## 測試規範

測試類型與名詞的白話說明、各類測試的位置與執行方式見[測試名詞與類型說明](測試名詞與類型說明.md)。

### 通則

- 新增測試**首選 `t.Context()`** 而非 `context.Background()`，確保 goroutine 在測試結束時被 cancel
- 不要在 `t.Run` 閉包內呼叫 `t.Helper()`——該語句對 stack trace 無效，應直接將 subtest 寫為獨立的 `t.Run` 呼叫
- assertion 統一使用 `github.com/stretchr/testify/require` 與 `assert`，避免 raw `t.Fatalf` + `if got != want` 模式；既有手寫 `t.Fatalf` 的檔案是否全樹改寫尚未決定，目前只在改到該檔時順手轉換
- 前置條件（後面要取索引、解參考或依賴其結果）用 `require`，最終驗證用 `assert`；套用在新增或修改的測試，不做全樹機械改寫
- `require`／`t.Fatal` 只能在測試 goroutine 呼叫：背景 goroutine 與 `Eventually` 的 condition 內改用回傳 error 的 helper（例如 `testenv.TryReadMessage`），或改用 `EventuallyWithT` 對 `c` 斷言
- 平行子測試（`t.Run` + `t.Parallel()`）的前置閉包（setup／load）與共用 fixture 要接收**子測試自己的 `t`**，不可捕獲父測試的 `t`：前置條件失敗時才能指出是哪個案例，也不會對父測試呼叫 `FailNow`；計數變數等狀態移進各子測試，避免平行子測試共用未同步變數
- 斷言全域指標（Prometheus 計數器等）只看本輪增量（前後差），不要斷言絕對值；測試要能以 `-count=N` 重跑通過（需要時先清掉專屬序列，fake driver 不要每次 `sql.Register` 固定名稱，改用 `sql.OpenDB(connector)`）。斷言全域指標增量的測試分兩類：指標 label 取自測試可控的名稱（client 名稱、World 編號、app 名稱）時，改用**專屬 label 值**，其他測試寫不到同一序列，就可以並行；label 由正式碼寫死（`world`、`grant_item`、`PanicRecovered` 的固定來源等）無法隔離時，測試**序列執行**（`//nolint:paralleltest // 原因`）並以 `InDelta` 比對精確增量，不要用 `Greater`——其他並行測試的遞增會遮蔽漏計的回歸。不要比對全域向量的序列總數（並行測試隨時可能在同一個 `CounterVec` 新增序列），改逐條收集、只看自己標籤的序列。會改寫或斷言全域狀態的測試維持序列
- `Eventually`／`EventuallyWithT` 的上限統一 5 秒、輪詢 10ms（避免 `-race` 與並行負載下偶發逾時，也避免 1ms 輪詢空耗 CPU）；condition 內不呼叫 `t.Fatal`。例外需在測試內註明理由：kick queue 退避測試用 4 秒（配合重試次數上限）、GM grant 多 worker 測試用 10 秒。整合測試（`-tags integration`、連真實 MySQL／Redis／RabbitMQ 或子行程）屬類別例外：上限可放寬到 10～30 秒、輪詢 ≥50ms，不必逐處註明（第十一輪 TF-L3）
- condition 內要查詢可能失敗的資源（MySQL、Redis、HTTP）時用 `EventuallyWithT`，在條件內 `require.NoError(c, err)`，逾時才看得到原因；`Never` 之後補一次確實的查詢並斷言，避免條件內一直出錯而空轉通過
- `testing/synctest` 氣泡內等待一律寫 `synctest.Sleep(d)`，不寫 `time.Sleep` 加 `synctest.Wait` 兩行；`synctest.Sleep` 內含 `Wait`，多個 goroutine 同時睡眠或與忙迴圈並存會 panic（氣泡外呼叫也會），這類情形保留 `time.Sleep`；`internal/archtest` 的 `TestSynctestWaitsUseSynctestSleep` 掃全樹測試檔，`time.Sleep` 緊接 `synctest.Wait` 就失敗
- Go 1.23 起計時器的 `Stop`／`Reset` 不會留下過期的值在 `C`，不必再手動排空 `timer.C`
- Stub 實作 `Context()` 方法時仍回傳 `context.Background()`（正確語意）
- Socket stub 優先使用 `pkg/testutil/fakes` 提供的 `NewSocket` + `SocketOption` factory，減少自訂 inline stub 的維護成本
- 每個有測試檔的目錄都要有 `TestMain`，並在其中呼叫 `goleak.VerifyTestMain(m)` 或 `testutil.VerifyTestMain(m)`；後者另外忽略函式庫自己的 goroutine（rueidis 的 LazyDo／DelayDo 延遲 singleflight；GORM 預備語句快取的 LRU 清理已不必忽略，`pkg/mysql` 不再使用該快取），用到 Redis 或 MySQL 的套件用它。`pkg/testutil` 本身匯入的套件為避免匯入循環直接用 goleak
- 測試環境變數只有一份表：`testutil.ConfigEnvPrefixes`／`ConfigEnvNames`（`testutil.IsConfigEnv` 判斷）列出會被服務讀成設定的環境變數，單元測試的 `ScrubConfigEnv` 與整合測試啟動子行程（`integration/testenv`）共用；新增讀環境變數的設定區段只改這裡。出貨設定範本用 `repo.ShippedConfigs(service)`（`config/*/<service>.yaml` 與 `docker/prod/config/<service>.yaml`）取路徑，各服務對自己的範本跑純設定驗證函式，壞值在 CI 就擋下
- 測試檔以被測原始檔命名：新測試放進 `<source>_test.go`，檔案太大才拆成 `<source>_<concern>_test.go`，不要以情境另開檔名（如 `set_bounds_test.go`、`ring_empty_test.go`），否則同一個原始檔的測試會散在十幾個檔案，IDE 跳轉、覆蓋率對照與審查都得靠全文搜尋。命名由 `internal/archtest` 的 `test_file_naming_test.go` 守門：新增不合規的測試檔會失敗；規則訂出前就存在的不合規檔（約 900 個）凍結在 `internal/archtest/test_file_naming_frozen.txt`，只減不增（改名或合併後要自清單移除，已合規或已不存在的項目也會讓測試失敗）。既有檔不做大搬；是否逐目錄合併尚未決定
- 斷言訊息語言：除有意凸顯的業務術語外，assert 的錯誤說明用**英文**（CI log 編碼相容性佳），測試內部註解與函式命名用**中文**（團隊慣例）

### 單元測試

- 在專案根目錄執行一次（`go test ./...`，涵蓋所有服務與 tools）
- 必須加 `-race` flag 偵測資料競爭
- 必須加 `-shuffle=on` flag 隨機化測試順序，抓出 inter-test 相依
- CI 中單元測試有 `-timeout=10m` 上限，防止 hung test 卡住 pipeline
- 使用 `pkg/testutil/fakes` 提供的 StubSocket、StubService
- CI `unit` job 分四片（依測試量平衡）：`./pkg/...`、`./cmd/world/... ./cmd/record/...`、`./cmd/gate/... ./cmd/lobby/... ./cmd/chat/...`、`./cmd/central/... ./internal/... ./tools/...`；帶 `integration` 標記的測試另由 `integration`、`e2e` job 執行
- 零配置守門測試（斷言 `testing.AllocsPerRun` 為 0）名稱一律含 `AllocatesNothing`：`-race` 會改變配置行為，這類測試在 `-race` 下 `Skip`，所以 `unit` 分片從未真正執行它們，改由不帶 `-race` 的 CI `alloc-guard` job（本機 `make ci-alloc`）跑；新增同類測試除了沿用這個名稱，還要把套件加進 `scripts/ci-alloc-guard.sh` 的套件清單（目前只掃 `./pkg/framecodec/`、`./pkg/msg/`）才會被執行；Makefile 的 `ci-alloc` 只是呼叫這支腳本
- 測試預設呼叫 `t.Parallel()`（paralleltest 強制）。會改寫全域狀態的測試維持序列，並以 `//nolint:paralleltest // 原因` 註明：`t.Setenv`、logger／tracer／故障注入／協定錄製／協定版本等全域設定、斷言全域 Prometheus 指標的增量
- 父測試底下有並行子測試時，共用資源用 `t.Cleanup` 釋放，不可用 `defer`：父函式回傳時並行子測試還沒開始執行
- 子測試彼此有先後依賴（後者讀前者寫入的資料）時不可並行

#### Windows race test

Windows 的 Go race detector 需要 `CGO_ENABLED=1` 與可用的 C compiler。先以 user scope 安裝 LLVM MinGW UCRT：

```powershell
winget install --id MartinStorsjo.LLVM-MinGW.UCRT --exact --scope user --accept-package-agreements --accept-source-agreements
```

再從專案根目錄執行 `.\scripts\test-race.ps1`。腳本會檢查 Go、CGO 與 `CC`，接著在專案根目錄執行一次 `go test -race -shuffle=on -count=1 ./...`（涵蓋所有服務與 tools）；它會自動尋找 PATH 或 WinGet user package 內的 `clang.exe`／`gcc.exe`，找不到 compiler 時會直接失敗並列出安裝指令，不會靜默跳過 race test。環境變數只在腳本程序內暫時設定。

### 整合測試

- 位於 `integration/` 目錄
- 所有測試檔案必須有 `//go:build integration` 標記
- 整合測試需帶 `-tags=integration`；`make ci-it` 跑 `integration/`，`make ci-it-pkg` 跑各套件內的整合測試（gamestore、recordmq、central/record store、tools 等）
- `testdb.Open` 經 `pkg/mysql.OpenDSN` 開連線；`OpenDSN` 與服務連線一樣套用 `innodb_lock_wait_timeout=4` 與撥號逾時（DSN 已明確指定的值保留），整合測試與維運工具的鎖競爭不再等伺服器預設的 50 秒。直接沿用正式的 GORM 與 DSN 設定（`SkipDefaultTransaction`、`SingularTable`、`parseTime`／`loc=UTC`／`time_zone`／`interpolateParams`），不再複製一份；`pkg/mysql` 的整合測試改為外部套件 `mysql_test`，沒有匯入循環。整合測試不支援 `PrepareStmt` session（加了之後 `CREATE TRIGGER` 類回滾測試會回 Error 1295）。
- 各套件整合測試以 `pkg/testutil/testdb` 開啟 MySQL：`testdb.Open(t, "WORLD_MYSQL_DSN", models...)` 會建立並改連「原資料庫名_套件名_雜湊」的套件專用資料庫，套件之間可並行，不需要 `-p 1`；同一行程內同一模型只 AutoMigrate 一次。測試 schema 必須等同正式遷移：`gamedb` 的整合測試 `TestMigrateMatchesAutoMigrateSchema` 在兩個全新資料庫分別跑 `AutoMigrate`（`gamedb` 內未匯出的 `models()`）與 `migrate`，逐項比對欄位、索引並確認都沒有外鍵；`Migrate` 也會冪等移除既有庫遺留的盤面子表外鍵。GitLab 的 `integration` 與 `e2e` job 分別執行兩者
- 不帶 `-tags=integration` 時這些測試不會被編譯，也不會顯示跳過；改動 gamestore 等 MySQL 路徑時務必在本機或 CI 實際跑過
- 必須加 `-count=1` 禁用測試快取，避免快取結果隱藏服務互動的 flaky 問題
- 啟動真實 Central、Gate、World 子程序
- 透過 `testenv/` 建構測試環境，二進位檔只編譯一次後快取
- 二進位暫存檔在 `TestMain` 結束時由 `testenv.CleanupAll()` 自動清理；Windows 上服務子行程另外加入 Job Object，測試逾時或被強制結束時也會一併終止，不會留下佔用連接埠的程序
- `StartCluster`、`RestartGate` 會等 Gate 送出 `SyncUsersGateToCentral`（`FakeCentral.WaitForGateReady`）才返回：Gate 處理完 Central 的 ConnectInfo、把 Central 加入雜湊環後才會送，只等 TCP 連線就登入可能被 ServiceUnavailable 拒絕。手動組叢集且之後要登入時同樣改用 `WaitForGateReady`
- Gate、World、Chat、Lobby 收到 Central 第一則 TimeSync 前不接登入或不寫入：`FakeCentral` 與真實 Central 一樣在連線建立後立即送 TimeSync；`StartChat`、`StartLobby` 以 `startTimeCentral` 模擬 Central 的 chat／lobby 監聽（連線即送、之後每秒補送），等服務收到第一則才返回；真實叢集的 Central 設定含 chat／lobby 監聽，Chat 連真實 Central
- Central 每秒對 Gate 連線廣播 TimeSync，Gate 只用來校時、不轉發給玩家連線（Client 校時走 TimeSyncRequest）；讀取指定回應用 `testenv.ReadNext[T]`，它會略過 TimeSync 等系統訊息（直連 Central 的測試會收到），不要假設回應一定是下一則訊息
- 冒煙測試 `TestSmoke_*` 起真實 Central、World、Gate，檢查各服務 `/health`、`/ready` 與一次登入；CI 的 `e2e` job 先單獨跑它，叢集起不來就在一分鐘內失敗；完整測試改以 `-skip '^TestSmoke_'` 排除冒煙，不再重跑第二次（`make ci-it` 同）。真實叢集的服務各自用 `debug.addr` 綁空閒診斷埠（`RealCentralCluster.DebugPorts`），不搶預設的固定診斷埠
- 測試以 `-race` 執行時，`integration/testenv` 也以 `go build -race` 編譯 Central、World、Gate、Record 子行程，並在 `Cleanup` 檢查子行程 stderr 是否含 `DATA RACE`、`panic`、`fatal error` 與退出碼 66（race detector 的結束碼），任一項出現即讓測試失敗，不會因子行程內的競態被丟棄而假性通過；`Stop` 先送 `SIGTERM`，逾時 10 秒改送 `SIGQUIT`（讓 runtime 把全部 goroutine 堆疊印到子行程 stderr，等 2 秒），仍未結束才 `Kill`；Windows 送不出訊號時直接 `Kill`。子行程固定帶 `GOTRACEBACK=all`，並拿掉 `testutil.IsConfigEnv` 判定的設定類環境變數（清單見本文件「測試環境變數只有一份表」那一條的共用表，約 21 個前綴加 19 個整層名稱，例如 `DEBUG_`、`SESSION_`、`TCP_`、`S2S_AUTH_`、`MYSQL_`、`REDIS_`、`RABBITMQ_`；只保留 `LOG_*` 以便除錯，所以想用 shell 的 `SESSION_*`、`DEBUG_*` 調整子行程是無效的；viper `AutomaticEnv` 會用這些變數覆寫測試產生的設定檔，shell 裡為套件整合測試匯出的 `RABBITMQ_URL` 會讓 `FaultProxy` 被繞過、注入的故障根本沒發生）
- 等待 Gate 重連／斷線不比對日誌字串：`Cluster` 為 Gate 配置診斷埠（`GateDebugPort`，`WriteGateConfig` 缺 `debug` 時補上），`WaitForGateWorldConnect`、`WaitForGateUserDisconnect` 讀 Gate `/metrics` 的 `tcp_connections_total`、`tcp_connections_active`，日誌格式或層級改動不會讓這些等待失效
- 多節點測試用 `testenv.StartMultiCluster`（N 個 Gate × M 個 World，Gate 的 `dial.world` 列出全部 World、World 各有獨立 `spill_dir`），`KillWorld`／`StartWorld`／`StartGate` 與 `InterruptWorld`／`InterruptGate` 控制單一節點（Gate 沒有 `KillGate`，要先 `InterruptGate` 優雅關閉再 `StartGate`）；優雅關閉用 `ServiceProcess.Interrupt`（Unix 送 SIGINT、Windows 對子行程群組送 CTRL_BREAK），World 在 Gate 仍連著時會等滿排空期限後以 1 結束，先關 Gate 再關 World 才會以 0 結束
- 新玩家的背包在 `LoadPlayer` 時才初始化：測試要照 Client 實際流程，登入後先載入盤面再擲骰，否則擲骰結果的快照沒有背包
- 洩漏類測試讀診斷埠 `/metrics` 的 `go_goroutines` 比對起跑線；掃日誌的測試用 `t.Setenv("LOG_LEVEL", "debug")` 開 debug 並讀 `RealCentralCluster.Logs()`
- 故障注入用 `testenv.FaultProxy`（夾在服務與依賴之間的 TCP 代理，`Cut()`／`Restore()`），不依賴 docker 指令，本機與 CI services 都能跑；`StartRecordVia` 讓 Record 改連代理。崩潰用 `ServiceProcess.Kill`（`SIGKILL`）與 `RealCentralCluster.RestartWorldHard`；此類測試必須先斷言「中斷確實生效」，否則故障沒注入也會假性通過
- 登入遇到 `ServiceUnavailable`（叢集剛啟動）或 `RateLimited`（同帳號快速重登）是設計上可重試的回應：用 `loginAs`／`loginOnConn`／`logout` 等 helper，不要把它們當失敗；每次用新帳號（帶時間戳），資料庫跨次保留盤面與登入冷卻
- 同一來源 IP 在極短時間建立大量連線會碰到 Gate 的接入限流（每秒 10、burst 20）；要打這類場景的測試用 `setupGateWorldWith` 附加 `tcp.rate_limit_per_second`、`tcp.rate_limit_burst` 放寬，其他測試維持預設
- `TestSmoke_LoginLogoutExternal` 對已啟動的叢集做一輪版本握手、登入、心跳、登出，需設定 `IT_SMOKE_GATE_ADDR`（例如 `127.0.0.1:62001`）才會執行；帳號、密碼預設 `smoke_login_check`／`smoke-secret`，可用 `IT_SMOKE_ACCOUNT`／`IT_SMOKE_PASSWORD` 覆寫。叢集的發版資訊須與本倉庫相同，版本握手才會通過。登入到登出的步驟與 CI 冒煙測試 `TestSmoke_ClusterReadyAndLogin` 共用，不會再無人發現地腐化。用法：`IT_SMOKE_GATE_ADDR=127.0.0.1:62001 go test -tags integration -count=1 -run '^TestSmoke_LoginLogoutExternal$' ./integration/`
- 依賴服務預設使用 `docker-deps-up` 的連接埠：Redis `127.0.0.1:16379`、World MySQL `13306`、Central MySQL `13307`、RabbitMQ `25672`；其他位址以 `IT_REDIS_ADDR`、`IT_WORLD_MYSQL_HOST`／`IT_WORLD_MYSQL_PORT`、`IT_CENTRAL_MYSQL_HOST`／`IT_CENTRAL_MYSQL_PORT`、`IT_RABBITMQ_URL` 覆寫
- 整合測試會寫入固定 ID 的資料；要避免殘留在開發資料庫，用 `scripts/integration-deps-up.sh` 啟動專用依賴（埠號與開發環境錯開）並依它印出的環境變數執行，用完 `down` 移除
- 開發時可用 `INTEGRATION_SKIP_SLOW=1` 跳過 TTL expiry 等依賴真實時間等待的測試
- `testenv.Cluster` 的 `WaitReady`／`DialUser` 與 `RealCentralCluster` 的 `RestartWorldHard`／`DialUser` 使用建立叢集時的 `t`，只能在該測試的 goroutine 呼叫；需要子測試自己的 `t` 時用帶 `t` 參數的方法（`RestartGate(t)`、`RestartWorld(t)`）
- `TestGate_GracefulShutdown` 以 `ServiceProcess.Interrupt(timeout)` 對 `-race` 編譯的 Gate 子行程送 SIGINT 並斷言 drain 行為與結束碼；Windows 無法對子行程送 SIGINT，明確 Skip，只在 Linux／CI 驗證
- 已知：`TestRecordFault_RabbitMQOutage_NoEventLoss` 在 Windows 本機必定失敗（基準版本同樣失敗，疑 `FaultProxy.Cut` 在 Windows 沒有切斷既有連線），Linux 容器內與 CI 通過，尚未修

- 七個「程式與文件對照」測試只在有 docs 工作樹（主倉庫的 `docs/`，被 `.gitignore` 忽略）的本機跑，CI 沒有 docs 倉庫一律 Skip：`internal/archtest/docs_links_test.go`、`cmd/central/internal/app/account_lock_timing_test.go`、`pkg/grantitem/key_schema_doc_test.go`、`pkg/recordevent/type_literals_test.go`、`pkg/rediskeys/hash_field_names_test.go`、`pkg/rediskeys/schema_doc_contract_test.go`、`pkg/rediskeys/rediskeys_schema_doc_keys_test.go`。改 Redis key schema、事件型別字串、鎖定時序時，請在本機有 docs 工作樹的情況下跑一次（CI 要跑需在 GitLab 設定 docs 倉庫的唯讀憑證，尚未設定）
- 依賴子模組的測試：`tools/releasemanifest` 的 `TestProtocolLockSchemaHashMatchesGeneratedCode` 守 `protocolLockSchemaHash` 與上游 `ProtocolLock.ps1` 演算法一致，並比對 lock 與 `pkg/protocol` 的 schema hash。第十二輪 CI-M1 起 `unit` 含 `./tools/...` 的分片淺取 `deps/PJA-Protocol`，**在 CI（`testutil.InCI`）找不到 lock 檔即 Fatal**，子模組指標更新卻沒重產 `pkg/protocol` 時 MR／分支 pipeline 就擋下；本機沒 checkout 子模組時仍 Skip。改協定同步或 lock 格式時，先 `git submodule update --init deps/PJA-Protocol` 在本機跑一次
- 測試檔命名守門對 `main_test.go` 的放行條件：同目錄有 `main.go`，或檔內除 `TestMain` 與其輔助函式外沒有 Test／Benchmark／Fuzz／Example 案例；沒有 `main.go` 卻塞一堆測試的檔案不再放行。
- 日誌鍵 camelCase 守門（`internal/archtest`）：掃描 `cmd`／`pkg`／`internal` 非測試檔內 `logger.Debug`／`Info`／`Warn`／`Error`（含 `Ctx` 版本）的字串字面值鍵，含底線的 snake_case 一律失敗；另有檢查經 `[]any` 字面值與 `append` 組成、再以 slice 傳入的 kv 鍵（例如 `httpx.AuditFields`、稽核行的固定鍵）同樣必須 camelCase，原本的守門看不到 slice 傳入的鍵。
- 組合根就緒檢查登記（`internal/archtest` 的 `TestCompositionRootsRegisterReadyChecks`）：mysql／redis 的就緒檢查一律經 `dbstartup.RegisterReady`、`redisstartup.RegisterReady` 登記（Central、Chat、Lobby、Record、World、Gate 共用，連線池關閉或 Redis 故障時啟動自檢失敗並標明名稱），守門逐檔斷言組合根的登記呼叫與次數，並禁止 `cmd` 下手寫 `RegisterReadyChecker("mysql"`／`"redis"`；拿掉登記，測試會紅。
- `internal/archtest/owner_lifecycle_boundary_test.go`：`tcpserver.Server`、`tcpclient.Client` 嵌入 `*tcpsocket.OwnerBase`，把 `ServeConn`、`CloseRuntime`、`MarkClosed`、`RunLifecycle`、`SleepOrStop` 提升成公開方法；`pkg/tcpsocket`、`pkg/tcpserver`、`pkg/tcpclient` 以外的非測試程式不得呼叫（呼叫 `srv.ServeConn` 會繞過連線上限、來源 IP 限流與 S2S 驗證）。
- 掃描原始碼的結構性測試（`internal/archtest`）透過共用 walk helper 略過隱藏目錄與 `testdata`（新增守門請用該 helper，不要自行 `filepath.WalkDir`）：有 worktree 的開發機（`.claude/worktrees`）不會因掃到其他工作樹而誤報。
- `TestTestPackagesHaveGoroutineLeakDetection`（`pkg/pkg_goleak_test.go`）驗證每個有測試檔的目錄都有 `TestMain`，且函式本體呼叫 `goleak.VerifyTestMain` 或 `testutil.VerifyTestMain`（TestMain 必須在 `_test.go` 檔內；帶 `integration` build tag 的檔案只有在目錄內所有測試檔都帶該標記時才算數，如 `integration/main_test.go`）；隱藏目錄、`testdata` 與本機私有的 `tools/private` 不檢查

### 覆蓋率

- CI 執行單元測試並保存覆蓋率；全專案覆蓋率只做趨勢觀測，新增／修改程式碼的 patch coverage 目標為 **≥ 60%**
- MR 的 `coverage-report` job（`needs` 單元測試與 `integration`）另跑 `scripts/ci-patch-coverage.sh`：以 `git diff -U0` 的改動行對照單元測試與整合測試兩份 profile（直接串接，腳本逐行 OR：改動行只要任一份有執行即算覆蓋），改動行覆蓋率低於 60% 即失敗（排除 `_test.go`、生成碼、子模組與 `integration/*`：`integration/testenv` 不在任何一份 profile 裡，只改它會被算成 0%）；沒有任何覆蓋區塊的檔案，分母只計新增的非空白、非 `//` 註解行，不再把空行與註解當未覆蓋；主要靠整合測試覆蓋的程式因此不會被誤擋
- patch coverage 排除所有帶 `Code generated … DO NOT EDIT.` 檔頭的生成碼（含 `pkg/msg`），不只列舉的生成目錄
- `make cover` 產生覆蓋率報告（本機用）
- 本機 `make ci-unit` 產出 `coverage-unit.out`、`make ci-it-pkg` 產出 `coverage-integration.out`，兩者與 CI 的 `unit`、`integration` job 帶同一個 `-coverpkg`（第十一輪；本機覆蓋率數字與 CI patch coverage 一致）；全專案覆蓋率與 Cobertura 仍只合併單元測試分片（維持趨勢可比），整合測試的 profile 只供 patch coverage 使用
- GitLab 的 `coverage-report` job 合併單元測試覆蓋率並輸出 Cobertura 報告，MR 頁面顯示覆蓋率

## Git 慣例

### Commit 訊息格式

```
<type>: <中文描述>
```

常用 type：
- `feat` — 新功能
- `fix` — 修復 bug
- `refactor` — 重構
- `test` — 測試相關
- `docs` — 文件
- `ci` — CI/CD 設定
- `chore` — 基礎設施、依賴套件、例行維護
- `perf` — 效能改動。**效能理由必須用 `perf:`**，不得偽裝成 `fix`／`refactor` 夾帶耗時宣稱；body 要附 benchstat 對照（`vs base`、`goos:`、`cpu:`、含 `p=` 與 `n=` 的表格，`-count≥10`，n 必須 ≥10），守門見 CI 表的 `perf-commit-msg`；量不到數字就改用 `fix`／`refactor`，且不寫耗時數字。commit-msg 守門（`scripts/check-perf-commit-msg.sh`，pre-commit 的 commit-msg 階段與 CI `perf-commit-msg` 共用）還有兩條：① 第一行前綴只能是 feat／fix／test／docs／refactor／chore／perf／ci（可帶 `(scope)` 與 `!`；merge、revert、`fixup!`／`squash!`／`amend!` 放行）；② 非 `perf:` 的提交，訊息若帶耗時、配置量等效能宣稱數字（認得的寫法含「降到／降至／降為／降成／變為／變成／改為」箭頭詞、`N B/M allocs`，以及 allocs／B／ns 以全形斜線、逗號、頓號、對、`vs` 並列的前後對照；規則與回歸案例見 `scripts/lib/perfmsg_test.sh`），又改到 `bench/packages.txt` 內套件的非測試 `.go`，拒絕並要求改用 `perf:`，避免以 `refactor:` 繞過；已進 develop 又不改寫歷史的提交，依 `scripts/perf-msg-exempt.txt` 慣例以完整 SHA 加標題列入豁免。`perf:` 的 benchstat 另須至少一列 `[+-]N% (p=… n=…)` 且每個 n≥10

## CI/CD Pipeline（GitLab CI）

正式 remote 為自架 GitLab，CI 入口是根目錄的 `.gitlab-ci.yml`，也是唯一的 CI 設定；倉庫不再保留 GitHub Actions。

各 job 以 `needs: []` 組成 DAG 同時啟動，stage（lint、test、post-test、release）只用於介面分組。`default` 設有 `retry`（最多 1 次），只在 runner 故障（`runner_system_failure`）時重跑，測試失敗不會被重試掩蓋；不用已棄用的 `stuck_or_timeout_failure`（它含腳本掛住）。`build-images`、`deploy-staging`、`deploy-production` 設 `retry: 0`，發版與部署不自動重試。

### CI 決策紀錄

- **develop push pipeline 必建立且不被取消**（第十六輪 CI-M2／L1）：`workflow` 原本排除 develop，且 develop→main 的 MR 常駐開著時 push pipeline 不建立，`perf-commit-msg-push` 與 `bench-smoke` 永遠不跑；連續 push 也會取消前一條，使 `CI_COMMIT_BEFORE_SHA` 範圍漏檢。現在 develop push 一定建立 pipeline（`auto_cancel on_new_commit: none`）；代價是 develop push 與 MR 各跑一條，已寫在 `.gitlab-ci.yml` 註解。

- **不新增 AI 審查 job**（第十二輪 CI-L5，刻意不做）：自架 GitLab 把程式碼送到外部 API 涉及資料外流政策，目前以 MR 人工核准加離線的多輪 Go 技能審查（紀錄在 `90-參考附件/歷史/`）替代。政策改變前後續審查不再重報；若要加，限 MR、`allow_failure: true`、API key 用 Protected＋Masked 變數，結果只寫 MR 留言或 artifact。
- **`build-images-mr` 觸發條件縮小**（第十二輪 CI-L3）：原本 `changes` 含 `cmd/**/*`、`pkg/**/*`、`internal/**/*`、`tools/**/*`，幾乎每個 MR 都在 production 主機（deploy runner）跑六次 PGO 建置、一次 `apt-get upgrade` 與六次 `trivy image`，與線上 Gate／World 搶 CPU。改為只在映像相關檔、`go.mod`／`go.sum` 與 `cmd/*/main.go` 變動時觸發；Go 程式碼能否編譯交給 `lint` 的型別檢查與 `unit`，基底映像 CVE 由 tag pipeline 的 `build-images` 與每月人工升級把關。根本解法仍是移到獨立 runner（[已知安全風險](./已知安全風險.md)）。

## 依賴管理

### 人工定期升級

專案不使用 Renovate／Dependabot，依賴與映像每月人工升級，流程見[依賴管理](./tools/依賴管理.md#定期維護流程)。升級時注意：

- 升 Go 後若要跑 `go fix`，一律用 `go fix -embedlit=false ./...`，並確認 diff 不含 `pkg/dataconfig/generated`：Luban 生成檔的標頭不是標準的 `Code generated ... DO NOT EDIT.`，`go fix`／gopls／`gofmt -l` 認不得它是生成檔，會改寫成手改；`embedlit` 也被 `.golangci.yml` 刻意停用（保留協定包裝型別名稱）。根本解法是 PJA-Config 的 Luban 輸出改成標準標頭（需改上游）。
- `.gitlab-ci.yml` 的 `compose-config` 映像 tag 目前是 `docker:29-cli`；digest 不變時要檢查 tag 的主版本是否仍在維護（`docker:27-cli` 曾停更一年半，每月「換 digest」換不到東西）。

- `github.com/redis/rueidis` 主 module 已升到 v1.0.79：新版 singleflight 的 `DelayDo` 會留下 sleep 中的 goroutine，`pkg/testutil` 的 goleak 已忽略（`LazyDo`、`DelayDo`）；`deps/PJA-Database` 子模組依賴也已對齊（rueidis v1.0.79）。
- Go 版本散在 golang 映像（`.gitlab-ci.yml`、`docker/app.Dockerfile`、`scripts/ci-deploy.sh` 的 `GO_IMAGE`）、`go.mod` 的 `toolchain`、`tools/gotools/go.mod` 的 `toolchain` 與 `.gitlab-ci.yml` 的 `GO_VERSION`，必須同一個 commit 一起升（工具模組的 `toolchain` 行決定開發機跑 lint、govulncheck 所用的 Go）。
- 映像一律 `tag@sha256:digest` 釘選；`.gitlab-ci.yml` 的 `trivy` job、`build-images` 與 `build-images-mr` 內共三處 trivy 映像要同版本。
- 升 Go 或 trivy 版本時，上述位置（`go.mod` 與 `tools/gotools/go.mod` 的 toolchain、`.gitlab-ci.yml` 的 `GO_VERSION`／golang 映像／三處 trivy 映像、`docker/app.Dockerfile`、`scripts/ci-deploy.sh` 的 `GO_IMAGE`）由 `tools/internal/configaudit` 的 `TestToolchainVersionsAreConsistent` 比對，漏改任何一處測試就失敗。
- 升 MySQL、RabbitMQ、Redis 映像時，`.gitlab-ci.yml` services、`docker/compose/compose.prod.yml` 預設值與 `.env.prod.example` 的 `*_IMAGE`（正式環境實際由複製出的 `.env.prod` 決定映像，compose 預設值只在未設定時生效）三處須同 digest；`scripts/backup-restore-drill.sh` 的 MySQL／Redis 預設映像也要與 `compose.prod.yml` 一致，否則演練驗證的是舊版備份格式。同一個測試比對，漏改即失敗。

### 依賴原則與工具

- 新增依賴前先確認標準函式庫是否已涵蓋。

## 本機開發流程

### 快速啟動

```bash
# 一鍵啟動（需先 ./scripts/docker-deps-up.sh；啟動 Central、Record、Lobby、Chat、World、Gate、User）
MYSQL_USERNAME=root ./scripts/dev-up.sh

# 或用 Docker Compose
docker compose -f docker/compose/compose.full.yml up -d --build
```

開發環境設定檔位於：

- `config/dev/central.yaml`
- `config/dev/world.yaml`
- `config/dev/gate.yaml`
- `config/dev/user.yaml`
- `config/dev/lobby.yaml`
- `config/dev/chat.yaml`
- `config/dev/record.yaml`

`dev-up.sh` 直接使用這些檔案，不另產生範本；各 cmd 啟動時驗證 `id`、`s2s_auth.enabled`、`redis.addr` 等必填鍵，新增必填鍵時同步補齊 `config/dev/*.yaml`。

組合根呼叫 `startup.InitializeRuntime` 成功後要**立刻** `defer rt.Close()`（`*startup.Runtime`）：它持有設定監看器與協定檔案記錄器，之後任何早退路徑都會一併關閉，不必在各分支手動收尾。

### OTel 分散式追蹤設定

Gate / Central / World 的設定檔均支援以下區塊：

```yaml
debug:
  pprof_enabled: true                # pprof handler 開關；缺省為 false（關閉），dev 設定檔明確寫 true

otel:
  exporter: ""                       # 留空 = noop（不輸出）; "stdout" = 終端機; "otlp" = OTLP HTTP
  endpoint: "http://localhost:4318"  # OTLP HTTP exporter 目標（exporter=otlp 時生效）
  sample_rate: 0                     # 0=全量(預設), 0~1=比例取樣, 負值=停用
```

本機快速啟動 Jaeger（All-in-One，含 OTLP HTTP 接收器）：

```bash
# 4318：OTLP HTTP 接收；16686：Jaeger UI。反斜線必須是行尾最後一個字元，後面不可再接註解。
docker run -d --name jaeger \
  -p 4318:4318 \
  -p 16686:16686 \
  jaegertracing/all-in-one:1.62.0
```

映像版本只供本機查看 trace，可自行換成較新的固定版本，不要用 `:latest`。

啟動後將 `otel.exporter` 設為 `otlp` 即可在 `http://localhost:16686` 查看 Trace。

OTLP 只有在設定檔的 `otel.endpoint` 與環境變數 `OTEL_EXPORTER_OTLP_ENDPOINT`／`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` 都沒有指定時（本機預設 `localhost:4318`）才用明文；任一處指定 endpoint 時由 endpoint 的 scheme 決定，`https://` 不會被降級成明文。

#### DB 自動追蹤

Redis 與 MySQL 查詢已自動加入 OTel tracing span：

- **Redis**：`pkg/redis.Client.Do` / `DoMulti` 自動包裝 `redis.call` / `redis.pipeline` span
- **MySQL**：GORM 註冊 tracing plugin，`mysql.query` span 附加 `table` 屬性

無需手動改寫 caller，所有查詢在 Jaeger/Tempo 中可見。前提是追蹤已開啟，且 ctx 帶有遊戲 `traceID`（協定訊息 handler）或已有取樣中的 span（HTTP 請求的 `otelhttp` 請求 span）：這兩者都沒有時 `StartSpan` 不建立 span。HTTP 請求底下的 Redis／MySQL 子 span 是第十輪才補上的（`StartSpan` 在 traceID 為 0 時，原本直接返回）。

#### 錯誤記錄到 span

```go
tracing.RecordSpanError(ctx, err)
```

在 handler error 路徑加上此行，span 會標為紅色並附帶 error message。需同時保持 `logger.ErrorCtx` 記錄結構化日誌。

### Gate 排空設定

Gate 支援 `drain_timeout` 設定，覆寫預設的 30 秒排空等待。
值必須是正的 duration，且不得超過 40 秒（`services.MaxDrainTimeout`，第十一輪）；壞值（缺單位、亂碼、非正數、超過上限）使 Gate 拒絕啟動（不是忽略後改用預設），未設定才使用預設值。上限讓 Gate 最壞關機耗時（drain 40 秒＋其餘任務＋收尾 4 秒＝74 秒）一定小於 `stop_grace_period` 75 秒；真的需要更長時，`MaxDrainTimeout`、四份 compose 的 grace 與契約測試要一起改：

```yaml
drain_timeout: 35s  # 根據玩家平均會話長度調整，上限 40s
```

`drain_timeout` 只套給 drain 任務，其餘關機任務維持單一任務逾時 5 秒；最壞關機耗時＝各任務逾時加總＋2 次 5 秒（RunApp 的 app shutdown 與等事件迴圈退出），TCP 服務（Gate、Central）最後再多等一次背景工作 5 秒，各服務再加 debug server 與 tracing 收尾（`pkg/startup` 內未匯出的 `observabilityCleanupTimeout` 各 2 秒、合計上限 `ObservabilityCleanupMax` 4 秒；第十一輪起計入契約，原本各 5 秒且未計入，World 75 秒加 debug 5 秒剛好等於 grace 80 秒，開 tracing 就超過；debug server 收尾逾時會 `srv.Close()` 切斷進行中的 pprof 或卡住的 `/ready`）。容器 `stop_grace_period` 必須大於它，各 compose（`full`、`debug`、`core-test`、`prod`）已補齊：Gate 75 秒、Central 65 秒、World 80 秒（盤面工作者停止任務另有 10 秒期限，最壞約 75 秒）、Chat 30 秒、Lobby／Record 20 秒。調高 `drain_timeout`（超過預設 30 秒時）或新增關機任務，都要同步調高 grace；各服務的 `shutdown_plan_test.go` 契約測試會斷言最壞耗時小於四份 compose 的 grace，漏改就失敗。

事件迴圈本體 panic 時（`RunApp`，第十輪）：`RunApp` 先 `app.Stop()` 再跑關機協調器，PreDrain 期間 App ctx 已取消、`PostEvent` 回 false，等事件迴圈的背景迴圈才會退出；以前先跑關機任務，PostEvent 回 true 卻永遠沒人執行，卡住的背景 goroutine 洩漏。看門 goroutine 也改用 `defer` 收掉，不會在 panic 後 20 秒誤報 `event loop stalled`。`RunApp` 回傳的錯誤含 `appcore: event loop panicked`。

HTTP 服務的關機（`httpx.ServeLimited`，Lobby、Record，第十輪）：請求的 `BaseContext` 沿用啟動 ctx 的值但用 `context.WithoutCancel` 切斷取消，SIGTERM 時 in-flight 的寫入型請求（例如封禁後踢線、發道具入列）能做完，不會做一半。關機仍有上限：停止接受新連線後最多等 5 秒（`serverShutdownTimeout`）優雅關閉，逾時就 `srv.Close()` 強制中斷，卡住的 handler 不會讓關機無上限；Lobby／Record 的 `stop_grace_period` 20 秒足以容納。多個 server（Lobby 公開與 admin）以 goroutine **並行** `Shutdown`、共用同一個期限（第十一輪；原本依序關閉，第一個被慢連線用完期限後，第二個拿到過期 ctx 直接被 Close，執行中的 admin 寫入被切斷）。Lobby 寫入型 admin 請求的 ctx 另以 `context.WithoutCancel(r.Context())` 為父 ctx（上界仍是 3 秒 `requestTimeout`），GM 用戶端逾時或中途斷線時，封禁後的踢線步驟不會因 ctx 已取消而失敗。

### 服務 ID 設定

`id` 必須是正整數，以 `bootstrap.Int` 嚴格解析（十進位整數；`1001.5`、`6k`、`6,000` 一律報錯，環境變數 `01001` 也不會被當成八進位；設定檔寫未加引號的 `id: 01001` 在讀檔時就被拒絕，第十二輪 V-L3）。啟動與熱重載共用 `bootstrap.ValidateLoaded`，`id` 必須寫在設定檔裡，熱重載也同樣嚴格解析。
壞值會在啟動期直接報錯，不會被截斷、轉成其他數字或繞過驗證；驗證後以十進位結果寫回 viper，各服務之後讀到的是同一個值。

### World 容量設定

World 支援 `max_players` 設定，用來限制單台世界服最多承載的玩家數：

```yaml
max_players: 5000
```

- 未設定或 `0` 使用程式內建預設值
- 負值是設定錯誤，World 拒絕啟動（錯誤訊息 `max_players: config max_players=-1: must not be negative`，`-1` 依實際值），不會被當成預設值悄悄吞掉
- 以 `bootstrap.Int` 嚴格解析：`6k`、`6,000`、`5000.5` 等壞值啟動失敗，不會靜默退回預設值（行為變更：原本會被寬鬆解析成 0 再退回預設 5000）

### Go 執行檔輸出位置

- 本機開發服務使用 GoLand 的 Go Application 設定或 `go run`，不在專案目錄留下服務 exe。
- 需要保留編譯好的服務或工具時（Linux／macOS／WSL 建出的 binary 沒有 `.exe` 副檔名，`.gitignore` 已列各 main 套件的同名檔，但仍建議輸出到 `bin/`），從專案根目錄執行 `make build`（全部服務）或 `go build -o bin/<名稱>.exe ./cmd/<服務>`；運維工具統一用 `go build -o bin/pja.exe ./tools/pja`；`bin/` 是手動建置二進位檔的標準輸出目錄，已加入 `.gitignore`。
- 執行 `go test` 時讓 Go 管理測試產物；若使用 `go test -c`，以 `-o bin/<名稱>.test.exe` 指定輸出位置。
- 不要在根目錄直接執行會輸出單一執行檔的 `go build ./cmd/<服務>`；`.run/` 留給本機執行狀態，`make clean` 刪 `bin/`、全樹（`cmd`／`pkg`／`internal`／`tools`／`integration`，`tools/private` 除外）的 `*.exe`、`*.test` 與無副檔名的服務 binary，以及 `coverage-*.out`，不碰 `.run/` 或工具相依檔案，也不再 `go clean -cache`（那是使用者全域快取，需要時自行執行）。

## Pre-commit Hooks

`.pre-commit-config.yaml` 於專案根目錄，本機 commit 前自動執行風格檢查，減少 CI 因 formatting 失敗。

啟用方式：

```bash
pip install pre-commit
pre-commit install
```

`pre-commit install`（或 `make hooks`）依 `.pre-commit-config.yaml` 的 `default_install_hook_types` 一次裝 pre-commit、commit-msg 與 pre-push 三種 hook，不必再加 `--hook-type`（舊 clone 重跑一次才有 pre-push，見上文）。commit-msg 階段的 `perf-commit-evidence`（`scripts/check-perf-commit-msg.sh`）檢查 `perf:` 前綴的提交內文必須含 benchstat 輸出（`vs base` 表頭）或寫明「量測方式」，否則拒絕提交。在 `default_install_hook_types` 加入之前就裝過 hook 的 clone 只有 `.git/hooks/pre-commit`，必須重跑一次 `pre-commit install`（確認 `.git/hooks/commit-msg` 存在）；第十一輪 BM-M3 發現第九輪後 8 個 `perf:` 提交都沒附量測，因為本機沒有這個 hook、CI 也不檢查；現在 MR 另有 `perf-commit-msg` job 對每個提交執行同一支腳本。效能改善一律先量測：`perf:` 提交的被改程式沒有 benchmark 時，同一個提交補 `_bench_test.go` 並列入 `bench/packages.txt`，否則 `bench-gate` 量不到退化；新套件的基準檔段落可先列入 `bench/pending-baseline.txt`，不必為此局部改基準檔。

`test-file-names` hook：`.go` 檔新增、刪除或改名（含 `_test.go` 與其來源檔）時自動跑 `TestTestFileNamesMatchSourceFiles`（測試檔命名守門），避免中間提交變紅、之後才補而無法 bisect；pre-commit 的 `files` 篩選看不到已刪除的檔案，所以此 hook 用 `always_run` 自己檢查 staged 的 A／D／R。

手動對所有檔案執行一次：

```bash
pre-commit run --all-files
```

## Docker 部署規則

### 映像檔

- 多階段建構：Go builder + Debian runtime
- 基底映像固定到 digest（`golang:1.27.3-bookworm@sha256:…`、`debian:bookworm-slim@sha256:…`），CI 與 Dockerfile 使用同一組 Go 映像；升版時需同步更新 `.gitlab-ci.yml` 與 `docker/app.Dockerfile`
- 建置：映像在發版時建置（CI 的 `build-images` 呼叫 `scripts/docker-build-images.sh`，手動發版走 `scripts/docker-release.sh`）；MR 動到映像相關檔案時由 `build-images-mr` 以相同腳本建置並掃描（不推送）。`docker/app.Dockerfile` 的 `ARG APP_DIR`、`ARG VERSION` 放在 `go mod download` 之後，否則 BuildKit 會讓每個服務、每次發版都使下載層快取失效
- runtime 階段的 `apt-get upgrade` 層帶 `ARG APT_REFRESH`：`docker-build-images.sh` 預設傳 `CI_PIPELINE_ID`（本機為日期），讓這一層每條 pipeline 重跑一次；基底映像以 digest 釘死，沒有它，deploy 主機的 BuildKit 快取會一直重用舊的安全更新層
- `scripts/ci-deploy.sh` 跑 migrate 時，MySQL DSN 以環境變數傳入容器（`-e MYSQL_DSN` 不帶值），不再出現在 `docker run` 命令列（`ps`、日誌看不到密碼）
- 映像掃描：`build-images` 建置後、推送前對六個映像跑 `trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed`（有可修補的漏洞即失敗）；runtime 階段先 `apt-get upgrade` 套用 Debian 安全更新，否則基底映像已有修補的套件會擋下發版
- 已提供：`build-images` 對每個映像產出 CycloneDX SBOM（trivy `--format cyclonedx`，`sbom/` 存成 365 天 artifact）。尚未提供：多平台建構、`provenance` 證明與映像簽章；要啟用時在發版腳本或 CI 加入
- CI 的映像倉庫登入（`scripts/ci-registry.sh login`，`build-images`、`deploy-*`）：設定了 `REGISTRY_USER` 就用 `REGISTRY_USER`／`REGISTRY_PASSWORD` 登入外部倉庫；否則目標主機等於 `CI_REGISTRY` 時用 GitLab 的 `CI_REGISTRY_USER`／`CI_REGISTRY_PASSWORD`；其餘情況（未啟用 Container Registry、外部倉庫沒給帳密）略過登入。有給帳密就必須登入成功，失敗即讓 job 失敗（不再 `|| true` 吞掉）
- `workflow:rules` 只對 `push` 事件擋下已開 MR 的分支 pipeline（避免與 MR pipeline 重複）；排程與手動（`web`）pipeline 不受影響
- 健康檢查：Docker HEALTHCHECK 指令（`wget http://localhost:${HEALTHCHECK_PORT}/ready`）；`HEALTHCHECK_PORT` 以 build arg 傳入各服務的除錯埠並轉成 ENV，建置腳本與 workflow 已依服務設定；`scripts/failover-drill.ps1`、`production-smoke.ps1` 也在容器內讀這個 ENV 打 `/ready`，不另寫埠表，建置腳本列的埠由 `pkg/debug` 契約測試比對 `debug.Endpoint`；p0-daily-check、alert-selfheal 的診斷網址參數預設空字串，交給工具依 `<SERVICE>_DIAG_URL` 或預設埠決定
- 健康檢查間隔：30s、timeout 5s、start-period 15s、重試 3 次
- Config 透過 volume mount 掛載

### 備份/還原

#### 基本備份與還原

- `scripts/docker-backup-mysql.sh` / `scripts/docker-restore-mysql.sh`
- `scripts/docker-backup-redis.sh` / `scripts/docker-restore-redis.sh`

#### 還原演練

- `scripts/backup-restore-drill.sh` 用臨時 MySQL / Redis 容器驗證備份、還原、資料校驗流程，不碰正式資料

#### schema 與衍生資料變更

- `PJA-Database/cmd/datamigrate` 用 migration plan 跑 MySQL schema 與 Redis persistent-data 變更，支援 apply / rollback，適合發版前先驗回滾。多句 plan 中斷（DDL 隱式提交）時進度記在 `schema_migrations_progress`，重跑 `apply` 從失敗步接續；人工處理完該步用 `-mode resolve -target <version> -confirm` 略過它（見 PJA-Database README 3.1）；Redis `rename_prefix` 用 `RENAMENX`，目標鍵已存在即中止
- `tools/private/datasurgeon` 可修 `central:routing`、`player:{playerID}`、`world:{worldID}:players`、`gm:grant_item:deadletter` 這類 Redis 衍生資料

#### 資料庫交易

- World 的熱路徑交易（`SavePlayerChanges`、`LoadPlayerSnapshot`、`archivePlayerBundle`、`initializePlayer`）使用 `pkg/mysql.RetryableTransaction`，遇到 MySQL deadlock（Error 1213）自動重試 3 次，間隔指數退避（約 50ms → 100ms → 200ms，各帶 ±50% 抖動，避免互相 deadlock 的兩筆交易同時重試）
- 非 deadlock 錯誤直接回傳不重試，保留錯誤排查的可觀測性
- Record / Central / Chat / World 服務在 shutdown 時執行 `sqlDB.Close()` 關閉連線池，防止 rolling update 時殘留連線

### 資料保留

- `request journal` / `replay cache` 的重試預算優先內化到實際使用端；目前只保留世界服 grant queue 與 deadletter replay 的本地 helper
- `grant item dead-letter` 預設保留 7 天，避免 Redis list 永久長大
- `player_profile` / `player_inventory_item` 的 archive 規則以不活躍 90 天為基準，封存 job 每日跑一次
- `gm audit` 建議保留 30 天，後續再交由 log sink / table retention 落地

## TCP 協定說明

**Frame 格式**（`pkg/framecodec/coder.go`）：

```
[4 bytes uint32 LE: total size] [2 bytes uint16 LE: msgID] [payload bytes...]
```

- `size` = 4（size 欄位本身）+ 2（msgID）+ len(payload)
- 最大訊息大小：4 MB（`maxMsgSize = 4 * 1024 * 1024`）
- **協定為 breaking change**：客戶端必須使用 uint32 讀取 frame size，不相容舊版 uint16 協定

## User 測試客戶端指令

透過 stdin 輸入以空白分隔的指令（`tools/user/internal/stdinevent/`，以 `strings.Fields` 切欄位）：

```bash
printf 'login 0 alice mypassword\n' | go run ./tools/user -config config/dev/user.yaml
```

格式：`login <accountType> <account> [password]`

| 位置 | 說明 |
|------|------|
| 第 1 欄 | 指令名稱（`login`，不分大小寫） |
| 第 2 欄 | 帳號類型（accountType，0～255 的數字，範例用 `0`） |
| 第 3 欄 | 帳號名稱（account） |
| 第 4 欄 | 密碼（password，可省略） |

> **注意**：新帳號必須帶非空密碼（首次登入時會以 bcrypt 雜湊存入 MySQL，空密碼回 `AuthWrongPassword`），所以第一次登入要帶密碼；既有舊帳號可省略。未知指令記 `unknown command` 警告並以 `available` 欄位列出可用指令；stdin 讀到 EOF（例如背景執行、輸入已關閉）時記一行 `stdin closed; commands disabled`，之後只保持連線、不再收指令。

## 進階測試

### Fuzz Testing

目前的 fuzz target（以 `git grep -n '^func Fuzz'` 為準）：

| 套件 | Fuzz target | 測試路徑 |
|------|-------------|----------|
| `framecodec` | `FuzzWriteFrame` | WriteFrame 的 header／payload 正確且可由 Decode 讀回 |
| `framecodec` | `FuzzCoderDecode` | Decode／DecodePooled 三條解碼路徑結果一致，且可由 WriteFrame 還原 |
| `tcpsocket` | `FuzzPackedMsgUnpack` | 任意位元組不 panic |
| `tcpsocket` | `FuzzPackedMsgRoundTrip` | Pack/Unpack 往返一致性 |
| `msg` | `FuzzClientMessageUnpack` | 玩家端每一種訊息 Unpack 任意位元組不 panic，長度宣稱不會造成超量配置 |
| `msg` | `FuzzForwardToWorld`、`FuzzTimeSync`、`FuzzHeartbeatReq` | 個別 S2S 訊息 Unpack 不 panic、往返一致 |
| `msg` | `FuzzMsgID`、`FuzzMalformedUnpack`、`FuzzMalformedPack` | 訊息 ID 解析與畸形輸入不 panic |
| `cmd/gate/internal/app` | `FuzzSessionState` | 以任意位元組序列驅動正式路徑的 session 操作（每個位元組選一個操作與參數），每步實際斷言 session 狀態不變式 |

新增玩家端訊息時，`FuzzClientMessageUnpack` 的型別清單取自 `clientRoundTripCases`（`Sender=="Client"`），要同步把新訊息加進該表。

執行 fuzz test：

```bash
go test -fuzz=FuzzCoderDecode ./pkg/framecodec/
go test -fuzz=FuzzPackedMsgUnpack ./pkg/tcpsocket/
```

GitLab 的 `fuzz` job 在排程 pipeline 或從介面手動執行 pipeline 時，自動找出所有 `func Fuzz*` 並各跑 `FUZZ_TIME`（預設 60 秒）；失敗輸入存成 artifact（路徑限縮為 `cmd`、`internal`、`pkg`、`tools` 底下的 `testdata/fuzz/`；原本的 `**/testdata/fuzz/` 會走進 `.gocache` 模組快取，把第三方套件的 corpus 約 24 MB 一起上傳）。排程需在 GitLab 專案的 Build → Pipeline schedules 建立（建議每日一次）。

fuzz 找到的失敗輸入（`testdata/fuzz/<Target>/`）修好 bug 後要連同修正一起提交：artifact 只留 30 天，沒提交的話日後回歸時單元測試不會把它當 seed 重跑。

新增 fuzz test 的時機：
- 處理外部輸入的協定解碼器
- 二進位序列化/反序列化
- 任何接受 `[]byte` 作為輸入的公開函式
