# 全專案審查提示詞

用途：請代理對整個專案做唯讀審查，並在使用者確認後逐項修正。分兩層：**通用層**可跨專案使用；**本專案附錄**只適用 PJA-Server。使用時把 `{…}` 填好；`{報告輸出路徑}` 未指定時預設 `docs/90-參考附件/歷史/全專案審查紀錄-<日期>.md`，不確定就先問。

---

## 通用層

請審查全專案，找出下列問題並列出證據。**審查階段唯讀**：不修改專案檔、不 commit、不 push。

### 開始前

1. 先讀專案說明與規範（README、CLAUDE.md、AGENTS.md、架構文件、開發規範），硬規則照做。
2. 先讀上一輪審查紀錄與「刻意不改」清單（`docs/90-參考附件/歷史/`、專案記憶），已列項目不重報；有新證據推翻才標「需確認」。
3. 用搜尋找出實際的資料層、業務層、傳輸層、共用層檔案，不憑目錄或檔名判斷。忽略舊副本與產物目錄（worktrees、唯讀備份、bin、`*.exe`）。
4. 同類實作（多個 store、handler、client，正式版與測試版）逐份比對，不可只看一份。
5. 用平行子代理分區審查時：子代理一律以**文字**回傳 findings（不要寫報告檔），由主代理合併；每個子代理都附同一份簡報與判定規則。

### 設計原則（審查與修正的判斷基準）

以下原則是 A～I 各項的共同標準；兩種做法都行時，選更符合這些原則的一種。

1. **高內聚、低耦合**：一個模組只負責一件事，相關的規則與資料放在一起；模組之間只透過窄介面溝通，不依賴對方的內部實作。
2. **遊戲邏輯只有一套**：同一套遊戲邏輯不因儲存方式（MySQL、Redis、記憶體、檔案）而各寫一份。規則與資料結構集中在共用的領域模組，儲存後端只負責存取，並透過介面替換。
3. **外部依賴一律注入**：資料庫、快取、訊息佇列、HTTP client、檔案系統等外部依賴，由呼叫端以介面傳入，業務程式不直接 import 具體實作。
4. **時間與亂數也是外部依賴**：`time.Now()`、全域亂數、環境變數不得出現在業務與領域程式；改由 `Clock`、`Rand`、設定等介面注入，測試與模擬器才能固定結果、與正式流程共用同一條路。
5. **依賴方向只往內**：傳輸層與資料層依賴領域層，領域層不依賴它們；組裝根（main、services）負責把具體實作接上介面。
6. **同一套邏輯、多種載體**：正式服務、模擬器、工具、測試替身呼叫的是同一個共用模組，差別只在注入的依賴不同。

審查時對照：違反上述任何一條的地方，歸入對應的 A／B／C／F／H 項，並在「建議搬移或修正位置」寫明要抽出的共用模組與要新增的介面。

### 審查目標

#### A. 分層與共用核心
- A1 資料存取層（ORM、SQL、快取、檔案 IO）混入業務邏輯：呼叫領域規則函式（計算、上下限、溢位、狀態機）；決定寫什麼或跳過什麼（去重、冪等、補償）；與資料存取無關的通用工具；同一規則在資料層與另一實作（如記憶體版）各一份。不算問題：純查詢組合、交易邊界、row lock、型別轉換；為交易一致性必須同 tx 內做的判斷標「合理」並說明。
- A2 非資料存取的型別、介面、純函式放在資料層檔案，應搬到領域層。
- A3 傳輸層（handler、controller、RPC、訊息消費者）自行做計算、狀態判斷、規則驗證，而其他入口有同一份規則。
- A4 依賴注入與單一邏輯（對應設計原則 2～4）：
  - 業務層與領域層直接 import ORM、SQL、Redis、MQ、HTTP client，或直接呼叫 `time.Now()`、全域亂數、讀環境變數，應改為介面注入。
  - 同一流程在不同儲存後端（MySQL、Redis、記憶體、檔案）各寫一套，應抽成共用模組：資料結構與規則共用，後端只透過介面替換。

#### B. 測試工具與真實流程一致性（有模擬器、fixture、替身時才查）
- B1 是否使用與真實系統相同的核心資料結構。B2 是否呼叫正式核心流程，而不是重寫規則。
- B3 同一組操作，真實與測試流程的狀態是否一致。**先列出所有「待處理／一次性資格」狀態**（待處理報價、待結算、已用資格等），逐一比對；並比對測試用 schema 與正式遷移是否一致（外鍵、索引、欄位寬度），以及記憶體版與 SQL 版的准入規則。
- B4 API、表單、CLI 是否只做格式轉換。B5 是否有只給測試用的旁路（測試模式分支、跳過檢查）。
- B6 是否有一致性測試（同輸入，真實與模擬結果必須相同）；缺少者列為待補，並列出要補的情境。

#### C. 同一規則多份實作
- C1 同一判斷多處：ID 解析、長度上限、錯誤碼分類、設定有效性、請求欄位驗證、「保存資料是否合法」。
- C2 兩端結果不同（一端放行 0、另一端拒絕）。
- C3 手寫名稱表或枚舉對照應由單一來源反查。**跨服務清單**（轉送白名單、路由表、訊息 ID 表、失敗回應表）要比對集合是否相等，並要求有一致性測試。
- C4 寫死的字串或數字（參數名、路徑、上限、初始值、服務名、debug 埠、環境變數名、指標名稱）應改共用常數。
- C5 工具或診斷程式自己重做讀取與解碼，而函式庫已有。

#### D. 設定與協定
- D1 設定載入時順便算業務結果；同一份設定多處各自解析、各自套預設值；**驗證函式與解析函式各寫一套規則**（驗證過、解析失敗），驗證應直接呼叫解析。
- D2 序列化層（protobuf、JSON、DTO）轉換時補預設業務值、過濾資料，或同一欄位在不同轉換函式對應不同。

#### E. 背景任務與觀測
- E1 排程、worker、cron、outbox、清理迴圈內直接寫業務規則，或排程迴圈放在資料層或 handler。
- E2 業務分支只為打點存在；打點失敗影響業務；同事件多層重複記錄。

#### F. 工具套件
- F1 通用套件 import 業務套件，或內含特定 ID、數值（含寫死服務名）。
- F2 同一工具多處各寫一份（含維運工具各自寫死的服務名、埠、環境變數、指標名稱）。

#### G. 資料庫與依賴
- G1 外鍵：列出真外鍵與應用層假關聯；判斷是否造成刪除順序、封存還原順序、分表、跨服務寫入的耦合；列出可改為應用層一致性的候選與理由；確認測試 schema 是否也建立外鍵。
- G2 套件循環與過度依賴（用 `go list` 之類的工具產依賴圖，列扇入扇出過大者與概念上的雙向依賴）。
- G3 同一規則寫在領域、資料、傳輸多處，建議單一來源。
- G4 文件與設定一致性：比對 docs 與 compose、設定檔、實際部署（例如資料庫實例、埠、保留期限）。

#### H. SOLID / DRY / KISS / YAGNI
- H1 單一職責被破壞的大型結構或函式；介面過胖；高層直接依賴低層實作。
- H2 重複超過兩處且行為應一致。H3 不必要的抽象、只有一個實作的介面。
- H4 沒有呼叫端的方法、欄位、介面成員、設定項、參數；註解宣稱「某某會使用」但無呼叫端。**對每個訊息類型列出發送端與接收端，缺一端者標出。**
- H5 只在套件內使用卻匯出；未被引用的程式。刪除前必須 grep：全專案、測試、tools、不進版控目錄、特殊 build tag 檔，**並確認同套件其他檔沒有呼叫**。判斷要由第二個視角覆核。

#### I. 並行、時序與錯誤處理
- I1 快取載入與寫入／作廢交錯，舊資料以新時間寫回（是否需世代計數）；過期、不存在、TTL 邊界值（如 `PTTL=-2`）被當成合法資料寫入備份。
- I2 非同步刪除或清理期間，對象已重建或重新登入，舊動作抹掉新狀態；**刪除一律要 compare-and-delete，條件含擁有者**（如 worldID、gateID）。
- I3 先刪後寫，或檢查與動作之間沒有鎖。
- I4 內部錯誤被轉成通用拒絕碼卻沒記日誌；**每個失敗分支都要有日誌**；暫時錯誤與永久錯誤是否用不同結果碼。
- I5 錯誤格式化用了 nil（Go 的 `%w` 配 nil err）。
- I6 部分成功被當整體失敗而丟掉結果（含診斷工具）。
- I7 永久錯誤被無限重試，或暫時錯誤被誤標為已處理。
- I8 失敗結果被算成功：只看有無回應、不看回應碼；**驗證閘門遇缺欄位、空檔、零值時必須失敗，不可略過**。
- I9 資料競爭：列出所有在事件迴圈（或單一擁有者）之外讀寫應用狀態的 goroutine，要求 `-race` 測試。
- I10 無條件覆寫：寫入前來源欄位為空時，是否把既有值蓋成空值。

### 判定規則

- 每項先證明「真的會出錯」：具體輸入與錯誤輸出，或能重現的測試概念（修正前失敗、修正後通過）。只有推測標低信心。
- 不確定是否刻意設計，標「需確認」，不得直接判定為問題。
- 不列風格與命名建議。不臆測：讀完函式本體再下結論，不可只看函式名。
- 死碼與「無呼叫端」結論，輸出前再做一次覆核（見 H5）。

### 輸出格式

每項一行，依嚴重度排序：

`path:line | 類別 | 問題說明（附程式片段；重複的附另一處 path:line） | 建議搬移或修正位置 | 信心（高／中／低）｜分級（確定要修／需決定／刻意不改）｜修正方式（fix／refactor）`

類別填大項加問題類型，例如「A1-混入業務」「C2-分歧」「G1-外鍵耦合」。

### 最後分組

1. 可合併成一個重構提交的群組（行為不變，純搬移或抽取）。
2. 需分開做的項目：會改行為的標 fix；需我先決定的列選項與各自代價。
3. 查過但刻意不改的項目，附原因。
4. 用白話說明每一類問題，各附一個本專案的實際例子。
5. 一致性測試待補清單（B6）。

結果超過一頁，寫成 Markdown 檔放在 `{報告輸出路徑}`，對話中只給摘要與檔案連結。

## 修正階段（使用者確認後）

- 一步一提交，一個提交只含一件事；commit 訊息遵守專案規範。
- 會改行為的項目先寫「修正前失敗」的測試再修；純搬移不改行為。
- 需決定項不擅自選邊：只列選項與代價；使用者要求「全做」時，僅實作有明確建議、低風險的部分，其餘原樣列出。
- 動到資料庫路徑時，自起拋棄式資料庫容器跑整合測試。
- 不進版控的目錄（如私有工具）可以改，但不要加入提交。
- 報告判斷與實況不符時（例如「無呼叫端」其實有），跳過並在修正紀錄註明，不硬改。
- 全部完成後把修正紀錄（commit 對照、跳過項、行為變更須知、待決策清單）補回審查文件。
