# 日誌規範

## 原則

- 專案新程式碼一律使用 [`pkg/logger`](../../pkg/logger/logger.go)
- [`pkg/logger`](../../pkg/logger/logger.go) 底層固定使用 `zerolog`
- Call site 不直接依賴 `log/slog`、`logrus`、`zap`
- 新增日誌欄位前，先確認是否已有既有欄位可重用
- 能不用 log 就不用 log；能少打就少打

## 標準入口

### 初始化

- 服務啟動時，以 `logger.Configure(format, level)` 設定輸出格式與層級
- `format` 只接受 `text` 或 `json`
- `level` 採 `debug` / `info` / `warn` / `error`
- `warning` 會正規化成 `warn`

### 呼叫

- 一般情況用 `logger.Debug/Info/Warn/Error`
- 有 `context.Context` 時，用 `logger.DebugCtx/InfoCtx/WarnCtx/ErrorCtx`
- 跨服務請求要先補 `trace_id`，再記 log

## 層級定義

### `Debug`

- 只放除錯細節
- 頻率高的訊息要能接受抽樣
- 不要把 `Debug` 當成正常營運日誌

### `Info`

- 正常流程節點
- 例如服務啟動、連線建立、狀態切換、任務完成

### `Warn`

- 可恢復異常
- 例如 fallback、retry、degrade、timeout、資料缺失但流程可繼續

### `Error`

- 流程失敗
- 例如 DB 失敗、初始化失敗、請求無法完成、不可忽略的 runtime error

## 欄位規範

### 必用欄位

- `err`：錯誤物件一律用這個 key
- `traceID`：跨服務鏈路才加

### 常用欄位

- `service`
- `account`
- `playerID`
- `worldID`
- `gateID`
- `requestID`
- `addr`
- `key`
- `count`
- `elapsed_ms`
- `threshold_ms`

### 命名規則

- camelCase 優先，與現有 `pkg/logger` 輸出一致
- 同一語意固定同一欄位名
- 不要同時混用 `uid`、`player_id`、`playerID`

## `trace_id`

- `trace_id` 用於串聯 Gate / Central / World 日誌
- 跨服務 request 進入 Gate 後建立
- 只在需要追蹤鏈路時才補
- dispatch 層會自動從 `TraceScopedMessage` 中提取 `traceID` 注入 `sock.Context()`
- handler 中直接使用 `sock.Context()` 即可，無需手動呼叫 `logger.WithTraceID`
- `tracing.StartSpan(ctx, 0, ...)` 會從 ctx 自動讀取 `traceID`
- 需手動注入的情境：背景 goroutine、非訊息入口、建立新 trace 的入口點
- 實際 log 欄位名使用 `traceID`，不是 `trace_id`

## 與 metrics 的分工

- log 記單筆事件與上下文
- metrics 記聚合結果與趨勢
- 不要把狀態機轉移規則藏進 log
- 不要把單筆除錯訊息當成監控依據

## 敏感資料

以下內容禁止直接寫入 log：

- 密碼
- token
- session secret
- 完整 bcrypt hash
- DB password
- Redis secret
- 大段 request body
- 大段 response body

需要查問題時，只記可識別最小集合欄位，不記原文。

## 重複與噪音

- 同一個錯誤不要在同一條鏈路重複狂打
- 高頻事件要先想 sampling
- 背景 loop 不要無條件每輪都打 log
- 重試時只記關鍵轉折，不要每次都輸出一大包欄位

## 錯誤訊息原則

### 錯誤訊息保持低基數

不要在 error message 中嵌入動態變數（key、ID、路徑、使用者名稱等），否則 APM 工具（Datadog、Sentry、Loki）會將每個不同值視為獨立 error group，導致錯誤無法聚合。

```go
// 不要 — key 嵌入 error string，每個 key 自成一個 error group
return "", fmt.Errorf("redis: 取得 key %q 失敗: %w", key, err)

// 要 — 低基數 error string，key 由呼叫端以 structured field 附加
return "", fmt.Errorf("redis: 取得 key 失敗: %w", err)
```

呼叫端在記錄時以 structured field 提供 key 等上下文：

```go
logger.ErrorCtx(ctx, "redis get failed", "key", key, "err", err)
```

### 生命週期階段日誌：正常流程用 Debug，異常事件用 Info/Warn

階段進入與流程節點日誌使用 `Debug`，只有在發生逾時、錯誤、或確認完成時才用 `Info`/`Warn`：

```go
// Debug — 階段進入，正常流程無需 Info
logger.Debug("shutdown phase", "phase", phaseName)

// Info — 生命週期確認完成
logger.Info("shutdown complete")

// Warn — 異常事件，需要 ops 注意
logger.Warn("drain timeout, remaining connections", "count", remaining)
```

### `errors.Join` 的包裝使用 `%v` 而非 `%w`

`errors.Join` 本身已聚合多個 sub-error 並支援 `errors.Is/As`。再用 `%w` 包裝只會多一層 unwrap 鏈結，而呼叫端通常不會對驗證類 sub-error 做 Is/As 比對。

```go
// 不要 — errors.Join 已有 Is/As 能力，無需多一層 %w 鏈結
return fmt.Errorf("config: 驗證失敗: %w", errors.Join(errs...))

// 要 — %v 保留 joined message 但不增加 unwrap 深度
return fmt.Errorf("config: 驗證失敗: %v", errors.Join(errs...))
```

### 儲存層使用 `samber/oops` 附加 stack trace

底層套件（`pkg/redis`、`pkg/mysql`、`pkg/appcore`）的錯誤包裝已使用 `github.com/samber/oops`，每個 wrapped error 自動攜帶 stack trace。`oops.Wrapf` 與 `fmt.Errorf("... %w")` 行為一致，支援 `errors.Is/As`：

```go
import "github.com/samber/oops"

// oops.Wrapf 等價於 fmt.Errorf("... %w", err) + 自動 stack trace
return oops.Wrapf(err, "redis: 取得 key 失敗")
```

在 APM 中看到底層錯誤（如 `redis: 取得 key 失敗`）時，可直接從 error 的 stack trace 定位到原始呼叫方，無需依賴日誌行號。

### 使用 `oops.Errorf` 產生結構化 panic 錯誤

`RecoverPanic` 已使用 `oops.Errorf` 包裹 panic 值，產生帶 stack trace 的結構化錯誤供程序化檢查：

```go
panicErr := oops.Errorf("recovered panic: %v", r)
logger.Error("panic recovered", "err", panicErr, "msg", msg, "stack", string(buf[:n]))
```

### Panic 日誌在單一呼叫內完成

panic 值與 stack trace 應在同一筆 logger.Error 呼叫中輸出，避免在 APM 中拆成兩筆無法關聯的事件：

```go
// 不要 — 兩次 logger.Error 產生兩筆獨立事件
logger.Error(msg, "panic", r)
stack := buf[:runtime.Stack(buf, false)]
logger.Error("stack", "trace", string(stack))

// 要 — 先取得 stack，再一次性輸出
stack := buf[:runtime.Stack(buf, false)]
logger.Error(msg, "panic", r, "stack", string(stack))
```

## 範例

```go
logger.Info("gate chat service enabled", "gateID", appID)
logger.Warn("redis unavailable, persistent journals disabled", "err", err)

// dispatch 層已自動注入 traceID，handler 直接使用 sock.Context()
ctx, endSpan := tracing.StartSpan(sock.Context(), 0, "handler.name")
defer endSpan()
logger.InfoCtx(ctx, "login request", "account", m.Account)
logger.ErrorCtx(ctx, "login failed: DB error", "account", m.Account, "err", err)
```

## 反例

```go
// 不要
log.Println("login failed", err)
slog.Error("login failed", "err", err)
logger.Info("login", "password", password)
logger.Error("db error", "err", err, "err", err)
```

## 導入原則

- 舊程式碼先維持 `pkg/logger`
- 不要為了「統一」再引入第二套 wrapper
- 若要改欄位名，先改規範，再改實作，再補文件
