# 日誌規範

## 原則

- 專案新程式碼一律使用 [`pkg/logger`](../../pkg/logger/logger.go)
- [`pkg/logger`](../../pkg/logger/logger.go) 底層固定使用 `zerolog`
- Call site 不直接依賴 `log/slog`、`logrus`、`zap`，也不直接匯入 `github.com/rs/zerolog`（含全域 `zerolog/log`）：會繞過 `pkg/logger` 的取樣、非同步緩衝與 loggercheck。depguard 對正式碼擋 `log`、`log/slog` 與 zerolog（測試與 `pkg/logger` 本身除外；測試要擷取 Warn 時用 `logger.CaptureWarnForTest`，第十二輪）
- 第三方套件自帶的內部 logger 也要轉接到 `pkg/logger`（第十二輪 PLIB-M1）：go-sql-driver/mysql 由 `pkg/mysql` 在套件 init 以 `mysql.SetLogger` 安裝 `driverLogger`（必須早於任何 `NewConfig`／`ParseDSN`，晚裝不生效）；OTel 由 `tracing.Init` 一開始以 `otel.SetLogger` 換成 logr／funcr 轉接（冗長度維持 0，只輸出 Error 與 V(0)）。兩者預設都是自建的 `log.New(os.Stderr)`，會輸出純文字並繞過 stdlog 橋接
- 新增日誌欄位前，先確認是否已有既有欄位可重用
- 能不用 log 就不用 log；能少打就少打

## 標準入口

### 初始化

- 服務啟動時，以 `logger.Configure(format, level, service)` 設定輸出格式、層級與服務名稱（由 `startup` 帶入；`service` 非空時每筆日誌自動附上 `service` 欄位）
- `format` 只接受 `text` 或 `json`（空字串視為 `json`）
- `level` 採 `trace` / `debug` / `info` / `warn` / `error`
- `warning` 會正規化成 `warn`
- 時間欄位用 `RFC3339Nano`（含奈秒），同一秒內多筆日誌可正確排序
- `json` 格式的 Warn／Error（含 `WarnCtx`／`ErrorCtx`）會附 `caller`（呼叫端檔案與行號，已跳過 logger 包裝層）；Info／Debug 不取 caller

### 呼叫

- 一般情況用 `logger.Debug/Info/Warn/Error`
- 有 `context.Context` 時，用 `logger.DebugCtx/InfoCtx/WarnCtx/ErrorCtx`：請求路徑上（handler、store、recordmq 消費）已有 ctx 卻用非 Ctx 版，日誌會失去 `gameTraceID`／`trace_id` 而無法串起同一筆請求
- 跨服務請求要先補 `trace_id`，再記 log

## 層級定義

### `Debug`

- 只放除錯細節
- 頻率高的訊息要能接受抽樣
- 不要把 `Debug` 當成正常營運日誌
- 玩家連線的 `connect`／`disconnect` 與 Gate `client version hello` 記 Debug（S2S 連線維持 Info），量改看 `game_connections`、`game_version_hello_total`。Gate 的 `login request`、`logout request`、`logout response to user`、逐連線的 `client version notice` 與 `version grace period over` 也記 Debug（第十一輪；原本部分是 Info），版本政策變更與寬限期掃描後各彙總一行 Info：`client version notices sent after policy change`、`version grace period over, closed sockets`（欄位 `count`）；次數改看 `game_login_total`、`game_logout_total`、`game_version_notice_total`

### `Info`

- 正常流程節點
- 例如服務啟動、連線建立、狀態切換、任務完成

### `Warn`

- 可恢復異常
- 例如 fallback、retry、degrade、timeout、資料缺失但流程可繼續

### `Error`

- 流程失敗
- 例如 DB 失敗、初始化失敗、請求無法完成、不可忽略的 runtime error
- 玩家可觸發的逐筆事件不得記 Error，免得被刷成 Error 告警或洗版：玩家連線的解包失敗記 Warn（S2S 維持 Error），解碼失敗的 Warn 每 10 秒取樣一行並標 `(sampled)`；寫入失敗（`failSend`）分三種：連線已關閉造成的 `net.ErrClosed` 是正常收尾，不記；對端斷線（ECONNRESET、EPIPE 等）降為 Debug `<原因>, peer disconnected`；其餘記 Warn `<原因> (sampled)`（例如 `write error (sampled)`，每 10 秒一行），S2S 連線仍逐筆 Error；訊息 ID 越界、單 IP 連線上限、hello 前送訊息、TCP accept 階段拒絕（`rate_limited`／`at_capacity`）、Chat 房間佇列滿、登入待處理時重送記 Debug，量看對應指標；World 盤面指令 payload 解碼失敗（`board.ErrDecode`）與不認識的玩家（`unknown_player`）取樣記 Warn（第十二輪起 unknown player、worker queue full、decode 三種各有一個取樣器，互不吃額度）。其他 Client 可逐則觸發的 Warn（Central 新帳號密碼／bcrypt busy／沒有可選 World、Gate 登出限流、Lobby 公告同步與服務清單載入失敗）以 `rate.Sometimes` 每 10 秒一筆、訊息加 `(sampled)` 後綴；Chat 歷史寫入／查詢失敗另帶 `suppressed`（上次輸出後略過的筆數）。新增這類日誌時同樣取樣，次數改看指標

## 欄位規範

### 必用欄位

- `err`：錯誤物件一律用這個 key
- `gameTraceID`：跨服務鏈路才加（由 ctx 自動附上）

### 自動欄位

- `service`：由 `logger.Configure` 依服務名稱自動附上，**呼叫端禁止手寫 `"service"` 鍵**（JSON 會出現重複鍵；`internal/archtest` 的 `TestLoggerCallsDoNotRepeatServiceKey` 守門）。連線所屬的服務（`tcpsocket`、`tcpserver`、`s2shandshake` 記的連線擁有者）改用 `owner` 欄位

### 常用欄位

- `accountHash`（`accountrule.LogHash`；只出現在 Lobby admin／gm 的封禁稽核與補踢，以及 Central 啟動時掃描未正規化帳號的 Warn，不記明文帳號；登入、路由、其他稽核類日誌改記 `playerID`／`requestID`）
- `playerID`
- `worldID`
- `gateID`（Lobby discovery 的 `invalid gate load`／`negative gate load` 以前寫 `id`，第十輪起統一為 `gateID`）
- `requestID`
- `addr`
- `key`
- `count`
- `elapsed`（`time.Duration`，輸出為毫秒）
- `threshold`（`time.Duration`）

### 命名規則

- camelCase，與現有 `pkg/logger` 輸出一致（例如 `sessionKey`、`driftMs`、`droppedTotal`；Gate session key 統一用 `sessionKey`，不再用 `session`）
- 同一語意固定同一欄位名；第十輪統一的舊鍵：World persist pool 丟棄任務日誌的 `world` 改 `worldID`、Central `sendDirectError` 的 `code`（Debug）改 `responseCode`。第二十八輪（行為變更：日誌欄位名）再統一：World `data config reloaded` 的 `duration` 改 `elapsed`、`pkg/mysql` 的 `dbname`／`db` 統一為 `dbName`、tools/user gate login／logout 的 `code` 改 `responseCode`。`panicx` 記錄 panic 用的 `"msg"` 鍵是刻意保留（對應 `game_panic_recovered_total{msg}` 標籤），不改
- 不要同時混用 `uid`、`player_id`、`playerID`

## `trace_id`

- `trace_id` 用於串聯 Gate / Central / World 日誌
- 跨服務 request 進入 Gate 後建立
- 只在需要追蹤鏈路時才補
- dispatch 層會自動從 `TraceScopedMessage` 中提取 `traceID` 注入 `sock.Context()`
- handler 中直接使用 `sock.Context()` 即可，無需手動呼叫 `logger.WithTraceID`
- `tracing.StartSpan(ctx, 0, ...)` 會從 ctx 自動讀取 `traceID`
- 需手動注入的情境：背景 goroutine、非訊息入口、建立新 trace 的入口點
- 實際 log 欄位名使用 `gameTraceID`；`trace_id`／`span_id` 是 OTel span 的欄位，兩者不同
- 已知限制：`gameTraceID` 由 `pkg/msg` 生成碼以行程內序號產生，多個 Gate 實例在同一毫秒可能產生相同值（兩個 Gate 各每秒 50 次登入時約每秒撞 2.4 次）；跨實例查詢時要同時以 `service`／`instance`、`requestID` 或時間範圍過濾。修正需改 PJA-Protocol 的產生器，尚未處理
- HTTP 請求沒有 OTel span（正式環境 `otel.exporter` 為空）且 ctx 沒有 traceID 時，`httpx` 的 logging 中介層產生一個關聯 ID 放進請求 ctx（handler 的 `*Ctx` 日誌帶 `gameTraceID`），並寫入回應標頭 `X-Request-ID`，存取日誌與 handler 日誌可用它串起；呼叫端回報問題時可附上這個標頭值
- ctx 已帶同一條 trace 的 span 時，`StartSpan` 以它作為 parent，巢狀 span（例如 `central.login` 內的 `mysql.*`、`redis.call`）會形成呼叫階層；ctx 沒有 span 時才以 traceID 注入 root。HTTP 請求沒有遊戲 traceID（`otelhttp` 已把請求 span 放進 ctx，`httpx` 的關聯 ID 不是 `gameTraceID`）：`StartSpan(ctx, 0, ...)` 讀不到 traceID 時，若 ctx 已有**取樣中**的 span 就在它底下建子 span，Redis／MySQL 子 span 才看得到；ctx 既沒有 traceID 也沒有取樣中的 span 時不建立 span。追蹤沒開（`otel.exporter` 為空，取樣門檻 0）時一律不建立，連 traceID 都不查。
- 日誌等級：登入請求（只記 `requestID`，不含帳號）、連線正常關閉、解碼已關閉、玩家連線斷線造成的讀取失敗（`peer disconnected while reading`：unexpected EOF、讀取逾時、ECONNRESET、EPIPE）等高頻事件使用 Debug（格式錯誤維持 Warn，S2S 維持 Error）；Gate 玩家心跳逾時被踢（次數看 `game_heartbeat_timeout_total`）、HTTP 存取日誌的 429（限流擋下）與 404（掃描器）也是 Debug：次數已計入 `game_http_request_seconds_count`，攻擊流量不再灌爆日誌，其餘 4xx（400、403、405 等未驗證流量）依狀態碼各自每 10 秒取樣一行 Info（帶 `suppressed` 略過筆數，次數看 `game_http_request_seconds_count`），5xx 為 Warn 且同樣每 10 秒一行；401（未授權）降為 Debug；Client 撥號失敗使用 Warn，避免對端長時間不在線時洗版

## 與 metrics 的分工

- log 記單筆事件與上下文
- metrics 記聚合結果與趨勢
- 不要把狀態機轉移規則藏進 log
- 不要把單筆除錯訊息當成監控依據

## 敏感資料

以下內容禁止直接寫入 log：

- 密碼
- token
- session secret
- 完整 bcrypt hash
- DB password
- Redis secret
- 大段 request body
- 大段 response body
- MySQL 伺服器錯誤的訊息文字：唯一鍵衝突等錯誤訊息會帶資料值（如 `Duplicate entry '<帳號>' for key ...`），帳號是個資。記日誌時用 `mysql.RedactedError(err)`，只留 `mysql error <碼> (<SQLSTATE>)`；gorm 失敗日誌（`gorm query failed`）與 Central 登入的 DB 錯誤日誌（`login failed: DB error (sampled)`、`login failed: save user (sampled)`）已套用。回傳值只供記錄、不保留錯誤鏈，判斷邏輯（`IsDataRejection` 等）要對原始錯誤做

需要查問題時，只記可識別最小集合欄位，不記原文。

## 重複與噪音

- 同一個錯誤不要在同一條鏈路重複狂打
- 高頻事件要先想 sampling
- 背景 loop 不要無條件每輪都打 log
- 重試時只記關鍵轉折，不要每次都輸出一大包欄位

## 錯誤訊息原則

### 日誌 message 固定，錯誤值可以帶上下文

分組依據是**日誌 message**，不是錯誤字串：日誌 message 一律用固定的英文字串，玩家 ID、key 等以結構化欄位附加，Loki／APM 才能依 message 聚合。錯誤值本身可以帶操作脈絡（ID、路徑、設定檔名），方便定位；只要避免熱路徑重複記錄的錯誤同時在錯誤字串和欄位重複帶同一個 ID。

```go
// 日誌 message 固定，ID 放欄位
logger.ErrorCtx(ctx, "gamestore flush failed", "playerID", playerID, "err", err)

// 錯誤值可帶 ID（外部來源的字串值用 %q）
return fmt.Errorf("gamestore memory flush player %d: %w", playerID, err)
return fmt.Errorf("read schema file %q: %w", name, err)
```

錯誤字串的寫法（與程式現況一致，revive `error-strings` 檢查首字母與結尾標點）：

- 一律英文（錯誤會層層包裝，混用中文會出現中英混雜的訊息）
- 首字母小寫、結尾不加標點；識別碼、設定鍵、縮寫保留原樣（例如 `S2S`、`SHA`、`max_players`）
- 以所在套件或元件名當前綴（`redis: get key: %w`、`boardconfig: evaluate condition: %w`），不用 `failed to`、`error`、`err` 當包裝前綴，也不重複下層已帶的前綴
- 包裝一律用 `%w`，保留原因，不要換成沒有原因的新錯誤

### 生命週期階段日誌：正常流程用 Debug，異常事件用 Info/Warn

階段進入與流程節點日誌使用 `Debug`，只有在發生逾時、錯誤、或確認完成時才用 `Info`/`Warn`：

```go
// Debug — 階段進入，正常流程無需 Info
logger.Debug("shutdown phase", "phase", phaseName)

// Info — 生命週期確認完成
logger.Info("shutdown complete")

// Warn — 異常事件，需要 ops 注意
logger.Warn("drain timeout, remaining connections", "count", remaining)
```

### `errors.Join` 照常以 `%w` 包裝

`errors.Join` 的結果再包一層前綴時用 `%w`，呼叫端才能以 `errors.Is`／`errors.As` 判斷其中的子錯誤；改用 `%v` 會切斷鏈結。例如任務進度解碼失敗以 `errors.Join(errInvalidInput, err)` 標記為輸入錯誤，呼叫端靠 `errors.Is(err, errInvalidInput)` 改記 Warn 而非 Error。

```go
// 要 — 呼叫端仍能 errors.Is 子錯誤
return fmt.Errorf("config: validate: %w", errors.Join(errs...))
return fmt.Errorf("mission progress: decode progress: %w", errors.Join(errInvalidInput, err))

// 不要 — %v 讓 errors.Is(err, errInvalidInput) 失效
return fmt.Errorf("mission progress: decode progress: %v", errors.Join(errInvalidInput, err))
```

只彙整已帶來源的錯誤、不加前綴時，直接回傳 `errors.Join(...)`（wrapcheck 的 `ignore-sigs` 已放行）。

### 底層套件一律以 `fmt.Errorf` 包裝

`pkg/redis`、`pkg/mysql` 與其他套件相同，以 `fmt.Errorf("...: %w", err)` 包裝錯誤，支援 `errors.Is/As`。專案不使用 `samber/oops`：日誌輸出不會展開它附帶的 stack trace，每次包裝卻都要擷取一次呼叫堆疊，只有成本沒有效益。定位錯誤來源靠錯誤訊息的套件前綴（例如 `redis: get key`；寫法見上方「日誌 message 固定，錯誤值可以帶上下文」）與日誌的 `gameTraceID`／`trace_id`。

```go
return fmt.Errorf("redis: get key: %w", err)
```

### Panic 錯誤

recover 點一律經 `pkg/panicx`：訊息固定為 `panic recovered`，欄位為 `err`（error 型別，內容為 `recovered panic: <panic 值>`，以 `%w: %v` 格式化，`errors.Is` 解不到原 error）、`msg`（呼叫點標籤，常數字串）、`stack`（`debug.Stack()`），同時計入 `game_panic_recovered_total{msg}`。不再有 `panic` 欄位。

唯一例外是 `pkg/tcpsocket/socket_events.go` 的 `tcp handler`：它自寫 Error 日誌 `handler panic`（欄位 `sockID`、`msgID`、`untrusted`、`err`、`stack`）並遞增 `game_panic_recovered_total{msg="tcp handler"}`，原因是這條是每則訊息的熱路徑，要同時帶 socket 識別欄位、清 `dispatchCtx` 並決定關閉玩家連線或只丟棄 S2S 訊息，不走 `panicx` 的通用日誌；新增 recover 點不得比照，一律走 `panicx`。

實際由 `panicx.RecoveredError`／`LogRecovered` 輸出（`.golangci.yml` 的 `loggercheck.rules` 已登記，kv 須成對、key 為字串）：日誌 `err` 欄位為 `recovered panic: <panic 值>`（`%w: %v`，`errors.Is` 解不到原 error）。回傳給呼叫端的錯誤是另一個短字串，`Error()` 為 `recovered panic (<label>)`，保留 `Unwrap` 到 `ErrRecovered`；完整 panic 值只出現在含 stack 的 Error 日誌 `panic recovered`，下游看到 `recovered panic (<label>)` 時搜 `panic recovered` 且 `msg=<label>` 回查；所以下游失敗日誌照常寫 `"err", err` 即可，不會重複整串 panic 值（`panicx.ErrField` 已刪除，改由源頭解決）。處理鏈上有 ctx 時用 `panicx.RunRecoveredCtx(ctx, label, fn)`（`RunRecovered` 的帶 ctx 版），panic 日誌會帶請求／事件的 traceID，可與同一條處理鏈的其他日誌串起；Record consumer、GM 發放 worker、outbox relay 已改用它。注意 World outbox 的 Record 事件（`RecordOutboxEvent`）沒有 TraceID／GateID／RequestID 欄位，`PublishOutboxRecord` 不設 Envelope.TraceID，發布與消費端也不建 span，所以 relay 的 panic 日誌帶不到 trace：這是已知限制（R28 O-L2，是否加欄位與 migration 待決策）。

### Panic 日誌在單一呼叫內完成

panic 值與 stack trace 應在同一筆日誌輸出，避免在 APM 中拆成兩筆無法關聯的事件；日誌 message 必須固定（低基數），也不可自己 `recover()` 後直接呼叫 logger，否則不會計入指標、欄位也對不上告警與查詢：

```go
// 不要 — 兩次 logger.Error 產生兩筆獨立事件，message 還是變數
logger.Error(msg, "panic", r)
logger.Error("stack", "trace", string(debug.Stack()))

// 不要 — 直接 recover() 後自己記，沒計入 game_panic_recovered_total
defer func() { if r := recover(); r != nil { logger.Error("worker panic", "panic", r) } }()

// 要 — 統一經 panicx（固定 message「panic recovered」，欄位 msg／err／stack）
defer func() {
	if r := recover(); r != nil {
		panicx.LogRecovered(ctx, "handler.xxx", r)
	}
}()
// 或 panicx.RecoveredError（要回傳錯誤時）、panicx.RunRecoveredCtx（包住整個函式）
```

## 範例

```go
logger.Info("gate chat service enabled", "gateID", appID)
logger.Warn("redis unavailable, persistent journals disabled", "err", err)

// dispatch 層已自動注入 traceID，handler 直接使用 sock.Context()
ctx, endSpan := tracing.StartSpan(sock.Context(), 0, "handler.name")
defer endSpan()
logger.DebugCtx(ctx, "login request", "requestID", m.RequestID)
logger.ErrorCtx(ctx, "login failed: DB error", "requestID", m.RequestID, "err", err)
```

## 導入原則

- 舊程式碼先維持 `pkg/logger`
- 不要為了「統一」再引入第二套 wrapper
- 若要改欄位名，先改規範，再改實作，再補文件
