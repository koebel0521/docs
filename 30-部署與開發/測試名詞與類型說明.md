# 測試名詞與類型說明

本專案用到的測試類型、名詞與輔助工具的白話說明，以及每一類在本專案的位置、執行方式與守的風險。規範細節（flag、並行、斷言語言）在[開發規則](開發規則.md#測試規範)，整合測試的場景清單在[整合測試地圖](../10-核心流程/整合測試地圖.md)，壓測見[壓測手冊](壓測手冊.md)。

## 一眼看懂：該寫哪一種測試

```
要驗證的是什麼？
│
├─ 一個函式、一條規則的結果（骰子、抽獎、扣款、編碼）
│     └─ 單元測試（最快、最便宜，優先選它）
│
├─ 同一個東西的「每一種輸入組合」或「亂七八糟的輸入」
│     ├─ 已知的邊界與固定輸入 ─────────── 表格測試／邊界測試
│     ├─ 任意位元組都不能 panic ────────── Fuzz
│     └─ 隨機操作序列後狀態仍合法 ───────── 隨機序列測試（不變量）
│
├─ 多個服務串起來才會出錯（登入、擲骰經過 Gate→World→資料庫）
│     └─ 整合測試／端到端測試（較慢，只寫核心流程與跨服務風險）
│
├─ 依賴（MySQL、RabbitMQ、Redis）斷線或服務當機後能不能恢復
│     └─ 故障注入測試／崩潰恢復測試
│
├─ 資料格式、協定位元組、設定表引用不能被悄悄改掉
│     └─ 契約測試（golden）／懸空引用注入測試
│
└─ 改動後效能或經濟數字有沒有變
      ├─ 速度與配置次數 ─────────────────── Benchmark／退化守門
      ├─ 能撐多少人 ─────────────────────── 壓力測試（見壓測手冊）
      └─ 玩家金幣產出有沒有漂移 ──────────── 經濟漂移偵測
```

寫之前先問自己：「把對應的正式碼改壞一處，這個測試會失敗嗎？」不會就不要寫（見[工作規範](../00-導讀/工作規範.md#測試)）。

## 一、測試類型

| 名詞 | 白話 | 本專案的位置與執行 |
|---|---|---|
| 單元測試（Unit） | 只測一個函式或一條規則，不碰網路與資料庫，毫秒級 | 各套件的 `*_test.go`；`make test`，CI `unit` job |
| 整合測試（Integration） | 把幾個真實元件串起來測，會用到真實的 MySQL、Redis、RabbitMQ | 帶 `//go:build integration` 的檔案；`make ci-it`、`make ci-it-pkg` |
| 端到端測試（E2E） | 以真實子行程啟動 Central、World、Gate 等服務，從玩家連線一路走到資料庫 | `integration/`；CI `e2e` job。本專案的 E2E 不含瀏覽器或遊戲 Client（PJA-Client 不在本倉庫範圍） |
| 冒煙測試（Smoke） | 先花十幾秒確認「東西起得來、核心路徑通」，失敗就不必跑後面幾十分鐘的測試 | `TestSmoke_*`；CI 的 `e2e` job 最先單獨跑它 |
| 回歸測試（Regression） | 修過的 bug 加一個測試，確保不會再壞回去 | 不另成一類，直接寫在對應套件，測試註解寫明原因 |
| 契約測試（Contract） | 把「雙方約好的格式」鎖死，任何一方偷偷改就失敗 | 見下方「Golden」；協定位元組、持久化 JSON 鍵、Redis 鍵格式 |
| 壓力測試（Stress／Load） | 用大量虛擬玩家測極限與穩定性 | 工具在本機 `tools/private/`（不進版控）；方法見[壓測手冊](壓測手冊.md)，結果見[容量與壓測基準](../20-排障與監控/容量與壓測基準.md) |
| 浸泡測試（Soak） | 中等負載長時間跑，抓記憶體或 goroutine 洩漏 | `soakload` 工具（私有） |
| 基準測試（Benchmark） | 量一段程式碼的耗時與記憶體配置 | `func Benchmark*`；`make bench`；清單在 `bench/packages.txt` |
| 模糊測試（Fuzz） | 讓 Go 自動產生大量隨機輸入餵函式，看會不會 panic | `func Fuzz*`；CI `fuzz` job（排程或手動） |
| 故障注入（Fault injection） | 故意讓依賴斷線再恢復，看服務會不會崩、資料會不會丟 | `FaultProxy`、`TestRecordFault_*` |
| 崩潰恢復（Crash recovery） | 把服務用 `SIGKILL` 直接殺掉再重啟，看狀態能不能恢復 | `TestCrashRecovery_*` |
| 滾動重啟（Rolling restart） | 發版時逐個關閉再啟動服務：優雅關閉要排空連線、不遺失已確認的結算，玩家改連其他節點後狀態一致 | `TestRollingRestart_*` |
| 網路劣化測試 | 用代理注入高延遲、連線卡住（半開）、送出後斷線，驗證行動網路下指令的順序與「恰好一次」 | `TestNetwork_*` |
| 洩漏回歸測試 | 玩家大量進出後比對 goroutine 數是否回到起跑線，抓執行期間緩慢累積的洩漏（goleak 只在行程結束時檢查） | `TestLeakRegression_*` |
| 協定層模糊測試 | 對真實連線送格式正確但內容亂的資料，驗證服務不當機、不 panic、不影響其他玩家（單元層的 Fuzz 只測解碼函式） | `TestProtocolFuzz_*` |
| 變異測試（Mutation） | 把正式碼故意改壞一處，確認測試會失敗；測「測試」本身 | 手動做：每個新測試提交前都至少改壞一次驗證，結果寫在 commit 訊息 |
| 結構性測試 | 檢查程式碼結構本身，不測行為 | `TestTestPackagesHaveGoroutineLeakDetection`、`internal/archtest` |
| 靜態檢查 | 不執行程式就找問題 | `make lint`（golangci-lint）、`govulncheck`、`trivy` |

## 二、本專案專有的測試手法

| 名詞 | 白話 | 例子 |
|---|---|---|
| Golden（金標準資料） | 事先存好的「正確答案」，之後每次用程式產生結果與它逐位元組比對 | `pkg/msg` 的 `s2sWireVectors`、`csharpCodecVectors`、C# 客戶端產生的向量 |
| 完整性守門 | 規則「每一個都要有」：新增項目卻漏補時直接失敗 | `TestEveryS2SMessageHasWireVector`：訊息表的每一則 S2S 訊息都要有 golden |
| 不變量（Invariant） | 不管怎麼操作都必須成立的條件 | 道具數量不為負、棋子在盤面上、拒絕的指令不改變玩家狀態 |
| 隨機序列測試（Stateful） | 用固定種子隨機混合多種操作，每一步後檢查不變量 | `TestPlayerStateful_RandomCommandSequence` |
| 固定種子（Seed） | 讓「隨機」可重現：同一個種子永遠得到同樣的序列，失敗時能重播 | 失敗訊息會印出種子與步驟編號 |
| 冪等（Idempotent） | 同一個請求重送多次，結果和送一次相同 | 擲骰以 `RequestID` 去重，重送回放原結果 |
| 回放（Replay） | 重送時伺服器不重新計算，直接回傳第一次的結果 | request journal；回放的位元組必須複製後再交給呼叫端 |
| 卡方檢定（Chi-square） | 用統計判斷「實際次數」像不像「理論機率」；p 值越小越不像 | `TestSecureDiceIsUniformAndIndependent`，顯著水準 1e-9 |
| 漂移偵測（Drift） | 把當下的數字釘成基準，之後偏離超過容忍值就失敗，逼人有意識地更新 | `TestEconomyStaysNearBaseline` |
| 懸空引用注入 | 對真實配表故意塞一個不存在的 ID，確認載入時就被拒絕 | `TestLoadRejectsDanglingReferencesInShippedTables` |
| 假時鐘（Fake clock） | 測試自己控制「現在幾點」，不用真的等 | `pkg/testutil/clock.go`；遊戲時間可注入 |
| 金標準重播（Golden playthrough） | 固定骰子與事件種子玩 300 回合，逐回合狀態存成檔案；任何規則或配表改變都會讓檔案不同並指出第一個不同的回合，有意改規則時用 `-update-golden` 重寫；比對前會把檔案的 CRLF 正規化成 LF，所以 Windows checkout（`core.autocrlf`）或 worktree 換行不同不會造成偽失敗 | `internal/game/simulation/testdata/golden_playthrough.txt` |
| 可達性與軟鎖檢查 | 找出玩家永遠碰不到的內容：沒被引用的抽獎群組、永遠取不到的貨幣、伺服器不發事件的任務指標；檢查邏輯另有自我驗證測試 | `TestShippedConfigHasNoUnreachableContent` |
| 敏感度分析 | 把一組設定數值上下調 10%，看經濟產出跟著變多少：抓懸崖（調一點變幾倍）與失效旋鈕（調了沒反應） | `TestEconomySensitivityToConfigKnobs` |
| 日誌機密掃描 | debug 日誌等級下走完整流程，掃描全部服務日誌確認密碼與基礎設施機密不出現 | `TestLogs_NeverContainSecrets` |
| 退化守門（Regression gate） | 在 MR 比較改動前後的效能，退化超過門檻就擋下 | `scripts/ci-bench-gate.sh`、CI `bench-gate` job |
| 基準線（Baseline） | 當作比較對象的「已知良好」數字或檔案 | `bench/benchmark_baseline.txt`、經濟漂移測試的常數 |

## 三、測試替身與輔助元件

| 名詞 | 白話 | 位置 |
|---|---|---|
| Stub／Fake | 假的依賴，回傳預先設定的結果，讓被測程式不必接真實依賴 | `pkg/testutil/fakes`、`FakeCentral`、`FakeChat` |
| Mock | 會記錄「被怎麼呼叫」並驗證的假依賴；本專案偏好簡單的 Fake，少用 Mock | — |
| `testenv` | 整合測試的環境工具：啟動真實子行程、保留埠、讀寫訊息、等待就緒 | `integration/testenv/` |
| 真實叢集 | 真實 Central＋World＋Gate（＋Chat）一起啟動 | `testenv.StartRealCentralCluster` |
| `FaultProxy` | 夾在服務與依賴之間的 TCP 代理；`Cut()` 切斷並拒絕新連線，`Restore()` 恢復。不需要 docker 指令，本機與 CI 都能用 | `integration/testenv/faultproxy.go` |
| `RestartWorldHard` | 用 `SIGKILL` 殺掉 World 再用同一份設定重啟，模擬當機 | `RealCentralCluster` |
| `DebugPorts` | 真實叢集各服務的診斷埠（`/health`、`/ready`、`/metrics`），每個服務各自一個空閒埠 | `RealCentralCluster.DebugPorts` |
| `MultiCluster` | 多 Gate × 多 World 的全真實叢集（每個 Gate 的 `dial.world` 列出全部 World、每個 World 有獨立 `spill_dir`），可單獨殺掉、優雅關閉或重啟任一個 Gate 或 World | `testenv.StartMultiCluster` |
| `FaultProxy` 的延遲與卡住模式 | `SetLatency` 讓每個方向每塊資料多等一段時間，`SetStalled` 讓連線保持開著但暫停轉送；玩家連線經代理連 Gate 就能測網路劣化 | `integration/testenv/faultproxy.go` |
| `TestMain` + goleak | 每個測試目錄結束時檢查有沒有洩漏的 goroutine | 每個有測試檔的目錄都要有 |
| `require`／`assert` | testify 的斷言：`require` 失敗就停止，`assert` 失敗繼續；背景 goroutine 內不能用 `require` | 見[開發規則](開發規則.md#通則) |
| `Eventually` | 反覆檢查條件直到成立或逾時，取代固定 `sleep` | testify |
| `t.Parallel()` | 讓測試彼此並行；會改全域狀態的測試要註明原因維持序列 | 見[開發規則](開發規則.md#單元測試) |
| 建置標記（build tag） | 檔案頂端 `//go:build integration`，沒帶 `-tags=integration` 就不會被編譯 | 整合測試 |

## 四、測試與執行的名詞

| 名詞 | 白話 |
|---|---|
| 競爭偵測（Race detector） | `go test -race`：執行時偵測兩個 goroutine 同時讀寫同一塊記憶體 |
| `-shuffle=on` | 隨機化測試順序，抓出測試之間的隱性相依 |
| `-count=1` | 不用測試快取，每次真的重跑；整合測試必加 |
| Flaky（偶發失敗） | 同一份程式有時過有時不過。處理原則：先抓到失敗現場找根因，不要加重試掩蓋（例：`RapidLoginDisconnect` 的每 IP 接入限流） |
| 覆蓋率（Coverage） | 測試跑過多少比例的程式行；本專案看改動行的 patch coverage ≥ 60% |
| 試跑（Dry run）／冒煙環境 | 起一套拋棄式依賴跑測試，用完移除：`scripts/integration-deps-up.sh`／`down` |
| 拋棄式依賴 | 專為整合測試起的 MySQL、Redis、RabbitMQ 容器，埠號與開發環境錯開，不污染開發資料 |
| 寫回間隔（write-behind） | World 把玩家資料先放記憶體、約每秒批次寫進 MySQL；崩潰最多遺失約 1 秒，崩潰恢復測試依此設計 |
| 限流與冷卻 | 伺服器刻意的保護：Gate 每 IP 接入、每連線盤面指令、登入與登出冷卻。測試遇到 `RateLimited`（code 8）或 `ServiceUnavailable`（code 9）要重試，不是 bug |

## 六、判讀失敗的常見訊息

| 看到 | 多半代表 |
|---|---|
| 登入回應 code 9（`ServiceUnavailable`） | 叢集剛啟動，World 還沒向 Central 登錄；稍後重試即可 |
| 登入或登出回應 code 8（`RateLimited`） | 同帳號短時間內重登或重複登出的冷卻；稍後重試 |
| 盤面指令送出後完全沒有回覆 | 超過 Gate 每連線盤面指令限流（每秒 10、burst 20）被丟棄，或玩家未登入 |
| 第 21 條連線被關閉 | Gate 每來源 IP 接入限流（每秒 10、burst 20）；日誌只在 Debug（`pkg/tcpserver/server_accept.go`），預設看不到，改看 `tcp_rejected_connections_total{reason="rate_limited"}`；只在有意壓測的測試放寬 |
| `golangci-lint` 在 commit 時失敗且「files were modified」 | hook 自動修了檔案（例如移除多餘的 `//nolint`）；`git add` 後重新 commit |
| `docker ps` 逾時 | Docker Desktop 的 daemon 卡住；重啟 Docker Desktop |

## 七、目前沒有的測試類型

| 類型 | 原因與替代 |
|---|---|
| 瀏覽器或遊戲 Client 的 UI 測試 | PJA-Client 不在本倉庫範圍 |
| 混沌工程（隨機殺 Pod、網路延遲注入） | 以 `FaultProxy` 的受控中斷與崩潰恢復測試涵蓋最重要的幾個場景；規模擴大前不需要 |
