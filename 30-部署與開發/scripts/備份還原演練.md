# `scripts/backup-restore-drill.sh`

## 作用
在臨時容器上演練 MySQL / Redis 備份與還原。

## 目的
先驗證備份還原流程，再碰正式環境。

## 流程
1. 以拋棄式 compose 專案（專案名稱含時間戳，不開埠，與任何既有堆疊隔離）起臨時 MySQL / Redis 容器與 volume；env 檔刻意帶含括號未加引號的 `MYSQL_DSN`，與 `.env.prod` 格式一致。
2. 寫入測試資料（MySQL 一筆 `backup_drill`、Redis 一個 key）。Redis 的備份由正式腳本自己 `BGSAVE`，演練不另外 `SAVE`。
3. 呼叫正式的 `docker-backup-mysql.sh`、`docker-backup-redis.sh` 產生備份。
4. 弄壞資料，再呼叫正式的 `docker-restore-mysql.sh`、`docker-restore-redis.sh` 還原（在同一組 volume 上），驗證回來的是備份內容。

演練實際呼叫正式備份還原腳本，所以正式腳本壞掉（例如讀 env 檔出錯）時，演練會跟著失敗。收到 INT／TERM 時清理後以 130／143 結束（第十一輪；原本 trap 不 exit，會對已拆掉的堆疊空轉重試約 2 分鐘再以 1 結束）。在 Windows Git Bash 執行會自動關閉路徑轉換（`MSYS_NO_PATHCONV=1`）。

CI 的 `backup-restore-drill` job 設 `interruptible: false`，不會被同分支新 pipeline 自動取消；`after_script` 另對 `docker compose ls --filter name=drill-` 列出的專案逐一 `down -v`，腳本被 SIGKILL 時也清掉殘留容器與 volume（第十二輪 CI-L4）。

## 主要參數
- 透過環境變數控制：`RUN_DIR`（相對 repo 根目錄的路徑，預設 `.run/backup-restore-drill/<時間>`）、`MYSQL_IMAGE`、`REDIS_IMAGE`、`DRILL_KEEP`（設 `1` 則失敗後保留堆疊供檢查，用完自行 `compose down -v`）
