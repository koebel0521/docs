# 效能嘗試紀錄

> 本文為歷史紀錄：其中的檔案路徑與套件（例如已移除的 `pkg/packet`）是撰寫當時的狀態，現況以程式碼為準。

記錄「試過但不採用」的效能優化，避免重複嘗試。採用的優化看各 `perf:` commit；暫緩的項目見 [已知效能待辦](已知效能待辦.md)。

判準：輸出逐位元相同，且耗時改善 ≥ 20% 或分配次數明顯下降，且既有測試全過；任一條不成立就還原，只留這份紀錄。

環境（以下各筆相同，不同時另註）：AMD Ryzen 5 9600X 6-Core、Windows 11、Go 1.27.2、`GOMAXPROCS` 預設（12）。

## 2026-10-21（第十三輪 perf 審查：P-L1、P-L3 採用，P-L2 放棄）

- **P-L1 採用**（`3d4025588`）：擲骰、升級 journal 每次都是新 requestID，`Load` 必 miss，miss 卻走兩層 `fmt.Errorf` 包裝與對這兩種 journal 沒作用的 singleflight。改成 `redis.ErrNil` 直接回哨兵、新增 `WithoutCoalescing` 讓 World 的 roll／upgrade journal 跳過 singleflight（同一玩家由同一個盤面工作者依序呼叫，不會並行 `Load` 同一鍵；Central 以帳號為 scope 的登入 journal 可能同帳號併發，維持合併）。只宣稱 allocs/op 改善：`LoadMiss/bare` 約 -26%、`LoadMissParallel/coalesced` 約 -43%，其餘列雜訊大。
- **P-L3 採用**（`030631b2b`）：戰鬥快照背景重建每則盤面指令都排一次，卻每次整份載入盤面（取玩家鎖、複製、建 map、排序）與整個背包只為找一顆子彈。改成不載入盤面、背包走新增的 `Memory.LoadItemQuantity`（一次 `readPlayer` 只讀一個道具）：`LoadItems` 約 1.2 µs／2384 B／4 allocs → `LoadItemQuantity` 約 130 ns／384 B／2 allocs，每則指令的背景重建取玩家鎖由 3 次減為 2 次。
- **P-L2 放棄**：每個分片使用子 context 的做法量測不支持（沒有達到判準的改善），不採用。

## 2026-10-13

### `normalizeBoardState` 少量道路星星改線性比對重複格子

- 熱點：`cmd/world/internal/store/gamestore/board_normalize.go`，每次存盤面（擲骰）都為檢查重複格子建一張 `seenSpaces` map。
- 做法：星星數 ≤ 12 時，與前面已處理的項目逐一比對，不建 map；超過才建 map；錯誤訊息與檢查順序不變。
- commit 基準：`10b2aa947`（develop）。
- 對決 benchmark（0、3、8、12、30、60 項與含重複共 7 組輪替）：
  - 舊（map）：約 690–730 ns/op、3 allocs/op
  - 新（混合）：約 665–675 ns/op、2 allocs/op
- 不採用原因：耗時只改善約 4%，平均配置 3 → 2，未達 20%；30、60 項的案例走 map 路徑，整體被它們主導。
- 何時值得重試：盤面道路格大幅減少（多數玩家星星 ≤ 12 筆）且量測顯示此函式占擲骰成本明顯比例時；或與 `normalizedBoard`、`boardState` 的複製一併整併成一次配置。

### `requestjournalredis.redisKey` 改用 `strconv.AppendInt` 組 key

- 熱點：`pkg/requestjournalredis/redis.go` 的 `redisKey`，每次請求日誌讀寫都組一次 Redis key。
- 做法：預留容量的位元組緩衝，依序 append 前綴、scope、請求編號，最後轉字串（輸出逐位元相同，key 格式有測試鎖住）。
- commit 基準：`6d87317ac`（develop）。
- 對決 benchmark（3 種前綴 × 4 組玩家／請求編號輪替，int64 與字串 scope 各一）：
  - 舊（字串串接）：約 43–56 ns/op、67 B/op、int64 為 2 allocs、字串為 1 alloc
  - 新（append）：約 51–57 ns/op、132–136 B/op、2 allocs
- 不採用原因：反而慢約 20%、多配置一次；編譯器對固定段數的字串串接已一次配好，`FormatInt` 小數字還走查表不配置。
- 何時值得重試：key 段數明顯增加（目前固定 3 段），或呼叫端能傳入可重用的緩衝直接寫入 Redis 命令，不再轉成字串時。

## 2026-10-13（續：需要 MySQL 的項目）

環境：MySQL 8.4（Docker 拋棄式容器，Windows Docker Desktop）、同一台 Ryzen 5 9600X、Go 1.27.2。

### 道路星星寫回：用戶端計時沒變快，但後來仍採用

- 第一次只看用戶端計時：10 格 8.0 → 7.7ms、40 格 9.0 → 8.2ms（−4%～−9%），當時判定收益不足。
- 之後改看 MySQL 自己的列異動計數（`Innodb_rows_*`，200 次寫回、40 格、每次只變 1 格）：舊 刪除 7960＋新增 8001 列；新 刪除 0＋新增 41＋更新 464 列（−97%）。交易時間被提交刷寫主導，所以計時看不出來，但重做日誌與二進位日誌的量大幅下降，因此採用。
- 教訓：資料庫寫入的優化不能只看用戶端耗時，要同時看伺服器端的列異動與日誌量。

### `pkg/packet` 的 `Append`／`Decode` 改泛型，讓 `ByteBuf` 留在堆疊

- 熱點：`pkg/packet/generated.go`，手寫訊息型別（45 個）編碼與解碼各多一次 `luban.ByteBuf` 配置（48 位元組）。
- 做法：把 `Append`／`Decode` 從介面參數改成泛型（`[T any, P interface{ *T; Serialize(*luban.ByteBuf) }]`），函式內用堆疊上的 `ByteBuf` 並呼叫 `ReplaceForAppend`／`Replace`，期望編譯器對具體型別直接呼叫。全專案編譯通過，呼叫端不必改。
- commit 基準：`fc838d203`（develop）。
- 對決 benchmark（`BoardProtocolRollDiceCommand`，5 組請求編號輪替，輸出逐位元相同）：
  - 編碼：舊 約 17.5ns、1 alloc（48B）；新 約 17ns、1 alloc（48B）
  - 解碼：舊 約 15.8ns、1 alloc（48B）；新 約 16ns、1 alloc（48B）
- 不採用原因：沒有改善。Go 的泛型以形狀分組並經字典呼叫方法，編譯器看不出具體型別，`&buf` 仍逃逸到堆積。
- 何時值得重試：改成每個訊息型別直接呼叫自己的具體 `Serialize`（如 `forward_to_world.go` 與先前熱路徑訊息的做法），或由 PJA-Protocol 生成器直接產出這種包裝；後者要與該專案負責人協調。每次省約 17ns 與 1 次配置，只在極高訊息量時才有感。

### Lua 腳本改 `EVALSHA`

- 熱點：`pkg/redis/redis_script.go` 的 `Eval`／`EvalInt`，每次送完整腳本；週期性呼叫者有 gm grant 佇列（每秒）與 lobby admin。
- 做法：多 key 腳本改用 `rueidis.NewLuaScript(...).Exec`（EVALSHA）。
- 環境：Redis 7（Docker，經 Windows 埠映射，單次往返約 0.5ms）。
- 對決 benchmark（`moveDueRetriesScript` 同型的 2 key 腳本，各 3000 次，四輪）：舊 EVAL 約 492–507µs/次；新 EVALSHA 約 495–501µs/次，差異在誤差內。
- 不採用原因：時間幾乎全在網路往返，腳本只有幾百位元組，傳送與編譯快取都不是瓶頸。
- 何時值得重試：腳本大到數十 KB，或呼叫頻率高到每秒數千次、頻寬成為瓶頸時。

- 後續：只對每次擲骰必經的五組手寫訊息（擲骰、使用道具、升級建築、商店結算、載入玩家）改成直接呼叫具體型別的 `Serialize`／`Deserialize`，擲骰指令解碼約 15 → 4ns、結果編碼約 72 → 60ns，皆 1 → 0 次配置。其餘約 40 種訊息頻率低，不改；產生檔（如 `change_set_event.go`）不手改。
- 最終解法：在 `pkg/packet` 內以 `sync.Pool` 重用 `ByteBuf`（commit `264b3dcd6`），所有呼叫點一次受益。編碼約 17 → 11.5ns、解碼約 16 → 11ns，並行編碼約 10.7 → 2.6ns，皆 1 → 0 次配置。為什麼「每次都會逃逸」：逃逸是編譯期的靜態判斷，與資料無關；`Append`／`Decode` 內聯成本 108 超過預算 80，編譯器看不到具體型別，只能假設介面方法會留住 `ByteBuf`。
- 根治（commit `27f826b05`，PJA-Protocol `662c0f3`）：產生器為每個結構輸出具體型別的 `AppendTo`／`DecodeFrom`／`UnpackFrom`（`ByteBuf` 在堆疊上、直接呼叫具體型別），gomsg 包裝與所有手寫訊息都改用，`pkg/packet` 與物件池一併刪除。小訊息解碼約 15 → 4ns、編碼 0 配置；大型巢狀訊息（擲骰結果）編碼約 183 → 167ns，因為成本主要在內容。

### 擲骰略過 `requestjournalredis` 的 Redis 讀取（未實作）

- 熱點：每次擲骰，即使是新的 requestID，也先 `GET` 一次（miss）再 `SET` 回應；本專案環境單次往返約 0.5ms，是一次擲骰裡最大的固定成本。
- 想法：本機記住每位玩家看過的最大 requestID，更大的 ID 視為新請求而略過 `GET`。
- 為什麼沒做：略過 `GET` 的前提是「這位玩家所有已處理的請求本節點都看過」。玩家換 World（故障轉移、重新分配）後，舊節點已處理並寫入 Redis 的較大 requestID 若被重送，本節點會當成新請求，**重複擲骰並重複扣骰子**。要成立必須由 Client／協議保證 requestID 單調遞增且換節點時帶回最大已處理值；PJA-Client 不在本專案範圍，無法驗證。
- 何時值得重試：Client 負責人確認 requestID 單調遞增，並同意換節點時由伺服器端交接該玩家的最大 requestID（例如寫在玩家主資料）後。
- 看代碼確認的風險（2026-10-13）：
  - journal 的 Redis key 前綴用的是 World ID（`rediskeys.RequestJournal("world", worldLabel, ...)`），不是行程識別；專案內沒有任何機制保證同一個 World ID 同時只有一個行程（Central 登錄表沒有拒絕重複 ID 的檢查），換行程或滾動更新時兩個行程可能共用同一組 key。
  - 「本機快取沒看過就代表 Redis 也沒有」只有在單一寫入者且行程已運作超過 `ReplayTTL`（2 分鐘）、期間沒有因容量（4096 筆）淘汰時才成立，這幾項都是營運假設，代碼無法證明。
  - `PJA-Docs` 與協議文件都沒有規定 `requestId` 必須單調遞增，只說「對應 Client 的請求」。
  - 結論：沒有風險可以用代碼排除，所以維持每次先 `GET`；損失是每次擲骰多一次約 0.5ms 的 Redis 往返。

### 擲骰結果 `Pack()` 預留 512 位元組容量

- 熱點：`pkg/msg/board/roll_dice.go` 的 `RollDiceResultEvent.Pack()`，從容量 0 開始編碼，`luban.ByteBuf` 依 16、32、64…倍增，擲骰整條 handler 剖析中 `EnsureWrite` 占配置位元組約 7.5%。

### 設計取捨

- 批次與並行都保留舊路徑當退路：消費端整批失敗就退回逐筆（重試、死信、`ErrPermanent` 語意不變）；outbox 整批標記失敗就退回逐筆標記；發送端不支援 `Begin` 時沿用逐筆 `Publish`。
- outbox 並行發布後再整批標記：標記前行程中斷只會讓該批在租約到期後重送，Record 以 `event_id` 去重，不會重複落地。
- 事件在 channel 上的順序不變：發送端依序 `Begin`、只讓「等確認」並行；真 RabbitMQ 整合測試確認 500 筆順序與數量一致。

### 量測後沒有熱點的路徑

- Gate：`FindSessionByKey` 等查詢只在登入時呼叫（約 48ns、1 次配置）；盤面指令轉發與回應已是池化加交換緩衝。
- Chat：每則訊息一句 INSERT 加房間序列佇列，頻率低；歷史讀取多一次 `slices.Clone` 不構成熱點。
- Central：路由快取寫入已是單一 pipeline；登入流程的 Redis 往返來自帳號鎖與 journal，屬設計，不是重複工作。
- World 登入載入快照：同一交易內 13 句查詢，要維持一致性快照，無法拆成並行連線；合併成少數語句需要改查詢結構，風險大於收益。
- World 寫回：已用 `flushConcurrency` 並行，只處理有異動的玩家。
- 純函式 `Roll`：約 413ns，占整條擲骰 handler 約 17%，即使再省 20% 也只改善整體 3%。
- Lobby `/gates`：每次請求複製加編碼約數 µs，遠小於 HTTP 本身的成本。
- outbox 發布前把 payload 解碼成 `any` 再編碼：CPU 成本遠小於一次 broker 確認往返，且改成原樣轉送會讓 JSON 鍵順序不同，不值得。（後續已改為 `json.Valid` 驗證後以 `json.RawMessage` 原樣發布，commit `774d01128`。）
- 頻道廣播每則配置一份成員切片：廣播成本主要在逐一送出，不到 20%。

## 2026-10-13（續：戰鬥快照背景更新）

- 熱點：`cmd/world/internal/services/combat_refresher.go`。每個會改變盤面或背包的指令（含每次擲骰）之後，單一背景 goroutine 逐位玩家做：讀盤面、讀背包、MySQL 單列 upsert、Redis `SADD`，每位約 4ms，超過每秒約 250 位更新就會落後。
- 做法：同一輪排入的玩家合併，`Snapshots.SaveMany`（`cmd/world/internal/store/combatstore`）單句 INSERT 加固定次數的 `SADD`／`SREM`（每句最多 200 位）；快照計算與寫入拆開，LoadPlayer 路徑不變。
- 量測（MySQL 8.4、Redis 7，50 位玩家）：逐位約 210ms → 批次約 6.4ms（−97%），MySQL 寫入語句 50 → 1。commit `352a16307`。
- 沒做的相關想法：內容沒變就跳過發布。玩家持有量達攜帶上限時內容不變，但 Redis 候選集合遺失（failover）後，目前每次指令會自動補回，跳過會讓補回延遲到內容變動或重啟；屬營運假設，不做。

### 再查一輪後沒有熱點的路徑

- GM 發放佇列：每筆約 3 次 Redis 往返（約每秒 600 筆），大量補償是低頻管理操作，改批次要改 ack 語意。
- 擲骰 journal：每次擲骰一次 `GET` 加同步 `SET`，是「回覆前已持久化」的設計；`GET` 不能略過（見前述）。
- 戰鬥場次建立與結算：每場數句交易，頻率低。
- 世界輪詢金幣調整：每秒一句查詢。
- Central 登出：已是整批 pipeline。

## 2026-10-13（續：系統級剖析，Gate → World → 真 MySQL／Redis／RabbitMQ）

方法：用拋棄式容器（MySQL 8.4、Redis 7.4、RabbitMQ 3.13）起 Central、Record、World、Gate，以私有壓測工具（`tools/private/rollload`，不進版控）讓玩家登入後連續擲骰並自動略過商店；開 MySQL general log 與 World pprof 找熱點。結果：World 在 300 位玩家時 CPU 只用約 0.4 核，瓶頸不在 CPU，而在資料庫往返次數與鎖衝突。

| 熱點 | 舊 → 新 | commit |
|---|---|---|
| 效果來源寫回先 DELETE 空範圍再 INSERT，新玩家併發互相死結 | 32 位新玩家同時第一次寫回約 220～270ms、每輪約 37 次死結 → 約 36ms、0 次 | `088dc1485` |

### 設計取捨

- 寫回改 READ COMMITTED：寫回只動自己玩家鍵值的列，沒有讀後寫的範圍不變量；MySQL 8 預設 binlog 格式為 ROW，不受影響。只套用在 `SavePlayerChanges`，其他交易（領獎、商店、盤面升級等會先讀再寫）維持 REPEATABLE READ。
- 任務事件預取結果只放在該次事件分派的 `ctx`，不跨請求保存；否則重送同一事件時可能讀到過期的「查無」而重複累計進度。

### 量測後沒有熱點的路徑

- 擲骰的 Redis 往返：每次只有 1 次 `GET requestjournal`（見前述，不能略過）。
- `DELETE FROM player_board_road_star ... NOT IN` 偶爾 200ms 以上：每輪只有幾句、都在多位玩家同時提交時出現，像是容器磁碟 fsync 停頓，不是這句 SQL 本身；`EXPLAIN` 走主鍵範圍、約 20 列。

### 4. 依賴凍結時的降級行為（`docker pause`）

`soakload` 150～300 位玩家每秒擲骰，凍結依賴 8 秒（模擬封包被丟、主從切換）：

| 依賴 | 結果 |
|---|---|
| Redis（8 秒） | 影響很小：擲骰 max 約 500ms，沒有失敗，凍結結束後立刻恢復 |
| RabbitMQ（8 秒） | 沒有影響（outbox 非同步），max 約 7ms |
| MySQL（8 秒） | 擲骰吞吐崩潰（每 5 秒約 1000 次降到 76 次），解凍後立刻恢復，無失敗 |

- MySQL 凍結造成吞吐崩潰的原因（goroutine dump）：盤面指令走「依玩家分片的工作者」，同一分片依序處理；經過起點的擲骰會做任務去重 `LoadMissionEvents`，查詢沒有期限，卡在凍結的 MySQL 上，分片內所有玩家的指令都停住。`pkg/mysql` 的 DSN 刻意不設 ReadTimeout（避免 DDL 被誤斷），查詢期限本來應由呼叫端 context 控制，但盤面指令的 context 是連線的 context，沒有期限。
- 較長的凍結（25 秒，150 位玩家）：舊版指令全數無回應超過 15 秒，Client 讀取逾時後 150 位全部斷線；
- 修正（`37849c9a7`）：`runBoardCommand` 加 10 秒處理期限（`PlayerStoreOperationTimeout`），逾時回覆失敗並讓斷路器看到失敗。同樣 25 秒凍結：指令在 10 秒內回覆失敗，連線保留 150 位，解凍後約 5 秒回到每 5 秒約 490 次擲骰。
- 沒做：斷路器開啟後的快速失敗（目前每則指令仍會各自等到 10 秒才失敗，凍結期間吞吐仍很低）；若要更快失敗，可把期限縮短或讓斷路器在連續逾時後直接拒絕，需要決定可接受的誤判（慢查詢被當成故障）。

## 2026-10-19（第五輪：關閉 GORM PrepareStmt、改 interpolateParams）

- 起因：gorm `PrepareStmt` 在交易內每句都重新 PREPARE／CLOSE（`database/sql` 的 `Tx.StmtContext` 對綁在 Tx 的語句不重用）。World 寫回與 outbox 幾乎都只在交易內執行，語句快取完全無效，等於每句多一次往返加一個 CLOSE。
- 量測（拋棄式 MySQL 8.4，`BenchmarkFlushRoundByConcurrency/concurrency=16`，400 位玩家寫回，`SavePlayerChanges` 平均約 6.8 句／交易）：
  - 伺服器端 `Com_stmt_prepare`／`execute`／`close`：每交易 6.8／6.8／6.8 → 0／0／0。
  - 每交易往返（`SET TRANSACTION` + `START` + 每句 PREPARE 與 EXECUTE + `COMMIT`）：約 16.6 → 9.8，另少 6.8 個單向 CLOSE 封包。
  - 每輪配置：31.2 MB／290k allocs → 26.3 MB／257k allocs（B/op -16%、allocs/op -12%）。
  - ns/op 受本機同時有其他工作負載影響，波動大（1.8～4.6 s → 1.9～2.7 s），不作結論；寫回吞吐需在有 MySQL 的環境 `-count≥6` 實跑確認。
- 做法：DSN 開 `interpolateParams=true`，移除 `PrepareStmtMaxSize`／TTL 與 LRU 常數；連帶消除 `max_prepared_stmt_count` 風險，以及 `PrepareStmt` 在連線失敗時 `Row()` 回空 `*sql.Row` 導致 `Scan` nil 指標 panic 的潛在問題。
- 副作用與規則：`interpolateParams` 會把 `[]byte` 寫成 `_binary'…'`，寫 JSON 欄位會回 Error 3144，所以 JSON 欄位一律傳 `string` 或 `gamestore.JSONBytes`（見[開發規則](./開發規則.md)）。
- 其他小項：`roadStarsRemoved` 加逐位置比對快速路徑，一般擲骰不再配置 map（`BenchmarkRollSaveShape` 5417 B/op、21 allocs/op → 3580 B/op、18 allocs/op）；Record 批次消費成功改批尾一次 `Ack(multiple)`，100 筆批次從 100 次 write syscall 降為 1 次。
