# PJA-Server 無效測試清理：提示詞與決策紀錄

本文整理這次清理工作的原始需求、判定標準、執行流程、已做的決定與結果，供日後重做或審查參考。

## 一、原始需求（使用者原話摘要）

- 檢查整個 PJA-Server 的測試，清掉無意義的測試檔。
- PJA-Client 不在範圍；不動 docs 目錄與正式碼（除非為了刪測試後移除未使用的 helper）。
- 流程一律「先清單、後刪除，分批進行」：
  - 第 0 步：盤點各目錄 `*_test.go` 數量與行數，給總覽表。建議批次順序 `pkg/*` → `internal/*` → `cmd/*/internal/*` → `tools/*`，每批最多 40 個檔。
  - 第 1 步：逐批審查（不改檔），輸出「保留／刪除／合併／不確定」表。
  - 第 2 步：等使用者確認清單，確認前不刪。
  - 第 3 步：執行，每批一個 commit，標題「test: 精簡 xxx 套件無效測試」，內文用「- 」條列。每批後 `golangci-lint fmt`（不只 goimports）、go vet、go test（必要時 -race）、golangci-lint，確認沒有未使用的 helper 或 import。
  - 第 4 步：收尾。全專案 `go test ./...`（含 -race）與 golangci-lint；統計刪除檔數、合併檔數、淨減行數、整體與各套件覆蓋率變化；更新 goal_report.md，標明「第 660 輪以後新增的測試中，刪除了 X 個、保留了 Y 個」；把判定標準寫進 docs/00-導讀/工作規範.md 的測試章節（docs 為獨立倉庫，另行提交）。
- 限制：每批若覆蓋率下降超過 0.5 個百分點，立即停止並回報，不硬刪。
- 禁止 `git add -f`、`--no-verify`；不一次提交多批；push 到目前分支，每批確認 Pipeline 已建立。

### 刪除的證據（擇一，沒有證據就標「不確定」）

1. 把對應正式碼改壞一處，該測試仍通過。
2. 刪除後該套件 `go test -count=1 -cover` 覆蓋率沒有下降（有浮動的取多次平均）。
3. 明確指出重複覆蓋它的另一個測試。

讀程式碼推論不算證據。覆蓋率不變只代表沒有語句失去涵蓋，不代表行為仍被斷言。

## 八、通用經驗：發現的問題與修正

以下依類別整理，與專案細節無關，可套用到其他 Go 專案的測試清理。

### 8.1 Git 操作

| 問題 | 原因 | 修正／預防 |
|---|---|---|
| 用 merge 同步分支，產生無內容的 merge commit | 另一個 session 在本機分支執行 `git merge` 或 `git pull` | 同步一律 cherry-pick 或 fast-forward；設 `pull.rebase=true`；推送前用 `git log --merges` 檢查 |
| commit 把別的套件的暫存刪除一起帶進去 | 共用 index，`git rm` 後未限定 pathspec 就 commit | 每次 `git add` 與 `git commit` 限定 pathspec；commit 前看 `git diff --cached --stat` |
| 共用暫存目錄的檔名互相覆蓋 | 多代理寫同名 script／commit message 檔 | 每個代理用唯一前綴（如 `audN_`、`exN_`） |
| 第一次推送把別人還沒推的 commit 一起推上去 | 推送目前分支時未先確認差異 | 推送前 `git log origin/<branch>..<branch>` 看清楚內容；需要時先問 |
| 強推風險 | 分支分岔時想用 `--force` | 不強推；改 cherry-pick 或建立新分支 |

### 8.2 子模組與分支對齊

- 超專案釘住的 commit 若只存在本機（detached HEAD、未在任何遠端分支上），別人 `git submodule update` 會失敗。推送前先確認 `git branch -r --contains <sha>`。
- 子模組的「本機分支」與「釘住的 commit」可能是不同線（patch-id 相同但 hash 不同）。比對用 `git patch-id --stable`，找出可 fast-forward 的版本再改指標。
- 改指標前比對生成物與設定檔是否完全一致（`diff -rq`），避免無意中改變產出。

### 8.3 工具與環境

- **golangci-lint 鎖競爭：** 多個代理並行時會回報 "parallel golangci-lint is running"，這是等待訊號，不是失敗。重試，不可跳過 pre-commit。
- **工具版本不符：** 專案用 `go tool -modfile=tools/gotools/go.mod golangci-lint`（v2）時，全域安裝的 v1 會報設定檔版本錯誤。統一用 repo 內宣告的工具版本。
- **Heredoc 在 Windows shell 被打壞：** 會產生沒有輸入而卡住的 `python -` 行程。發現長時間 CPU 空轉的 `python`／`go` 行程要先查命令內容再處理。
- **Docker 容器名衝突：** 固定名稱的測試容器殘留時會 Conflict，啟動前先 `docker rm -f` 自己的容器，不碰別人的。

### 8.4 測試刪除的常見陷阱

- **覆蓋率不變 ≠ 行為仍被守住。** 單獨 skip 一個測試覆蓋率不變，但可能只是被別的測試以其他路徑涵蓋。必須再加「改壞正式碼一處，確認有測試失敗」或指名重複者。
- **整批 skip 的覆蓋率要與個別 skip 的結果一起看。** 個別都不掉、整批卻掉，代表彼此互為備援，不能全刪。
- **合併成表格時容易丟斷言。** 每個原案例、每個原 `require`／`assert` 都要搬過去；只併輸入、丟了期望值等於沒測。
- **有斷言的測試不可併進沒斷言的。** 合併前確認原測試的斷言數。
- **只有 `NotPanics` 的測試：** 刪除可能掉覆蓋率，應改寫成有斷言（例如計數器、輸出內容）而非直接刪。
- **只測測試自己的 stub／mock 的測試：** 刪除不會影響正式碼，屬於無效測試。但要確認它沒被其他測試當 helper。
- **搬移獨有斷言要先於刪除。** 若刪除的測試含唯一的修復順序、唯一的邊界值，先搬到保留的測試，再刪。
- **刪頂層函式用 AST 工具比手動編輯安全**，能連同 doc 註解一起刪，也避免正則誤傷字串。注意 CRLF 行尾：正則替換時要保留 `\r\n`，否則會產生 "newline in string" 語法錯誤。
- **deleted helper 要一併清理。** 刪測試後未使用的 helper、import、測試專用型別，lint（unused、unparam）會抓出來。

### 8.5 測試本身的問題（在清理過程中發現）

清理時發現的問題多數是測試的問題，不是正式碼的問題。處理順序：先確認測試期望是否正確，再看正式碼。

| 類型 | 症狀 | 修正 |
|---|---|---|
| 期望寫錯 | 測試讀取的是錯誤的 response，把第一則訊息當成另一種型別 | 先斷言預期的回覆再斷言後續狀態 |
| 等待條件不完整 | 看到主 key 就讀索引，索引尚未寫入（MULTI 寫入順序） | `Eventually` 同時等所有相關 key 都就位 |
| 固定等待時間 | 負載下啟動慢超過固定秒數就逾時 | 用條件等待取代固定 sleep；無法改時標記為已知不穩定，單獨重跑確認 |
| 共用外部狀態 | 測試依賴其他測試殘留的資料庫資料才會過 | 測試自己建立並清理資料；不要依賴執行順序 |
| 偶發失敗 vs 真實失敗 | 整包失敗、單獨通過、重跑 3～40 次都過 | 記錄失敗頻率與時間點；在 CPU 負載高（如殘留的空轉行程）時重跑；確認後才當作不穩定，不要忽略 |

### 8.6 正式碼的問題（測試揭露）

清理過程有時會因測試失敗而挖出正式碼的錯誤。原則：

- **整數運算的浮點捨入：** 先除後乘會因浮點誤差讓整除結果少 1。改為先乘後除，並以「整除的案例」當回歸測試。
- **溢位保護要保留：** 修正時若只改主要路徑，要確認原本的溢位測試仍通過（必要時對極端值另走舊算法）。
- **不穩定測試可能是 bug 的徵兆：** 只偏差 1 的斷言失敗，優先懷疑計算方法（捨入、時區、排序）。
- **時區：** 取「今天」「每日重置」時，用 UTC 或明確指定的時區，不要用輸入時間自己的時區。
- **鎖與回收：** 限流或鎖的過期回收若與重排入桶的邏輯耦合，應各有測試守住。

修正正式碼時的規則：只修測試揭露的錯誤，附回歸測試（修正前失敗、修正後通過）；與清理工作分開 commit；不順便重構。

### 8.7 Lint 與 CI

- CI 的 lint job 失敗會跳過後面的 unit、integration、e2e。先修 lint，否則看不到測試結果。
- lint 失敗時先在本機跑全專案（而非只跑單一套件）才能確認是既有問題還是新增問題。
- 修 lint 時優先用不改行為的重構（拆函式、搬到 helper、加理由的 `//nolint`），不為了過 lint 改邏輯。
- 修正 `wrapcheck` 時用 `%w` 包裝，不吞錯誤。
- `unparam` 警告：移除沒用到的參數，呼叫端一併調整。

### 8.8 整合測試（真實服務）

- 覆蓋率對整合測試沒有意義，改用「改壞一處、看哪些測試失敗」與「名稱指向另一個保留的測試」作為刪除證據。
- 測試依賴的容器用隔離的名稱與埠（與開發堆疊分開），跑完移除。
- 同時只跑一個整合測試指令，避免埠衝突。
- 測試用的「假服務」（fake）本身的測試通常無效，只測 stub 的行為，可以刪。

## 九、新增測試的過濾規則（補充）

本節適用於「寫新測試」，清理刪除時也可反過來檢驗：留下的測試是否都能通過這些條件。

### 9.1 案例必須同時滿足

1. **有行為風險：** 把對應正式碼改壞一處（反轉條件、換運算子、刪呼叫、改邊界），預期會出現使用者可見或資料錯誤的後果（資料遺失、重複發放、鎖卡死、狀態不一致、安全放行、回應碼錯誤、舊資料讀不回來）。
2. **現有測試抓不到：** 先 grep 同套件測試並跑 `go test -cover`；若已有測試在該行為失敗時會報錯，不要重複寫。
3. **能用變異驗證：** 寫完把正式碼改壞一處，確認新測試失敗，改回後通過。commit 說明只能宣稱「真的被殺掉」的突變，不可寫推測的。

### 9.2 直接排除（不要寫）

- 只重述常數、字串字面值、JSON 鍵名、TTL 數值，且該值只在同一套件內使用（改常數時測試只會跟著改）。
- 只測日誌文字、顯示字串、錯誤訊息文字（除非是維運依文字 grep 的固定格式）。
- 只測 panic 訊息、反射型別名稱（`%T`）、模擬器內部 key。
- 等價突變：改了之後行為完全相同。例如初始值一定被覆蓋、對未包裝哨兵值調換 `errors.Is` 引數、timer 的 `Stop` 排空。
- 純委派、nil 防護、main 接線、空的 Disconnect 方法。
- 重複覆蓋既有測試的同一行為。
- 只為讓覆蓋率數字上升而執行程式、卻沒有斷言行為。

### 9.3 例外：釘住字面值只在下列情況才寫

字面值是「契約」而不是「抄常數」，只在以下情況成立：

- **持久化格式：** 值會寫入資料庫、Redis、檔案、MQ，且可能與舊版資料共存。
- **對外介面：** HTTP 回應鍵名、告警規則／面板／compose／腳本／文件引用的名稱，並且測試要讀那份外部檔案來對照，而不是另外手寫一份。
- **安全或營運前提：** 例如預設只綁 loopback、鎖存活時間與持鎖上限的大小關係。這類請寫「關係或範圍」，不要寫單一數字。

### 9.4 寫的時候

- 優先驗證行為與不變式（冪等、回滾、競態、單調性、邊界），其次才是契約對照。
- 同一套件的契約釘住盡量合併成一個表格測試，不要一個常數一個檔。
- 測試要能在乾淨 checkout 與 CI 通過：讀 docs 目錄前先 Stat，不存在就 `t.Skip`；整合測試加 build tag；不依賴本機路徑或時區。
- 測試名稱與 commit 標題說明「保護的風險」，不要只寫「補 xxx 測試」。

### 9.5 每輪結束前自我檢查

三題都答「是」才提交，任一題答「否」就換下一個案例：

- 這個測試若被刪掉，會不會有一種真實的 bug 從此沒人發現？
- 我是否親眼看到突變讓它失敗？
- 它是否沒有和既有測試重複？

### 9.6 與清理規則的對應

| 清理判定 | 新增規則對應 |
|---|---|
| A（只釘常數） | 9.2 第一條；9.3 的例外才可保留 |
| B（日誌、顯示、stub） | 9.2 第二、三條 |
| C（重複） | 9.2 第六條、9.1 第二條 |
| E（保留） | 9.3 三種契約與 9.1 的行為風險 |
| 刪除證據 | 9.1 第三條的變異驗證，與 4.4 的證據一致 |

若找不到合格案例，停止並回報，不為湊數降低標準。

## 十、重做此流程的最短步驟

1. 盤點：`find` 列出各目錄 `*_test.go` 數量與行數，依批次排序。
2. 每批用唯讀代理依第二節標準審查，每個刪除候選附證據。
3. 整理清單交使用者確認，確認前不刪。
4. 每批用獨立 worktree 執行，每套件一個 commit，覆蓋率與 lint 驗證。
5. cherry-pick 到目標分支，逐批推送並確認 Pipeline。
6. 收尾：全專案測試與 lint、統計、更新 goal_report.md、判定標準寫入 docs。
