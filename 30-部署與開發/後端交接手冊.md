# 後端啟動與發布流程

## 本機完整啟動

環境需求：Go 1.27+、Docker Compose、Bash（Linux、macOS 或 WSL）。在 Server 專案目錄執行：

```bash
./scripts/docker-deps-up.sh
./scripts/dev-up.sh
```

`dev-up.sh` 以 `config/dev/*.yaml` 啟動 Central、Record、Lobby、Chat、World、Gate 與 User。若要連監控一起啟動，改用 Docker 全堆疊：

```bash
./scripts/docker-full-up.sh
```

全堆疊啟動後，檢查容器狀態：

```bash
docker compose -f docker/compose/compose.full.yml ps
```

預設玩家連線埠為 `62001`，Record HTTP 為 `6070`，Grafana 為 `http://localhost:3000`，Prometheus 為 `http://localhost:9090`。

## 正式發布

以下命令在已配置正式環境變數及憑證的發布環境執行。建置及推送腳本處理六個自建服務（Central、World、Gate、Chat、Lobby、Record）；`compose.prod.yml` 要求 `CHAT_IMAGE`、`RECORD_IMAGE` 必填，`.env.prod` 的六個 `*_IMAGE` 都要指向本次版本。建置腳本另有選用環境變數 `APT_REFRESH`（預設取 `CI_PIPELINE_ID` 或當天日期，讓 runtime 階段的 apt upgrade 層定期失效）。先設定本次版本並建置、推送：

```bash
export REGISTRY=registry.example.com/project
export IMAGE_TAG=<release-tag>
./scripts/docker-build-images.sh
./scripts/docker-push-images.sh
```

在 `PJA-Server` 目錄執行資料遷移；`scripts/migrate-prod.sh` 與 `ci-deploy.sh` 一樣使用子模組 `deps/PJA-Database`（可用 `PJA_DATABASE_DIR` 覆寫）。遷移腳本的 `AUTO_MIGRATE_DISABLED` 預設為 `true`（設成其他值會被拒絕），`compose.prod.yml` 對各服務也已固定，不需要在 `.env.prod` 設定；正式 `.env.prod` 須有正確的 `MYSQL_DSN` 與 `MIGRATION_PLAN_DIR`（映像不含 migrations；留空時 CD 掛載部署主機的 `deps/PJA-Database` 讀 `/src/migrations`，手動 `migrate-prod.sh` 預設讀 `${ROOT_DIR}/migrations`；自訂須為宿主機上已存在的絕對路徑，相對路徑或不存在的目錄 `ci-deploy.sh` 在關服前就報錯退出）。先驗證版本鏈，再正式套用。`scripts/migrate-prod.sh` **不接受任何參數**（內層固定對正式庫 `-mode apply -confirm`），預檢請直呼 `datamigrate -mode validate`（下方第一行）；`ci-deploy.sh` 現在於關服前就預檢 `MYSQL_DSN`（缺值、鍵名打錯、仍是 `change_me` 佔位值都會在停服前失敗），手動執行時請自行先確認該值：

```bash
# 子模組沒有 toolchain 行：沿用根 module 解析出的 Go 版本（go1.27.3），主機 Go 較舊時才不會編出帶已修補標準庫漏洞的 datamigrate
(export GOTOOLCHAIN="$(go env GOVERSION)"; cd deps/PJA-Database && go run ./cmd/datamigrate -dir migrations -mode validate -environment production)
# .env.prod 是 compose 的 dotenv 格式、不是 bash：未加引號的 MYSQL_DSN=...@tcp(...)/... 交給 source 會語法錯誤，改以 env_get 逐鍵讀
source scripts/lib/envfile.sh
ENV_FILE=.env.prod
export MYSQL_DSN="$(env_get MYSQL_DSN)"
plan_dir="$(env_get MIGRATION_PLAN_DIR)"
if [ -n "${plan_dir}" ]; then export MIGRATION_PLAN_DIR="${plan_dir}"; fi
./scripts/migrate-prod.sh   # 內部同樣以 GOTOOLCHAIN=$(go env GOVERSION) 進子模組
```

Migration 前（或與它同一個維護窗）還要發布本版的設定 artifact，否則 World 以 `pkg/release/verify.go` 比對映像內嵌的 `config_version`／`config_seq` 與 `current.json` 不符，拒絕啟動。先記下目前 `current.json` 的 `config_version`（回滾用），再預檢並發布：

```powershell
.\scripts\publish-data-config.ps1 -DryRun -Source config\data -Root <DATA_CONFIG_ROOT>
.\scripts\publish-data-config.ps1 -Source config\data -Root <DATA_CONFIG_ROOT>
```

Migration 成功後，確認 `.env.prod` 的 Central、World、Gate、Chat、Lobby、Record image 都指向預期版本，再到 `PJA-Server` 目錄部署：

```bash
docker compose --env-file .env.prod -f docker/compose/compose.prod.yml up -d
docker compose --env-file .env.prod -f docker/compose/compose.prod.yml ps
docker compose --env-file .env.prod -f docker/compose/compose.prod.yml logs --tail 100 central world gate
powershell -ExecutionPolicy Bypass -File .\scripts\production-smoke.ps1
```

Migration 失敗時停止發布並保留現行服務。回退時映像與設定一起退：先 `docker compose ... stop` 六個服務，用 `.\scripts\rollback-data-config-release.ps1 -Root <DATA_CONFIG_ROOT> -Version <上一版 config_version>` 把 `current.json` 切回升版前記下的版本（舊映像配新 `current.json` 時 World 起不來，回滾會失敗），再把 `.env.prod` 的六個 `*_IMAGE` 改回上一個穩定版本（compose 不讀 `IMAGE_TAG`），重新執行 `docker compose ... up -d` 並確認 smoke。若 migration 已套用，先確認舊 image 與新 schema 相容；不可直接對正式資料降版。
