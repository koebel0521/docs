# 灰度回退點

灰度回退點是先定好「做到哪一步，出事就退回哪一步」。

目的不是漂亮。目的是：

- 出事時不用現場想
- 縮小回滾範圍
- 讓 canary / rolling / config change 都有可停點

## 什麼是回退點

回退點是一個可驗證的 checkpoint，通常要同時滿足：

1. 已完成某一小步變更
2. 已看過最基本 smoke / ready
3. 若下一步壞掉，可以直接退回這一步

## 在這專案裡常見回退點

### 1. Canary 流量切片

- `traffic_slice_percent = 1` 可以當第一個回退點
- `5`、`10` 可以是放量前的下一個回退點
- 一旦指標掉，就先退回 0%

### 2. Rolling upgrade

- 限制：服務之間的 `ServiceHello` 要求發版身分一致（`pkg/s2shandshake/service_identity.go`），不同發版的服務不能混跑。**跨發版升級或回退必須整批替換**所有服務，不可逐台升級。
- 逐台 rolling 只適用於**同一發版內**的重建（例如 Gate 排空重啟、單一服務重啟），每一台重建完都是一個回退點。
- 整批替換的回退點是「整批替換前的舊發版映像組」，不是單一服務。

### 3. 設定變更

- 版本政策（`gm:version:policy` 的 `min`、`latest`、維護開關）
- `feature flag`
- `drain` / `limit` / `timeout`

這些都要先定「改前」與「改後」的回退點。

### 4. 資料變更

- migration apply 前
- migration rollback 前
- 任何 schema / key 改動都要先定回退點

## 好回退點的條件

1. 小
2. 可逆
3. 可觀察
4. 已驗證
5. 不會把壞狀態擴散到全站

## 不好的回退點

- 全量流量已切完才想回退
- code + config + 流量一起改
- 只看功能通不通，不看 queue / latency / reconnect
- 沒有驗 rollback，就先把舊版砍掉

## 實務做法

1. 先列操作步驟
2. 每一步後面寫回退動作
3. 每一步後面寫觀察指標
4. 每一步都要能單獨停

範例（同一發版內逐台重建，例如 Gate 排空重啟；跨發版升級改為整批替換後再跑一次 smoke）：

1. 重建第一台 `gate`（先排空）
2. 跑 smoke
3. 若正常，再重建下一台 `gate`
4. 跑 smoke
5. 最後才放大 canary
