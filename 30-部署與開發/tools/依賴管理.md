# 依賴管理工具

本專案的 Go 依賴管理工具與流程。

## Makefile 指令速查

| 指令 | 說明 | 需要安裝 |
|------|------|----------|
| `make vuln` | 依賴漏洞掃描 | 無（`go tool -modfile=tools/gotools/go.mod govulncheck`） |
| `make ci-vuln` | CI 等價漏洞掃描 | 無（同上） |
| `make outdated` | 列出有新版的依賴（主 module 只列實際編入的 module，`tools/gotools` 只列 tool 本身） | 無（`go list -u -m`） |
| `make deps-size` | 分析 binary 大小分布（以 Central 為代表，旗標與正式建置一致：固定 `GOOS=linux GOARCH=amd64`（Windows 主機也量 Linux 版）、`CGO_ENABLED=0 -trimpath -pgo=default.pgo -ldflags="-s -w"`；輸出 `.run/size-report.html`） | 無（`go tool -modfile=tools/gotools/go.mod gsa`） |
| `make dep-graph` | 產生依賴圖 .run/deps.png | Graphviz `dot`（`modgraphviz` 鎖在 `tools/gotools/go.mod`） |

## 工具模組（`tools/gotools`）：CLI 工具版本鎖定

CLI 工具（golangci-lint、govulncheck、benchstat、goimports、gocover-cobertura、gsa、modgraphviz）宣告在獨立的 `tools/gotools/go.mod`，不進主 module 的 `go.mod`／`go.sum`。`make`、pre-commit 與 GitLab CI 都經這個 modfile 執行同一版本，不需要另外 `go install`。

### 鎖定的工具

| 工具 | 套件路徑 | 用途 |
|------|----------|------|
| `golangci-lint` | `github.com/golangci/golangci-lint/v2/cmd/golangci-lint` | 靜態分析與格式化 |
| `govulncheck` | `golang.org/x/vuln/cmd/govulncheck` | 漏洞掃描 |
| `benchstat` | `golang.org/x/perf/cmd/benchstat` | Benchmark 比較 |
| `goimports` | `golang.org/x/tools/cmd/goimports` | 單獨整理 import 時使用；pre-commit 與 CI 用的是 `golangci-lint fmt`（gofumpt、goimports、gci），提交前跑 `make fmt` |
| `gocover-cobertura` | `github.com/boumenot/gocover-cobertura` | CI 覆蓋率轉換 |
| `gsa` | `github.com/Zxilly/go-size-analyzer/cmd/gsa` | Binary 大小分析（`make deps-size`） |
| `modgraphviz` | `golang.org/x/exp/cmd/modgraphviz` | 依賴圖（`make dep-graph`，另需 Graphviz `dot`） |

### 執行

```bash
go tool -modfile=tools/gotools/go.mod golangci-lint run ./...
go tool -modfile=tools/gotools/go.mod govulncheck ./...
```

不加 `-modfile=tools/gotools/go.mod` 在根目錄執行會得到 `no such tool`。`go tool cover` 等標準工具不受影響。

### 升級

```bash
go get -C tools/gotools -tool github.com/golangci/golangci-lint/v2/cmd/golangci-lint@<版本>
go -C tools/gotools mod tidy
```

### 新增工具

1. `go get -C tools/gotools -tool <path>@<version>`
2. `go -C tools/gotools mod tidy`
3. 以 `go tool -modfile=tools/gotools/go.mod <name>` 呼叫

### 注意

- 不要在根目錄對工具 modfile 執行 `go mod tidy -modfile=...`：根目錄的套件會被算進工具模組，tidy 會拉進整棵專案的依賴。工具模組一律在 `tools/gotools` 目錄內 tidy。
- CI 的 `lint` job 與 `make ci-lint` 會在 `tools/gotools` 內 tidy，並檢查工具模組的 `go.mod`／`go.sum` 沒有未提交的改動。
- 根 module 的 `go.mod` 以 Go 1.25+ 的 `ignore ./tools/private` 排除不進版控的私人工具（第十一輪），本機 tidy 結果與 CI 相同；CI `lint` job、`make ci-lint` 與 pre-commit 的 `go-mod-tidy` hook 都以 `go mod tidy -diff` 檢查（只比對、不改寫）。代價：`./...` 與 `./tools/private/x/...` 不再涵蓋私人工具，build／vet 私人工具要寫明確的套件路徑（例如 `go vet ./tools/private/boardsimulator`）。
- `.gitattributes` 對 `go.mod`、`go.sum` 設 `eol=lf`，Windows 本機工作樹也是 LF，`go mod tidy -diff` 不會再因換行誤判有差異；既有的 CRLF 工作樹檔案需重新檢出一次（確認沒有未提交的修改後，刪除檔案再 `git checkout -- go.mod go.sum tools/gotools/go.mod tools/gotools/go.sum`；工具模組的 go.sum 同樣可能仍是 CRLF，`go -C tools/gotools mod tidy -diff` 會整檔誤報）才會換成 LF。`tools/private` 已由 `go.mod` 的 `ignore` 排除，不再影響根 module 的 tidy 結果。

## govulncheck: 漏洞掃描

### 使用

```bash
# 掃描整個 module
go tool -modfile=tools/gotools/go.mod govulncheck ./...

# 或透過 Makefile
make vuln
```

### 注意

- GitLab 的 `govulncheck` job 依序掃三處，有可達漏洞即擋下合併：主 module（`go tool -modfile=tools/gotools/go.mod govulncheck ./...`）、`deps/PJA-Database`（正式部署時 `ci-deploy.sh` 會在正式機 `go run` 它的 `datamigrate`，所以 job 只 checkout 該子模組並掃描），以及工具模組宣告的全部工具（`go -C tools/gotools tool govulncheck tool`）。`make ci-vuln` 依同樣順序列三行，第二行掃 `deps/PJA-Database` 需先 `git submodule update --init`
- govulncheck 由 `tools/gotools/go.mod` 的 `tool` directive 管理，版本見 `tools/gotools/go.mod`
- 本機開發時若遇到 `package requires newer Go version` 錯誤，表示某個工具版本尚未追上專案使用的 Go 版本，可升級該工具或暫緩升級 Go，不影響專案建置

## 過時依賴追蹤

不需另裝工具，`make outdated` 直接用 `go list -u -m` 列出有新版本的依賴（第十一輪起只列實際用到的 module）：主 module 只列 `go list -deps -test ./...` 實際編進套件（含測試）的 module，不列 `all` 裡被剪枝的圖節點（對圖外 module 照輸出 `go get` 會把多餘的 require 寫進 `go.mod`；只反映執行平台的 build tag，Linux 專屬依賴要在 Linux 上跑）；工具模組只列 `tool` 本身，不列工具的傳遞依賴。實測主 module 約 3 行、工具 7 行（原本 29 行與 164 行）：

```bash
go list -u -m -f '{{if .Update}}{{.Path}} {{.Version}} -> {{.Update.Version}}{{if .Indirect}} (indirect){{end}}{{end}}' $(go list -deps -test -f '{{with .Module}}{{if not .Main}}{{.Path}}{{end}}{{end}}' ./... | sort -u)
go -C tools/gotools list -u -m -f '{{.Path}} {{.Version}}{{if .Update}} -> {{.Update.Version}}{{end}}' $(go -C tools/gotools list -f '{{.Module.Path}}' tool | sort -u)

# 或透過 Makefile
make outdated
```

## gsa: 二進位大小分析

`go-size-analyzer`（`gsa`）鎖在 `tools/gotools/go.mod`，不需另行安裝。`make deps-size` 以 Central 為代表建置後輸出 HTML 報告：

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -pgo=default.pgo -ldflags="-s -w" -o .run/central ./cmd/central
go tool -modfile=tools/gotools/go.mod gsa -f html -o .run/size-report.html .run/central

# 或透過 Makefile
make deps-size
```

依賴圖同樣由 `tools/gotools/go.mod` 的 `modgraphviz` 產生，只需另裝 Graphviz `dot`：

```bash
go mod graph | go tool -modfile=tools/gotools/go.mod modgraphviz | dot -Tpng -o .run/deps.png
# 或 make dep-graph
```

## golangci-lint 依賴檢查

`.golangci.yml` 已啟用以下依賴相關 linter：

| Linter | 作用 |
|--------|------|
| `depguard` | 封鎖 `log/slog` 與 `log`（日誌統一走 `pkg/logger`）；正式碼（非測試）另擋 `encoding/json`（改用 `github.com/goccy/go-json`），以及 `pkg/logger` 以外直接 import `github.com/rs/zerolog`（測試可用） |
| `gomodguard_v2` | 封鎖與既有選型重複的套件（logrus、zap、其他 JSON／YAML 函式庫、`pkg/errors`、`samber/oops`（改用標準 `errors`）、gobreaker v1、舊版或不同選型的 backoff 與 Redis 用戶端（含 `go-redis/redis` v8 與無版本路徑、`redigo`）、已棄用的 `streadway/amqp`（改用 `amqp091-go`）、`golang-lru` v1（改用 `/v2`）） |
| `gomoddirectives` | 不允許任何 `replace`（白名單為空），`retract` 須附原因 |

## Pre-commit 自動檢查

`.pre-commit-config.yaml` 的 `golangci-lint` 是 local hook，以 `go tool -modfile=tools/gotools/go.mod golangci-lint run --new-from-rev HEAD --whole-files --fix` 只檢查相對 HEAD 有改動的檔案（整個檔案的問題都回報）；`make lint` 與 CI 則檢查全樹（`.golangci.yml` 不設 `new-from-rev`）。

另有兩個 golangci-lint hook 補主 hook 的盲區：

- `golangci-lint (other GOOS)`：改到 `integration/testenv`、`pkg/dataconfig` 底下的 `.go`，或任何以 `_windows`／`_other`／`_linux`／`_unix`／`_darwin` 結尾的 `.go` 時，執行 `scripts/lint-other-goos.sh`，以另一個 GOOS 檢查 `*_other.go`、`*_windows.go` 等在主機 GOOS 不會編譯的平台專屬檔（與 `make ci-lint`、CI 一致）
- `golangci-lint (full tree)`：只改 `.golangci.yml` 或 `tools/gotools/go.mod`／`go.sum`（升級 golangci-lint 版本）時跑全樹 `golangci-lint run ./...`，因為主 hook 的 `--new-from-rev` 會濾掉既有檔案的新問題

`pre-commit install` 會一次裝 pre-commit 與 commit-msg 兩種 hook（`default_install_hook_types`），commit-msg 階段的 `perf-commit-evidence` 才會生效。

`go-mod-tidy` local hook 的作用：

- 根 module 只檢查不改寫：`go mod tidy -diff`，有差異就擋下並提示執行 `go mod tidy`（`go.mod` 以 `ignore` 排除 `tools/private`，本機結果與 CI 相同）
- 工具模組 `tools/gotools` 直接 tidy 後比對（不 find 所有 `go.mod`，以免動到其他工作樹）
- 若 tidy 後工具模組仍有未提交的變更，commit 會被擋下並提示執行 `go -C tools/gotools mod tidy`
- 安裝：`pre-commit install`

## 定期維護流程

專案不使用 Renovate／Dependabot（GitLab 上從未運作，`renovate.json` 已刪除），依賴與映像一律人工定期升級：

1. **每月**：執行 `make outdated`。主 module 的 minor／patch（含 indirect）以 `go get -u=patch -t ./...`（`-t` 連測試依賴一起升）、`go get <模組>@<版本>` 升級；工具模組沒有任何套件，`./...` 在那裡不會升級任何東西，改用 `go get -C tools/gotools -u=patch tool`（或 `-u tool`）再 `go -C tools/gotools mod tidy`。跑 `make ci-lint`、`make ci-unit` 後提交；major 更新另開 MR 人工審查
2. **每月**：更新固定 digest 的映像：`.gitlab-ci.yml`（golang、trivy、docker-cli、services）、`docker/app.Dockerfile`、`scripts/ci-deploy.sh` 的 `GO_IMAGE`、`docker/compose/compose.prod.yml` 與 `.env.prod.example`；`.pre-commit-config.yaml` 的 hook 以 commit SHA 釘選，一併檢查新版
3. **發版前**：執行 `make ci-vuln` 掃描 CVE（以 `go tool -n govulncheck` 取出執行檔路徑後固定 `GOOS=linux GOARCH=amd64` 執行，Windows 主機也分析 Linux 專屬路徑；與 CI `govulncheck` job 相同的三段：主 module、`deps/PJA-Database`、`tools/gotools` 的全部工具；`make vuln` 只掃主 module）；有可達漏洞立即升級，不等每月例行
4. **每季**：執行 `make deps-size` 監控 binary 膨脹趨勢

## Module 現狀

module 清單以[工作規範](../../00-導讀/工作規範.md#go-module)為準：

- 主 module `local/server`（根目錄）：`cmd/`、`internal/`、`pkg/`、`integration/` 與 `tools/` 下的運維工具（`tools/gotools` 除外）。
- 工具 module `local/server/tools/gotools`（`tools/gotools/go.mod`）：只宣告 CLI 工具，見上方「工具模組」。
- `deps/` 子模組：`deps/go.mod`（`local/deps`）與 `deps/PJA-Database`（`local/database`，正式部署會 `go run` 它的 datamigrate，`make ci-vuln` 會掃）等，各自有 `go.mod`，不在根 module 的 `./...` 內。

服務邊界靠 Go 的 `internal` 規則（`cmd/<service>/internal/`，跨服務 import 由編譯器擋）加上 `internal/archtest/cmd_boundary_test.go` 的 `TestCmdNonInternalPackagesAreMain`（`cmd` 下非 `internal` 的套件只能是 `main`）維持。`tools/pja` 把各運維工具編成單一 binary，子命令直接分派到各工具套件，見[工具總覽](../工具總覽.md)。
