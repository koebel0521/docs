# 已知安全風險

本文件記錄審查找到、**決定接受**的安全風險。處理前請先與 PJA-Client 負責人確認，Client 不在本專案範圍。

| # | 項目 | 位置 | 現況 | 影響 | 緩解 |
|---|---|---|---|---|---|
| 1 | 玩家連線無 TLS | `cmd/gate/internal/services/userserver.go`（對外埠 `62001`，見 `docker/compose/compose.prod.yml`） | Gate 收明文 TCP，只有 S2S 連線用 TLS（`pkg/s2sauth`）；PJA-Client 決定不做 TLS（2026-10-13） | 登入帳號與密碼在公網以明文傳輸，路徑上的人可竊聽或竄改封包；bcrypt 只保護資料庫中的密碼 | 玩家走 VPN，或以防火牆／安全群組限制來源網段；之後若 Client 支援 TLS，在 Gate 前放 TLS 終結（nginx stream、HAProxy、stunnel）或讓 Gate 自行 `crypto/tls`，Client 需同步改 |
| 2 | Redis、RabbitMQ 連線無 TLS；MySQL TLS 預設關閉 | `pkg/redis/client_new.go`、`RABBITMQ_URL`（World、Record，`docker/compose/compose.prod.yml`）、`pkg/mysql/mysql.go`（`mysql.tls`） | Redis 沒有 TLS 設定；RabbitMQ 以 `amqp://` 連線，帳密寫在 URL；MySQL 需設 `mysql.tls` 才加密；`mysql.tls` 設為 `skip-verify`（不驗證憑證）或 `preferred`（會靜默退回明文）時啟動只記 Warn、不拒絕啟動（專案沒有可靠的 prod 判斷慣例） | 跨主機部署時密碼與資料明文 | 資料庫、Redis、RabbitMQ 只放同一內網或 Docker network，不對外開放；跨主機時 MySQL 設 `mysql.tls: true` 或帶 CA 的自訂設定名（`skip-verify`、`preferred` 擋不住中間人）、RabbitMQ 改 `amqps://` |
| 3 | 登入限流不含每帳號全域上限；首次登入自動建帳 | `cmd/gate/internal/flow/user/login/coordinator.go`、`cmd/central/internal/flow/login/new_user.go` | 只限每 IP、每（帳號, IP）；不鎖帳號是刻意設計。限流表滿載（10 萬 key）時淘汰最久沒碰的 key 而非拒絕新 key，被淘汰 key 的鎖定狀態會消失（見[容量與壓測基準](../20-排障與監控/容量與壓測基準.md)）。首次登入的帳號自動建立，建帳速率原本只受每 IP 登入限流約束、新帳號沒有最短密碼 | 換 IP 的分散式猜密碼對同一帳號沒有全域上限；可大量建立垃圾帳號（從未活躍的帳號 360 天才清） | bcrypt 槽位已加 3 秒等待期限，滿載回服務暫不可用，不會拖垮 Central。Central 選填 `new_user.rate`／`new_user.burst`（全服建帳速率，超過回 `AuthServiceUnavailable`）與 `new_user.min_password_bytes`（新帳號最短密碼，過短回 `AuthWrongPassword`），預設皆 0＝不限制；最短密碼**須先與 PJA-Client 註冊提示同步**才開（見[設定注入與熱更新](../00-導讀/設定注入與熱更新.md#central-new_user-選填鍵)）。Gate 每 IP 同時連線上限可用 `session.max_connections_per_ip` 調整（預設 100，CGNAT 取捨）。**未登入連線有全域上限**：未登入（`sock.ID() == 0`）連線可存活到握手逾時（約 30 秒），只靠每 IP 上限時約 11 個來源（每來源 100 條）即可佔滿預設 1024 的連線槽、擋掉所有新玩家；Gate 現在把未登入連線總數限制在 `max_connections` 的 1/4（未設定 `max_connections` 時為 256，`defaultMaxUnauthenticated`，位於 `cmd/gate/internal/handler/user/connect.go`），超過時**關閉最舊的未登入連線**讓新連線進來，計入 `tcp_rejected_connections_total{service="user",reason="unauth_evicted"}`。正常玩家的新連線因此永遠進得來，攻擊者必須持續用新連線換掉自己的舊連線；代價是尖峰時剛連上、還沒送完登入的合法連線也可能被淘汰（客戶端重連即可）。計數為樂觀計數（連線時加一，超過上限才掃描，每 5 秒的連線檢查順便重算修正偏差），平時不遍歷連線 |
| 3a | Lobby 公開 `:8080` 的資源上限 | `cmd/lobby/internal/handler/servers.go`（`BuildServers`、`MaxConns`） | 同時連線上限 2048、每個來源 IP（IPv6 以 /64 計）每秒 20 個請求、突發 40（超過回 429）；每個請求 3 秒期限；公開 listener（Lobby、Record）keep-alive 閒置 5 秒（原 30 秒） | CGNAT 下大量玩家共用 IP 時可能被 429；超過 2048 條同時連線的新連線要排隊 | 數值寫在程式常數，需要時調整後重新發版；閒置連線約 20 KB／條，2048 條約 40 MB，遠低於 Lobby 容器上限 |
| 3b | 封禁狀態在驗證密碼前就回給 Client | `cmd/gate/internal/flow/user/login/coordinator.go`（`afterBanCheck`） | Gate 先以帳號查 Redis 封禁狀態，被封禁就直接回 `AuthAccountBanned`，不轉送 Central 驗證密碼；不需要密碼即可得知該帳號存在且被封禁（第十一輪 SC-L3，決定接受） | 輕微資訊揭露：可列舉被封禁的帳號，或確認特定玩家的處分狀態 | 刻意取捨：被封禁帳號的登入不進 Central、不花 bcrypt（若改成密碼通過才回封禁，被封禁帳號的每次重試都要做一次 bcrypt、佔用 `bcryptSlots`）。查詢仍受每 IP、每（帳號, IP）登入限流約束；封禁查詢失敗時 fail-closed 回 `AuthServiceUnavailable`。日後若要隱藏封禁狀態，改由 Central 在 bcrypt 通過後才查封禁，密碼錯誤一律回 `AuthWrongPassword` |
| 3c | Chat 房間成員上限先到先得 | `cmd/chat/internal/app`（`room_max_members`，預設 500）、`cmd/gate/internal/handler/user/on_chat.go` | 任何已登入玩家都可加入任意 `RoomID`，房間滿後新成員的加入被靜默拒絕（第十一輪為擋扇出加上的上限）。第十二輪 SC-L2：Gate 另限制同一來源 IP（IPv6 以 /64 計）在同一房間經此 Gate 的成員數（`session.chat_room_members_per_ip`，預設 50），被拒計入 `game_chat_rate_limited_total{kind="join"}` | 少數來源的機器人帳號可佔滿已知房間，正常玩家加入被靜默拒絕且 Client 收不到原因；IP 配額下佔滿 500 人房間至少要 10 個來源 | 先接受：IP 配額只按單一 Gate 計數，來源分散到多台 Gate 時名額按 Gate 算；網咖／CGNAT 共用 IP 的大量玩家可能被擋。保留名額、帳號年齡門檻、系統房間改伺服器端權威成員（需 World 管理成員）與加入結果訊息（需 PJA-Protocol）仍待決策 |
| 4 | Lobby admin 與 Record `/events` 以明文 HTTP 收 Bearer token | `cmd/lobby/internal/handler/servers.go`（`ADMIN_ADDR`／`admin_addr`）、`cmd/record/run.go`（`addr`） | 預設只綁 loopback（開發用 `config/dev/lobby.yaml` 的 `addr`／`admin_addr` 與 `compose.full.yml` 的 `8080`、`compose.debug.yml` 的 `18080` 對外埠也只綁 `127.0.0.1`，不再是 `0.0.0.0`；debug 版 Lobby 的公開埠與 admin 路由共用同一個 listener，`config/docker/lobby.yaml` 的 `admin_token` 又是寫死在版本庫的公開值，發布到所有介面等於區網任何人都能打 admin。要給區網實機 Client 連 debug 版 Lobby 時，依 `compose.debug.yml` 註解：刪掉 Lobby 的 `ALLOW_DEV_TOKENS`、把 `admin_token`、`ops_token`、`gm_token` 換成隨機值，再把埠改成 `"18080:8080"`，沒換 token 時 Lobby 拒絕啟動（第十二輪改註解，預設值不變）；綁內網介面時 token 在內網路徑上明文傳輸（2026-10-16 審查） | 內網被竊聽時 token 可被重放，取得 GM 發放與玩家事件查詢權限 | 只綁 loopback，或以 nginx／stunnel 在前面做 TLS 終結；token 常數時間比對、最短 32 字元、拒絕 `change-me` 開頭的範本佔位（Lobby 三個 token 與 Record `http_token` 皆是）；版本庫內公開的開發 token（以 `-local-stack-only` 結尾）綁在非 loopback 位址時拒絕啟動（`httpx.RejectDevStackToken`，Lobby 依實際 admin 位址檢查三個 token、Record 檢查 `http_token`；第十一輪，原本這些值長度剛好 32 字元又不是 `change-me` 開頭，兩道驗證都放行），只有 Docker 開發堆疊（`compose.full.yml`、`compose.debug.yml`，容器內必須綁所有介面、主機只發布在 loopback）以環境變數 `ALLOW_DEV_TOKENS=true` 放行，單純把開發設定檔搬到可對外連線的環境不會帶上它；**熱重載走同一道守門**（第十二輪 SC-L1／DI-M1）：Lobby 啟動與 token 熱重載共用 `services.NewTokenValidator`，以啟動時的實際 admin 位址與 `allow_dev_tokens` 建立一次，把公開開發 token 貼進非 loopback 的設定檔熱重載會被拒絕（`config hot reload not applied`），`allow_dev_tokens` 固定取啟動值、熱重載關不掉守門（第十一輪只有啟動時檢查，熱重載可繞過）。Lobby 的 admin／ops／gm 三個非空 token 不可相同；每 IP 失敗鎖定只有 Lobby admin 有，Record `/events`（`requireBearerToken`）沒有，只靠 token 的熵；Record `/events` 每次成功查詢記 Info 稽核 `record events audit`（`audit=true`、`remote_addr`、`playerID`、`eventType`、`rows` 等，不取樣；第十二輪 SC-L3），token 外洩被濫用時可查誰查了哪位玩家。Lobby admin 鎖定期間直接拒絕、不再比對 token：被鎖定的來源連正確 token 也回 429，同一 NAT 後的合法維運會與攻擊者共用額度而被暫時擋住（每 12 秒回復一次嘗試機會）；HTTP 伺服器另限制標頭 `MaxHeaderBytes=16KB`，存取日誌的 path 截斷為 256 bytes，避免未驗證來源以超長 URL 灌爆日誌 |
| 5 | MR 可在 deploy runner 執行任意程式碼；MR 與發版共用 BuildKit 快取（**待處理**） | `.gitlab-ci.yml`（`build-images-mr`、`build-images` 共用 `tags: [deploy]`）、`docker/app.Dockerfile`（`RUN --mount=type=cache`） | rules 只限同專案 MR 才上 deploy runner，但 `.gitlab-ci.yml` 本身在 MR 內，有 push 權限者可自加 `tags: [deploy]` 的 job；MR 與發版建置共用 `/go/pkg/mod`、`/root/.cache/go-build` 快取（2026-10-17 審查 H4） | 在 production 主機（shell executor、可存取 docker.sock）執行任意指令；MR 可改寫快取內的模組原始碼，之後發版直接使用而產出被植入的正式映像 | 待處理：GitLab 將 deploy runner 設為 Protected（只跑 protected branch／tag）；`build-images-mr` 改用獨立的 docker executor runner 或 rootless 建置；發版建置使用不同的 cache id 或 `--no-cache` |
