# 狀態對帳操作手冊

這份 runbook 專門對應 Central / Gate / World 的週期性狀態對帳。
目前 Central 會主動向 Gate / World 拉 live snapshot，並對 `MySQL / Redis / Memory` 做三方比對；當 MySQL 與記憶體一致、但 Redis 漂移時，Central 會自動把 Redis 修回來。
Gate / World 也會在 audit 後重建可安全重建的衍生索引，讓長時間運行後的狀態自動收斂。
`mismatch` 代表本地索引、跨服務路由，或已被自動修復的暫態漂移；`error` 則通常代表 snapshot、MySQL、Redis，或其他外部依賴失敗。
audit 自己也有 timeout、late reply、service restart / recovery 的演練測試，目的是確保對帳機制本身不會在故障時污染下一輪。
當 `game_state_audit_total` 出現 `mismatch` 或 `error`，先走這份流程。

## 第一判斷

`game_state_audit_total` 的 `result` 只有 `ok`、`mismatch`、`error`、`skipped`（`pkg/audit/report.go`）；沒有 `repair` 標籤。值班時先把事件分成三類，再決定下一步：

1. `mismatch`
   - 優先看衍生索引、路由表、session 綁定
2. `error`
   - 優先看 Redis / MySQL / timeout / snapshot 失敗
3. 日誌 summary 的 `repairs=`（不是指標標籤）
   - 代表系統已把可安全收斂的部分修回，接著追根因，不要停在表面恢復

順序固定：

1. 先看 `game_state_audit_total`
2. 再看 `資源預算`
3. 最後才下鑽 handler、TCP、DB log

## 狀態邊界

`authoritative state = 真相狀態`

- Central: `users`
- Gate: `sessionsByKey`、`users`
- World: `users`

`derived state = 衍生索引`

- Central: `usersByAccount`、`usersByGate`、`usersByWorld`
- Gate: `usersByWorld`、`sessionKeyByUser`、`sessionCentral`
- World: `usersByGate`

`rebuildable cache = 可重建快取`

- Central: `loginRequests`、`logoutRequests`、`worldRegistry.warmupUntil`、`worldRegistry.drained`
- Gate: `validateCache`、`ipLoginLimiter`、`loginLimiter`、`logoutLimiter`、`worldGrace`
- World: `journals`（`requestJournals` 的 `login`／`logout`／`validate`／`roll`／`upgrade`）、`gateGrace`

原則：

1. handler 只直接改真相狀態
2. 衍生索引只能跟著真相狀態更新，或由 reconcile 全量重建
3. cache 壞掉只准影響效能或重試，不准改變正確性
4. 值班時先分清是 `source drift` 還是 `derived drift`

## 快速判讀

1. 先看 `game_state_audit_total` 的 `result`
2. `mismatch` -> 先看索引 / 路由
3. `error` -> 先看 Redis / MySQL / timeout
4. 日誌 summary 的 `repairs=` 大於 0 -> 代表已自動修回一部分漂移，但根因還要追（`repair` 不是 `result` 標籤）
5. 判不出來 -> 回 [本機監控](./本機監控.md) 與 [問題排查筆記](./問題排查筆記.md)

## 先看哪個服務

### Central Audit

先看：

1. `central consistency audit detected drift` 的 log（Central 自己的稽核仍以服務名開頭；`samples` 是分類取樣後的全部樣本：issue 最多 3 筆、redis／db／transport／repair／repair_error 各最多 2 筆，共最多 13 筆，不再截斷成 5 筆）
2. `summary` 裡的 `issues / db_errors / redis_errors / repairs`
3. `usersByAccount` 是否指到不存在或錯位的 `playerID`
4. `usersByGate` 與 `usersByWorld` 是否跟 `users` 內的 `GateID / WorldID` 一致
5. Redis 的 `routing:{playerID}` 與 `account:{account}` 是否跟記憶體一致
6. MySQL `user` 表是否跟記憶體一致

常見原因：

- `user` 在記憶體刪了，但 Redis routing 還留著
- `account cache` 與 `user` 的 `WorldID` 不一致
- MySQL 還在舊資料，或寫回尚未完成
- `usersByGate` / `usersByWorld` 在 failover 後沒有跟著收斂

下一步：

- 先看 summary 的 `repairs=` 是否大於 0，代表 Redis 已自動修回
- 再比對 Central 內部索引
- 再看 Redis route / account cache 與 MySQL
- 最後才看 login / logout handler log

### Gate Audit

先看：

1. `consistency audit detected drift` 的 log（固定訊息，`service=gate`；`samples` 最多 3 筆，`audit.IssueSampleLimit`）
2. `sessionsByKey` 是否和 `sessionKeyByUser` 互相對得上
3. `pending_login / logged_in / pending_logout` 的 state 是否合理
4. `usersByWorld` 是否還殘留已刪除或錯 world 的 user
5. `sessionCentral` 是否還有不存在的 session key

常見原因：

- pending login 被清理掉，但索引沒有一起刪
- logout replay / duplicate delivery 後 session state 沒收斂
- user 已轉移 world，但 `usersByWorld` 沒更新

自動收斂：

- `Gate` 會在 `Update1m` 後重建 `usersByWorld`、`sessionKeyByUser` 與可安全重建的 session-derived 關聯。
- 若 audit 後仍有 `mismatch`，通常代表 source of truth 本身就不一致，或有外部依賴問題。

下一步：

- 先看 `sessionKeyByUser` 與 `sessionsByKey`
- 再看對應的 login / logout handler 是否有重送
- 若是 sweep 後問題，先查 `DeleteSessionByKey` / `DeleteUser`

### World Audit

先看：

1. `consistency audit detected drift` 的 log（固定訊息，`service=world`；`samples` 最多 3 筆）
2. `usersByGate` 是否和 `users` 內的 `GateID` 一致

常見原因：

- gate 斷線清理時，只刪了 user 但沒清 `usersByGate` 的對應項目

自動收斂：

- `World` 會在 `Update1m` 後重建 `usersByGate` 的可安全部分。
- 若 audit 後仍有 `mismatch`，先看是否是 cache source data 本身出錯。

下一步：

- 先看 `usersByGate`
- 最後才看 logout 的 handler 與 store log

## 值班順序

1. 看 `State Audit (5m)` 圖
2. 找出是 `Central`、`Gate` 還是 `World`
3. 看對應服務的 audit log
4. 比對那個服務的索引或 Redis 快取
5. 只有當 audit 真的指向資料面，才往下看 handler / TCP / DB

## 判讀原則

- `mismatch` 是邏輯不一致
- `error` 是 audit 自己在外部依賴上失敗，通常先看 Redis / MySQL / context timeout / 不可用
- summary 的 `repairs=` 代表 audit 已經把能安全修的 Redis 漂移收斂掉（只出現在日誌，不是 `result` 標籤），但仍然要追查根因
- audit 本身不是修復機制，它是發現漂移的哨兵

### 收斂 gate

  - 目前固定驗證 `Central / Gate / World` 的 derived-state reconcile 與 invariant 測試

### 修復（`repairs=`）例子

- Central 看到 `routing:{playerID}` 漂掉，但 `user` 與 MySQL 一致，audit 先把 Redis 修回，後面再追是哪個 logout / recovery 路徑寫歪
- Gate 看到 `sessionKeyByUser` 與 `sessionsByKey` 暫態不一致，但 sweep 後可自動重建，audit 先修回並計入 `repairs=`，再追 duplicate delivery
- World 看到 `usersByGate` 只差可安全重建的索引，audit 先修索引，再追 logout 寫回的來源
- 修復不是已解決；它只是表示系統已把能安全回正的部分先收斂

## 一句話

- `mismatch` -> 索引 / route
- `error` -> 依賴 / timeout
- summary `repairs=` -> 已修回，續追根因

## GameRecoveryMismatchDetected 判讀與處置

- 條件：`sum by (job) (increase(game_recovery_validation_total{result="recovery_mismatch"}[10m])) > 0`，warning。
- 意義：World 重啟或 Gate 重連後，World 把 Redis 內的玩家狀態還原，並請 Gate 驗證這些玩家的 session；Gate 回覆「沒有對應 session」（`AuthRecoveryMismatch`）時，World 會移除該還原玩家（`recovery validation removed stale player`）。一筆代表一位玩家被判定為殘留並移除，不代表資料遺失，但若 Gate 其實還有該玩家的連線，會讓在線玩家被誤踢。
- 判讀：
  1. 窗口是 10 分鐘，所以 Redis 或 Gate 中斷、World 重啟後這條會殘留最多 10 分鐘，不一定是持續不一致；先看 `increase(...[1m])` 是否仍在增加，已歸零就只是殘留訊號。
  2. 同時有 `GameProcessRestarted`、`GameServiceDown`、Redis 錯誤告警時，屬預期的重啟後清理，確認服務穩定即可。
  3. 先看 `game_recovery_validation_rejected_total{reason="queue_full"}` 同時間是否也在增加：Gate 背景佇列滿時會直接回 `RecoveryMismatch`，World 端因此跟著計 `recovery_mismatch`，結果碼上分不出來；有增量就是 Gate 過載（World 重啟後一次送來大量驗證，或 Gate 到 Redis 變慢），不是真的狀態不一致。
  4. 沒有任何重啟或中斷卻持續增加：查 Gate 的 `sessionKeyByUser` 與 World 的 `usersByGate` 是否漂移（見[狀態對帳流程](#先看哪個服務)的 Gate／World Audit），再對照 `GameRecoveryCorrectnessLow`（比例）與 `GameStateAuditMismatch`。
- 處置：看 World Info 日誌 `recovery validation removed stale player`（帶 `playerID`、`gateID`、`requestID`）與 Gate 對應時間的 session 日誌；確認被移除的玩家是否仍在線，在線則請其重新登入，並依 Audit 結果找出 session 與 World 索引漂移的來源。

## GameRecoveryValidationRejected 判讀與處置

- 條件：`sum by (job, instance, reason) (increase(game_recovery_validation_rejected_total[10m])) > 0`，warning。
- 意義：Gate 對 World 的恢復驗證會把碰 Redis 的查詢排進有界背景佇列。`reason="queue_full"`：佇列滿，Gate 不排隊等待，直接回 `RecoveryMismatch`，World 會依不一致處理（移除該還原玩家），所以 `GameRecoveryMismatchDetected` 常同時觸發；`reason="journal_skipped"`：驗證已完成，但結果日誌沒寫入 Redis（World 重送同一請求時無法回放，會重新驗證）。
- 判讀：先看 Gate 到 Redis 的延遲與錯誤（`GameRedisCommandErrors` 等 Redis 告警）、World 是否剛重啟（重啟後一次送來所有恢復玩家的驗證）。World 重啟的短暫尖峰屬預期；持續出現代表 Gate 或 Redis 長期過載。
- 處置：被誤移除的玩家請其重新登入；Gate 日誌的佇列滿訊息有取樣（每 10 秒一筆），次數以這個計數為準，不要用日誌筆數推估。
