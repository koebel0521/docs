## 排查工具箱

### 工具箱目的

`tools` 這一組是給值班、排障、回歸測試用的刀具箱，目標是：

- 快速確認服務是否正常
- 快速查單一帳號、session、路由
- 快速追一筆協定的送收鏈路
- 快速看 dead-letter、健康狀態、配置漂移
- 盡量少翻 log、少手查 Redis、少進服務內部

### 依賴健康總表

用 `tools/dephealth` 一次看 `ready`、service class、queue 深度：

```bash
cd tools/dephealth
go run . -json
```

用途：
- 值班先看整體健康，不先翻細節 log
- 快速分辨 `critical / core / peripheral` 哪一層在退化
- `readyFail > 0` 或 `status=degraded` 時，再往下查 queue / async failure

### 本機監控入口

若要先把 Grafana / Prometheus 接起來，再看值班面板：

- [本機監控](./本機監控.md)

用途：
- 先開 `本機監控`，再看 `Dependency Health`
- `dephealth` 先抓服務整體狀態
- `opsdiag` 再補路由查核與關鍵 metrics 摘要
- 要把監控、告警和一致性快照一起跑，直接用 `scripts/p0-daily-check.ps1 -Mode env`

### 狀態對帳入口

當 `game_state_audit_total` 出現 `mismatch` 或 `error`：

- 先進 [狀態對帳流程](./狀態對帳流程.md)
- 先看 `result`
- `mismatch` 看索引 / 路由
- `error` 看 Redis / MySQL / timeout
- `repair` 表示已修回一部分漂移，但根因還要追
- 要驗收斂 gate，直接用 `scripts/p0-daily-check.ps1 -Mode reconcile`

### 事故時間線

用 `scripts/incident-timeline.ps1` 把多份 log 依時間排序：

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/incident-timeline.ps1 -Path .\logs\central.log,.\logs\gate.log,.\logs\world.log
```

用途：
- 自動拉出 `route / session / alert / deploy` 時序
- 事故復盤先看時間線，再看單點 log
- `-Json` 可直接丟給別的分析工具

### 故障單模板

每次事故先用固定格式記錄：

- `docs/20-排障與監控/故障單模板.md`

用途：
- 先填人、時間、影響、處置、回滾、結論
- 後續再補 log、dashboard、metrics、commit
- 事故資訊先收斂成同一種格式，復盤比較快

### 配置熱重載

現在主服務會盯 config 檔：

- `Central / Gate / World / User / Lobby`
- config 檔變動後，會重新讀 `viper`
- `protocol_version_blacklist`、`feature.*`、`traffic_slice_*` 可熱更

用途：
- 改旗標或 canary 切流，不必全重啟
- 出事先回改 config，少跑一輪 deploy
- 若某值仍是 startup cache，要回頭看是不是還沒接到 reload callback

## 先看 SLO

值班先看少數主指標。其他 metrics 只用來定位根因，不當主畫面。

1. 登入成功率與延遲
   - 主看：`game_login_total{result="success" / "fail"}`、`game_login_duration_seconds`、`game_login_e2e_seconds`
   - 意義：登入鏈路有冇被 DB、鎖、World 路由拖慢
2. 登出成功率與排空
   - 意義：logout / drain 有冇卡住或落資料
3. 恢復校驗成功率
   - 主看：`game_recovery_validation_total`、`game_recovery_validation_replay_cache_total`
   - 意義：World 重啟後有冇收斂
4. 重連成功率
   - 主看：`tcp_reconnect_attempts_total`、`tcp_reconnect_total`
   - 意義：Gate / World / Central 斷線後有冇真恢復
5. 狀態對帳健康度
   - 主看：`game_state_audit_total`
   - 意義：長跑後有冇漂移、repair 有冇跟上

### SLO 告警分級

三層就夠：

1. `warning`
   - 有風險，但先看趨勢與 headroom。
   - 例：`game_login_failure_ratio_5m`、`game_handler_duration_p95_seconds`
2. `page`
   - 已經影響使用者或資料收斂，值班要直接看。
   - 例：`game_handler_duration_p99_seconds`
3. `ignore`
   - 只進 dashboard 或 debug，不做 alert。
   - 例：高基數 debug 值、單次排查用 counter

原則：
- `page` 要少，`warning` 要能收斂成 `page`，`ignore` 不進告警
- 先看 SLO，再看對應 log / trace / queue depth

### 日誌追蹤

所有跨服務訊息攜帶 `trace_id`，可一次搜尋整條鏈路：

```bash
# 追蹤單一請求在所有服務的日誌
grep 'trace_id=0x123abc' central.log gate.log world.log
```

### 協定記錄

各服務 debug server 現在提供 `/diag/protocol`：

- `GET /diag/protocol?traceID=...`
- `GET /diag/protocol?requestID=...`
- `GET /diag/protocol?limit=...` 直接看最近一批記錄
- 這個路由由 `pkg/debug` 直接掛載，不需要各 app 再手動註冊
- `pkg/debug` 的額外路由只用 `RegisterHandlerFunc` 掛到私有 mux

用途：
- 直接看同一條協定鏈的送收事件
- 每筆記錄會帶 `service / direction / msgID / requestID / traceID / status`
- 先從 Gate / Central / World 的邊界點查，再往下看 handler
- 記錄功能本身可開關：`protocol_record_enabled` 預設在 debug 設定開、prod 設定關；`DEBUG_PROTOCOL_RECORD` 可手動覆蓋
- 記錄容量與保留時間可由 `protocol_record_limit` / `protocol_record_ttl` 調整
- 啟動旗標 `-protocol-record=true|false` 會優先於 `DEBUG_PROTOCOL_RECORD`，再往下才看設定檔

### 跨服務合併查詢

用 `tools/protocoldiag` 一次抓 `Central / Gate / World` 的 `/diag/protocol` 並合併排序：

```bash
cd tools/protocoldiag
go run . -trace-id 123
go run . -request-id 456
```

用途：
- 一次看三邊同一條鏈路
- 輸出會包含每個服務的子結果與合併後的 `records`
- 若某個服務查詢失敗，仍會回其他服務成功抓到的記錄與該服務錯誤
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode protocoldiag -ProtocolDiagTraceID <id>`；`-ProtocolDiagRequestID` 也可單獨使用。

### Prometheus 關鍵指標

- `tcp_connections_active` — 只算 accepted connection；異常下降 = 網路問題
- `pkg/tcpclient` 的 rate limit 會從 `RemoteAddr()` 解析 host；若解析失敗，會退回原始地址，不會把異常來源壓成空字串共用桶。
- `tcp_send_queue_overflow_total` — 佇列溢出 = 對端處理不及
- `game_account_lock_total` — 帳號鎖定頻率
- `game_account_lock_wait_seconds` — 帳號鎖等待時間（p95 高 = 鎖競爭瓶頸）
- `game_login_db_query_seconds` — 登入 DB 查詢延遲（`find` / `save`）
- `game_handler_duration_seconds` — Handler 延遲分佈
- `game_heartbeat_timeout_total` — 心跳超時被踢次數
- `game_world_online_players` — 各 World 在線人數

其餘 metrics 主要用於交叉驗證與 debug，不作為第一優先 alert 入口。

### 告警抑制

現在用 Alertmanager 做降噪：

- 同一 `alertname + service` 先 group，再送通知
- `page` 壓 `warning`
- `P99` 壓 `P95`
- `overflow` 壓 `depth high`

位置：
- [monitoring/alertmanager/alertmanager.yml](../../monitoring/alertmanager/alertmanager.yml)
- [monitoring/compose.yml](../../monitoring/compose.yml)

用途：
- 減少同一故障連炸
- 先看根因，不先被次級告警淹沒

### 限流分級

現在把常見熱點拆成不同桶：

1. `login`
   - Gate 內用 account 粒度。
   - 連續重試同帳號會先進暫時鎖定。
2. `logout`
   - Gate 內用 playerID 粒度。
   - 避免同一玩家一直重送 logout 把 Central / World 打爆。
3. `GM`
   - Lobby admin API 走獨立 token bucket。
   - 免 admin token 外洩時把所有管理操作一起灌死。
4. `audit`
   - GM audit log 用獨立桶。
   - 讓審計輸出不跟 GM 請求共用同一條限流線。

用途：
- 一條線超，不代表全線一起死
- 不同入口各自退化，各自收斂

### 資源告警去重

現在資源告警用 `resource_class` 合併：

- `queue`
- `latency`
- `login`
- `logout`
- `recovery`
- `reconnect`
- `audit`

排查順序：
- 先看同一 `service` 的 group 裡面哪一類資源在叫
- 再看是哪個 panel 超線
- 最後再看單一 alertname

### 資料修復工具

用 `tools/datasurgeon` 修 Redis 內的 derived data：

```powershell
go run ./tools/datasurgeon -mode route -apply
go run ./tools/datasurgeon -mode playerstore -apply
go run ./tools/datasurgeon -mode deadletter -world-id 9 -apply -purge-malformed
```

用途：
- `route`：修 `central:routing:{playerID}` 與 `central:account:{account}` 的衍生狀態
- `playerstore`：重建 `world:{worldID}:players`
- `deadletter`：清掉 malformed payload，順手補 TTL

原則：
- 先 `-mode ...` 不加 `-apply` 看差異
- 只修 derived data，不碰 source of truth

`PJA-Database/cmd/datamigrate` 的 plan 解析會對未知欄位報錯，不再讓拼字錯誤的 migration plan 直接執行。

### 狀態修復 CLI

用 `tools/staterepair` 修 session / route / world drain / account lock：

```powershell
go run ./tools/staterepair -account alice -user-id 7 -world-id 9 -clear-route -clear-lock -clear-session -repair-session -backup-file staterepair.backup.json
go run ./tools/staterepair -rollback -backup-file staterepair.backup.json
```

用途：
- `clear-route`：清 `central:account:{account}` 與 `central:routing:{playerID}`
- `clear-lock`：清 `central:lock:account:{account}`
- `clear-session`：清 Gate 驗證 replay cache
- `repair-session`：請 Gate 重新收斂 derived session state
- `drain-world` / `undrain-world`：修 `central:world:drain`
- `rollback`：從 backup file 還原 Redis state
- `clear-route` 至少要帶 `-account` 或 `-user-id`
- `clear-lock` 一定要帶 `-account`
- `clear-session` 一定要帶 `-user-id`
- `drain-world` / `undrain-world` 一定要帶 `-world-id`
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode staterepair`；預設會先做 dry-run，明確帶 `-StateRepairRollback` 才會回滾。

原則：
- 先 `-dry-run` 看會做什麼
- 需要可回滾時，先指定 `-backup-file`
- 只修可重建的 derived state
- 不碰 source of truth
- `staterepair` 的 rollback backup 現在會對未知欄位與壞 entry type 報錯，不再靜默還原錯檔案
- `staterepair` 的 Gate repair 回應會檢查尾巴資料與欄位型別，不再把壞回應當成功
- `staterepair` 的 backup file 寫出時會自動建立父目錄，不必手動先 mkdir

### 熔斷演練

用 `scripts/circuit-breaker-drill.ps1` pause Redis / MySQL / World：

### 長跑壓測

用 `tools/loadtest` 跑 soak，抓長時間漂移：

```bash
cd tools/loadtest
go run . -gate 127.0.0.1:62001 -n 100 -duration 30m -soak -session 45s -cooldown 2s
```

觀察重點：
- `game_state_audit_total` 是否持續正常
- `tcp_reconnect_total` 與 `tcp_reconnect_attempts_total` 是否收斂
- `game_login_e2e_seconds` / `game_handler_duration_seconds` 是否越跑越高
- `tcp_send_queue_overflow_total` 是否出現
- `game_async_failure_total{queue="grant_item"}` 是否集中在 `retry_schedule_failed` / `dead_letter_failed`

### 值班一鍵診斷

用 `tools/opsdiag` 一次看 readiness、路由查核、關鍵 metrics 摘要；要固定落檔快照時改用 `tools/consistencysnapshot`，或直接走 `scripts/p0-daily-check.ps1 -Mode consistencysnapshot`：

```bash
cd tools/opsdiag
go run .
```

輸出會分成三段：
- `ready`：`Central / Gate / World / User` 的 `/ready`
- `route`：dev config 的 listen / dial port 是否一致；`user.lobby_url` 會先當 URL 解析，再和 `lobby.addr` 比對 port
- `metrics`：各服務 `/metrics` 的關鍵指標快照；若 queue 或 async failure 觸及 budget，會標 `degraded`

用途：
- 先判斷是服務沒起、路由漂了、還是 metrics 已開始異常
- 值班時先看這份，不用先跳進每個服務的 log

### 故障注入

World 可用 `FAULT_INJECT` 觸發本機故障：

```bash
set FAULT_INJECT=world.grant_item.on_grant
```

可用名稱：
- `world.grant_item.on_grant`
- `world.grant_item.ack`

用途：
- 驗證 async retry / dead-letter / ack fail metric
- 觀察 queue 是否能在故障後收斂
- 只建議在本機或測試環境開啟

### 故障演練常態化

用 `scripts/fault-drill.ps1` 固定演練 async fault：

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/fault-drill.ps1 -PlayerID 10001 -FaultName world.grant_item.on_grant
```

排查重點：
- `game_async_failure_total{service="world",queue="grant_item"}` 是否上升
- `retry_scheduled`、`ack_failed` 是否符合預期
- `world` 重啟後 `ready` 與 queue metric 是否回到正常

用途：
- 驗證故障不只是能注入，還能被 metrics 看見
- 固定打 `grant_item` 的 grant / ack 兩個點，檢查 retry、dead-letter、觀測鏈路
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode fault`

### 備援切換演練

### 流量回切演練

### 資料保留策略

目前先定這幾條：

1. `request journal`
- `Central` login / logout journal 的重試預算已收在各自 app 的 request journal 實作內。
   - 預設保留 2 分鐘。
2. `replay cache`
- `Gate` / `World` replay cache 的重試預算已收回各自 app / tool 本地 helper。
   - 預設保留 2 分鐘。
3. `dead-letter`
   - `grant item dead-letter` 進 Redis 後預設保留 7 天。
   - 逾期自動清，避免人工堆積。
4. `audit record`
   - `gm audit` 視為操作記錄，建議保留 30 天。
   - 實際清理交由外部 log / table retention。

原則：
- TTL 要跟用途綁定，不要散在各 service 裡各寫各的
- dead-letter 不可永久保存
- audit 可查，但不要無限長

## 常見問題

### 0. 玩家登入失敗（密碼錯誤）

**症狀**: 玩家送出登入後立即收到失敗回應（return code 13）

**排查步驟**:
1. 確認玩家使用的密碼與首次登入時一致
2. 在 Central 日誌搜尋 `"login failed"` + `"code=13"` 或 `"wrong password"`
3. 若懷疑帳號 hash 損壞，直接查 MySQL `users.password_hash` 欄位

**常見原因**:
- 玩家輸入密碼有誤（最常見）
- 舊帳號遷移測試時傳入密碼，但 `password_hash` 為空 → 空 hash 應允通過，若仍收到 code 13 代表欄位讀取有誤
- Redis 帳號快取中 `hash` 欄位值不正確（可清除 `account:<account>` key 強制回 MySQL）

### 1. 玩家登入卡住（pending_login 超時）

**症狀**: 玩家送出登入後無回應，45 秒後被清除

**排查步驟**:
1. 用 `trace_id` 追蹤訊息流向
2. 確認 Gate → Central 連線是否正常（`tcp_connections_active`，只算 accepted connection）
3. 確認 Central → World 連線是否正常
4. 檢查 Central 日誌是否有 MySQL 錯誤
5. 檢查是否觸發帳號鎖定（5 次/10 秒限制）

**常見原因**:
- Central 與 MySQL 連線中斷（斷路器開啟）
- World 未啟動或未連上 Central
- 帳號被速率限制鎖定（等 30 秒）

### 2. World 重啟後玩家狀態遺失

**症狀**: World 重啟後，玩家未恢復到線上狀態

**排查步驟**:
1. 確認 Redis 是否正常運行
2. 檢查 World 啟動日誌是否有 Redis 載入紀錄
3. 確認 Gate 是否在 30 秒寬限期內重新連上 World
4. 檢查 `game_recovery_validation_total` 指標

**常見原因**:
- Redis 斷路器開啟，無法讀取玩家狀態
- Gate 重連超過 30 秒寬限期，玩家被清除
- 玩家在 World 重啟期間已從 Gate 登出

### 3. 重複登入/重複操作

**症狀**: 同一操作被執行多次

**排查步驟**:
1. 檢查 `game_login_replay_cache_total{result="hit"}` — 去重快取是否生效
2. 確認 `request_id` 是否正確傳遞
3. 檢查 Central 的 request journal 快取狀態

**常見原因**:
- 客戶端重送但 request_id 不同（應相同）
- Replay cache TTL（2 分鐘）已過期
- 要重演這條情境，可直接用 `scripts/p0-daily-check.ps1 -Mode session`

### 4. Central 在登入途中斷線或重啟

**症狀**: 玩家登入卡住、收到 `service unavailable`，重試後才成功

**排查步驟**:
1. 檢查 Gate 日誌是否在 `pending_login` 期間失去與 Central 的連線
2. 檢查 `tcp_reconnect_attempts_total` / `tcp_reconnect_total`
3. 確認 Gate 是否已清理逾時的 `pending_login` session（TTL 45 秒）
4. 比對玩家端是否重新發起新請求，而不是重送舊上下文

**常見原因**:
- Central 程序重啟，Gate 對應 request 鏈路中斷
- Central 恢復後玩家重新登入，產生新的 `request_id` / `trace_id`
- 上游等待過久，誤以為可直接重放原請求
- 要驗 restart retry gate，可直接用 `scripts/p0-daily-check.ps1 -Mode failover`

### 5. 重複登入把舊連線踢下線

**症狀**: 同帳號新裝置登入後，舊連線收到重新登入或被迫下線

**排查步驟**:
1. 用 `trace_id` 比對兩條登入鏈路是否屬於不同請求
2. 檢查 Gate 是否有舊 session 被清理或轉成失效
3. 確認玩家端收到的 return code 是否為重新登入相關語意
4. 若是測試環境，確認是否有人共用同一組帳號

**常見原因**:
- 同帳號真的在多端同時登入
- 測試腳本重複使用固定帳號
- 本地 state 過舊，玩家端誤以為自己仍在線
- 要重演這條情境，可直接用 `scripts/p0-daily-check.ps1 -Mode session`

### 6. Gate 與 World 斷線

**症狀**: 玩家大量離線

**排查步驟**:
1. 檢查 `tcp_reconnect_attempts_total` — 重連嘗試次數
2. 確認網路連通性
3. 檢查 World 是否因 OOM 或 panic 崩潰
4. 確認是否在 30 秒內恢復（短期 vs 長期策略）

**處理策略**:
- < 30 秒：自動恢復，標記 unavailable 後恢復
- \> 30 秒：清理玩家，通知 Central 清除路由

### 7. Prometheus 抓不到 metrics

**症狀**: Grafana dashboard 沒資料，Prometheus `up` 為 0

**排查步驟**:
1. 確認服務 debug server 已啟動並開出 `:6060~:6063`
2. 檢查服務是否只允許 loopback，導致 container 抓不到 `/metrics`
3. 若 Prometheus 跑在 Docker container，確認有設定 `DEBUG_ALLOW_CIDRS`
4. 執行 `scripts/monitoring-smoke.ps1` 驗證 Grafana / Prometheus provisioning

**常見原因**:
- debug server 預設只允許 loopback
- Prometheus 容器網段未列入 `DEBUG_ALLOW_CIDRS`
- monitoring compose 沒有成功載入 dashboard 或 datasource

### 8. Docker 環境啟動失敗

**排查步驟**:
1. 確認 MySQL 與 Redis 已就緒（compose.deps.yml 先啟動）
2. 檢查 config 掛載路徑是否正確
3. 確認健康檢查通過（`wget /ready`）
4. 查看 `docker logs <container>` 確認錯誤訊息

### 10. 登入延遲高但失敗率正常

**症狀**: 玩家反映登入慢，但 `game_login_total{result="fail"}` 無明顯上升

**排查步驟**:
1. 查看 `game_account_lock_wait_seconds` p95 — 若偏高代表帳號鎖競爭（同帳號並發登入）
2. 查看 `game_login_db_query_seconds{operation="find"}` p95 — MySQL FindByAccount 慢
3. 查看 `game_login_db_query_seconds{operation="save"}` p95 — 新帳號 Save 慢
4. 對照 `game_handler_duration_seconds{handler="on_login_gate_to_central"}` 確認是哪段佔多數

**常見原因**:
- MySQL 負載高，查詢排隊（DB query 時間高）
- 同帳號短時間大量登入請求，鎖競爭嚴重（lock wait 時間高）

### 11. CI 整合測試失敗

**排查步驟**:
1. 整合測試啟動真實程序，確認 port 未被占用
2. 檢查是否有 race condition（`-race` flag）
3. 確認 testenv 是否正確清理上次的程序

### 12. Gate rolling deploy 後仍有玩家強制斷線

**症狀**: Gate 重啟後日誌出現 `"drain timeout reached, force-disconnecting remaining players"`

**排查步驟**:
1. 查看 `count` 欄位確認殘留人數與 `timeout` 欄位
2. 若殘留玩家偏多，考慮拉長 `drain_timeout`（在 gate.yaml 設定）
3. 確認 Lobby 服務探索是否已將此 Gate 標記為不可用（TTL 25s），避免新玩家繼續連入

**常見原因**:
- Gate 預設 `30s` 排空時間不夠長，部分玩家長連線沒有在期限內下線
- 玩家 heartbeat 仍正常，但業務邏輯端沒有登出流程觸發
- `drain_timeout` 設成壞值時會被忽略，Gate 仍用預設 30s

### 13. OTel Span 在 Jaeger 中找不到

**症狀**: Gate/Central/World 的 Span 各自獨立，不在同一條 Trace 下

**排查步驟**:
1. 確認 `otel.exporter` 設定為 `otlp`，且 `otel.endpoint` 正確指向 Collector
2. 檢查服務啟動日誌 — `"tracing init failed"` 表示 OTel 初始化失敗（span 不輸出但服務仍運作）
3. 確認三個服務的 `trace_id` 欄位值相同（跨服務同一條鏈路應共用）
4. 在 Jaeger UI 以 `trace_id` 的十六進位值搜尋（uint64 → hex）

**常見原因**:
- OTLP Collector 未啟動或 endpoint 設定有誤
- `otel.exporter` 未設定，預設為空字串（noop，不輸出）
- 服務間 `trace_id` 傳遞中斷（應由 Gate 建立後透傳，不可在中間重建）

### 14. 服務發現或路由漂移

**症狀**: 新玩家被派到維護中的 World、登出打到舊路由，或 Central / Gate / World 對同一資源路由不一致。

**排查步驟**:
1. 確認 `central:world:drain` 是否正確寫入 Redis
2. 檢查 Central 是否已刷新 `drainedWorlds`
3. 檢查 `routing:{playerID}` 與 `account:{account}` 是否仍對應 memory
4. 確認 Gate / World 的 `ConnectInfo` 是否有及時清除 unavailable 標記
5. 若是 Lobby 探測異常，先看 Redis TTL / heartbeat 是否失效

**常見原因**:
- Lobby 已把 World 標成維護，但 Central 還沒刷新 Redis drain set
- World / Gate 重連後沒送 `ConnectInfo`，導致 unavailable 標記殘留
- routing key TTL 沒 refresh，或舊節點殘留舊路由

**處理策略**:
- Redis drain set 先修，Central 再刷新
- reconnect 後先清 unavailable，再跑後續 recovery / cleanup
- 以 audit / reconcile 檢查 routing key 與 memory 是否一致
- 若 Redis routing/account key 出現壞值，Central 會直接忽略，不會回填成 `gate=0` / `world=0` 的假路由
- account cache 的 `uid` / `wid` / `hash` 壞值也會直接丟掉，不會當成 returning player 的真資料

### 15. 協定版本不相容

**症狀**: 登入、登出或恢復校驗直接回 `AuthProtocolMismatch`。

**排查步驟**:
1. 確認 Gate / World / Central / User 是否都在同一版
2. 檢查 `pkg/msg` 的 `ProtocolVersionCurrent`
3. 檢查 `protocol_version_blacklist` 是否把目前版本封掉
4. 確認客戶端或測試工具沒有送出錯誤的 `protocol_version`
5. 若正在 rolling upgrade，先看是否有舊節點還在跑舊 schema

**常見原因**:
- 舊節點尚未升級
- 客戶端或測試工具使用了不支援版本
- 版本已被黑名單先行封鎖，屬於預期拒絕
- 某段 reply schema 已改，但另一段還沒跟上
- 要驗 protocol 相容 gate，可直接用 `scripts/p0-daily-check.ps1 -Mode protocol`

### 16. 錯誤碼語意不一致

**症狀**: HTTP、RPC、queue 對同一類失敗回應完全不同。

**排查步驟**:
1. 先看 `pkg/errcode` 的 canonical class
2. 確認 HTTP status 是否由 `HTTPStatusFromAuthResultCode` 產生
3. 確認 queue / RPC 是否只看 `ack / retry / drop`
4. 確認 app 沒有自己硬編新語意

**常見原因**:
- 某條 handler 自己選了不同 HTTP status
- 某個 queue 失敗碼沒有接到 retry policy
- 舊 code 還在直接 compare 數字，不看 canonical class

### 17. 重試預算耗盡

**症狀**: `game_async_failure_total{queue="grant_item",outcome="retry_budget_exceeded"}` 上升，或命令很快進 dead-letter。

**排查步驟**:
1. 看 `RequestedAt` 是否過舊
2. 看 `Attempts` 是否已到上限
3. 看 `grant item queue` 是否長時間卡在下游 `onGrant` 錯誤
4. 若是 transient 錯，先修下游，不要盲目放大 retry window

**常見原因**:
- 下游服務長時間不可用
- command 在 queue 裡堆太久
- 重試次數已達 5 次
- 新舊 schema 混跑導致一直失敗，最後被 budget 擋下

### 18. 訊息版本鎖

`protocol_version_lock` 會把可接受的訊息版本鎖成單一值：

- 版本不等於 lock 值，直接回 `AuthProtocolMismatch`
- `protocol_version_blacklist` 仍會再擋已知壞版本
- `pkg/configwatch` 熱重載後，lock 會跟著更新

用途：
- rolling / canary 時先鎖版本
- 想先封死某次 schema 變更時，用 lock 比黑名單更直觀
- 出事可先把 lock 改回舊值，不必全重啟

### 死信再處理

用 `tools/deadletterreplay` 挑選 dead-letter 再送回 queue：

```bash
cd tools/deadletterreplay
go run . -world-id 9 -operation-id grant-op-1 -retryable -replay
```

用途：
- 手動挑選特定 `world / user / operationID`
- 先 `-dry-run` 看選到哪批，再決定 replay 或 discard
- `-retryable` 只列還在重試預算內的樣本
- 若 world capability 不在，先修 world，再重送
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode deadletterreplay`

### 容量預測

用 `tools/capacityforecast` 讀 `tools/loadtest` baseline：

```bash
cd tools/capacityforecast
go run . -baseline ..\..\loadtest-baseline.json
```

若 baseline 的 `sessions=0`，`capacityforecast` 會回 `reason=no_data`，代表資料不足，不可用於容量判讀。

用途：
- 用 baseline p95 / queue depth 推估可承載玩家數
- 先知道 headroom，避免等 queue 高才加機
- 若 `estimatedPlayers` 太低，先看 latency 還是 queue 壓力
- `capacityforecast` baseline 解析會對未知欄位與負值報錯，不再把壞 JSON 算進容量預測

## 日誌關鍵字速查

| 關鍵字 | 含義 |
|--------|------|
| `login failed` | 登入失敗，檢查 `code` 欄位 |
| `DB error` | MySQL 連線或查詢失敗 |
| `circuit breaker open` | 斷路器開啟，服務降級中 |
| `account locked` | 帳號被速率限制鎖定 |
| `session expired` | Session TTL 到期被清除 |
| `recovery validation` | World 重啟後的玩家校驗 |
| `send queue overflow` | TCP 發送佇列滿，強制斷線 |
| `reconnect` | ServiceClient 正在重連 |
| `heartbeat timeout` | 玩家心跳超時被踢，檢查網路品質 |
| `gamestore: failed to save player data on logout` | 正常登出時 DB 寫入失敗，進度可能遺失 |
| `per-IP connection limit exceeded` | 單一 IP 超過連線上限，被拒絕 |
| `wrong password` / `code=13` | 密碼驗證失敗，Central bcrypt 比對不符 |
| `stopped accepting new connections` | Gate StopAccepting 已執行，不再接受新連線 |
| `drain timeout reached` | Gate 排空逾時，剩餘玩家被強制斷線 |
| `drain complete` | Gate 排空完成，所有玩家已正常離線 |
| `tracing init failed` | OTel 初始化失敗，span 不輸出，服務仍正常運作 |

## 查詢降級

- Central audit record 讀取現在有 DB -> Redis cache fallback。
- 若看到 `central audit query degraded to cache`，代表 DB 短暫失敗，但快取命中，讀路徑還活著。
- 若快取也失敗，會回原本 DB error；先查 MySQL、再查 Redis、再看 cache key 是否過期。
- Redis routing / account 壞欄位時，Central audit 會直接報 invalid，不再把 `0` 當正常值。
- Central audit 做 Redis 修復時，壞 `gate/world` 也會算 drift，不會因為 memory 剛好是 `0` 就漏修。
- `configaudit` 遇到 Prometheus `scrape_configs` 結構壞掉會直接報錯，不再默默跳過。
- `opsdiag` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode opsdiag`；預設會維持 `--fail-on-degraded`
- `dephealth` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- `datasurgeon` apply 模式會刪掉 malformed `player:` / `world:*:players` key，不再讓壞 key 永久殘留。
- `datasurgeon` 讀 `player:` 狀態會對未知欄位報錯，不再把拼字錯誤的狀態當真。
- `datasurgeon` deadletter apply 模式會刪掉 malformed `gm:grant_item:deadletter:*` key，不再讓壞隊列殘留。
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode datasurgeon -DataSurgeonMode <mode>`；預設只做觀察，`-DataSurgeonApply` 才會真的修 Redis。
- `pkg/grantitem` 讀 GM 命令會對未知欄位與尾巴資料報錯，不再把壞 deadletter 當真命令。
- `pkg/playerstoreredis` 讀玩家狀態會對未知欄位報錯，不再把壞 JSON 當真玩家資料。
- `pkg/requestjournalredis` 讀 Redis journal 會對未知欄位與尾巴資料報錯，不再把壞 journal 當成 miss。
- `pkg/msg` 的 `AuditSnapshotRequest/Response` 解析會對未知欄位與尾巴資料報錯，不再吞掉快照拼字錯誤。
- `cmd/user` 的 lobby client 會對 non-200 或壞 `/gates` 回應直接放棄，不再拿錯 gate。
- `tools/consistencysnapshot` 會對 Prometheus 非 200、未知欄位與尾巴資料報錯，不再把壞快照寫出去。
- `tools/opsdiag` 的 `/ready` 解析會對未知欄位、尾巴資料與空 checks 報錯，不再把壞 ready 當正常。
- `tools/consistencysnapshot` 會對 endpoint down 與 Prometheus 非 200 / 壞 JSON 報錯，不再把壞快照寫出去；統一入口是 `scripts/p0-daily-check.ps1 -Mode consistencysnapshot`；`-output` 指定巢狀路徑時會自動建立父目錄
- `tools/playersnapshot` 會對 gate diag 與 ready 壞回應報錯，不再把壞快照當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- `tools/supportdiag` 會對 session 與 ready 壞回應報錯，不再把壞客服資料當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- `tools/configdrift` 的 `mustGetString` 會對 nil config 回錯，不再 panic。
- `configaudit` 會把 Grafana datasource 的 `url` 型別錯誤直接報成 invalid，不再當空值處理。
- Gate central ring 遇到 `ConnectInfo.ID == 0` 時會忽略，不再把 `0` 放進 hash ring。
- `deadletterreplay` 遇到 malformed deadletter key 會直接報錯，不再默默跳過。
- `deadletterreplay` 遇到 malformed deadletter payload 也會直接報錯，不再把壞 payload 吞掉。
- Lobby admin 的 grant-item dead-letter 列表 / replay / discard 遇到 malformed payload 會直接報錯。
- `playersnapshot` 與 `supportdiag` 讀 deadletter 時，遇到 malformed payload 會直接報錯，不再靜默跳過。

## 慢查追蹤

- `game_audit_record_lookup_seconds` 會記 Central audit record lookup 的 DB / cache 延遲。
- `central audit query slow` 代表該次 lookup 超過 `mysql.audit_record_slow_ms` 閾值，先看 MySQL 查詢、再看 Redis fallback。
- 若 p95 變差但沒有 error，通常是慢查不是故障；先查索引、鎖競爭、以及 cache 命中率。

## 資源自動回收

- `game_resource_recycle_total` 會記週期性清理的 stale 內存資源。
- Central 會清 `worldWarmupUntil`；Gate 會清過期 `login_attempt`、`logout_attempt`、`world_unavailable`；World 會清過期 `gate_unavailable`。
- 若這個數字持續長大，代表 ephemeral state 沒有按期回收，先看 1m sweep 有沒有跑。

## 回歸樣本庫

- `tools/regressionsample -list` 可列可重放樣本。
- `tools/regressionsample -validate` 可驗證樣本 JSON 是否可供 `tools/flowreplay` 使用。
- 每次事故先留一份 login / logout / recovery / GM 樣本，日後用 `flowreplay` 重打。
- `regressionsample` 會對未知欄位報錯，不再讓拼字錯誤樣本混進回歸庫。
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode regressionsample`；預設先做 `validate`，要列出或重放單一樣本再加對應旗標。

## 告警自愈

- `scripts/alert-selfheal.ps1` 是告警 warning 的輕修復入口。
- `route_drift` / `stale_index` 會清路由與鎖衍生資料；`session_reconcile` 會請 Gate 收斂 session；`world_drain_stale` 會撤掉過期 drain 標記。
- 先 dry-run，看動作對不對，再真的 apply。
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode alertselfheal -SelfHealAlertName <name>`；它會把 `AlertName / Redis / Gate / account / user / world` 參數原樣轉給 `alert-selfheal.ps1`。

## 變更審批

- `scripts/change-approval.ps1` 會寫 release/config/schema 審批 stamp。
- `scripts/docker-release.sh` 發版前會檢查 stamp；缺 stamp 或 target 不符就直接擋。
- release 前先看 checklist，再看回退點，再看監控。

## 服務分級

- `tools/dephealth` 把服務分成 `critical / core / peripheral`。
- `central`、`gate`、`world` 是 `critical`；`user` 是 `core`；其他暫歸 `peripheral`。
- 告警、限流、看板先盯 `critical`，`core` 次之，`peripheral` 再後。

## 冷資料搬遷

- `tools/coldstorage` 會把 `central:audit:record:*`、`gm:grant_item:deadletter:*`、`fault:archive:*` 匯出成 JSONL。
- `-purge` 會在匯出後刪 Redis 熱 key。
- 先 `-dry-run` 看 manifest，再決定要不要真搬。
- 要走統一入口時，直接用 `scripts/p0-daily-check.ps1 -Mode coldstorage`；預設只做 dry-run，看 manifest 不動資料。
