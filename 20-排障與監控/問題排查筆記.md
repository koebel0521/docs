## 排查工具箱

### 工具箱目的

`tools` 這一組是給值班、排障、回歸測試用的刀具箱，目標是：

- 快速確認服務是否正常
- 快速查單一帳號、session、路由
- 快速追一筆協定的送收鏈路
- 快速看 dead-letter、健康狀態、配置漂移
- 盡量少翻 log、少手查 Redis、少進服務內部

### 依賴健康總表

用 `tools/private/dephealth` 一次看 `ready`、service class、queue 深度：

```bash
go run ./tools/private/pja dephealth -json
```

用途：
- 值班先看整體健康，不先翻細節 log
- 快速分辨 `critical / core / peripheral` 哪一層在退化
- `readyFail > 0` 或 `status=degraded` 時，再往下查 queue / async failure

### 本機監控入口

若要先把 Grafana / Prometheus 接起來，再看值班面板：

- [本機監控](./本機監控.md)

用途：
- 先開 `本機監控`，再看 `Dependency Health`
- `dephealth` 先抓服務整體狀態
- `opsdiag` 再補路由查核與關鍵 metrics 摘要
- 要把監控、告警和一致性快照一起跑，直接用 `scripts/private/p0-daily-check.ps1 -Mode env`

### 狀態對帳入口

當 `game_state_audit_total` 出現 `mismatch` 或 `error`：

- 先進 [狀態對帳流程](./狀態對帳流程.md)
- 先看 `result`
- `mismatch` 看索引 / 路由
- `error` 看 Redis / MySQL / timeout
- 日誌 summary 的 `repairs=` 大於 0 表示已修回一部分漂移，但根因還要追（`repair` 不是 `game_state_audit_total` 的 `result` 標籤）
- 要驗收斂 gate，直接用 `scripts/private/p0-daily-check.ps1 -Mode reconcile`

### 事故時間線

用 `scripts/incident-timeline.ps1` 把多份 log 依時間排序：

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/incident-timeline.ps1 -Path .\logs\central.log,.\logs\gate.log,.\logs\world.log
```

用途：
- 自動拉出 `route / session / alert / deploy` 時序
- 事故復盤先看時間線，再看單點 log
- `-Json` 可直接丟給別的分析工具
- 支援服務預設的 JSON 日誌（取 `time` 欄位，依 `message` 分類）與 text 日誌，時間戳帶時區位移時依位移換算，分析機與日誌產生機時區不同也不會排錯序
- 日誌格式無法辨識（一行時間都取不到）時以非 0 結束並提示，不再印「no incident events found」造成「這段時間沒有事件」的誤判

### 故障單模板

每次事故先用固定格式記錄：

- `docs/20-排障與監控/故障單模板.md`

用途：
- 先填人、時間、影響、處置、回滾、結論
- 後續再補 log、dashboard、metrics、commit
- 事故資訊先收斂成同一種格式，復盤比較快

### 配置熱重載

現在主服務會盯 config 檔：

- 所有走 `startup.InitializeRuntime` 的服務（Central、Gate、World、Chat、Lobby、Record、User）
- config 檔變動後，會重新讀 `viper`
- 可熱更的只有白名單，由各服務經 `startup.WithHotReload(HotReload{Keys, Apply})` 宣告（`Keys` 是完整設定鍵，鍵本身或其巢狀子鍵才算，**不做前綴比對**，拼錯的鍵一律歸需重啟）：共用的 `protocol_record_*` 鍵（由 startup 共用處理，不必各服務宣告；`protocol-record` 旗標不經 viper、不熱更）、Central 的 `traffic_slice_percent`／`traffic_slice_world_id`、Lobby 的 `admin_token`／`ops_token`／`gm_token`；`feature.central.state_auditor` 與其他鍵只在啟動讀，改了要重啟
- 日誌有三種，判讀不同：
  - Info `config hot reload applied`（`keys`）：`keys` 只列這次**真的套用**的鍵；不再只看鍵名前綴就當作生效
  - Warn `config hot reload not applied`（`keys`、`err`）：服務宣告可熱更的鍵套用失敗（值無效、token 驗證失敗，或 Lobby 啟動時沒有 token、事後才補上——需重啟才有 admin 端點）；修正值或重啟，不要當作已生效
  - Warn `config change requires restart, not applied`（`keys`）：改了不可熱更的鍵，看到它就重啟
  - Warn `config change shadowed by environment variable or command-line flag, not applied`（`keys`）：改的鍵被同名環境變數或旗標遮蔽
  - Warn `configwatch: failed to reload config`（`path`、`err`）：重試後仍讀檔或驗證失敗（YAML 錯、`id` 不合法、前導零整數等），整份不套用、沿用舊設定
- 結果計數（第十二輪 O-L6）：`game_config_reload_total{result="applied"|"rejected"|"restart_required"|"shadowed"}`，監看開始時先建為 0；`rejected` 含套用回錯、`HotReload.Apply` panic（`startup.applyHotReload` 接住並轉成套用錯誤，baseline 不前進；以前只被 configwatch 接住、不計 `rejected`）與 configwatch 讀檔／驗證失敗。15 分鐘內有 `rejected` 觸發 `GameConfigReloadRejected`（warning），多實例不必逐台翻日誌
- 啟動與熱重載共用 `ReadConfigPair` 讀檔與 `bootstrap.ValidateLoaded` 驗證（第十二輪），熱重載也嚴格解析 `id`；設定檔未加引號的前導零整數（`010`、`09`）讀檔即拒絕，見[設定注入與熱更新](../00-導讀/設定注入與熱更新.md)
- Lobby token 熱重載與啟動共用 `services.NewTokenValidator`：admin 綁非 loopback 時，`-local-stack-only` 結尾的公開開發 token 熱重載同樣被拒（`not applied`）；`allow_dev_tokens` 固定取啟動值，熱重載改它不生效
- Central 在 `initStorage` 期間收到的 `traffic_slice_*` 重載，會在 App 建好後套用，不再被啟動時的舊值蓋掉；這段期間不合法的值直接回錯（記 `not applied`／`rejected`），不覆寫已存的上一份合法重載，也不會關掉啟動設定的切片（第十二輪 V-L1）
- 資料設定（dataconfig）watcher 啟動時若 `current.json` 損壞或排程時間有誤，會立即走 reload 路徑、記 failed 計量（`data_config_reload_total{result="failed"}`）並呼叫 `onError`，不必等到下一次檔案事件才發現
- 協定檔案記錄（`protocol_record_file_*`）參數沒變時沿用同一個記錄器，熱重載不會每次關檔重開
- 正式 compose 掛整個設定目錄；改完確認出現 `config hot reload applied` 且 `keys` 含你改的鍵，沒有就看有沒有 `not applied`／`requires restart`，再決定修值或重啟

用途：
- 改旗標或 canary 切流，不必全重啟
- 出事先回改 config，少跑一輪 deploy
- 若某值仍是 startup cache，要回頭看是不是還沒接到 reload callback

## 先看 SLO

值班先看少數主指標。其他 metrics 只用來定位根因，不當主畫面。

1. 登入成功率與延遲
   - 主看：`game_login_total{result="success"}` 與失敗值（`busy` 或 `errcode.MetricOutcomeFromAuthResultCode` 的值，如 `server_fail`；Gate 本地限流等就地拒絕不在此，改看 `game_login_rejected_total{reason}`；Gate 回 `service_unavailable` 的原因拆解看 `game_login_unavailable_total{reason}`，持續時 `GameLoginGateUnavailable` 會響）、`game_login_duration_seconds`（毫秒級桶，與 `game_login_e2e_seconds` 一致）、`game_login_e2e_seconds`
   - 意義：登入鏈路有冇被 DB、鎖、World 路由拖慢
2. 登出成功率與排空
   - 意義：logout / drain 有冇卡住或落資料
3. 恢復校驗成功率
   - 主看：`game_recovery_validation_total`、`game_recovery_validation_replay_cache_total`
   - 意義：World 重啟後有冇收斂
4. 重連成功率
   - 主看：`tcp_reconnect_attempts_total`、`tcp_reconnect_total`
   - 意義：Gate / World / Central 斷線後有冇真恢復
5. 狀態對帳健康度
   - 主看：`game_state_audit_total`
   - 意義：長跑後有冇漂移、repair 有冇跟上

### SLO 告警分級

三層就夠：

1. `warning`
   - 有風險，但先看趨勢與 headroom。
   - 例：`game_login_failure_ratio_5m`、`game_handler_duration_p95_seconds`
2. `page`
   - 已經影響使用者或資料收斂，值班要直接看。
   - 例：`game_handler_duration_p99_seconds`
3. `ignore`
   - 只進 dashboard 或 debug，不做 alert。
   - 例：高基數 debug 值、單次排查用 counter

原則：
- `page` 要少，`warning` 要能收斂成 `page`，`ignore` 不進告警
- 先看 SLO，再看對應 log / trace / queue depth

### 日誌追蹤

遊戲鏈路的日誌欄位是 `gameTraceID`（十進位 int64，由 ctx 自動附上）；請求編號欄位是 `requestID`。`trace_id`／`span_id` 是 OTel span 的欄位（32 位 hex），只在有 span 時才出現，正式環境 `otel.exporter` 為空時根本沒有。預設日誌格式是 JSON，可一次搜尋整條鏈路：

```bash
# 追蹤單一請求在所有服務的日誌
grep '"gameTraceID":123456' central.log gate.log world.log
# 或用 jq 過濾
jq -c 'select(.gameTraceID==123456)' central.log gate.log world.log
# 以請求編號查
grep '"requestID":<id>[,}]' central.log gate.log world.log   # requestID 是數字，JSON 沒有引號；也可用 jq 'select(.requestID==<id>)'
```

已知限制：`gameTraceID` 是行程內序號，多個 Gate 實例同一毫秒可能撞號，跨實例查詢要搭配 `requestID` 或時間範圍過濾（見[日誌規範](../30-部署與開發/日誌規範.md)）。

### 協定記錄

各服務 debug server 現在提供 `/diag/protocol`：

- `GET /diag/protocol?traceID=...`
- `GET /diag/protocol?requestID=...`
- `GET /diag/protocol?limit=...` 直接看最近一批記錄
- 這個路由由 `pkg/debug` 直接掛載，不需要各 app 再手動註冊
- `pkg/debug` 的額外路由以 `*debug.Server` 的 `HandleProtectedFunc`（需 `DEBUG_PPROF_BASIC_AUTH`）掛到私有 mux；不提供無驗證的 `HandleFunc`，新路由一律走受保護版本

用途：
- 直接看同一條協定鏈的送收事件
- 每筆記錄會帶 `service / direction / msgID / requestID / traceID / status`
- 先從 Gate / Central / World 的邊界點查，再往下看 handler
- 記錄功能本身可開關：`protocol_record_enabled` 預設在 debug 設定開、prod 設定關；`DEBUG_PROTOCOL_RECORD` 可手動覆蓋（接受 `true/false/on/off/yes/no`；無法解析記 Warn 並退回設定值）
- 記錄容量與保留時間可由 `protocol_record_limit`（上限 131072，超過啟動失敗；負值也在啟動與熱重載被拒，不再靜默換成預設值）/ `protocol_record_ttl` 調整；落檔另有每服務每小時 256 MiB 的單檔上限（`defaultMaxFileBytes`，不可設定），寫滿後記錄全部丟棄直到下一個小時，追玩家問題時若該小時後段沒有封包，先查日誌有無 `protocol file size cap reached`，不要誤判為玩家沒送封包
- 啟動旗標 `-protocol-record=true|false` 會優先於 `DEBUG_PROTOCOL_RECORD`，再往下才看設定檔的 `protocol_record_enabled`；旗標不經 viper，設定檔寫 `protocol-record` 鍵沒有作用

### 跨服務合併查詢

用 `tools/private/protocoldiag` 一次抓 `Central / Gate / World` 的 `/diag/protocol` 並合併排序：

```bash
go run ./tools/private/pja protocoldiag -trace-id 123
go run ./tools/private/pja protocoldiag -request-id 456
```

用途：
- 一次看三邊同一條鏈路
- 輸出會包含每個服務的子結果與合併後的 `records`
- 若某個服務查詢失敗，仍會回其他服務成功抓到的記錄與該服務錯誤

### 健康檢查端點

| 服務 | 端點 | 用途 |
|------|------|------|
| Central | `http://localhost:6060/ready` | DB ping 確認 |
| Gate | `http://localhost:6061/ready` | 服務就緒 |
| World | `http://localhost:6062/ready` | 服務就緒 |
| User | `http://localhost:6063/ready` | 服務就緒 |
| Lobby | `http://localhost:6064/ready` | 服務就緒（含 `time_sync`） |
| Record | `http://localhost:6065/ready` | 服務就緒 |
| Chat | `http://localhost:6066/ready` | 服務就緒（含 `time_sync`） |

TCP 伺服器（Gate 玩家端、Central、World、Chat）會註冊 `tcp_listen_<名稱>` 檢查：尚未監聽成功、監聽失敗（例如埠被占用）或已停止接受連線時 `/ready` 回 503。這個檢查在 `tcpserver.New` 時就登記，啟動自檢會等第一次監聽有結果（最多 `ReadyCheckTimeout` 3 秒），**監聽失敗時啟動自檢失敗、行程以非 0 結束**交給 restart policy（第十二輪 DP-L1；以前檢查要等監聽有結果才登記，自檢先跑完就通過，留下不收連線的殭屍容器），日誌看啟動自檢的錯誤含 `tcp_listen_<名稱>`。啟動後才發生的 accept 迴圈 panic（第十輪）行程不會退出：Error `panic recovered`（`msg="tcpserver accept loop"`，`game_panic_recovered_total` 同標籤遞增）、listener 關閉、`tcp_listen_*` 轉為不就緒，新連線直接被拒；這是需要重啟並查堆疊的訊號。`/ready` 的各項檢查並行執行、各自上限 3 秒（`ReadyCheckTimeout`），整體耗時約等於最慢一項，不會因多項同時無回應而超過 Docker HEALTHCHECK 的 5 秒；單項檢查 panic 會轉成該項的錯誤，不會讓整個 `/ready` 失敗得沒有原因。檢查回傳的錯誤訊息為空時 body 填 `unknown error`。`/ready` 結果由成功轉為失敗時記一行 Warn `ready check failed`（`failed` 為失敗項目摘要），恢復時記 Info `ready check recovered`；容器 healthcheck 丟掉輸出，事後查 readiness 抖動看這兩行。`opsdiag`、`dephealth` 等工具讀到 503 時會解碼 body，錯誤顯示為 `503 Service Unavailable: status=fail <失敗的檢查項目>`；其他非 200 狀態仍帶 body 開頭。

**啟動閘門（第十輪）**：`startup.InitializeObservability` 在 debug 埠開始監聽**之前**先登記一個 runtime-only 的 `startup` 檢查（`debug.Server.BeginStartup`），放行前 `/ready` 回 503，body 的失敗檢查是 `startup: starting`。以前啟動中（連線、還原玩家、載入設定）尚未登記任何檢查時 `/ready` 會回 200，compose healthcheck 與 `ci-deploy.sh` 因而誤判就緒。放行時機依服務而異：

- Central、Gate、Chat、Record、World：啟動自檢（`selfCheck`，組合根傳 `debugSrv.CheckStartupAndMarkStarted`）通過才放行。World 第十二輪起也走這條：`Start` 完成（還原玩家、載入設定、重建候選、開始監聽）後跑自檢（含 MySQL、Redis、`data_config`、`tcp_listen_*`），通過才 `MarkStarted` 並開始向 Lobby 公告，失敗即走關機流程、以非 0 結束（以前 `Start` 完成就放行）。
- Lobby：Redis 檢查與 `time_sync` 都登記完、`httpx.ServeLimited` 開始前放行。放行當下 HTTP 埠其實還沒綁上（Lobby 沒有 `tcp_listen` 類檢查）；監聽失敗時 `ServeLimited` 回錯、行程直接結束，所以不會長時間「就緒但沒在聽」。程式註解（`pkg/startup/observability.go`、`pkg/debug/server_ready.go`）寫的「監聽就緒後」對 Lobby 不精確（第十一輪 DOC-L8）。

閘門只列入 `/ready`、不列入啟動自檢（`debug.Server.CheckStartup`，第十二輪前叫 `CheckReady`），不影響服務自行判斷啟動失敗；與 `/ready` 相同、含閘門與 `time_sync` 的完整檢查是 `CheckServing`，Lobby 公告用它（見下方 `time_sync` 段）。閘門 5 分鐘未放行觸發 `GameStartupStuck`，`GameReadyCheckFailing` 不看 `check="startup"`（第十二輪）。服務啟動久未就緒時，先看 `/ready` body 是 `startup: starting`（還在啟動流程、看服務日誌）還是別的檢查項目（依賴問題）。`compose.prod.yml` 六個服務的 healthcheck 都加了 `start_period: 120s`：World 還原玩家與重建候選最久約 2 分鐘，這段期間的失敗不計入 `retries`（12 次 × 10 秒）；`ci-deploy.sh` 的 `HEALTH_TIMEOUT` 維持 180 秒。User 實例（`tools/user`，`6063`）曾漏掉放行而 `/ready` 恆為 `startup: starting`，develop `a43fb0537` 已修正（啟動自檢 `debugSrv.CheckStartupAndMarkStarted` 通過後放行）；舊版映像的 user healthcheck 會一直不是 healthy。

啟動與關機期間的幾個行為（第六輪調整）：

- 啟動自檢與 S2S TLS／身分握手現在都隨停止訊號（ctx）中止，不再等滿逾時（自檢 5 秒、握手 n×3 秒）。
- `RunTCPService` 新增 `selfCheck` 參數，`/ready` 檢查改由組合根傳遞的 `*debug.Server` 登記，沒有全域登記表。Gate 的 `/diag/*` 路由在 debug 伺服器開始監聽**之後**才登記，啟動瞬間打 `/diag/*` 可能 404，對 `/ready` 與 `/metrics` 沒有影響。
- World 沒有設定 MySQL（`mysql.host` 為空）時，在 `openWorldStores` 就拒絕啟動，錯誤含 `world requires the memory game store`（`game store setup: mysql is not configured, ...`）；`max_players` 為負值同樣拒絕啟動（`read max players: config max_players=-1: must not be negative`）。World 啟動時 `watchGameConfig` 先於傳輸層，設定監看失敗不會留下已接受 Gate 連線卻沒人收尾的傳輸層。
- Central 共享路由（Redis）的讀寫改用呼叫端 ctx 且不受取消影響：關機 drain 期間登出仍會刪除路由，不再殘留最長 24 小時的幽靈在線。讀取失敗時有 Warn `central: shared routing read failed, falling back`。

### 服務抓取失敗（GameServiceDown）

`GameServiceDown`（`up == 0` 持續 1 分鐘，page）代表 Prometheus 抓不到該 job 的 `/metrics`，告警 labels 的 `job`／`instance` 指出是哪個服務。處置：

1. 看容器或行程是否還在（`docker compose ps`）；已退出就查最後的日誌找退出原因。
2. 行程還在時打 `http://localhost:<埠>/ready`（埠見上表）：連不上代表 debug HTTP 沒起來或卡住；回 503 看 body 是哪個檢查失敗。
3. 服務正常但仍 `up == 0`：查 Prometheus 抓取設定的 target 與埠是否對上 `pkg/debug.Endpoints`（`go run ./tools/pja configaudit`），以及網路（本機監控用 `host.docker.internal`）。
4. 服務恢復後 `up` 回到 1，告警自動解除；同一 job＋instance 的 warning 在 page 期間被正式環境 Alertmanager 抑制（`GameHandlerP99Critical` 除外），恢復後再看是否仍有 warning。

Gate、World、Chat、Lobby 另註冊 `time_sync` 檢查（`debug.RegisterRuntimeReadyChecker`）：收到 Central 第一則 `TimeSync` 前 `/ready` 回 503。它只列入 `/ready`、不列入啟動自檢，Central 晚啟動時服務不會自行退出，收到 TimeSync 後自動就緒。Gate、World、Central 每輪向 Lobby 公告前跑 `CheckServing`（與 `/ready` 同一組檢查，第十二輪 N-M1），所以 `time_sync` 或啟動閘門未就緒時不公告：**Central 全斷時所有 Gate／World 都會從 Lobby 撤除**，Central 恢復後各自在下一輪（最多 10 秒）重新公告；重啟後第一次公告也要等閘門放行且收到 TimeSync。`time_sync` 長時間不就緒先查 Central 是否可達、`<id>.dial.central` 與 Central `listen.*` 埠是否對上（`go run ./tools/pja configaudit`、`tools/private/opsdiag` 的 route 段）、S2S token。

### Prometheus 關鍵指標

- `tcp_connections_active` — 只算 accepted connection；異常下降 = 網路問題
- `pkg/tcpclient` 的 rate limit 會從 `RemoteAddr()` 解析 host；若解析失敗，會退回原始地址，不會把異常來源壓成空字串共用桶。
- `tcp_send_queue_overflow_total` — 佇列溢出 = 對端處理不及
- `tcp_unknown_messages_total` — 收到沒有型別或 handler 的訊息；玩家連線會被關閉，S2S 連線只丟棄。S2S 持續增加代表服務間協定版本不一致或漏註冊 handler
- `game_account_lock_total` — 帳號鎖定頻率
- `game_account_lock_wait_seconds` — 帳號鎖等待時間（p95 高 = 鎖競爭瓶頸）
- `game_login_db_query_seconds` — 登入 DB 查詢延遲（`find` / `save`）
- `game_handler_duration_seconds` — Handler 延遲分佈
- `game_heartbeat_timeout_total` — 心跳超時被踢次數
- `game_world_online_players` — 各 World 在線人數
- `game_panic_recovered_total` — `RecoverPanic` 擷取的 panic 次數（label `msg`），任何增加都觸發 `GamePanicRecovered`。背景 goroutine 與服務本體的 `msg` 帶服務名（`<服務名> async panic recovered`、`<服務名> service body panic recovered`），dataconfig 熱重載回呼 panic 為 `dataconfig onReload`；事件迴圈本體 panic 為 `event loop panic recovered`（`RunApp` 接住後不崩潰行程，改走關機協調器寫回並以 `appcore: event loop panicked` 結束；看到它要當成服務已停擺，查堆疊後重啟），看門 goroutine 自身 panic 為 `event loop stall watchdog panic recovered`，HTTP handler panic 由 `httpx.Recover` 計入並回 500。`task group panic recovered` 是 `TaskGroup.Go`／`GoBackground` 未指定標籤時的共用標籤（只剩未指定標籤的背景工作用它，日誌沒有 traceID、playerID，只能靠 stack 判斷函式；Gate 封禁查詢 panic 記為 `gate ban check panic recovered`（帶 traceID 與 `requestID`），Central 登入在 `login.Coordinator.Handle` 內就地 recover，記為 `central login panic recovered`（帶 `requestID`、`sessionKey`、`replied` 與 ctx 的 traceID，不經 `OwnerBase.Async`；panic 時若尚未回覆 Gate／轉送 World 才補送 `AuthServerFail`，不再讓玩家等到逾時；已轉送 World 之後才 panic 只記錄，不補送失敗，避免同一筆登入收到兩個矛盾結果）；World 的登入續行排隊訊息與帳號保留改以 `RunRecoveredCtx` 帶 ctx（traceID）與 `playerID`（`world deferred player message`、`world account retention`，後者另帶 `operation`，第十一輪）。`tcpserver accept loop` 代表 listener 已關閉、行程不會退出也不會重建 listener，必須重啟該服務；`lobby game clock loop panic recovered` 之後 Lobby 會取消服務 ctx 並以錯誤結束，交給 restart policy 拉起（第十一輪；原本遊戲時間凍結而 `/ready` 仍 200）
- panic 日誌的識別欄位：盤面指令 `playerID`／`msgID`；shardqueue 工作 `key`（playerID）；Chat 房間工作 `roomID`（`msg="chat room job panic recovered"`）；`fnEvent.Run` 的 `fn`（回呼函式名，只在 panic 時解析，事件沒有 ctx 與業務識別，靠它找到是哪個 `PostEvent` 呼叫點）；World 玩家寫回 `playerID`；Gate 恢復驗證背景工作 `playerID`、`requestID`。
- 未被 recover 的 panic：映像（含正式環境）預設 `GOTRACEBACK=all`（`docker/app.Dockerfile`），崩潰時印出全部 goroutine 堆疊，排死結／洩漏才看得到其他 goroutine 狀態；compose 可用環境變數覆寫。本機 `scripts/dev-up.sh` 現在也預設 `all`
- recover 到的 panic 日誌統一由 `panicx.RecoveredError`／`LogRecovered` 輸出（`appcore` 的同名轉呼叫已於第十三輪刪除）：訊息固定為 Error `panic recovered`，欄位 `msg`（recover 標籤，同時是 `game_panic_recovered_total` 的 label）、`err`（error 型別，內容為 `recovered panic: <panic 值>`；日誌欄位是 `%w: %v` 格式化，`errors.Is` 解不到原 error，原因在這一筆的 `msg=<label>` 與 `stack`）、`stack` 與各呼叫端的額外欄位；Record consumer（`record consumer iteration`）、shutdown task、recordmq handler、dataconfig（`dataconfig reload`／`dataconfig prepare`／`dataconfig onReload`）、World 登入活動（`world login activity`）、gamestore（`gamestore save player changes`）、circuitbreaker 都走這條（第十一輪：Record consumer panic 只記這一行，重連迴圈不再另記 `record consumer stopped, retrying` Warn；`gamestore save player changes`、`gamestore settle flush` 帶 `playerID`，`changes` 為 nil 時記 0）。舊版各處自己的訊息（`recordmq: handler panic`、`data config reload panic` 等）與 `panic` 欄位已不存在，日誌查詢與告警規則要改查 `panic recovered` 與 `msg`／`err`。例外：只剩一個就地 recover 點（tcp handler）雖然也遞增 `game_panic_recovered_total`，日誌訊息不是 `panic recovered`、也沒有 `msg` 欄位，要依下表以訊息搜尋（`err`、`stack` 欄位相同）；`/ready` 檢查函式 panic 已改走 `panicx`（`msg="ready check"`，另帶 `check`），不在例外內。HTTP handler panic 第十二輪起改走 `panicx.LogRecovered`：訊息由 `http handler panic` 改為 `panic recovered`（`msg="http handler"`，另帶 `method`、`path`），舊查詢要改搜 `panic recovered` 且 `msg="http handler"`。Record consumer 的錯誤訊息改為 `record consumer: iteration panicked`（第十二輪，原 `record consumer: panic`）。

  下游回頭找 panic：`panicx` 回傳的短字串錯誤 `Error()` 為 `recovered panic (<label>)`（仍可 `errors.Is(err, panicx.ErrRecovered)`），值班在 `data config reload failed`、World 寫回失敗等下游日誌看到這串時，改搜 `panic recovered` 且 `msg=<label>`，那一筆才有 panic 值與 stack。

- `game_heartbeat_timeout_total{service=<owner>}` 現在也計入 S2S 連線的讀取逾時（日誌為 Warn `peer read deadline exceeded`，原為 Error `decode error ... i/o timeout`）；S2S 對端無回應時看這個指標與日誌
- `tcp_rejected_connections_total` — TCP 伺服器在 accept 階段拒絕的連線（label `service`、`reason`：`rate_limited`、`at_capacity`、`handshake_timeout`，Gate 另有 `unauth_evicted`）；拒絕明細只在 Debug 日誌，量看此指標。`handshake_timeout` 是 Gate 連上後沒在期限內登入，可用來分辨攻擊或 Client 異常
- `game_account_purge_total` — 每日帳號清除結果（label `result`：`purged`、`failed`），失敗觸發 `GameAccountPurgeFailing`
- `recordmq_consume_total{result}` — Record 消費端處理結果（`ok`、`retry`、`dead_letter`），`dead_letter` 增加觸發 `GameRecordConsumerDeadLetter`

- `recordmq_enabled` — 設定了 RabbitMQ 即為 1（與連線成敗無關），搭配 `recordmq_connection_status` 判斷「設定了卻沒連上」
- `tcp_rejected_connections_total{service="user",reason="logged_in_per_ip"}` — Gate 同一來源同時已登入或登入進行中的連線數達上限（`session.max_logged_in_per_ip`，預設 20；檢查排在登入限流之後）而拒絕的登入請求數（玩家收到 `AuthRateLimited`）；持續增加先確認是否 CGNAT／網咖共用 IP（調高上限），否則是單一來源在灌自動建帳的已登入連線（對照 `new_user.rate` 與來源 IP）。
- `tcp_rejected_connections_total{service,reason}` 的 `reason="unauth_evicted"`（`service="user"`）— Gate 未登入連線超過全域上限（`max_connections` 的 1/4，預設 256）時被淘汰的最舊未登入連線數（超過上限時一次多淘汰 `maxUnauth/16` 條最舊者，把掃描成本攤到多次連線，所以計數會成批增加；同時只有一個掃描者，其餘並行的新連線直接返回）；持續增加代表有來源在灌未登入連線或握手卡住，對照 `tcp_connections_active` 與來源 IP
- `game_connections_rejected_total` — 應用層拒絕的連線（label `service`，例如 Gate 連線洪水時的拒絕），每條連線不另寫日誌

其餘 metrics 主要用於交叉驗證與 debug，不作為第一優先 alert 入口。

### 告警抑制

現在用 Alertmanager 做降噪：

- 同一 `alertname + job + resource_class` 先 group（`group_by: [alertname, job, resource_class]`，本機與正式設定相同），再送通知
- `page` 壓 `warning`（正式環境 `equal: [job, instance]`：只壓同一實例的 warning，World 多實例時一台 `GameServiceDown` 不會壓掉其他實例的 warning；`GameHandlerP99Critical` 是症狀，不當來源，不會壓同實例的 DB 連線池、Redis 錯誤等根因 warning。本機演練用的 `monitoring/alertmanager/alertmanager.yml` 與正式相同，`TestAlertmanagerInhibitRulesMatchProd` 比對兩份 `inhibit_rules`）
- 沒有「`P99` 壓 `P95`」「`overflow` 壓 `depth high`」這類規則（本機與正式設定都沒寫）：`GameHandlerP99Critical` 被排除當 page 抑制來源，`GameQueueOverflow` 是 page、會抑制同實例的 warning（它已帶 `instance` 標籤，對得上 `equal: [job, instance]`）
- `GameLoginCentralBusy` 不再壓 `GameLoginAvailabilityLow`／`GameLoginFailureRatioHigh`（第十五輪 O-L8 移除：busy 門檻低，無條件抑制會蓋住同時發生的 server_fail；開服尖峰的重複通知看 busy 佔比自行判斷）
- `GameLoginFailureRatioHigh` 壓 `GameLoginAvailabilityLow`（`equal: [job]`；失敗率超過 10% 必然也讓可用率低於 99%，只留失敗率一條；本機與正式設定相同）

位置：
- [monitoring/alertmanager/alertmanager.yml](../../monitoring/alertmanager/alertmanager.yml)
- [monitoring/compose.yml](../../monitoring/compose.yml)

用途：
- 減少同一故障連炸
- 先看根因，不先被次級告警淹沒

### 限流分級

現在把常見熱點拆成不同桶：

1. `login`
   - Gate 內用 account 粒度。
   - 連續重試同帳號會先進暫時鎖定。
2. `logout`
   - Gate 內用 playerID 粒度。
   - 避免同一玩家一直重送 logout 把 Central / World 打爆。
3. `GM`
   - Lobby admin API 走獨立 token bucket。
   - 免 admin token 外洩時把所有管理操作一起灌死。
4. `audit`
   - GM audit log 用獨立桶。
   - 讓審計輸出不跟 GM 請求共用同一條限流線。

用途：
- 一條線超，不代表全線一起死
- 不同入口各自退化，各自收斂

### 狀態修復 CLI

用 `tools/private/staterepair` 修 session / route / world drain / account lock：

```powershell
go run ./tools/private/pja staterepair -account alice -user-id 7 -world-id 9 -clear-route -clear-lock -clear-session -repair-session -backup-file staterepair.backup.json
go run ./tools/private/pja staterepair -rollback -backup-file staterepair.backup.json
```

用途：
- `clear-route`：清 `central:account:{account}` 與 `central:routing:{playerID}`
- `clear-lock`：清 `central:lock:account:{account}`
- `clear-session`：清 Gate 驗證 session 殘留（Gate 驗證 journal 已刪，舊版寫入的 `requestjournal:gate:*:validate` 鍵仍由此工具清除）
- `repair-session`：請 Gate 重新收斂 derived session state
- `drain-world` / `undrain-world`：修 `central:world:drain`
- `rollback`：從 backup file 還原 Redis state
- `clear-route` 至少要帶 `-account` 或 `-user-id`
- `clear-lock` 一定要帶 `-account`
- `clear-session` 一定要帶 `-user-id`
- `drain-world` / `undrain-world` 一定要帶 `-world-id`
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode staterepair`；預設會先做 dry-run，明確帶 `-StateRepairRollback` 才會回滾。

原則：
- 先 `-dry-run` 看會做什麼
- 需要可回滾時，先指定 `-backup-file`
- 只修可重建的 derived state
- 不碰 source of truth
- `staterepair` 的 rollback backup 現在會對未知欄位與壞 entry type 報錯，不再靜默還原錯檔案
- `staterepair` 的 Gate repair 回應會檢查尾巴資料與欄位型別，不再把壞回應當成功
- `staterepair` 的 backup file 寫出時會自動建立父目錄，不必手動先 mkdir

| 訊息 | 意義 | 處理 |
|---|---|---|
| Warn `S2S allowed_cidrs is empty: source IP is not restricted, only token authenticates peers`（欄位 `listener`） | S2S 驗證啟用但該監聽區段 `allowed_cidrs` 為空：來源 IP 不受限，只靠 token 驗證；每個區段啟動記一次（Central 四段都空會看到四筆） | 正式環境把 `allowed_cidrs` 填成 compose 網段，見 S2S身份驗證 |
| 啟動錯誤 `s2s_auth.enabled is not set` | S2S 驗證開關漏設；不再退回明文 | 設定檔明確設 `s2s_auth.enabled: true`（正式）或 `false`（開發） |
| `rejecting connection: at capacity`、`rejecting connection`（TCP server）與 `per-IP connection limit exceeded, closing`（Gate） | 連線名額已滿、被限流或單一 IP 超過上限，新連線被直接關閉；這三筆都是 **Debug** 等級，預設 Info 看不到 | 不要 grep 日誌，改看 `tcp_rejected_connections_total{service,reason}` 與 `game_connections_rejected_total`；再看 `tcp_connections_active` 與連線上限設定，確認是否有連線洩漏（`game_connection_leak_diff`） |
| `world record sink unavailable at startup, retrying in background; Record events are dropped until it connects`（Error）、`world record sink retry failed`（Warn）、`world record sink connected after startup retry`（Info） | World 啟動時連不上 RabbitMQ 不再拒絕啟動，改在背景以指數退避（1 秒倍增到 30 秒）持續重試；連上前不發 Record 事件，必須送達的 outbox 事件留在 MySQL，連上後由 relay 照常發送（有設定 RabbitMQ 就一律啟動 relay，連上前整輪略過、不燒重試次數） | `recordmq_connection_status=0` 現在是**暫態**，不再是「重啟前永不恢復」；先修 RabbitMQ，不必重啟 World。對照 `GameRecordMQDisconnected` |
| `central: shared routing read failed, falling back`（Warn，欄位 `kind`、`err`） | Central 讀 Redis 共享路由快取失敗，退回本機判斷；有冷卻，最多約每 10 秒一筆 | 看 Redis 健康與 `circuit_breaker_state`；沒有這筆日誌不代表 Redis 正常，持續出現再查連線 |
| `peer read deadline exceeded`（Warn） | S2S 對端超時沒有任何資料，連線被關；計入 `game_heartbeat_timeout_total{service}` | 查對端行程是否卡住或網路中斷 |
| `async log buffer overflow, entries dropped`（Warn，欄位 `dropped`、`droppedTotal`） | 設了 `LOG_ASYNC_BUFFER` 且緩衝滿了，最舊的日誌被丟棄 | 調大 `LOG_ASYNC_BUFFER` 或查 stderr 消費是否太慢；計入 `logger_async_dropped_total`。行程崩潰（panic、SIGKILL）時緩衝內最後幾筆可能遺失，正常結束由 `startup.Main` 排空 |
| `shutdown timed out, goroutine dump`（Error，欄位 `reason`、`truncated`、`goroutines`） | 關機任務逾時（drain 除外）、`appcore: event loop did not stop`、最後等背景工作逾時，或 Lobby／Record 的 HTTP 優雅關閉逾時（5 秒，`reason=http shutdown timed out: <addr>`；多個 server 並行關閉時，第一個逾時的 server 以 `sync.Once` 立刻傾印、只輸出一次，`<addr>` 只帶該 server 的位址，其他同時逾時者不會列出）時，一次輸出 goroutine 堆疊（僅關機逾時用這則；SIGUSR1 主動採證是另一條管道：直接寫 stderr 的 `goroutine dump requested, reason=...`（不經 logger），不代表關機卡住；`pprof goroutine debug=1`，相同堆疊合併並附數量，上限 128KB，超過 `truncated=true`） | 看 `reason` 是哪個任務，再到 `goroutines` 找卡在哪裡（鎖、channel、I/O）；詳見[現場採證](#現場採證服務卡住cpu-高記憶體持續成長) |
| `pprof disabled; set debug.pprof_enabled=true to enable`（Info） | 該服務未啟用 pprof（正式環境缺省如此） | 要採證時見[現場採證](#現場採證服務卡住cpu-高記憶體持續成長)的前置條件 |
| `DEBUG_PPROF_BASIC_AUTH invalid: ...`（Error） | `DEBUG_PPROF_BASIC_AUTH` 有設定但不合格（格式非 `user:pass`、密碼短於 16 字元、`change-me` 開頭），pprof 與 Gate `/diag/session`、`/diag/player`、`/diag/reconcile`（GET 與 POST）一律回 503（`/diag/protocol` 不受保護） | 修正環境變數後重啟；空字串（僅本機開發）則只靠 CIDR 並記 Warn `pprof basic auth not configured` |
| `outbox: claim failed`、`outbox: publish failed`（限流，依訊息文字分別計算，每種訊息每 5 秒最多一筆，先出現的失敗類型不會吃掉另一種故障的額度） | World 的 Record outbox 領取或發布失敗，事件留在 MySQL 重試 | 先看 MySQL 與 RabbitMQ 健康；對照告警 `GameRecordMQPublishErrors`、`GameRecordMQDisconnected` |
| `recordmq: async publisher drain interrupted, dropping queued events`（Warn，欄位 `queued`）、`... stopped by context, dropping queued events` | 關機時 `Stop(ctx)` 的期限到了仍未排空（例如 broker 慢），或發布迴圈的 ctx 被取消，佇列中剩下的事件被放棄 | 不代表關機順序有誤；看 `queued` 筆數，對照 RabbitMQ 健康與 `recordmq_connection_status`。必須送達的事件走 outbox 留在 MySQL，一般 Record 事件（稽核）會遺失 |
| `record publish dropped`（Warn，欄位 `eventType`、`err`） | World 的一般 Record 事件沒進非同步佇列：`err` 為 `async queue full`（佇列滿，發布端比 broker 快或 broker 斷線）、`async publisher stopped`（已進入關機）、`async publish context canceled`（呼叫端 ctx 已取消）或 `async publisher not ready` | 持續出現先查 RabbitMQ 與 `recordmq_connection_status`；這類事件不重送，稽核紀錄會缺；丟棄量看 `recordmq_async_dropped_total{reason}`（`queue_full`、`stopped`、`not_ready`；`not_ready` 不寫此日誌，此日誌每 10 秒最多一行，筆數以指標為準）；`queue_full`／`not_ready` 超過 0 會觸發 `GameRecordEventsDropped`。`recordmq: async publish failed`（Warn，欄位 `eventID`、`eventType`、`failedSinceLastLog`、`err`）則是已入佇列但送出或確認失敗，每 10 秒最多一行，計入 `recordmq_publish_error_total`。broker 斷線期間發布迴圈暫停出列，事件留在佇列等重連，佇列填滿後才出現 `async queue full` |
| `combat: remove stale candidate failed` | PvP 候選清單的 Redis 清理失敗 | 下次抽到時會再清；持續出現時查 Redis |
| Redis 重啟／`FLUSHALL` 後 `combat:eligible-player` 缺玩家 | World 只在玩家戰鬥快照內容改變或上次寫入超過 10 分鐘時重寫候選集合 | 不必重啟 World：每位有操作的玩家最長 10 分鐘自癒；要立即恢復就重啟 World（啟動會 `RebuildCandidates`；重建先寫專屬暫存 key（TTL 1 小時），完成後原子換上，滾動部署時其他 World 配對不會遇到空集合，重建期間其他 World 的更新由 10 分鐘強制重寫補回） |
| 登入回 `AuthRateLimited` 且 `game_account_lock_total{result="timeout"}` 增加 | 同帳號另一筆登入或清除仍持有鎖 | 查是否有慢登入（`game_account_lock_wait_seconds`、登入 P99），持鎖處理上限為 10 秒 |
| 登入回 `AuthServiceUnavailable` 且 `game_account_lock_total{result="error"}` 增加（告警 `GameAccountLockError`） | 共享帳號鎖（Redis）故障，不是鎖競爭。Central 關機（Stop）造成的等鎖取消（`context.Canceled`）仍回 `AuthServiceUnavailable`，但**不計 error、不記 Error**，所以滾動重啟不會誤發此告警 | 查 Redis 健康與 Central 的 `account lock` 錯誤日誌（10 秒取樣）；Client 不應猛重試 |

### 故障注入

停掉 World、Redis、RabbitMQ、MySQL 或切斷 Gate 與 World 之間連線時各服務的反應、告警與恢復時間，見[容量與壓測基準](容量與壓測基準.md)的「故障與恢復」。

World 可用 `FAULT_INJECT` 觸發本機故障：

```bash
FAULT_INJECT=world.grant_item.on_grant ./world ...
```

PowerShell 用 `$env:FAULT_INJECT='world.grant_item.on_grant'`；bash 的 `set X=y` 不會設定環境變數。

可用名稱（程式端單一清單是 `cmd/world/internal/faultinject` 未匯出的 `known`，名稱常數同套件匯出）：
- `world.grant_item.on_grant`
- `world.grant_item.ack`
- `world.recovery.restore`
- `world.recovery.validate.delete`

`world.recovery.*` 兩個不由 `fault-drill.ps1` 判定，需手動設 `FAULT_INJECT` 並看恢復指標／日誌。名稱拼錯會記 Warn `unknown fault name ignored`（欄位 `fault`、`known`），該名稱不會啟用（其餘正確名稱照常啟用），看到就對照上面清單。

用途：
- 驗證 async retry / dead-letter / ack fail metric
- 觀察 queue 是否能在故障後收斂
- 只建議在本機或測試環境開啟；啟用時服務會以 Warn 列出故障名稱，正式 compose 不傳此變數

### 資料保留策略

目前先定這幾條：

1. `request journal`
- 登入、登出與 Gate 驗證 journal 已刪（2026-10-30）；World 擲骰、建築升級與驗證 journal 的重試預算收在 World app 的 request journal 實作內。
   - 預設保留 2 分鐘。
2. `replay cache`
- World replay cache 的重試預算已收回 app / tool 本地 helper。
   - 預設保留 2 分鐘。
3. `dead-letter`
   - `grant item dead-letter` 進 Redis 後預設保留 7 天。
   - 逾期自動清，避免人工堆積。
4. `audit record`
   - `gm audit` 視為操作記錄，建議保留 30 天。
   - 實際清理交由外部 log / table retention。

原則：
- TTL 要跟用途綁定，不要散在各 service 裡各寫各的
- dead-letter 不可永久保存
- audit 可查，但不要無限長

## 常見問題

### 0. 玩家登入失敗（密碼錯誤）

**症狀**: 玩家送出登入後立即收到失敗回應（return code 13）

**排查步驟**:
1. 確認玩家使用的密碼與首次登入時一致
2. 在 Central 日誌（需 Debug 等級）搜尋 `login failed, notifying gate directly`，看 `responseCode` 欄位為 13（`AuthWrongPassword`）；預設 Info 看不到這行，也沒有 `wrong password` 這種日誌，要看量請用 `game_login_total` 的 `result` 標籤
3. 若懷疑帳號 hash 損壞，直接查 MySQL `users.password_hash` 欄位

**常見原因**:
- 玩家輸入密碼有誤（最常見）
- `password_hash` 為空的帳號（例如舊帳號遷移）只接受空密碼，帶任何密碼都回 code 13；這是預期的安全行為（防冒用），不是欄位讀取錯誤。要讓該帳號改用密碼，需由維運重設 hash
- 新帳號（DB 無記錄）送空密碼 → 一律回 code 13，Central 日誌為 `login failed: new user without password`；這是預期行為，不是故障
- Redis 帳號快取中 `hash` 欄位值不正確（可清除 `central:account:<account>` key 強制回 MySQL；HASH 的 `hash` 欄位，鍵結構見[Redis鍵值結構](../90-參考附件/Redis鍵值結構.md)）

### 1. 玩家登入卡住（pending_login 超時）

**症狀**: 玩家送出登入後無回應，30 秒後被清除（預設，可由 `session.pending_login_ttl` 調整）

**排查步驟**:
1. 用 `gameTraceID` 追蹤訊息流向
2. 確認 Gate → Central 連線是否正常（`tcp_connections_active`，只算 accepted connection）
3. 確認 Central → World 連線是否正常
4. 檢查 Central 日誌是否有 MySQL 錯誤
5. 檢查是否觸發帳號鎖定（5 次/10 秒限制）

**常見原因**:
- Central 與 MySQL 連線中斷（斷路器開啟）
- World 未啟動或未連上 Central
- 帳號被速率限制鎖定（等 30 秒）

### 2. World 重啟後玩家狀態遺失

**症狀**: World 重啟後，玩家未恢復到線上狀態

**排查步驟**:
1. 確認 Redis 是否正常運行
2. 檢查 World 啟動日誌是否有 Redis 載入紀錄
3. 確認 Gate 是否在 30 秒寬限期內重新連上 World
4. 檢查 `game_recovery_validation_total` 指標

**常見原因**:
- Redis 斷路器開啟，無法讀取玩家狀態
- Gate 重連超過 30 秒寬限期，玩家被清除
- 玩家在 World 重啟期間已從 Gate 登出

### 3. 重複登入/重複操作

**症狀**: 同一操作被執行多次

**排查步驟**:
1. 確認 `requestID` 是否正確傳遞（登入、登出沒有去重：Gate 每次都用新的 RequestID，`game_login_replay_cache_total` 已刪；重複登入看 `game_request_ignored_total` 與 Central 帳號鎖）
2. 擲骰、建築升級重複執行：檢查 World 的 request journal（`cmd/world/internal/store/requestjournal`）

**常見原因**:
- 客戶端重送但 requestID 不同（應相同）
- Replay cache TTL（2 分鐘）已過期
- 要重演這條情境，可直接用 `scripts/private/p0-daily-check.ps1 -Mode session`

### 4. Central 在登入途中斷線或重啟

**症狀**: 玩家登入卡住、收到 `service unavailable`，重試後才成功

**排查步驟**:
1. 檢查 Gate 日誌是否在 `pending_login` 期間失去與 Central 的連線
2. 檢查 `tcp_reconnect_attempts_total` / `tcp_reconnect_total`
3. 確認 Gate 是否已清理逾時的 `pending_login` session（TTL 預設 30 秒，`session.pending_login_ttl`）
4. 比對玩家端是否重新發起新請求，而不是重送舊上下文

**常見原因**:
- Central 程序重啟，Gate 對應 request 鏈路中斷
- Central 恢復後玩家重新登入，產生新的 `requestID` / `gameTraceID`
- 上游等待過久，誤以為可直接重放原請求
- 要驗 restart retry gate，可直接用 `scripts/private/p0-daily-check.ps1 -Mode failover`

### 5. 重複登入把舊連線踢下線

**症狀**: 同帳號新裝置登入後，舊連線收到重新登入或被迫下線

**排查步驟**:
1. 用 `gameTraceID` 比對兩條登入鏈路是否屬於不同請求
2. 檢查 Gate 是否有舊 session 被清理或轉成失效
3. 確認玩家端收到的 return code 是否為重新登入相關語意
4. 若是測試環境，確認是否有人共用同一組帳號

**常見原因**:
- 同帳號真的在多端同時登入
- 測試腳本重複使用固定帳號
- 本地 state 過舊，玩家端誤以為自己仍在線
- 要重演這條情境，可直接用 `scripts/private/p0-daily-check.ps1 -Mode session`

### 6. Gate 與 World 斷線

**症狀**: 玩家大量離線

**排查步驟**:
1. 檢查 `tcp_reconnect_attempts_total` — 重連嘗試次數
2. 確認網路連通性
3. 檢查 World 是否因 OOM 或 panic 崩潰：`docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' <容器>`；崩潰堆疊用 `docker logs --since <時間> <容器>` 找 `panic: ` 或 `fatal error: ` 起頭的段落，其後 `[running]:` 的 goroutine 才是出事的那條（`goroutine 1` 是 main，平常停在 RunApp 的 select，不是根因）。Docker 秒級拉起時 `up==0` 告警不會響，改看 `GameProcessRestarted`（`changes(process_start_time_seconds[15m])`；發版重啟已由 `game_build_info` 排除，15 分鐘內同一實例出現兩組 `release`／`server_commit` 時容許重啟一次，同版本重新部署仍會觸發一次，新版 crash loop 第二次重啟起照樣告警）
4. 確認是否在 30 秒內恢復（短期 vs 長期策略）

**處理策略**:
- < 30 秒：自動恢復，標記 unavailable 後恢復
- \> 30 秒：清理玩家，通知 Central 清除路由

### 7. Prometheus 抓不到 metrics

**症狀**: Grafana dashboard 沒資料，Prometheus `up` 為 0

**排查步驟**:
1. 確認服務 debug server 已啟動並開出 `:6060~:6066`（Central 6060、Gate 6061、World 6062、User 6063、Lobby 6064、Record 6065、Chat 6066）；埠被佔用時服務記一筆 `debug server disabled` 錯誤後照常啟動，但該實例沒有 `/health`、`/ready`、`/metrics`（同一台主機跑多個同類服務時，後啟動的必然綁不到）
2. 檢查服務是否只允許 loopback，導致 container 抓不到 `/metrics`
3. 若 Prometheus 跑在 Docker container，確認有設定 `DEBUG_ALLOW_CIDRS`
4. 來源 IP 通過但仍回 403：debug server 的 `accessGuard` 另外檢查請求的 `Host` 標頭（防 DNS 重綁定；Lobby admin 路由與 Record `/events` 套用同一份 `httpx.HostAllowlist`，Host 不符同樣回 403；Lobby admin 與 Record `/events` 的 Host 擋下另記取樣 Warn `host header not allowed (sampled)`（欄位 `host`、`remote`，每 10 秒一筆）；debug server 的來源 CIDR 或 Host 不符 403 會記取樣 Warn `debug access denied (sampled)`（欄位 `reason`、`remote`、`host`；`reason` 為 CIDR 與 Host 兩種，**各自**每 10 秒一筆，互不吃額度，可用 `reason` 確認是被哪一關擋下），改用 IP 或單一標籤名稱存取，或把網域列入 `DEBUG_ALLOWED_HOSTS`）。內建接受 IP 字面值、`localhost`、`*.localhost`、`host.docker.internal` 與不含 `.` 的單一標籤名稱（compose 服務名、容器名）；Prometheus 以 FQDN 抓取（例如 `world.internal.example.com:6062`）時，要把該名稱列入 `DEBUG_ALLOWED_HOSTS`
5. 執行 `scripts/monitoring-smoke.ps1` 驗證 Grafana / Prometheus provisioning

**常見原因**:
- debug server 預設只允許 loopback
- Prometheus 容器網段未列入 `DEBUG_ALLOW_CIDRS`
- Prometheus 用 FQDN 抓取，`Host` 標頭不在內建白名單，也沒列入 `DEBUG_ALLOWED_HOSTS`
- monitoring compose 沒有成功載入 dashboard 或 datasource

### 8. Docker 環境啟動失敗

**排查步驟**:
1. 確認 MySQL 與 Redis 已就緒（compose.deps.yml 先啟動）
2. 檢查 config 掛載路徑是否正確
3. 確認健康檢查通過（`wget /ready`）
4. 查看 `docker logs <container>` 確認錯誤訊息

### 10. 登入延遲高但失敗率正常

**症狀**: 玩家反映登入慢，但 `game_login_total{result!="success"}`（如 `server_fail`）無明顯上升（Gate 本地限流不在此指標，另看 `game_login_rejected_total{reason}`）

**排查步驟**:
1. 查看 `game_account_lock_wait_seconds` p95 — 若偏高代表帳號鎖競爭（同帳號並發登入）
2. 查看 `game_login_db_query_seconds{op="find"}` p95 — MySQL FindByAccount 慢
3. 查看 `game_login_db_query_seconds{op="save"}` p95 — 新帳號 Create 慢（程式呼叫 `store.Create`，指標 `op="save"` 標籤沿用舊名）
4. 對照 `game_handler_duration_seconds{handler="on_login_gate_to_central"}` 確認是哪段佔多數

**常見原因**:
- MySQL 負載高，查詢排隊（DB query 時間高）
- 同帳號短時間大量登入請求，鎖競爭嚴重（lock wait 時間高）

### 11. CI 整合測試失敗

**排查步驟**:
1. 整合測試啟動真實程序，確認 port 未被占用
2. 檢查是否有 race condition（`-race` flag）
3. 確認 testenv 是否正確清理上次的程序：Windows 上找 `%TEMP%\testenv-bin-*` 底下仍在執行的 central／gate／world／chat，父行程已不存在的就是殘留程序
4. 偶發逾時先看是否少了就緒等待：登入前要等 `WaitForGateReady`；讀回應用 `ReadNext`，不要假設回應一定是下一則訊息

### 12. Gate rolling deploy 後仍有玩家強制斷線

**症狀**: Gate 重啟時關機錯誤出現 `shutdown task "user drain": user drain: drain timeout with N remaining connections: context deadline exceeded`（Central 為 `central drain`、World 為 `world drain`）；沒有 `drain timeout reached, force-disconnecting remaining players`、`drain complete` 這類訊息，也沒有 `count`／`timeout` 欄位

**排查步驟**:
1. 從錯誤訊息的 `N remaining connections` 確認殘留人數；開始排空時另有 Info `stopped accepting new connections`（欄位 `owner`）
2. 若殘留玩家偏多，考慮拉長 `drain_timeout`（在 gate.yaml 設定，上限 40 秒），同時要把容器 `stop_grace_period` 一併調高（見[開發規則](../30-部署與開發/開發規則.md)的 Gate 排空設定）
3. 確認 Lobby 服務探索是否已將此 Gate 標記為不可用（TTL 25s），避免新玩家繼續連入
4. drain 逾時是常態、不輸出 goroutine 堆疊；其他關機任務逾時才有 `shutdown timed out, goroutine dump`

**常見原因**:
- Gate 預設 `30s` 排空時間不夠長，部分玩家長連線沒有在期限內下線
- 玩家 heartbeat 仍正常，但業務邏輯端沒有登出流程觸發
- `drain_timeout` 設成壞值（缺單位、亂碼、非正數）時 Gate 拒絕啟動（`drainTimeoutFromConfig`），不會悄悄沿用預設 30s；未設定才用預設值。它現在只套給 drain 任務，其餘關機任務維持 5 秒
- World、Central 正常滾動重啟時，drain 會等滿 5 秒才以 `drain timeout` 回錯、結束碼 1，屬設計行為，不是故障（見[容量與壓測基準](./容量與壓測基準.md)第 38、138 行的說明）；編排系統若以結束碼判斷成功與否，要容忍這個 exit 1

### 13. OTel Span 在 Jaeger 中找不到

**症狀**: Gate/Central/World 的 Span 各自獨立，不在同一條 Trace 下

**排查步驟**:
1. 確認 `otel.exporter` 設定為 `otlp`，且 `otel.endpoint` 正確指向 Collector
2. 檢查服務啟動日誌 — `"tracing init failed"` 表示 OTel 初始化失敗（span 不輸出但服務仍運作）
3. 確認三個服務日誌中的 OTel `trace_id`（32 位 hex）相同（跨服務同一條鏈路應共用）；`gameTraceID` 是另一個十進位欄位，不能拿來搜尋 Jaeger
4. 在 Jaeger UI 直接以日誌裡的 `trace_id`（hex）搜尋

**常見原因**:
- OTLP Collector 未啟動或 endpoint 設定有誤
- `otel.exporter` 未設定，預設為空字串（noop，不輸出）
- 服務間鏈路編號（`gameTraceID`／OTel `trace_id`）傳遞中斷（應由 Gate 建立後透傳，不可在中間重建）

### 14. 服務發現或路由漂移

**症狀**: 新玩家被派到維護中的 World、登出打到舊路由，或 Central / Gate / World 對同一資源路由不一致。

**排查步驟**:
1. 確認 `central:world:drain` 是否正確寫入 Redis
2. 檢查 Central 是否已刷新 `worldRegistry.drained`（每 5 秒從 `central:world:drain` 重讀）
3. 檢查 `routing:{playerID}` 與 `account:{account}` 是否仍對應 memory
4. 確認 Gate / World 的 `ConnectInfo` 是否有及時清除 unavailable 標記
5. 若是 Lobby 探測異常，先看 Redis TTL / heartbeat 是否失效

**常見原因**:
- Lobby 已把 World 標成維護，但 Central 還沒刷新 Redis drain set
- World / Gate 重連後沒送 `ConnectInfo`，導致 unavailable 標記殘留
- routing key TTL 沒 refresh，或舊節點殘留舊路由

**處理策略**:
- Redis drain set 先修，Central 再刷新
- reconnect 後先清 unavailable，再跑後續 recovery / cleanup
- 以 audit / reconcile 檢查 routing key 與 memory 是否一致
- 若 Redis routing/account key 出現壞值，Central 會直接忽略，不會回填成 `gate=0` / `world=0` 的假路由
- account cache 的 `uid` / `wid` / `hash` 壞值也會直接丟掉，不會當成 returning player 的真資料

### 15. 版本不相容（強制更新）

**症狀**: Client 連上後收到 `HelloResponse` 的強制更新或維護後被斷線；或服務之間的連線一建立就被關閉。

**排查步驟**:
1. 看 Gate log 的 `client version hello`（**Debug** 等級，正式環境預設 Info 看不到；平時先看第 3 步的指標，必要時才調 `LOG_LEVEL=debug`；它只在啟動時讀、沒有熱重載，要改必須重建該服務容器，Gate 會斷開全部玩家連線，World 會走一次完整關機與還原）：`result`、`reason`、`platform`、`gameVersion`、`protocolVersion`、`clientContract`、`configSeq`
2. 依 `reason` 判斷（日誌與指標的值是 snake_case，不是協定列舉名）：`protocol_mismatch` 與 `client_contract_mismatch` 是 Client 與 Server 的版本不同；`game_version_too_old` 看 `GET /admin/version-policy` 該平台的 `min`；`config_too_old` 看 Server 的 `min_config_seq`
3. 查 `game_version_hello_total{result,reason,platform}` 看是不是特定平台或版本集中被擋
4. 服務之間被拒絕：查 `game_service_hello_mismatch_total` 與 `service hello mismatch`／`service hello timeout`／`message before service hello` log，確認所有服務都來自同一次發版且都會送 ServiceHello
5. 服務啟動就失敗：看 `release info` 與 `verify` 的錯誤，通常是協定、設定或資料庫 schema 與嵌入的 `release.json` 不一致

**常見原因**:
- 營運把該平台的 `min` 調太高，或維護旗標忘了關
- 新安裝包還沒上架就調高了 `min`
- 部署時新舊版服務混跑
- 同步 PJA-Protocol 或 PJA-Config 後沒有更新開發版 `pkg/release/release.json`

完整流程見 [版本握手與強制更新](../10-核心流程/版本握手與強制更新.md)。

### 16. 錯誤碼語意不一致

**症狀**: HTTP、RPC、queue 對同一類失敗回應完全不同。

**排查步驟**:
1. 先看 `pkg/errcode` 的 canonical class
2. 確認指標 outcome 是否由 `MetricOutcomeFromAuthResultCode` 產生；私有壓測與回歸工具的重試判斷在 `tools/private/internal/authcode.ShouldRetry`
3. 確認 queue / RPC 是否只看 `ack / retry / drop`
4. 確認 app 沒有自己硬編新語意

**常見原因**:
- 某條 handler 自己選了不同 HTTP status
- 某個 queue 失敗碼沒有接到 retry policy
- 舊 code 還在直接 compare 數字，不看 canonical class

### 17. 重試預算耗盡

**症狀**: `game_async_failure_total{queue="grant_item",outcome="retry_budget_exceeded"}` 上升，或命令很快進 dead-letter。

**排查步驟**:
1. 看 `RequestedAtMs`（佇列 JSON 鍵 `requestedAt`，Unix 毫秒）是否過舊（Lobby 以遊戲時間填入，World 以遊戲時間比較重試期限，兩台主機時鐘偏差不影響）
2. 看 `Attempts` 是否已到上限
3. 看 `grant item queue` 是否長時間卡在下游 `onGrant` 錯誤
4. 若是 transient 錯，先修下游，不要盲目放大 retry window

**常見原因**:
- 下游服務長時間不可用
- command 在 queue 裡堆太久
- 重試次數已達 5 次
- 新舊 schema 混跑導致一直失敗，最後被 budget 擋下

### 死信再處理

**GM 重試發道具必須帶 `operationID`：** `POST /admin/grant-item` 以查詢參數 `operationID`（英數字、連字號、底線，最長 48 字）作冪等鍵；沒帶時伺服器每次產生新的 ID，Lobby 回逾時或連線中斷後重送，可能重複發放。Lobby 每個請求有 3 秒處理期限（小於 http.Server 的 5 秒寫入期限）：唯讀請求（GET／HEAD）以 `http.TimeoutHandler` 到期回 503 `request timeout`；寫入型請求（POST／PUT／DELETE 等）只設 ctx 期限、**不由中介層回 503**，避免 503 回出去後 handler 仍完成寫入、GM 工具依 503 重試而重複發放。寫入請求 ctx 到期時結果可能不明（可能已寫入），重試時一律帶同一個 `operationID`，World 以它去重。

不依賴私人工具的做法是直接呼叫 Lobby admin 端點（需 gm token，帶 `X-Requested-By: admin` 與 `Authorization: Bearer <token>`）：`GET /admin/grant-item/dead-letter?worldID=<id>` 列出死信（可加 `operationID`、`playerID` 篩選）；`POST /admin/grant-item/replay?worldID=<id>&operationID=<op>` 送回佇列重試，成功回 204，找不到回 404；`POST /admin/grant-item/discard?worldID=<id>&operationID=<op>` 丟棄，成功回 204，找不到回 404。無法解碼的死信（清單中標記為不可用）不可 replay（回 400），只能 discard。 grant 端點會把呼叫端的 operationID 加上 `gm-` 前綴後才存入（`grantitem.ClientOperationID`，已從 Lobby gm 搬進 `pkg/grantitem`，`MaxClientOperationIDBytes` 同處）；**呼叫端自帶 `gm-` 開頭的 ID 會被拒絕**（以 `a` 與 `gm-a` 發放會存成 `gm-a` 與 `gm-gm-a`，死信分不出是哪一筆）。死信篩選、replay、discard 的 `operationID` 參數可填原始值（如 `ticket-123`）或完整的 `gm-ticket-123`，三者與 `tools/private/deadletterreplay` 共用同一個 `DeadLetterFilter.Match`（去掉前綴後單次比對；`FindByOperationID` 已刪）；既有的 `gm-gm-*` 仍可用完整 ID 處理。

**冪等鍵命中要比對內容**：World 以 `OperationID` 查到已存在的 `gm_grant_record`（`FindGrantRecord`）時，玩家、道具與數量必須一致才視為已發放；內容不同回永久錯誤 `ErrOperationConflict`，指令直接進死信，不再被當成已發放回成功。

用 `tools/private/deadletterreplay` 挑選 dead-letter 再送回 queue：

```bash
go run ./tools/private/pja deadletterreplay -world-id 9 -operation-id grant-op-1 -retryable -replay
```

用途：
- 手動挑選特定 `world / user / operationID`
- 先 `-dry-run` 看選到哪批，再決定 replay 或 discard
- `-retryable` 只列還在重試預算內的樣本
- 若 world capability 不在，先修 world，再重送
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode deadletterreplay`

Record 事件佇列（`recordmq`）進 `<queue>.dead` 的事件計入 `recordmq_consume_total{result="dead_letter"}` 並觸發 `GameRecordConsumerDeadLetter`。死信規則：內容無法解析、缺少 `OccurredAt`、寫入違反約束（SQLSTATE 22xxx、23xxx，以及 MySQL 錯誤碼 1366／1265／1300／4025，如非法 UTF-8、資料截斷、JSON 不合法）或 handler panic（逐筆處理時）直接進 `<queue>.dead`；其他錯誤放回佇列並以 1s、2s、4s… 退避（上限 30 秒），同一事件連續失敗 20 次才進死信，避免單一事件卡住整條佇列；單一事件獨佔時以退避計算約 9 分鐘，一批多筆輪流重試時每筆各退避一次，要數倍到數十倍時間，所以進死信前先由 `GameRecordConsumerRetrying` 告警（5 分鐘內有 `result="retry"` 且無成功寫入，持續 5 分鐘，warning）提醒。失敗次數紀錄保留 2 小時（`failureRetention`），超過仍未再失敗的事件從頭計；`recordmq_queue_messages` 在重試退避期間仍每 15 秒取樣。MySQL 長時間故障後，`<queue>.dead` 可能留有當時正在重試的少數事件，恢復後確認內容再重送。

Record `/events` 查詢的 `event_type` 超過欄位長度 64 時直接回 `400 event_type too long`（必然查無資料，免得對 31 張分表各跑一次 UNION）。事件寫入的時間下界與查詢涵蓋的分表對齊：取最舊查詢分表的當日 00:00（UTC，`earliestAcceptedAt`；表名與回看範圍一律以 UTC 計，與行程時區無關），不是 `now-31 天` 的瞬間，落在界線與最舊分表當日 00:00 之間的事件不會寫入後查不到。

## 現場採證（服務卡住、CPU 高、記憶體持續成長）

原則：**先採證再重啟**。重啟會清掉 goroutine、heap 與鎖的現場，之後只剩症狀。判斷卡住時先看指標：`game_event_loop_last_tick_timestamp_seconds{service}` 停止更新（`GameEventLoopStalled`）才是事件迴圈卡死；`game_event_queue_depth` 只在排空時更新，迴圈卡住時會凍結在舊值，不能當依據。

**前置條件：pprof 是否可用。** 正式環境 pprof 缺省**關閉**：`debug.pprof_enabled` 缺省為 false，`docker/prod/config/*.yaml` 沒有這個鍵；dev 與 docker 範例設定只有 Central、Gate、World 明確寫 `true`（Chat、Lobby、Record、User 沒有這個鍵，缺省關閉，要先在設定補上才有 `/debug/pprof/`）。要在正式環境開：

1. 在該服務設定檔寫 `debug.pprof_enabled: true`（需重啟該服務，所以卡住當下通常來不及，建議平時就在要觀察的服務開好）。
2. `.env.prod` 設定 `DEBUG_PPROF_BASIC_AUTH=user:pass`：`compose.prod.yml` 六個服務**必填**（缺值 `compose up` 直接失敗），密碼至少 16 字元、不可 `change-me` 開頭；不合格時 pprof 與 Gate `/diag/session`、`/diag/player`、`/diag/reconcile`（GET 與 POST）一律回 503 並記 Error；`/diag/protocol` 不受 basic auth 保護，只靠來源 CIDR 與 Host 檢查。空字串（僅本機開發）則只靠來源 CIDR 並記 Warn。受保護的寫入端點（Gate `POST /diag/reconcile`）外層還有跨站防護（`http.CrossOriginProtection`）：瀏覽器從別的網站送來的請求（`Sec-Fetch-Site`／`Origin` 顯示跨站）回 403；curl 等 CLI 不帶這些標頭，不受影響。
3. 啟動日誌沒有 Info `pprof disabled; set debug.pprof_enabled=true to enable`，才代表 pprof 已註冊。環回位址永遠允許，所以可以進容器內取：`docker exec <容器> wget -qO- --user=<user> --password=<pass> 'http://localhost:<診斷埠>/debug/pprof/goroutine?debug=2' > goroutine.txt`（診斷埠見[健康檢查端點](#健康檢查端點)；本機直接 `curl -u user:pass`）。

**服務卡住（hang）**

- `curl -u user:pass 'http://127.0.0.1:<診斷埠>/debug/pprof/goroutine?debug=2' -o goroutine.txt`：所有 goroutine 的完整堆疊；找停在 `sync.Mutex.Lock`、`chan receive`、`select`、`IO wait` 很久的，同一個位置大量重複通常就是根因。`debug=1` 為合併後的摘要。
- Go 1.27 的 `/debug/pprof/goroutineleak`：列出被判定為永遠無法喚醒的 goroutine（洩漏）。
- 鎖爭用：`rate(go_sync_mutex_wait_total_seconds_total[5m])` 持續偏高再開 `PPROF_MUTEX_FRACTION`，抓 `/debug/pprof/mutex`；這個環境變數只在啟動時讀一次，要重啟（爭用現場會隨之消失），且只在 `debug.pprof_enabled=true` 時生效（pprof 停用時不套用取樣，啟動記 Warn `PPROF_MUTEX_FRACTION／PPROF_BLOCK_RATE set but pprof disabled`），所以要觀察的服務平時就以低取樣率（例如 100）開著。
- **第一個採證來源是日誌**：事件迴圈超過 20 秒沒有 tick 時，行程會自動記 Error `event loop stalled`（`name`、`stalledFor`）並輸出一筆 `event loop stalled, goroutine dump`（`reason` 為服務名），同一次卡死只輸出一次、tick 恢復後重新武裝（看門以單調時間計算，NTP 校時或 VM 暫停恢復造成的牆鐘跳動不會誤報或漏報），比 `GameEventLoopStalled`（30 秒）更早；先查這筆日誌，不必重啟開 pprof 或送 SIGQUIT。事件迴圈本體 panic 後看門 goroutine 會一起結束，不會在 20 秒後補報 `event loop stalled`；此時要看的是 `panic recovered`（`msg="event loop panic recovered"`）與之後的關機日誌。
- 關機卡住時不必手動抓：關機任務逾時（drain 除外）、`appcore: event loop did not stop`、最後等背景工作逾時，都會有一筆 Error `shutdown timed out, goroutine dump`（`reason`、`truncated`、`goroutines`），debug server 也會一直開到關機最後的 Cleanup。Lobby 遊戲時鐘停止（`reason=lobby game clock stop`）與 Record 背景工作停止（`reason=record background workers stop`，5 秒）、HTTP 優雅關閉（`reason=http shutdown timed out: <addr>`，5 秒）逾時同樣會輸出堆疊。

**CPU 高**

- `curl -u user:pass -o cpu.pprof 'http://127.0.0.1:<診斷埠>/debug/pprof/profile?seconds=30'`，再 `go tool pprof -top cpu.pprof` 或 `go tool pprof -http=:0 cpu.pprof`。debug server 沒有 WriteTimeout，30 秒 profile 不會被截斷。
- 同時看 `go_sync_mutex_wait_total_seconds_total` 與 `game_sched_latency_p99_5m`，分辨是算力不足還是鎖等待。
- **排程延遲、GC 停頓、goroutine 飢餓**：抓執行追蹤 `curl -u user:pass -o trace.out 'http://127.0.0.1:<診斷埠>/debug/pprof/trace?seconds=5'`，再 `go tool trace trace.out`。追蹤檔會很大且有額外負擔，只抓 5 秒左右。
- **GC 行為**：對單一服務在 compose 加環境變數 `GODEBUG: gctrace=1`（排程用 `schedtrace=1000`）後重啟該服務，輸出到 stderr，不必改程式。`gctrace=1` 每次 GC 一行、`schedtrace` 每秒一行，會增加日誌量，採完證據就移除。

**記憶體持續成長**

- `curl -u user:pass -o heap1.pprof 'http://127.0.0.1:<診斷埠>/debug/pprof/heap'`，過一段時間（成長明顯後）再抓 `heap2.pprof`，用 `go tool pprof -base heap1.pprof heap2.pprof` 看增量。
- `go_goroutines` 持續上升就改看上面的 goroutine 摘要與 `goroutineleak`，記憶體成長多半來自洩漏的 goroutine。

**pprof 不可用、日誌也沒有自動堆疊時**（正式環境缺省，或已經來不及重啟開啟）：先依序試非破壞性的做法，最後才用 SIGQUIT。

1. 日誌自動堆疊：事件迴圈卡死的 `event loop stalled, goroutine dump` 與關機逾時的 `shutdown timed out, goroutine dump`（Error，見上）；SIGUSR1 主動採證不走 logger，直接寫 stderr 的 `goroutine dump requested, reason=...`（見下）。
2. **不結束行程的堆疊管道（SIGUSR1，Linux 容器）**：`docker exec <容器> sh -c 'kill -USR1 1'`，行程把全部 goroutine 堆疊以 `debug=2` 格式（逐條列出，含 `[chan receive, N minutes]` 這類狀態與等待時間，可分出卡很久的 goroutine）**直接寫到 stderr**，第一行為 `goroutine dump requested, reason=<訊號名>`，並繼續運作，不走關機流程、不遺失資料；因為不經 logger，**不受 `LOG_LEVEL` 影響**（`LOG_LEVEL=error` 也印得出來），也不是 JSON 日誌行、不觸發 Error 日誌告警，與關機逾時的 Error `shutdown timed out, goroutine dump`（走 logger、`debug=1` 合併格式、截到 128 KiB）是不同管道；之後 `docker logs <容器>` 取堆疊（stderr 內容夾在 JSON 日誌中間，用 `goroutine dump requested` 搜起點；標題之後可能夾雜數行 JSON 日誌，以標題定位後往下找第一個 `goroutine N [` 行才是堆疊本體）。傾印期間行程會短暫停頓（需先停住 goroutine 取堆疊），goroutine 極多時 runtime 會把輸出截斷在 64MB。World 與 MySQL 異常時也適用，是採證的第一選擇；Windows 沒有此訊號。
3. 診斷埠只綁環回位址時，進容器內用 `docker exec` 打 `/debug/pprof/goroutine?debug=2`（前提是該服務已開 `debug.pprof_enabled`；沒開就只能重啟開，開了之後下一次卡住才抓得到）。
4. 以上都沒有，才用 `docker exec <容器> sh -c 'kill -QUIT 1'`（映像以 `app` 使用者執行，PID 1 就是 Go 行程）：Go 收到 SIGQUIT 會印出所有 goroutine 堆疊（映像預設 `GOTRACEBACK=all`）並**立即結束行程**，Docker 視為行程自行結束，restart policy 照常拉起（不要改用 `docker kill -s QUIT`：`docker kill` 會把容器標成手動停止，`unless-stopped` 不會重啟，服務會一直停著，要自己 `docker start <容器>`）；之後 `docker logs <容器>` 取堆疊。

**SIGQUIT 的資料風險（尤其是 World）：** SIGQUIT 不走 `RunApp` 的關機任務，跳過 World 的最後寫回、spill 落地與 Record sink 排空。正常重啟（SIGTERM）不會遺失的玩家異動，在這條路上會遺失；例如 MySQL 正卡住、異動全堆在記憶體時，SIGTERM 會落地到 spill 檔，SIGQUIT 不會。所以：

- **MySQL 或其他依賴異常時，不要對 World 使用 SIGQUIT**；先確認依賴正常，或接受該 World 記憶體內尚未寫回的異動會遺失。
- Gate、Central、Lobby、Chat 沒有 World 的最後寫回問題，但 Gate 的連線與 pending session 同樣會直接斷掉，玩家需重連。
- 要採證又不想冒資料風險，先用上面第 2 點的 `kill -USR1 1`（不結束行程）；只有它也印不出來時才考慮 SIGQUIT。

採證完畢才重啟，並把 `goroutine.txt`／`cpu.pprof`／`heap*.pprof`、關機堆疊日誌與當時的 `game_event_loop_last_tick_timestamp_seconds` 附在[故障單](故障單模板.md)。

## 日誌關鍵字速查

| 關鍵字 | 含義 |
|--------|------|
| `login failed` | 登入失敗。訊息以冒號帶原因（如 `login failed: bcrypt busy (sampled)`、`login failed: account lock timeout`），欄位多為 `requestID`、`err`，**沒有 `code` 欄位**；回給 Gate 的 `responseCode` 只出現在 Debug 日誌 `login failed, notifying gate directly`（預設 Info 看不到），改以 `game_login_total` 的 `result` 看分布 |
| `DB error` | MySQL 連線或查詢失敗 |

| Lobby `/admin/ban` 之後的補踢日誌 | 封禁設有 `rekickDelay` 時由 `gm.Rekicker` 排程延後再踢一次（玩家正在登入、封禁當下踢不到時補上），工作納入 Lobby 生命週期：延遲等待隨關機 ctx 取消，組合根在關 Redis 前等待。關機時尚未觸發的補踢記 Warn `gm: rekick after ban skipped by shutdown`（`accountHash`），屬預期；補踢失敗記 Warn `gm: rekick after ban failed`（`accountHash`、`err`）；補踢成功踢到在線玩家記 Info `gm: rekick after ban kicked online player`（`accountHash`、`kickedGateID`），沒踢到人不記 |
| 稽核日誌的來源與角色欄位 | `audit=true` 的管理端點稽核行（Lobby admin／gm、Record `/events`、Gate `/diag/reconcile`）來源欄位三服務統一為 camelCase：`remoteAddr`，經反向代理時另有 `xRealIP`、`xForwardedFor`（由 `httpx.AuditFields` 產生）；舊版 Lobby／Record 的 `remote_addr`、`x_real_ip`、`x_forwarded_for` 已改名，Loki／jq 查詢要用新鍵（歷史日誌仍是舊鍵，跨版本查詢兩種都要帶）。GM 操作日誌另帶 `actorRole`（原 `actor_role`，值 `admin`／`ops`／`gm`），是實際授權通過的 token 層級，不含 token 本身 |

| 回應碼 `AuthWrongPassword`（13）、`login failed, notifying gate directly`（**Debug**，欄位 `responseCode`，第十輪前叫 `code`） | 密碼驗證失敗（新帳號空密碼也回 13，日誌為 `login failed: new user without password`）；沒有 `wrong password` 日誌，量看 `game_login_total` 的 `result` |

## 查詢降級

- Central audit record 讀取現在有 DB -> Redis cache fallback。
- 若看到 `central audit query degraded to cache`，代表 DB 短暫失敗，但快取命中，讀路徑還活著。
- 若快取也失敗，會回原本 DB error；先查 MySQL、再查 Redis、再看 cache key 是否過期。
- Redis routing / account 壞欄位時，Central audit 會直接報 invalid，不再把 `0` 當正常值。
- Central audit 做 Redis 修復時，壞 `gate/world` 也會算 drift，不會因為 memory 剛好是 `0` 就漏修。
- `configaudit` 遇到 Prometheus `scrape_configs` 結構壞掉會直接報錯，不再默默跳過。
- `opsdiag` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode opsdiag`；預設會維持 `--fail-on-degraded`
- `dephealth` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- `datasurgeon` apply 模式會刪掉 malformed `player:` / `world:*:players` key，不再讓壞 key 永久殘留。
- `datasurgeon` 讀 `player:` 狀態會對未知欄位報錯，不再把拼字錯誤的狀態當真。
- `datasurgeon` deadletter apply 模式會刪掉 malformed `gm:grant_item:deadletter:*` key，不再讓壞隊列殘留。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode datasurgeon -DataSurgeonMode <mode>`；預設只做觀察，`-DataSurgeonApply` 才會真的修 Redis。
- `pkg/grantitem` 讀 GM 命令會對未知欄位與尾巴資料報錯，不再把壞 deadletter 當真命令。
- `pkg/playerstoreredis` 讀玩家狀態會對未知欄位報錯，不再把壞 JSON 當真玩家資料。
- `cmd/world/internal/store/requestjournal` 讀 Redis journal 會對未知欄位與尾巴資料報錯，不再把壞 journal 當成 miss。
- `pkg/msg` 的 `AuditSnapshotRequest/Response` 解析會對未知欄位與尾巴資料報錯，不再吞掉快照拼字錯誤。
- `tools/private/consistencysnapshot` 會對 Prometheus 非 200、未知欄位與尾巴資料報錯，不再把壞快照寫出去。
- `tools/private/opsdiag` 的 `/ready` 解析會對未知欄位、尾巴資料與空 checks 報錯，不再把壞 ready 當正常。
- `tools/private/consistencysnapshot` 會對 endpoint down 與 Prometheus 非 200 / 壞 JSON 報錯，不再把壞快照寫出去；統一入口是 `scripts/private/p0-daily-check.ps1 -Mode consistencysnapshot`；`-output` 指定巢狀路徑時會自動建立父目錄
- `tools/private/playersnapshot` 會對 gate diag 與 ready 壞回應報錯，不再把壞快照當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- `tools/private/supportdiag` 會對 session 與 ready 壞回應報錯，不再把壞客服資料當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- （歷史）`tools/configdrift` 的 `mustGetString` 會對 nil config 回錯，不再 panic；該工具已移除，路由檢查併入 `tools/configaudit`。
- `configaudit` 會把 Grafana datasource 的 `url` 型別錯誤直接報成 invalid，不再當空值處理。
- Gate central ring 遇到 `ConnectInfo.ID == 0` 時會忽略，不再把 `0` 放進 hash ring。
- `deadletterreplay` 遇到 malformed deadletter key 會直接報錯，不再默默跳過。
- `deadletterreplay` 遇到 malformed deadletter payload 也會直接報錯，不再把壞 payload 吞掉。
- Lobby admin 的 grant-item dead-letter 列表會把無法解碼的 payload 以 `invalid:true` 列出（`operationID` 為內容雜湊），不會讓整個列表失敗；replay 回 400，只能 discard。
- `playersnapshot` 與 `supportdiag` 讀 deadletter 時，遇到 malformed payload 會直接報錯，不再靜默跳過。

## 慢查追蹤

- `game_audit_record_lookup_seconds` 會記 Central audit record lookup 的 DB / cache 延遲。
- `central audit query slow` 代表該次 lookup 超過 `mysql.audit_record_slow` 閾值（帶單位的時長，原名 `mysql.audit_record_slow_ms` 已不再讀取），先看 MySQL 查詢、再看 Redis fallback。
- 若 p95 變差但沒有 error，通常是慢查不是故障；先查索引、鎖競爭、以及 cache 命中率。

## 資源自動回收

- `game_resource_recycle_total{service,resource}` 記各服務清掉的過期狀態，實際的組合只有：
  - `central` / `world_warmup`：Central 每分鐘（`Update1m`）回收的 World 冷卻記錄數。
  - `central` / `gate_disconnected`：Gate 斷線寬限到期（30 秒，每 5 秒掃描）後清掉的玩家數。
  - `central` / `gate_sync_stale`：Gate 重連後以在線快照對帳，移除快照裡已沒有的玩家數。
  - `gate` / `world_unavailable`：Gate 對 World 斷線寬限到期後清掉的玩家數。
  - `world` / `gate_unavailable`：World 對 Gate 斷線寬限到期後清掉的玩家數。
- 寬限類計數平時應為 0；持續增加代表對端反覆斷線超過寬限，先看對端存活與網路，再看 `game_service_grace_total`。

- `scripts/private/alert-selfheal.ps1` 是告警 warning 的輕修復入口。

- `scripts/change-approval.ps1` 會寫 release/config/schema 審批 stamp。

## 服務分級

- `tools/private/dephealth` 把服務分成 `critical / core / peripheral`。
- `central`、`gate`、`world` 是 `critical`；`user` 是 `core`；其他暫歸 `peripheral`。
- 告警、限流、看板先盯 `critical`，`core` 次之，`peripheral` 再後。

## 冷資料搬遷

- `tools/private/coldstorage` 會把 `central:audit:record:*`、`gm:grant_item:deadletter:*`、`fault:archive:*` 匯出成 JSONL。
- `-purge` 會在匯出後刪 Redis 熱 key。
- 先 `-dry-run` 看 manifest，再決定要不要真搬。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode coldstorage`；預設只做 dry-run，看 manifest 不動資料。
