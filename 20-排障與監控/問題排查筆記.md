## 排查工具箱

### 工具箱目的

`tools` 這一組是給值班、排障、回歸測試用的刀具箱，目標是：

- 快速確認服務是否正常
- 快速查單一帳號、session、路由
- 快速追一筆協定的送收鏈路
- 快速看 dead-letter、健康狀態、配置漂移
- 盡量少翻 log、少手查 Redis、少進服務內部

### 依賴健康總表

用 `tools/private/dephealth` 一次看 `ready`、service class、queue 深度：

```bash
go run ./tools/private/pja dephealth -json
```

用途：
- 值班先看整體健康，不先翻細節 log
- 快速分辨 `critical / core / peripheral` 哪一層在退化
- `readyFail > 0` 或 `status=degraded` 時，再往下查 queue / async failure

### 本機監控入口

若要先把 Grafana / Prometheus 接起來，再看值班面板：

- [本機監控](./本機監控.md)

用途：
- 先開 `本機監控`，再看 `Dependency Health`
- `dephealth` 先抓服務整體狀態
- `opsdiag` 再補路由查核與關鍵 metrics 摘要
- 要把監控、告警和一致性快照一起跑，直接用 `scripts/private/p0-daily-check.ps1 -Mode env`

### 狀態對帳入口

當 `game_state_audit_total` 出現 `mismatch` 或 `error`：

- 先進 [狀態對帳流程](./狀態對帳流程.md)
- 先看 `result`
- `mismatch` 看索引 / 路由
- `error` 看 Redis / MySQL / timeout
- `repair` 表示已修回一部分漂移，但根因還要追
- 要驗收斂 gate，直接用 `scripts/private/p0-daily-check.ps1 -Mode reconcile`

### 事故時間線

用 `scripts/incident-timeline.ps1` 把多份 log 依時間排序：

```powershell
powershell -ExecutionPolicy Bypass -File ./scripts/incident-timeline.ps1 -Path .\logs\central.log,.\logs\gate.log,.\logs\world.log
```

用途：
- 自動拉出 `route / session / alert / deploy` 時序
- 事故復盤先看時間線，再看單點 log
- `-Json` 可直接丟給別的分析工具

### 故障單模板

每次事故先用固定格式記錄：

- `docs/20-排障與監控/故障單模板.md`

用途：
- 先填人、時間、影響、處置、回滾、結論
- 後續再補 log、dashboard、metrics、commit
- 事故資訊先收斂成同一種格式，復盤比較快

### 配置熱重載

現在主服務會盯 config 檔：

- 所有走 `startup.InitializeRuntime` 的服務（Central、Gate、World、Chat、Lobby、Record、User）
- config 檔變動後，會重新讀 `viper`
- 可熱更的只有白名單，由各服務經 `startup.WithHotReload(HotReload{Prefixes, Apply})` 宣告：共用的 `protocol_record*`（`protocol-record` 旗標不經 viper、不熱更）、Central 的 `traffic_slice_*`、Lobby 的 `admin_token`／`ops_token`／`gm_token`；`feature.central.state_auditor` 與其他鍵只在啟動讀，改了要重啟
- 日誌有三種，判讀不同：
  - Info `config hot reload applied`（`keys`）：`keys` 只列這次**真的套用**的鍵；不再只看鍵名前綴就當作生效
  - Warn `config hot reload not applied`（`keys`、`err`）：服務宣告可熱更的鍵套用失敗（值無效、token 驗證失敗，或 Lobby 啟動時沒有 token、事後才補上——需重啟才有 admin 端點）；修正值或重啟，不要當作已生效
  - Warn `config change requires restart, not applied`（`keys`）：改了不可熱更的鍵，看到它就重啟
- Central 在 `initStorage` 期間收到的 `traffic_slice_*` 重載，會在 App 建好後套用，不再被啟動時的舊值蓋掉
- 資料設定（dataconfig）watcher 啟動時若 `current.json` 損壞或排程時間有誤，會立即走 reload 路徑、記 failed 計量（`data_config_reload_total{result="failed"}`）並呼叫 `onError`，不必等到下一次檔案事件才發現
- 協定檔案記錄（`protocol_record_file_*`）參數沒變時沿用同一個記錄器，熱重載不會每次關檔重開
- 正式 compose 掛整個設定目錄；改完確認出現 `config hot reload applied` 且 `keys` 含你改的鍵，沒有就看有沒有 `not applied`／`requires restart`，再決定修值或重啟

用途：
- 改旗標或 canary 切流，不必全重啟
- 出事先回改 config，少跑一輪 deploy
- 若某值仍是 startup cache，要回頭看是不是還沒接到 reload callback

## 先看 SLO

值班先看少數主指標。其他 metrics 只用來定位根因，不當主畫面。

1. 登入成功率與延遲
   - 主看：`game_login_total{result="success"}` 與失敗值（`busy` 或 `errcode.MetricOutcomeFromAuthResultCode` 的值，如 `server_fail`、`rate_limited`）、`game_login_duration_seconds`（毫秒級桶，與 `game_login_e2e_seconds` 一致）、`game_login_e2e_seconds`
   - 意義：登入鏈路有冇被 DB、鎖、World 路由拖慢
2. 登出成功率與排空
   - 意義：logout / drain 有冇卡住或落資料
3. 恢復校驗成功率
   - 主看：`game_recovery_validation_total`、`game_recovery_validation_replay_cache_total`
   - 意義：World 重啟後有冇收斂
4. 重連成功率
   - 主看：`tcp_reconnect_attempts_total`、`tcp_reconnect_total`
   - 意義：Gate / World / Central 斷線後有冇真恢復
5. 狀態對帳健康度
   - 主看：`game_state_audit_total`
   - 意義：長跑後有冇漂移、repair 有冇跟上

### SLO 告警分級

三層就夠：

1. `warning`
   - 有風險，但先看趨勢與 headroom。
   - 例：`game_login_failure_ratio_5m`、`game_handler_duration_p95_seconds`
2. `page`
   - 已經影響使用者或資料收斂，值班要直接看。
   - 例：`game_handler_duration_p99_seconds`
3. `ignore`
   - 只進 dashboard 或 debug，不做 alert。
   - 例：高基數 debug 值、單次排查用 counter

原則：
- `page` 要少，`warning` 要能收斂成 `page`，`ignore` 不進告警
- 先看 SLO，再看對應 log / trace / queue depth

### 日誌追蹤

遊戲鏈路的日誌欄位是 `gameTraceID`（十進位 int64，由 ctx 自動附上）；請求編號欄位是 `requestID`。`trace_id`／`span_id` 是 OTel span 的欄位（32 位 hex），只在有 span 時才出現，正式環境 `otel.exporter` 為空時根本沒有。預設日誌格式是 JSON，可一次搜尋整條鏈路：

```bash
# 追蹤單一請求在所有服務的日誌
grep '"gameTraceID":123456' central.log gate.log world.log
# 或用 jq 過濾
jq -c 'select(.gameTraceID==123456)' central.log gate.log world.log
# 以請求編號查
grep '"requestID":"<id>"' central.log gate.log world.log
```

已知限制：`gameTraceID` 是行程內序號，多個 Gate 實例同一毫秒可能撞號，跨實例查詢要搭配 `requestID` 或時間範圍過濾（見[日誌規範](../30-部署與開發/日誌規範.md)）。

### 協定記錄

各服務 debug server 現在提供 `/diag/protocol`：

- `GET /diag/protocol?traceID=...`
- `GET /diag/protocol?requestID=...`
- `GET /diag/protocol?limit=...` 直接看最近一批記錄
- 這個路由由 `pkg/debug` 直接掛載，不需要各 app 再手動註冊
- `pkg/debug` 的額外路由以 `*debug.Server` 的 `HandleFunc`（一般）或 `HandleProtectedFunc`（需 `DEBUG_PPROF_BASIC_AUTH`）掛到私有 mux

用途：
- 直接看同一條協定鏈的送收事件
- 每筆記錄會帶 `service / direction / msgID / requestID / traceID / status`
- 先從 Gate / Central / World 的邊界點查，再往下看 handler
- 記錄功能本身可開關：`protocol_record_enabled` 預設在 debug 設定開、prod 設定關；`DEBUG_PROTOCOL_RECORD` 可手動覆蓋（接受 `true/false/on/off/yes/no`；無法解析記 Warn 並退回設定值）
- 記錄容量與保留時間可由 `protocol_record_limit` / `protocol_record_ttl` 調整
- 啟動旗標 `-protocol-record=true|false` 會優先於 `DEBUG_PROTOCOL_RECORD`，再往下才看設定檔的 `protocol_record_enabled`；旗標不經 viper，設定檔寫 `protocol-record` 鍵沒有作用

### 跨服務合併查詢

用 `tools/private/protocoldiag` 一次抓 `Central / Gate / World` 的 `/diag/protocol` 並合併排序：

```bash
go run ./tools/private/pja protocoldiag -trace-id 123
go run ./tools/private/pja protocoldiag -request-id 456
```

用途：
- 一次看三邊同一條鏈路
- 輸出會包含每個服務的子結果與合併後的 `records`
- 若某個服務查詢失敗，仍會回其他服務成功抓到的記錄與該服務錯誤
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode protocoldiag -ProtocolDiagTraceID <id>`；`-ProtocolDiagRequestID` 也可單獨使用。

### 健康檢查端點

| 服務 | 端點 | 用途 |
|------|------|------|
| Central | `http://localhost:6060/ready` | DB ping 確認 |
| Gate | `http://localhost:6061/ready` | 服務就緒 |
| World | `http://localhost:6062/ready` | 服務就緒 |
| User | `http://localhost:6063/ready` | 服務就緒 |
| Lobby | `http://localhost:6064/ready` | 服務就緒（含 `time_sync`） |
| Record | `http://localhost:6065/ready` | 服務就緒 |
| Chat | `http://localhost:6066/ready` | 服務就緒（含 `time_sync`） |

TCP 伺服器（Gate 玩家端、Central、World、Chat）會註冊 `tcp_listen_<名稱>` 檢查：尚未監聽成功、監聽失敗（例如埠被占用）或已停止接受連線時 `/ready` 回 503。監聽失敗時行程不會退出，只有這個檢查會失敗，查 `/ready` 的 body 看原因。`/ready` 的各項檢查並行執行、各自上限 3 秒（`ReadyCheckTimeout`），整體耗時約等於最慢一項，不會因多項同時無回應而超過 Docker HEALTHCHECK 的 5 秒；單項檢查 panic 會轉成該項的錯誤，不會讓整個 `/ready` 失敗得沒有原因。檢查回傳的錯誤訊息為空時 body 填 `unknown error`。`/ready` 結果由成功轉為失敗時記一行 Warn `ready check failed`（`failed` 為失敗項目摘要），恢復時記 Info `ready check recovered`；容器 healthcheck 丟掉輸出，事後查 readiness 抖動看這兩行。`opsdiag`、`dephealth` 等工具讀到 503 時會解碼 body，錯誤顯示為 `503 Service Unavailable: status=fail <失敗的檢查項目>`；其他非 200 狀態仍帶 body 開頭。

啟動與關機期間的幾個行為（第六輪調整）：

- 啟動自檢與 S2S TLS／身分握手現在都隨停止訊號（ctx）中止，不再等滿逾時（自檢 5 秒、握手 n×3 秒）。
- `RunTCPService` 新增 `selfCheck` 參數，`/ready` 檢查改由組合根傳遞的 `*debug.Server` 登記，沒有全域登記表。Gate 的 `/diag/*` 路由在 debug 伺服器開始監聽**之後**才登記，啟動瞬間打 `/diag/*` 可能 404，對 `/ready` 與 `/metrics` 沒有影響。
- World 沒有設定 MySQL（`mysql.host` 為空）時，在 `openWorldStores` 就拒絕啟動，錯誤含 `world requires the memory game store`（`game store setup: mysql is not configured, ...`）；`max_players` 為負值同樣拒絕啟動（`max_players must not be negative`）。World 啟動時 `watchGameConfig` 先於傳輸層，設定監看失敗不會留下已接受 Gate 連線卻沒人收尾的傳輸層。
- Central 共享路由（Redis）的讀寫改用呼叫端 ctx 且不受取消影響：關機 drain 期間登出仍會刪除路由，不再殘留最長 24 小時的幽靈在線。讀取失敗時有 Warn `central: shared routing read failed, falling back`。

### 服務抓取失敗（GameServiceDown）

`GameServiceDown`（`up == 0` 持續 1 分鐘，page）代表 Prometheus 抓不到該 job 的 `/metrics`，告警 labels 的 `job`／`instance` 指出是哪個服務。處置：

1. 看容器或行程是否還在（`docker compose ps`）；已退出就查最後的日誌找退出原因。
2. 行程還在時打 `http://localhost:<埠>/ready`（埠見上表）：連不上代表 debug HTTP 沒起來或卡住；回 503 看 body 是哪個檢查失敗。
3. 服務正常但仍 `up == 0`：查 Prometheus 抓取設定的 target 與埠是否對上 `pkg/debug.Endpoints`（`go run ./tools/pja configaudit`），以及網路（本機監控用 `host.docker.internal`）。
4. 服務恢復後 `up` 回到 1，告警自動解除；同一 job 的 warning 在 page 期間被正式環境 Alertmanager 抑制，恢復後再看是否仍有 warning。

Gate、World、Chat、Lobby 另註冊 `time_sync` 檢查（`debug.RegisterRuntimeReadyChecker`）：收到 Central 第一則 `TimeSync` 前 `/ready` 回 503。它只列入 `/ready`、不列入啟動自檢，Central 晚啟動時服務不會自行退出，收到 TimeSync 後自動就緒；長時間不就緒先查 Central 是否可達、`<id>.dial.central` 與 Central `listen.*` 埠是否對上（`go run ./tools/pja configaudit`、`tools/private/opsdiag` 的 route 段）、S2S token。

### 程式與持久化告警

以下告警的 `runbook_url` 都指向本文件，定義在 `monitoring/prometheus/alert-rules.yml`：

| 告警 | 條件 | 等級 | 處置 |
| --- | --- | --- | --- |
| `GamePanicRecovered` | `increase(game_panic_recovered_total[5m]) > 0`，或 5 分鐘前不存在的新 `msg` 序列（依 `job`、`instance`、`msg`；第一次 panic 才出現的序列也會告警） | page | `appcore.RecoverPanic` 或就地 recover 擷取到 panic，服務帶病續跑；依 `msg` 到日誌找 stack 修正。玩家連線 handler、World 登入活動、Record 消費迭代、斷路器 callback、recordmq handler、關機任務、dataconfig reload／prepare 等自己 recover 的路徑，也都遞增此計數 |
| `GameAccountPurgeFailing` | `game_account_purge_total{result="failed"}` 一天內增加 | warning | 每日帳號清除（保留期合規作業）有失敗；World 暫時不可用不計入，下輪自會重試。看 Central 日誌 |
| `GameRecordOutboxDeadLetter` | `game_record_outbox_total{result="dead_letter"}` 5 分鐘內增加 | page | World Record outbox 事件重試耗盡轉入 dead letter，不會再送 Record；查 Record／RabbitMQ 可用性與 World 日誌找出失敗原因，再決定人工補送 |
| `GamePlayerVariableFlushFailure` | `game_player_variable_flush_total{result="failed"}` 5 分鐘內增加，持續 2 分鐘 | page | World 玩家變數寫回 MySQL 持續失敗，異動只留在記憶體；先查 MySQL 連線與慢查詢，勿重啟 World 以免遺失 |
| `GameBoardTopologyMigrationFailed` | `game_board_topology_migration_total{result="failed"}` 5 分鐘內增加 | warning | 玩家盤面拓撲遷移失敗，該玩家盤面無法載入；看 World 日誌與設定版本，必要時用 `cmd/world/tools/topologybaseline` 檢查基準點 |
| `GameEventLoopStalled` | `time() - game_event_loop_last_tick_timestamp_seconds > 30` 持續 1 分鐘 | page | app 事件迴圈超過 30 秒沒有 tick，handler 可能卡死。`game_event_queue_depth` 只在排空時更新，迴圈卡住時會凍結在舊值，**判斷卡死看 tick 時間戳**；先照[現場採證](#現場採證服務卡住cpu-高記憶體持續成長)抓 goroutine，不要先重啟。目前沒有 `/ready` 的迴圈存活檢查 |
| `GameAccountPurgeStalled` | `time() - game_account_purge_last_run_timestamp_seconds{job="central"} > 2 * 86400` 持續 1 小時（只看 Central；Central 啟動時就設為現在） | warning | 每日帳號清除超過 2 天沒有完整跑完（沒有 World 連線時該輪直接略過、不計失敗，所以 `GameAccountPurgeFailing` 看不到停擺）；查 Central 與 World 的連線 |
| `GameGrantItemDeadLettered` | `game_async_failure_total{queue="grant_item",outcome="dead_lettered"}` 5 分鐘內增加 | warning | GM 發道具重試耗盡或原文無法解碼而轉入死信，玩家沒拿到道具；用 `/admin/grant-item/dead-letter` 查看並補發，死信再處理見[死信再處理](#死信再處理) |
| `GameCircuitBreakerOpen` | `min_over_time(circuit_breaker_state[2m]) >= 1` 持續 1 分鐘（依 `name`） | page | 斷路器 2 分鐘內從未回到 closed；half-open 試探不再重置計時，持續故障不會因試探而漏報。`name` 指出是 MySQL 或 Redis 等哪一個；日誌為 Warn `circuit breaker state changed` |
| `GameProcessRestarted` | `changes(process_start_time_seconds[15m]) > 0`（六個服務） | warning | 行程重新啟動；發版也會觸發一次。非發版時查 `docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' <容器>`，再用 `docker logs --since <時間> <容器>` 找 `goroutine 1 [` 起頭的崩潰堆疊 |
| `GameGoroutineLeakPossible` | `delta(game_goroutines_residual[1h]) > 500` 且 `deriv(game_goroutines_residual[30m]) > 0`，持續 30 分鐘 | warning | 扣掉連線後的 goroutine 持續成長，疑似洩漏；先抓 `/debug/pprof/goroutine?debug=1` 再重啟（門檻待壓測校正） |
| `GameRedisCommandErrors` | `increase(redis_command_errors_total[5m]) > 10`（依 `op`），持續 5 分鐘 | warning | Redis 指令持續失敗；先看 Redis 連線、延遲與 `circuit_breaker_state` |
| `GameDBPoolWaitHigh` | `rate(go_sql_wait_duration_seconds_total[5m]) > 0.05`（依 `db_name`），持續 5 分鐘 | warning | MySQL 連線池飽和；查慢查詢或調大 `mysql.max_open_conns`，World 登入批次池看 `<db>_batch` |
| `Watchdog` | `vector(1)`，恆為 firing | info | 告警管線存活訊號，Alertmanager 路由到 blackhole，平常不通知；要當死人開關需另外把它接到外部心跳服務（接收端 N 分鐘沒收到就通知），目前沒有接。正式環境也還沒有 MySQL／Redis／RabbitMQ exporter |

### Prometheus 關鍵指標

- `tcp_connections_active` — 只算 accepted connection；異常下降 = 網路問題
- `pkg/tcpclient` 的 rate limit 會從 `RemoteAddr()` 解析 host；若解析失敗，會退回原始地址，不會把異常來源壓成空字串共用桶。
- `tcp_send_queue_overflow_total` — 佇列溢出 = 對端處理不及
- `tcp_unknown_messages_total` — 收到沒有型別或 handler 的訊息；玩家連線會被關閉，S2S 連線只丟棄。S2S 持續增加代表服務間協定版本不一致或漏註冊 handler
- `game_account_lock_total` — 帳號鎖定頻率
- `game_account_lock_wait_seconds` — 帳號鎖等待時間（p95 高 = 鎖競爭瓶頸）
- `game_login_db_query_seconds` — 登入 DB 查詢延遲（`find` / `save`）
- `game_handler_duration_seconds` — Handler 延遲分佈
- `game_heartbeat_timeout_total` — 心跳超時被踢次數
- `game_world_online_players` — 各 World 在線人數
- `game_panic_recovered_total` — `RecoverPanic` 擷取的 panic 次數（label `msg`），任何增加都觸發 `GamePanicRecovered`。背景 goroutine 與服務本體的 `msg` 帶服務名（`<服務名> async panic recovered`、`<服務名> service body panic recovered`），dataconfig 熱重載回呼 panic 為 `dataconfig onReload`，HTTP handler panic 由 `httpx.Recover` 計入並回 500
- 未被 recover 的 panic：映像（含正式環境）預設 `GOTRACEBACK=all`（`docker/app.Dockerfile`），崩潰時印出全部 goroutine 堆疊，排死結／洩漏才看得到其他 goroutine 狀態；compose 可用環境變數覆寫。本機 `scripts/dev-up.sh` 現在也預設 `all`
- recover 到的 panic 日誌，dataconfig、recordmq、Record consumer 的 panic 值欄位統一為 `err`（原本是 `panic`），日誌查詢與告警規則要改查 `err`
- `game_event_loop_last_tick_timestamp_seconds{service}` — 事件迴圈開始時才建立並設值、之後每次 tick 更新的時間戳（App 建立到迴圈開始之間沒有序列，啟動耗時長也不會誤觸）；`time() - 值` 持續超過 30 秒觸發 `GameEventLoopStalled`。`game_event_queue_depth` 只在排空時更新，迴圈卡住時會凍結，不能用它判斷卡死
- `go_sync_mutex_wait_total_seconds_total` — goroutine 等鎖的累計秒數（`runtime/metrics` 的 `/sync/mutex/wait/total:seconds`）；`rate()` 持續偏高代表鎖爭用，不必先開 `PPROF_MUTEX_FRACTION`。目前沒有對應告警規則
- `logger_async_dropped_total` — 非同步日誌緩衝滿了、被丟棄的最舊日誌筆數（只有設了 `LOG_ASYNC_BUFFER` 才會增加）；`increase(...[5m]) > 0` 代表緩衝太小或 stderr 太慢
- `redis_command_errors_total{op}` — `pkg/redis` 指令失敗次數（`Do` 以指令名、`DoMulti` 以 `pipeline` 為 `op`；不計 Nil 回覆與呼叫端取消），持續增加觸發 `GameRedisCommandErrors`
- 告警會看的有標籤計數器（死信、丟棄、設定重載失敗等）在元件建構時就以 0 建立，唯一一次事件也看得到；`game_messages_total` 已移除（原本只計 Gate 登入請求），訊息量改看 `tcp_messages_received_total`
- `game_account_purge_last_run_timestamp_seconds` — 每日帳號清除最近一次完整跑完的時間；超過 2 天觸發 `GameAccountPurgeStalled`
- `game_login_total{result="session_expired"}`、`game_login_e2e_seconds`、`game_logout_total{result="service_unavailable"}` 現在包含 Gate 掃描到的 pending 逾時（Central／World 不回覆的登入與登出，Gate 補計），登入失敗比例（`game_login_failure_ratio_5m`）的失敗 regex 也納入 `session_expired`；舊版這些請求不計量，登入可用率與 P99 看不到 Central／World 無回應的情況
- `game_heartbeat_timeout_total{service=<owner>}` 現在也計入 S2S 連線的讀取逾時（日誌為 Warn `peer read deadline exceeded`，原為 Error `decode error ... i/o timeout`）；S2S 對端無回應時看這個指標與日誌
- `tcp_rejected_connections_total` — TCP 伺服器在 accept 階段拒絕的連線（label `service`、`reason`：`rate_limited`、`at_capacity`、`handshake_timeout`）；拒絕明細只在 Debug 日誌，量看此指標。`handshake_timeout` 是 Gate 連上後沒在期限內登入，可用來分辨攻擊或 Client 異常
- `game_account_purge_total` — 每日帳號清除結果（label `result`：`purged`、`failed`），失敗觸發 `GameAccountPurgeFailing`
- `recordmq_enabled` — 設定了 RabbitMQ 即為 1（與連線成敗無關），搭配 `recordmq_connection_status` 判斷「設定了卻沒連上」
- `game_connections_rejected_total` — 應用層拒絕的連線（label `service`，例如 Gate 連線洪水時的拒絕），每條連線不另寫日誌

其餘 metrics 主要用於交叉驗證與 debug，不作為第一優先 alert 入口。

### 限流分級

現在把常見熱點拆成不同桶：

1. `login`
   - Gate 內用 account 粒度。
   - 連續重試同帳號會先進暫時鎖定。
2. `logout`
   - Gate 內用 playerID 粒度。
   - 避免同一玩家一直重送 logout 把 Central / World 打爆。
3. `GM`
   - Lobby admin API 走獨立 token bucket。
   - 免 admin token 外洩時把所有管理操作一起灌死。
4. `audit`
   - GM audit log 用獨立桶。
   - 讓審計輸出不跟 GM 請求共用同一條限流線。

用途：
- 一條線超，不代表全線一起死
- 不同入口各自退化，各自收斂

### 常見啟動與連線訊息

| 訊息 | 意義 | 處理 |
|---|---|---|
| 啟動錯誤 `s2s_auth.enabled is not set` | S2S 驗證開關漏設；不再退回明文 | 設定檔明確設 `s2s_auth.enabled: true`（正式）或 `false`（開發） |
| `rejecting connection: at capacity`、`rejecting connection`（TCP server）與 `per-IP connection limit exceeded, closing`（Gate） | 連線名額已滿、被限流或單一 IP 超過上限，新連線被直接關閉；這三筆都是 **Debug** 等級，預設 Info 看不到 | 不要 grep 日誌，改看 `tcp_rejected_connections_total{service,reason}` 與 `game_connections_rejected_total`；再看 `tcp_connections_active` 與連線上限設定，確認是否有連線洩漏（`game_connection_leak_diff`） |
| `world record sink unavailable at startup, retrying in background; Record events are dropped until it connects`（Error）、`world record sink retry failed`（Warn）、`world record sink connected after startup retry`（Info） | World 啟動時連不上 RabbitMQ 不再拒絕啟動，改在背景以指數退避（1 秒倍增到 30 秒）持續重試；連上前不發 Record 事件，必須送達的 outbox 事件留在 MySQL，連上後由 relay 照常發送（有設定 RabbitMQ 就一律啟動 relay，連上前整輪略過、不燒重試次數） | `recordmq_connection_status=0` 現在是**暫態**，不再是「重啟前永不恢復」；先修 RabbitMQ，不必重啟 World。對照 `GameRecordMQDisconnected` |
| `central: shared routing read failed, falling back`（Warn，欄位 `kind`、`err`） | Central 讀 Redis 共享路由快取失敗，退回本機判斷；有冷卻，最多約每 10 秒一筆 | 看 Redis 健康與 `circuit_breaker_state`；沒有這筆日誌不代表 Redis 正常，持續出現再查連線 |
| `peer read deadline exceeded`（Warn） | S2S 對端超時沒有任何資料，連線被關；計入 `game_heartbeat_timeout_total{service}` | 查對端行程是否卡住或網路中斷 |
| `async log buffer overflow, entries dropped`（Warn，欄位 `dropped`、`droppedTotal`） | 設了 `LOG_ASYNC_BUFFER` 且緩衝滿了，最舊的日誌被丟棄 | 調大 `LOG_ASYNC_BUFFER` 或查 stderr 消費是否太慢；計入 `logger_async_dropped_total`。行程崩潰（panic、SIGKILL）時緩衝內最後幾筆可能遺失，正常結束由 `startup.Main` 排空 |
| `shutdown timed out, goroutine dump`（Error，欄位 `reason`、`truncated`、`goroutines`） | 關機任務逾時（drain 除外）、`appcore: event loop did not stop` 或最後等背景工作逾時時，一次輸出 goroutine 堆疊（`pprof goroutine debug=1`，相同堆疊合併並附數量，上限 128KB，超過 `truncated=true`） | 看 `reason` 是哪個任務，再到 `goroutines` 找卡在哪裡（鎖、channel、I/O）；詳見[現場採證](#現場採證服務卡住cpu-高記憶體持續成長) |
| `pprof disabled; set debug.pprof_enabled=true to enable`（Info） | 該服務未啟用 pprof（正式環境缺省如此） | 要採證時見[現場採證](#現場採證服務卡住cpu-高記憶體持續成長)的前置條件 |
| `DEBUG_PPROF_BASIC_AUTH invalid: ...`（Error） | `DEBUG_PPROF_BASIC_AUTH` 有設定但不合格（格式非 `user:pass`、密碼短於 16 字元、`change-me` 開頭），pprof 與 Gate `POST /diag/reconcile` 一律回 503 | 修正環境變數後重啟；空字串（僅本機開發）則只靠 CIDR 並記 Warn `pprof basic auth not configured` |
| `outbox: claim failed`、`outbox: publish failed`（限流，每 5 秒最多一筆） | World 的 Record outbox 領取或發布失敗，事件留在 MySQL 重試 | 先看 MySQL 與 RabbitMQ 健康；對照告警 `GameRecordMQPublishErrors`、`GameRecordMQDisconnected` |
| `recordmq: async publisher ... dropping queued events` | 非同步發布器因 ctx 取消而丟棄佇列事件（關機路徑） | 正常關機應走 `Stop()` 排空；出現代表關機流程順序有誤 |
| `combat: remove stale candidate failed` | PvP 候選清單的 Redis 清理失敗 | 下次抽到時會再清；持續出現時查 Redis |
| Redis 重啟／`FLUSHALL` 後 `combat:candidates` 缺玩家 | World 只在玩家戰鬥快照內容改變或上次寫入超過 10 分鐘時重寫候選集合 | 不必重啟 World：每位有操作的玩家最長 10 分鐘自癒；要立即恢復就重啟 World（啟動會 `RebuildCandidates`；重建先寫專屬暫存 key（TTL 1 小時），完成後原子換上，滾動部署時其他 World 配對不會遇到空集合，重建期間其他 World 的更新由 10 分鐘強制重寫補回） |
| 登入回 `AuthRateLimited` 且 `game_account_lock_total{result="timeout"}` 增加 | 同帳號另一筆登入或清除仍持有鎖 | 查是否有慢登入（`game_account_lock_wait_seconds`、登入 P99），持鎖處理上限為 10 秒 |
| 登入回 `AuthServiceUnavailable` 且 `game_account_lock_total{result="error"}` 增加（告警 `GameAccountLockError`） | 共享帳號鎖（Redis）故障，不是鎖競爭 | 查 Redis 健康與 Central 的 `account lock` 錯誤日誌（10 秒取樣）；Client 不應猛重試 |

### 資料保留策略

目前先定這幾條：

1. `request journal`
- `Central` login / logout journal 的重試預算已收在各自 app 的 request journal 實作內。
   - 預設保留 2 分鐘。
2. `replay cache`
- `Gate` / `World` replay cache 的重試預算已收回各自 app / tool 本地 helper。
   - 預設保留 2 分鐘。
3. `dead-letter`
   - `grant item dead-letter` 進 Redis 後預設保留 7 天。
   - 逾期自動清，避免人工堆積。
4. `audit record`
   - `gm audit` 視為操作記錄，建議保留 30 天。
   - 實際清理交由外部 log / table retention。

原則：
- TTL 要跟用途綁定，不要散在各 service 裡各寫各的
- dead-letter 不可永久保存
- audit 可查，但不要無限長

## 常見問題

### 0. 玩家登入失敗（密碼錯誤）

**症狀**: 玩家送出登入後立即收到失敗回應（return code 13）

**排查步驟**:
1. 確認玩家使用的密碼與首次登入時一致
2. 在 Central 日誌搜尋 Warn `login failed, notifying gate directly`，看 `code` 欄位為 13（`AuthWrongPassword`）；沒有 `wrong password` 這種日誌，要看量請用 `game_login_total` 的 `result` 標籤
3. 若懷疑帳號 hash 損壞，直接查 MySQL `users.password_hash` 欄位

**常見原因**:
- 玩家輸入密碼有誤（最常見）
- 舊帳號遷移測試時傳入密碼，但 `password_hash` 為空 → 空 hash 應允通過，若仍收到 code 13 代表欄位讀取有誤
- 新帳號（DB 無記錄）送空密碼 → 一律回 code 13，Central 日誌為 `login failed: new user without password`；這是預期行為，不是故障
- Redis 帳號快取中 `hash` 欄位值不正確（可清除 `account:<account>` key 強制回 MySQL）

### 1. 玩家登入卡住（pending_login 超時）

**症狀**: 玩家送出登入後無回應，45 秒後被清除

**排查步驟**:
1. 用 `gameTraceID` 追蹤訊息流向
2. 確認 Gate → Central 連線是否正常（`tcp_connections_active`，只算 accepted connection）
3. 確認 Central → World 連線是否正常
4. 檢查 Central 日誌是否有 MySQL 錯誤
5. 檢查是否觸發帳號鎖定（5 次/10 秒限制）

**常見原因**:
- Central 與 MySQL 連線中斷（斷路器開啟）
- World 未啟動或未連上 Central
- 帳號被速率限制鎖定（等 30 秒）

### 2. World 重啟後玩家狀態遺失

**症狀**: World 重啟後，玩家未恢復到線上狀態

**排查步驟**:
1. 確認 Redis 是否正常運行
2. 檢查 World 啟動日誌是否有 Redis 載入紀錄
3. 確認 Gate 是否在 30 秒寬限期內重新連上 World
4. 檢查 `game_recovery_validation_total` 指標

**常見原因**:
- Redis 斷路器開啟，無法讀取玩家狀態
- Gate 重連超過 30 秒寬限期，玩家被清除
- 玩家在 World 重啟期間已從 Gate 登出

### 3. 重複登入/重複操作

**症狀**: 同一操作被執行多次

**排查步驟**:
1. 檢查 `game_login_replay_cache_total{result=~"hit_success|hit_failure"}` — 去重快取是否生效
2. 確認 `requestID` 是否正確傳遞
3. 檢查 Central 的 request journal 快取狀態

**常見原因**:
- 客戶端重送但 requestID 不同（應相同）
- Replay cache TTL（2 分鐘）已過期
- 要重演這條情境，可直接用 `scripts/private/p0-daily-check.ps1 -Mode session`

### 4. Central 在登入途中斷線或重啟

**症狀**: 玩家登入卡住、收到 `service unavailable`，重試後才成功

**排查步驟**:
1. 檢查 Gate 日誌是否在 `pending_login` 期間失去與 Central 的連線
2. 檢查 `tcp_reconnect_attempts_total` / `tcp_reconnect_total`
3. 確認 Gate 是否已清理逾時的 `pending_login` session（TTL 45 秒）
4. 比對玩家端是否重新發起新請求，而不是重送舊上下文

**常見原因**:
- Central 程序重啟，Gate 對應 request 鏈路中斷
- Central 恢復後玩家重新登入，產生新的 `requestID` / `gameTraceID`
- 上游等待過久，誤以為可直接重放原請求
- 要驗 restart retry gate，可直接用 `scripts/private/p0-daily-check.ps1 -Mode failover`

### 5. 重複登入把舊連線踢下線

**症狀**: 同帳號新裝置登入後，舊連線收到重新登入或被迫下線

**排查步驟**:
1. 用 `gameTraceID` 比對兩條登入鏈路是否屬於不同請求
2. 檢查 Gate 是否有舊 session 被清理或轉成失效
3. 確認玩家端收到的 return code 是否為重新登入相關語意
4. 若是測試環境，確認是否有人共用同一組帳號

**常見原因**:
- 同帳號真的在多端同時登入
- 測試腳本重複使用固定帳號
- 本地 state 過舊，玩家端誤以為自己仍在線
- 要重演這條情境，可直接用 `scripts/private/p0-daily-check.ps1 -Mode session`

### 6. Gate 與 World 斷線

**症狀**: 玩家大量離線

**排查步驟**:
1. 檢查 `tcp_reconnect_attempts_total` — 重連嘗試次數
2. 確認網路連通性
3. 檢查 World 是否因 OOM 或 panic 崩潰：`docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' <容器>`；崩潰堆疊用 `docker logs --since <時間> <容器>` 找 `goroutine 1 [` 起頭的段落。Docker 秒級拉起時 `up==0` 告警不會響，改看 `GameProcessRestarted`（`changes(process_start_time_seconds[15m]) > 0`，發版也會觸發一次）
4. 確認是否在 30 秒內恢復（短期 vs 長期策略）

**處理策略**:
- < 30 秒：自動恢復，標記 unavailable 後恢復
- \> 30 秒：清理玩家，通知 Central 清除路由

### 7. Prometheus 抓不到 metrics

**症狀**: Grafana dashboard 沒資料，Prometheus `up` 為 0

**排查步驟**:
1. 確認服務 debug server 已啟動並開出 `:6060~:6066`（Central 6060、Gate 6061、World 6062、User 6063、Lobby 6064、Record 6065、Chat 6066）；埠被佔用時服務記一筆 `debug server disabled` 錯誤後照常啟動，但該實例沒有 `/health`、`/ready`、`/metrics`（同一台主機跑多個同類服務時，後啟動的必然綁不到）
2. 檢查服務是否只允許 loopback，導致 container 抓不到 `/metrics`
3. 若 Prometheus 跑在 Docker container，確認有設定 `DEBUG_ALLOW_CIDRS`
4. 執行 `scripts/monitoring-smoke.ps1` 驗證 Grafana / Prometheus provisioning

**常見原因**:
- debug server 預設只允許 loopback
- Prometheus 容器網段未列入 `DEBUG_ALLOW_CIDRS`
- monitoring compose 沒有成功載入 dashboard 或 datasource

### 8. Docker 環境啟動失敗

**排查步驟**:
1. 確認 MySQL 與 Redis 已就緒（compose.deps.yml 先啟動）
2. 檢查 config 掛載路徑是否正確
3. 確認健康檢查通過（`wget /ready`）
4. 查看 `docker logs <container>` 確認錯誤訊息

### 10. 登入延遲高但失敗率正常

**症狀**: 玩家反映登入慢，但 `game_login_total{result!="success"}`（如 `server_fail`、`rate_limited`）無明顯上升

**排查步驟**:
1. 查看 `game_account_lock_wait_seconds` p95 — 若偏高代表帳號鎖競爭（同帳號並發登入）
2. 查看 `game_login_db_query_seconds{operation="find"}` p95 — MySQL FindByAccount 慢
3. 查看 `game_login_db_query_seconds{operation="save"}` p95 — 新帳號 Save 慢
4. 對照 `game_handler_duration_seconds{handler="on_login_gate_to_central"}` 確認是哪段佔多數

**常見原因**:
- MySQL 負載高，查詢排隊（DB query 時間高）
- 同帳號短時間大量登入請求，鎖競爭嚴重（lock wait 時間高）

### 11. CI 整合測試失敗

**排查步驟**:
1. 整合測試啟動真實程序，確認 port 未被占用
2. 檢查是否有 race condition（`-race` flag）
3. 確認 testenv 是否正確清理上次的程序：Windows 上找 `%TEMP%\testenv-bin-*` 底下仍在執行的 central／gate／world／chat，父行程已不存在的就是殘留程序
4. 偶發逾時先看是否少了就緒等待：登入前要等 `WaitForGateReady`；讀回應用 `ReadNext`，不要假設回應一定是下一則訊息

### 12. Gate rolling deploy 後仍有玩家強制斷線

**症狀**: Gate 重啟時關機錯誤出現 `shutdown task "user drain": user drain: drain timeout with N remaining connections: context deadline exceeded`（Central 為 `central drain`、World 為 `world drain`）；沒有 `drain timeout reached, force-disconnecting remaining players`、`drain complete` 這類訊息，也沒有 `count`／`timeout` 欄位

**排查步驟**:
1. 從錯誤訊息的 `N remaining connections` 確認殘留人數；開始排空時另有 Info `stopped accepting new connections`（欄位 `owner`）
2. 若殘留玩家偏多，考慮拉長 `drain_timeout`（在 gate.yaml 設定），同時要把容器 `stop_grace_period` 一併調高（見[開發規則](../30-部署與開發/開發規則.md)的 Gate 排空設定）
3. 確認 Lobby 服務探索是否已將此 Gate 標記為不可用（TTL 25s），避免新玩家繼續連入
4. drain 逾時是常態、不輸出 goroutine 堆疊；其他關機任務逾時才有 `shutdown timed out, goroutine dump`

**常見原因**:
- Gate 預設 `30s` 排空時間不夠長，部分玩家長連線沒有在期限內下線
- 玩家 heartbeat 仍正常，但業務邏輯端沒有登出流程觸發
- `drain_timeout` 設成壞值（缺單位、亂碼、非正數）時 Gate 拒絕啟動（`drainTimeoutFromConfig`），不會悄悄沿用預設 30s；未設定才用預設值。它現在只套給 drain 任務，其餘關機任務維持 5 秒

### 13. OTel Span 在 Jaeger 中找不到

**症狀**: Gate/Central/World 的 Span 各自獨立，不在同一條 Trace 下

**排查步驟**:
1. 確認 `otel.exporter` 設定為 `otlp`，且 `otel.endpoint` 正確指向 Collector
2. 檢查服務啟動日誌 — `"tracing init failed"` 表示 OTel 初始化失敗（span 不輸出但服務仍運作）
3. 確認三個服務日誌中的 OTel `trace_id`（32 位 hex）相同（跨服務同一條鏈路應共用）；`gameTraceID` 是另一個十進位欄位，不能拿來搜尋 Jaeger
4. 在 Jaeger UI 直接以日誌裡的 `trace_id`（hex）搜尋

**常見原因**:
- OTLP Collector 未啟動或 endpoint 設定有誤
- `otel.exporter` 未設定，預設為空字串（noop，不輸出）
- 服務間鏈路編號（`gameTraceID`／OTel `trace_id`）傳遞中斷（應由 Gate 建立後透傳，不可在中間重建）

### 14. 服務發現或路由漂移

**症狀**: 新玩家被派到維護中的 World、登出打到舊路由，或 Central / Gate / World 對同一資源路由不一致。

**排查步驟**:
1. 確認 `central:world:drain` 是否正確寫入 Redis
2. 檢查 Central 是否已刷新 `drainedWorlds`
3. 檢查 `routing:{playerID}` 與 `account:{account}` 是否仍對應 memory
4. 確認 Gate / World 的 `ConnectInfo` 是否有及時清除 unavailable 標記
5. 若是 Lobby 探測異常，先看 Redis TTL / heartbeat 是否失效

**常見原因**:
- Lobby 已把 World 標成維護，但 Central 還沒刷新 Redis drain set
- World / Gate 重連後沒送 `ConnectInfo`，導致 unavailable 標記殘留
- routing key TTL 沒 refresh，或舊節點殘留舊路由

**處理策略**:
- Redis drain set 先修，Central 再刷新
- reconnect 後先清 unavailable，再跑後續 recovery / cleanup
- 以 audit / reconcile 檢查 routing key 與 memory 是否一致
- 若 Redis routing/account key 出現壞值，Central 會直接忽略，不會回填成 `gate=0` / `world=0` 的假路由
- account cache 的 `uid` / `wid` / `hash` 壞值也會直接丟掉，不會當成 returning player 的真資料

### 15. 版本不相容（強制更新）

**症狀**: Client 連上後收到 `HelloResponse` 的強制更新或維護後被斷線；或服務之間的連線一建立就被關閉。

**排查步驟**:
1. 看 Gate log 的 `client version hello`（**Debug** 等級，正式環境預設 Info 看不到；平時先看第 3 步的指標，必要時暫時調 `LOG_LEVEL=debug`）：`result`、`reason`、`platform`、`gameVersion`、`protocolVersion`、`clientContract`、`configSeq`
2. 依 `reason` 判斷：`ProtocolMismatch` 與 `ClientContractMismatch` 是 Client 與 Server 的版本不同；`GameVersionTooOld` 看 `GET /admin/version-policy` 該平台的 `min`；`ConfigTooOld` 看 Server 的 `min_config_seq`
3. 查 `game_version_hello_total{result,reason,platform}` 看是不是特定平台或版本集中被擋
4. 服務之間被拒絕：查 `game_service_hello_mismatch_total` 與 `service hello mismatch`／`service hello timeout`／`message before service hello` log，確認所有服務都來自同一次發版且都會送 ServiceHello
5. 服務啟動就失敗：看 `release info` 與 `verify` 的錯誤，通常是協定、設定或資料庫 schema 與嵌入的 `release.json` 不一致

**常見原因**:
- 營運把該平台的 `min` 調太高，或維護旗標忘了關
- 新安裝包還沒上架就調高了 `min`
- 部署時新舊版服務混跑
- 同步 PJA-Protocol 或 PJA-Config 後沒有更新開發版 `pkg/release/release.json`

完整流程見 [版本握手與強制更新](../10-核心流程/版本握手與強制更新.md)。

### 16. 錯誤碼語意不一致

**症狀**: HTTP、RPC、queue 對同一類失敗回應完全不同。

**排查步驟**:
1. 先看 `pkg/errcode` 的 canonical class
2. 確認指標 outcome 是否由 `MetricOutcomeFromAuthResultCode` 產生；私有壓測與回歸工具的重試判斷在 `tools/private/internal/authcode.ShouldRetry`
3. 確認 queue / RPC 是否只看 `ack / retry / drop`
4. 確認 app 沒有自己硬編新語意

**常見原因**:
- 某條 handler 自己選了不同 HTTP status
- 某個 queue 失敗碼沒有接到 retry policy
- 舊 code 還在直接 compare 數字，不看 canonical class

### 17. 重試預算耗盡

**症狀**: `game_async_failure_total{queue="grant_item",outcome="retry_budget_exceeded"}` 上升，或命令很快進 dead-letter。

**排查步驟**:
1. 看 `RequestedAt` 是否過舊（Lobby 以遊戲時間填入，World 以遊戲時間比較重試期限，兩台主機時鐘偏差不影響）
2. 看 `Attempts` 是否已到上限
3. 看 `grant item queue` 是否長時間卡在下游 `onGrant` 錯誤
4. 若是 transient 錯，先修下游，不要盲目放大 retry window

**常見原因**:
- 下游服務長時間不可用
- command 在 queue 裡堆太久
- 重試次數已達 5 次
- 新舊 schema 混跑導致一直失敗，最後被 budget 擋下

### 死信再處理

用 `tools/private/deadletterreplay` 挑選 dead-letter 再送回 queue：

```bash
go run ./tools/private/pja deadletterreplay -world-id 9 -operation-id grant-op-1 -retryable -replay
```

用途：
- 手動挑選特定 `world / user / operationID`
- 先 `-dry-run` 看選到哪批，再決定 replay 或 discard
- `-retryable` 只列還在重試預算內的樣本
- 若 world capability 不在，先修 world，再重送
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode deadletterreplay`

Record 事件佇列（`recordmq`）的死信規則：內容無法解析、缺少 `OccurredAt`、寫入違反約束（SQLSTATE 22xxx、23xxx）或 handler panic（逐筆處理時）直接進 `<queue>.dead`；其他錯誤放回佇列並以 1s、2s、4s… 退避（上限 30 秒），同一事件連續失敗 20 次（約 9 分鐘）才進死信，避免單一事件卡住整條佇列。MySQL 長時間故障後，`<queue>.dead` 可能留有當時正在重試的少數事件，恢復後確認內容再重送。

Record `/events` 查詢的 `event_type` 超過欄位長度 64 時直接回 `400 event_type too long`（必然查無資料，免得對 31 張分表各跑一次 UNION）。事件寫入的時間下界與查詢涵蓋的分表對齊：取最舊查詢分表的當日 00:00（UTC，`earliestAcceptedAt`；表名與回看範圍一律以 UTC 計，與行程時區無關），不是 `now-31 天` 的瞬間，落在界線與最舊分表當日 00:00 之間的事件不會寫入後查不到。

### 容量預測

用 `tools/private/capacityforecast` 讀 `tools/private/loadtest` baseline：

```bash
go run ./tools/private/pjaload capacityforecast -baseline .\.run\loadtest-baseline.json
```

若 baseline 的 `sessions=0`，`capacityforecast` 會回 `reason=no_data`，代表資料不足，不可用於容量判讀。

用途：
- 用 baseline p95 / queue depth 推估可承載玩家數
- 先知道 headroom，避免等 queue 高才加機
- 若 `estimatedPlayers` 太低，先看 latency 還是 queue 壓力
- `capacityforecast` baseline 解析會對未知欄位與負值報錯，不再把壞 JSON 算進容量預測

## 現場採證（服務卡住、CPU 高、記憶體持續成長）

原則：**先採證再重啟**。重啟會清掉 goroutine、heap 與鎖的現場，之後只剩症狀。判斷卡住時先看指標：`game_event_loop_last_tick_timestamp_seconds{service}` 停止更新（`GameEventLoopStalled`）才是事件迴圈卡死；`game_event_queue_depth` 只在排空時更新，迴圈卡住時會凍結在舊值，不能當依據。

**前置條件：pprof 是否可用。** 正式環境 pprof 缺省**關閉**：`debug.pprof_enabled` 缺省為 false，`docker/prod/config/*.yaml` 沒有這個鍵；dev 與 docker 範例設定才明確寫 `true`。要在正式環境開：

1. 在該服務設定檔寫 `debug.pprof_enabled: true`（需重啟該服務，所以卡住當下通常來不及，建議平時就在要觀察的服務開好）。
2. `.env.prod` 設定 `DEBUG_PPROF_BASIC_AUTH=user:pass`：`compose.prod.yml` 六個服務**必填**（缺值 `compose up` 直接失敗），密碼至少 16 字元、不可 `change-me` 開頭；不合格時 pprof 與 Gate `POST /diag/reconcile` 一律回 503 並記 Error。空字串（僅本機開發）則只靠來源 CIDR 並記 Warn。
3. 啟動日誌沒有 Info `pprof disabled; set debug.pprof_enabled=true to enable`，才代表 pprof 已註冊。環回位址永遠允許，所以可以進容器內取：`docker exec <容器> wget -qO- --user=<user> --password=<pass> 'http://localhost:<診斷埠>/debug/pprof/goroutine?debug=2' > goroutine.txt`（診斷埠見[健康檢查端點](#健康檢查端點)；本機直接 `curl -u user:pass`）。

**服務卡住（hang）**

- `curl -u user:pass 'http://127.0.0.1:<診斷埠>/debug/pprof/goroutine?debug=2' -o goroutine.txt`：所有 goroutine 的完整堆疊；找停在 `sync.Mutex.Lock`、`chan receive`、`select`、`IO wait` 很久的，同一個位置大量重複通常就是根因。`debug=1` 為合併後的摘要。
- Go 1.27 的 `/debug/pprof/goroutineleak`：列出被判定為永遠無法喚醒的 goroutine（洩漏）。
- 鎖爭用：`rate(go_sync_mutex_wait_total_seconds_total[5m])` 持續偏高再開 `PPROF_MUTEX_FRACTION`，抓 `/debug/pprof/mutex`。
- **第一個採證來源是日誌**：事件迴圈超過 20 秒沒有 tick 時，行程會自動記 Error `event loop stalled`（`name`、`stalledFor`）並輸出一筆 `event loop stalled, goroutine dump`（`reason` 為服務名），同一次卡死只輸出一次、tick 恢復後重新武裝，比 `GameEventLoopStalled`（30 秒）更早；先查這筆日誌，不必重啟開 pprof 或送 SIGQUIT。
- 關機卡住時不必手動抓：關機任務逾時（drain 除外）、`appcore: event loop did not stop`、最後等背景工作逾時，都會有一筆 Error `shutdown timed out, goroutine dump`（`reason`、`truncated`、`goroutines`），debug server 也會一直開到關機最後的 Cleanup。Lobby 遊戲時鐘停止（`reason=lobby game clock stop`）與 Record 背景工作停止（`reason=record background workers stop`，5 秒）逾時同樣會輸出堆疊。

**CPU 高**

- `curl -u user:pass -o cpu.pprof 'http://127.0.0.1:<診斷埠>/debug/pprof/profile?seconds=30'`，再 `go tool pprof -top cpu.pprof` 或 `go tool pprof -http=:0 cpu.pprof`。debug server 沒有 WriteTimeout，30 秒 profile 不會被截斷。
- 同時看 `go_sync_mutex_wait_total_seconds_total` 與 `game_sched_latency_p99_5m`，分辨是算力不足還是鎖等待。

**記憶體持續成長**

- `curl -u user:pass -o heap1.pprof 'http://127.0.0.1:<診斷埠>/debug/pprof/heap'`，過一段時間（成長明顯後）再抓 `heap2.pprof`，用 `go tool pprof -base heap1.pprof heap2.pprof` 看增量。
- `go_goroutines` 持續上升就改看上面的 goroutine 摘要與 `goroutineleak`，記憶體成長多半來自洩漏的 goroutine。

**pprof 不可用、日誌也沒有自動堆疊時**（正式環境缺省，或已經來不及重啟開啟）：先依序試非破壞性的做法，最後才用 SIGQUIT。

1. 日誌自動堆疊：事件迴圈卡死的 `event loop stalled, goroutine dump` 與關機逾時的 `shutdown timed out, goroutine dump`（見上）。
2. 診斷埠只綁環回位址時，進容器內用 `docker exec` 打 `/debug/pprof/goroutine?debug=2`（前提是該服務已開 `debug.pprof_enabled`；沒開就只能重啟開，開了之後下一次卡住才抓得到）。
3. 以上都沒有，才用 `docker kill -s QUIT <容器>`：Go 收到 SIGQUIT 會印出所有 goroutine 堆疊（映像預設 `GOTRACEBACK=all`）並**立即結束行程**，容器由 restart policy 拉起，之後 `docker logs <容器>` 取堆疊。

**SIGQUIT 的資料風險（尤其是 World）：** SIGQUIT 不走 `RunApp` 的關機任務，跳過 World 的最後寫回、spill 落地與 Record sink 排空。正常重啟（SIGTERM）不會遺失的玩家異動，在這條路上會遺失；例如 MySQL 正卡住、異動全堆在記憶體時，SIGTERM 會落地到 spill 檔，SIGQUIT 不會。所以：

- **MySQL 或其他依賴異常時，不要對 World 使用 SIGQUIT**；先確認依賴正常，或接受該 World 記憶體內尚未寫回的異動會遺失。
- Gate、Central、Lobby、Chat 沒有 World 的最後寫回問題，但 Gate 的連線與 pending session 同樣會直接斷掉，玩家需重連。
- 目前沒有不結束行程的訊號堆疊管道（如 `SIGUSR1`）；World 要採證請預先開好 pprof。

採證完畢才重啟，並把 `goroutine.txt`／`cpu.pprof`／`heap*.pprof`、關機堆疊日誌與當時的 `game_event_loop_last_tick_timestamp_seconds` 附在[故障單](故障單模板.md)。

## 日誌關鍵字速查

| 關鍵字 | 含義 |
|--------|------|
| `login failed` | 登入失敗，檢查 `code` 欄位 |
| `DB error` | MySQL 連線或查詢失敗 |
| `circuit breaker state changed` | 斷路器狀態改變（Warn，帶 `name` 與新舊狀態）；沒有 `circuit breaker open` 這條訊息，持續開啟看 `circuit_breaker_state` 與 `GameCircuitBreakerOpen` |
| `login failed: account lock timeout` | 同帳號另一筆登入或清除仍持有鎖，這筆等鎖逾時（對應 `AuthRateLimited`）；沒有 `account locked` 這條訊息 |
| `expired gate session cleaned` | Gate 掃描到逾時 session 並清除（Warn，欄位 `sessionKey`、`state`、`playerID`）；`pending_login` 逾時會補計 `game_login_total{result="session_expired"}`。回應碼 `AuthSessionExpired` 沒有獨立的 `session expired` 日誌，只有回應碼與 `game_login_total` 的 `result` 標籤 |
| `recovery validation` | World 重啟後的玩家校驗 |
| `send queue overflow` | TCP 發送佇列滿，強制斷線 |
| `reconnect` | ServiceClient 正在重連 |
| `heartbeat timeout` | 玩家心跳超時被踢，檢查網路品質 |
| `gamestore memory flush failed, will retry` | 背景寫回常駐玩家資料失敗；異動仍保留在記憶體，下個週期（1 秒）重試，持續出現代表 MySQL 異常 |
| `gamestore memory final flush failed` | 背景寫回迴圈結束前的寫回失敗；關機流程還會再以不經斷路器的寫回重試 |
| `world shutdown could not write player game data to mysql; spilled to file and will replay on next start`（Error，欄位 `players`、`path`） | 關機時 MySQL 仍寫不進去，異動已落地到 `path`；下次啟動前自動重放，不要刪除該檔 |
| `world shutdown lost unsaved player game data`（Error，欄位 `players`、`dir`、`err`；`cmd/world/internal/app/users_types.go` 的 `FinalizePlayerData`） | **資料遺失訊號**：關機時 MySQL 寫不進去且落地檔也寫失敗，`players` 位玩家的最後異動遺失（同時關機錯誤帶 `spill unsaved player game data`）；檢查 `dir`（`game_store.spill_dir`）的權限與空間，並盤點該時段玩家進度。這筆是固定訊息的 Error，值班與告警以此搜尋 |
| `replayed player game data spilled at last shutdown` | 啟動時已重放上次關機落地的異動；暫時性錯誤（例如 MySQL 不可用）重放失敗時 World 會拒絕啟動並保留原檔，先恢復 MySQL 再重啟 |
| `gamestore spill replay permanently rejected by mysql; changes quarantined` | 開機重放時該玩家的落地異動被 MySQL 永久拒絕，已轉存 `<spillDir>/rejected/`（`path`）後繼續重放其他玩家，World 照常啟動；需人工檢視隔離檔 |
| `write-back permanently rejected by mysql; changes quarantined` | 該玩家待寫資料被 MySQL 永久拒絕（欄位過長、約束違反），已轉存 `<spillDir>/rejected/` 下的隔離檔並從 pending 移除，不再每秒重試（背景寫回、登出卸載、delegate、寫穿都會）；隔離檔不會被開機重放，需人工檢視資料來源並修正後處理 |
| `outbox: decode payload failed, dead-lettered` | Record outbox 列的 payload 不是單一合法 JSON 值（含尾隨資料），已直接標記死信（不退避重試）；查產生該事件的程式 |
| `outbox: lease lost before ...` | outbox 標記送出或重試前租約已被其他 World 取走，該列不計送出，計入 `game_record_outbox_total{result="lease_lost"}`；偶發屬正常，持續出現查 World 是否卡頓超過租約 |
| `recordmq: handler panic` | Record 處理事件時 panic，已接住；逐筆處理時該事件直接進 `<queue>.dead`，依 `stack` 修正 |
| `data config reload panic`、`data config prepare panic` | 設定熱重載 panic，已接住並計入 `data_config_reload_total{result="failed"}`，服務沿用舊快照；準備階段 panic 會還原 `current.json` |
| `login rejected: cannot restore previous gate, falling back to logout` | Central 無法把被 World 拒絕的登入還原回舊 Gate，改走登出；看 `reason`（`no_previous_gate`、`request_mismatch`、`no_services`、`previous_gate_offline`、`restore_precondition_failed`） |
| `login rejected ignored: ...` | Central 收到的 `LoginRejected` 已過時（玩家不在、玩家 ID 為空或已不在回報的 Gate），略過 |
| `central notify dropped: no central connection` | Gate 要把登出或登入被拒（`kind`）回報給處理該 session 的 Central，但該 Central 連線不在；Central 端可能殘留路由 |
| `login failed: bcrypt busy` | Central 新帳號取不到 bcrypt 槽位，回 `AuthServiceUnavailable`、不寫 journal，玩家可重試 |
| `login failed: password too long` | 密碼超過 bcrypt 上限，回 `AuthWrongPassword`（不可重試） |
| `login aborted: gate connection gone` | World 登入活動背景寫入期間 Gate 斷線或換了連線，該次登入不回覆、不建立在線玩家 |
| `login dropped after ban check: connection closed`、`recovery validation dropped: world connection closed` | Gate 背景工作完成時連線已關閉，結果無法推回事件迴圈，已收尾並丟棄 |
| `protocol file write error, records dropped` | 協定紀錄檔寫入失敗（例如磁碟滿），紀錄丟棄；只在由正常轉為失敗時記一筆，恢復後再次失敗才再記 |
| `clock drift jumped` | 與 Central 的時間偏差達 1 秒，遊戲時間直接跳（往回時停住直到追上）；第一次同步也會記，但只有之後的大跳計入 `game_time_sync_jumps_total`；反覆出現查 NTP |
| `failed to write back player game data` | 玩家登出時寫回失敗；資料保留在記憶體，由背景寫回重試 |
| `gamestore memory poll gold adjustments failed` | 讀取跨 World 的 PvP 金幣調整失敗；調整仍在 `player_gold_adjustment`，下個週期或玩家下次載入時套用 |
| `playerstore redis restore incomplete` | World 重啟時部分玩家的 Redis 狀態讀取失敗被略過，`skippedPlayers` 為略過人數 |
| `code=8`（`AuthRateLimited`） | 同帳號或同來源 IP（IPv6 以 /64 計）登入過於頻繁被鎖定；NAT 後大量玩家可能共用 IP |
| `code=9`（`AuthServiceUnavailable`）且 Central 正常 | 可能是 Central 同時處理的登入達上限（64）、Central 新帳號取不到 bcrypt 槽位、Gate 查封禁時 Redis 出錯（fail-closed），或 Gate／World 尚未收到 Central 第一則 `TimeSync`（看 `/ready` 的 `time_sync`） |
| Lobby admin 回 `429 too many failed attempts` | 同一來源 IP（IPv6 以 /64 計）連續驗證失敗 5 次被鎖定，每 12 秒回復一次嘗試機會；追蹤表（10000 筆）滿且沒有可回收的條目時，**未追蹤的來源共用一組失敗額度**（5 次突發、每 12 秒回復 1 次），用完後一律 429，不會整張清空；表滿時每秒最多做一次全表清理，其餘新來源 O(1) 直接計入共用額度。驗證失敗日誌為 Warn `lobby admin auth failed`（`ip`、`route`＝路由樣板如 `POST /admin/grant-item`，不記原始路徑、`role`）。取捨：攻擊期間新來源的合法維運會暫時被擋 |
| GM 稽核日誌的 `actor_role` 欄位 | `audit=true` 的 GM 操作日誌帶 `actor_role`（`admin`／`ops`／`gm`），是實際授權通過的 token 層級，不含 token 本身 |
| `per-IP connection limit exceeded, closing`、`rejecting connection`、`rejecting connection: at capacity` | 單一 IP 超過連線上限、限流或名額已滿；**Debug 等級**，預設 Info 看不到。改看 `tcp_rejected_connections_total{reason}` 與 `game_connections_rejected_total` |
| 回應碼 `AuthWrongPassword`（13）、`login failed, notifying gate directly`（Warn，欄位 `code`） | 密碼驗證失敗（新帳號空密碼也回 13，日誌為 `login failed: new user without password`）；沒有 `wrong password` 日誌，量看 `game_login_total` 的 `result` |
| `stopped accepting new connections`（Info，欄位 `owner`，值為 TCP 服務名稱） | TCP 服務已停止接受新連線，開始排空 |
| `shutdown task "user drain": user drain: drain timeout with N remaining connections: context deadline exceeded`（Central 為 `central drain`、World 為 `world drain`） | 排空逾時，剩 N 條連線被強制關閉；沒有 `drain timeout reached`、`drain complete` 這類訊息，排空順利時不輸出獨立訊息 |
| `tracing init failed` | OTel 初始化失敗，span 不輸出，服務仍正常運作 |
| `board command failed` | 盤面指令內部失敗（資料庫／Redis 錯誤、逾時、斷路器開啟），同時計入 `game_board_command_total{result="error"\|"timeout"}`；日誌每 10 秒取樣一筆（帶 `err`），依賴故障時不會每則指令一行，要看量請用指標。商店金幣不足、互動失效、動作無效屬正常玩家回饋，只記 Debug |
| 格式非 JSON、帶 `component=stdlib_log` 的日誌 | 標準庫 `log` 的輸出（OTel 匯出錯誤、`net/http` 內部錯誤）已導向 zerolog；專案內只有 `pkg/logger` 可以 import `log` |

## 查詢降級

- Central audit record 讀取現在有 DB -> Redis cache fallback。
- 若看到 `central audit query degraded to cache`，代表 DB 短暫失敗，但快取命中，讀路徑還活著。
- 若快取也失敗，會回原本 DB error；先查 MySQL、再查 Redis、再看 cache key 是否過期。
- Redis routing / account 壞欄位時，Central audit 會直接報 invalid，不再把 `0` 當正常值。
- Central audit 做 Redis 修復時，壞 `gate/world` 也會算 drift，不會因為 memory 剛好是 `0` 就漏修。
- `configaudit` 遇到 Prometheus `scrape_configs` 結構壞掉會直接報錯，不再默默跳過。
- `opsdiag` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode opsdiag`；預設會維持 `--fail-on-degraded`
- `dephealth` 讀非 200 HTTP body 失敗時會直接報錯，不再吞掉讀取錯誤。
- `datasurgeon` apply 模式會刪掉 malformed `player:` / `world:*:players` key，不再讓壞 key 永久殘留。
- `datasurgeon` 讀 `player:` 狀態會對未知欄位報錯，不再把拼字錯誤的狀態當真。
- `datasurgeon` deadletter apply 模式會刪掉 malformed `gm:grant_item:deadletter:*` key，不再讓壞隊列殘留。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode datasurgeon -DataSurgeonMode <mode>`；預設只做觀察，`-DataSurgeonApply` 才會真的修 Redis。
- `pkg/grantitem` 讀 GM 命令會對未知欄位與尾巴資料報錯，不再把壞 deadletter 當真命令。
- `pkg/playerstoreredis` 讀玩家狀態會對未知欄位報錯，不再把壞 JSON 當真玩家資料。
- `pkg/requestjournalredis` 讀 Redis journal 會對未知欄位與尾巴資料報錯，不再把壞 journal 當成 miss。
- `pkg/msg` 的 `AuditSnapshotRequest/Response` 解析會對未知欄位與尾巴資料報錯，不再吞掉快照拼字錯誤。
- `tools/private/consistencysnapshot` 會對 Prometheus 非 200、未知欄位與尾巴資料報錯，不再把壞快照寫出去。
- `tools/private/opsdiag` 的 `/ready` 解析會對未知欄位、尾巴資料與空 checks 報錯，不再把壞 ready 當正常。
- `tools/private/consistencysnapshot` 會對 endpoint down 與 Prometheus 非 200 / 壞 JSON 報錯，不再把壞快照寫出去；統一入口是 `scripts/private/p0-daily-check.ps1 -Mode consistencysnapshot`；`-output` 指定巢狀路徑時會自動建立父目錄
- `tools/private/playersnapshot` 會對 gate diag 與 ready 壞回應報錯，不再把壞快照當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- `tools/private/supportdiag` 會對 session 與 ready 壞回應報錯，不再把壞客服資料當真；`-output` 指定巢狀路徑時會自動建立父目錄。
- （歷史）`tools/configdrift` 的 `mustGetString` 會對 nil config 回錯，不再 panic；該工具已移除，路由檢查併入 `tools/configaudit`。
- `configaudit` 會把 Grafana datasource 的 `url` 型別錯誤直接報成 invalid，不再當空值處理。
- Gate central ring 遇到 `ConnectInfo.ID == 0` 時會忽略，不再把 `0` 放進 hash ring。
- `deadletterreplay` 遇到 malformed deadletter key 會直接報錯，不再默默跳過。
- `deadletterreplay` 遇到 malformed deadletter payload 也會直接報錯，不再把壞 payload 吞掉。
- Lobby admin 的 grant-item dead-letter 列表 / replay / discard 遇到 malformed payload 會直接報錯。
- `playersnapshot` 與 `supportdiag` 讀 deadletter 時，遇到 malformed payload 會直接報錯，不再靜默跳過。

## 慢查追蹤

- `game_audit_record_lookup_seconds` 會記 Central audit record lookup 的 DB / cache 延遲。
- `central audit query slow` 代表該次 lookup 超過 `mysql.audit_record_slow_ms` 閾值，先看 MySQL 查詢、再看 Redis fallback。
- 若 p95 變差但沒有 error，通常是慢查不是故障；先查索引、鎖競爭、以及 cache 命中率。

## 資源自動回收

- `game_resource_recycle_total{service,resource}` 記各服務清掉的過期狀態，實際的組合只有：
  - `central` / `world_warmup`：Central 每分鐘（`Update1m`）回收的 World 冷卻記錄數。
  - `central` / `gate_disconnected`：Gate 斷線寬限到期（30 秒，每 5 秒掃描）後清掉的玩家數。
  - `central` / `gate_sync_stale`：Gate 重連後以在線快照對帳，移除快照裡已沒有的玩家數。
  - `gate` / `world_unavailable`：Gate 對 World 斷線寬限到期後清掉的玩家數。
  - `world` / `gate_unavailable`：World 對 Gate 斷線寬限到期後清掉的玩家數。
- 寬限類計數平時應為 0；持續增加代表對端反覆斷線超過寬限，先看對端存活與網路，再看 `game_service_grace_total`。

## 回歸樣本庫

- `go run ./tools/private/pja flow sample -list` 可列可重放樣本。
- `go run ./tools/private/pja flow sample -validate` 可驗證樣本 JSON 是否可供 `pja flow replay` 使用。
- 每次事故先留一份 login / logout / recovery / GM 樣本，日後用 `pja flow replay` 重打。
- `regressionsample` 會對未知欄位報錯，不再讓拼字錯誤樣本混進回歸庫。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode regressionsample`；預設先做 `validate`，要列出或重放單一樣本再加對應旗標。

## 告警自愈

- `scripts/private/alert-selfheal.ps1` 是告警 warning 的輕修復入口。
- `route_drift` / `stale_index` 會清路由與鎖衍生資料；`session_reconcile` 會請 Gate 收斂 session；`world_drain_stale` 會撤掉過期 drain 標記。
- 先 dry-run，看動作對不對，再真的 apply。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode alertselfheal -SelfHealAlertName <name>`；它會把 `AlertName / Redis / Gate / account / user / world` 參數原樣轉給 `alert-selfheal.ps1`。

## 變更審批

- `scripts/change-approval.ps1` 會寫 release/config/schema 審批 stamp。
- `scripts/docker-release.sh` 發版前會檢查 stamp；缺 stamp 或 target 不符就直接擋。
- release 前先看 checklist，再看回退點，再看監控。

## 服務分級

- `tools/private/dephealth` 把服務分成 `critical / core / peripheral`。
- `central`、`gate`、`world` 是 `critical`；`user` 是 `core`；其他暫歸 `peripheral`。
- 告警、限流、看板先盯 `critical`，`core` 次之，`peripheral` 再後。

## 冷資料搬遷

- `tools/private/coldstorage` 會把 `central:audit:record:*`、`gm:grant_item:deadletter:*`、`fault:archive:*` 匯出成 JSONL。
- `-purge` 會在匯出後刪 Redis 熱 key。
- 先 `-dry-run` 看 manifest，再決定要不要真搬。
- 要走統一入口時，直接用 `scripts/private/p0-daily-check.ps1 -Mode coldstorage`；預設只做 dry-run，看 manifest 不動資料。
