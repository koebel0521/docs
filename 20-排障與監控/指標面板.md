# 指標面板與告警

> 最後更新：Grafana dashboard 已擴充至 20 面板、新增 Go runtime 與 GameDataSaveFailure 告警、HandlerDuration 一律由預先解析 label 的 `metrics.HandlerTimer` 記錄。
> 回溯相容：現有 PromQL recording rule 名稱不變，現有 alert rule 名稱不變。

這份文件描述目前專案建議的 Prometheus / Grafana dashboard 與告警門檻。

指標定義請參考 `pkg/metrics/metrics.go`。
登入、登出、恢復校驗語意請參考 [[連線與登入流程]]。
資源 owner 與上限請參考 [[資源預算]]。告警 labels 也建議固定帶 `owner` + `severity`，方便 Alertmanager group / 抑制對齊責任域。
服務分級請參考 `tools/dephealth` 內建的 `critical / core / peripheral` 規則。
詞彙判讀請參考 [觀測詞彙表](./觀測詞彙表.md)。

## 目標

- 在 1 個 dashboard 內看出登入、登出、恢復、重連的健康度
- 能快速分辨問題是發生在 `Gate`、`Central`、還是 `World`
- 把「玩家感知問題」轉成可量測的 fail ratio、latency、mismatch rate
- 把 queue / backlog budget 一眼看出來，別等到 overflow 才知道

## 快速看圖

先看這個順序：

1. `SLO Summary`
2. `State Audit`
3. `Dependency Health`
4. `Capacity Budget`
5. `Login Outcomes` / `Logout Outcomes` / `Recovery Validation`

判讀：

- `ready` 壞 -> 先看 `SLO Summary` 與 `Dependency Health`
- `mismatch / error` -> 先看 `State Audit`
- `status=degraded` -> 先看 `Capacity Budget`
- `queue` 類指標先碰線 -> 先修 backlog，不先翻 handler

## Dashboard 版面建議

建議切成 13 個 panel 區塊。

### 1. SLO Summary

用途：

- 第一眼直接看服務是否達標
- 以錄製後的 availability / correctness / success percent 呈現，不需要自行重算

PromQL：

```promql
game_login_availability_percent_5m
game_logout_availability_percent_5m
game_recovery_correctness_percent_10m
tcp_reconnect_success_percent_5m
```

建議呈現：

- 4 個 Stat panel
- 顏色門檻以 99 / 95 / 90 為分界

### 1.1 Dependency Health

用途：

- 值班先看服務整體是否健康
- 和 `tools/dephealth` / `tools/opsdiag` 的輸出對齊
- 先看 `ready`，再看 `status`
- `status=degraded` 代表已碰到 warn threshold，不等於已經 down

建議欄位：

- `ready` / `status`
- `class`
- `tcp_send_queue_depth`
- `game_event_queue_depth`
- `game_async_failure_total`

建議呈現：

- table + conditional color
- `critical` 先排前
- `degraded` 標黃，`down` 標紅
- 右側可附 `reason`，直接顯示是哪個 budget 先碰線

建議門檻：

- `tcp_send_queue_depth >= 3000`
- `game_event_queue_depth >= 8000`
- `game_async_failure_total > 0`

### 2. Login Outcomes

用途：

- 觀察登入成功與失敗原因
- 快速判斷是入口阻擋、依賴故障、還是 World 拒絕

PromQL：

```promql
sum by (service, result) (
  increase(game_login_total[5m])
)
```

建議呈現：

- Stacked bar
- `service` 分欄
- `result` 分色

重點觀察：

- `gate_user / rate_limited`
- `gate_user / service_unavailable`
- `central / save_fail`
- `gate_user / server_full`

### 3. Login Failure Ratio

用途：

- 用單一百分比觀察登入是否正在退化

PromQL：

```promql
game_login_failure_ratio_5m * 100
```

建議呈現：

- Stat + sparkline

### 4. Logout Outcomes

用途：

- 觀察登出是否卡在 session 過期或依賴服務不可用

PromQL：

```promql
sum by (service, result) (
  increase(game_logout_total[5m])
)
```

建議呈現：

- Stacked bar

重點觀察：

- `gate_user / session_expired`
- `central / service_unavailable`
- `world / service_unavailable`

### 5. Recovery Validation

用途：

- 觀察 World 重啟恢復是否健康
- 追 `recovery_mismatch` 是否異常增加

PromQL：

```promql
sum by (service, result) (increase(game_recovery_validation_total[10m]))
```

失敗比例：

```promql
100 * sum(increase(game_recovery_validation_total{result="recovery_mismatch"}[10m])) / sum(increase(game_recovery_validation_total[10m]))
```

建議呈現：

- bar chart
- mismatch ratio stat

### 6. Replay Cache

用途：

- 觀察登入重送是否增加
- 分辨是正常 miss 還是 replay 風暴

PromQL：

```promql
sum by (service, result) (
  increase(game_login_replay_cache_total[5m])
)
```

建議呈現：

- Stacked bar 或 time series

重點觀察：

- `hit_failure` 暴增代表上游重送或依賴不穩
- `hit_success` 提高代表 retry 生效，但也可能是 client timeout 過短

### 7. Login Path Internal Latency

用途：

- 觀察登入流程的內部瓶頸：帳號鎖等待時間 vs DB 查詢時間

Account lock wait p95：

```promql
histogram_quantile(0.95, sum by (le, service) (rate(game_account_lock_wait_seconds_bucket[5m])))
```

DB query p95（find / save）：

```promql
histogram_quantile(0.95, sum by (le, service, operation) (rate(game_login_db_query_seconds_bucket[5m])))
```

Central audit lookup p95：

```promql
histogram_quantile(0.95, sum by (le, service, source, result) (rate(game_audit_record_lookup_seconds_bucket[5m])))
```

建議呈現：

- time series，lock wait、DB query、audit lookup 分線
- 若 lock wait 比 DB query 高，代表鎖競爭是瓶頸（帳號被大量並發登入）

### 8. World Online Players

用途：

- 即時觀察各 World 的在線人數分佈，及早發現負載不均
- 只統計 `GateID != 0` 的 active player；`GateID = 0` 的 logout 殘留不算在線

PromQL：

```promql
game_world_online_players
```

建議呈現：

- Gauge / stat，每個 `world_id` 一格

### 9. Heartbeat Timeout

用途：

- 監控玩家心跳超時被踢的頻率，偵測網路品質退化

PromQL：

```promql
sum by (service) (
  increase(game_heartbeat_timeout_total[5m])
)
```

建議呈現：

- time series
- 健康狀態下應接近 0；突然暴增代表網路抖動或客戶端異常

### 9. State Audit

用途：

- 觀察 Central / Gate / World 的週期性對帳結果
- 先抓「索引漂移」這類平常不容易直接看到的狀態不一致

PromQL：

```promql
sum by (service, result) (
  increase(game_state_audit_total[5m])
)
```

建議呈現：

- stacked bar
- `mismatch` 或 `error` 非 0 時要優先處理
- Central 在狀態鎖被持有（例如登入尖峰）時略過該輪並計為 `skipped`；`skipped` 長時間取代 `ok` 代表稽核實際上沒有在跑

### 9. Capacity Budget

用途：

- 先看 backlog 是否快爆掉
- 直接抓 `event queue` 與 `send queue` 的資源壓力
- 這一格要和 `資源預算`、`dephealth`、`opsdiag` 同一套門檻

PromQL：

```promql
game_event_queue_depth
tcp_send_queue_depth
increase(game_event_queue_overflow_total[5m])
increase(tcp_send_queue_overflow_total[5m])
```

建議呈現：

- event / send queue depth 用 time series
- overflow 用 stat 或 bar
- `3000 / 8000` 先亮黃，`overflow` 才亮紅

如果你要自動擴 World，可以把這一格當觸發條件：

- `game_world_online_players` 總和太高
- `game_event_queue_depth` 長時間高
- `tcp_send_queue_depth` 長時間高

對應工具：

- [scripts/world-autoscale.ps1](../../scripts/world-autoscale.ps1)

### 9. Handler Latency P95 / P99

用途：

- 觀察 handler latency，P95 與 P99 同面板方便對比

Handler p95 + p99（合併面板）：

```promql
game_handler_duration_p95_seconds
game_handler_duration_p99_seconds
```

建議呈現：

- time series，P95 與 P99 分色顯示

### 9. Reconnect Outcomes / Failure Ratio

用途：

- 觀察 TCP 連線穩定度

Reconnect outcomes：

```promql
sum by (service, result) (increase(tcp_reconnect_total[5m]))
```

Reconnect fail ratio：

```promql
tcp_reconnect_failure_ratio_5m * 100
```

建議呈現：

- stacked bar + stat

### 9. Resource Alert Dedup

用途：

- 讓同一類資源告警合成一條通知
- 先看 `resource_class`，不要被同時爆出的多條告警淹沒

Alertmanager 規則：

- `service + resource_class` 作為 group key
- `severity=page` 會壓同組 `warning`

建議分類：

- `queue`
- `latency`
- `login`
- `logout`
- `recovery`
- `reconnect`
- `audit`

### 9. Chat Room Queue

用途：

- 看 Chat 房間佇列有沒有積壓，以及訊息是不是因為佇列滿了被丟棄
- Chat 的歷史寫入與查詢在房間序列佇列中執行，慢查詢只會拖慢同一房間，這一格用來分辨是單點慢還是整體壓力

PromQL：

```promql
game_chat_room_queue_pending
game_chat_room_queue_active_rooms
histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_wait_seconds_bucket[5m])))
histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_duration_seconds_bucket[5m])))
increase(game_msg_queue_dropped_total{service="chat_room"}[5m])
```

指標說明：

- `game_chat_room_queue_pending`：所有房間等待執行的工作總數，單一房間上限 256
- `game_chat_room_queue_active_rooms`：目前有工作的房間數
- `game_chat_room_job_wait_seconds`：排入佇列到開始執行的等待時間，同房間前面的工作越慢越高
- `game_chat_room_job_duration_seconds`：單一工作的執行時間，主要反映 MySQL 延遲
- `game_msg_queue_dropped_total{service="chat_room"}`：單一房間佇列滿載而被丟棄的訊息數

判讀：

- 執行時間高、等待時間也高：MySQL 變慢，先查資料庫
- 執行時間正常、等待時間高：單一房間訊息量過大，檢查是否有人洗版
- 有丟棄計數：代表已經掉訊息，優先處理

## 初始告警門檻

這些門檻先以「偵測退化」為主，不以極端嚴格為目標。

### SLO Violation

- 條件：`game_login_availability_percent_5m < 99`
- 等級：warning
- 用途：登入健康度低於目標，先看 login outcomes 與 handler latency

- 條件：`game_logout_availability_percent_5m < 99`
- 等級：warning
- 用途：登出健康度低於目標，先看 logout outcomes 與 replay cache

- 條件：`game_recovery_correctness_percent_10m < 99.9`
- 等級：warning
- 用途：恢復校驗不穩，先看 World recovery validation 與 Gate session 對帳

- 條件：`tcp_reconnect_success_percent_5m < 99`
- 等級：warning
- 用途：重連成功率低於目標，先看 reconnect outcomes 與 socket queue overflow

### Service Down

- 規則：`GameServiceDown`
- 條件：`up == 0` 持續 1 分鐘，涵蓋 Prometheus 抓取的全部 job（central、gate、world、user、lobby、record、chat；正式環境設定沒有 user job）
- 等級：page
- 用途：服務停止或 `/metrics` 抓不到時，用 `rate`／`increase` 的告警都變成無資料而不會觸發，只能靠這條；處置見 [問題排查筆記](./問題排查筆記.md#服務抓取失敗gameservicedown)
- Grafana 總覽的 `Dependency Health` 以 `up{job=~"central|gate|world|user|lobby|record|chat"}` 列出每個服務的抓取狀態
- 正式環境 Alertmanager 的抑制規則以 `job` 為準：同一個 job 有 page 告警時，不再同時送出它的 warning

### Data Save Failure

- 規則：`GameDataSaveFailure`
- 條件：`increase(game_player_flush_failures_total[5m]) > 0` 持續 2 分鐘
- 等級：page
- 用途：World 把玩家異動寫回 MySQL 持續失敗，異動只留在記憶體；先查 MySQL 可用性與連線池，關機前確認 spill 目錄是否有落地檔

### Login Failure Ratio

- 條件：5 分鐘內登入失敗率 > 10%
- 等級：warning
- 用途：第一時間知道登入體驗正在退化

### Recovery Mismatch Detected

- 條件：10 分鐘內 `recovery_mismatch` > 0
- 等級：warning
- 用途：World 恢復與 Gate session 不一致

### Reconnect Failures Sustained

- 條件：5 分鐘內 reconnect fail 次數持續增加且成功為 0
- 等級：warning
- 用途：依賴服務可能斷線或網路異常

### Handler P95 Too High

- 條件：任一 handler 的 p95 > 0.2 秒持續 10 分鐘
- 等級：warning
- 用途：找出變慢中的 handler

### Handler P99 Critical

- 條件：任一 handler 的 p99 > 0.5 秒持續 10 分鐘
- 等級：page（Alertmanager 只把 `severity=page` 當成立即通知，原本的 `critical` 不會被路由）
- 用途：找出明顯影響玩家體驗的延遲

### Replay Cache Failure Hit Surge

- 條件：依 `job`／`instance`，5 分鐘內登入加登出 `hit_failure` > 20
- 等級：warning
- 用途：重送風暴、上游 timeout 過短、依賴不穩

### Heartbeat Timeout Surge

- 條件：依 `job`／`instance`／`service`，5 分鐘內 `game_heartbeat_timeout_total` > 50（`service` 分開玩家心跳與 S2S 心跳）
- 等級：warning
- 用途：大量連線心跳超時，可能是網路抖動、對端異常或過載

### World Online Player Imbalance

- 條件：單一 World `game_world_online_players` 超過其他 World 平均值 2 倍以上
- 等級：info（正式 Alertmanager 把 `severity="info"` 導到 blackhole，不通知值班，只在 UI 查看）
- 用途：提示負載不均，考慮調整 World 指派策略

## 新增告警規則

以下告警已加入伺服器倉庫的 `monitoring/prometheus/alert-rules.yml`（所有 compose 都從這裡掛載）。告警規則的單元測試在 `monitoring/prometheus/tests/alert-rules.test.yml`，以 `monitoring/prometheus/tests/run.sh` 執行（用 docker 的 `prom/prometheus` 映像跑 `promtool check rules` 與 `promtool test rules`，本機不需安裝 promtool）；改告警條件時一併補測試：

### GameGCPressureHigh

- 條件：`game_gc_cpu_fraction_5m > 0.25`
- 等級：warning
- 用途：GC 佔用 CPU 超過 25%，記憶體配置率過高

### GameMemoryPressureHigh

- 條件：`go_memstats_heap_inuse_bytes / go_gc_gomemlimit_bytes > 0.85 and go_gc_gomemlimit_bytes < 1e15`（持續 5m）
- 等級：warning
- 用途：以 `GOMEMLIMIT` 軟上限的比例判斷 heap 壓力：各服務上限不同（128～512MB），固定絕對值會讓小上限的服務先被 OOM 也不告警。`go_gc_gomemlimit_bytes` 為 MaxInt64 代表沒設上限，由 `< 1e15` 排除；heap_inuse 與 heap_sys 的比值在 GC 鋸齒下接近 1，無法反映壓力

### GameHighThreadCount

- 條件：`go_threads > 100`
- 等級：warning
- 用途：OS thread 數量異常，可能發生 thread 洩漏或 cgo 阻塞

### GameAsyncFailureDiscardDetected

- 條件：`game_async_failure_discard_rate_5m > 0`
- 等級：page
- 用途：非同步任務因佇列滿被丟棄，玩家資料可能遺失

### GamePersistPoolDiscardDetected

- 條件：`game_persist_pool_discard_rate_5m > 0`
- 等級：page
- 用途：持久化 pool 任務被丟棄，遊戲資料有遺失風險

### GameClockOffsetHigh

- 條件：`abs(game_clock_offset_seconds) > 1`
- 等級：warning
- 用途：該服務主機時鐘與 Central（遊戲時間來源）相差逾 1 秒；檢查兩台主機的 NTP（`chronyc tracking`），見 [Docker 生產部署](../30-部署與開發/Docker生產部署.md#主機時鐘ntp)

### GameTimeSyncJump

- 條件：`game_time_sync_jumps_5m > 0`（錄製自 `game_time_sync_jumps_total`，偏差達 1 秒直接跳到 Central 的次數，第一次同步不計）
- 等級：warning
- 用途：時間同步大跳；往回跳時遊戲時間停住直到追上，往前跳時遊戲時間一次前進（冷卻、恢復等提早到期）。多為 Central 或該主機 NTP 校正、手動改時間或 VM 暫停所致。舊的 `game_time_sync_adjustments_total` 每次同步都計數，只供觀察方向，不用於告警

### GameGoroutineLeakPossible

- 條件：`game_goroutine_growth_rate > 50`
- 等級：warning
- 用途：goroutine 持續以 >50/sec 增長，可能發生洩漏

### GameLoginE2EP99High

- 條件：`game_login_e2e_p99_seconds > 2`
- 等級：warning
- 用途：登入端到端 P99 超過 2 秒，玩家體驗受影響

### GameSchedLatencyHigh

- 條件：`game_sched_latency_p99_5m > 0.01`
- 等級：warning
- 用途：goroutine 排程 P99 超過 10ms，可能 CPU/thread/GC 競爭

### GameConnectionLeakPossible

- 條件：`game_connection_leak_diff > 5`
- 等級：warning
- 用途：TCP 層與應用層連線數不一致，可能 socket 洩漏

### GameChatRoomMessageDropped

- 條件：`increase(game_msg_queue_dropped_total{service="chat_room"}[5m]) > 0`
- 等級：page
- 用途：Chat 單一房間佇列已滿，新訊息被丟棄，玩家會看到訊息遺失

### GameChatRoomQueueBacklog

- 條件：`game_chat_room_queue_pending > 1000`
- 等級：warning
- 用途：Chat 房間佇列持續積壓，通常是 MySQL 變慢或某些房間訊息量異常

### GameChatRoomJobWaitHigh

- 條件：`histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_wait_seconds_bucket[5m]))) > 1`
- 等級：warning
- 用途：訊息排隊等待超過 1 秒才開始處理，聊天延遲明顯

### GameChatRoomJobSlow

- 條件：`histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_duration_seconds_bucket[5m]))) > 1`
- 等級：warning
- 用途：單一 Chat 工作執行超過 1 秒，檢查 MySQL 延遲與連線池

### GameSendQueueDepthHigh

- 條件：`tcp_send_queue_depth > 3000` 持續 5m
- 等級：warning
- 用途：socket 送出佇列持續積壓，對端消費太慢或廣播量過大；面板「Capacity Budget (Queue Depth)」

### GameEventQueueDepthHigh

- 條件：`game_event_queue_depth > 8000` 持續 5m
- 等級：warning
- 用途：app 事件佇列持續積壓，事件迴圈已追不上；面板「Capacity Budget (Queue Depth)」

### GameQueueOverflow

- 條件：`sum by (job, service) (label_replace(increase(tcp_send_queue_overflow_total[5m]), "queue", "send", "", "") or label_replace(increase(game_event_queue_overflow_total[5m]), "queue", "event", "", "")) > 0`（`increase()` 會去掉 `__name__`，兩側標籤組相同時 `or` 只留左側，事件佇列溢位會被吞掉，所以先用 `queue` 標籤區分兩側）
- 等級：page
- 用途：送出或事件佇列已溢位，連線被關閉或訊息被丟棄；面板「Capacity Budget (Overflows)」

### GameHTTPErrorRatioHigh

- 條件：`sum by (job, route) (rate(game_http_request_seconds_count{code=~"5.."}[5m])) / sum by (job, route) (rate(game_http_request_seconds_count[5m])) > 0.01` 持續 5m
- 等級：warning
- 用途：Lobby／Record HTTP 端點 5xx 比例超過 1%；面板「HTTP 5xx Ratio (5m)」

### GameHTTPLatencyP99High

- 條件：`histogram_quantile(0.99, sum by (job, le) (rate(game_http_request_seconds_bucket[5m]))) > 1` 持續 5m
- 等級：warning
- 用途：HTTP 請求 P99 超過 1 秒；面板「HTTP Latency P99 (5m)」

## 落地順序建議

1. 先接 Prometheus `/metrics`
2. 建第一版 dashboard
3. 先開 warning，再逐步開 page 通知
4. 跑一次壓測或本地故障演練，校準門檻
5. 再依實際流量調整 ratio 與觸發時間

### GameCircuitBreakerOpen

- 條件：`max by (job, instance, name) (circuit_breaker_state) == 2`，持續 2 分鐘
- 等級：page
- 用途：某個斷路器（MySQL、Redis 等）持續開啟，下游依賴不可用；`name` label 指出是哪一個

### GameRecordMQPublishErrors

- 條件：`sum by (job, instance) (increase(recordmq_publish_error_total[5m])) > 0`，持續 5 分鐘
- 等級：warning
- 用途：Record 事件發布到 RabbitMQ 持續失敗，事件會堆積在 World 的 outbox

### GameRecordMQDisconnected

- 條件：`job="record"` 的 `min by (job, instance) (recordmq_connection_status) == 0`；或 `job="world"` 的連線狀態為 0 且 `recordmq_enabled == 1`，持續 5 分鐘
- 等級：warning
- 用途：Record 消費端或 World 發布端的 RabbitMQ 連線中斷超過 5 分鐘。Central、Chat 也連進 recordmq 套件但不連線（恆為 0），不納入；World 設定了 RabbitMQ 就把 `recordmq_enabled` 設為 1（與連線成敗無關），所以「啟動後從未連上」也會告警；未設定 RabbitMQ 的 World 為 0，不納入。World 啟動首次連不上不會重試，整個行程期間都不發 Record（日誌 Error），需重啟 World。Record 消費端連線成功才設為 1、`Close` 時設為 0。`/ready` 不檢查 RabbitMQ，短於 5 分鐘的中斷不會觸發

### GameRecordQueueBacklog

- 條件：`max by (job, instance) (recordmq_queue_messages{job="record"}) > 10000`，持續 5 分鐘
- 等級：warning，`resource_class: async`
- 用途：Record 佇列持續積壓，代表消費長期跟不上發布。指標由 Record 消費端每 15 秒以被動宣告取樣 `record.events` 的待消費訊息數。門檻依實測訂定：2.8 萬筆／秒的突發發布會暫時積壓約 5 萬筆並在十幾秒內排空，不會誤報；先看 Record 的 MySQL 慢查詢與消費端是否停擺

### GameLoginCentralBusy

- 條件：`sum by (job) (increase(game_login_total{job="central", result="busy"}[5m])) > 10`，持續 2 分鐘
- 等級：warning，`resource_class: login`
- 用途：Central 同時處理登入達上限（`maxConcurrentLogins = 64`）時立刻回「服務忙碌」（code 9，客戶端會重試）；持續出現表示登入併發飽和，先看開服或大批重連尖峰與 bcrypt 併發。它 firing 時 Alertmanager 會抑制 `GameLoginAvailabilityLow` 與 `GameLoginFailureRatioHigh`（Gate 把 busy 拒絕計成 `service_unavailable`，但客戶端重試後實際沒有失敗）。容量背景見[容量與壓測基準](容量與壓測基準.md)

### GamePlayerStoreRedisErrors

- 條件：`sum by (job, instance) (increase(playerstore_redis_errors_total[5m])) > 10`，持續 5 分鐘
- 等級：warning
- 用途：玩家狀態 Redis 操作持續出錯（World 重啟恢復候選的寫入）；`op` 標籤指出是哪個操作。斷路器狀態看 `circuit_breaker_state{name="redis-playerstore"}`（原 `playerstore_redis_circuit_open` 已移除）

### GameDataConfigReloadFailing

- 條件：`increase(data_config_reload_total{result!="success"}[15m]) > 0`
- 等級：warning
- 用途：設定 artifact 重新載入失敗（`result` 為 `failed` 或 `rejected`），服務仍使用舊設定

### GameBoardCommandErrorRatioHigh

- 條件：依 `job`／`instance`／`command`，`game_board_command_total{result=~"error|timeout"}` 佔全部的比例 > 1%，持續 5 分鐘
- 等級：warning
- 用途：某種盤面指令持續失敗或逾時；`decode`（Client payload 解不開）不計。商店、道具、升級、擲骰遇到資料庫／Redis 錯誤、逾時或斷路器開啟時，回應仍是 Rejected，但內部失敗（`board.ErrResolutionFailed`）現在也計為 `error`／`timeout`，不再記成 `ok`。指令別延遲看 `game_handler_duration_seconds{handler="board_<指令名>"}`，排隊等待看 `handler="board_queue_wait"`

### GameServiceHelloMismatch

- 條件：`sum by (job, instance) (increase(game_service_hello_mismatch_total[5m])) > 0`
- 等級：page
- 用途：服務間發版身分不同而拒絕連線，代表混版本部署。撥號成功時已計 `tcp_reconnect_total{result="success"}`，之後才因 hello 不符關閉，重連類告警不會觸發

### GameConnectionsAtCapacity

- 條件：`increase(tcp_rejected_connections_total{reason="at_capacity"}[5m]) > 0`
- 等級：warning
- 用途：連線數已滿，新玩家連不上（容量飽和）。`tcp_rejected_connections_total` 的 `reason` 另有 `rate_limited`（來源 IP 超速）與 `handshake_timeout`（Gate 連上後沒在期限內登入，Debug 日誌、不寫 Warn）；本告警只篩 `at_capacity`，不受其他原因影響

### GameMessagesDropped

- 條件：`sum by (job, instance, reason) (increase(tcp_dropped_messages_total{reason!="board_decode"}[5m])) > 10`，持續 5 分鐘
- 等級：warning
- 用途：持續丟棄訊息；Gate 的 `no_world`／`world_unavailable` 代表盤面指令找不到 World 連線（Client 只會等逾時），World 的 `board_queue_full`／`unknown_player`、S2S 的 `unpack`／`handler_panic` 見指標註解

### GameAccountPurgeFailing

- 條件：`sum by (job, instance) (increase(game_account_purge_total{result="failed"}[1d])) > 0`
- 等級：warning
- 用途：每日帳號清除（保留期合規作業，見[帳號保留政策](../帳號保留政策.md)）近一天有失敗，合規作業可能沒有完成。`game_account_purge_total{result}` 的 `result` 為 `purged`（清除成功一個帳號）或 `failed`（掃描或清除步驟失敗）；World 暫時不可用不計失敗，下輪會自行重試。看 Central 日誌與 World 連線

### GameUnknownMessages

- 條件：`increase(tcp_unknown_messages_total{service!="user"}[5m]) > 0`，持續 5 分鐘
- 等級：warning
- 用途：S2S 連線持續收到未知訊息，服務間協定版本不一致或漏註冊 handler

### GameAccountLockError

- 條件：`increase(game_account_lock_total{result="error"}[5m]) > 0`，持續 2 分鐘
- 等級：warning，`resource_class: login`
- 用途：共享帳號鎖本身故障（非鎖競爭），登入回 `AuthServiceUnavailable`；Central 錯誤日誌已改為 10 秒取樣一筆

### GameFileDescriptorsHigh

- 條件：`process_open_fds / process_max_fds > 0.8`，持續 5 分鐘
- 等級：warning，`resource_class: runtime`
- 用途：fd 將耗盡時 accept 會失敗（Gate 上限 4096 條玩家連線加 S2S 連線）

### GameS2SPeersMissing

- 條件：`tcp_dial_targets`（全連模式設定的對端數）大於 `tcp_connections_active`，持續 5 分鐘
- 等級：warning，`resource_class: reconnect`
- 用途：Gate 同時連每個 World 時少連了幾台；哪個位址撥不通看 `dial error` 日誌的 `addr`

## 寬限期與佇列飽和指標

- `game_service_grace_total{service, outcome}`：對端服務斷線寬限 `entered`／`reconnected`／`expired` 次數；`game_service_grace_pending{service}` 為目前仍在寬限中的對端數。
- `game_resource_recycle_total{service, resource}`：寬限到期（Central `gate_disconnected`、World `gate_unavailable`、Gate `world_unavailable`）與 Central 對帳移除（`gate_sync_stale`）計的是實際清掉的玩家數，對端已重連或沒有玩家時不計。
- `game_shard_queue_depth_max{queue}`：World 分片佇列（`board`、`persist`、`write_back`）最深分片的長度，scrape 時取樣，丟棄前就看得到熱分片積壓。
- `game_http_request_seconds` 在有取樣 span 時附 `trace_id` exemplar；`/metrics` 支援 OpenMetrics，Prometheus 以 `--enable-feature=exemplar-storage` 啟動才會保存。

## 連線池與延遲桶

- MySQL 連線池統計由 `pkg/mysql` 在 `Connect` 後註冊（`go_sql_*`：`max_open_connections`、`open_connections`、`in_use_connections`、`idle_connections`、`wait_count_total`、`wait_duration_seconds_total`），`db_name` label 為資料庫名稱。`wait_count_total` 持續增加代表連線池飽和，需調大 `max_open` 或查慢查詢。Redis 用戶端（rueidis）沒有提供連線池統計。
- `game_handler_duration_seconds` 使用自訂桶（0.5ms 到 10s），遊戲 handler 多半在數毫秒內完成，P50／P95 才不會擠在同一個桶。桶邊界變動不影響既有 PromQL 與 recording rule 名稱。
