# 指標面板與告警

> 最後更新：Grafana dashboard 已擴充至 48 面板（含 Alert Coverage 列）、新增 Go runtime 與 GameDataSaveFailure 告警、HandlerDuration 一律由預先解析 label 的 `metrics.HandlerTimer` 記錄。
> 回溯相容：現有 PromQL recording rule 名稱不變，現有 alert rule 名稱不變。

這份文件描述目前專案建議的 Prometheus / Grafana dashboard 與告警門檻。

指標定義請參考 `pkg/metrics/metrics.go`。
登入、登出、恢復校驗語意請參考 [[連線與登入流程]]。
資源 owner 與上限請參考 [[資源預算]]。告警 labels 也建議固定帶 `owner` + `severity`，方便 Alertmanager group / 抑制對齊責任域。
服務分級請參考 `tools/private/dephealth` 內建的 `critical / core / peripheral` 規則。
詞彙判讀請參考 [觀測詞彙表](./觀測詞彙表.md)。

## 目標

- 在 1 個 dashboard 內看出登入、登出、恢復、重連的健康度
- 能快速分辨問題是發生在 `Gate`、`Central`、還是 `World`
- 把「玩家感知問題」轉成可量測的 fail ratio、latency、mismatch rate
- 把 queue / backlog budget 一眼看出來，別等到 overflow 才知道

## 快速看圖

先看這個順序：

1. `SLO Summary`
2. `State Audit`
3. `Dependency Health`
4. `Capacity Budget`
5. `Login Outcomes` / `Logout Outcomes` / `Recovery Validation`

判讀：

- `ready` 壞 -> 先看 `SLO Summary` 與 `Dependency Health`
- `mismatch / error` -> 先看 `State Audit`
- `status=degraded` -> 先看 `Capacity Budget`
- `queue` 類指標先碰線 -> 先修 backlog，不先翻 handler

## Dashboard 版面建議

建議切成 13 個 panel 區塊。

### 1. SLO Summary

用途：

- 第一眼直接看服務是否達標
- 以錄製後的 availability / correctness / success percent 呈現，不需要自行重算

PromQL：

```promql
game_login_availability_percent_5m
game_logout_availability_percent_5m
game_recovery_correctness_percent_10m
tcp_reconnect_success_percent_5m
```

建議呈現：

- 4 個 Stat panel
- 顏色門檻以 99 / 95 / 90 為分界

### 1.1 Dependency Health

用途：

- 值班先看服務整體是否健康
- 和 `tools/private/dephealth` / `tools/private/opsdiag` 的輸出對齊
- 先看 `ready`，再看 `status`
- `status=degraded` 代表已碰到 warn threshold，不等於已經 down

建議欄位：

- `ready` / `status`
- `class`
- `tcp_send_queue_depth`
- `game_event_queue_depth`
- `game_async_failure_total`

建議呈現：

- table + conditional color
- `critical` 先排前
- `degraded` 標黃，`down` 標紅
- 右側可附 `reason`，直接顯示是哪個 budget 先碰線

建議門檻：

- `tcp_send_queue_depth >= 3000`
- `game_event_queue_depth >= 8000`
- `game_async_failure_total > 0`

### 2. Login Outcomes

用途：

- 觀察登入成功與失敗原因
- 快速判斷是入口阻擋、依賴故障、還是 World 拒絕

PromQL：

```promql
sum by (service, result) (
  increase(game_login_total[5m])
)
```

建議呈現：

- Stacked bar
- `service` 分欄
- `result` 分色

同一面板另有第二條查詢（refId B，圖例「gate 本地拒絕 / {{reason}}」）：`sum by (reason) (increase(game_login_rejected_total[5m]))`，顯示 Gate 本地拒絕；這些不計入 `game_login_total`。

第三條查詢（refId C，圖例「gate service_unavailable 原因 / {{reason}}」）：`sum by (reason) (increase(game_login_unavailable_total[5m]))`，拆解 `game_login_total{result="service_unavailable"}` 中 Gate 自己回的原因（`ban_check_failed`、`no_central`、`time_not_synced`、`central_gone` 等）；`GameLoginGateUnavailable` 響時先看這條。


重點觀察：

- `gate_user / rate_limited`（只剩 Central 鎖競爭造成的；Gate 本地限流不再計入 `game_login_total`，改看 `game_login_rejected_total{reason}`）
- `gate_user / service_unavailable`
- `gate_user / session_expired`（只代表 pending 真正逾時）
- `gate_user / client_closed`（玩家自己斷線，用戶端放棄，不算失敗）
- `central / save_fail`
- `gate_user / server_full`

### 3. Login Failure Ratio

用途：

- 用單一百分比觀察登入是否正在退化

PromQL：

```promql
game_login_failure_ratio_5m * 100
```

失敗 regex 為 `server_fail|save_fail|service_unavailable|session_expired|unknown`。Gate 掃描到的 pending 逾時（Central／World 沒有回覆的登入）現在由 Gate 補計：`game_login_total{result="session_expired"}`、`game_login_e2e_seconds`（登出為 `game_logout_total{result="service_unavailable"}`），所以 Central／World 無回應時登入可用率與 P99 告警會反映出來，不再是分母不含這些請求。補計之後晚到的上游回覆（連線還在但 session 已不存在）不會再計一次 `game_login_total`，同一次登入只有一筆結果（由取走 pending 的同一次持鎖決定，沒取到就不計）。玩家在上游回覆前自己斷線改計 `result="client_closed"`：它是用戶端放棄而非伺服器失敗，不在失敗 regex 內，也不進 `game_login_e2e_seconds`，且與 `GameLoginAvailabilityLow`／`GameLoginFailureRatioHigh` 的分母一併排除（規則用 `result!="client_closed"`），避免單一客戶端反覆「送 LoginRequest 就關連線」洗掉或稀釋 SLI。`session_expired` 只代表 pending 真正逾時，Central 斷線中止登入計 `service_unavailable`。登入處理中的重送（`duplicate_pending`）與未登入連線送來的登出（`not_logged_in`）不是一次完整的登入／登出，不計入 `game_login_total`／`game_logout_total` 與登入延遲直方圖（避免稀釋失敗率與 P99），改計 `game_request_ignored_total{flow,cause}`（`flow` 為 `login`、`logout`），用 `sum by (flow, cause) (increase(game_request_ignored_total[5m]))` 觀察。Gate 在建立 pending 之前就地拒絕的登入只有四類（`account_empty`、帳號正規化失敗或密碼過長的 `wrong_password`、`already_logged_in`、`rate_limited`；`checkLoginRequest` 失敗走 `rejectLocal`）同樣不計入 `game_login_total` 與 `game_login_e2e_seconds`，改計 `game_login_rejected_total{reason}`，用 `sum by (reason) (increase(game_login_rejected_total[5m]))` 觀察；它**不在** `GameLoginFailureRatioHigh`、`GameLoginAvailabilityLow`、`GameLoginE2EP99High` 的分子或分母內，所以單一用戶端灌這類請求不會稀釋或洗掉登入 SLI（原本它們留在分母，會讓三條告警一併失靈），要看被拒絕的量或來源異常請看這個指標。pending 建立之後的拒絕（封禁查詢失敗、帳號被封、沒有 Central、Central ctx 已取消）走 `Coordinator.rejectPending(sock, code, reason, start)`（以 `TakePendingLogin` 取走 pending），**不是**本地拒絕：它們照常計 `game_login_total`（`service_unavailable`／`account_banned`）與 `game_login_e2e_seconds`，在登入告警的分母內，Redis 或封禁查詢故障時 `GameLoginAvailabilityLow`／`GameLoginFailureRatioHigh` 會響。時間未同步的 `service_unavailable` 同樣仍計 `game_login_total`。登入結果計量的單一入口是 `flowbase.CountLoginResult`（`service_unavailable` 轉 `CountUnavailableLogin` 並記 `game_login_unavailable_total{reason}`，其他結果碼走 `CountLogin`）。`CountLogin` 是 pending 取走（`TakePendingLogin`、`BindPendingLogin`、逾時掃描、Central 斷線）後的計量入口，傳入取走 pending 時回傳的建立時間，沒取到就不計，避免與斷線路徑重複計；`rejectLocal` 在 pending 建立前拒絕，以請求起點計 `game_login_rejected_total`。登出 pending 重送（`flow="logout"`、`cause="duplicate_pending"`）與 Gate 本地限流擋下的登出（`cause="rate_limited"`）改計 `game_request_ignored_total`，不再計入 `game_logout_total`（行為變更，避免洪水重送稀釋登出告警）。

建議呈現：

- Stat + sparkline

### 4. Logout Outcomes

用途：

- 觀察登出是否卡在 session 過期或依賴服務不可用

PromQL：

```promql
sum by (service, result) (
  increase(game_logout_total[5m])
)
```

建議呈現：

- Stacked bar

重點觀察：

- `gate_user / service_unavailable`（Gate 端登出 pending 逾時計此值，不是 `session_expired`；`client_closed` 只出現在登入，登出面板沒有）
- `central / service_unavailable`
- `world / service_unavailable`

### 5. Recovery Validation

用途：

- 觀察 World 重啟恢復是否健康
- 追 `recovery_mismatch` 是否異常增加

PromQL：

```promql
sum by (service, result) (increase(game_recovery_validation_total[10m]))
```

失敗比例：

```promql
100 * sum(increase(game_recovery_validation_total{result="recovery_mismatch"}[10m])) / sum(increase(game_recovery_validation_total[10m]))
```

Gate 拒絕的驗證（`game_recovery_validation_rejected_total{service,reason}`）：目前只有 `reason="queue_full"`，是 Gate 背景佇列滿而拒絕恢復驗證，Gate 仍回 `RecoveryMismatch`，World 端因此跟著計 `recovery_mismatch`。驗證已完成但結果日誌沒寫入 Redis（重送時無法回放）另計 `game_recovery_validation_journal_skipped_total{service}`：這種情況 Gate 回的是真實結果，**不是**被拒或降級，所以不進 `rejected_total`（舊版把它記成 `reason="journal_skipped"`，已移除）。看 `recovery_mismatch` 升高時先對照 `rejected_total`：同時間有增量就是 Gate 過載，不是真的狀態不一致。

```promql
sum by (service, reason) (increase(game_recovery_validation_rejected_total[10m]))
```

建議呈現：

- bar chart
- mismatch ratio stat

### 6. Replay Cache

用途：

- 觀察登入重送是否增加
- 分辨是正常 miss 還是 replay 風暴

PromQL：

```promql
sum by (service, result) (
  increase(game_login_replay_cache_total[5m])
)
```

登出對應 `game_logout_replay_cache_total`（label 相同），`GameReplayCacheFailureHitSurge` 把兩者的 `hit_failure` 加總。

建議呈現：

- Stacked bar 或 time series

重點觀察：

- `hit_failure` 暴增代表上游重送或依賴不穩
- `hit_success` 提高代表 retry 生效，但也可能是 client timeout 過短

### 7. Login Path Internal Latency

用途：

- 觀察登入流程的內部瓶頸：帳號鎖等待時間 vs DB 查詢時間

Account lock wait p95：

```promql
histogram_quantile(0.95, sum by (le, service) (rate(game_account_lock_wait_seconds_bucket[5m])))
```

DB query p95（find / save）：

```promql
histogram_quantile(0.95, sum by (le, service, op) (rate(game_login_db_query_seconds_bucket[5m])))
```

Central audit lookup p95：

```promql
histogram_quantile(0.95, sum by (le, service, source, result) (rate(game_audit_record_lookup_seconds_bucket[5m])))
```

建議呈現：

- time series，lock wait、DB query、audit lookup 分線
- 若 lock wait 比 DB query 高，代表鎖競爭是瓶頸（帳號被大量並發登入）

### 8. World Online Players

用途：

- 即時觀察各 World 的在線人數分佈，及早發現負載不均
- 只統計 `GateID != 0` 的 active player；`GateID = 0` 的 logout 殘留不算在線

PromQL：

```promql
game_world_online_players
game_world_online_players / game_world_max_players
```

`game_world_max_players{world_id}` 是 World 啟動時設定的 `max_players` 上限（不熱重載），用來算容量使用率；告警見 `GameWorldNearCapacity`。

建議呈現：

- Gauge / stat，每個 `world_id` 一格

### 9. Heartbeat Timeout

用途：

- 監控玩家心跳超時被踢的頻率，偵測網路品質退化

PromQL：

```promql
sum by (service) (
  increase(game_heartbeat_timeout_total[5m])
)
```

`service="gate_user"` 是玩家心跳（告警 `GameHeartbeatTimeoutSurge`，依在線數比例）；其他 `service` 是 S2S 心跳（告警 `GameS2SHeartbeatTimeout`，每次都代表一條服務連線斷掉）。S2S 端的序列在建立連線解析指標時就以 0 建立（第十二輪 O-L4），第一次逾時 `increase()` 就看得到；以前第一次逾時才出現序列、值一出現就是 1，告警要多等一次。Gate 玩家心跳與握手逾時第十二輪起以單調時鐘判斷，主機牆鐘前跳不再造成全體逾時斷線。

建議呈現：

- time series
- 健康狀態下應接近 0；突然暴增代表網路抖動或客戶端異常

### 9. State Audit

用途：

- 觀察 Central / Gate / World 的週期性對帳結果
- 先抓「索引漂移」這類平常不容易直接看到的狀態不一致

PromQL：

```promql
sum by (service, result) (
  increase(game_state_audit_total[5m])
)
```

建議呈現：

- stacked bar
- `mismatch` 或 `error` 非 0 時要優先處理
- Central 在狀態鎖被持有（例如登入尖峰）時略過該輪並計為 `skipped`；`skipped` 長時間取代 `ok` 代表稽核實際上沒有在跑

### 9. Capacity Budget

用途：

- 先看 backlog 是否快爆掉
- 直接抓 `event queue` 與 `send queue` 的資源壓力
- 這一格要和 `資源預算`、`dephealth`、`opsdiag` 同一套門檻

PromQL：

```promql
game_event_queue_depth
tcp_send_queue_depth
sum by (service, action) (increase(game_event_queue_overflow_total[5m]))
increase(tcp_send_queue_overflow_total[5m])
```

`game_event_queue_overflow_total` 的 `action`（第十一輪）：`closed`＝玩家連線因事件佇列滿被關閉；`backpressure`＝S2S 連線阻塞等待後仍送入，不丟訊息、不斷線。兩個序列在服務啟動時都先建為 0。

建議呈現：

- event / send queue depth 用 time series
- overflow 用 stat 或 bar
- `3000 / 8000` 先亮黃，`overflow` 才亮紅

注意：`game_event_queue_depth` 只在排空時更新，事件迴圈被 handler 卡住時它會凍結在舊值、不會升高。判斷迴圈卡死看 `game_event_loop_last_tick_timestamp_seconds{service}`（迴圈啟動與每次 tick 更新）與 `GameEventLoopStalled`；目前沒有 `/ready` 的迴圈存活檢查，深度也沒有改成 scrape 時讀取。

如果你要自動擴 World，可以把這一格當觸發條件：

- `game_world_online_players` 總和太高
- `game_event_queue_depth` 長時間高
- `tcp_send_queue_depth` 長時間高

對應工具：

- [scripts/world-autoscale.ps1](../../scripts/world-autoscale.ps1)

### 9. TCP 訊息量與設定熱重載

- `tcp_messages_sent_total{service}`：TCP 層送出訊息數，與 `tcp_messages_received_total` 對照看收發是否失衡，例如 `sum by (service) (increase(tcp_messages_sent_total[5m]))`。
- `data_config_reload_duration_seconds`：設定 artifact 重載耗時 histogram，例如 `histogram_quantile(0.95, sum by (le) (rate(data_config_reload_duration_seconds_bucket[5m])))`。
- `data_config_last_reload_timestamp_seconds`：最近一次成功重載的 Unix 時間；`time() - data_config_last_reload_timestamp_seconds` 是距上次成功重載的秒數。失敗次數看 `data_config_reload_total{result}`。
- `game_config_reload_total{result}`：應用設定（`config/*.yaml`）熱重載結果（第十二輪），`result` 為 `applied`、`rejected`（讀檔／驗證失敗、套用回錯或 Apply panic，panic 時 baseline 不前進）、`restart_required`（改了不可熱更的鍵）、`shadowed`（被環境變數或旗標遮蔽），監看開始時先建為 0；例如 `sum by (job, instance, result) (increase(game_config_reload_total[1h]))`。`rejected` 對應告警 `GameConfigReloadRejected`。

### 9. Reconnect Outcomes / Failure Ratio

用途：

- 觀察 TCP 連線穩定度

Reconnect outcomes：

```promql
sum by (service, result) (increase(tcp_reconnect_total[5m]))
```

Reconnect fail ratio：

```promql

```

錄製規則 `tcp_reconnect_failure_ratio_5m` 與兩條重連告警都依 `job`、`instance`、`service`（對端）分開計算（第十一輪）：原本只依 `job` 加總，同一 Gate 連 Chat 有成功就遮住連 World 的持續失敗。

建議呈現：

- stacked bar + stat

### 9. Resource Alert Dedup

用途：

- 讓同一類資源告警合成一條通知
- 先看 `resource_class`，不要被同時爆出的多條告警淹沒

Alertmanager 規則：

- `alertname + job + resource_class` 作為 group key（`group_by: [alertname, job, resource_class]`）
- `severity=page` 會壓同 `job`＋`instance` 的 `warning`（`equal: [job, instance]`，開發 `monitoring/alertmanager/alertmanager.yml` 與正式 `docker/monitoring/alertmanager.prod.yml` 相同，`TestAlertmanagerInhibitRulesMatchProd` 比對兩份），且排除 `GameHandlerP99Critical` 當來源
- `GameLoginFailureRatioHigh` 會壓同 `job` 的 `GameLoginAvailabilityLow`（失敗率超過 10% 必然讓可用率低於 99%，只留一封）

規則檔實際使用的 `resource_class`（其餘告警沒有這個標籤，只依 `alertname`＋`job` 分組）：

- `persistence`
- `async`
- `queue`
- `latency`
- `login`
- `logout`
- `recovery`
- `reconnect`
- `http`
- `database`
- `runtime`

Alertmanager 路由另外預留 `clock` 的比對，但目前沒有任何告警使用它。

### 9. Chat Room Queue

用途：

- 看 Chat 房間佇列有沒有積壓，以及訊息是不是因為佇列滿了被丟棄
- Chat 的歷史寫入與查詢在房間序列佇列中執行，慢查詢只會拖慢同一房間，這一格用來分辨是單點慢還是整體壓力

PromQL：

```promql
game_chat_room_queue_pending
game_chat_room_queue_active_rooms
histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_wait_seconds_bucket[5m])))
histogram_quantile(0.99, sum by (le) (rate(game_chat_room_job_duration_seconds_bucket[5m])))
increase(game_msg_queue_dropped_total{service="chat_room"}[5m])
```

指標說明：

- `game_chat_room_queue_pending`：所有房間等待執行的工作總數，單一房間上限 256
- `game_chat_room_queue_active_rooms`：目前有工作的房間數
- `game_chat_room_job_wait_seconds`：排入佇列到開始執行的等待時間，同房間前面的工作越慢越高
- `game_chat_room_job_duration_seconds`：單一工作的執行時間，主要反映 MySQL 延遲
- `game_msg_queue_dropped_total{service="chat_room"}`：單一房間佇列滿載而被丟棄的訊息數；關機排空期間佇列已關閉而被拒的工作只記 Debug、不計入（第十一輪，避免正常發版誤 page）

判讀：

- 執行時間高、等待時間也高：MySQL 變慢，先查資料庫
- 執行時間正常、等待時間高：單一房間訊息量過大，檢查是否有人洗版
- 有丟棄計數：代表已經掉訊息，優先處理

聊天歷史讀寫結果（第十二輪）：`game_chat_history_ops_total{op, result}`，`op` 為 `append`（玩家訊息寫入）、`sync`（歷史查詢）、`system`（系統訊息寫入）、`purge`（保留期清理），`result` 為 `ok`／`error`，Chat 套件載入時各序列預建為 0。寫入失敗的訊息不入庫也不送達；MySQL 唯讀、磁碟滿時 ping 照樣成功，就緒檢查看不到，只能看這個計數。Gate 斷線造成的 sync 取消、關機時的 purge 取消不計失敗。例如 `sum by (op, result) (increase(game_chat_history_ops_total[5m]))`；告警 `GameChatHistoryWriteFailing`、`GameChatHistorySyncFailing`、`GameChatHistoryPurgeFailing`。

保留期作業結果：`game_retention_ops_total{task,result}`，涵蓋 World／Record 背景清理與封存；`task` 為 `outbox`、`combat_session`、`unsettled_combat_session`、`mission_event`、`player_archive`、`record_table`，另有 `round`（World 整輪取鎖／連線失敗），`result` 為 `ok`／`error`，啟動時各序列預建為 0，關機取消不計；依賴索引的作業在索引缺少時跳過並計 `error`。Chat 聊天紀錄與 Central 帳號清除另有既有指標，不併入。清理失敗只記 Warn（World 大表單一作業 `retention job failed`、整輪 `retention purge failed`；玩家封存 `player archive failed`；Record 日分表 `record table retention: list tables failed／drop failed, will retry next check`）、下一輪再試，連續失敗時資料表無上限成長，只能靠這個計數發現；例如 `sum by (task, result) (increase(game_retention_ops_total[1d]))`；告警 `GameRetentionPurgeFailing`。

Gate 同來源房間配額（第十二輪 SC-L2）：同一來源 IP 在同一 Chat 房間經同一台 Gate 加入超過 `session.chat_room_members_per_ip`（預設 50）時，Gate 不轉送加入，計入 `game_chat_rate_limited_total{kind="join"}`。

## 初始告警門檻

這些門檻先以「偵測退化」為主，不以極端嚴格為目標。

### SLO Violation

- 條件：`game_login_availability_percent_5m < 99`
- 等級：warning
- 用途：登入健康度低於目標，先看 login outcomes 與 handler latency

- 最低流量門檻：下列五條比例告警（`GameLoginAvailabilityLow`、`GameLogoutAvailabilityLow`、`GameRecoveryCorrectnessLow`、`TCPReconnectSuccessLow`、`GameLoginFailureRatioHigh`）都再加一個條件：對應計數器每秒速率（`rate(...)`，登入／登出 5 分鐘、恢復 10 分鐘窗口）須大於 0.05（約每分鐘 3 筆）；低流量時一兩筆失敗會讓比例劇烈擺盪，不觸發。流量低於門檻（例如深夜）時這幾條告警不會響，登入完全失敗要靠 `GameServiceDown` 等不依賴比例的告警

- 規則：`GameLogoutAvailabilityLow`（登入為 `GameLoginAvailabilityLow`，皆持續 5 分鐘）
- 條件：`game_logout_availability_percent_5m < 99`
- 等級：warning
- 用途：登出健康度低於目標，先看 logout outcomes 與 replay cache

- 規則：`GameRecoveryCorrectnessLow`（持續 10 分鐘）
- 條件：`game_recovery_correctness_percent_10m < 99.9`
- 等級：warning
- 用途：恢復校驗不穩，先看 World recovery validation 與 Gate session 對帳

- 規則：`TCPReconnectSuccessLow`（持續 5 分鐘）
- 條件：`tcp_reconnect_success_percent_5m < 99`，且同一 `job`／`instance`／`service` 的重連速率 > 0.05/s
- 等級：warning
- 用途：重連成功率低於目標，先看 reconnect outcomes 與 socket queue overflow

### Service Down

- 規則：`GameServiceDown`
- 條件：`up == 0` 持續 1 分鐘，涵蓋 Prometheus 抓取的全部 job（central、gate、world、user、lobby、record、chat；正式環境設定沒有 user job，但多抓 `prometheus`、`alertmanager` 兩個告警管線自身的 job，它們掛掉同樣觸發）
- 等級：page
- 用途：服務停止或 `/metrics` 抓不到時，用 `rate`／`increase` 的告警都變成無資料而不會觸發，只能靠這條；處置見 [問題排查筆記](./問題排查筆記.md#服務抓取失敗gameservicedown)
- Grafana 總覽的 `Dependency Health` 以 `up{job=~"central|gate|world|user|lobby|record|chat"}` 列出每個服務的抓取狀態
- 正式環境 Alertmanager 的抑制規則以 `job`＋`instance` 為準：同一個實例有 page 告警時，不再同時送出它的 warning；多實例（World file_sd）時一台出事不會壓掉其他實例的 warning。`GameHandlerP99Critical` 是症狀，不當抑制來源，免得壓掉 DB 連線池、Redis 錯誤等根因 warning。本機演練用的 `monitoring/alertmanager/alertmanager.yml` 的抑制規則與正式完全相同（第十輪前只比 `job`，演練結論會與正式相反；`configaudit` 的 `TestAlertmanagerInhibitRulesMatchProd` 比對兩份）。另有一條衍生告警抑制：`GameLoginFailureRatioHigh` 壓 `GameLoginAvailabilityLow`（`equal: [job]`；失敗率超過 10% 必然也讓可用率低於 99%，只留失敗率一條）

### Data Save Failure

- 規則：`GameDataSaveFailure`
- 條件：`increase(game_player_flush_failures_total[5m]) > 0` 持續 2 分鐘
- 等級：page
- 用途：World 把玩家異動寫回 MySQL 持續失敗，異動只留在記憶體；先查 MySQL 可用性與連線池，關機前確認 spill 目錄是否有落地檔
- 關機取消不計：SIGTERM 取消 App ctx 後進行中或排隊的寫回會得到 `context canceled`，`flushOnce` 在 ctx 已取消時不計 `game_player_flush_failures_total`、不記 Warn（異動仍在 pending，由關機落地階段寫回或 spill），所以滾動重啟不會誤發本告警；離線玩家卸載（`evictOfflinePlayers`）在 ctx 已取消時同樣不記失敗 Warn。`Memory.Run` 收到取消直接返回，最後寫回只由 `FlushPlayerData`／`FinalizePlayerData` 負責（不再於 Run 結束時另做 10 秒的重複寫回）

### Login Failure Ratio

- 規則：`GameLoginFailureRatioHigh`
- 條件：5 分鐘內登入失敗率 > 10%，且登入速率 > 0.05 筆／秒（最低流量門檻）
- 等級：warning
- 用途：第一時間知道登入體驗正在退化

### Recovery Mismatch Detected（GameRecoveryMismatchDetected）

- 條件：`sum by (job, instance) (increase(game_recovery_validation_total{result="recovery_mismatch"}[10m])) > 0`（保留 `instance`：多 World／Gate 時通知看得出是哪一台，也才能被同實例的 page 抑制）
- 等級：warning
- 用途：World 恢復與 Gate session 不一致；World 端也會因 Gate 背景佇列滿（回 `RecoveryMismatch`）而計 `recovery_mismatch`，先看下一條 `GameRecoveryValidationRejected` 的計數是否同時增加，有則是 Gate 過載而不是真的狀態不一致

### Recovery Validation Rejected

- 規則：`GameRecoveryValidationRejected`
- 條件：`sum by (job, instance, reason) (increase(game_recovery_validation_rejected_total[10m])) > 0`
- 等級：warning
- 用途：Gate 的恢復驗證背景佇列已滿而拒絕驗證（`reason="queue_full"`），回給 World 的是 `RecoveryMismatch`；只管這一種，結果日誌略過另有 `GameRecoveryValidationJournalSkipped`；`runbook_url` 指向[狀態對帳流程](./狀態對帳流程.md)

### GameRecoveryValidationJournalSkipped

- 條件：`sum by (job, instance) (increase(game_recovery_validation_journal_skipped_total[10m])) > 0`
- 等級：warning（`resource_class=recovery`）
- 用途：Gate 的恢復驗證已完成並回了真實結果，只是結果日誌因背景佇列已滿沒寫入 Redis，World 重送同一個 `requestID` 時無法回放、會依當時狀態重新判定；回覆沒有被降級，所以與 `GameRecoveryValidationRejected` 分開。處置：先看 Gate 到 Redis 的延遲與 World 重啟後的驗證量；`runbook_url` 指向[狀態對帳流程](./狀態對帳流程.md)

### Reconnect Failures Sustained

- 規則：`TCPReconnectFailuresSustained`
- 條件：依 `job`／`instance`／`service`（對端），5 分鐘內 reconnect fail 次數持續增加且同一組成功為 0
- 等級：warning
- 用途：依賴服務可能斷線或網路異常

### Handler P95 Too High

- 規則：`GameHandlerP95High`
- 條件：任一 handler 的 p95 > 0.2 秒持續 10 分鐘，且該 handler 近 5 分鐘請求速率 > 0.05/s（錄製規則 `game_handler_request_rate_5m`；低頻 handler 的 p95 等於視窗內最慢的一筆，不單筆告警，第十五輪 O-L6）
- 等級：warning
- 用途：找出變慢中的 handler

### Handler P99 Critical

- 規則：`GameHandlerP99Critical`
- 條件：任一 handler 的 p99 > 0.5 秒持續 10 分鐘，且 `game_handler_request_rate_5m` > 0.05/s（最低流量門檻，同上）
- 等級：page（Alertmanager 只把 `severity=page` 當成立即通知，原本的 `critical` 不會被路由）
- 用途：找出明顯影響玩家體驗的延遲

### Replay Cache Failure Hit Surge

- 規則：`GameReplayCacheFailureHitSurge`（持續 2 分鐘）
- 條件：依 `job`／`instance`，5 分鐘內登入加登出 `hit_failure` > 20
- 等級：warning
- 用途：重送風暴、上游 timeout 過短、依賴不穩

### Heartbeat Timeout Surge

- 規則：`GameHeartbeatTimeoutSurge`（持續 2 分鐘）
- 條件：只看玩家心跳（`service="gate_user"`），依 `job`／`instance`，5 分鐘內逾時數 > 50 **且** > 平均在線連線數（`game_connections{service="gate_user"}`）的 5%（第十一輪；原本玩家與 S2S 共用絕對門檻 50，大 Gate 上過敏、對 S2S 又太遲鈍。門檻待壓測校正）
- 等級：warning
- 用途：大量玩家連線心跳超時，可能是網路抖動或 Gate 過載

### S2S Heartbeat Timeout

- 規則：`GameS2SHeartbeatTimeout`（持續 5 分鐘）
- 條件：`sum by (job, instance, service) (increase(game_heartbeat_timeout_total{service!="gate_user"}[5m])) > 0`
- 等級：warning
- 用途：S2S 每次心跳逾時都代表一條服務連線斷掉；5 分鐘內反覆發生先看對端是否過載或網路異常

### World Online Player Imbalance

- 規則：`GameWorldOnlinePlayerImbalance`（持續 15 分鐘，World 數需 > 1）
- 條件：單一 World `game_world_online_players` 超過所有 World 平均值的 1.5 倍，**且**比人數最少的 World 多 100 人以上（舊條件「超過平均 2 倍」在兩台 World 時數學上不可能成立，告警等於失效）
- 等級：info（正式 Alertmanager 把 `severity="info"` 導到 blackhole，不通知值班，只在 UI 查看）
- 用途：提示負載不均，考慮調整 World 指派策略

### GameWorldNearCapacity

- 條件：`game_world_online_players / game_world_max_players > 0.9`，持續 10 分鐘
- 等級：warning
- 用途：容量預警。`game_world_max_players{world_id}` 是 World 啟動時設定的 `max_players`（不熱重載）；滿載後該 World 回 `AuthServerFull`，Central 不會改派其他 World，綁定在該 World 的玩家登入不了。處置：擴容、調高 `max_players` 或調整指派策略

### GameWorldRejectingLogins

- 條件：`sum by (job, instance) (increase(game_login_total{result="server_full"}[5m])) > 0`，持續 5 分鐘
- 等級：warning
- 用途：已經有玩家因 World 滿載被拒。`server_full` 刻意不計入登入可用率與失敗率（不是故障，也不要和伺服器故障混在一起），所以 `GameLoginAvailabilityLow`、`GameLoginFailureRatioHigh` 不會響，由這條補上；用 `game_world_online_players` 對照 `game_world_max_players` 找出是哪個 World

### GameBoardCommandErrorsWithoutSuccess

- 條件：`sum by (job, instance, command) (increase(game_board_command_total{result=~"error|timeout"}[15m])) >= 5`，且同窗口該指令沒有任何 `result="ok"`；持續 5 分鐘
- 等級：warning
- 用途：補 `GameBoardCommandErrorRatioHigh` 的盲區。那條要求每個 World、每種指令每秒至少 0.05 筆，戰鬥結算、開戰、抽獎、商店這類低頻指令就算全部失敗也達不到；這條不看流量，只要 15 分鐘內累計 5 次以上失敗而且一次成功都沒有就響

### GameCombatSettlementIncomplete

- 條件：`sum by (job, instance) (increase(game_board_command_total{result="settlement_incomplete"}[5m])) > 0`，不設 `for`
- 等級：page
- 用途：戰鬥結算金幣已入帳，但標記場次已結算或建立通知失敗（`ErrSettlementIncomplete`），涉及資產，每一筆都要人工對帳。這類錯誤計入獨立的 `settlement_incomplete`，不再混進 `error`；日誌為 Error `board command failed: combat settlement incomplete`（逐筆、不取樣，帶 sessionID 與 settlementID）

### GameCombatTicketConsumeFailed

- 條件：`sum by (job, instance) (increase(game_combat_ticket_consume_failed_total[15m])) > 0`
- 等級：warning
- 用途：開戰 Session 已建立，但消耗戰鬥資格失敗（通常是玩家資料已卸載），資格沒有被扣。Session 照常回給 Client；日誌為 Error `consume combat ticket failed`。用獨立計數器 `game_combat_ticket_consume_failed_total`，而不是 `game_board_command_total` 的 `result`：`start_combat` 本身仍計一個 `result="ok"`，不會重複計兩次

### GameLoginTrafficDrop

- 條件：`sum(rate(game_login_total{job="gate"}[10m])) < 0.2 * sum(rate(game_login_total{job="gate"}[10m] offset 1d))`，且前一天同時段速率 > 0.5 筆/秒；持續 15 分鐘
- 等級：warning
- 用途：黃金訊號中的 Traffic。其他登入／HTTP／盤面比例告警都要求最低流量，流量歸零時全部靜默，`/ready` 也只檢查本機監聽與依賴，所以 Lobby discovery 回空清單、前端 LB 或 DNS 設錯、Redis 公告 key prefix 不一致這類「客戶端連不上」的事故沒有任何訊號；這條與前一天同時段比較補上。離峰與新環境（前一天同時段速率低於門檻）不比較；閾值待壓測與實際流量校正。處置：查 Lobby discovery 回傳的 Gate 清單、前端 LB／DNS 與 Gate 連線入口

## 新增告警規則

以下告警已加入伺服器倉庫的 `monitoring/prometheus/alert-rules.yml`（所有 compose 都從這裡掛載）。告警規則的單元測試在 `monitoring/prometheus/tests/alert-rules.test.yml`，CI 的 `alert-rules` job 每次都會跑 `promtool check rules`、`promtool test rules` 與 `promtool check config --syntax-only`（涵蓋正式、全堆疊、開發與本機四份 Prometheus 設定；與 `compose.prod.yml` 同一個 Prometheus 映像，列入發版前置檢查），本機可用 `monitoring/prometheus/tests/run.sh`（docker 的 `prom/prometheus` 映像，不需安裝 promtool）；改告警條件時一併補測試。

有標籤的計數器要等第一次事件才會出現序列，`increase()` 看不到「第一次（或唯一一次）」事件；告警會看的標籤組合（GM 死信與捨棄類、outbox 死信、persist pool 丟棄、拓撲遷移失敗、恢復不符、變數寫回失敗、帳號鎖錯誤、帳號清除失敗、service hello 不符、設定重載失敗／拒絕）在元件建構時就先建立為 0。panic 的 `msg` 無法全部列舉，`GamePanicRecovered` 另加「新序列」分支（`last_over_time(...[1h] offset 5m)` 在 5 分鐘前往前 1 小時內查不到的序列）。promtool 測試以 `_` 起頭的序列重現正式環境。新增這類告警時要同步預先建立序列：


### GameGCPressureHigh

- 條件：`game_gc_cpu_fraction_5m > 0.25`
- 等級：warning
- 用途：GC 佔用 CPU 超過 25%，記憶體配置率過高

### GameMemoryPressureHigh

- 條件：`go_memstats_heap_inuse_bytes / go_gc_gomemlimit_bytes > 0.85 and go_gc_gomemlimit_bytes < 1e15`（持續 5m）
- 等級：warning
- 用途：以 `GOMEMLIMIT` 軟上限的比例判斷 heap 壓力：各服務上限不同（128～512MB），固定絕對值會讓小上限的服務先被 OOM 也不告警。`go_gc_gomemlimit_bytes` 為 MaxInt64 代表沒設上限，由 `< 1e15` 排除；heap_inuse 與 heap_sys 的比值在 GC 鋸齒下接近 1，無法反映壓力

### GameHighThreadCount

- 條件：`go_threads > 100`，持續 5 分鐘
- 等級：warning
- 用途：OS thread 數量異常，可能發生 thread 洩漏或 cgo 阻塞

### GameAsyncFailureDiscardDetected

- 條件：`game_async_failure_discard_rate_5m > 0`，持續 1 分鐘
- 等級：page
- 用途：非同步任務因佇列滿被丟棄，玩家資料可能遺失

### GamePersistPoolDiscardDetected

- 條件：`game_persist_pool_discard_rate_5m > 0`，持續 1 分鐘
- 等級：page
- 用途：持久化 pool 任務被丟棄，遊戲資料有遺失風險；來源計數為 `game_persist_pool_discard_total{world_id}`（`sum by (world_id) (increase(...[5m]))`）

### GameClockOffsetHigh

- 條件：`abs(game_clock_offset_seconds) > 1`，持續 5 分鐘
- 等級：warning
- 用途：該服務主機時鐘與 Central（遊戲時間來源）相差逾 1 秒；檢查兩台主機的 NTP（`chronyc tracking`），見 [Docker 生產部署](../30-部署與開發/Docker生產部署.md#主機時鐘ntp)

### GameTimeSyncJump

- 條件：`game_time_sync_jumps_5m > 0`（錄製自 `game_time_sync_jumps_total`，偏差達 1 秒直接跳到 Central 的次數，第一次同步不計），持續 1 分鐘
- 等級：warning
- 用途：時間同步大跳；往回跳時遊戲時間停住直到追上，往前跳時遊戲時間一次前進（冷卻、恢復等提早到期）。多為 Central 或該主機 NTP 校正、手動改時間或 VM 暫停所致。舊的 `game_time_sync_adjustments_total` 每次同步都計數，只供觀察方向，不用於告警

### GameGoroutineLeakPossible

- 條件：`delta(game_goroutines_residual[1h]) > 500 and deriv(game_goroutines_residual[30m]) > 0`，持續 30 分鐘（錄製規則 `game_goroutines_residual` 為 `go_goroutines` 扣掉 2 × `tcp_connections_active`，沒有 TCP 的服務直接用 `go_goroutines`；原本的 `game_goroutine_growth_rate` 已移除）
- 等級：warning
- 用途：扣掉連線固定成本後的 goroutine 1 小時淨增 500 以上且仍在成長，疑似逐請求洩漏；登入潮過後回落不會觸發。原本 `deriv > 50`（每秒 50）約要多 3 萬個 goroutine 才響，抓不到逐請求洩漏。門檻待壓測校正。pprof 可用時先抓 `goroutineleak` 與 `goroutine?debug=1`；正式環境 pprof 預設關閉，先 `docker exec <容器> sh -c 'kill -USR1 1'` 取 `debug=2` 傾印（不用重啟、不清現場），之後才考慮開 `debug.pprof_enabled` 重啟，見問題排查筆記〈現場採證〉

### GameProcessRestarted

- 條件：`changes(process_start_time_seconds{job=~"central|gate|world|chat|lobby|record"}[15m]) > 1`，或 `> 0` 且非發版（`unless` 15 分鐘內同一 `job`／`instance` 的 `game_build_info` 出現兩組以上 `release`／`server_commit`）。發版只容許重啟一次（第十二輪 O-L1）：新版一啟動就 crash loop 時舊版序列仍在視窗內，以前整整 15 分鐘都被當成發版，現在第二次重啟起照樣告警
- 等級：warning
- 用途：行程重新啟動。崩潰或 OOM 後 Docker 秒級拉起，`up == 0 for 1m` 的 `GameServiceDown` 不會響；發版重啟已由 `game_build_info{release, server_commit, config_version}`（`startup.InitializeObservability` 以已驗證的 `release.Info` 設為 1，第十一輪）排除，同版本重新部署仍會觸發一次，非發版時先查 `docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}'` 與崩潰堆疊（見[問題排查筆記](問題排查筆記.md)）

### GameRedisCommandErrors

- 條件：`sum by (job, instance, op) (increase(redis_command_errors_total[5m])) > 10`，持續 5 分鐘
- 等級：warning
- 用途：`pkg/redis` 的指令持續失敗（`op` 為指令名，`DoMulti` 為 `pipeline`；不計 Nil 回覆與呼叫端取消）；先看 Redis 連線與延遲

### GameDBPoolWaitHigh

- 條件：`sum by (job, instance, db_name) (rate(go_sql_wait_duration_seconds_total[5m])) > 0.05`，持續 5 分鐘
- 等級：warning，`resource_class: database`
- 用途：MySQL 連線池持續有人在等連線（每秒累積等待超過 0.05 秒），代表池飽和；調大 `mysql.max_open_conns` 或查慢查詢。World 登入批次池看 `db_name` 為 `<db>_batch` 的序列

### GameLoginE2EP99High

- 條件：`game_login_e2e_p99_seconds > 2 and sum by (job) (rate(game_login_e2e_seconds_count[5m])) > 0.05`，持續 5 分鐘（低流量每秒 < 0.05 筆不響，避免單筆慢請求撐過 P99）
- 等級：warning
- 用途：登入端到端 P99 超過 2 秒，玩家體驗受影響

### GameSchedLatencyHigh

- 條件：`game_sched_latency_p99_5m > 0.01`
- 等級：warning
- 用途：goroutine 排程 P99 超過 10ms，可能 CPU/thread/GC 競爭

### GameConnectionLeakPossible

- 條件：`game_connection_leak_diff > 5`，持續 5 分鐘
- 等級：warning
- 用途：TCP 層與應用層連線數不一致，可能 socket 洩漏

### GameChatRoomMessageDropped

- 條件：`increase(game_msg_queue_dropped_total{service="chat_room"}[5m]) > 0`，持續 1 分鐘
- 等級：page

### GameChatRoomQueueBacklog

- 等級：warning
- 用途：Chat 房間佇列持續積壓，通常是 MySQL 變慢或某些房間訊息量異常

### GameChatRoomJobWaitHigh

### GameChatRoomJobSlow

- 等級：warning
- 用途：單一 Chat 工作執行超過 1 秒，檢查 MySQL 延遲與連線池

### GameSendQueueDepthHigh

- 條件：`tcp_send_queue_depth > 3000` 持續 5m
- 等級：warning
- 用途：socket 送出佇列持續積壓，對端消費太慢或廣播量過大；面板「Capacity Budget (Queue Depth)」

### GameEventQueueDepthHigh

- 條件：`game_event_queue_depth > 8000` 持續 5m
- 等級：warning
- 用途：app 事件佇列持續積壓，事件迴圈已追不上；面板「Capacity Budget (Queue Depth)」

### GameQueueOverflow

- 條件：`sum by (job, instance, service, queue) (label_replace(increase(tcp_send_queue_overflow_total[5m]), "queue", "send", "", "") or label_replace(increase(game_event_queue_overflow_total{action="closed"}[5m]), "queue", "event", "", "")) > 0`（事件佇列只看 `action="closed"`，S2S 背壓另由 `GameEventQueueBackpressure`；第十一輪起 `queue` 也帶進 summary。保留 `instance`：Alertmanager 的 page 壓 warning 抑制以 `job`＋`instance` 為 `equal`，缺它會誤壓同 job 其他實例的 warning；summary 也帶 instance。`increase()` 會去掉 `__name__`，兩側標籤組相同時 `or` 只留左側，事件佇列溢位會被吞掉，所以先用 `queue` 標籤區分兩側），持續 1 分鐘
- 等級：page
- 用途：送出或事件佇列已溢位，連線被關閉或訊息被丟棄；面板「Capacity Budget (Overflows)」

### GameEventQueueBackpressure

- 條件：`sum by (job, instance, service) (increase(game_event_queue_overflow_total{action="backpressure"}[5m])) > 0`，持續 5 分鐘
- 等級：warning
- 用途：S2S 連線遇事件佇列滿時阻塞等待，訊息最後仍會執行、連線不斷；持續發生代表事件迴圈處理不及，先看 `GameEventQueueDepthHigh` 與迴圈耗時。第十一輪前背壓也計入 `GameQueueOverflow`，Central、World 開服或大量重連時會誤 page

### GameReadyCheckFailing

- 條件：`max by (job, instance, check) (game_ready_check_failing{check!="startup"}) > 0`，持續 2 分鐘（第十二輪排除啟動閘門：`MarkStarted` 前 `startup` 恆為失敗是預期狀態，World 啟動接近 2 分鐘時每次發版都會誤報）
- 等級：warning
- 指標：`game_ready_check_failing{check}`（`debug.Server` 每輪 readiness 檢查都設定，1＝失敗、0＝通過；`/ready` 與 lobby reporter 公告前的就緒檢查都會更新，第十一輪）
- 用途：compose 不會因 healthcheck unhealthy 重啟容器，行程活著但 `/ready` 失敗時只有這條會響。`check=tcp_listen_*` 代表監聽已關（監聽失敗或 accept 迴圈 panic）、收不到新連線，需重啟該服務；`redis`／`mysql` 等依賴檢查失敗先查依賴本身。`time_sync` 失敗代表尚未收到 Central 的 TimeSync，先查與 Central 的 S2S 連線。Gate、Central、World 的 Lobby 公告會因此撤除（lobbyreporter 改用 `debug.Server.CheckServing`，與 `/ready` 同一組檢查，第十二輪），但服務不會自行恢復。啟動自檢失敗（含監聽失敗）時行程直接退出，不會停在這個狀態

### GameStartupStuck

- 條件：`max by (job, instance) (game_ready_check_failing{check="startup"}) > 0`，持續 5 分鐘（第十二輪）
- 等級：warning
- 用途：啟動閘門 5 分鐘未放行（World 啟動上限約 2 分鐘，留 2.5 倍餘裕）；看服務日誌卡在哪個啟動步驟，以及 MySQL／Redis 是否可用

### GameHTTPErrorRatioHigh

- 條件：`sum by (job, route) (rate(game_http_request_seconds_count{code=~"5.."}[5m])) / sum by (job, route) (rate(game_http_request_seconds_count[5m])) > 0.01`，且該路由請求量 > 0.1 筆／秒，持續 5m（低流量時一筆失敗就 100% 不再誤報）
- 等級：warning
- 用途：Lobby／Record HTTP 端點 5xx 比例超過 1%；面板「HTTP 5xx Ratio (5m)」。Lobby 的 `route` 標籤現在是 ServeMux 的路由樣板（例如 `GET /notices`）；舊版因 `http.TimeoutHandler` 複製 request 使外層讀不到樣板，全部記成 `unmatched`

### GameHTTPLatencyP99High

- 條件：`histogram_quantile(0.99, sum by (job, instance, le) (rate(game_http_request_seconds_bucket[5m]))) > 1` 且該實例近 5 分鐘 HTTP 請求速率 > 0.1/s，持續 5m（依實例分開，通知看得出是哪一台；最低流量門檻避免低頻維運路由一筆慢請求撐住告警，第十五輪 O-L6）
- 等級：warning
- 用途：HTTP 請求 P99 超過 1 秒；面板「HTTP Latency P99 (5m)」

## 落地順序建議

1. 先接 Prometheus `/metrics`
2. 建第一版 dashboard
3. 先開 warning，再逐步開 page 通知
4. 跑一次壓測或本地故障演練，校準門檻
5. 再依實際流量調整 ratio 與觸發時間

### GameCircuitBreakerOpen

- 條件：`min by (job, instance, name) (min_over_time(circuit_breaker_state[2m])) >= 1 and max by (job, instance, name) (max_over_time(circuit_breaker_state[2m])) >= 2`，持續 1 分鐘
- 等級：page
- 用途：某個斷路器（MySQL、Redis 等）持續開啟，下游依賴不可用；`name` label 指出是哪一個。舊條件 `== 2` 加 `for: 2m` 會被 half-open 試探重置計時、持續故障時漏報，現在改取 2 分鐘內的最小值：狀態從未回到 closed 才算。狀態改變的日誌為 Warn `circuit breaker state changed`。gobreaker 的 open→half-open 是惰性轉換，沒有請求經過就不會觸發狀態回呼；`pkg/circuitbreaker` 的 Tracker 由 central、world 的 `main` 以 `circuitbreaker.NewTracker()` 建立並 `MustRegister`（沒有 `init()` 與全域單例），經 `services.Config.Breakers`、`gamedb.StoreDeps.Breakers`、`gamestore.NewCBStores`、`playerstore.New` 注入各 store；`Tracker.New` 一律串接 gauge 更新（`DefaultSettings` 只回純設定），每次 scrape 先輪詢 `State()`，所以離峰無流量時 gauge 也會在 Timeout 後變成 half-open（第十四輪 O-M1，之前會卡在 open 讓這條 page 持續響到下一筆請求）。gobreaker 的 half-open 沒有逾時，依賴恢復後若沒有請求試探會一直停在 1，所以條件另外要求視窗內出現過 open(2)：持續故障時 2 與 1 交替仍會告警，閒置停在 half-open 約 2 分鐘後自動消除；half-open 長時間不變代表沒有流量試探，不代表依賴仍故障，依賴是否可用看 `/ready`

### GameEventLoopStalled

- 條件：`time() - game_event_loop_last_tick_timestamp_seconds > 30`，持續 1 分鐘
- 等級：page，`resource_class: queue`
- 用途：app 事件迴圈超過 30 秒沒有 tick，handler 可能卡死；`game_event_queue_depth` 在迴圈卡住時會凍結，無法偵測。處置見[現場採證](問題排查筆記.md#現場採證服務卡住cpu-高記憶體持續成長)

### GameGrantItemDeadLettered

- 條件：`sum by (job, instance) (increase(game_async_failure_total{queue="grant_item",outcome="dead_lettered"}[5m])) > 0`
- 等級：warning，`resource_class: async`
- 用途：GM 發道具重試耗盡或原文無法解碼而轉入死信，玩家沒拿到道具；用 `/admin/grant-item/dead-letter` 查看並補發。`dead_lettered` 不在 `GameAsyncFailureDiscardDetected` 的捨棄類 outcome 內（那只涵蓋「連死信都寫不進」），所以另立告警

### GameAccountPurgeStalled

- 條件：`time() - max_over_time(game_account_purge_last_run_timestamp_seconds{job="central"}[3d]) > 2 * 86400` 且序列 2 天前就存在（`and on (job, instance) ... offset 2d`），持續 1 小時（這個 gauge 每個服務都會輸出 0，只看 Central；Central 啟動時不再把它設為現在，因為每次重啟都歸零計時，部署頻繁時偵測永遠不會到期；改取 3 天內最大值保留重啟前的最近完成時間，序列存在不滿 2 天的新環境不告警）
- 等級：warning
- 用途：每日帳號清除（保留期合規作業）超過 2 天沒有完整跑完。沒有 World 連線時該輪直接略過、不計失敗，`GameAccountPurgeFailing` 看不到作業其實停擺，所以另立這條

### Watchdog

- 條件：`vector(1)`，恆為 firing
- 等級：info（Alertmanager 路由到 blackhole，平常不通知）
- 用途：告警管線存活訊號。Prometheus 或 Alertmanager 掛掉時這筆會消失；要真正當死人開關，需把它路由到外部心跳服務（接收端 N 分鐘沒收到就通知），目前**沒有接**，MySQL／Redis／RabbitMQ exporter 也尚未部署

### GameRecordMQPublishErrors

- 條件：`sum by (job, instance) (increase(recordmq_publish_error_total[5m])) > 0`，持續 5 分鐘
- 等級：warning
- 用途：Record 事件發布到 RabbitMQ 持續失敗，事件會堆積在 World 的 outbox；`recordmq_reconnect_total` 為重連次數，頻繁增加代表連線不穩

### GameRecordMQDisconnected

- 條件：`job="record"` 的 `min by (job, instance) (recordmq_connection_status) == 0`；或 `job="world"` 的連線狀態為 0 且 `recordmq_enabled == 1`，持續 5 分鐘
- 等級：warning
- 用途：Record 消費端或 World 發布端的 RabbitMQ 連線中斷超過 5 分鐘。Central、Chat 也連進 recordmq 套件但不連線（恆為 0），不納入；World 設定了 RabbitMQ 就把 `recordmq_enabled` 設為 1（與連線成敗無關），所以「啟動後從未連上」也會告警；未設定 RabbitMQ 的 World 為 0，不納入。World 啟動時連不上 RabbitMQ 不拒絕啟動，改在背景以指數退避（1 秒到 30 秒）持續重試（日誌 Error `world record sink unavailable at startup, retrying in background`，之後每次失敗 Warn `world record sink retry failed`，連上 Info `world record sink connected after startup retry`），所以 `recordmq_connection_status=0` 是**暫態**，不再是「重啟前永不恢復」；連上前不發 Record 事件，outbox 事件留在 MySQL，連上後由 relay 照常發送，不必重啟 World。Record 消費端連線成功才設為 1、`Close` 時設為 0。`/ready` 不檢查 RabbitMQ，短於 5 分鐘的中斷不會觸發

### GameRecordQueueBacklog

- 條件：`max by (job, instance) (recordmq_queue_messages{job="record"}) > 10000`，持續 5 分鐘
- 等級：warning，`resource_class: async`
- 用途：Record 佇列持續積壓，代表消費長期跟不上發布。指標由 Record 消費端每 15 秒以被動宣告取樣 `record.events` 的待消費訊息數（重試退避期間也照常取樣，不會停在舊值）。門檻依實測訂定：2.8 萬筆／秒的突發發布會暫時積壓約 5 萬筆並在十幾秒內排空，不會誤報；先看 Record 的 MySQL 慢查詢與消費端是否停擺

### GameRecordConsumerRetrying

- 條件：`sum by (job, instance) (increase(recordmq_consume_total{result="retry"}[5m])) > 0` 且同窗口沒有任何 `result="ok"` 的成功寫入（`unless on (job, instance)`），持續 5 分鐘
- 等級：warning，`resource_class: persistence`
- 用途：Record 寫入持續失敗但 MySQL ping 正常（例如當日分表沒建、MySQL 唯讀或鎖等待）時，事件只會被放回佇列重試，`/ready` 不會變紅，要等逐筆輪流達 20 次上限才進死信（單一事件約 9 分鐘，一批多筆輪流重試要數倍到數十倍時間）；本告警讓維運在進死信前就發現。先看 Record Warn `recordmq: handler failed`（分表是否建立、MySQL 狀態）

### GameRecordConsumerDeadLetter

- 條件：`sum by (job, instance) (increase(recordmq_consume_total{result="dead_letter"}[5m])) > 0`
- 等級：page，`resource_class: persistence`
- 用途：Record 消費端把事件轉入 `<queue>.dead`（內容無法解析、缺 `OccurredAt`、寫入違反約束、handler panic 或連續失敗達 20 次），這些事件不會再寫進資料庫。`recordmq_consume_total{result}` 另有 `ok`、`retry`，序列事先建立（值 0），`increase()` 看得到第一次死信。先看 Record Warn 的原因：`recordmq: handler failed`（處理失敗），或 `recordmq: invalid event payload`（內容無法解析，帶 `messageID`、`bodySHA`、`bodyLen`，不放內容），修好後確認 `.dead` 內容再重送（見[問題排查筆記](./問題排查筆記.md)的「死信再處理」）。World 端非同步發布階段的丟棄看 `recordmq_async_dropped_total{reason}`（`queue_full`、`not_ready`、`stopped`），對應告警見下一節 `GameRecordEventsDropped`

### GameRecordEventsDropped

- 條件：`sum by (job, instance, reason) (increase(recordmq_async_dropped_total{reason=~"queue_full|not_ready"}[5m])) > 0`（無 `for`，立即觸發）
- 等級：warning，`resource_class: persistence`
- 用途：World 的一般 Record 事件在發布端被丟棄，這類事件不會重送，稽核紀錄會缺。`queue_full` 是 RabbitMQ 斷線太久、發布佇列滿；`not_ready` 是已設定 RabbitMQ 但發布器尚未建立（啟動背景重試期間）就收到事件。`stopped`（關機後的丟棄）不告警。三個 reason 的序列在元件建構時事先建立為 0，`increase()` 看得到第一次丟棄。與 `GameRecordMQDisconnected` 搭配看：先修連線，再評估缺少的稽核紀錄範圍

### GameLogAsyncDropped

- 條件：`sum by (job, instance) (increase(logger_async_dropped_total[5m])) > 0`
- 等級：warning
- 用途：非同步日誌緩衝（`LOG_ASYNC_BUFFER`）滿了而丟棄最舊日誌。預設緩衝為 0＝關閉，沒開時計數器恆為 0，不會觸發；觸發時調大 `LOG_ASYNC_BUFFER`，或查 stderr 消費端（容器日誌驅動）是否被壓住

### GameStateAuditMismatch

- 條件：`sum by (job, instance, service, result) (increase(game_state_audit_total{result=~"mismatch|error"}[15m])) > 0`，持續 30 分鐘
- 等級：warning
- 用途：Gate／World／Central 之間的狀態稽核持續 `mismatch` 或 `error`，狀態可能漂移。單次差異可由修復流程自癒，因此要求 15 分鐘窗口內持續有事件且延續 30 分鐘。`audit.PrimeMetrics` 在 Gate／World／Central 建構時事先建立 `mismatch`、`error` 為 0 的序列，`increase()` 才算得到第一次事件。處理流程見[狀態對帳流程](./狀態對帳流程.md)

### GameLoginCentralBusy

- 條件：`sum by (job) (increase(game_login_total{job="central", result="busy"}[5m])) > 10`，持續 2 分鐘
- 等級：warning，`resource_class: login`
- 用途：Central 同時處理登入達上限（`maxConcurrentLogins = 64`）時立刻回「服務忙碌」（code 9，客戶端會重試）；持續出現表示登入併發飽和，先看開服或大批重連尖峰與 bcrypt 併發。瓶頸位置尚未驗證，處理方案草稿見[Central 登入忙碌處理方案](../90-參考附件/方案草稿/Central登入忙碌處理方案-2026-10-28.md)。它 firing 時 Alertmanager **不**抑制 `GameLoginAvailabilityLow` 與 `GameLoginFailureRatioHigh`（第十五輪 O-L8 移除：Gate 把 busy 拒絕計成 `service_unavailable`，開服尖峰會多收到這兩封，但同時發生的真故障不會被壓掉）。容量背景見[容量與壓測基準](容量與壓測基準.md)

### GameLoginGateUnavailable

### GameBoardCommandErrorRatioHigh

- 條件：依 `job`／`instance`／`command`，`game_board_command_total{result=~"error|timeout"}` 佔全部的比例 > 1%，且該指令請求量 > 0.05 筆／秒，持續 5 分鐘（避免一筆失敗就 100%）
- 等級：warning
- 用途：某種盤面指令持續失敗或逾時；`decode`（Client payload 解不開）不計。商店、道具、升級、擲骰遇到資料庫／Redis 錯誤、逾時或斷路器開啟時，回應仍是 Rejected，但內部失敗（`board.ErrResolutionFailed`）現在也計為 `error`／`timeout`，不再記成 `ok`。第十輪起 `start_combat`、`submit_combat_result`、`activate_mission`、`claim_mission_reward` 同樣如此：這四個指令的內部失敗（儲存層、配對、快照同步、結算失敗）以前把錯誤吞進回應、計量記成 `ok`，告警看不到；現在計為 `result="error"`、span 標錯、取樣 Error 日誌 `board command failed`，Client 回覆不變（仍是 Rejected）。玩家操作造成的拒絕（無對手、已在戰鬥中、不在戰鬥格、場次不屬於玩家或已逾時、傷害無效、任務條件不符等）與 `resolve_shop` 的 `InteractionID <= 0`（歸為 `InvalidInteraction`）不算內部失敗。指令別延遲看 `game_handler_duration_seconds{handler="board_<指令名>"}`，排隊等待看 `handler="board_queue_wait"`

- 等級：page
- 用途：服務間發版身分不同而拒絕連線，代表混版本部署。撥號成功時已計 `tcp_reconnect_total{result="success"}`，之後才因 hello 不符關閉，重連類告警不會觸發

### GameConnectionsAtCapacity

- 條件：`increase(tcp_rejected_connections_total{reason="at_capacity"}[5m]) > 0`
- 等級：warning
- 用途：連線數已滿，新玩家連不上（容量飽和）。`tcp_rejected_connections_total` 的 `reason` 另有 `rate_limited`（來源 IP 超速）、`handshake_timeout`（Gate 連上後沒在期限內登入，Debug 日誌、不寫 Warn）與 `unauth_evicted`（Gate 未登入連線超過上限時淘汰最舊者）；本告警只篩 `at_capacity`，不受其他原因影響

### GameMessagesDropped

- 條件：`sum by (job, instance, reason) (increase(tcp_dropped_messages_total{reason!="board_decode"}[5m])) > 10`，持續 5 分鐘
- 等級：warning
- 用途：持續丟棄訊息；Gate 的 `no_world`／`world_unavailable` 代表盤面指令找不到 World 連線（Client 只會等逾時），World 的 `board_queue_full`／`change_notify_queue_full`（資源變更通知排不進玩家分片：佇列滿或已停止，日誌每 10 秒取樣一行）／`unknown_player`／`board_decode`（Client 送壞 payload 解碼失敗，只記取樣 Warn，不算進上面的丟棄告警）、S2S 的 `unpack`／`handler_panic` 見指標註解（`unpack` 只計 S2S 連線，玩家連線的壞封包會關閉連線、記每 10 秒取樣一行的 Warn，不計入此指標）；`loop_closed` 是事件迴圈已停止後才收到的 S2S 訊息（例如 World 關機 PostDrain 之後 Gate 仍轉送的指令），關機期間少量出現屬正常

### GameAccountPurgeFailing

- 等級：warning
- 用途：每日帳號清除（保留期合規作業，見[帳號保留政策](../帳號保留政策.md)）近一天有失敗，合規作業可能沒有完成。World 回報處理失敗與 Central 自己的錯誤計入 `failed`；World 無回應（逾時、取消、斷線）不計入、該 World 被移出本輪，作業停擺改由 `GameAccountPurgeStalled` 發現。`game_account_purge_total{result}` 的 `result` 為 `purged`（清除成功一個帳號）或 `failed`（掃描或清除步驟失敗）；World 暫時不可用不計失敗，下輪會自行重試。看 Central 日誌與 World 連線

### 告警管線自身（PrometheusRuleEvaluationFailing、PrometheusNotificationsDropped、AlertmanagerNotificationsFailed）

正式 Prometheus（`docker/monitoring/prometheus.prod.yml`）多抓 `prometheus`（`localhost:9090`）、`alertmanager`（`alertmanager:9093`）兩個 job，三條告警都是 warning、持續 5 分鐘，runbook 為[問題排查筆記](./問題排查筆記.md)：

- `PrometheusRuleEvaluationFailing`：`sum by (job, instance) (increase(prometheus_rule_evaluation_failures_total[5m])) > 0`。規則評估失敗，部分告警可能不會觸發；看 Prometheus 日誌
- `PrometheusNotificationsDropped`：`sum by (job, instance) (increase(prometheus_notifications_dropped_total[5m])) > 0`。送往 Alertmanager 的通知被丟棄，檢查 Alertmanager 是否可連線
- `AlertmanagerNotificationsFailed`：`sum by (job, instance, integration) (increase(alertmanager_notifications_failed_total[5m])) > 0`。Alertmanager 對接收端（webhook）送出失敗，值班可能收不到告警；檢查 `webhook_url` 與接收端

限制：webhook 本身壞掉時這三條也送不出去，只能在 Alertmanager 介面與 Grafana 看到；徹底解法仍是把 `Watchdog` 路由到外部心跳服務（目前沒有接）。本機開發的 Prometheus 設定沒有這兩個 job，這三條在本機不會有資料。

## 寬限期與佇列飽和指標

- `game_service_grace_total{service, outcome}`：對端服務斷線寬限 `entered`／`reconnected`／`expired` 次數；`game_service_grace_pending{service}` 為目前仍在寬限中的對端數。
- `game_resource_recycle_total{service, resource}`：寬限到期（Central `gate_disconnected`、World `gate_unavailable`、Gate `world_unavailable`）與 Central 對帳移除（`gate_sync_stale`）計的是實際清掉的玩家數，對端已重連或沒有玩家時不計。
- `game_shard_queue_depth_max{queue}`：World 分片佇列（`board`、`persist`、`write_back`）最深分片的長度，scrape 時取樣，丟棄前就看得到熱分片積壓。
- `game_http_request_seconds{route, method, code}`：Lobby、Record HTTP 端點的請求耗時直方圖。`route` 取 `ServeMux` 路由樣板，未匹配記為 `unmatched`（路徑參數不會讓基數失控）；`method` 只保留 `GET`／`POST`／`PUT`／`DELETE`／`HEAD`／`OPTIONS`，其餘一律記 `other`（method 由用戶端任意指定）；用戶端取消且處理器沒寫回應的請求記 `code="499"`（非標準狀態碼），不算 5xx，`GameHTTPErrorRatioHigh` 不計入。
- `game_http_request_seconds` 在有取樣 span 時附 `trace_id` exemplar；`/metrics` 支援 OpenMetrics，Prometheus 以 `--enable-feature=exemplar-storage` 啟動才會保存。

- `go_sync_mutex_wait_total_seconds_total`：goroutine 等待鎖的累計秒數（`runtime/metrics` 的 `/sync/mutex/wait/total:seconds`）。`rate()` 持續偏高代表鎖爭用，不必先開 `PPROF_MUTEX_FRACTION`；目前沒有對應告警規則。
- `logger_async_dropped_total`：非同步日誌緩衝（環境變數 `LOG_ASYNC_BUFFER`，預設 0＝關閉）滿了而被丟棄的最舊日誌筆數，丟棄時另寫一行 Warn `async log buffer overflow, entries dropped`；對應告警 `GameLogAsyncDropped`。
- `game_event_loop_last_tick_timestamp_seconds{service}`、`game_account_purge_last_run_timestamp_seconds`：分別供 `GameEventLoopStalled`、`GameAccountPurgeStalled` 使用的時間戳。

## 連線池與延遲桶

- MySQL 連線池統計由 `pkg/mysql` 在 `Connect`（`Open` 也經由它）建立連線後註冊（`go_sql_*`：`max_open_connections`、`open_connections`、`in_use_connections`、`idle_connections`、`wait_count_total`、`wait_duration_seconds_total`），`db_name` label 為資料庫名稱。World 玩家載入走的多語句池（`OpenBatchReader`，16 條連線）另以 `<db>_batch` 為 `db_name` 註冊同一組統計，登入熱路徑的池耗盡看這組；該路徑同時有 `mysql.player_snapshot.batch_load` span。`wait_count_total` 持續增加代表連線池飽和，需調大 `mysql.max_open_conns` 或查慢查詢。Redis 用戶端（rueidis）沒有提供連線池統計。
- `game_account_lock_wait_seconds`、`game_audit_record_lookup_seconds` 改用共用的 `latencyBuckets`（1ms 到 5s），原本用 `DefBuckets`（最低 5ms）；改桶那一刻分位數會有一次斷層。
- `game_handler_duration_seconds` 使用自訂桶（0.5ms 到 10s），遊戲 handler 多半在數毫秒內完成，P50／P95 才不會擠在同一個桶。桶邊界變動不影響既有 PromQL 與 recording rule 名稱。
- 告警門檻必須落在桶界上（第十二輪 O-L2）：`latencyBuckets` 補 2 秒（`GameLoginE2EP99High`）、handler 桶補 0.2 秒（`GameHandlerP95High`）。`histogram_quantile` 在桶內線性內插，門檻落在桶中間時實際延遲遠低於門檻也會被估成超過（例如 handler 全部 110ms 被估成 P95 0.2425）；每個 label 組合多一個 `le` 序列，既有查詢不受影響。
