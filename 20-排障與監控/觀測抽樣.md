# 觀測抽樣

這份文檔說明長跑環境下，log / trace / metric 要怎麼降噪。

## 目標

- 避免觀測本身把系統吵爆
- 讓長跑壓測時還能看清趨勢
- 保留足夠訊號，不要一刀切到完全沒資料

## Log

Debug log 可以抽樣：

- `LOG_SAMPLE_RATE=0.1` 代表保留 10% debug log
- `LOG_SAMPLE_RATE=25` 也可，視為 25%
- `Info / Warn / Error` 不抽樣

用途：

- 長跑時降低 debug noise
- 只在需要時把抽樣率拉高

## Trace

Trace 可以抽樣：

- `TRACE_SAMPLE_RATE=0.1`
- `TRACE_SAMPLE_RATE=25`

現在 `pkg/bootstrap.InitRuntime` 會讀這個值並注入到 `pkg/tracing`，`pkg/tracing` 再依它決定是否建立 span。
`pkg/logger` 與 `pkg/tracing` 本身不再靠 package init 偷塞預設值；只有啟動流程明確注入時才會啟用對應抽樣率。
`pkg/logger/sampling.go`（原 `pkg/sampling`）保留共用的數值抽樣函式；debug log 的字串 hash 抽樣由 `pkg/logger` 自己處理。

用途：

- 長跑時不需要每條 trace 都進 Jaeger / Tempo
- 只保留一部分代表性鏈路

## Metric

Metric 不建議在 counter / histogram 這種核心 SLO 指標上做事件級抽樣。

實務上用這幾種方式降噪：

1. 提高 scrape interval
2. 降低 dashboard refresh rate
3. 調整 recording rule 週期
4. 對 snapshot / diagnostic tool 做可調抽樣

### 原則

- SLO 指標盡量保留完整
- 只有 debug / snapshot 類指標才考慮抽樣
- 不要把高基數資料直接當 metric label
