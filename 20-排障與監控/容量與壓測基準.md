# 容量與壓測基準

本文件整理 2026-10-15～16 在本機做的壓測結論，供調整限流、告警門檻與評估容量時查閱。逐步的測試過程與原始數字在[壓測紀錄](../90-參考附件/歷史/壓測紀錄-2026-10-15.md)，怎麼重跑見[壓測手冊](../30-部署與開發/壓測手冊.md)。

## 適用範圍與限制

- 全部是**單機 loopback**（Windows 11、12 核、Docker Desktop 跑 MySQL／Redis／RabbitMQ，服務為本機程序），沒有網路延遲。數字當作下界與相對比較，不能直接當正式容量。
- dev MySQL 的 `innodb_buffer_pool_size` 只有 128MB，資料庫約 600MB 並未全放進記憶體，但壓測的熱資料多在快取內。聊天表放大到約 1280 萬列的冷讀與清理成本見下方「第四輪補充驗證結論」。
- 未涵蓋：真實多機與網路、戰鬥配對與結算（Gate 尚未轉送）、多 Gate × 多 World 全網狀（World 數增加）的 S2S 握手總量、Gate 到 Chat 的多 Gate 握手與 CA 輪替。

## 容量邊界

| 邊界 | 值 | 來源 | 超過時的行為 |
|---|---|---|---|
| Gate 總連線數 | 根層 `max_connections`（dev 4096，預設 1024；`tcp.max_connections` 是已棄用別名，只在根層鍵未設定時沿用並記 Warn `tcp.max_connections is deprecated`） | `config/dev/gate.yaml` | 直接關閉新連線；Debug 日誌 `rejecting connection: at capacity`（欄位 `owner`、`ip`、`max`），量看 `tcp_rejected_connections_total{reason="at_capacity"}` |
| 單一來源 IP 連線數 | 預設 100，Gate 選填 `session.max_connections_per_ip` 可調（CGNAT 下多位玩家共用 IP，調低前先評估） | `cmd/gate/services_config.go` | 拒絕新連線；Debug 日誌 `per-IP connection limit exceeded, closing` |
| 未登入連線總數 | `max_connections` 的 1/4（未設定時 256；預設 1024 的 Gate 即 256，dev 4096 即 1024） | `cmd/gate/internal/services`（`maxUnauthenticated`）、`defaultMaxUnauthenticated`（`cmd/gate/internal/handler/user/connect.go`） | **關閉最舊的未登入連線**讓新連線進來（超過上限時一次多淘汰 `上限/16` 條，並行的 Connect 只有一個執行掃描）；計入 `tcp_rejected_connections_total{service="user",reason="unauth_evicted"}`，不另寫日誌 |
| 單一來源 IP 接入速率 | 10／秒，burst 20；限流表最多追蹤 100,000 個來源（填滿時記憶體約 23 MB，實測每筆約 227 B，不含 key 字串；Lobby 對外 HTTP 用同一個 `IPLimiter`，在 `mem_limit: 160m` 下要把這份算進去），**滿載時淘汰最久未見的來源**（O(1)）而非拒絕新來源，被淘汰的來源最多重新取得一次突發額度 | `tcp.rate_limit_*`、`pkg/ratelimit`（`IPLimiter`，套用於 Gate、Central、World、Lobby） | 直接關閉新連線；Debug 日誌 `rejecting connection`（`reason=rate limited`、`owner`、`ip`），量看 `tcp_rejected_connections_total{reason="rate_limited"}` |
| 單連線盤面指令速率 | 10／秒，burst 20（`defaultBoardCommandPerSecond`、`defaultBoardCommandBurst`；Gate 選填 `session.board_command_rate`／`session.board_command_burst` 可調，嚴格解析，寫錯拒絕啟動） | `cmd/gate/internal/handler/user/connect.go` | 超額指令**靜默丟棄**（不回覆、不排隊、不斷線），計入 `game_chat_rate_limited_total{kind="board"}`；Client 只會等到逾時 |
| 單一來源 IP 登入嘗試 | 10 秒窗口內 30 次（`maxLoginAttemptsPerIP`）；單帳號 5 次。三個限流器（登入（帳號, IP）、登入（來源 IP）、登出（玩家））各自最多追蹤 100,000 個 key，滿載時由 LRU **淘汰最久沒碰的 key**，不拒絕新 key（第十輪起；原為 fail-closed：攻擊者以大量來源位址灌滿表就擋掉所有新上線玩家，而 key 含 IP，換 IP 本來就繞得過單一 key 的鎖定，拒絕新 key 換不到安全性）。被淘汰的 key 鎖定狀態消失、重新計數；每個限流器填滿約 18 MB（實測每筆約 179 B，不含 key 字串），閒置條目另由每分鐘稽核從 LRU 最舊端回收（窗口與鎖定都已結束才刪，遇到第一筆仍有效就停；不配置、持鎖時間只和可回收筆數成正比），不在請求路徑上 | `cmd/gate/internal/app` | 回 `RateLimited`（code 8） |
| 單連線訊息速率 | 50／秒，burst 100 | `gateUserRatePerSec`、`gateUserRateBurst` | `rate limit exceeded, closing connection`，**斷線** |
| Chat 房間成員 | 每房間 `room_max_members`（預設 500，第十一輪）；每位玩家最多 16 個房間（`chat.MaxRoomsPerPlayer`）；同一來源 IP 在同一房間經同一 Gate 最多 `session.chat_room_members_per_ip`（預設 50，第十二輪） | `config/*/chat.yaml`、`cmd/chat/internal/app`、Gate `session.*` | 房間已滿時新成員的 `ChatJoin` 靜默被拒，之後在該房間送訊因非成員被拒；同來源配額滿時 Gate 不轉送加入並計 `game_chat_rate_limited_total{kind="join"}`；扇出隨成員數平方成長，上限擋單一房間壓垮 Gate |
| Central 同時處理登入 | 64 | `maxConcurrentLogins` | 立刻回 code 9（`AuthServiceUnavailable`，可重試），計入 `game_login_total{result="busy"}` |
| Central bcrypt 併發 | `max(2, NumCPU/2)`（12 核為 6） | `bcryptSlots` | 暫時失敗，重送重試 |
| 玩家登入逾時 | 約 31～35 秒（絕對期限，慢送資料不延長） | Gate | 關閉連線 |
| World 玩家上限 | `max_players: 5000` | `config/dev/world.yaml` | 見 `ServerFull`（code 7） |
| World MySQL 連線池 | `max_open_conns: 40`、`max_idle_conns: 40`（寫回同時 16 位；Central 等其他服務預設 25／25），另有載入用多語句池 16 條，每個 World 合計最多 56 條；MySQL `--max-connections` 為 300，扣掉 Central／Chat／Record 的 75 與保留 10 後最多 3 個 World（`world-autoscale.ps1` 擴容前檢查） | `config/dev/world.yaml`、`docker/compose/compose.full.yml`、`compose.prod.yml` | 排隊，登入與寫回變慢；超過連線預算時補建連線撞 MySQL Error 1040 |
| Lobby admin API | 全域約 10 rps；錯誤 token 連續 5 次鎖定來源 IP（IPv6 以 /64 計） | `cmd/lobby/internal/handler/admin` | 429 |
| Lobby HTTP 逾時 | 讀標頭 2 秒、讀／寫 5 秒、閒置 30 秒 | `pkg/httpx/serve.go` | 關閉連線 |
| S2S 重連退避 | 1 秒起、倍率 2、上限 30 秒、jitter 0.3 | `pkg/tcpclient` | — |
| World 斷線寬限（Gate／World 互相） | 30 秒 | `ServiceDisconnectGracePeriod` | 超過才清掉玩家 |
| World 重連冷卻（Central） | 30 秒 | `worldRouteCooldown` | 冷卻期不指派新玩家給它 |
| 優雅關機 drain | Gate 30 秒、其他 5 秒；有連線殘留就以 `drain timeout` 結束並 exit 1 | `DefaultDrainTimeout`、`DefaultShutdownTimeout` | 強制收尾 |

## 每連線的資源成本

| 指標 | 數值 | 條件 |
|---|---|---|
| Gate goroutine | 約 3／連線（舊量測；`d2bb0a73a` 接收迴圈併入 ServeConn 後約 2／連線） | 1500 連線 4550、3800 連線 11450 |
| Gate heap_inuse | 約 70～100KB／連線 | 3800 連線峰值約 300MB（GC 鋸齒），2.5 小時 1000 連線為 55～150MB |
| Gate RSS | 約 290MB（1500 連線）、540MB（3800 連線） | 初期成長後持平 |
| World goroutine | 378～416，**不隨玩家數成長** | 1500～3800 人 |
| World RSS | 約 115～140MB | 1500 人 60 分鐘、1000 人 2.5 小時持平 |
| 閒置（只連線不登入）連線 | 約 3 個 goroutine（舊量測，現約 2 個）＋40KB，持續 31～35 秒 | 2000 條 |

結論：記憶體隨連線數線性成長、沒有慢性洩漏（1500 人 60 分鐘、1000 人 2.5 小時，goroutine、RSS、Redis 全部持平）。

## 對外部條件的敏感度

| 條件 | 結果 |
|---|---|
| World 到 MySQL 的 RTT 100ms | 登入約 7 次連續往返（平均 693ms），擲骰 p50 由 1.6ms 拉長到 10ms |
| World 到 MySQL 的 RTT 400ms | 登入近乎崩潰（400 人 3.5 分鐘只上線約 22 人）；沒有 crash 或死結，恢復後正常 |
| Gate 到 World 的 RTT | **線性**：每個需要 World 的指令多一個 RTT（p50 ≈ RTT、p99 ≈ 2 RTT），無放大效應 |
| 玩家到 Gate 的 RTT | 登入延遲約等於 RTT，高延遲（600ms）也沒有逾時失敗 |
| 備份（`mysqldump --single-transaction`）、全表分析查詢、Redis 匯出 | 對擲骰 p99 幾乎沒有影響（max 偶爾跳到 19～55ms） |
| Redis 每 100ms 停 50ms（約 33% 時間被擋） | 擲骰 p50 由 1.6ms 到約 15ms；無失敗、無斷線，擾動結束立即恢復 |
| Redis 每 250ms 停 200ms（約 80% 時間被擋） | 擲骰 p50 約 100ms；同上。**Redis 是玩家路徑最敏感的依賴** |
| Redis 被擋約 33%／80% 時的登入 | 登入平均 58ms → 310ms／13 秒；80% 時 100 人中 67 人登入失敗（重試用完）。**登入是對 Redis 變慢最敏感的路徑**；已在線玩家不被踢（只讀指令幾乎不變，寫狀態指令 p50 受影響） |
| Redis 停機 20 秒（500 人常駐） | **連線全部保留**，Central／Gate／World／Lobby 的 `/ready` 為 503，Chat 仍 200；擲骰立即失敗；Redis 回來後約 10 秒內恢復，無需重連 |
| Central 到 MySQL 的 RTT 50～200ms | 既有帳號登入與常駐玩家幾乎無影響（走 Central 記憶體快取）；只有新帳號建立與路由寫入經過 MySQL |
| RabbitMQ 暫停 30 秒 | 玩家路徑無影響（事件走 World outbox 非同步送出）；短於 `GameRecordMQDisconnected` 的 5 分鐘不響 |

World 與 MySQL 必須在同一個機房（同區 RTT 約 1～2ms 不會觸發上述現象）。

## 第四輪補充驗證結論

逐步數字見[壓測紀錄 2026-10-16 第四輪](../90-參考附件/歷史/壓測紀錄-2026-10-16-第四輪.md)。

| 項目 | 結論 |
|---|---|
| 多 Gate × 多 World（2×3 全網狀） | 任一 Gate 可服務任一 World；Gate 或 World 重啟不需重啟另一端。新帳號依最少負載分散到各 World |
| 跨 Gate 重複登入 | 舊 Gate 收到 `AuthReLogin`、清 session 並通知玩家，**不關舊 TCP**；同 Gate 重複登入則直接關舊 socket。新連線都存活 |
| World 排空 | 新帳號完全不分到被排空的 World，既有帳號不受影響；三個 World 全排空時新帳號回 `AuthServiceUnavailable`、帳號不建立。運維避免全部排空 |
| canary 流量切片 | 命中 `fnv32a(帳號) % 100 < 百分比` 的新帳號確定性導向指定 World；`traffic_slice_*` 可熱重載，不必重啟 Central |
| 玩家端訊息解碼（fuzz） | 畸形輸入不 panic、不被宣稱長度騙去配置記憶體，畸形 payload 出現連線即被關閉 |
| S2S 認證（TLS 1.3＋節點 token） | 效能成本可忽略：穩態擲骰幾乎相同，登入平均多約 6ms，World 重啟後重連多約 2 秒。不在授權清單的 Gate 與明文客戶端都被拒絕 |
| 聊天落庫 | 被房間接受並廣播的訊息必定寫入 `chat_message`（約 1100 列／秒）。Gate 每連線 2 則／秒限流是主要節流；1000 人同房且持續發言時單房佇列（256）滿載，丟棄約 13%、p99 約 0.86 秒，`GameChatRoomMessageDropped` 正確 firing，Chat 不崩潰 |
| 長時間 soak（約 2 小時、33 萬次登入登出） | goroutine、RSS、fd、Redis key 全部持平，無慢性洩漏；資料一致性驗證 `bad=0` |
| 資料量放大（`chat_message` 約 1280 萬列、2.8GB，遠大於 128MB buffer pool） | 歷史查詢冷讀 p50 14ms（小表 1ms），仍走索引；追加寫入不受影響（約 1700 批／秒）。**保留期清理一批 1000 列約 0.65 秒（最慢 1.8 秒）**，清完 677 萬列約 1.2 小時，期間同表讀寫 p99 升到約 100～215ms；持續寫入超過約 1500 列／秒清理會追不上 |
| S2S 維運動作（撤銷、輪替、憑證換發） | 輪替 Gate token：約 1～2 秒瞬斷後重連，Central 對 Gate 斷線有 30 秒寬限期，**300 位玩家全部保留**（第 42 步；修正前會全部掉線）；剛好送出的請求遺失，客戶端需重試。撤銷：重連被拒，寬限期後清掉其玩家；撤銷後 `Rotate` 不會重新開通，須 `Add`。憑證換發：既有連線與玩家零影響 |
| 設定熱重載（400 人在線） | 有效新 release 重載 7.3ms 無影響；繞過發布端的損毀 release 被 World 以檔案雜湊拒絕、保留舊設定；發布端先擋損毀資料與同版本不同內容 |
| 無 swap 的 OOM kill（Docker，Gate 1500 連線） | `--memory 160m --memory-swap 160m` 在連線穩定後 80～100 秒被 OOM kill（137），全部玩家斷線且不自動重啟；同樣 160MB 允許 swap 時則撐住。1500 連線約 185MiB、3800 連線約 600MB，容器上限須高於此並設重啟策略 |
| 多 Gate 的 S2S 握手（5 個 Gate 同時啟動） | 到 Central 與 World 的 10 條 TLS 連線約 1 秒內全部完成，Central 約 0.42 CPU 秒，各 Gate 登入 20／20 成功；Chat 端因測試環境複本過時沒有驗證 |
| 5000 人（本機 Docker 模擬 GCP 機型，每 3 秒擲骰） | 伺服端 4 核可撐住：CPU 合計約 2.7 核（約 68%）、記憶體約 2.6GiB，穩態擲骰 p99 8～10ms；8 核餘裕大（約 35%），p99 < 5ms；5000 個新帳號進場約 14 分鐘（bcrypt 與登入間隔限制）。本機（Ryzen 5 9600X）單執行緒估計比 GCE E2 快約 2～3 倍，上雲要乘上換算係數並先用 `calibrate` 校準；4 核在 E2 上可能不夠 |
| 玩家大表放大（`player_lottery_draw` 582 萬列、`player_mission_event` 1513 萬列，遠大於 128MB buffer pool） | 登入、LoadPlayer、盤面指令延遲與放大前相同（`player_lottery_draw` 的索引以 `player_id` 開頭，熱路徑只碰少量列；`player_mission_event` 主鍵是 `(event_id, mission_id)`，熱路徑以主鍵點查；這次壓測時它**沒有** `player_id` 索引，帳號清除的 `DELETE ... WHERE player_id = ?` 對它是全表掃描。第十輪已在 `PlayerMissionEvent.PlayerID` 補 `idx_player_mission_event_player`（`type=ALL` 預估 219,139 列 → `type=range` 預估 200 列，MySQL 8.0 拋棄式容器、20 萬列實測）；既有大庫（例如本壓測庫 1513 萬列）須先手動建索引，見[第十輪審查紀錄](../90-參考附件/歷史/Go技能審查紀錄-2026-10-20-第十輪.md)與[資料一致性](../10-核心流程/資料一致性.md)）；1500 人登入洪水全部成功 |
| 3800 連線 4 小時 soak | 1239 萬次擲骰遺失 0，p50 0.52ms、p99 約 1.1～1.6ms；goroutine、heap、RSS、Redis、MySQL 連線持平或下降，無洩漏跡象（Gate fd 一次 +64 階梯後持平） |
| Gate 與 World 瞬斷（每 25～35 秒） | 每次切斷遺失約 0.7 秒的請求（3.55%），玩家全部保留；遺失的請求沒有回應，客戶端需自行重送且要冪等 |
| 資源上限（執行期旋鈕模擬） | CPU：`GOMAXPROCS` 4／2 仍可承受，1 時擲骰 p99 約 42ms（無失敗）。**記憶體：`go.memory_limit_mb` 低於服務總記憶體（1500 連線 Gate 約 140MB）會造成 GC 死亡螺旋**——GC 每分鐘上萬次、吃約 1/3 CPU、Gate 從 0.1 核到 4.3 核、p99 約 15ms。不是 cgroup，沒有 OOM kill |
| 容器 cgroup 限制（Docker，Gate） | CPU：吞吐與配額成正比，延遲線性惡化，無失敗無斷線（`--cpus 1` 時 1.5 萬次／秒負載 p50 約 180ms，0.25 核登入明顯變慢）。記憶體：1500 人約 185MiB，256MB 以上無影響；128MB 以下 p99 到數百 ms，Docker Desktop VM 內沒有 OOM kill。建議 `go.memory_limit_mb` 低於容器上限 10～20% |

## 故障與恢復

| 事件 | 影響 | 恢復 |
|---|---|---|
| 殺 World（單 World） | Gate 立即踢掉全部玩家；`GameServiceDown` 1 分鐘後 firing | World 重啟後約 25 秒內全部重連（`loadtest -soak`，成功率 100%） |
| 殺一個 World（多 World） | 只有綁在它上面的玩家失去服務，其他 World 的玩家與擲骰延遲不變 | 重啟後不需重啟 Gate，約 45～60 秒內重連（Gate 退避最長 30 秒＋Central 冷卻 30 秒） |
| 停 Redis | 四個依賴 Redis 的服務 `/ready` 失敗；`GameRecoveryMismatchDetected` firing（10 分鐘窗口才消） | 數秒內 6/6 ready |
| 停 MySQL | 三個服務 `/ready` 失敗；`GameCircuitBreakerOpen` pending | 5 秒內 6/6 ready |
| 停 RabbitMQ | 服務仍 ready（`/ready` 不檢查 MQ）；`GameRecordMQDisconnected` pending（`for: 5m`，短於 5 分鐘不會響） | 還原後恢復 |
| Gate 與 World 之間的連線被切斷 | Gate 1～2 秒內重連；**不踢玩家**；切斷瞬間送出的指令失敗一次 | 自動 |
| 滾動優雅重啟 | Gate 重啟會中斷其上全部玩家（約 20 秒恢復）；World、Central 重啟不踢人；World 停機前寫回全部在線玩家，無寫回失敗 | — |
| 機器重開 | Docker Desktop 不會自動啟動；`sailor-ingest.sock` 刪不掉時把 `%LOCALAPPDATA%\Docker\run` 改名再重啟（不要刪、不要重設為出廠預設） | `scripts/dev-up.sh` 重拉服務 |

## 現行告警與調整（`monitoring/prometheus/alert-rules.yml`）

- `GameMemoryPressureHigh`：`heap_inuse / go_gc_gomemlimit_bytes > 0.85`（5 分鐘，未設 GOMEMLIMIT 的不納入）。舊的 `heap_inuse / next_gc` 比值在 GC 鋸齒下常態接近 1，閒置就誤報；曾改用固定 512MB，但各服務上限不同（128～512MB），小上限的服務會先 OOM 也不告警，所以改以軟上限比例判斷。
- `GameRecordMQDisconnected`：限縮為 `job="record"`；Record 消費端連線成功才把 `recordmq_connection_status` 設為 1。（另納入設定了 RabbitMQ（`recordmq_enabled == 1`）的 World 發布端，含啟動後尚未連上的情況；World 啟動連不上改為背景指數退避重試，連上後狀態自動恢復，見[指標面板](指標面板.md)與[RabbitMQ 發布可靠性](../00-導讀/RabbitMQ發布可靠性.md)。）
- `GameLoginCentralBusy`：5 分鐘內 `busy` 超過 10 次且持續 2 分鐘；它**不**抑制 `GameLoginAvailabilityLow`／`GameLoginFailureRatioHigh`（第十五輪 O-L8 起移除：Gate 把 busy 計成 `service_unavailable`，開服尖峰會多收到這兩封，但同時發生的真故障不會被壓掉）。
- `GameRecordQueueBacklog`：`recordmq_queue_messages{job="record"} > 10000`（5 分鐘）。指標由 Record 消費端每 15 秒以被動宣告取樣。
- `GameCircuitBreakerOpen`：改為 `min_over_time(circuit_breaker_state[2m]) >= 1` 且 `max_over_time(circuit_breaker_state[2m]) >= 2`（視窗內出現過 open）持續 1 分鐘（舊的 `== 2` 加 `for: 2m` 會被 half-open 試探重置計時而漏報）。
- 第六輪新增：`GameEventLoopStalled`（事件迴圈 tick 時間戳 30 秒不動，page）、`GameAccountPurgeStalled`（帳號清除 2 天未完整跑完）、`GameGrantItemDeadLettered`（GM 發道具死信，warning）、`Watchdog`（severity=info，路由 blackhole；要當死人開關需另接外部心跳）。登入失敗比例的失敗 regex 加入 `session_expired`，Gate 掃描到的 pending 逾時現在計入登入／登出指標。細節見[指標面板](指標面板.md)。
