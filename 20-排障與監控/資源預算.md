# 資源預算

這份表只做一件事：把常見資源的 owner 與上限寫清楚。
它不是附錄，是 state audit 之後的第二步：先確認有沒有 drift，再看是不是資源把系統推歪。

## 目的

- 出事時先知道誰負責
- 看圖時先知道哪條線算超標
- 新資源加入時有地方補註記

## 資源表

| 資源 | Owner | 上限 | 備註 |
|------|-------|------|------|
| CPU | 對應 service owner / 值班 | 持續 80%，短峰值 90% | 超過先看 handler p95、GC、queue backlog |
| Memory | 對應 service owner / 值班 | RSS 75%，接近 OOM 立即處理 | 優先看 cache、queue、未釋放物件 |
| `tcp_send_queue_depth` | `Gate` / `World` owner | 4096 | 超過會觸發 slow consumer 保護 |
| `game_event_queue_depth` | `Central` / `World` owner | 10000 | 超過代表事件處理已追不上 |
| DB pool | 對應 service owner | `max_open_conns` 的 80% 以下 | 若長期接近上限，先看 query latency 與鎖競爭 |

## 標註原則

1. 新增任何資源時，一律先填 owner
2. 一律要有可量化上限
3. 上限要對應 alert 或 dashboard panel
4. 不要只寫「看情況」

## 告警去重

同一類資源告警會用 `resource_class` 合併：

- `queue`
- `latency`
- `login`
- `logout`
- `recovery`
- `reconnect`
- `audit`

用途：

- 避免 `depth high`、`overflow`、`P95 high` 一起炸一堆通知
- 同一個 service + 同一個 class，只留一條通知線

## 健康檢查門檻

`tools/dephealth` 會用這份表的門檻判斷是否退化：

- `tcp_send_queue_depth >= 3000`

### 2026-05-30 — 第 5 波：packedMsg buffer 保留 + msgpool 全型別 Reset()

- `pkg/tcpsocket/packed_msg.go` — `Put()` 改 `payload = payload[:0]` 保留 backing array，
  消除每次 broadcast 的 heap 分配
- `pkg/msgpool/` — 全 13 個訊息型別補上 `Reset()`（含 slice field `[:0]` 保留 cap），
  移除 `NewMsgPool` 中運行期 `any(&sample).(Message)` 動態偵測
- 新增 `pkg/tcpsocket/sendpath_bench_test.go` 端到端 send pipeline benchmark
- `Makefile` 新增 `bench` target + 首次基準線存檔

### 2026-05-29 — 第 2 波：日誌 hash、Decoder pool、測試 HTTP Transport

- `pkg/logger/logger_sampling.go` — `hashKeyToUint64` 以 inline FNV-1a 取代 `fnv.New32a()`，
  消除 debug log 採樣路徑的 per-call heap 分配（`LOG_SAMPLE_RATE < 1.0` 時生效）
- `pkg/requestjournalredis/journal_load.go` — 新增 `pooledDecoder`（sync.Pool），
  重用 `bytes.Reader` 減少 journal cache miss 路徑的 Decoder + Reader 分配
- `integration/testenv/net.go` — 新增 `HTTPClient()` singleton，`MaxIdleConnsPerHost=100`，
  避免整合測試用 `http.DefaultTransport`（預設 2）造成的頻繁 TCP 重建
- 本次「SendAll msg.Pack() 分配」經評估後，部分解法（
  `packedMsg.Put()` 保留 buffer）於第 5 波實作
  因 `Msg` 介面無 `PackTo([]byte)` 方法，且 `packedMsg` 非同步 ref-count 生命週期
  原生無法安全歸還 pool buffer；折衷方案為保留 payload backing array
  (而非回傳 pool)，減少下次 broadcast 的重新分配

### 2026-05-29 — Sockets 鎖競爭改善

- `pkg/tcpsocket.Sockets` 自 `sync.RWMutex + map` 遷移至 `sync.Map`
- 消除 `SendAll`（RLock 迭代）與 `AddNew`/`Delete`（Lock 寫入）之間的鎖競爭
- `SendAll.Range` 使用 `sync.Map` 內部分區鎖，可與並發 `Store`/`Delete` 共存
- 移除 `activeKeys`/`activeIndex`（原用於 `Random()` O(1) 查詢），改為 `Range` 收集
- `SendByID` 保持 `idToKey` 反向索引 O(1) 快速路徑
- 影響：大量連線（>10k）場景下的 broadcast 延遲應顯著下降
- 回溯：若有 `sync.Map` 效能退化，可還原為分片 RWMutex（16~32 shards）
- `game_event_queue_depth >= 8000`
- `game_async_failure_total > 0`

意思是：

- 小幅 queue 波動不算退化
- 接近 alert 門檻時才在 daily check 先亮黃
- 真正的 budget 上限仍以本表與對應 alert 為準

## 排障順序

當 audit 已經指出是 `error`，或 `mismatch` 反覆出現時，先看這三項：

1. `tcp_send_queue_depth`
2. `game_event_queue_depth`
3. DB pool 使用率

這三個先爆，後面才會看到延遲、重試、session 抖動。
